# 已退役：双仓单向快照发布

> **不要再按本文执行任何发布动作。** 本文只解释发生了什么，以及遇到"发布到开源仓"这类请求时该怎么办。

## 为什么说它退役了

原机制：把内部仓（`EOS.dev`，私有）的阶段性成果按白名单裁剪后发布到公开仓（`EOS`），两仓**不共享 git 历史**，靠白名单 + 门禁扫描 + 人工复核推送保证不外泄。

**执行这套机制的资产已不存在**：

| 原引用 | 现状 |
|---|---|
| `scripts/publish-oss.ps1` | **已删除**（`chore: 删除已废弃的双仓发布脚本`，`428630d`） |
| `scripts/export-oss-seed.ps1` | **已删除**（同上提交） |
| `docs/oss-release/README.md` | **不存在** |
| `publish/`（发布产物目录） | **不存在** |

## 本仓现在的形态

- 定位为**面向全体开发者的单仓**：`AGENTS.md` 已入库（`docs: AGENTS.md 首次入库并梳理为面向全体开发者的通用指引`，`760774a`）；
- 许可与第三方声明**就地维护**：`LICENSE`、`THIRD-PARTY-NOTICES.md`；
- 仓库内**没有**任何可执行的发布脚本或发布配置。

## 原白名单条目一律失效

旧白名单曾规定"不发布 `EOS.Database` / `docs/plans/` / `ERP_REFACTOR_HANDOFF.md` / `AGENTS.md`"，
并要求清理代码注释里对 `docs/plans/`、`docs/decisions/ADR-` 的引用。

**这些条目随机制退役一并失效，不要拿来裁剪或改写任何内容。** 当前哪些目录纳入版本控制，以
`.git/info/exclude` 与其恢复副本 `.local-exclude.txt` 为准。

## 遇到"发布到开源仓"请求时的正确做法

**不要去找脚本，也不要凭 git 历史即兴重做一套发布流程**（历史里有已删除的实现，照抄等于复活一个被明确废弃的机制）。按下面两步走：

1. **先问用户**：发布机制是否已重建？
2. **按答复分派**：
   - **用户确认未重建** → 告知该机制已退役、本仓当前就是分发形态；不要执行任何动作；
   - **用户表示已重建** → 请用户指出**新的**脚本与文档位置，按新流程执行。**本文不维护流程细节，不要以本文为依据推断新流程。**
