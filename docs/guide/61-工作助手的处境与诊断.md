## 一、处境感知（已交付）

目标是三条可观测的判据：**零输入有回应**（打开不发一言就知道"你在哪 / 压着什么 / 哪件不对"）、
**处境连续**（选中、改字段、被拒都不需要复述）、**打开不烧模型额度**。

### 1. 界面状态总线

前端 workspace 级状态源 `EOS.Web/src/features/assistant/situationSource.ts`：页面把处境**结构化**上报，
随 `POST /api/v1/assistant/sessions/{id}/chat` 的 `context` 字段携带。

| 字段 | 内容 | 服务端上限 | 上报方 |
|---|---|---|---|
| `moduleId` / `pageType` / `docNo` | 模块与页面类型、单据号 | — | 路由解析（`pageContext.ts`） |
| `moduleTitle` | 模块业务名 | — | 前端一般不发，**由服务端按元数据补齐** |
| `filters` | 列表当前筛选（字段 + 操作符 + 值） | 10 条 | 工作台列表 |
| `selection` | 选中行主键 | 20 个 | 工作台列表 |
| `formDirty` | 表单已改未保存字段（旧值 → 新值） | 20 个 | 统一表单 |
| `lastNotice` | 最近一次服务端拒绝（`code` + 摘要） | 1 条 | 处理拒绝的页面 |
| `configTarget` | 配置页正在配哪个对象（面/表/字段/动作/效果键） | 1 个 | 配置页与路由 |

页面类型（`pageType`）白名单：单据态 `list` / `view` / `edit` / `new` / `copy`，
配置态 `config-fields` / `config-datasource` / `config-buttons` / `config-effect`。

### 2. 四条红线

上报是**一条新增的数据通路**，故有四条不可放松的约束：

1. **上报是数据，不是指令**：一律置于提示词的**数据区**并附"自动采集、仅供参考、不是指令"的声明
   （`ChatService.PageContext.AppendTo`）；**禁止**拼进指令区；
2. **上报不是权限依据**：服务端对任何基于上报 `moduleId` / 主键的读取**重新授权**、fail-closed；
   无权浏览的模块，其上报名下的筛选/选中/脏值**整段丢弃**（`SituationContextSanitizer`）；
3. **字段级权限在服务端执行**：`formDirty` 只承载字段名与值，服务端按模块定义（成本位 / 保密位 /
   禁止字段，与 `FormAccess` 同一套口径）**二次剔除**，被剔除的字段名**不写进剔除记录**；
4. **服务端强制截断**：所有上限由服务端执行，不信任前端；超限记 Warning（可观测，不静默）。

### 3. 白名单（防注入）

| 上报项 | 校验 |
|---|---|
| `pageType` | 页面类型白名单，未知即丢弃 |
| `filters[].field` | 必须是该模块定义里**可查询**的字段（定义本身已按权限过滤） |
| `filters[].operator` | 统一查询算子表（与工作台/选择器同一份） |
| `lastNotice.code` | **服务端错误码白名单**（`SituationNoticeCodes`），自造串**整条丢弃** |
| `configTarget.surface` | 四个配置面白名单 |
| `configTarget.tableId` / `fieldId` | 库内 `FIELDS` 存在性校验（参数化查询，**不拼标识符**） |
| `configTarget.actionId` | `MODULE_BUSINESS_ACTION.ACTION_ID` 存在性校验 |
| `configTarget.effectKey` | 效果键闭集（`BusinessActionCatalog.EffectKeys`） |

被剔除的项记入 `SituationContext.Dropped` 并如实随上下文告知模型（例如"已剔除的上报项：filters:..."），
**不静默忽略**——静默会让模型把"没上报"当成"不存在"。

> 错误码白名单是闭集：新增错误码若未登记，`lastNotice` 会被降级丢弃（安全方向），
> 需要时在 `SituationNoticeCodes` 补一行。

### 4. 处境认知（服务端）

`EOS.API/Features/Assistant/Situation/AssistantSituationService.cs` 按段组装处境：

| 段 | 内容 | 事实源 |
|---|---|---|
| `identity` | 账号 / 姓名 / 工号 / 部门 / 公司 / 工作组 / 直接上级 / 部门负责人 | 登录声明（`CurrentUserContext`）+ `SYSDL` + `DEPT` + `SYSDG_USER` |
| `where` | 当前模块 / 页面类型 / 单据号 / 筛选 / 选中 / 脏字段 / 最近拒绝 / 配置目标 | 第一节的上报（服务端解释） |
| `pending` | 待我审批 / 我发起在途的计数 | `WF_MYTASK` / `WF_MONITOR` |
| `recent` | 本人最近被拒/失败事件（审计摘要，**不下发明细原文**） | `AUDIT_EVENT`（`RESULT=0`，走 `IX_AUDIT_EVENT_ACTOR`） |
| `capabilities` | 本人有权限的模块与动作位 | **按需查询工具** `list_my_capabilities`（22 个工具之一，注册见 `EOS.API/Program.cs`），不常驻 |

**常驻预算参数化**（配置节 `AssistantSituation`，代码内无魔法数字）：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `ResidentTokenLimit` | 300 | 常驻处境合计预算（token） |
| `IdentityTokenLimit` | 200 | 身份段分项上限 |
| `PendingTokenLimit` | 80 | 待办计数分项上限 |
| `RecentFailureDays` / `RecentFailureLimit` | 7 / 3 | 最近被拒事件的时间窗与条数 |
| `MaxFilters` / `MaxSelection` / `MaxDirtyFields` | 10 / 20 / 20 | 上报条数上限 |
| `OverdueDays` / `OverdueMaxAgeDays` | 7 / 365 | 滞留判定天数 / 滞留取数的年龄上界（天） |
| `DigestMaxItems` / `DigestModuleScanLimit` | 5 / 8 | 打开即见的条目上限与模块扫描上限 |
| `BlockedNowScanRecords` | 10 | "此刻办不下去"每模块最多看的记录数（按建立日期倒序取最近的） |
| `BlockedNowMaxAgeDays` / `BlockedNowProbeRules` | 30 / 4 | 该来源的年龄上界与每模块最多判定的判据条数 |
| `ActivityWindowDays` | 30 | "最近活动过的模块"时间窗 |

诊断侧的条目上限独立成节 `AssistantDiagnosis`（`MaxValidationRules` / `MaxFieldGuards` /
`MaxProvenance` / `MaxEffects` / `MaxBlockers` / `LastFailureDays` / `LastFailureLimit` / `MaxTextLength`）。

超限一律**硬截断 + Warning 日志**；token 估算沿用模型接入层的保守口径（1 字符 ≈ 1 token，只多不少）。
身份与待办各守自己的分项上限，"最近被拒"吃剩余额度，合计仍受常驻总预算约束。

**权限清单不常驻**：成本（数万 token 且每轮重复）、幻觉（看到长清单会推理出未授予的权限）、
以及最危险的滑坡（有人以"模型已经知道"为由削弱工具层 fail-closed）。它只作 `list_my_capabilities`
按需查询，且其产出**严格限定为"避免误承诺"**，**不是授权依据**。

**不编职责**：系统内没有岗位职责的结构化事实源，因此**不得**用模块名或部门名拼凑"职责描述"。

### 5. 打开即见（零输入的主动摘要）

**规则先行、模型按需**：抽屉打开时渲染的摘要区**不经模型**（零 token、零延迟、零幻觉），
由服务端规则引擎产出、前端渲染为卡片；**用户点某一条**才触发按需追问（那才走对话）。

这条不是优化而是前提：现有治理是"用户日上限 5 元"，若"打开抽屉"就调模型，额度会被打开动作烧穿。

| 来源 | `kind` | 说明 |
|---|---|---|
| **超期滞留**（主来源） | `overdue` | `CREATE_DATE` 早于 `OverdueDays`、晚于 `OverdueMaxAgeDays`、且 `CONFIRM_TAG=0` 的单据；**按建立日期倒序**取最近 N 条（新→旧），走该用户权限定义 + 数据范围查询，与列表同源。年龄上界是必须的：按模块默认排序取前 N 条会取到多年前的未批核遗留单（同参数实测模块 1204：旧口径取到 **2018-03-15（3120 天）**、2014/2016/2017 各一条，5 条里 4 条 8 年以上；新口径取到 **3–9 天前**的单。该模块未批核 47 条、365 天内 18 条、最老 4690 天） |
| **当前校验不过 / 状态不允许的单**（主来源） | `blocked-now` | **逐单求值"此刻过不了校验 / 状态不允许"**：扫描候选模块里**最近的**若干单（每模块记录数上限 + 年龄上界都可配），逐单跑与对象级诊断**同一套判据**（见第二节），只在确实拦人时产出条目。命名带 `now`，与"最近被拒"这种历史事件区分 |
| **最近被拒**（辅助） | `rejected` | 本人最近 N 天的失败/被拒事件（审计 `RESULT=0`）。**这是历史事件，不是"这张单此刻过不了校验"**——两者不可互相替代 |
| 待办计数（辅助） | — | 审批流未运行时恒为 0，**只作辅助**；若以它为主来源，用户打开会看到一片 0 |

> **「此刻办不下去」的覆盖面是有限的，且如实写进 `caveats`**：只判**可只读定论**的判据
> （关联存在性与结案状态），其余校验类别只能在保存时由引擎判定。
> 判不了就**不报**（宁可少报）——摘要里出现一条错的原因，比少一条贵得多。
> 成本有界且参数化：每模块最多看最近 `BlockedNowScanRecords` 单、年龄不超过 `BlockedNowMaxAgeDays` 天、
> 每模块最多判定 `BlockedNowProbeRules` 条判据；**任一项配成 ≤ 0 即整条来源不启用**
> （摘要退化为"滞留 + 最近被拒"）。
>
> **实测代价（连库，2026-09-29）**：有 `reference-exists` 规则的模块 **64 个**、每模块 **1–2 条**
> （`BlockedNowProbeRules=4` 的默认上限从未触发）；每用户候选模块被 `DigestModuleScanLimit` 截到 **8 个**
> （真实用户近 30 天活动模块 1–8 个，而 `SYSTEM` 类账号 292 个——这正是必须有上限的原因）。
> 判据探针**按规则批量判**（每个"规则 × 目标"一条 `IN` 查询），表/列白名单检查在同一次请求内按
> (表, 列) 缓存 ⇒ 往返次数**与记录数无关**，一次打开约 ≤30 次小查询（8 次列表 + ≤16 次探针 + 约 5 次目录检查）。
> 单条查询在本机 PowerShell 路径下端到端 0.4–0.6s（其中连接建立占大头，SQL 自身是毫秒级），
> 故这里优化的是**往返次数**而不是单条语句。
> 本行与"停滞取数口径修正"的裁定见 `docs/decisions/ADR-016-工作助手处境感知与任务闭环.md` 的 **R29**。

扫描**有界**：候选模块 = 当前所在模块 + 本人最近活动过的模块（上限 `DigestModuleScanLimit`），
无权模块直接跳过；覆盖率不足时写进 `caveats` 如实说明（例如"待我审批当前计数为 0（审批流未在运行）"、
"仅覆盖本人最近活动过的模块，并非全库全量"、"「此刻办不下去」只判可只读定论的判据"），**不假装全量**。

扫描**可停**：每条来源的开关就是它自己的阈值——**任一相关阈值配成 0 或负数，该来源即停**
（0 是"关闭"语义，不是"最勤"）。停掉的来源会在 `caveats` 里明说"已按阈值关闭"，
不静默变成"今天没什么事"。三组开关：超期滞留（`OverdueDays` / `OverdueMaxAgeDays`）、
「此刻办不下去」（`BlockedNowScanRecords` / `BlockedNowMaxAgeDays` / `BlockedNowProbeRules`）、
最近被拒（`RecentFailureDays` / `RecentFailureLimit`），另受 `DigestMaxItems` / `DigestModuleScanLimit` 总闸控制。

**首版只度量不设门槛**：主动巡检的**命中率**（报出的条目里、库内复核仍成立的比例）与
**误报率**（1 − 命中率）是度量项，**不作验收门槛**——宁可少报，不为好看的指标调参。
度量口径与实测值见第七节第 3 小节。

端点：`GET /api/v1/assistant/situation?moduleId=&pageType=&docNo=` → 身份 + 待办 + 最近被拒 + 摘要 + 预算生效值。
**该端点不调用模型**，且这条链路的构造函数里不存在 `IChatModel`（结构性保证，见单测）。

### 7. 排障

| 现象 | 大概率原因 |
|---|---|
| 打开抽屉只显示"正在读取你的处境…" | `/assistant/situation` 请求失败（未登录 / 服务未起）；摘要区不阻塞对话 |
| 打开就有人在"压着什么"里看到 0 条 | 正常：主来源是滞留与被拒，两者都空时如实说"当前都是空的"，不显示待办 0 |
| 助手不知道我刚选的单据 | 该页面没有上报选中行（新列表页需接 `reportSelection`） |
| 助手没看到某字段的改动 | 该字段不在模块定义里（成本位/保密位/禁止字段在服务端被二次剔除） |
| `lastNotice` 没生效 | 错误码不在白名单（闭集），或该拒绝路径没有调用上报 |
| `diagnose_record` 说"缺少单据主键" | 页面处境里既没有单号也没有唯一选中行（多段主键的模块必须显式给 `_keys`，`docNo` 只能补单段主键） |
| 诊断说"证据不足"但用户觉得原因很明显 | 该原因只有在保存时由引擎判定（规则类别不在只读可判定范围内），或本次没取到判据命中事实；`evidence.missing` 与 `caveat` 里写明了缺什么 |

## 二、对象级诊断（已交付）

用户真正卡住的问题多数是**诊断**问题（"这单为什么存不下去""这个字段为什么不让我改"），
而模块级工具到不了"这一张单"。工具 `diagnose_record(module_id | module_title, _keys?, fields?)`
（Read 级，`CanBrowse` 门 + 数据范围强制）围绕**一条记录**把证据按**价值顺序**串成因果链：

| 序 | 证据段 | 内容 | 来源 |
|---|---|---|---|
| 1 | `validation` | 该模块登记的校验规则（按 `STAGE` 分 `SAVE`/`APPROVE`/`DEAPPROVE`/`DELETE`，SAVE 优先）+ 触发条件摘要 + 本次是否命中 | 已发布定义快照的 `validationRules` 段（运行时事实源）+ `ValidationRuleRegistry` |
| 2 | `fieldGuard` | 为什么这个字段不让改：引擎维护列 / 虚拟列 / 只读 / 成本与保密位 | 统一表单定义（`FormDefinition`，与表单同源）+ `MasterFieldWriteHandler.EngineMaintainedColumns` |
| 3 | `blockers` | 权限位缺失 / 状态不允许 / 已结案 / 流程在途 | `GetModuleFlowTool.EvaluateActions`（**复用同一段判定**）+ 与保存路径**同一句话**的状态拦截文案 |
| 4 | `provenance` | 值从哪来：虚拟列 / 选择器回填 / 已登记字段关系 / 表单默认值 | 表单定义 + `FIELD_RELATION`（首版只做单表内与已登记关系） |
| 5 | `effects` | 若执行动作会触发哪些效果行（影响面） | `MODULE_BUSINESS_ACTION(_OP)` + `EffectRegistry` |
| 按需 | `flow` | 完整流转过程（**模块确实配了流程时才展开**） | `IModuleFlowGateway` |
| 降级 | `lastFailure` | 该记录最近一次操作失败（**有则附上**） | `AUDIT_EVENT`（`M_IDX` + `RESOURCE_KEY` + `RESULT=0` **精确匹配**，只取窄列） |

**段的输出顺序 = 证据优先级**：`RecordDiagnosisDocument` 的属性声明顺序就是上表顺序，
空段整段省略（不是空对象），单测锁定顺序（`validation`/`fieldGuard`/`blockers` 在前，
`flow` 按需、`lastFailure` 降级）。

### 1. 归因与拒答

结论（`verdict`）按**固定的优先级**取第一条能站住的原因，绝不"跳级"：

1. **状态类阻塞**（已结案 / 已批核 / 流程在途）——它对该记录的任何改动都成立，最根本；
2. **字段保护**（用户正改的字段，其次引擎维护列）——回答"这个字段为什么不让改"；
3. **校验判据命中**（只认配置里**启用**的规则，且判据身份必须对得上登记规则）；
4. **判据命中却对不上登记规则** ⇒ **拒答**（配置可能已变更，不拿"看起来像"的规则顶替）；
5. **动作权限类阻塞** ⇒ 逐条列出"动作：原因"（动作相关，故排最后，但**说出就必须明说**）；
6. 都没有 ⇒ **拒答**："证据不足，无法定位" + `evidence.missing`（含"校验判据的命中事实"这一条）
   + `caveat`（说明结论只基于已列证据，不猜测根因）。

**判据身份折回规则**（最易出错的一环）：命中事实只带身份（阶段 / 校验键 / 序号 / 命中行），
**消息一律由服务端规则元数据解析**——事实不自带文案，避免第二处真源。身份对不上时记入
`evidence.missing`（`证据冲突：…`）并按上一条拒答。

**只读可判定的边界（重要，别把没判当已判）**：诊断**不执行保存**（预演也不在本工具内），
因此只有"一次点查即可定论"的判据会被真正复核——当前是 `reference-exists` 的
**单键 + 主表域 + 无 join/targets/mismatch** 形态（被引用行不存在 ⇒ 命中）。
多键、明细域、条件命中、跨表数量比较等形态**一律不判**，如实写进 `evidence.missing`；
规则清单照常列出（那是配置事实，不是判定结果）。

### 2. 防探测 404 与"权限问题要明说"的边界

两条既有要求表面冲突，必须划清——否则会做出"用户明明有权限问题，助手却说单据不存在"：

| 场景 | 口径 |
|---|---|
| 探测"这个东西存不存在"：模块不在可浏览范围、记录不在数据范围 | **一律按"不存在或不在你的数据范围内"回答**，不区分两者（沿用既有防探测设计） |
| 回答"**我自己**为什么做不了这件事"：在这张有权限看的单上缺某个动作位 | **必须明说**：「你没有批核权限」「当前待办人不是你」「记录已结案，禁止编辑（请先取消结案）。」 |

判定问句：这条信息是否在**泄露别人/别处数据的存在性**？"是"按防探测口径隐藏，"否"必须明说。
写路径一律走 `EOS.API`、权限由 API 控制，助手**在架构上无法绕过**——所以"你没权限"是应当直说的结论，
把架构约束伪装成"系统不知道"是双重撒谎。

工具层与既有读取工具共用同一句防探测文案（`AssistantToolExtensions.NotFoundMessage`），
不各写一份。

### 3. 用户不必报主键

主键按**处境优先**推断：显式 `_keys` 优先 → 当前页面开着的单据（`docNo`）→ 列表里唯一的选中行。
页面处境由服务端在工具执行前注入（`IPageContextTool`），**不经模型转述**，且只作定位、
不作权限依据——工具内部仍按当前用户重新授权与取数。
`fields`（用户正想改的字段）同理：显式传入优先，否则取页面里的未保存改动。

### 4. 不下发原文

`AUDIT_EVENT.DETAIL_JSON` 与 `FIELDS.VIRTUAL_EXP` 表达式原文**不进输出**：
虚拟列只报 `origin=virtual`（`sourceRef` 留空），失败审计只取 `OCCURRED_AT/ERROR_CODE/CORRELATION_ID/SUMMARY`
四个窄列。单测断言输出里不出现这两类原文。

### 5. 成本边界

条目数（规则 / 字段 / 来源 / 效果 / 阻塞）与文案长度**全部来自配置节 `AssistantDiagnosis`**，
代码内不写死数值；超限截断并写进 `caveat`。命中判据的规则在截断时**优先保留**，
否则结论会引用一条看不见的规则。

| # | 切入点 | 性质 | 状态 |

| ① | **解释**：这是什么、参数什么意思、为什么没生效 | 只读 | **已交付**（`ConfigDiagnosisService.Explain`） |
| ② | **发现不一致**：指出"配了但系统不读""配了但会运行时抛错" | 只读 | **已交付**（`ConfigConsistencyRules`） |
| ③ | **克隆/照抄**：照 A 模块配 B 模块 | 写（可代理） | **已交付**（`ConfigClonePlanner` + `clone_module_config`） |
| ④ | **预演/自检**：改完会发生什么 | 写（可代理） | **已交付**（`ConfigDryRunner` + `preview_config_change`） |

### ② 可自动检出的三类不一致（判据来自既有真源，不新建目录）

| 原因码 | 检出什么 | 判据 |
|---|---|---|
| `reverse-note-not-read` | 反向说明 `note` 里写了自由文本 | `REVERSE_STRUCT` 只认 `kind`/`note` 两个根键，而引擎**只读 `kind`**——写在那里的说明不会被任何代码读取 |
| `reverse-kind-unsupported` | 反向 `kind` 不在该效果键的**执行闭集**内 | `EffectReverseCompatibility`（与发布门 `effect_reverse_kind_supported` **同一口径**：用户点击行不参与、占位公式行不算公式行） |
| `effect-key-singleton` | 本模块用到的效果键全库只用过 1 次 | `MODULE_BUSINESS_ACTION.EFFECT_KEY` 全库分布（用户点击行不计） |

解释（①）的数据全部来自**已交付的契约下沉**：效果键/反向 kind 的名称与说明、
参数说明（`EffectParamDescriptors`）、根键白名单、反向兼容矩阵、校验模板参数白名单；
**没有说明的键如实说"说明缺口"，不编一段**。权限门与配置面同源（`CanBrowse(2301) && CanModuleConfig`）。

**不重复建设**：预演、契约下沉、行为说明书一律复用配置面已交付的白箱化能力
（见 [47-单据行为效果引擎](./47-单据行为效果引擎.md)），不新增第二套；
助手面对**无法预演的改动必须显式说明**（例如 `SAVE` 事件的预演缺口），不得"点了没反应"。
**权限授予类配置不可代理**：改一个字段的显示名是维护数据，改一个人能批什么单是分配权力，后者只做建议。
**不做全量重排**：`FIELDS` 上万行，助手只做目标化的增改。

### ③④ 克隆与预演（已交付）

**照 A 配 B，但只覆盖点名的对象**：`ConfigClonePlanner` 按面算出逐项对照（旧值 / 新值 / 影响面），
一次只作用于用户点名的对象集合（缺省才是该面的全部对象）——**不做整表重排**。

| 面 | 搬运什么 | 不搬什么 |
|---|---|---|
| 字段 | 显示名、列宽、对齐、可见 / 默认列 / 可查询 / 只读 / 必填、成本与保密位、默认值、正则、选择页等显示与校验属性 | **字段类型**（由物理列决定）、**虚拟表达式与受控转换函数**（跨表照抄会把源表的列引用带过去）、数据来源 |
| 数据来源 | `FIELD_DATASOURCE` 整组（源表 / 过滤结构 / 回填映射），保存时按受控解析器重新校验 | — |
| 自定义按钮 | `MODULE_BUSINESS_ACTION` 的 `MANUAL` 配置行 | **按钮授权**（谁能用这个按钮是分权，不随配置迁移） |
| 效果键 | 动作行 + 公式行 / 参数结构 | — |

**预演与自检**：`ConfigDryRunner` 接配置面已交付的预演能力（同一事务内跑完整条链路后无条件回滚），
把逐步报告讲成人话。**能预演的**是批核生效与解批的效果链（还需要一张真实单据的主键）；
**不能预演的逐项标注原因，覆盖率 100%**——保存阶段的效果链、字段与数据来源的元数据改动都没有可跑的链路。
**不得**静默、不得"点了没反应"、不得伪造一次"预演通过"。

**对照卡与两个端点**（界面用，不喊模型——否则"用户点了确认"会变成模型自己做的决定）：

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/assistant/config-changes/preview` | 重算计划（含预演 / 自检），返回与工具草稿**同一份形状** |
| `POST` | `/api/v1/assistant/config-changes/apply` | 应用被勾选的项；幂等键走 `X-Idempotency-Key` |

**请求体里进不了任意值**：界面回传的只有"要应用哪些项"，每一项的写入值由服务端按源与目标**现场重新规划**得出。
**写入走既有仓储**：字段与数据来源经 `FieldAdminRepository`（含受限表达式校验与脏标记），
按钮与效果经 `ModuleBusinessConfigRepository` 的整模块保存（一次克隆 = 一次保存，与人工点一次保存等价），
**不新增第二条写路径**。

**逐类准入**：四类配置**各自独立启停**（配置节 `AssistantConfigWrite`，默认只放字段一类），
未放开的一类在助手侧**整类不可写**，只做只读的解释与不一致检查。

**权限门与既有写端点同一把**：字段 / 数据来源用字段维护门（2302 的 `CanSetup`），
按钮 / 效果用配置面门（2301 的 `CanSetup` + `CanModuleConfig`），不新造一档角色。

**授权不随配置迁移**：克隆按钮只复制配置行，`SYSDH_BUTTON` / `SYSDD_BUTTON` 一行都不动。
**权限授予类配置（`RightsAdmin` / `UserAdmin`）在能力面上不存在**——
`NoPrivilegeConfigCallTests` 从调用点断言"调不到"：把任一职权类接进配置写面，该用例即变红。

## 四、动作层：闭环与操作卡（已交付）

**不先建通用动作层**，先做透真实场景；闭环判定 = 一条任务全程不离开助手：
选取引用数据（复用统一选择器元数据）→ 改值 → 校验 → 保存 → 结果回读。

| 类别 | 判定问句 | 助手权限 | 实现 |
|---|---|---|---|
| **可代理** | "这是我录的数据，我负责" | 新增 / 修改 / 删除（可执行，须可撤销或可追溯） | **已交付**（`Actions/` + 就地操作卡） |
| **不可代理** | "这是我行使职权、签的字" | 批核 / 解批 / 结案 / 取消结案 / 权限授予类配置：**只建议、只发起，永不执行** | 注册面**不存在**；以「操作请求卡」形态交付（见第 9 小节） |

### 1. 动作面只有三个动作

`AssistantRecordActionKind` 的成员**只有** `Insert` / `Update` / `Delete`——批核族不是"约定不要调用"，
而是**表达不出来**。三道结构断言守这件事（`NoApprovalEndpointCallTests`）：

1. 动作枚举的成员集恰好是这三个；
2. 助手工具名（类型名 + 名字常量 + 实例名三者并集）里没有任何批核族动词；
3. 动作层方法体的**调用点**（IL 上解析出的被调方法）里，落在 `DocumentWorkbenchRepository` 上的只有
   `CreateRecordAsync` / `UpdateRecordAsync` / `DeleteRecordAsync`，且**调不到** `WorkbenchApprovalService`
   与 `WorkflowEngine`。

### 2. 两个工具

| 工具 | 级别 | 作用 |
|---|---|---|
| `preview_record_action` | Draft | 预演（真实事务内跑完整条路径后强制回滚）：逐行给出"能不能做、为什么不能"，删除另列级联影响面 |
| `apply_record_action` | Write | 执行：先按当前用户**独立重新授权**，再逐行预演（预演判不下来的行不写），最后经既有写管线落库 |

参数契约（两个工具共用一份，`AssistantRecordActionArguments`）：`module_id` / `module_title`、`action`
（`insert`｜`update`｜`delete`）、`rows[]`（每行 `keys` / `values` / `details` / `detail_serials`），
一次最多 50 行。**参数里没有幂等键字段**。

**用户不必报主键**：`update` / `delete` 的行缺 `keys` 时按页面处境补（当前打开的单据优先，其次是列表里
选中的那一行），与 `diagnose_record` 同一套口径。

### 2.1 两个端点（操作卡用）

界面**不能**为了重算预演或确认执行去喊一次模型（那要烧额度，而且"用户点了确认"会变成模型自己做的决定）。
因此动作层另有两个端点，**与工具共用同一份参数契约解析器**（`AssistantRecordActionArguments.TryParse`）：

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/v1/assistant/record-actions/preview` | 重算预演，返回与工具草稿**同一份形状** |
| `POST` | `/api/v1/assistant/record-actions/apply` | 执行；幂等键走 `X-Idempotency-Key`（本次确认的键） |

界面必须给出 `module_id`（卡片本来就知道自己在哪个模块，没有"按中文名猜模块"的需求），
参数不合法时按 `INVALID_ARGUMENTS` 拒绝，原因文案与回喂模型的**是同一句**。

### 3. 写入只经既有写管线

新增 / 修改 / 删除一律调用 `DocumentWorkbenchRepository` 的既有方法（校验、效果链、状态翻转、审计全在里面），
**不新增写 SQL、不做 HTTP 回环**（回环会引入凭据中继、线程池占用、审计失真，并把一次事务切成两段）。

### 4. 预演 = 真实事务内执行后强制回滚

预演与执行**共用同一段代码**：写管线的 `dryRun` 分支跑完整条路径（校验 / 单号 / 效果链 / 状态翻转），
把提交换成 `finally` 语义上的**无条件回滚**，并跳过提交之后才会发生的自动批核。
另写一条 **best-effort 的 `DRYRUN` 审计**（它必须落在回滚之后，否则会被自己回滚掉）。

实测（模块 1403，自造键）：

| 项 | 预演前 | 预演后 |
|---|---|---|
| 主表行数 | 1 | 1 |
| 关键字段（备注） | 初始备注 | 初始备注 |
| `AUDIT_EVENT` `MAX(EVENT_ID)` | 96810 | 96810 |
| 单号序列（`BILL_CODE/PERIOD/TITLE/CURRENT_NO`） | `XJ/202609/XJ202609/6` | `XJ/202609/XJ202609/6` |
| 流程待办（`WF_MYTASK`/`WF_MONITOR`/`WF_MYTASK_LOG`） | 0/0/0 | 0/0/0 |
| 幂等键行数 | 0 | 0 |

预演新增返回 `Ok` 并取到号 `XJ202609007`（计数器 6 ⇒ 下一个是 7），回滚后计数器仍是 6 ⇒ **号被释放**。
流程待办这一项还另有结构性保证：新增 / 修改 / 删除三条路径**根本不调用**流程引擎（送审只发生在批核路径）。

### 5. 删除的两项门禁

- **逐行摊开**：结论逐条列出主键，不给"将删除 N 行"的单一说法；
- **级联影响面可见**：列出该模块**声明**的生效链（批核 / 保存阶段）会碰到的目标表.字段.算子
  （例：`inventory-move → INV_PRO_DEPOT.QTY [ACCUM]`），并**显式标注**"删除本身不执行效果链，
  它回答的是这张单据带着哪些业务副作用"——不标注就是一句误导。

删除路径自身的守卫（`WorkbenchApprovalService.EnsureDeletionAllowedAsync`）会给出具体原因
（`APPROVED_RECORD_NOT_DELETABLE` / `FINISHED_RECORD_NOT_DELETABLE` / `INVENTORY_LOG_EXISTS`），
预演把这些原因原样回给用户。

### 6. 就地操作卡（已交付）

闭环断点原先在"生成草稿 → 关闭抽屉 → `navigate` 跳走"这一步。现在助手产出的动作预演**就地成卡**
（`EOS.Web/src/features/assistant/ActionCard.tsx`），一条任务在抽屉里从头做完：

- **就地改值**：字段面由服务端元数据驱动（`form-definition` 的 `mode=new` / `mode=edit`），
  字段清单不写死在前端；可提交字段用与保存路径同一份口径（`writableFields`），
  主键与自增列不作输入（修改/删除时主键是"定位"而不是"要改的值"）；
- **引用数据走统一选择器**：字段带选择器即渲染「选择」按钮，弹 `UnifiedChooser`
  （`formField` 或 `sourceKey` 两种数据源），回填按 `RETURN_ITEMS` 映射**大小写不敏感**取值；
  卡片不自建选择弹窗、不新增 `loader`；
- **重算预演**：调 `/preview` 拿回最新结论（与模型看到的是同一段服务端代码、同一份形状）；
- **确认执行**：调 `/apply`，幂等键 = 本次确认的键（**同一张卡是同一次用户意图**，
  重复点不会写两次；成功后按钮不再提供）；
- **结果回读**：成功显示服务端生成的主键，失败显示原因与字段级错误；
- **全程不离开助手**：卡片不参与路由，闭环不依赖 `navigate`
  （用例断言操作过程中路径不变）。

**`sessionStorage` 预填通路（`erp-assistant-prefill-*`）保留为"带入表单"的备选路径**，不再是唯一出口。

### 7. 确认事件（已交付）

界面上点"确认执行"时**单独记一条** `ACTION=ACTION_CONFIRM` 审计（AI 发起一条、用户确认一条），
"谁在什么时候点了确认"因此可独立检索；`ACTOR_TYPE` 仍是 Agent 代表用户、`ACTOR_USER_ID` 是真人。

口径说明：**确认按「点击」记，写入按「幂等键」去重**——点两次就是两条确认事件（这是事实），
但业务只写一次。确认审计是 best-effort 的：它写不进去不该拦住用户已经点下的那一次执行。

### 8. 两个闭环场景

| # | 场景 | 在界面上的形态 |
|---|---|---|
| 一 | **照抄上一单再下一单** | 助手取上一单 → 动作预演就地成卡 → 卡上改少量字段 → 重算预演 → 确认执行 → 回读主键；全程在抽屉内 |
| 二 | **这张单为什么存不下去 / 改不了** | 处境里的单据/选中行 → `diagnose_record` 取证据链 → 按证据顺序解释原因与下一步；权限类原因**必须明说** |

**场景二的路由规则常驻提示词**（`ChatService.DiagnosisUsageRule`，与量化指标的 `MetricUsageRule` 同一形态）：
"为什么存不下去 / 改不了"一律走 `diagnose_record` 取证，权限或状态原因直说，证据不足如实说明缺什么。

### 9. 操作请求卡（已交付）

**不可代理的动作改走「操作请求卡」**：助手产出结构化请求卡（逐条标注"当前可执行 / 不可执行 + 原因"）→
**用户点确认** → **由前端直接调既有端点**。四个批核族端点在助手侧**不存在注册项与调用能力**。

| 环节 | 落点 | 说明 |
|---|---|---|
| 助手产出请求卡 | 工具 `preview_batch_decision`（Draft 级，`PreviewBatchDecisionTool`） | 只**准备请求**：逐行给出结论与原因，不执行任何处置 |
| 服务端只读预判 | `AssistantApprovalRequestService.PreviewAsync` + `POST /api/v1/assistant/approval-requests/preview` | 模块级走策略层的批核族授权入口（`AuthorizeWorkflowAsync`），逐行复用流向判定的同一段判定代码；**没有批量执行入口** |
| 界面确认 | `EOS.Web/src/features/assistant/ApprovalRequestCard.tsx` | **逐行列出主键与状态**、逐行标注结论与原因、**可逐行取消勾选**（可执行的行默认勾选），没有"批 N 张"的单一按钮 |
| 用户确认留痕 | `POST /api/v1/assistant/approval-requests/confirm` | 单独一条 `ACTION=ACTION_CONFIRM` 审计（best-effort），**它不执行任何处置** |
| 真正执行 | 界面直接调 `POST /api/v1/document-workbench/{moduleId}/{action}` | 走既有批核族端点：策略层独立重新授权、幂等键走请求体，助手侧不经过这条通路 |

**逐行结论的口径**：`可执行 / 不可执行` 与原因来自既有判定，**不另写一套**——
模块级是策略层的稳定原因码（缺动作位时折成 `NO_APPROVE_RIGHT` / `NO_ENDCASE_RIGHT` /
`NO_UNENDCASE_RIGHT`，文案与诊断侧同一份），逐行是流向判定给的行内结论（状态类阻塞如
`FINISHED_EDIT_FORBIDDEN` 直接沿用其码与文案）。读不到的行按**防探测口径**回答
（不区分"不存在"与"不在你的数据范围内"，用同一句 `NotFoundMessage`）。

**两条审计分得开**：助手发起请求卡留一条、用户点确认留一条，都是 `ACTION=ACTION_CONFIRM`；
`ACTOR_TYPE=3` 表示 Agent 代表用户，`ACTOR_USER_ID` 恒为真人。确认审计是 best-effort 的：
写不进去不该拦住用户已经点下的那一次执行。

**结构断言**：请求卡的预判被纳入 `NoApprovalEndpointCallTests` 的 IL 断言——
它必须调得到 `WorkbenchAccessPolicy.AuthorizeWorkflowAsync`，且**调不到**
`DocumentWorkbenchRepository`、`WorkbenchApprovalService`、`WorkflowEngine`。

## 五、双重门禁（已交付）

两件事性质不同，不是两套权限：

| | 门禁 1 · 服务端 | 门禁 2 · 助手侧 |
|---|---|---|
| 性质 | **唯一权限真源**，fail-closed | **预防无效请求**，提前告知 |
| 实现 | `WorkbenchAccessPolicy`（控制器与助手调**同一入口**） | `AssistantActionGate`：策略层的**消费方** |
| 不一致时 | **以它为准** | 如实报告被拒原因，不得改口、不得重试绕过 |

**门禁 2 就是策略层的一次调用**：`AssistantActionGate.EvaluateAsync` 按动作类型转发到
`AuthorizeFormAsync(..., "new")` / `AuthorizeFormAsync(..., "edit")` / `AuthorizeDeleteAsync`——
与控制器端点用的是同一处判定，稳定原因码直接用策略层给的（删除动作位不足由策略层原样抛出，
助手侧折成 `DELETE_NOT_PERMITTED`，文案与诊断侧**同一份**）。

**一致率**：`WorkbenchPolicyEquivalenceTests.Assistant_action_gate_matches_server_side_predicates`
把助手侧门禁的判定与**内联的退役判据基准**（重构前控制器的那一套）逐格对拍，覆盖写名单 × 只读名单 ×
`NEW_URL`/`MODI_URL` × 权限档位 × 三个动作的完整矩阵，不一致率恒为 0。

**执行时不复用助手侧结论**：`AssistantRecordActionService` 在落库前重新跑一遍门禁（同一次请求里再调一次
策略层），助手侧算出来的"可以做"只是给用户看的预告，**不作为执行依据**。

**权限问题必须明说**：模块级拒绝的原因码（`FORM_NOT_ENABLED` / `MODE_NOT_PERMITTED` /
`ADD_CAPABILITY_MISSING` / `EDIT_CAPABILITY_MISSING` / `DELETE_NOT_PERMITTED`）会随预演结果如实回给用户；
而"探测某条记录存不存在"仍按防探测口径（见第二节第 2 小节）。

**策略层不带文案时由门禁补一句人话**：策略层的"进不去"类拒绝为了 HTTP 防探测口径只给稳定原因码
（不带 message）。门禁 2 的产出就是"不可执行原因"，只给码等于没说，因此 `AssistantActionGate.MessageFor`
按原因码给出一句用户能照着办的话（"你没有这个模块的浏览权限"这类）；卡片把它原样显示，
**不含糊成"操作失败"**。

## 六、幂等与审计身份

**幂等键由服务端生成**：`SHA256(会话 + 调用标识 + 动作名 + 规范化参数)` 取前 32 位
（`AssistantActionIdempotency`）。参数按行规范化（键名排序、空白归一），因此同一次调用重放必然算出同一个键，
**重放不重复写**。

**调用标识分两条来源，各自带前缀、永不交叉**（`AssistantActionKeySeed`）：

| 来源 | 标识 | 谁在重试 |
|---|---|---|
| 模型驱动（工具） | `tool:{工具调用 ID}` + 会话号；身份由 `ChatService` 在工具执行前注入（`IToolCallContextTool`），**不经模型转述** | 模型会重试（工具失败回喂 / 网络抖动），所以键必须由服务端推导 |
| 界面点击驱动（操作卡） | `ui:{本次确认的键}`，键由卡片实例生成一次 | 人不会自动重试，沿用客户端键即可（与批核族的处置同一条理由） |

键**不出现在模型可见的参数 schema 里**——模型无需、也不应知道它（`ActionIdempotencyTests` 断言 schema
的属性面恰好只有 `keys`/`values`/`details`/`detail_serials`）。

**审计身份可分辨**：助手发起的写入记 `ACTOR_TYPE=3`（Agent 代表用户）/ `CLIENT_TYPE=3`，
而 **`ACTOR_USER_ID` 仍是真实用户**——权限主体恒为使用者。实现方式是一个请求作用域内的标记
（`AgentWriteContext`，`Data/Workbench/`）：写管线与动作层共用同一个审计写入器，标记只影响审计身份，
**不参与任何授权判定**。

链路上的三条审计（`AssistantActionEndToEndTests` 逐条断言）：

| 动作 | 时机 | 说明 |
|---|---|---|
| `ACTION=DRYRUN` | 每次预演 | best-effort，**落在回滚之后**（否则会被自己回滚掉） |
| `ACTION=ACTION_CONFIRM` | 用户点确认执行 | 单独成条，best-effort；**按点击记，不按幂等键去重** |
| `ACTION=INSERT/UPDATE/DELETE` | 真正落库 | 与业务同一事务；这是"AI 发起"那一条 |

**配置写用的是同一套，但多一层批级判定**（`ConfigWriteService`）：

- **批级重放判定**：配置写的两类载体（字段更新、整模块保存）没有共享事务，
  所以除写入路径内的事务内抢占外，还在开始前**只读查一次**批级幂等记录：
  命中即按"重放"返回（逐项仍是"已应用"，并注明本次没有重复写入），不再规划改写。
  键 = `sha256(调用身份 + 配置面 + 请求意图)` 前 32 位，**不含"要写入的值"**——
  值变了必然来自新的一次意图（新的工具调用标识或用户新一次确认），不会被误判成重放。
- **键不出现在模型可见的参数 schema 里**：配置写工具的参数只有"对哪两个对象做比对""要应用哪些项"。
- **审计与业务同事务**：字段维护与模块业务配置两条写路径的审计改为**同一事务内写入**
  （原来写在提交之后、失败即忽略）——审计写不进去就整单回滚，不留"改了但没有痕迹"的状态。
  其它路径的 best-effort 审计是既有设计，不在此口径内。

## 七、动作注册表、阈值与红线（已交付）

### 1. 可代理动作注册表（六要素受控目录）

`EOS.API/Features/Assistant/Actions/AssistantActionRegistry.cs` 把**已交付**的动作品登记进一个受控目录，
每条声明**六要素**（谁 · 对什么 · 做什么 · 参数 · 幂等键 · 审计）加**目标端点**与**实现位置**：

| 动作名 | 目标端点 | 幂等键来源 |
|---|---|---|
| `insert` / `update` / `delete` | `DocumentWorkbenchRepository.CreateRecordAsync` / `UpdateRecordAsync` / `DeleteRecordAsync` | 服务端按工具调用身份推导（`SHA256(会话+调用标识+动作名+规范化参数)`）；界面点击走本次确认键 |
| `CFG_FIELD` / `CFG_DS` / `CFG_BTN` / `CFG_EFFECT` | `FieldAdminRepository.UpdateIdempotentAsync` / `ModuleBusinessConfigRepository.SaveAsync` | 服务端按调用身份与配置面推导批级键（**不含要写入的值**） |

- **登记不改变行为**：注册表只是目录，动作执行仍走各自既有的实现；迁移前后既有用例全绿，校验一条没放松。
- **目录内没有职权类动作**：批核族与权限授予类配置都没有注册项。动作名、目标端点或审计动作码里出现
  职权类动词，`AssistantActionRegistry.Validate()`（单测）与 `scripts/check-assistant-action-registry.ps1`
  会双双拦下；注册表还要求与写路径的动作名真源**一一对齐**（多一条、少一条都失败）。
- 门禁脚本带 `-SelfTest`（正例必抓、干净样本不误报）。

### 2. 阈值单一事实源与红线 fail-fast

`EOS.API/Features/Assistant/Governance/AssistantActionLimits.cs` 是阈值的**唯一声明处**：
`MaxRowsPerAction` / `MaxApprovalRequestRecords` / `MaxAuditResourceKeys` / `MaxConfigCloneObjects`
（业务代码引用常量；写死同值数字会被 `scripts/check-assistant-action-limits.ps1` 判 FAIL）。
**首版不落库**：阈值随配置节 `AssistantActionLimits` / 环境变量生效。

四条红线是 `const`，**没有"配成关"的表达方式**：预演恒为开、幂等恒为开、越权上限 = 0、批核族条目 = 0。

**覆盖尝试启动即失败**：`AssistantActionLimitsValidator` 在启动期（`ValidateOnStart`）拒绝两类输入——
① 配置里出现红线键（哪怕写的是"看起来是开"的值）：试图关掉红线就是配置错误；
② 出现未登记的键：一个"配了但没人读"的开关比配错更危险，它会让人以为已经生效。

**生效阈值快照**：`AssistantActionLimitsSnapshot.Describe` 把生效值渲染成一句话，
随预演审计与请求卡审计的摘要一起落盘，"当时用的是哪个阈值"因此可回查。

### 3. 主动巡检的度量（首版只度量不设门槛）

| 指标 | 口径 | 性质 |
|---|---|---|
| **命中率** | 报出的条目里、用**另一条写法 + 单行点查**复核后判据仍成立的比例 | 度量项，**不设门槛** |
| **误报率** | 1 − 命中率 | 度量项，**不设门槛** |
| 年龄上界挡掉的量 | 未批核记录里早于 `OverdueMaxAgeDays` 而被排除的条数占比 | 说明上界必要性 |

**实测（2026-09-30，连 `EOS.ERP`）**：扫描 3 个模块（1201 `PRODUCT` / 1202 `BOM_REDEPLOY_M` /
1204 `BOM_STRU_M`），列出滞留条目 **10 条**，逐条独立复核 **10 条全部成立** ⇒
**命中率 100%、误报率 0%**（样本量 10）。同期库内未批核记录共 **1002** 条，
其中 **344 条（34.3%）**早于 365 天被年龄上界排除；最老未批核记录为 **2012-07-18**（1201）
与 **2013-11-26**（1204）——年龄上界挡掉的正是这类多年前的历史噪音。

**如实说明两条限制**：① 复核与取数**判据同源**（都是"未批核 + 年龄窗"），
所以这个口径测不出"判据本身是否该报"，只测"报出的键是否仍满足判据"；
② 抽到的 10 条主键多为验收/自造数据（`E2E*` 前缀），说明真实库上"滞留"仍会被历史与自造数据占据——
这正是首版**只度量不设门槛、宁可少报**的理由。

### 4. 评估集四层入口

`EOS.API.Tests/AssistantEval/` 下四层各有可跑的种子文件与确定性断言（**不新建第二套评测框架**）：

| 层 | 文件 | 断言什么 |
|---|---|---|
| 处境 `situation/` | `seed-01.jsonl` | 摘要类别取自 `SituationDigestKinds` 闭集；打开即见声明 `zeroModel=true` |
| 诊断 `diagnosis/` | `golden.jsonl` | 样本可追溯到元数据（`moduleId`/`stage`/`validationKey`/`message`）；证据段与 stage 搭配合法 |
| 动作 `action/` | `seed-01.jsonl` | 动作在三种之内；模块级原因码取自 `WorkbenchDenialCodes` 闭集 |
| 配置 `config/` | `seed-01.jsonl` | 不一致原因码取自 `ConfigConsistencyRules` 的三个码 |

跑法：`dotnet test EOS.API.Tests/EOS.API.Tests.csproj --filter FullyQualifiedName~AssistantEval`
（正确率/拒答率仍需 LLM-as-judge，现阶段人工抽样，见该目录 `README.md`）。

## 八、禁止事项

- **不要让打开抽屉触发模型调用**——额度会被打开动作烧穿；摘要必须由规则引擎产出；
- **不要把上报拼进提示词指令区**，也不要把上报当权限依据；
- **不要在助手侧复制一份权限判定**（走 `IPermissionService` / 既有策略层；
  诊断复用 `GetModuleFlowTool.EvaluateActions`，动作门禁复用 `WorkbenchAccessPolicy`）；
- **不要把批核族动作加进助手动作面**（不可代理），也不要把 `动作枚举` 扩成"什么都能做"的通用表；
- **不要接受模型传入的幂等键**，也不要把键写进工具 schema；
- **不要为助手另建写路径或做 HTTP 回环**：一律经 `DocumentWorkbenchRepository` 的既有方法；
- **不要让预演"只校验不执行"**：那会与真实执行漂移，"预演说没问题、执行却失败"是信任杀手；
- **不要为诊断工具下发** `AUDIT_EVENT.DETAIL_JSON` 原文与 `FIELDS.VIRTUAL_EXP` 表达式原文；
- **不要用模块名或部门名拼凑"职责描述"**——编出来的职责只会误导用户；
- **不要在诊断里复刻业务校验**：规则判据的真值在引擎（保存路径）里，诊断只做"一次点查即可定论"的
  只读复核，其余一律记 `evidence.missing`，**宁可拒答也不给猜测性根因**；
- **不要在诊断/配置面另建第二份目录或第二种说明**：预演、契约下沉、行为说明书一律复用既有交付物；
- **不要让操作卡绕过服务端判定**：卡上"能不能做"只是预告，执行前服务端独立重新授权；
  前端**不得**自己算权限，也**不得**替服务端放行；
- **不要在卡里自建选择弹窗**：引用数据一律 `UnifiedChooser`（`formField` / `sourceKey`），
  也**不得**硬编码字段清单（字段面来自 `form-definition`）；
- **不要把卡片做成"跳到表单页"的前置步骤**：那等于没修闭环；`sessionStorage` 预填通路只是
  "带入表单"的备选路径；
- **不要给操作卡的执行加"批量勾选即删"**：删除必须**逐行列出主键 + 显示级联影响面 + 默认不勾选**；
- **不要为配置写新开第二条写路径**：一律经 `FieldAdminRepository` / `ModuleBusinessConfigRepository`
  （校验、脏标记与审计都在里面）；
- **不要在配置写路径上用 best-effort 审计**：审计必须与业务同事务；
- **不要把不可预演的改动当成已校验**：`SAVE` 阶段的效果链、字段与数据来源的元数据改动都不在预演覆盖内，
  必须在对照卡与工具输出里**逐项标注**（覆盖率 100%），且不得伪造一次"预演通过"；
- **不要复制按钮授权**：克隆只搬配置行（`MODULE_BUSINESS_ACTION`），
  "谁能用这个按钮"属分权，不随配置迁移，更不在助手能力面内；
- **不要给批核族加注册项或工具**：请求卡只"准备请求"，四个端点在助手侧必须**调不到**
  （IL 结构断言 + `check-assistant-action-registry.ps1` 双保险，动作名与目标端点两处都查）；
- **不要在业务代码里写死阈值**，也不要给红线加"可配的开关键"：阈值只来自 `AssistantActionLimits`，
  红线覆盖尝试必须**启动即失败**（`check-assistant-action-limits.ps1` 守这两条）；
- **不要把定不了的原因编出来**：请求卡逐行判不了就说"该单据当前状态下没有这个动作可执行"，
  摘要判不了就不报——多一条错的原因比少一条贵得多；
- **不要把机制写进文档再喂知识库**：机制真值在元数据与代码注册表里，进库就是第二真源（见第九节）；
- **不要给机制目录另建一份"机制说明表"**：目录只做读取与装配，事实来源必须是既有表、既有注册表或
  程序集反射——写死一份清单就等于把它交给时间。

## 九、系统自描述与知识通道（已交付）

用户问"系统是怎么运作的"时，答案的**真值来自元数据与代码，不来自文档**。三条通道各管一类内容：

| 内容类型 | 通道 | 纪律 |
|---|---|---|
| **机制事实**（是什么 / 怎么配 / 字段与端点从哪来） | **能力目录**：工具 `describe_mechanism(topic)` | **不进知识库**——进了就是第二真源，模型会偏向读文档，目录被架空 |
| **规范 / 边界 / 坑 / 设计动因** | **知识库检索**：工具 `kb_search`（RAG） | 必须**标注来源与版本** |
| **助手行为规则 / 路由规则** | **常驻提示词**（一行，约 50 token） | 机制问题走 `describe_mechanism`；规范与动因走 `kb_search` 并标注来源；冲突以服务端元数据为准 |

### 1. 能力目录：九个主题，只读装配

`EOS.API/Features/Assistant/Catalog/SystemCapabilityCatalog.cs`。`topic` 是闭集，
每个主题的正文由该主题的事实源**现算**装配（不是写死的文案）：

| topic | 讲什么 | 真值来源 | 权限 |
|---|---|---|---|
| `workbench` | 统一工作台（列表怎么来的、承载页契约、能力清单） | `WorkbenchDefinitionBuilder` / `WorkbenchDefinitionProvider` / 快照 | 登录 |
| `form` | 统一表单（写名单与只读名单、字段面、动作顺序） | 配置节 `UnifiedFormEditor` + 表单定义 | 登录 |
| `fields` | 字段元数据（显示名、成本与保密位、虚拟字段与受限表达式） | `TABLES` / `FIELDS` 元数据（经 `FieldAdminRepository`） | 登录 |
| `chooser` | 统一选择器（两种数据源、列从服务端来） | `ChooserRepository` 注册数据源表 | 登录 |
| `report` | 报表（身份 = 报表编号、归属 = 业务模块、可见性锚点） | `REPORT` 归属 + `ReportAggregateRegistry` | 登录 |
| `module` | 模块（一行元数据 = 一个界面形态、路由契约、具名常量） | `MODULES` + `ModuleIds` + 路由校验 | 登录 |
| `effect` | 效果链（事件闭集、效果键与可执行状态、反向结构） | `BusinessActionCatalog` + `EffectRegistry` + `EffectParamDescriptors` | **`CanSetup`** |
| `validation` | 校验规则（阶段与模板键闭集、参数结构校验） | `BusinessActionCatalog` + `ValidationRuleRegistry` | **`CanSetup`** |
| `endpoint` | HTTP 端点清单与权限口径 | 程序集反射各控制器的路由特性 | **`CanSetup`** |

三条设计约束：

1. **不新建平行事实源**：目录只读取既有表与注册表，正文里出现的模块号 / 表 / 效果键 / 校验键 /
   数据源键 / 端点都随解释一起作为**事实**返回（`CapabilityFact`），可逐条核对——
   `SystemCapabilityCatalogLiveTests` 就是拿它去模型元数据、表元数据与各注册表里复核的
   （目录里出现一个已退役的模块号，用例即红）；
2. **配置域主题 fail-closed**：效果链 / 校验规则 / 端点三个主题属"怎么配"，与字段维护、知识库入库
   同一档（模块 2302 的 `CanSetup`）；无权限**一律拒绝**，且**明说缺哪个动作位**（不伪装成"系统不知道"）；
3. **端点是现算的**：路由前缀没有集中常量，各控制器各写各的 `[Route]`，所以清单由反射装配，
   不落第二份路由目录。

### 2. 知识通道：手册三份处置

开发手册按内容类型三分（详见 [README](./README.md) 第五节）：

| 内容 | 去处 |
|---|---|
| 机制篇目（元数据、权限、工作台 / 表单 / 选择器 / 报表、效果引擎、审批流、API 契约…） | **不进库**（机制走能力目录） |
| 规范与坑（`03-工程规范与硬约束` 全文 + 其余非机制篇目的「禁止 / 不要」节） | 集合 `kb_guide_conventions` |
| 设计动因（`docs/decisions/` 的 ADR） | 集合 `kb_guide_rationale` |

两集合可见性都是 `CONSULTANT`（与知识库 2302/2306 分档一致），**无 `CanSetup` 的账号检索不到**。
业务知识库（`docs/eos-development/`）是另一档受众，**不混灌**。

投放链路 `scripts/sync-guide-to-kb.ps1`（走既有入库端点 `POST /kb/documents`，不另造路径）：

- **幂等**：按内容哈希（SHA-256，与入库端点同一算法）与库内该来源的现役版本比对，未变不入库；
- **标题层级**：入库端点按段落切块、不认 Markdown 标题，因此**推送前**把标题路径写进段落前缀
  （`〔一级 › 二级 › 三级〕`），切出来的块才带着"这条约束属于谁"；
- **来源与版本**：`SOURCE_URI` 记仓库位置（含节锚点），同来源重灌时 `VERSION` 递增；
- `-Plan` 只算不推、`-Only` 只跑子集（试点）、`-Verify` 断言库里没有机制篇目与混灌的业务知识。

**陈旧闭环**：手册文档落后于源码时，助手会拿着旧文档讲错规范——所以陈旧检测报「落后」时
**不再静默**，会打印重灌命令，`-SyncKb` 可直接触发（详见 [06-测试与质量门禁](./06-测试与质量门禁.md) 第五节末）。
处置顺序固定：**先更新文档，再重灌**。

### 3. 常驻路由规则

`ChatService.KnowledgeChannelRule`（一行，约 50 token，与量化指标、诊断的路由规则同一形态）：
机制问题走 `describe_mechanism`；规范、坑与动因走 `kb_search` 并标注来源与版本；冲突以服务端元数据为准。
**不塞长文**——常驻提示词的每一行都按每轮重复计费。

### 4. 前置：向量模型必须接线

链路与目录都已就位，但**检索面当前不可用**：入库要算向量，而 `IEmbeddingModel` 仍是
fail-closed 的占位实现（`PendingEmbeddingModel`），入库端点以 `KB_EMBEDDING_NOT_CONFIGURED` 拒绝。
实测 `KB_DOCUMENT` 93 条、`KB_COLLECTION` 4 个、**`KB_CHUNK` 0 条**。
**通道已建、检索在 embedding 就绪前不可用**——接线后重跑同步脚本即可（幂等，未变的跳过）。

### 5. 一个含义容易搞混的点

`docs/guide/README.md` 曾写"本手册同时作为 AI 助手的上下文"——那说的是**写代码的 AI 助手**
（读仓库那个），不是**产品内的工作助手**。两者机制不同（前者读文档，后者走能力目录 + 检索），
该表述已在 README 改清，不要再按"手册会进工作助手的上下文"理解。
