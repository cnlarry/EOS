# 48 生命周期与审批流

单据的"状态"由主表上的**一组标准列**承载，不是另建状态表。这篇讲这组列的规约、
状态怎么流转、以及审批流。

实现：`EOS.API/Data/WorkflowStates.cs`（列与状态常量）、
`EOS.API/Data/WorkbenchApprovalService.cs`（批核/解批/结案/工作流）、
`EOS.API/Data/WorkflowEngine.cs`（流程引擎）、
`EOS.API/Controllers/WorkflowController.cs`、`FlowDefinitionController.cs`。

## 一、生命周期列：13 列

`WorkflowStates.LifecycleColumns` 是**单点定义**（其他类一律委托它，不得各自重复声明）：

| 组 | 列 | 语义 |
|---|---|---|
| 建立 | `CREATE_PERSON`、`CREATE_DATE` | 谁建的、什么时候 |
| 修改 | `LAST_UPDATE_BY`、`LAST_UPDATE_DATE` | 最后一次改动 |
| 批核 | `CONFIRM_TAG`、`CONFIRM_PERSON`、`CONFIRM_DATE` | 是否已批核、批核人、批核时间 |
| 结案 | `FINISHED_TAG`、`FINISHED_PERSON`、`FINISHED_DATE` | 是否已结案、结案人、结案时间 |
| 归属 | `CI`、`OWNER`、`OWNER_G` | 行公司 / 建单用户 / 建单用户主组 |

按用途另有几个子集常量：

| 常量 | 内容 | 用途 |
|---|---|---|
| `LifecycleTagColumns` | `CONFIRM_TAG`、`FINISHED_TAG` | 状态位 |
| `LifecycleActorColumns` | 8 个经办人/日期列 | 服务端持有的经办快照 |
| `RecordStatusColumns` | 批核/结案的状态位 + 人 + 日期 | **记录读取契约必须返回**，即使不在表单定义内 |
| `OwnershipColumns` | `CI`、`OWNER`、`OWNER_G` | 数据范围归属 |

## 二、为什么状态位在单据主表上，不拆状态表

这是理解整套设计的前提。核心原因是**同行原子守卫**：

```sql
UPDATE 单据表 SET CONFIRM_TAG=1, CONFIRM_PERSON=..., CONFIRM_DATE=...
WHERE 主键=... AND ISNULL(CONFIRM_TAG,0)=0
```

用"影响行数"**同时**完成状态翻转与并发防重——拆表后要么退化成"先 SELECT 再 UPDATE"
（引入竞态），要么上显式事务与额外锁。

另外几条：

- **状态位与快照的一致性由同一条 UPDATE 免费保证**。拆表会出现"`CONFIRM_TAG=1` 但 `CONFIRM_PERSON IS NULL`"，
  且"未批核"与"生命周期行缺失"会塌缩成同一个 NULL；
- **列表要能按这些列排序与过滤**。虚拟列机制虽然能在列表渲染，但**不可排序、不可过滤**，
  而建立/修改/批核日期恰是最高频的排序筛选列；
- **删除与复制**：拆表后删除需级联，残留孤儿指向不了任何主表行、也无法被校验发现。

因此：**状态与经办快照留在主表，历史不回流主表**。完整历史由 `AUDIT_EVENT` /
`AUDIT_FIELD_CHANGE` / `WF_*` 承载；主表上的 `CONFIRM_PERSON/DATE` 只是"最近一次生效的经办快照"，
**不是过程**。

## 三、空值口径（写代码时要照着来）

| 列 | 约束 | 理由 |
|---|---|---|
| `CONFIRM_TAG`、`FINISHED_TAG` | `NOT NULL DEFAULT 0` | 状态位非真即假，没有"未知" |
| `CREATE_PERSON`、`CREATE_DATE` | `NOT NULL` | 新建即由服务端写入 |
| `LAST_UPDATE_*`、`CONFIRM_PERSON/DATE`、`FINISHED_PERSON/DATE` | **永久可空** | NULL = **事件尚未发生**（未修改/未批核/未结案）。回填即伪造历史，所以不补不收紧 |

最后一条最容易写错：**看到 NULL 不要"顺手补上"**，那是在编造历史。

## 四、服务端独占写入

这组列由**服务端统一写入**（保存 / 批核 / 解批 / 结案 / 工作流末步）：

- **客户端提交同名列一律被忽略或拒绝**——这是防止"自己给自己批核"的关键；
- 归属三列（`CI` / `OWNER` / `OWNER_G`）：新建时服务端回填，更新时忽略客户端提交；
  `CI` 取当前用户所属公司，用户没有公司归属时回填哨兵值 `DEFAULT` 并记警告
  （哨兵公司不得指向任何真实客户公司，否则无法归属的行会被静默算到该客户名下）。

## 五、呈现规则

| 场景 | 呈现 |
|---|---|
| 统一表单 **新增态** | 隐藏（服务端生成，无需用户输入） |
| 统一表单 **编辑态** | 隐藏 |
| 统一表单 **浏览态** | 只读显示（批核/结案人日期是追溯入口） |
| 列表选择列 | **可选**（既有默认列里已有系统列，不在本次调整范围） |

> 隔离发生在**元数据与呈现层，不动表结构**。

## 六、批核 / 解批 / 结案

端点（`DocumentWorkbenchController`，前缀 `api/v1/document-workbench/{moduleId}`）：

| 方法 | 路径 | 动作 |
|---|---|---|
| `POST` | `/approve` | 批核 |
| `POST` | `/deapprove` | 解批 |
| `POST` | `/endcase` | 结案 |
| `POST` | `/unendcase` | 取消结案 |

服务侧入口（`WorkbenchApprovalService`）：

| 方法 | 作用 |
|---|---|
| `RunApprovalCoreAsync` | 批核核心 |
| `RunFinishCoreAsync` | 结案核心 |
| `AutoApproveAsync` | 保存路径上的自动批核 |
| `WorkflowAsync` | 走流程（送审） |
| `CheckApprovalPreconditionsAsync` | 前置校验 |
| `CheckSimulationSupportedAsync` | 是否支持模拟 |

两条要点：

- **自动批核是纯状态翻转**：模块满足"自动批核 + 无效果链 + 无流程"时，保存即批核，
  性质与显式批核一致（`IsStatelessApproveCapable`，服务端分支与表单按钮显隐共用此判定，两边不得分叉）；
- **删除守卫引用状态位与库存流水**：已批核/已结案的单据不能直接删。

## 七、能力 → 列：单向强制

> **任何模块只要启用批核/结案能力，就必须具备对应状态位。**

判据取自会触达 `CONFIRM_TAG` 读写路径的**后端事实**（自动批核、效果引擎接管、工作流、
批核/解批效果链），**不看只控制显示的表单按钮配置**。

模块类型分层：

| 模块类型 | 生命周期列 | 可用能力 |
|---|---|---|
| 单据型（有批核/结案/流程） | 全组必备 | 批核/解批/结案/流程 |
| 档案型（纯 CRUD / 字典） | 可不建 | 列表不出现这些列，工具栏不出批核/结案按钮 |

**不要靠运行期判列存不存在来静默跳过**：缺列时若直接返回成功，使用者会以为已经批核了。
缺列应在**发布校验**时报出来并引导补列。

## 九、工作流与效果引擎的关系

效果链把状态位当作**守卫与读条件**，所以：

- 行内状态保证效果链的触发点（批核效果、解批、结案）语义一致；
- 状态位的写入收口在统一管线，旧的过程直写随体系演进逐步退役；
- "批核时该做什么"由**效果配置**表达，不是写死在代码里——见 [47-单据行为效果引擎](./47-单据行为效果引擎.md)。

## 十、排障

| 现象 | 原因 |
|---|---|
| 批核按钮点了没反应/报 404 | 模块未启用批核能力（`NEW_URL` 为空或缺状态位）；或只读模块 |
| 批核报冲突 | 同行原子守卫拦下——单据已被他人批核 |
| 批核成功但状态没变 | 检查是不是"缺列时静默跳过"的老路径；正常应报错而不是假装成功 |
| 用户能自己批核自己 | 客户端提交了状态列且未被忽略——服务端独占写入被绕开了 |
| 结案后退不回 | 结案有下游约束；用 `/unendcase` 且需权限 |
| 审批历史为空 | 走的是直接批核（无流程），历史在 `AUDIT_EVENT` 里，不在 `WF_*` |
| 看到经办人/日期为 NULL | **正常**：NULL 表示事件未发生，不要补 |
| 发布时提示缺状态列 | 模块声明了批核能力但主表没有状态位，按提示加列（走 DbUp 迁移） |

## 解批与批核的上下游规则（产品口径）

单据之间的引用是有方向的：下游引用上游（如收料单引用采购单）。**批核是"生效"，解批是"撤销生效"**，
两者都要顺着这条方向校验——否则单据会落进"来源已失效"的状态，而录入时的数据源条件拦不住它
（那个条件只保证"录单那一刻上游是批核的"，之后上游被解批就失效了）。

**解批（撤销生效）**

- **不删除任何下游单据。** 解批只翻转本单的生效状态（并冲销本单产生的库存/账务流水），下游原样保留。
- **只有"没有下游单据"或"下游单据都还没批核"时才允许解批。** 下游一旦批核，说明它已经基于本单的生效
  而生效，必须先解批下游。
- 引用链要**逐级解开**：A → B → C → D，解批 A 要求 B 未批核；B 已批核就先解批 B，而解批 B 又要求 C 未批核……
  依此类推。
- **已结案的单据不允许解批**（结案意味着本单已转出下游、已过账），须先取消结案。

**批核（生效）**

- **批核前检查上游的批核状态**：上游未批核时本单是**没有来源的无效单据**，批核必须被拦住。
  例：B 未批核时，批核 C 要被拒绝。
- 这道闸门之所以必要，正因为解批会制造"上游退回去了、下游还站着"的中间态——录入时的数据源条件
  只保证录单那一刻，保证不了批核那一刻。

> **实现（2026-10-07）**：这两条闸门已落地在 `EOS.API/Data/Workbench/DocumentChainGuard.cs`，
> 挂在批核/解批的**两条**路径上（引擎接管走 `CheckApprovalPreconditionsAsync`，无副作用走
> `StatelessApproveAsync`）。判据只取自 `FIELD_RELATION` 的 `EFFECT` 登记边：同一 `RELATION_NAME`
> 下的多行合起来算一条边，用"本单在这些列上的值"去对面表匹配，再看对面行的 `CONFIRM_TAG`。
> **"查不到就放行"是刻意选择**（宁可漏拦、不可误拦）：对面表没有 `CONFIRM_TAG` 列、键列读不到值、
> 边落在明细/中间表上——一律视为"这条链看不全"，不拦。错误码 `DOWNSTREAM_CONFIRMED` /
> `UPSTREAM_NOT_CONFIRMED`。
>
> "已结案不许解批"与"解批不删除下游单据"是更早落地的两条，仍然有效；
> `MODULES.NOT_BACK_FIELDS(_M)` 的字段级闸（"该字段已发生业务即不许回退"）也在，三者互补。

## 收口：月结单的「建单 / 审核」两个权限位（迁移 331）

- **月结单（1304）不再是自动批核**。它是业务单据而不是基础数据，"建单"与"审核"是两个权限位：官方路径
  是「建单 → 生成快照 → 批核」，不再需要"先反结账再生成"这种绕法（那条绕法源于"建单那一刻就已经关账，
  而快照还没生成"）。
- **批核阶段有闸**：该期快照明细（`INV_PRO_MONTH_D`）一行都没有就**拒绝批核**，文案"该期快照尚未生成
  （明细为空），不能关账：请先生成快照。"。闸门是通用规则 `detail-required-on-approve`
  （`MODULE_VALIDATION_RULE` 的 `APPROVE` 阶段 + `custom-validation`），**只按模块定义判"明细表按本单主键
  是否零行"，不认模块号**——任何"明细靠动作生成"的模块都能挂。
- **为什么不复用 `line-require`**：那条规则管的是"某明细**字段**在触发条件下必填"，管不了"**一行明细都没有**"；
  这里管的是**行数**。
- **一条必须记住的判据（本轮修掉）**：`WorkflowStates.IsStatelessApproveCapable` 曾经是
  `AUTO_APPROVE && !效果链 && !流程`，把"纯状态翻转批核"的能力**绑在自动批核上**。后果是——把某个模块的
  自动批核关掉（就像这里的月结单），它的**手工批核/解批入口会一起消失**：服务端回 404
  `WORKFLOW_NOT_SUPPORTED`，前端工具栏也不显示按钮。现在判据只认「无流程、无效果链」，与 `AUTO_APPROVE`
  无关。记住**批核能力有三条互斥来源**：效果链（引擎接管）、审批流程（送审）、无副作用状态翻转；
  前两条都没有时第三条必须成立，否则模块会变成"能录不能审"。

## 收口：批核阶段的校验闸对"无副作用批核"同样生效

- **实测暴露的现象**：给月结单挂上 `APPROVE` 阶段的校验规则后，点批核**照样成功**（`CONFIRM_TAG` 变 1），规则形同虚设。根因是 `WorkbenchApprovalService` 的分支顺序——无副作用批核走 `StatelessApproveAsync` **独立路径，那条路上从不跑 `ValidateStageAsync`**；只有"引擎接管"那条（`RunApprovalCoreAsync`）才跑。
- **修法**：`StatelessApproveAsync` 也先过同一道闸，并把「校验闸 → 状态翻转 → 审计」收进**同一个事务**（早退返回时未提交即回滚，校验不过时状态与审计都不落库）。**声明式校验目录与"谁负责执行批核"无关**——这正是 SAVE 阶段一直坚持的口径（"无论走效果动作还是遗留钩子，都必须先过这道闸"）。
- **记住这条排查姿势**：规则挂了却不生效，先看**这条业务路径有没有跑校验链**，不要先怀疑规则写错——很多"配置不生效"是那条路径根本没走到校验。
- 附带一条运维注意：验证月结单这类"关账"单据时**用后必须立即删掉**。一张已批核、期末在其他业务日期之后的月结单，会把**所有更早日期的库存流水**拦成"记账到已关账期间"（本轮就因此让 51 条库存相关单测红过两次）。
