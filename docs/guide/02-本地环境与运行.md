# 02 本地环境与运行

目标：从空环境把 EOS 跑起来，看到完整的模块菜单与空的业务数据。

## 一、环境要求

| 项 | 要求 |
|---|---|
| 运行时 | .NET 10 SDK |
| 前端 | Node.js 20+ 与 npm |
| 数据库 | SQL Server 2025+（结构含原生 `vector` 列，兼容级别 170） |
| 命令行工具 | `sqlcmd`（随 SQL Server 客户端工具安装） |

数据库需具备建库权限（dbcreator / sysadmin），或由 DBA 代为执行建库脚本。

## 二、初始化数据库

仓库**不附带业务数据库备份**。建库脚本在 `db/bootstrap/`，必须按编号顺序执行：

| 步骤 | 脚本 | 作用 |
|---|---|---|
| 1 | `00_create_database.sql` | 创建 `EOS.ERP` 数据库 |
| 2 | `10_schema.sql` | 表、函数、视图与运行时依赖的存储过程（纯结构，无数据） |
| 3 | `20_metadata.sql` | 元数据种子：模块菜单、字段登记、通用查询、报表与表单版式 |
| 4 | `30_admin.sql` | 初始管理员账号 |
| 5 | `40_journal_baseline.sql` | 登记已固化的迁移编号，使应用启动时不重复执行 |

```powershell
# 脚本为 UTF-8，sqlcmd 必须带 -f 65001（否则中文脚本在部分区域设置下解析失败）
sqlcmd -S . -E -i db/bootstrap/00_create_database.sql -f 65001
sqlcmd -S . -E -d "EOS.ERP" -i db/bootstrap/10_schema.sql -f 65001
sqlcmd -S . -E -d "EOS.ERP" -i db/bootstrap/20_metadata.sql -f 65001
sqlcmd -S . -E -d "EOS.ERP" -i db/bootstrap/30_admin.sql -f 65001
sqlcmd -S . -E -d "EOS.ERP" -i db/bootstrap/40_journal_baseline.sql -f 65001
```

以上以当前 Windows 账户连接本机默认实例（`-E`）。用 SQL 账号登录时换成 `-U <用户> -P <口令>`。

**建库后的口径**：

- 元数据（模块、字段、查询列、报表版式、表单布局、流程定义）随仓库走，
  新库会用与开发环境一致的界面元数据启动；
- 业务数据（单据、主档、员工等）全部为空，需在界面中自行建立；
- 除 `admin` 外不预置任何账号。

## 三、配置并启动后端

```powershell
cd EOS.API
Copy-Item appsettings.Development.example.json appsettings.Development.json
```

默认连接串（可按需编辑）：

```json
"ErpDatabase": "Server=localhost;Database=EOS.ERP;Trusted_Connection=True;TrustServerCertificate=True"
```

```powershell
dotnet run
```

- 服务监听 `http://localhost:5261`；
- 健康检查：`/health/live`（存活）、`/health/ready`（就绪）。

**首次启动会做什么**：应用经 DbUp 检查迁移台账 `dbo.ERP_SCHEMA_JOURNAL`，只执行台账中没有记录的
迁移脚本。由于 `40_journal_baseline.sql` 已预登记基线内的编号，首次启动通常只跑基线之后的新迁移，
属正常现象。

**日常开发不需要手工跑迁移**，也不需要手工改 `ERP_SCHEMA_JOURNAL`——新增脚本放到
`EOS.API/Data/Migrations/` 后，启动即自动应用。

## 四、启动前端

```powershell
cd EOS.Web
npm install
npm run dev
```

开发服务器读 `vite.config.ts`：

- 端口 **80**（如需改端口或与其他服务冲突，改 `server.port` 即可）；
- 把 `/api` 代理到 `http://localhost:5261`，所以前端**不需要**配置 API 基址；
- 只允许 `localhost` / `127.0.0.1` / `www.erp.com` 作为 Host 访问（`server.allowedHosts`；
  本地 hosts 把 `www.erp.com` 指向本机时即以该域名打开，见 `AGENTS.local.md`）；
- 构建时把仓库根 `version.json` 的产品版本注入产物（`__APP_VERSION__`，供「日志管理」页展示）；
  版本真源与发布流程见 [`docs/decisions/ADR-026`](../decisions/ADR-026-版本管理与发布流程.md)。

打开 `http://localhost/` 即可。

## 六、验证与测试

```powershell
# 后端
cd EOS.API
dotnet build

# 后端测试（从仓库根执行，显式指定 csproj）
dotnet test EOS.API.Tests\EOS.API.Tests.csproj

# 前端
cd EOS.Web
npm run lint
npm run build
npm test
```

测试分成两类，用途不同：

- `EOS.API.Tests/*Tests.cs`（xUnit）：不依赖运行中的服务，随时可跑；
- `EOS.API.Tests/E2e*.ps1`、`Acceptance*.ps1`：需要 API 在线或需要连接真库，
  跑之前先确认环境可用。

## 七、常见问题

| 现象 | 排查方向 |
|---|---|
| 登录提示用户不存在 | 确认已执行 `30_admin.sql`，且连接串指向正确的数据库 |
| 菜单不完整 / 字段缺失 | 确认已执行 `20_metadata.sql` |
| 启动时迁移报错 | 确认 bootstrap 五个脚本已按顺序执行完；`10_schema.sql` 与 `40_journal_baseline.sql` 必须来自同一版本 |
| 日志提示表名/列名不存在 | `10_schema.sql` 是结构快照；用旧快照建库后再升级代码，要么重新初始化，要么等新迁移补齐结构 |
| 前端起来但接口 404 | 确认后端在 `5261` 上运行（Vite 把 `/api` 代理到该端口） |
| 80 端口起不来 | 该端口可能被系统服务占用；改 `server.port` |
| 助手回复"尚未配置模型接入" | `Assistant:ApiKey` 为空——见第八节的配置来源 |

## 八、生产环境的配置来源（含凭据放哪）

配置源与优先级（后者覆盖前者）：

```
appsettings.json  →  appsettings.{环境名}.json  →  环境变量  →  命令行
```

- `appsettings.json`（**入库**）只放与部署无关的默认值，**不得写凭据**；
- `appsettings.Development.json`（**已 gitignore**）是开发机的本地配置，从模板复制：
  `Copy-Item appsettings.Development.example.json appsettings.Development.json`；
- `appsettings.Production.json`（**已 gitignore**）是生产环境的本地配置，同样从模板复制：
  `Copy-Item appsettings.Production.example.json appsettings.Production.json`；
- 环境变量（如 `Assistant__ApiKey`，**双下划线**代替 `:`）不进任何文件，适合临时覆盖或由部署流程注入。

**生产建议以 `appsettings.Production.json` 为主真源**（明文、按 ACL 限权、随部署放置），环境变量作覆盖层：
文件看得见、可审计，轮换＝改文件＋重启；而环境变量在 Windows 下最容易"配了没生效"
（要重启启动它的宿主进程；IIS 下还要经 `web.config`，那份通常入库，**不要**把值写进去）。

### 生产通常需要配的键

| 键 | 说明 |
|---|---|
| `ConnectionStrings:ErpDatabase` | 业务库连接串。**基础 `appsettings.json` 里没有这一节**，生产必须给 |
| `Assistant:ApiKey` | 工作助手的模型密钥。留空 = 助手降级（回复"尚未配置模型接入"），其余功能不受影响 |
| `Assistant:BaseUrl` / `Model` / `TimeoutSeconds` | 仅当不用默认的 DeepSeek 官方端点时才要改 |
| `DataProtection:KeysDirectory` | 数据保护密钥环目录（登录 Cookie 等依赖它）。以服务账户运行时必须指到**该账户可读写的固定目录**；多实例部署要共享同一目录 |
| `Attachment:StorageRoot` / `ReportFormats:StorageRoot` | 附件与版式资产的落盘根目录。留空 = 落输出目录（重新发布易丢），生产应指到固定数据目录 |
| `Logging:File:Path` | 文件日志路径，建议指到固定目录（默认 `logs/api-json.log` 相对输出目录） |

模板只列**键名与占位**，不含任何真值。

### 两个容易踩的坑

1. **数组是整段覆盖，不是合并**：`Security:AllowedOrigins` 这类数组，环境文件里写了几项就**只剩**那几项，
   基础配置里的项会被整段挤掉。生产若前后端不同源，这份必须**写全**（开发机加白 `www.erp.com` 时同理）。
2. **服务读的是输出目录那份配置**：`dotnet run` 会先 build 再运行，所以改源码目录的配置后重启即可同步；
   但若直接运行 `bin/Debug/net10.0/EOS.API.exe`，改源码那份**不会**自动生效——要么重新构建，要么改输出目录那份。

### 轮换与限权

- 密钥轮换：改 `appsettings.Production.json` 后重启服务（环境变量方式则改完要重启宿主进程）；
- 文件 ACL 只给运行账户可读；
- 诊断包与日志**不会**带走密钥：`configDigest` 按白名单只报"某个配置节是否已设置"（不列值），
  日志经 `LogRedactor` 脱敏（见 [`31-运行日志与诊断.md`](31-运行日志与诊断.md)）。
