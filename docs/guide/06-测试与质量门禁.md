# 06 测试与质量门禁

## 一、两端的入口

```powershell
# 后端（从仓库根执行，显式指定 csproj）
dotnet build EOS.API/EOS.API.csproj
dotnet test  EOS.API.Tests\EOS.API.Tests.csproj

# 前端
cd EOS.Web
npm run lint     # oxlint
npm run build    # tsc -b && vite build
npm test         # vitest run
```

`dotnet test` 必须显式指定 csproj：在错误目录下执行会**静默空跑且无输出**，
看起来"通过"，实际一个测试都没跑。

## 二、测试分三层

| 层 | 资产 | 依赖 | 何时跑 |
|---|---|---|---|
| 单元测试 | `EOS.API.Tests/*Tests.cs` 中不带 `Live` 的部分 | 无外部依赖 | 每次改动，提交前必跑 |
| 真库用例 | `EOS.API.Tests/*LiveTests.cs` | 可连的 `EOS.ERP` | 涉及领域规则、SQL、迁移时 |
| 端到端脚本 | `EOS.API.Tests/E2e*.ps1`、`Acceptance*.ps1` | 运行中的 API（部分还需前端） | 改接口、改流程、发版前 |

规模参考：后端约 240 个测试文件（其中约 100 个是真库用例）、约 50 个端到端脚本；
前端约 90 个测试文件。**你不必全跑**——按改动范围选层：

| 改了什么 | 至少跑到 |
|---|---|
| 纯函数、解析器、校验逻辑 | 单元测试 |
| 领域规则、SQL、元数据消费 | 单元 + 相关真库用例 |
| 接口、路由、权限门 | 单元 + 端到端脚本（只读端点优先） |
| 助手对话编排、指标口径 | 单元（`Assistant`、`ChatServiceTests`、`Metric` 等过滤器）+ 相关真库用例（`ReportMetricIntegrationTests`） |
| 前端组件与页面 | `npm run lint` + `npm run build` + 对应组件测试 |

### 评估集（`EOS.API.Tests/AssistantEval/`）

助手质量的评估集与上面三层并行，**不新建第二套框架**——与单元测试同一条命令：

```bash
dotnet test EOS.API.Tests/EOS.API.Tests.csproj --filter FullyQualifiedName~AssistantEval
```

**进自动回归**（不达标阻断发布）的部分：

| 层 | 断言什么 |
|---|---|
| `authz/` | 越权必须被拒，泄露 **= 0**（硬门槛） |
| `inference/` | 答案格式与必要来源声明（跨 ≥3 源；定量题须引用口径） |
| `situation/` `action/` `config/` | 样本声明的原因码必须落在代码闭集内（防漂移） |
| `diagnosis/` | 黄金集可追溯到元数据（错误归因 = 0、拒答率 ≤ 10%） |
| `functional/` `business/` | **来源锚定**：`sources[]` 必须在仓库里真实存在（模块映射已登记、工具名在工具源码里、文件在仓库里、类型或成员在程序集里、库对象名或错误码在业务代码与 SQL 里）；抽样前先用它挡住"依据自造"的样本 |

**仍需人工**：`functional/` 与 `business/` 的**答案对错**（正确率 / 拒答率）——同一事实有多种正确表述，
字符串匹配判不了，需 LLM-as-judge；judge 模型、rubric、季度校准未就绪前按人工抽样（每轮 ≥30 条，
结果落 `AssistantEval/` 留痕）。**不要把这两层写成"已自动断言"**；口径详见
`EOS.API.Tests/AssistantEval/README.md`。

## 四、真库用例的纪律

真库用例会连真实数据库（连接串取自环境变量 `MSSQL_ERP_CONN`；**没有连接串时跳过**——那属于"环境缺失"，
见本节末「'跳过'只留给环境缺失」，而"库里该有的样例数据"是**数据前提、必须断言**），
必须做到**跑完不留痕、不误伤既有数据**：

- **库结构类改动必须跑真库用例**：单测用的是假仓储，看不见"代码按某列写、库里却没有"这种不一致，
  它只会在真库用例里以 `列名 '…' 无效` 暴露（详见 [05](./05-数据库迁移与建库.md) 的「改表要连迁移一起改」）；
- **归属条件写在 SQL 里时，越权要断"受影响行数为 0"**：像 `UPDATE … WHERE ID=@Id AND USER_ID=@UserId`
  这种守卫，测试要**换个用户去改同一行**并断言返回 0——而不是断言"抛异常"。
  否则一旦有人把归属条件挪到调用方去判，测试照样绿；
- 用例自己造键（料号、单号、库别等），**不要借用真实主档的取样值去写入**——
  借来的 `TOP 1` 值只允许用来读；
- 不要删除审计记录（审计按设计保留）；
- 数量承载表（库存余额、流水、批次账、预留、冻结）**不得按库别整体删**；
  库别是借用来的话，必须再加料号条件收窄；
- **配置写用例自造"表标识 / 字段名 / 模块号"**：字段维护与模块业务配置的写目标不借用真实对象写入
  （真实对象只允许读来做对照），结束即清理自造行；
  自造模块还要一并清掉它的脏标记行（`WORKBENCH_MODULE_DIRTY`）——写配置会标模块脏，
  留下孤儿脏标记会让发布链路把已删除的模块当成"待发布"。

> `scripts/check-live-fixture-hygiene.ps1` 专门静态检查这三条（见第五节）。

**执行期缺陷要用"真的执行一次"的真库用例钉住**：拼出来的 SQL（选择器的 FROM、动态查询）里的毛病
——重复别名、引用了不存在的列、JOIN 顺序——**只在执行期暴露**，断言拼接结果里有没有某个子串是假绿
（`ON` 条件里也会出现同名标识符，`Contains("[PRODUCT]")` 这种断言根本区分不出"多了一次 JOIN"）。
写法：让生产代码产出片段、拼成完整语句，**两版各执行一次**（旧拼法必须抛 `SqlException`、
新拼法必须跑通），再补一条纯单测钉住片段之间的契约（如"回传的别名集合必须含依赖闭包"）。
实例：`EOS.API.Tests/ChooserJoinCompositionLiveTests.cs` —— 选择器过滤 JOIN 与虚拟列 JOIN
各拼一次同名别名导致的 500。

另一实例：`EOS.API.Tests/DepotDeleteCascadeLiveTests.cs` —— 自引用外键（SAME TABLE REFERENCE）是
**行级即时校验**，"按叶子优先删整棵自引用树"的写法只在真库上才会撞 `FK_DEPOT_LOCATION_PARENT`；
而"把没有上级的行当叶子"这个逻辑错误（根节点同样可能有子树）纯单测看不出来，
只有"三层库位树随宿主清理"那一条用例能红（见 `LESSONS.md` L70）。

**找仓库根有两条路，别把它们混成一条**：评测集（`EOS.API.Tests/AssistantEval/`）由**编译期注入的
`RepoRoot` 程序集元数据**定位仓库根，对它而言 `--artifacts-path` 指向仓库外也能跑；
但**目录扫描型**用例走 `FindRepoRoot()` / `RepositoryRoot()`——从 `AppContext.BaseDirectory`
逐级向上找 `EOS.API/EOS.API.csproj`，**产物一旦落在仓库外，它们会报"找不到仓库根目录"**
（看着像功能坏了，其实是环境；实测记录见本节末）。所以约定是：
**`--artifacts-path` 一律指到仓库内目录**（如 `--artifacts-path artifacts` 或 `$PWD/.artifacts`），
新增读取仓库内文件的用例沿用这条路径，**不要**假设运行目录一定在仓库里。

## 五、门禁脚本

`scripts/` 下另有一套**静态与连库门禁**，拦的是「编译与单测发现不了、只在运行时炸」的一类缺陷：
DI 漏注册、整页 500、迁移语法错、配置面白名单漂移、库存账务不平、样式类悬空等。

> **两条"编译与界面都不报"的回归用例（2026-09-29 新增）**，写在单测里而不是脚本里：
> `ModuleRouteValidatorTests.定制页路由_后端精确路径与前端路由表一致` 拦"新增定制页只登记了两处
> （库内模块 + 前端路由，漏了后端 `ExactRoutes`）"——表现为菜单点进去是 `/fallback/modules/{id}`
> 空壳页；`DiagnosticsConfigDigestTests` 拦"诊断包配置摘要把机器环境变量名列进去"。
> 两者都属于**加一处登记就绿、漏一处就红**的类型，属于"改了配置面才发现"的坑。
> 该用例的入参就是**页面的模块号**，所以它同时钉住"用例、迁移登记的模块号、前端路由守卫"
> 三者一致：定制页重编号时（如日志管理由 `110112` 改为 `2313`）三处要一起改，
> 漏改任一处这条用例即变红。
>
> 诊断包另有两条**构造型**用例（`LogFileReaderBundleToleranceTests`，用文件独占打开模拟不可读、用空目录模拟没日志）：单个日志文件不可读时打包**跳过该文件而不是整包失败**；目录里没有日志时返回**空清单**而不是报错。运行期已实测的相邻判据：日志总量超 100MB 时 `/api/v1/logs/bundle` 返回 **413 + `DIAGNOSTICS_BUNDLE_TOO_LARGE`** 且**不返回坏包**；无 `CanSetup` 权限时返回 **403** 并给出原因文案（注意改权限后**最多等 60 秒**权限缓存过期，见 [21-授权模型](./21-授权模型.md) 第七节）。

1. **`check-di-registrations.ps1` 建议每次都跑**——它拦的是"编译 0 错、单测全绿，

   新增命中即失败，这样债不会继续累积。

连库类脚本需要可用的 `EOS.ERP` 连接，配置见 [02-本地环境与运行](./02-本地环境与运行.md)。

### 手册陈旧 → 知识库重灌（闭环）

本手册的「规范与坑」「设计动因」两类内容会进产品内工作助手的知识库
（三份处置与两集合见 [README](./README.md) 第五节）。文档落后于源码时，
知识库里的内容也**可能**是旧的——助手会拿着旧文档讲错规范，这正是这条链路最怕的场景。

因此陈旧检测脚本在报「落后」时**不再静默**：

```powershell
pwsh docs/guide/_tools/check-freshness.ps1 -Strict            # 报落后并打印重灌命令
pwsh docs/guide/_tools/check-freshness.ps1 -Strict -SyncKb    # 直接触发重灌（幂等，未变的跳过）
```

处置顺序固定：**先更新文档，再重灌**——重灌读的是仓库里的文档，文档没改就重灌只会把同一份旧内容再推一遍。
重灌走 `scripts/sync-guide-to-kb.ps1`（内容哈希幂等）；`-Verify` 断言库里没有机制篇目。

> 链路本身要求向量模型接线（入库即算向量）。**未接线时入库会以 `KB_EMBEDDING_NOT_CONFIGURED` 失败**：
> 通道（集合、脚本、幂等、标题前缀）已建，检索要等 embedding 就绪——不要把"脚本跑通"当成"检索可用"。

## 七、写测试的几条经验

- **测试名说清场景与预期**，不要用 `Test1`、`TestOk`；
- **断言要能失败**：只断言"没抛异常"的测试没有价值；
- **涉及门禁/白名单的改动，先想清楚反例**：能被绕过就说明白名单开得太宽；
- **涉及"客户端上报"的改动，正例反例都要断言**：自造的错误码/未知字段名/越权字段必须被**丢弃**
  （只断言"合法值能通过"是半个测试）；"打开即见"这类声称零成本的能力还要断言
  **没有触发模型调用**（前端断言未发起对话请求，后端断言该链路的构造参数里不存在模型依赖）；
- **涉及"界面状态随请求携带"的改动，断言请求体**：模拟选中行 / 改字段 / 触发服务端拒绝后，
  下一次请求体的对应字段必须随之变化，而不是断言组件内部状态；
- **"结构上不可达"要断在调用点上，不断在名字上**：同一条红线（例如"某侧不得调用某组端点"）
  按三处递进断言——① 枚举/类型面的成员集（表达都表达不出来）；② 注册面的名字；
  ③ **方法体的 IL 调用点**（`MethodBody.GetILAsByteArray()` 走 opcode 表取出 `InlineMethod` 操作数，
  再 `Module.ResolveMethod` 解析）。第③条要**连嵌套类型一起扫**，否则 async 方法的调用点落在编译器
  生成的状态机里，断言会"永远绿"；它同时能给出一条正向断言（"可触达的仓储方法恰好是这三个"），
  比反向否定更难被绕过；
- **"预演不落库"必须逐项对拍，不能只断言返回码**：预演跑的是真实事务，"不落库"要拿**主表行数 /
  关键字段 / `AUDIT_EVENT` 最大事件号 / 单号序列计数器 / 流程待办计数 / 幂等键行数**这些前后快照
  逐项相等来证（`ActionDryRunTests`）；顺带把"取号被释放"也断上——预演取到的号必须等于取号前的下一个号；
- **"界面渲染"与"模型输出"之间的约定要有一条断言钉住**：助手回答由前端按 Markdown 渲染，
  若没人管着提示词，模型就会各写各的、界面上只剩标记本身。这类"两端契约"没法端到端断言
  （真调模型不可重复），但可以断言**契约文本本身**——`AssistantSettingsTests` 断言默认提示词必须
  含 Markdown 与"不要输出 HTML"，同时原有安全约束（不编造、说明不确定性）不得被格式约定挤掉；
  前端那侧则用渲染器单测覆盖（含"不注入 HTML"与危险 scheme 按纯文本）；
- **"点了没反应"在 jsdom 里常常是"节点被换掉了"**：列表页的行内按钮，如果在首屏渲染还没落定时
  就用 `findByRole` 拿到元素去点，React 紧接着的重渲染会把那个节点换掉——手里的是游离节点，
  事件走不到处理器，现象与"功能没做"一模一样。会话管理页的 8 条用例里有 3 条栽在这上面
  （`confirm` 调用次数为 0、弹窗不出现、`toBeInTheDocument` 报 *element could not be found in the
  document*，而那个元素明明刚被查出来过）。修法是**等表格落定、重新查询、再点**（先等表头出现，
  再让一拍，然后用 `getByRole` 取新节点），并把这套等待抽成一个小工具函数、在注释里写清缘由；
- **遇到"点了没反应"，先证明"点击有没有走到处理器"，再动被测代码**：这次的插桩方式是把
  `window.confirm` 换成 spy 后数调用次数、以及直接打印弹窗标题——两者都证明功能是好的，
  问题在测试。少了这一步，很容易把好好的一段实现"修坏"（比如给它加多余的重试或延迟）；
- **管理侧的"跨用户"能力，要配一条"个人侧仍然隔离"的对照断言**：助手管理面允许管理员看全系统会话，
  而个人侧那条"所有读写按 `USER_ID` 强制隔离"的契约必须原样成立。集成测试在同一个用例里两边都断言
  （管理侧看得见别人的会话 / 个人侧依旧看不见）——只测新能力的话，很容易在"顺手放开"时把隐私边界
  改掉而没人发现；
- **真库测试的清理要连"指针"一起清**：助手模型表里有一条 `IS_ACTIVE = 1` 的"当前模型"指针，
  测试要是只删自己的行、不管指针，开发环境的助手下次重启就会去用一个密钥没配的测试模型，
  表现成"助手突然不可用"而没人知道是谁干的。清理顺序是**先清当前、再删行**；
- **换掉某个接口的注入生命周期时，补一条"旧契约还在"的断言**：把 `IChatModel` 从单例改成按请求解析，
  最该防的不是新功能坏掉，而是原来那件事悄悄变了（比如一条回答中途被换了模型）。这类改动要在
  集成测试里把旧行为也钉住，而不是只看新路径通不通；
- **真库测试的清理要按"父"删，别只删跟踪到的 ID**：用例在"记下 ID"之前就断言失败时（例如
  `Assert.Equal(3, created)` 先炸），已经插进去的行根本没被跟踪到，只删 ID 会留下孤儿行。孤儿行不只是脏——
  它还让迁移干跑门禁误报成"表里有数据"，把一次正常的脚本改动判成危险操作。**按父实体删**（删该供应商名下的
  全部模型）才对；
- **扫描型测试依赖产物目录在仓库内**：`NolockAllowlistTests`、`PasswordHasherTests` 这类靠
  `FindRepoRoot()`（从 `AppContext.BaseDirectory` 往上找 `EOS.API/EOS.API.csproj`）的用例，一旦用
  `--artifacts-path` 把产物放到 `%TEMP%`，就会报"Repository root not found"——**看着像功能坏了，其实是
  环境**。要在"API 进程锁着 `bin`、不能就地重新构建"的时候跑测试，就把产物目录指到**仓库内**（如
  `--artifacts-path "$PWD/.artifacts"`），别指到仓库外；
- **工具类用例走"窄网关"而不是真仓储**：助手侧每个读类工具都在仓储之前放一层小接口
  （`IReportGateway` / `IRecordHistoryGateway` / `IAttachmentGateway`…），底层**只转发**既有实现、
  上面只暴露这一次调用需要的两三个方法。于是权限门、主键推断、防探测文案、上限截断这些
  **工具自己要负责的事**都能离线断言（用例里给假网关），不必为了测一句文案起一个库。
  这也是"读写权限判定不许在助手侧复制"的落点：判定写在既有仓储/服务里，工具只调用它；
- **测试里拼 JSON 参数别用原始插值字符串**：`$$"""{"a":{{x}}}"""` 这类写法会撞 `CS9007`
  （JSON 的 `}` 与插值的 `}}` 混在一起，编译器按"连续右花括号"计数），而且它在**换一个字段就复发**。
  用普通字符串拼接（或 `JsonSerializer.Serialize` 一个匿名对象）——测试的脚手架不该花时间跟编译器
  的括号规则搏斗；
- **新登记白名单要成对看**：`NolockAllowlist` 是"文件级"清单，未登记的文件会让门禁红、**已登记却不再用
  NOLOCK 的文件照样会让它红**（两个方向都断言）。补登记前先确认那处 NOLOCK 属于只读/报表路径——
  白名单自己的文件头写明"强一致路径（保存校验、主子表读取、审批、库存、金额、单号）不得加 NOLOCK"，
  遇到这类文件该做的是**改代码**，不是把文件加进清单；
- **"登记齐全"类门禁可以做，但别写成全量断言**：统一选择器新增一个数据源要在**四张表**里登记齐
  （列清单 / 排序白名单 / 关键字白名单 / 列表达式），漏一处不会编译报错，只在运行期炸成"一查就 500"
  （列表达式与排序白名单都是按 sourceKey **直接取下标**用的）。所以把"缺了哪几处"抽成
  `MissingRegistrations` 逐条断言；但**不要写成"所有已注册源都齐全"**——少数源有意不走通用路径
  （`menu-admin.records` 的列随模块主表在运行期解析、`user-admin.employees` 的显示列来自字段元数据），
  那种断言会写成假的，而**假断言比没有断言更糟**：它把"以后真的缺了"也一起判成绿的；
- **"跳过"只留给环境缺失，"数据前提"要断言**：真库用例开头那句
  `if (ConnectionString.Value is null) return;` 是合理的跳过（没库就没法测）；但"这台库里有没有
  可用的样例数据"是**数据前提**，写成 `if (x is null) return;` 就等于让"根本没跑到断言"与
  "断言通过"长得一模一样——一条永远绿的用例比没有用例更坏，因为它还在给你信心。
  该写成 `Assert.True(x.HasValue, "……应当存在")`：前提不成立时红出来，让人去修前提或改断言。
  判别法：这句话在**别人的机器上**是否可能为假？"没有连接串"会，所以跳过；
  "模块表里有名字"不会，所以断言；
- **"两处同源"要拿同源的那张表做等值断言**：助手作用域的模块候选集声称"与作用域键校验同源"，
  只断言"返回了若干行"对"候选集比校验严"和"比校验松"两种偏移都是绿的。真库用例改成
  **`Total == COUNT(1) FROM dbo.MODULES`**（同一张表、同样不带 `M_TAG` 之类"看起来更合理"的过滤），
  偏移哪个方向都会红。凡是靠"两处读同一份数据"来消除错配的设计，都值得配一条这样的镜像断言；
- **但真库的等值断言要夹逼（前后各读一次取闭区间）**：全量跑时上千条用例共用一个库，
  别的用例会在这个窗口里增删行——两次独立读到的计数本来就可能不同，等值断言于是随机变红，
  而那种红与"同源"无关（本仓中过一次：`QueryAssistantAdminModules` 单跑绿、全量红）。
  取调用**前后**两次计数做区间：真同源时结果必落在区间内，带过滤则会明显掉到区间外，
  区间窄到一两条，松弛量不足以掩盖有意义的偏移；
- **迁移放宽了列或改了索引，读取路径与校验要同批跟上**：迁移 307 把 `API_KEY_ENV_VAR` 放宽为可空、
  把"全表至多一条当前"的唯一索引改成"按用途各一条"，而读取仍用 `GetString`（遇 NULL 抛
  `SqlNullValueException`）、供应商校验仍要求变量名非空、"取消当前"仍是清全表。三处都不会编译报错，
  表现分别是"合法的行读不出来""合法的端点配不出来""换对话模型让嵌入模型悄悄下线"。
  评审这类改动时按"**这一列 / 这个索引有谁在读、有谁在校验**"逐个交待，别只看写入路径；
- **"每类各一条"的断言要连"动另一类不影响这一条"一起钉**：改为按用途各一条之后，
  只断言"两条当前都在"对"清空全表再置位"那种实现**仍然是绿的**（先激活嵌入、再激活对话，
  两条确实都在）。必须补上"换掉对话那条之后嵌入那条仍在"这一步，才钉得住清空范围。
  一般化：凡断言"某组约束下可以有多条"，都要顺手断言"改动其中一条不会伤到其余"；
- **跨边界的编码串要有一条"回环"用例，且把错误写法一起否掉**：模型用途（`'CHAT'`/`'EMBEDDING'`）
  在库里、接口下发、前端比对三处各写了一遍，接口那处误用枚举默认序列化（`"Chat"`），
  前端按大字字母过滤 → **列表静默变空**。两端各自的用例当时都是绿的：服务端解析不区分大小写、
  假数据里写的是 `'CHAT'`，所以只有"真接口"这条缝没人测。这条缝的补法是
  **断言编码 → 解析回来的回环**，并额外断言 `token != kind.ToString()`
  ——否则"改回默认序列化"这件事还会再发生一次；
- **"交付数据"要有完整性测试**：预设目录（`AssistantProviderCatalog`）是一份要交给用户的数据——
  端点能不能真的发出去、环境变量名合不合法、最大输出会不会超过上下文窗口，都值得断言。一个拼错的值
  要到管理员点了"添加"才会暴露，而那时看到的只是表单里一个怪值；
- **这类断言的上界要与库里的检查约束同源**：模型预设的"最大输出"上界与 `ASSISTANT_MODEL` 的
  `CHECK` 是同一条边界。这条边界实际散在**三处**——库约束、预设目录的初值、**服务端的写入校验**，
  厂商把输出上限提到 39 万时要一起改。**三处只改两处的真实后果**：从预设添加模型时保存失败，报错是
  "最大输出 token 需要在 1–200000 之间"，而目录里写的却是 393216（当时库约束与目录都已放宽，
  漏的是控制器里的校验）。所以边界类断言要挑**最靠近用户的那一处**去钉：`ValidateModel` 这类
  服务端校验做成 `internal` 并配一条"厂商公开值必须能存进去"的用例，比在目录侧断言更能拦住复发；
- **核出来的事实要写成断言，而不是注释**：供应商的"有没有嵌入端点 / 能不能列出模型 / 认证头是哪种"
  是逐家核过官方文档的结论，钉进用例（例：小米必须带 `ApiKeyHeader`）才挡得住"顺手把它们统一成
  Bearer"这类改动——那会让那家供应商再也接不上；
- **出网调用把"纯逻辑"抽出来测，别指望在单测里穷举网络**：型号拉取（`AssistantModelDiscovery`）里
  真正会写错的是两件事——**厂商的 JSON 怎么读**（OpenAI 最小形状、有的厂商多给窗口与最大输出、
  缺标识与重复条目怎么处理）与**状态码翻成什么原因**（401/403 换密钥、404/405 手工填、其余稍后再试）。
  这两件抽成 `Parse` / `FailureForStatus` 两个静态函数就都能离线断言，剩下的出网部分只剩"如实转达"。
  这也是为什么失败要**分成多个原因码**：一个笼统的"拉取失败"没法断言，也没法指导下一步；
- **"实际发出去的请求"也要断言，用假的 `HttpMessageHandler` 就够**：嵌入客户端那批里，
  错的从来不是 JSON 解析，而是 **URL 拼错（404）、认证头样式错（401）、请求体少了 `dimensions`
  （拿回与集合列宽不符的维度）**——这三样在本地都不会报错，只有真连厂商才暴露。
  一个记录请求的 handler + 一个只返回它的 `IHttpClientFactory`，就能把"发出去的是什么"钉住
  （见 `AssistantEmbeddingModelTests`）；这与上一条是同一件事的两半：**纯逻辑离线测，出网那一层钉形状**；
- **"配置没配好"的判定也抽成纯函数**：嵌入解析器把三种拒答（没配模型 / 模型没维度 / 密钥没配）
  抽成 `NotConfigured` / `RequiresKey` / `Compose`，于是 **fail-closed 这条性质可以离线断言**——
  它是"没配就拒答、绝不返回空向量假装查过"的唯一保证，而那种退化一旦发生，外表上"一切正常"；
- **全局门禁只有跑全量才会亮**：工具面总数、`NOLOCK` 清单这类**跨文件断言**不在任何"按名字筛"的
  子集里。本仓就中过一次——几批新工具把工具面从 27 带到 31，而门禁一直没人跑，
  直到某次全量才一起暴露。改完一批之后，至少跑一次**全量离线集**（连库用例可以先用
  `Category!=Integration` 与"清空连接串"绕开），别只跑筛出来的那几条；
- **前端测试里的三类"假失败"**，认清它们能省很多时间：  ① **同名文本在多处出现** —— 模型名会同时出现在
  "模型表"与"用量表"里、"删除"会同时出现在模型行与供应商行；`getByText` / `getByRole(name)` 会报
  "Found multiple"，该用 `getAllBy*`，或按容器与 `title` 定位（**有文本内容的按钮，`title` 不是可访问名**）。
  同类容器也会重名：按用途分区后两个用途各有一条告警，`findByRole('alert')` 直接报"Found multiple"——
  用 `findAllByRole('alert')` 再按内容挑出要说的那条，否则用例会随着"又多一种告警"而随机变红；
  ② **跨渲染帧的竞态** —— 预设回填表单发生在 `useEffect` 里，比"下拉框出现"晚一帧，直接断言会读到空值，
  要用 `waitFor`；首帧就渲染出来的告警（如"尚未配置"）会在数据回来后**换一支文案**，断言前要先等数据到位；
  **满量跑又比单跑慢一个数量级**：同一个文件单跑 1.4 秒、满量跑（上千条并行）十几秒，
  默认 1 秒的 `findBy*` 于是偶发失败。这类用例断言的是**行为**而不是速度，把 `findBy*` 的超时给足
  （如 10 秒）比事后反复重跑省事——但**别用它掩盖真的没渲染出来**：超时只是把"慢"与"坏了"分开。
  **两处都要给**：`findBy*` 的 1 秒之外，还有 vitest **整条用例的上限**——
  重流程（开弹窗 → 通用选择器取数 → 回填 → 提交）满量跑会顶到它，报的是一句
  `Test timed out in 5000ms`，**看着像死锁，其实只是慢**。
  实测这类用例在不同次满量跑里"轮流"失败（`ReportAdminPage` 两条、`MenuAdminPage` 一条，
  各自单跑都通过），所以**全局上限已经抬到 20 秒**（`EOS.Web/vitest.config.ts` 的 `testTimeout`），
  不必逐条去写；个别特别重的链路仍可显式写上限以标明意图，内部每处等待再用 10 秒——
  这样真"没渲染出来"时，先失败的是里面那条会说话的断言，而不是一句干巴巴的超时；
  ③ **分句拼接的文案** —— 逐句查容易因断句调整而误报，直接断言容器整段 `textContent` 更稳；
- **`git add` 用目录白名单时，别漏掉同级项目**：测试项目在 `EOS.API.Tests`（与 `EOS.API` **同级**），
  `git add EOS.API EOS.Web` 覆盖不到它——后果是两个提交里的测试项目**根本编不过**，而本地因为工作区文件
  还在、构建与测试全绿，看不出任何异常。**提交后核对 `git status --porcelain` 是否为空**，是这类漏网唯一
  可靠的哨兵（这次就是靠它发现的，补提交后 HEAD 才恢复可构建）；
- **返回值的语义写进名字里**：`InsertModelAsync` 返回**新主键**、`CreateModelsAsync` 返回**条数**——
  批量实现里顺手 `created += await InsertModelAsync(...)` 就得到 8+9+10=27 这种"插了 27 条"的假象。
  这类错单测能抓（断言条数），代码评审常常看漏；
- **删"半删"的东西，要断言它保住的那一半**：知识库文档删除是"软删墓碑 + 物理移除向量"——行还在、
  状态变 `deleted`、检索不到。用例只断言"DELETE 发出去了"是不够的；确认框的文案（"向量会被同步移除"）
  与列表对墓碑的呈现都得钉住，否则很容易被后人改成真删而无感；
- **"现算"的页面要断言它真的读了服务端**：像"机制与工具总览"这种把代码现状摊开给人看的页面，
  它的价值全在"跟代码一致"。前端用例至少钉住"数据确实来自接口"（mock 返回什么就渲染什么），
  否则把它改成前端硬编码一份清单，测试照样会绿；
- **"闭环"要断言"没有发生别的事"**：声称"全程不离开当前界面"时，光断言功能成功不算数——
  挂一个路由探针（读 `useLocation` 的 `pathname`）断言操作前后路径不变，否则一次偷偷的 `navigate`
  在功能断言下照样绿（`AssistantDock.test.tsx` 与 `ActionCard.test.tsx` 都是这么断的）；
- **"确认事件单独成条"要分别断"多了一条"和"它与写入不是同一条"**：审计是追加表，断言一律取**增量**
  （前后计数相减），再按 `ACTION` 分别核对；顺带把"重放确认不重复写业务"也断上——
  同一次确认重放两次，业务写入 1 条而确认事件 2 条（**点击去重与写入去重是两件事**）；
- **"审计与业务同事务"要正向注入来证**：把审计写入阻塞住（另一个连接持表锁 + 短取消窗口），
  断言**业务回滚**（字段没被改、幂等占位被释放）；判别性再验一次——把审计改回"提交后 best-effort"，
  该用例必须变红。只断言"审计行存在"证明不了同事务；
- **"只作用于点名的对象"要有一个反向断言**：目标集合里有未被点名的同类对象，
  断言它**一个字段都没变**。少了这条，"目标化增改"与"整表重排"在测试里是同一种绿；
- **"不可预演的改动必须显式标注"要断覆盖率**：逐项断言"标了不可预演 ⇒ 一定有原因文案"，
  并断言报告的计数等于"可预演 + 不可预演"（不给静默留缝），同时断言输出里确实出现"无法预演"这句话——
  只断"没有报错"会把一条静默的缺口放过去；
- **前端组件测试关注行为**（点了会怎样、无权限时渲染什么），不测实现细节
  （内部 state、DOM 层级）。

## 八、把可复用的坑写进 `LESSONS.md`

[`LESSONS.md`](../../LESSONS.md)（仓库根）是**给干活的 Agent 看的坑清单**：一条一个坑，四段固定
〔触发／症状 → 根因 → 处置 → 防线〕；第四条写不出具体防线时就写"无（靠人记）"。

- **收尾时加**：任务里踩到的坑，只要"下次还会踩"就往末尾补一条；**一条只记一次事故**——
  再撞同一个坑就在原条目上补一句"第二次"的现象，不新开条目；
- **不记什么**：一次性故障、进度汇报、"当时是怎么想的"——那些是提交信息与 ADR 的活；
- **编号只增不改**：`L<n>` 是引用锚点（讨论里会写"见 `LESSONS.md` L7"），不重排、不回收空号，
  新增取当前最大号 +1；
- **门禁**：`scripts/check-docs.ps1` 校验它存在、编号连续无重复、每条四段齐全——
  **只查结构，不判内容对错**（"这条值不值得记"靠人守）；
- **与 guide 的分工**：`docs/guide/` 是按能力分册的**规范与约定**（长期有效、可被门禁盯着），
  这里记的是**踩过的坑与教训**（发生过、可复用）；同一件事两个角度都值得写时交叉引用，别复制正文。
