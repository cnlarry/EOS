# 06 测试与质量门禁

## 一、两端的入口

```powershell
# 后端（从仓库根执行，显式指定 csproj）
dotnet build EOS.API/EOS.API.csproj
dotnet test  EOS.API.Tests\EOS.API.Tests.csproj

# 前端
cd EOS.Web
npm run lint     # oxlint
npm run build    # tsc -b && vite build
npm test         # vitest run
```

`dotnet test` 必须显式指定 csproj：在错误目录下执行会**静默空跑且无输出**，
看起来"通过"，实际一个测试都没跑。

## 二、测试分三层

| 层 | 资产 | 依赖 | 何时跑 |
|---|---|---|---|
| 单元测试 | `EOS.API.Tests/*Tests.cs` 中不带 `Live` 的部分 | 无外部依赖 | 每次改动，提交前必跑 |
| 真库用例 | `EOS.API.Tests/*LiveTests.cs` | 可连的 `EOS.ERP` | 涉及领域规则、SQL、迁移时 |
| 端到端脚本 | `EOS.API.Tests/E2e*.ps1`、`Acceptance*.ps1` | 运行中的 API（部分还需前端） | 改接口、改流程、发版前 |

规模参考：后端约 240 个测试文件（其中约 100 个是真库用例）、约 50 个端到端脚本；
前端约 90 个测试文件。**你不必全跑**——按改动范围选层：

| 改了什么 | 至少跑到 |
|---|---|
| 纯函数、解析器、校验逻辑 | 单元测试 |
| 领域规则、SQL、元数据消费 | 单元 + 相关真库用例 |
| 接口、路由、权限门 | 单元 + 端到端脚本（只读端点优先） |
| 前端组件与页面 | `npm run lint` + `npm run build` + 对应组件测试 |

## 三、前端测试设施

- 配置在 `EOS.Web/vitest.config.ts`，环境为 jsdom；
- `src/test/setup.ts`：全局测试初始化；
- `src/test/renderWithProviders.tsx`：带 Provider（Query、路由等）的渲染辅助——
  组件测试用它，不要自己拼 Provider 栈；
- `src/test/apiMock.ts`：接口 mock 辅助。

组件测试与实现文件同目录、同名加 `.test.tsx` 后缀（如 `ErpTable.tsx` / `ErpTable.test.tsx`）。

## 四、真库用例的纪律

真库用例会连真实数据库，必须做到**跑完不留痕、不误伤既有数据**：

- 用例自己造键（料号、单号、库别等），**不要借用真实主档的取样值去写入**——
  借来的 `TOP 1` 值只允许用来读；
- 不要删除审计记录（审计按设计保留）；
- 数量承载表（库存余额、流水、批次账、预留、冻结）**不得按库别整体删**；
  库别是借用来的话，必须再加料号条件收窄。

> `scripts/check-live-fixture-hygiene.ps1` 专门静态检查这三条（见第五节）。

## 五、门禁脚本

`scripts/` 下另有一套**静态与连库门禁**，拦的是「编译与单测发现不了、只在运行时炸」的一类缺陷：
DI 漏注册、整页 500、迁移语法错、配置面白名单漂移、库存账务不平、样式类悬空等。

按改动范围挑着跑：

| 脚本 | 拦什么 | 依赖 |
|---|---|---|
| `scripts/check-di-registrations.ps1` | 控制器与效果处理器的依赖是否都在 `Program.cs` 注册 | 静态 |
| `scripts/check-migration-journal.ps1` | 迁移台账与磁盘脚本是否一致 | 连库 |
| `scripts/check-css-classes.ps1` | JSX 里的 `erp-*` 类名在 CSS 里有没有定义 | 静态 |
| `scripts/check-data-layer-boundary.ps1` | `EOS.API/Data/` 根目录不再变胖 | 静态 |
| `scripts/check-retired-db-objects.ps1` | 已退役的库对象不再被引用 | 静态 |
| `scripts/check-lifecycle-columns.ps1` | 生命周期列的结构口径 | 连库 |
| `scripts/check-required-columns.ps1` | 必填口径（留空即撞库约束） | 连库 |
| `scripts/check-field-labels.ps1` | 字段标签不是占位文本 | 连库 |
| `scripts/check-form-layout.ps1` | 版式结构、必填列不被隐藏 | 连库 |
| `scripts/check-validation-rule-parity.ps1` | 校验规则口径：库内 `MODULE_VALIDATION_RULE` 逐条落在代码闭集内、全部进入当前快照、参数结构合法，并（默认）跑真库用例逐条过运行时加载器 | 连库 + `dotnet test`（`-SkipRuntime` 只做前几层） |
| `scripts/check-system-params.ps1` | 系统参数定义与引用完整性 | 连库 |
| `scripts/check-snapshot-staleness.ps1` | 定义快照是否**静默落后** | 需 API 在线 |
| `scripts/probe-env.ps1` | 开工前环境预检（库可达性、端口、bin 是否落后） | 连库 |
| `scripts/check-docs.ps1` | 内部文档新鲜度 | git |
| `docs/guide/_tools/check-freshness.ps1` | 本手册与源码是否同步 | git |
| `scripts/check-agent-skills.ps1` | Agent 技能引用的资产是否还在、名实是否相符、是否过时 | 静态 + git |

三条使用要点：

1. **`check-di-registrations.ps1` 建议每次都跑**——它拦的是"编译 0 错、单测全绿，
   但端点全挂"那类问题（历史上出现过服务漏注册导致一整组端点全 500）；
2. **多数脚本带 `-SelfTest`**：用合成数据做正反自检。**改门禁脚本本身时必跑**；
3. **"棘轮"是什么**：有些门禁对存量问题允许既有命中，但**只减不增**——
   新增命中即失败，这样债不会继续累积。

连库类脚本需要可用的 `EOS.ERP` 连接，配置见 [02-本地环境与运行](./02-本地环境与运行.md)。

## 七、写测试的几条经验

- **测试名说清场景与预期**，不要用 `Test1`、`TestOk`；
- **断言要能失败**：只断言"没抛异常"的测试没有价值；
- **涉及门禁/白名单的改动，先想清楚反例**：能被绕过就说明白名单开得太宽；
- **涉及"客户端上报"的改动，正例反例都要断言**：自造的错误码/未知字段名/越权字段必须被**丢弃**
  （只断言"合法值能通过"是半个测试）；"打开即见"这类声称零成本的能力还要断言
  **没有触发模型调用**（前端断言未发起对话请求，后端断言该链路的构造参数里不存在模型依赖）；
- **涉及"界面状态随请求携带"的改动，断言请求体**：模拟选中行 / 改字段 / 触发服务端拒绝后，
  下一次请求体的对应字段必须随之变化，而不是断言组件内部状态；
- **前端组件测试关注行为**（点了会怎样、无权限时渲染什么），不测实现细节
  （内部 state、DOM 层级）。
