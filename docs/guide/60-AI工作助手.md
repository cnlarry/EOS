# 60 AI 工作助手

工作助手是内嵌在工作台里的 AI 助手。这篇讲它的**边界**与子系统——边界比功能更重要，
因为它是一条新增的数据通路。

**处境感知、对象级诊断、配置面、动作层与双重门禁**另见
[61-工作助手的处境与诊断](./61-工作助手的处境与诊断.md)（处境感知、对象级诊断、配置面只读、
动作层与就地操作卡、配置面写与对照卡均已交付；批核族的请求卡待交付）。

实现：`EOS.API/Features/Assistant/`（7 个子系统 + `ChatService.cs` + `Situation/` + `Actions/` + `Config/` + `Catalog/`）、
`EOS.API/Controllers/AssistantController.cs`、`AssistantRecordActionController.cs`、
`AssistantConfigController.cs`、`KbController.cs`。

## 一、四条不可逾越的边界

| 边界 | 含义 |
|---|---|
| **模型推理内聚在 `EOS.API`** | 前端不持有厂商密钥、不直连模型厂商；模型调用经受控抽象 `IChatModel` |
| **模型输出永不进入 SQL 或表达式解析器** | 助手不能成为绕过白名单与参数化的后门 |
| **业务数据读取只能由 `EOS.API` 授权提供** | 助手读数据走语义接口，权限与普通请求同一套 |
| **助手不得绕过 API 直接访问数据库** | 与所有调用者同等约束 |

配套的设计约束（写在 `IChatModel` 的契约里）：

> 实现只负责**出网调用与协议解析**，不做权限判断、不落库、不组装提示词、不执行工具。

也就是说：模型接入层是最薄的一层，所有决策都在 `ChatService` 与工具层。

## 三、会话与流式对话

路由前缀 `api/v1/assistant`，**全部端点登录可用**；**数据按 `USER_ID` 服务端强制隔离**。

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` / `POST` | `/sessions` | 分页列会话（`?state=active\|archived\|all`、`offset`、`limit`、`keyword` 只搜标题；返回 `{items,total}`） / 建会话 |
| `PUT` | `/sessions/{sessionId}/rename` | 重命名（标题非空，按库内 200 宽截断） |
| `PUT` | `/sessions/{sessionId}/archive` | 归档 / 取消归档（`Archived` 缺省视为 `true`——空 body 不该把会话取消归档） |
| `DELETE` | `/sessions/{sessionId}` | 永久删除会话（连消息，不可恢复）。**只对已归档会话开放**：服务端强制，未归档一律 400 `SESSION_NOT_ARCHIVED`（见下「会话管理页」） |
| `GET` | `/sessions/{sessionId}/messages` | 取历史消息（含 `toolCalls`，见下） |
| `POST` | `/sessions/{sessionId}/chat` | **流式对话（SSE）** |
| `GET` | `/situation` | 打开即见的处境快照（**零模型调用**，见 [61](./61-工作助手的处境与诊断.md)） |

### 两种形态：半屏抽屉与全屏标签

助手有两种落脚处，**同一时刻只有一种**：

| 形态 | 是什么 | 怎么进 |
|---|---|---|
| **半屏** | 右侧固定 520px 的抽屉（浮球唤起，`Ctrl+/` 开合，点抽屉外或 Esc 收起） | 浮球 / `Ctrl+/` / 全屏页的「半屏」按钮 |
| **全屏** | 路由 `/assistant` 的**普通工作区标签页**（与统一工作台同构：可并存、随工作区持久化、可深链） | 抽屉头部的「全屏」按钮 |

**换形态不改工作内容**——这是硬约束：会话状态与流式请求都在 `AssistantProvider`
（`features/assistant/AssistantProvider.tsx`）里，抽屉（`AssistantDock`）与全屏页（`AssistantPage`）
只是两个**壳**，都渲染同一个 `AssistantPanel`。所以切换形态时对话、工具卡、以及
**正在流式生成的回答**都不受影响（流式请求跑在 Provider 里，与壳的挂载/卸载无关）。

三条容易踩的连线：

- **`Ctrl+/` 永远是「开合抽屉」**：全屏页里由 `AssistantPage` 接管（展开抽屉 + 关掉本标签 = 回半屏），
  `AssistantProvider` 里的同名快捷键按路径**让位**，否则两边同时响应会把开关又翻回去；
- **全屏页不显示浮球**：助手已占满屏幕，"叫出助手"的入口是多余的，点它还会造出两种形态并存；
- **`useAssistant()` 的 `open` 只管半屏抽屉**，全屏由**路由**表达——不要把两者混成一个开关；
- **两种形态不会并存**：深链或刷新进 `/assistant` 时，`AssistantProvider` 按路径把抽屉收起，
  `AssistantDock` 同样不渲染它——否则 localStorage 里残留的 `open=true` 会让抽屉与全屏页同时出现；
- **全屏页是页级卡片**（圆角 + 边框），与其它页面同风格：`erp-tab-panel` 只是"卡片浮在浅灰底上"
  的那层底色，卡片本身要页面自己给；但**页面自己不要再加留白**——标签内容外面已有
  `container-fluid px-3 px-lg-4` 出左右 10px、`.erp-tab-panel` 出上下 10px，这就是设计语言的 10px
  页边距（这里曾多给一层，实测量出来是 20px）。

### 会话管理（头部菜单 ＋ 独立管理页）

助手头部「…」菜单四个动作：**重命名 / 导出为 Markdown / 归档（选中已归档时变"取消归档"）/ 会话管理**。

- **归档**：`ARCHIVED_AT` 非空即已归档——默认列表看不到它，但消息一行不动、随时可取消归档
  （列见迁移 `287_assistant_session_archive.sql`）。
- **重命名**走行内输入（Enter 提交、Esc 取消、失焦提交），只写 `TITLE` 一列。
- **导出**是纯前端把消息拼成 Markdown 再触发下载（`sessionExport.ts`）：**工具摘要单独留一节**，
  否则导出的历史看不出结论是从哪几个工具来的。导出不新增端点——内容本来就在手里。

**会话管理页**（`/assistant/sessions`）应对的是"会话一多，头部下拉就不够用"（条数有上限、不能筛、
看不到时间）：它是**普通工作区标签页**，与助手全屏页同构（可并存、可深链、随工作区持久化），
照 `FieldAdminPage` 的范式搭（`ErpListCard` + 搜索框 + 分页器 + react-query + Toast），
列出**标题 / 消息数 / 最近活跃 / 创建时间 / 状态**，行内可**打开**（切到该会话并拉出助手）
**重命名** **归档 / 取消归档** **删除**。三件容易搞混的事：

- **视图三态由服务端做**（`state=active|archived|all`）："只看已归档"若靠前端从含归档的结果里筛，
  分页与总数都会算错。未知取值一律按 `active` 处理（旧调用传 `archived=true` 也照常工作）。
- **消息数在列表查询里现算**（子查询 `COUNT`），**不是**存下来的列：它只用于"哪些会话还有内容值得留"，
  不值得为它加一列并维护一致性。
- **归档与删除是两件事**：归档＝收起来（可逆），删除＝连消息一起抹掉（不可逆）。**删除只对已归档会话
  开放**，且由服务端强制（未归档一律 400 `SESSION_NOT_ARCHIVED`，仓储 SQL 里另有
  `ARCHIVED_AT IS NOT NULL` 作第二重守卫，防止与"取消归档"并发交错时误删在列会话）；
  界面上该按钮只在已归档行出现，点前过 `window.confirm` 并写清"不可恢复"。

> 这是**口径变更**：原先是"界面完全不提供删除"（怕误删）。改成"先归档、再删除"两步后，删除只可能
> 发生在已经收起来的会话上，比原先设想的"在列表里直接删"安全；历史数据也终于有了一个真出口。
> 管理页与助手头部共用同一份会话状态（`AssistantProvider`）——任何一处改动都会把另一处一起刷掉，
> 不会出现"管理页删了、下拉里还在"。

### 管理面：菜单组 31（见 [ADR-030](../decisions/ADR-030-工作助手管理面.md)）

上面那套是**个人视角**（服务端按 `USER_ID` 隔离，只看自己的会话）。系统侧另有一套管理面，落在**根级菜单组
31「工作助手管理」**下，走模块号与 `SYSDH`/`SYSDD` 权限体系（授权行镜像 `2306`，见迁移
`288_assistant_admin_module.sql`）：

| 模块 | 内容 | 状态 |
|---|---|---|
| 3101 会话管理 | **跨用户**看会话元数据（归属用户 / 标题 / 消息数 / 时间 / 归档状态），可归档·取消归档、可删除**已归档**会话 | 已落地 |
| 3102 模型与用量 | **两级**：供应商（端点 / 密钥环境变量名 / 默认超时）→ 模型（标识 / 窗口 / 最大输出 / 单价 / 是否支持工具）。一页给全，可从**预设目录**选供应商并批量落库；增改与切换**切完立即生效，无需重启**；用量看板给当日总览与近 N 天**按模型**与**按天**聚合。**密钥不入库**：供应商行里只存环境变量名，密钥只写不读、永不回显 | 已落地 |
| 3103 知识库管理 | 集合与文档清单（可连软删墓碑）、删除（软删墓碑 + 物理移除向量）。**不开放入库**（仍走 2302 那条链路），界面显眼标明"检索与入库待嵌入接线" | 已落地 |
| 3104 机制与工具总览 | 只读：工具清单与风险分级、可代理动作（含幂等键与审计动作）、能力面边界；数据**现算**不缓存 | 已落地 |
| 3105 助手设置 | 助手**参数目录**的一页视图：按域分组（提示词 / 能力面 / 成本与熔断 / 处境 / 诊断 / 记忆 / …），取值存 `dbo.SYSSS`（`OWNER_MODULE = 3105`）；写门 `CanSetup(3105)`，保存即生效。另有「按用户覆盖」（见下「取值分三层」） | 已落地 72 项（含 **27 个工具开关**）；`CHAT` / `TOOL_LIMIT` / `KB` 与动作族开关随各自的消费改造分批 |

**助手参数是一套目录，不是一页表单**（[ADR-030](../decisions/ADR-030-工作助手管理面.md) §5）：参数的
**声明**在服务端代码 `EOS.API/Features/Assistant/Parameters/AssistantParameterCatalog.cs`（键 / 标题 / 域 /
类型 / 单位 / 说明 / 默认值 / 作用域策略 / **读取方**），**取值**在 `dbo.SYSSS` 的 `OWNER_MODULE = 3105`，
解释在 `AssistantParameterResolver`——**运行期快照与页面保存校验共用同一份解释**，所以不会出现
"保存时通过、生效时被忽略"。三条要记住：

- **目录与库按批同步生长**：每批交付"目录条目 + 库行 + 消费改造 + 门禁"四件套。一次把目标态全部落库，
  会让其中绝大多数在"没人读"的状态下出现在管理界面上——那正是这套框架要根除的形态；
- **读取方声明是活的**：每条参数必须声明 `Consumers` 符号，离线门禁
  （`EOS.API.Tests/AssistantParameterCatalogTests.cs`）逐条断言它在源码里出现，且**声明自己不算**
  （扫描时排除目录文件本身）；连库门禁（`AssistantParameterIntegrationTests`）比对目录与库的定义；
- **旧表已退役**：`dbo.ASSISTANT_SETTING` 由迁移 `294` 并入 `SYSSS` 后 `DROP`——平台里两张同构的
  参数表就是第二处真源，而参数的**唯一入口**是 `SystemParameterService`。

**`appsettings` 里的四个助手节已经取消**（`AssistantSituation` / `AssistantDiagnosis` /
`AssistantActionLimits` / `AssistantConfigWrite`）：那 36 项此前**既不在库里、也不在文件里**
（`appsettings.json` 里根本没写这四个节），只存在于代码默认值中。迁移 `297` 把它们并入 `SYSSS`，
消费方（处境预算、诊断读者与编排、两个动作服务、配置写）改经
**运行期参数视图** `RuntimeParameterView<T>` 取值——它实现 `IOptions<T>`，但每次访问都从运行期快照现取，
所以既不用改消费方签名，也没有第二份默认值。唯一保留 `Bind(…).ValidateOnStart()` 的是
`AssistantActionLimitsOptions`：那条管线现在只负责启动时的**红线守卫**。

**能力面可以关**（域 `CAPABILITY`，ADR-030 §7.3）：每个工具一条开关（键名 = `TOOL_` + 工具名转大写，
由 `AssistantToolKeys` 机械生成——**不手写**，离线门禁扫源码里的 `ToolName` 常量逐名比对）。
关闭是**双向**的：注册表既不发它的工具声明给模型（`Definitions` 里没有它），也不接受模型对它的调用
（`TryGet` 拒绝，且 `IsDisabledByParameter` 让调用方把"被管理员关闭"与"不认识这个名字"分开说——
混成一句"未知工具"会让一次配置看起来像系统故障）。
**开关标题是中文的**（`AssistantToolKeys.Labels`）：页面上不再显示 `search_records` 这类标识符，
而工具名保留在每条的说明里（查问题、对日志时要用）。标题表与工具清单由门禁断言一一对应——
少一个只会让标题退回标识符，多一个却会在页面上摆出一个"关掉它有用"的、管着不存在东西的开关。
标题按风险分层：读类"查看 / 列出 / 搜索"，试算类"试算："，执行类"执行："。

**红线工具面（批核族、权限授予类）没有注册项，因此也没有开关**：迁移里有断言挡住这类键。

**记录动作族也可以关**：`ACTION_INSERT` / `ACTION_UPDATE` / `ACTION_DELETE` 三条，判定落在
`AssistantActionGate`——预演与执行都从那里过，所以关掉之后这个动作在助手侧**根本走不下去**
（不是靠模型自觉不调）。被关时给的是原因码 `ACTION_DISABLED_BY_ADMIN` 与一句"已被管理员关闭"，
**与"你没有权限"分开说**：前者要去找管理员，后者要去申请权限，两件事。
这三个是助手参数里**唯一声明了模块层**的键（模块 · 收紧）——"这个模块不许助手删除"是一条真能生效的配置。

**行为常量也进了参数表**（批 E，迁移 300）：历史条数、上下文预留、工具轮数、工具结果与审计的截断长度、
记忆的阈值与长度上限、知识库的检索命中与入库切块——这些数字此前散落在 `ChatService` 的私有常量、
`MemoryDistiller`/`AssistantMemoryStore`/`KbChunker` 的公开常量里（其中"工具摘要 160""审计参数片段 200"
连常量名都没有），调它们只有"改代码重新部署"一条路。

两条读法上的提醒：
- `CHAT_MAX_TOOL_ROUNDS` 不只是"慢一点"：**成本预留 = 单次预留 ×（轮数 + 1）**，调大它按倍数占额度；
- `MEM_SUGGEST_THRESHOLD` 管的是**候选记忆自动转正**（达到此分直接生效并覆盖同名），不是界面上的一个标记——
  调低它等于放宽"什么会被自动记住"。

**工具输出上限也是参数**（批 E2，迁移 301）：`search_records` 返回几行、每行几列、单值截到多少字符，
明细与试算的截断长度，模块描述列几个字段，几个列表类工具返回几个模块——都在 3105 的「工具输出」组里。
它们**同时决定发给模型的说明**：注册表会按参数在每个工具的声明末尾追加一句上限
（"输出上限：最多 5 行、每行 8 列、单值 40 字符"）。工具类里不再写死数字，
所以不会出现"系统给了模型 10 行、说明里还写着 5 行"。

**REST 检索端点的条数上界**（`KB_ENDPOINT_MAX_HITS`，默认 20）：
`POST /api/v1/assistant/kb/search` 的 `TopK` 由调用方传入，原先**没有上限**，现在被夹在 1 与这个值之间，
响应里回显实际生效的条数。它与「一次检索的命中条数上限」是**两个**键——
后者管"进模型上下文几条"（token 预算），前者管"界面能翻出几条"；合成一个的话，
为省 token 调小工具上限会把检索页一起缩水，而界面上看不出这层关联。

**提示词里的行为规则随能力面派生**（ADR-030 §7.4）：三段规则（指标口径 / 诊断取证 / 知识通道）
各自点名自己需要的工具，**少一个就整条不注入**。否则提示词里会留下"必须先通过 `enum_metrics` 查口径"
这类硬要求，而那个工具已经被管理员关掉——模型只能违反规则，或者空转着去找一个不存在的工具。

**取值分三层：用户 → 模块 → 全局**（ADR-030 §6.2）。全局值在 `SYSSS`，上面两层在
`dbo.ASSISTANT_PARAM_SCOPE`（迁移 `296`），叠加在 `AssistantEffectiveParameters` 里完成——
它把覆盖**压到全局行上**再交给同一个解释器，所以取值口径仍只有一处实现。三条要记住：

- **层与策略是两件事**：`ScopeLayers` 说"允许出现在哪些层"，`ScopePolicy` 说"能往哪个方向走"
  （`Tighten` = 只能更严："关得掉、放不开"；`Override` = 可高可低）。**收紧型只能声明一层**，
  否则"比谁更严"没有唯一答案；两者必须成对声明，离线门禁 `ValidateCatalog()` 逐条断言。
- **快照是单例、作用域不是**：`AssistantRuntimeRegistry` 只持全局那一层，按当事人叠加放在**请求作用域**里
  （`IAssistantEffectiveParameters`，一次请求只查一次库）。把"某个人的限额"塞进单例，
  等于把它发给所有人。
- **"配了没人读"同样适用**：模块层此刻**没有任何参数声明可被覆盖**，所以模块级覆盖一律被拒——
  这是 fail-closed，不是 bug；各域的参数随消费改造分批声明 `Layers` 后才可选。
  3105 页面的「按用户覆盖」只列出服务端给的可选参数，界面不自己判断"这条应该能改吧"。

> 写门为什么不是通用设置端点那条：通用参数端点的写门是 `CanEdit`，而 3105 声明的是 `CanSetup`
> （改的是系统提示词与全局限额，比模型管理更要紧）。所以助手参数的入口挂在 3105 自己的控制器下，
> `ModuleForScope` 里没有 `assistant` 令牌。见 ADR-030 §4.3。

两条口径要记住：**管理面只看元数据、不提供对话正文**（要看正文是另一个需要独立权限位与审计留痕的决定，
不要因为"反正有 3101 读权限"就放开）；**个人侧不加权限守卫**（`/assistant` 与 `/assistant/sessions` 仍然
登录即可用），不要拿管理面权限去卡普通用户使用助手。

### SSE 事件

| 事件 | 含义 |
|---|---|
| `delta` | 文本增量 |
| `done` | 回复已落库，**含用量** |
| `error` | 流中失败 |

两个行为要记住：

- **客户端断开即中止模型调用**——不会继续烧 token；
- **半截回复不落库**，历史经 `GET /messages` 恢复。

### 回答的呈现（与界面的格式契约）

助手回答**按 Markdown 渲染**（GFM 子集），渲染器在前端 `EOS.Web/src/features/assistant/markdown.tsx`：
标题 / 段落 / 有序无序列表（含缩进嵌套）/ 围栏代码块 / 行内码 / 粗体斜体删除线 / 链接 / 引用 /
分隔线 / 表格（含对齐）。它**只产出 React 元素、不做 HTML 注入**，所以文本里的 `<script>`、
`<img onerror=…>` 一律当纯文本——**不需要 sanitizer**；链接也只放行 `http`/`https`/`mailto`/`tel`
与站内路径，其余 scheme（含 `javascript:`）按纯文本显示。知识库来源引用是裸文本 `kb://doc/{id}#c{n}`，
挂在行内文本钩子上，与 Markdown 各管各的。

因此 `AssistantSettings.SystemPrompt` 里必须保留**输出格式约定**（结论先行、分点用列表、
多字段对照用表格、字段名与表名单号用反引号、只输出 Markdown 不输出 HTML）：这是**与渲染面的契约**——
提示词不约定格式，模型就各写各的，界面上只剩标记本身。`AssistantSettingsTests` 把这条契约钉住，
改回纯文本即变红。

> 结构化草稿（`done.drafts` 的那些卡片）走的是另一条路：它们是**服务端下发的结构化数据**，
> 由各自的组件就地渲染，不经 Markdown。

**工具调用**按可展开的结果卡呈现：默认收起成一枚芯片（工具名已翻成中文，未登记的回落原名），
点开才显示这次调用拿回的内容（服务端截断的工具返回前 160 字）。摘要以 `rejected:` / `error:`
开头时用警示色标出、写作"未能完成"——"没查到"与"查到了"在界面上必须看得出区别。

摘要**跟着消息一起恢复**：`GET /messages` 把库内 `TOOL_CALLS_JSON` 投影成与 `done` 事件同形的
`toolCalls: [{ name, digest }]`（工具参数不下发；形状只在一处定义，前端不必懂两种形状）。
所以刷新、或切回历史会话后工具卡仍然在——它不该只存在于流式那一瞬。
助手回答另有**复制**按钮，复制的是 Markdown 原文而非渲染后的文本。

**消息的操作按钮在气泡外侧**（气泡下方的小字：复制、记住）——平时半透明、悬停该消息或键盘聚焦才实显，
不挤在正文里抢视线；宽度上限放在**消息行**上，气泡只负责自身外观与左右对齐，操作区随气泡对齐。
用户输入仍按原样保留换行（`pre-wrap` 只留给用户气泡），助手侧走 Markdown 渲染。

**抽屉的收起与菜单**：点抽屉以外、或按 Esc，抽屉收起——但**不是销毁**：气泡都在组件 state 里，
再点浮球原样回来。"..."菜单同理，点它之外就关。Esc 是"先收菜单、没有菜单时收抽屉"。

> **一个必须记住的既有竞态**：打开抽屉时会自动选中最近会话并回读历史（`GET /messages`），
> 而这次回读**可能晚于**用户刚发出的消息落地——若直接拿回读结果 `setBubbles`，
> 会把用户消息与正在流出的回答一起抹掉。前端因此按会话记一次"新建跳过"，并给历史加载加**代次**：
> 本地一开新一轮就让在途回读作废（`AssistantDock.tsx` 的 `skipHistoryRef` / `historyLoadRef`）。
> 改动这块时，既有的 `AssistantDock.test.tsx` 用例会以"偶发找不到卡片"提醒你。

网关（`AssistantSchemaGateway`、`WorkbenchSearchGateway`、`ModuleFlowGateway`）负责把工具调用
转换成**受权限约束**的内部查询。

**两条硬约束**：

1. **工具声明的 JSON Schema 由服务端硬编码，绝不接受客户端传入**（`ToolDefinition` 的契约）；
2. 工具执行的每次数据读取都走正常的授权路径——**助手不是特权调用者**。

**结构化草稿（`done.drafts`）**：Draft/Write 级工具可以随回复下发一张结构化卡，前端就地渲染。
现有六种，靠 `kind` 区分：`admin-changeset`（元数据变更集）、表单草稿（无 `kind`，带入表单）、
`record-action-preview`（就地操作卡）、`record-action-result`（执行结果）、
`config-diff`（配置改动对照卡：旧值/新值/影响面逐项列出、逐项可勾选）、
`config-apply-result`（配置改动的应用结果）。

**闭环与交互面**：涉及单据新增/修改/删除的，助手不再"生成草稿 → 跳走"，而是在**助手内就地成卡**
（`EOS.Web/src/features/assistant/ActionCard.tsx`）：卡片内改值 → 重算预演 → 确认执行 → 回读结果，
全程不离开助手。卡片为重算预演与确认执行各调一个端点
（`/api/v1/assistant/record-actions/preview|apply`），**不喊模型**——否则"用户点了确认"会变成模型自己做的决定，
还要为一次点击烧掉额度。工具与端点共用同一份参数契约、同一个服务端执行体；细节见
[61](./61-工作助手的处境与诊断.md)（第四节）。

## 五、模型接入

`IChatModel` 是最小流式接口：

| 成员 | 说明 |
|---|---|
| `ModelName` | 实际模型名，写入 `ASSISTANT_MESSAGE.MODEL_NAME` 与审计 |
| `IsConfigured` | 配置是否齐备；**不可用时以 `AI_MODEL_NOT_CONFIGURED` 快速失败，不影响 API 其余功能** |
| `StreamAsync` | 按序产出文本/工具调用增量与 usage 收尾帧 |

消息角色（`ChatRole`）：`System` / `User` / `Assistant` / `Tool`。

> `Tool` 角色**只存在于单轮内存上下文，不落库**。

### 当前模型可运行期切换（管理面 3102）

模型以前是**启动期单例绑配置**（`AddSingleton<IChatModel, DeepSeekChatModel>` + `IOptions<AssistantSettings>`），
进程跑起来就改不了。管理员要能在界面上换模型，就必须有一个**运行期可刷新的快照**：

- `AssistantModelRegistry`（单例）持"当前模型"，刷新点只有两处：**启动时**（迁移之后，照
  `WorkbenchDefinitionProvider` 的既有做法）与**管理员每次改动之后**——所以切换**不需要重启服务**；
- 消费方 `IChatModel` 注册为 **Scoped**（`ResolvingChatModel`）。改生命周期而不改 `ChatService`：
  它是 Scoped，本来就只按接口注入，于是一行都不用动。Scoped 还顺带消掉一个真问题——一条回答要跑
  好几轮工具调用，若中途有人切换模型，同一条回答会跨两个模型，而落库的 `MODEL_NAME` 只有一个；
- 表里没有启用的当前模型（或那一把密钥没配）就是**未配置**：助手以 `AI_MODEL_NOT_CONFIGURED` 失败
  并把话说清楚（**指路到管理页**），**没有任何"退回配置文件"的退路**（ADR-030 §8）。所以新增模型后
  要显式「设为当前」才会换；`GET assistant/availability`（登录即可访问）让前端在**打开助手时**就能提示，
  而不是等用户打完字发送才失败；
- 温度 / 最大 token / 供应商是 3102 带来的**新调节能力**，只在配了才进请求体：传 `null` 会被部分厂商
  当成非法值，而"不传"才是各家一致认可的"用默认"。

**密钥不入库**（ADR-030 §3）：密钥挂在**供应商**上（`dbo.ASSISTANT_PROVIDER.API_KEY_ENV_VAR` 只存
**环境变量名**），管理员在界面上输入的密钥被写进
环境变量（进程级立即生效 + 用户级持久化），**只写不读**，界面只显示"变量名 + 是否已配置 + 掩码末四位"。
受限账户写不了用户级变量时**不假装成功**：接口如实回 `persisted=false`，界面提示"重启后需重设"。
于是数据库备份、导出、诊断包里都不含密钥。

两道守卫值得记住：**密钥未配置的模型不能设为当前**（否则所有人的助手立刻不可用，而原因只写在服务端日志里）；
**当前模型删不掉**（否则助手会在无人察觉时退回配置那套）。"至多一条当前模型"由数据库的**筛选唯一索引**
保证，不靠应用代码自觉。

### 模型配置是两级的：供应商 → 模型

同一个供应商下本来就有多个模型（DeepSeek 的 Flash 与 Pro、OpenAI 的 4o 与 4o-mini），所以配置分两级：

| 表 | 装什么 |
|---|---|
| `dbo.ASSISTANT_PROVIDER` | 供应商 / 接入点：`CODE`、`BASE_URL`、**密钥环境变量名**、默认超时 |
| `dbo.ASSISTANT_MODEL` | 模型：所属供应商、模型标识、**上下文窗口**、最大输出、默认温度、超时覆盖、**单价**、**是否支持工具**、是否当前 |

**一个供应商一个端点、一把密钥，通吃它名下所有模型** —— 加第二个模型不必重复填端点与变量名；换一把密钥
也只改一处（密钥就挂在供应商行上，存的是环境变量名）。

**预设目录在代码里、不写种子数据**（`AssistantProviderCatalog`）：系统"知道"的供应商与模型（DeepSeek /
OpenAI / 百炼 / 智谱 / Moonshot / 自定义）连同端点、上下文窗口、是否支持工具一起内置，界面
"选供应商 → 自动罗列可用模型 → 勾选落库"靠的就是它。写种子数据会绕过"初始状态必须配置才能用"
（表非空即等于已配置）。**价格刻意留空**：各家单价随账号折扣与时段变动，留空时界面会明确告诉你"当前用的是
全局兜底价"。

**这几个字段是真的被消费的**（配了不用，等于没配）：

| 字段 | 消费点 |
|---|---|
| 上下文窗口 | `ChatService` 按窗口推预算裁剪历史：从最老的一端丢、**最新一条无论如何保留**；token 按"1 字符 ≈ 1 个 token"取**上界**估算（没有引入 tokenizer：估多了只是少带些历史，估少了会被厂商直接拒绝） |
| 单价 | 台账结算（`SettleAsync` 写进 `ASSISTANT_USAGE_DAY` 的钱）与用量看板都按**当前模型**的单价算；留空退回全局兜底价，**不按 0 元**——0 元会让日上限形同虚设 |
| 是否支持工具 | 不支持的模型不带 `tools` 去请求（否则厂商直接报参数不合法，而错误里看不出真正原因） |

**停用供应商 = 它名下所有模型一起下线**，不必逐个停用模型。

## 六、治理：成本与熔断

`Governance/AssistantGovernance.cs`。默认值（可按真实数据校准，校准走评估集回归）：

| 项 | 默认 |
|---|---|
| 全局日上限 | **50 元** |
| 用户日上限 | **5 元** |
| 每百万 token 输入 / 输出单价 | 1 元 / 2 元（按公示价，可校准） |
| 每轮预留额 | 0.05 元 |
| 连续失败阈值 / 冷却 | 3 次 / 60 秒 |

两个实现细节值得注意：

**单请求预留是"轮数感知"的**：实际预留 = 每轮预留额 ×（`MaxToolRounds` + 1），
覆盖工具多轮调用的最坏调用次数。这样并发请求不会把额度算穿。

**失败熔断只统计技术性失败**：

| 计入 | 不计入 |
|---|---|
| 模型错误、超时、空回复 | **权限拒绝**、**用户取消**、**限额触发** |

这条区分很重要：用户"没权限"或"自己取消"不该把账号熔断掉。
熔断状态是**按用户、进程内**的，服务重启即重置。

## 八、知识库

表：`KB_COLLECTION`（集合）、`KB_DOCUMENT`（文档）、`KB_CHUNK`（切块）。

| 组件 | 职责 |
|---|---|
| `KbIngestScanner` | **敏感数据拦截 + 业务引用抽取**（注意：它**不扫文件系统**，尽管名字像扫描器） |
| `KbChunker` | 切块 |
| `KbReferenceVerifier` | **引用校验** |

`KbController` 提供摄取与检索入口。**摄取是推入式**：正文由请求体传入，服务端没有"扫描某个目录并入库"的通路
（`docs/` 下的文档不会自动进知识库）——仓库文档由 `scripts/sync-guide-to-kb.ps1` 在仓库侧读盘、
补标题前缀后经**同一个入库端点**推入，不另造入库路径（三份处置见 [README](./README.md) 第五节）。

**集合分档即受众分档**：可见性挂在集合上（`ALL` / `CONSULTANT` / `OPS`），检索时按当前用户的
`CanSetup`（模块 2302 / 2306）过滤。组织级共享知识（`kb_general`）之外，开发手册两集合
`kb_guide_conventions`（规范与坑）与 `kb_guide_rationale`（设计动因）都是 `CONSULTANT` 档——
未获配置维护权限的账号检索不到。**跨表/跨受众的东西不要合并成一个集合**：
`docs/eos-development/` 是生成型业务知识（另一档受众），与手册不混灌。

**同来源重灌 = 新版本**：`SOURCE_URI` 标识来源（含节锚点），内容哈希未变**不入库**；
内容变了则旧行退役、新行 `VERSION` 递增（列由入库端点维护，调用方不必传）。

> 实测现状（2026-09-30）：`KB_DOCUMENT` 100 行、`KB_COLLECTION` 4 个，但 **`KB_CHUNK` 为 0**，
> 且这 100 行**全部是 `STATUS='deleted'` 的退役墓碑、且都在测试集合里**（活跃文档 0 条）。
> 切块要算向量，而向量模型尚未接线（`PendingEmbeddingModel` fail-closed）。
> 也就是说：**通道已建、检索在 embedding 就绪前不可用**，入库会以 `KB_EMBEDDING_NOT_CONFIGURED` 失败。
> 不要把"脚本跑通/文档已录入"当成"检索可用"；文档行数不是检索面的证据，**活跃文档数 + 切块数**才是。

## 九、指标与字段关系

`Metrics/` 子系统：

| 组件 | 职责 |
|---|---|
| `MetricRepository` / `FieldRelationRepository` | 指标定义与**字段关系**（`FIELD_RELATION` 292 行） |
| `MetricExpressionParser` / `MetricPlanCompiler` | 表达式解析与计划编译 |
| `MetricExecutor` | 执行 |
| `MetricDefinitionValidator` | 定义校验 |
| `SysMetricSchemaProbe` | 结构探测 |

指标由助手经 `EnumMetricsTool` / `ResolveMetricTool` 使用，
对应端点 `api/v1/report-metrics`。

**注意**：指标表达式的解析同样受控——模型不能直接生成表达式去执行。

## 十、变更集与写入

这是助手唯一能"改东西"的通路：

| 组件 | 作用 |
|---|---|
| `DraftRecordTool` | 生成**草稿**（不落库） |
| `ApplyChangeSetTool` + `ChangeSetService` | 应用变更集 |
| `FieldMetaWriter` | 字段元数据写入 |
| 端点 `POST /apply-changeset` | 应用入口 |

约束：

- 草稿与应用**分离**——生成草稿不等于改数据；
- 应用时走正常鉴权与校验，**不是"助手特权写入"**；
- 与普通写入一样进审计。

## 十二、边界与禁止事项

- **不要在前端持有厂商密钥或直连模型**——所有推理走 `EOS.API`；
- **不要把模型输出拼进 SQL、表达式或动态标识符**——这是红线；
- **不要让工具绕过权限**：工具读的每条数据都要走正常授权；
- **不要接受客户端传入的工具 Schema**——由服务端硬编码；
- **不要跳过草稿直接写**：写入走变更集，走鉴权，进审计；
- **不要把批核族动作加进助手动作面**：批核 / 解批 / 结案 / 取消结案是职权行使，只以「操作请求卡」形态交付（由用户点击、前端调既有端点），助手侧**不存在**注册项；
- **不要接受模型传入的幂等键**：执行类动作的幂等键由服务端从工具调用身份推导，schema 里没有这个字段；
- **不要去造第二条写 SQL**：助手动作一律经统一表单的既有写管线（见 [61](./61-工作助手的处境与诊断.md)）；
- **不要用"用户取消"去触发熔断**：失败熔断只认技术性失败；
- **不要把机制事实写进知识库或提示词**：机制问题走 `describe_mechanism` 从元数据与代码注册表现算，
  写进文档再检索就是第二真源（助手会偏向读文档，目录被架空），见 [61](./61-工作助手的处境与诊断.md) 第九节。

## 十三、排障

| 现象 | 原因 |
|---|---|
| 提示 `AI_MODEL_NOT_CONFIGURED` | 管理面没"设为当前"的模型，或那把密钥没配（两者都在 3102）；**其余 API 功能不受影响** |
| 某个参数改了没反应 | 该参数此刻没有读取方（3105 页面会标出"暂无读取方"）；或库里的值解析不了——页面顶部的告警条会逐项列出原因 |
| 对话报额度不足 | 触发了用户日上限或全局日上限（见第六节） |
| 连续几次失败后被挡住 | 技术性失败达阈值，进入冷却（默认 60 秒） |
| 断线后没有回复 | 设计如此：客户端断开即中止，半截回复不落库 |
| 助手说"没有权限" | 工具走的正常授权——**当前用户的模块权限不足，不是助手故障** |
| 记忆没生效 | 可能在 `pending` 待确认状态 |
| 知识库搜不到内容 | `KB_CHUNK` 为空：向量模型未接线，入库即失败（`KB_EMBEDDING_NOT_CONFIGURED`） |
| 用量与账单不一致 | 单价是可校准配置（默认按公示价），费用为估算 |
