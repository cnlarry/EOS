# 47 单据行为效果引擎

单据动作的业务逻辑（"批核时联动这张表""保存后汇总到主表"）**不写死在代码里**，而是配成
**效果链**。这篇讲这套机制：怎么配、怎么执行、边界在哪。

实现：`EOS.API/Data/Effects/`（引擎与处理器）、`EOS.API/Data/DocumentActions/`（动作目录）、
`EOS.API/Data/BusinessActionCatalog.cs`、`EOS.API/Data/EffectStructSchemas.cs`（参数结构）。

## 一、核心概念

| 概念 | 含义 |
|---|---|
| **触发事件** | 什么时机执行（保存后、批核时、结案时……） |
| **业务动作** | 一条配置记录，绑定"模块 + 事件 + 一串效果步骤"。也承载自定义按钮 |
| **效果键** | 一步效果的实现标识（如 `inventory-move`、`detail-rollup`） |
| **参数结构** | 该效果键需要哪些参数（`PARAM_STRUCT`） |
| **效果计划** | 运行时把配置解析成的可执行结构（`ModuleEffectPlan`） |

配置表：

| 表 | 行数（实测） | 内容 |
|---|---|---|
| `MODULE_BUSINESS_ACTION` | 349 | 业务动作（效果链头） |
| `MODULE_BUSINESS_ACTION_OP` | 633 | 效果步骤与公式操作行 |
| `MODULE_VALIDATION_RULE` | 187 | 保存期校验规则目录 |

## 二、七个触发点

`EffectEvent`（`EffectPlanModels.cs`）：

| 事件码 | 含义 |
|---|---|
| `SAVE` | 保存后 |
| `APPROVE_EFFECT` | 批核时 |
| `DEAPPROVE` | 解批时（批核链的镜像，也需要状态位） |
| `ENDCASE` | 结案时 |
| `UNENDCASE` | 取消结案时 |
| `DELETE` | **删除前校验**：删除不产生"保存后行为"，但受保护的行（如哨兵行）要拦下 |
| `MANUAL` | **用户主动触发**，不由单据事件触发；**效果链不会执行这类动作**，映射在此只为让事件码是同一份闭集 |

`EffectEventMapper.TryParse` 是事件码的**唯一解析入口**，大小写不敏感。

## 三、效果键注册表：闭集

`EffectRegistry.Keys` 是"**这个动作能不能执行**"的唯一依据，当前 46 个键，四种状态：

| 状态 | 含义 |
|---|---|
| `Formula` | 由**公式解释器**执行，消费 `MODULE_BUSINESS_ACTION_OP` 里的操作行 |
| `Service` | 由**注册的服务处理器**执行，参数来自参数结构 |
| `Pending` | 翻译数据用占位行 + 参数，**处理器还没建** |
| `Reserved` | 在目录里注册但**没有配置实例**（如 `meta-link`、`flow-trigger`、`job-enqueue`） |

`IsImplemented` 只认 `Formula` 与 `Service`。

### 闭集原则（最关键的设计）

> **管线拒绝未实现的效果键，而不是猜着执行。**

配置里出现 `Pending` / `Reserved` / 未知键时，执行阶段直接拒绝。这条保证了
"配置写错了"表现为**明确的失败**，而不是静默什么都不做。

另一条同样重要：

> **模块行为绝不按注册表分支。**

注册表只回答"这个键能不能跑"，不参与业务判断。也就是说，不要写
"如果是 X 模块就走 A 路、否则走 B 路"——模块差异应该由**配置**表达。

### 现有键的分类（部分）

| 类别 | 键 |
|---|---|
| 库存 | `inventory-move`、`half-stock-move`、`balance-adjust`、`inventory-release-by-source`、`stocktake-scope-generate`、`depot-sentinel-location` |
| 状态 | `set-state`、`completion-close`、`card-sibling-close` |
| 汇总与回填 | `detail-rollup`、`detail-flag-and-rollup`、`field-accumulate`、`adjust-projection`、`field-copy`、`link-stamp`、`stamp-last-activity` |
| 同步（跨单据/跨表） | `pur-purchase-sync`、`pur-apply-sync`、`cus-account-sync`、`sfc-plan-sync`、`detail-field-sync`、`fields-metadata-sync` |
| 价格 | `client-price-sync`、`supplier-price-sync`、`quote-parameter-recalc`、`callback-reprice` |
| 变更单 | `order-change-apply`、`purchase-change-apply`、`produce-change-apply` |
| 人事 | `hr-usage-sync`、`employee-contract-sync`、`employee-dimission-sync` |
| 清理 | `wage-month-doc-prune`、`doc-orphan-prune` |

> 从审计里也能看出效果链在做什么：效果执行的审计动作带 **`EFFECT:` 前缀**
> （如 `EFFECT:detail-rollup`），见 [30-审计日志](./30-审计日志.md)。

## 四、效果计划的模型

配置在运行时被解析成 `ModuleEffectPlan`，其组成：

| 模型 | 含义 |
|---|---|
| `EffectSourceRef(Scope, Table, Field, Constant)` | **取值来源**：作用域 + 表 + 字段，或常量 |
| `EffectTerm(Field, Coef)` | 参与计算的项：字段 + 系数 |
| `EffectMatchItem(TargetColumn, Source)` | 匹配项：目标列 ← 来源 |
| `EffectOpPlan` | 一步操作 |
| `EffectActionPlan` | 一个动作（含若干操作） |
| `EffectValidationPlan` | 校验计划 |
| `ModuleEffectPlan` | 模块级计划（顶层） |

`EffectSourceRef` 的 `Scope` 决定取值范围（当前行 / 明细行 / 关联行），
`Constant` 走的是**服务端常量**，不是前端传值。

## 五、执行与追踪

执行会产生可观察的轨迹（用于模拟与排障）：

| 模型 | 含义 |
|---|---|
| `EffectStepOutcome` | 步骤结果 |
| `EffectColumnChange(Name, Before, After)` | 列级变更 |
| `EffectRowChange(Identity, Columns)` | 行级变更 |
| `EffectOpTrace` | 操作轨迹 |
| `EffectStepResult` | 步骤结果汇总 |

**模拟**（`EffectSimulationService`）让实施人员在**不真正改数据**的前提下看到
"这次动作会改哪些行、哪些列、从什么变成什么"。改效果配置后先用它验证。

相关守卫：

- `EffectParamPhysicalGate` / `EffectParamPhysicalValidator`：参数引用的物理列必须真实存在；
- `EffectValidationExecutor`：校验计划的执行；
- `EffectReverseCompatibility`：反向（解批/取消结案）路径的兼容处理。

## 六、效果链与生命周期状态位

效果链把状态位当作**守卫与读条件**，所以：

- 行内状态（`CONFIRM_TAG` / `FINISHED_TAG`）保证触发点语义一致；
- 反向事件（`DEAPPROVE` / `UNENDCASE`）是正向链的镜像，**同样需要状态位**；
- 模块只要启用了效果引擎（`EFFECT_ENGINE_TAG`）或声明了批核/解批效果链，
  就**必须具备对应状态位**——这条由发布校验强制，见 [48-生命周期与审批流](./48-生命周期与审批流.md) 第七节。

**状态位挡住编辑时说的是一句话**：`WorkbenchCommandHandler` 的
`FINISHED_EDIT_FORBIDDEN` / `CONFIRMED_EDIT_FORBIDDEN` / `FLOW_IN_PROGRESS_EDIT_FORBIDDEN`
三类拒绝文案与错误码统一登记在 `EOS.API/Data/Workbench/LifecycleEditGuards.cs`，
诊断侧引用同一份——**不许各写一句**：两份文案必然漂移，而用户会同时看到它们。
同理，`MasterFieldWriteHandler` 的引擎维护列集合与"由引擎维护，不允许人工修改"这句文案
也是**单点**（诊断侧按列名复用），改维护列范围只需改一处。

## 七、业务动作与自定义按钮

`MODULE_BUSINESS_ACTION` 同时承载两类东西：

1. **事件驱动的效果链**（保存/批核/结案时自动跑）；
2. **用户主动触发的动作**（`MANUAL`）——即统一表单工具栏上的**自定义按钮**。

自定义按钮的规则（见 [03-工程规范与硬约束](./03-工程规范与硬约束.md)）：

- 只在**浏览态**出现；
- **单据级**追加在"帮助"之后按序号排列；**明细级**另占子表标题栏右侧；
- **未获授权的用户不渲染该按钮**（fail-closed 名单，服务端另行鉴权）；
- 执行入口是 `POST /api/v1/document-workbench/{moduleId}/action/{actionKey}`。

服务端侧的动作目录在 `EOS.API/Data/DocumentActions/` 与 `BusinessActionCatalog`，
按钮文案在 `BusinessActionLabels`。

## 八、实施侧：配置一个效果

1. 确认**效果键已实现**（在 `EffectRegistry` 里是 `Formula` 或 `Service`）；
   不存在就先按第十节扩展；
2. 确定**触发事件**（`SAVE` / `APPROVE_EFFECT` / ……）；
3. 按该键的**参数结构**（`EffectStructSchemas`）填参数——参数里引用的表/列必须真实存在；
4. **先模拟**：用模拟探针看会改哪些行、哪些列；
5. 保存后跑一次**定义发布**（见 [41-定义快照与发布](./41-定义快照与发布.md)），否则运行时看不到；
6. 用一条真实单据走一遍，再看审计里的 `EFFECT:` 记录确认链路跑通。

## 九、排障

| 现象 | 原因 |
|---|---|
| 动作执行报"未实现的效果键" | 配了 `Pending` / `Reserved` / 未知键——这正是闭集在起作用，不是 bug |
| 效果没跑 | 事件码写错；或模块未启用效果引擎；或定义未重发布 |
| 效果跑了但数据不对 | 用模拟探针比对该改的行列；再看审计里的 `EFFECT:` 明细 |
| 参数报错"列不存在" | 参数引用的物理列被删或拼错（发布期与运行期都比对） |
| 解批不生效 | 反向链是独立的，要单独配 `DEAPPROVE` |
| 删除被拦 | 配了 `DELETE` 事件的删除前校验（这是设计意图，不是故障） |
| 自定义按钮不显示 | 未授权（fail-closed）；或该动作没配 `MANUAL` 事件；或按钮配置未发布 |

## 十、扩展：新增一个效果键

1. 在 `EffectRegistry.Keys` 登记键名与状态；
2. 若是服务型：在 `EOS.API/Data/Effects/ServiceEffectHandlers/` 实现处理器，
   并在参数结构（`EffectStructSchemas`）里声明参数；
3. 若是公式型：确认公式解释器能表达所需的运算，并把操作行格式定下来；
4. **键必须有非空的人话说明**——配置界面要展示它，空说明会露出英文码；
5. 补测试：正例（能正确执行）+ 反例（参数非法时拒绝）；
6. 若该键会写库存类表，注意它可能构成**绕过库存移动引擎的写入旁路**，
   需要按库存收口的口径登记与自证。

## 十一、注意事项

- **不要把业务规则写成 C# 分支**：这正是效果引擎要取代的东西。领域代码应处理
  "引擎本身的能力"，而不是"某模块的特殊流程"；
- **效果是配置，配置要发布**：改完不发布，运行时按旧定义跑；
- **反向链要单独配**：解批、取消结案不是"自动回退"，各自有链；
- **先模拟再上生产**：效果链一次会改多张表，模拟成本远低于事后修数。

## 收口（批核阶段的声明式校验新增一个 handler）

- `custom-validation` 的注册表新增 `detail-required-on-approve`（`Data/Effects/DetailRequiredOnApproveGuard.cs`）：**明细表按本单主键零行即拒绝批核**，只按模块定义（主表/明细表/主键序）判，**不认模块号**；参数只有可选的 `message`。第一个用它的是月结单（迁移 331，挂在 `APPROVE` 阶段，文案"该期快照尚未生成（明细为空），不能关账：请先生成快照。"）。
- 与 `line-require` 的分工：后者管"某明细**字段**在触发条件下必填"，管不了"**一行明细都没有**"；新 handler 管的是**行数**。
- 能挂在哪由阶段映射（`EffectPipeline.ValidationStagesByEvent`）决定：`Save→SAVE`、`ApproveEffect→APPROVE`、`Deapprove→DEAPPROVE`、`Delete→DELETE`；结案/取消结案与用户点击**不带校验闸**（映射为 null），挂不进去。
