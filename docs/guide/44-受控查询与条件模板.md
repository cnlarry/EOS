# 44 受控查询与条件模板

## 一、为什么不能把 SQL 交给前端

列表的查询条件是用户在界面上拼出来的，天然是外部输入。所以：

> **前端提交的是"结构"，不是 SQL。** 服务端把结构编译成参数化 SQL。

结构的最小单元是三元组：

```
字段 + 运算符 + 值
```

字段名要过白名单，值一律参数化，运算符来自固定的算子表。三者任一不受控就会开出口子。

## 二、算子表：唯一真源

实现：`EOS.API/Data/Query/QueryConditionRenderer.cs`。

| 运算符 | 生成的谓词 | 说明 |
|---|---|---|
| `eq` / `ne` | `=` / `<>` | 相等 / 不等 |
| `gt` / `gte` / `lt` / `lte` | `>` / `>=` / `<` / `<=` | 比较 |
| `contains` / `notcontains` | `LIKE '%值%'` / `NOT LIKE '%值%'` | 包含 |
| `startswith` / `endswith` | `LIKE '值%'` / `LIKE '%值'` | 前缀 / 后缀 |
| `empty` / `notempty` | `IS NULL OR =''` / `IS NOT NULL AND <>''` | 空 / 非空（不需要值） |
| `between` | `BETWEEN 值 AND 值2` | 区间，用两个参数 |

要点：

- **运算符不受支持时抛异常 → 400**，错误信息里带原始运算符，便于定位；
- `between` 的两个端点用 `参数名` 与 `参数名b` 两个独立参数，不是字符串拼接；
- **这张表是唯一真源**：工作台列表查询（`WorkbenchQueryComposer`）与统一选择器的高级查询
  （`ChooserConditionBuilder`）共用同一个渲染器。**加算子只改这一处**——历史上两处各有一份
  逐字相同的算子表，改一处漏一处会让两个入口对同一运算符给出不同结果。

### 条件数量与逻辑连接

- 单次查询条件数上限 **20**（`QueryConditionRenderer.MaxConditions`），超出即拒；
- 逻辑连接只支持 `AND` / `OR`，实现上给每条条件加前缀（首条的前缀在合并时去掉），
  整体用括号包裹；
- 值全部通过 `SqlCommand.Parameters` 登记——**渲染器不做字段白名单判断，
  列表达式由调用方按各自白名单解析后传入**。新入口要自己做白名单。

## 三、条件模板的存储

| 表 | 行数（实测） | 内容 |
|---|---|---|
| `SYSQR_DEFAULT` | 1323 | **模块默认查询条件**：`M_IDX` + `SERIAL_NO` + `F_ID` / `F_TYPE` / `F_EXPR` / `F_DESC` / `F_VALUE` / `PARA_NAME` / `FILTER_TEMPLATE` |
| `SYSQR_USER` | 1180 | **用户个人条件值**：`USER_ID` + `M_IDX` + `SERIAL_NO` + `F_TAG` + `F_VALUE` |
| `SYSQL_CONDITION` | 376 | **高级查询条件**（用户保存的条件行） |
| `SYSQR_DA` | 240 | 模块模板**头**：`M_IDX` + `REMARK` + 归属（`CI` / `OWNER` / `OWNER_G`）+ 审计列；对比上一行可见它**没有条件列**，条件行在 `SYSQR_DEFAULT` |

`SYSQL_CONDITION` 的列值得单独记一下（注意列名按库内实际拼写）：

| 列 | 含义 |
|---|---|
| `STEP_ID` | 步骤/行标识 |
| `USER_ID` | 归属用户 |
| `T_ID` / `T_ID_R` | 主表 / 目标表（与列配置同口径） |
| `F_ID` / `F_DESC` | 字段名 / 显示名 |
| `LEFT_KH` / `RIGHT_KH` | **左括号 / 右括号** |
| `OPERATOR` | 运算符（对应第二节的算子） |
| `CENTENT_KEY_1` / `CENTENT_DESC_1` | 条件内容与显示文本（列名如此拼写，不是笔误） |
| `LOGIC` | 与下一条的连接词（`AND` / `OR`） |
| `IS_USE` | 是否启用 |

**条件随模块**：这些表的 `M_IDX` 指向**归属模块**，不是承载页。

## 四、服务端怎么消费

```
前端提交 { conditions: [ { field, operator, value, valueTo, logic }, ... ] }
   ↓
校验字段是否在模块定义的可见列白名单内（不可见字段一律拒绝）
   ↓
QueryConditionRenderer.Render(...) 逐条渲染为参数化谓词
   ↓
合并数据范围过滤（AND）
   ↓
执行
```

两个容易漏的点：

1. **字段白名单来自模块定义**——连字段都不在定义里，更谈不上查询；
2. **数据范围是 `AND` 合并进来的**，不是可选项。前端提交的条件再宽，
   也突破不了用户自己的行级范围（见 [21-授权模型](./21-授权模型.md)）。

## 五、前端

| 位置 | 用途 |
|---|---|
| `EOS.Web/src/components/common/ErpQueryBuilder.tsx` | 条件构建器 UI |
| `EOS.Web/src/components/common/queryCondition.ts` | 条件模型与序列化 |

前端**不定义运算符语义**——下拉里的算子来自服务端口径，值原样提交，
不做本地过滤（本地过滤只会让"界面上有、后台没有"更难看）。

## 六、加一个算子

1. 在 `QueryConditionRenderer.Render` 的 switch 里加分支（**只此一处**）；
2. 需要两个值的（如 `between`）用两个参数名；
3. 同步更新前端构建器的运算符清单；
4. 补测试：**正例**（能正确过滤）+ **反例**（未知运算符被拒）；
5. 若该算子对两条入口（工作台 / 选择器）都开放，两边都要验。

## 七、排障

| 现象 | 原因 |
|---|---|
| 返回 400 且提示"无效查询运算符" | 前端传了算子表外的值；或大小写/空格不匹配（渲染器会 `Trim` + 转小写） |
| 400 且提示条件数超限 | 超过 20 条，需在前端分批或合并条件 |
| 用某字段查询始终无结果 | 该字段不在模块定义的可见列里，被白名单拦掉 |
| 工作台能查、选择器查不出 | 两条入口的字段白名单不同——渲染器共用，白名单各管各的 |
