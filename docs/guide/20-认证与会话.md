# 20 认证与会话

认证相关实现集中在 `EOS.API/Security/` 与 `EOS.API/Controllers/AuthenticationController.cs`。
**授权**（谁能看哪个模块）是另一件事，见 [21-授权模型](./21-授权模型.md)。

> `EOS.API/Security/PermissionModules.cs` 是**权限资源模块号的集中定义**
> （如 `SystemManagement = 2306`、`AssistantAdmin.SessionAdmin = 3101`、`AssistantAdmin.Mechanism = 3104`）：控制器里一律引用常量，
> 不在调用点散落裸数字。新模块的权限门先在那里登记，再到控制器里用。

## 一、端点一览

路由前缀 `api/v1/auth`。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/auth/login` | 登录，`[AllowAnonymous]` |
| `PUT` | `/api/v1/auth/password` | 自助改密，需登录 |
| `POST` | `/api/v1/auth/logout` | 登出，需登录 |

登录成功后返回 `{ userId, employeeName }`，同时下发会话 Cookie。

## 二、口令

### 存储

口令以 **PBKDF2-SHA256** 现代哈希存储，不存明文、不做可逆加密。
比对由服务端完成，口令永不回传前端。

### 策略（服务端唯一权威）

`EOS.API/Security/PasswordPolicy.cs`：

| 项 | 约束 |
|---|---|
| 长度 | **8 – 64** 个字符 |
| 首尾 | **不能以空格开头或结尾** |

管理员设密码与用户自助改密走**同一套校验**。前端可以给提示，但服务端才是判定方。

### 改密

`PUT /api/v1/auth/password`，请求体含当前密码与新密码。失败分支：

| 情况 | 返回 |
|---|---|
| 用户不存在 | 404 |
| 当前账号尚未设置密码 | 400，提示联系管理员分配初始密码 |
| 当前密码不正确 | 400 |
| 新密码不符合策略 | 400 |

改密**独立限流**（键为 `pwd|用户名|IP`），不复用登录的失败计数。

## 三、登录限流与临时锁定

实现：`EOS.API/Security/LoginThrottleService.cs`。

| 参数 | 默认值 |
|---|---|
| 失败阈值 | 5 次 |
| 统计窗口 | 10 分钟（滑动窗口） |
| 锁定时长 | 15 分钟 |

- 限流维度是 **「规范化用户名 + 客户端 IP」**——同一 IP 换用户名、或同一用户名换 IP，都各自计数；
- 达到阈值后返回 **`429`** 与错误码 `LOGIN_LOCKED`，消息里带剩余分钟数；
- **登录成功会清零**该键的失败计数；
- 实现是**进程内**的（`ConcurrentDictionary`）。单机部署够用；
  多实例部署必须换成共享存储，否则限流形同虚设。

> **限流日志的关联键（2026-09-29）**：登录与改密的限流/锁定 Warning 记的 `correlation`
> 取自 `RequestContext`，与响应体、请求日志、审计同值——按用户给的报障编号能一次检索到
> "他在被锁定期间还试了几次"。口径依据见
> [`docs/decisions/ADR-025`](../decisions/ADR-025-关联键单一真源与日志脱敏接入.md)。

失败返回的错误码区分具体原因，便于前端给出准确提示：

| 错误码 | 含义 |
|---|---|
| `LOGIN_INVALID_INPUT` | 用户名或密码为空 |
| `LOGIN_USER_NOT_FOUND` | 用户名不存在 |
| `LOGIN_INVALID_PASSWORD` | 密码不正确 |
| `LOGIN_DISABLED` | 账户已被禁用 |
| `LOGIN_LOCKED` | 失败次数过多，临时锁定（429） |

> 注意：区分"用户不存在"与"密码错误"会把用户名可枚举性暴露出去。
> 当前是内网 ERP 场景，可接受；若要收紧，把两者合并成同一条消息即可。

## 四、会话

- 认证方案是 **Cookie**（`CookieAuthenticationDefaults`），不是 Bearer Token；
- 记住我（`RememberMe`）时有效期 30 天，否则为会话 Cookie；
- Cookie 为 `SameSite=Lax`——**跨站表单提交不会携带会话**；
- 前端不需要手工管理令牌：登录后浏览器自动带上，请求失败拿到 401 即跳登录。

### Claims

登录时写入的声明，后端可从 `HttpContext.User` 取：

| Claim | 内容 |
|---|---|
| `NameIdentifier` | 用户 ID（`SYSDL.USER_ID`） |
| `Name` | 员工姓名 |
| `employee_id` | 员工编号 |
| `department_id` / `department_name` | 部门 |
| `company_id` | 公司别 |
| `default_group_id` | 默认用户组 |

后端取当前用户请用 `EOS.API/Security/CurrentUserContext.cs`，不要在各处直接翻 `HttpContext.User`。
它把上表的声明都读出来：`UserId` / `EmployeeName` / `EmployeeId` / `DepartmentId` /
`DepartmentName` / `CompanyId` / `DefaultGroupId`。

两条纪律：**声明缺失时返回空串而不抛错**（少一个声明不该让端点 500）；这些属性是**身份事实、
不是授权**——能不能办事只由权限服务判定，见 [21-授权模型](./21-授权模型.md) 第八节。

## 五、同源校验（CSRF 纵深防御）

实现：`EOS.API/Security/SameOriginGuardMiddleware.cs`。

对 `/api` 下的 **POST / PUT / PATCH / DELETE**：

- 请求带 `Origin` 头时，只接受**同源**（Host 与端口一致）或在
  `Security:AllowedOrigins` 白名单内的来源，否则返回 **403**；
- **不带 `Origin` 头的非浏览器客户端不受影响**（curl、脚本、服务间调用照常）。

这是第二道防线——第一道是 `SameSite=Lax` Cookie。

前端跨端口开发（Vite 与 API 不同端口）时，把前端来源加进 `Security:AllowedOrigins`。

## 六、前端怎么用

| 位置 | 作用 |
|---|---|
| `EOS.Web/src/features/auth/AuthProvider.tsx` | 提供当前用户、`hasPermission`、登录/登出 |
| `EOS.Web/src/features/auth/authContext.ts` | 上下文类型 |
| `EOS.Web/src/features/auth/RouteGuards.tsx` | 路由级守卫，无权限渲染 `ForbiddenPage` |
| `EOS.Web/src/features/auth/modulePermissions.ts` | 权限键工厂 |
| `EOS.Web/src/features/auth/LoginPage.tsx` | 登录页 |

应用初始化时调 `GET /api/v1/app/bootstrap`（`ApplicationController`）取回用户、权限与菜单树。

## 七、两条容易搞混的边界

1. **前端 `hasPermission` 不是安全机制**。它只决定"路线是否可进、按钮是否渲染"。
   服务端每个请求都会重新授权——绕过前端界面直接调接口，该 403 还是 403。
2. **认证 ≠ 授权**。登录成功只说明"你是谁"，不代表"你能看这个模块"。
   前者是本章，后者见 [21-授权模型](./21-授权模型.md)。
