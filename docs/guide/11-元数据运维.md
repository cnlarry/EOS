# 11 元数据运维

## 一、改元数据的三条途径

| 途径 | 适用 | 是否进版本控制 |
|---|---|---|
| 后台维护页 | 日常调整：字段标签、列宽、列配置、菜单、模块业务配置 | 否（只改库） |
| **迁移脚本** | **任何需要提交的改动** | 是 |
| 直接改库 | 仅排障定位，改完必须补迁移 | 否 |

**判断标准很简单**：这个改动别人拉下代码后需不需要？

- 需要（新模块、新字段、新列配置、新默认列、版式调整）→ **必须写成迁移**，
  否则别人建出来的库界面残缺，而且不缺报错——只是"某个模块没菜单""某个字段不显示"。
- 不需要（某用户自己调的列顺序、临时试的列宽）→ 后台页面即可。

迁移的写法见 [05-数据库迁移与建库](./05-数据库迁移与建库.md)：元数据种子写在迁移里，
**幂等**（先判断存在性再写），与结构改动可以放在同一个脚本里。

## 二、常见的维护任务

### 加一个新模块

按顺序做，缺一步就会出现"菜单在但页面打不开"这类半成品状态：

1. **`TABLES`**：登记主表（`T_ID`、`T_DESC`、`T_KIND='P'`）；有明细表再登记一行 `T_KIND='S'`；
2. **`FIELDS`**：为新表登记字段（每列一行，`T_ID` + `F_ID`）。
   至少要把主键列、必填列标清楚——`IS_PK`、`IS_VERIFY`；
3. **`MODULES`**：加模块行。关键列：
   - `M_IDX`：模块编号（唯一）；
   - `M_P_IDX` / `M_ROOT_IDX` / `SORT_IDX`：挂到菜单树的位置；
   - `M_DESC`：菜单显示名；
   - `MASTER_TABLE` / `DETAIL_TABLE`：绑定第 1 步登记的表；
   - `M_URL` / `NEW_URL` / `MODI_URL`：浏览 / 新增 / 修改路由。
     **留空即表示该能力不开放**——只读模块就让后两个留空；
   - `CONFIRM_TAG`：需要批核就置位，**主表必须有对应的状态位列**，否则门禁会拦；
   - `FORM_BUTTONS`：配置该模块出现哪些动作按钮；
4. **路由**：`M_URL` 指向的路由必须在服务端路由白名单里登记，并存在于前端路由表；
5. **权限**：给角色授权（用户组或个人），否则菜单不出现；
6. **版式**（可选）：需要特定排布时写 `MODULE_FORM_LAYOUT` / `MODULE_FORM_TAB`；
7. **可选**：需要领域规则时在 `ModuleBusinessMap` 登记（见第五节）。

### 加一个字段

1. 结构改动走迁移（`ALTER TABLE ... ADD`）；
2. `FIELDS` 加一行：`T_ID`、`F_ID`、`F_DESC`（显示名）、`F_TYPE`（**正确的 SQL 类型名**）、
   `DISPLAY_LENGTH`、`IS_VISIBLE`、`IS_QUERY` 等；
3. 如果需要出现在默认列表里，置 `IS_DEFAULT_FIELDS=1`，或往 `SYSQL_DEFAULT` 加行；
4. 如果要在表单里控制位置，往 `MODULE_FORM_LAYOUT` 加行。

**注意**：`F_DESC` 是显示名，不是列名。留空时界面回落显示列名，但**不要写成 `NULL` / `&nbsp;`
这类占位文本**——它们是非空值，会原样显示到标签上。

### 改字段设置（界面上）

字段设置页把改动写回 `FIELDS`，并**标记该模块的定义已过期**（脏标记），
下次读取时会重新推导定义。要点：

- 需要字段维护模块（`2302`）的 `CanSetup` 权限，不是随便谁都能改；
- 列宽被服务端钳制在 `[40, 300]`，前端拖动时也按同样区间钳制，两侧保持一致；
- 保存列宽是**批量事务写入**，不是逐列往返；
- 改完若走的是快照路径，需要重新发布快照（见 [41-定义快照与发布](./41-定义快照与发布.md)）。

**保存的并发口径（内容比对 + 乐观锁）**：

- 前端把**加载时的快照**（`original`）随改动一起回传；库中现值与快照不一致时拒绝，
  报"字段内容已被他人修改，请刷新后重试"（`400 INVALID_ARGUMENT`）——先比快照再写，避免覆盖他人改动；
- **提交内容与库中完全一致时判为无操作**：直接成功返回，不写库、不记审计，也**不比对快照**。
  否则"保存成功后紧接着再保存一次"（重复点击、离开确认带来的保存）会被误报成并发修改；
- 前端在保存成功后**失效元数据缓存并重取快照**，故连续保存拿到的是最新快照而不是保存前的旧值；
- 改类型只改 `FIELDS.F_TYPE`（元数据），**不动物理列**：`date` / `datetime` 等类型决定表单录入控件
  与显示格式，物理列的转换仍要另行走迁移。

**字段类型决定录入控件，`DISPLAY_FORMAT` 不参与**：`F_TYPE = datetime` 的表单一律渲染
"日期 + 时分秒"控件（`<input type="datetime-local">`），`date` 才是纯日期控件
（`<input type="date">`）。所以**只改显示格式不会去掉时分秒**——要改的是 `F_TYPE`。

**`DISPLAY_FORMAT` 只管显示，且"空"不是"不格式化"**：日期类字段的空格式会回落到
`toLocaleDateString`——**只出日期，时间被吞掉**（定义校验器的 `datetime_display_format_hint`
警告说的就是这件事："列表侧时间分量可能不显示"）。datetime 字段想要带时分秒，
必须显式写格式。

**日期格式串的小时 token 是 `HH` 不是 `hh`**：本平台与前端的日期 token 都对齐 .NET——
`hh` 是 **12 小时制**且无 AM/PM 设计符，15:28 会渲染成 `03:28`。库内遗留的
`yyyyMMdd hhmmss` 就是这个缺陷；规范写法见 `fieldFormat.test.ts` 里已钉住的
`yyyy-MM-dd HH:mm:ss`。格式串还会过打印层的白名单（`PdfLayout.DateFormatPattern`：
仅 `y M d H h m s : / - 空格`）。

**批量纠正类型与格式走迁移**（既有做法见 `309_date_only_fields_to_date_type.sql`）：

- 类型口径：`F_TYPE` 是 `datetime` / `smalldatetime` / `datetime2` **且** `DISPLAY_FORMAT` 已是纯日期
  （`yyyy-MM-dd`）的字段——这类字段"显示只到日、录入却要时间"，属自相矛盾的一批；
- 描述含"时间"的字段（打卡时间 / 处理时间 / 完成时间 / 预计开始·结束时间）**类型不动**，
  不因为显示格式凑巧只到日就丢掉时间语义——但它们的格式仍归入下面的格式收口；
- 建立 / 修改 / 批核 / 结案等生命周期列（`DISPLAY_FORMAT` 为空）**类型不动**（时间对审计有意义），
  格式由收口补齐，不再让它们在列表上"只剩日期"；
- 格式收口：其余 datetime 家族字段一律写成 `yyyy-MM-dd HH:mm:ss`（顺带把遗留的
  `yyyyMMdd hhmmss` 规范成 24 小时制）；`date` 字段一律写成 `yyyy-MM-dd`；
- 只改元数据、**不 `ALTER` 物理列**：既有时间部分不截断，存储过程里按 datetime 比较与赋值
  也不受影响（`PRODUCT.LAST_CHECK_DATE` 就是这个状态：元数据 `date`、物理列 `datetime`）；
- 迁移里必须**标脏受影响模块**（`WORKBENCH_MODULE_DIRTY`），否则已发布快照仍按旧口径渲染。

### 改列配置（用户自定义列）

- 用户保存的列进 `SYSQL_FIELDS`，**有配置就完全采用用户配置**，不与系统默认合并；
- 系统默认列在 `SYSQL_DEFAULT`（或字段上的 `IS_DEFAULT_FIELDS`）；
- 用户配置的上限是 200 列，重复列会被拒绝；
- 重置 = 删除该用户在该表上的 `SYSQL_FIELDS` 行。

规则细节见 [12-元数据消费](./12-元数据消费.md)。

### 改表单版式

版式在 `MODULE_FORM_LAYOUT`（字段级）与 `MODULE_FORM_TAB`（页签级）。
有可视化设计器，见 [43-表单版式设计](./43-表单版式设计.md)。

两条硬约束：

- 版式行引用的模块 / 表 / 字段必须真实存在；
- **用户能填的必填列不得被隐藏**（含"已定制的表里整行缺失"这种情况）。

## 三、扩展属性（MS_Description）约定

表与列的说明存在扩展属性里，但**本库沿用的不是标准位置**：

| 对象 | class | minor_id |
|---|---|---|
| 表描述 | `1` | `0` |
| 列描述 | `1` | 该列的 `column_id` |

标准写法是表描述用 `class=0`。**本库用 `class=1, minor_id=0`**——写工具或查询时按这个口径来，
否则会查不到或写到错位置。

## 四、改完元数据后的自查

| 检查 | 怎么做 |
|---|---|
| 结构真落库了吗 | 查 `sys.columns` / `sys.objects`，不要只看"启动成功 + 健康检查 Healthy" |
| 字段登记齐了吗 | 对照 `FIELDS`，缺行会让字段在界面上凭空消失 |
| 标签是占位文本吗 | `F_DESC` 不得为 `'NULL'` / `'&nbsp;'` |
| 必填列被隐藏了吗 | 版式表与字段表两侧对一遍 |
| 声明了批核能力吗 | 主表必须有 `CONFIRM_TAG` 对应的状态位列 |
| 定义快照落后了吗 | 配置改了但快照没重发布，就是**静默落后**——界面按旧定义运行 |
| 路由登记了吗 | 服务端路由白名单 + 前端路由表 |

## 五、模块与领域规则的登记

`EOS.API/Data/ModuleBusinessMap.cs` 是三处**服务端常量登记**，改模块时容易漏：

| 登记 | 用途 | 漏了会怎样 |
|---|---|---|
| `Rules` | 模块 → 领域规则（是否自动单号、单号字段、单别字段） | 单号不自动生成，或规则不生效 |
| `MasterTables` | 需批核的单据模块 → 主表映射 | **「我的任务」待办计数缺失**——不报错，只是数字少 |
| `CatalogAfterSaveMap` | 保存后行为已由校验目录承接的模块 | 保存期校验不执行 |

这三处都是显式白名单：**新模块要主动登记**，没有"自动发现"。

> 注意：`Rules` 的历史注释提到过程名取自 `MODULES.UPDATE_SP` / `AFTERSAVE_SP`，
> 但这两列已删除，过程钩子体系也已被校验与效果体系取代。读这段代码时以实际字典内容为准。

**"这个键在库内用了多少次"有两个只读口径**（都在 `ModuleBusinessConfigRepository`，都是参数化只读查询）：
`CountEventUsageAsync` 按 `EVENT_CODE` 计（2301 界面用它区分"配了不会跑"的事件），
`CountEffectKeyUsageAsync` 按 `EFFECT_KEY` 计且**不含用户点击行**（与效果说明门禁同一口径）。
配置诊断据此发现"全库只用过一次"的单例效果键——同一件事配出多个只用一次的键，是最难维护的一类配置。

### 配置写入：幂等键与审计同事务

配置面既能读也能写，所以"改配置"这条路径与单据写入守同样的两条底线：

- **幂等键由服务端生成**：键从调用身份（会话 + 工具调用标识，或用户本次确认的键）与请求意图推导，
  客户端与模型**都提交不了键**；重放同一键返回同一结果、不重复写。
  配置写的两种载体（字段更新、整模块保存）都在**业务事务内**抢占并写结果，
  因此业务失败即释放，不会留下"占了键却没有结果"的空档。
- **审计与业务同事务**：字段维护与模块业务配置这两条写路径的审计从"提交后 best-effort"
  改为**同一事务内写入**——审计写不进去即整单回滚，不留"改了但没有痕迹"的状态。
  其它路径的 best-effort 审计是既有设计，不在此口径内。
- **逐类准入**：字段 / 数据来源 / 自定义按钮 / 效果键四类配置在助手侧**各自独立启停**
  （配置节 `AssistantConfigWrite`，默认只放字段一类），未放开的一类只做只读的解释与不一致检查。

## 六、禁止事项

- 不要为配置写新开第二条写路径——一律经 `FieldAdminRepository` / `ModuleBusinessConfigRepository`；
- 不要在配置写路径上用 best-effort 审计——审计必须与业务同事务；
- 不要在前端硬编码列清单或模块清单——一律从元数据来；
- 不要直接 UPDATE 生产库的元数据后不留迁移；
- 不要绕过字段维护模块的权限门去改 `FIELDS`；
- 不要把"为了兼容旧数据"的临时补丁写成长期逻辑（见 [03-工程规范与硬约束](./03-工程规范与硬约束.md) 的变更取舍一节）。
