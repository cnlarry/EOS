# 30 审计日志

审计回答的是「**谁、什么时候、对哪条记录、做了什么、结果如何**」。
它与运行日志是两回事（后者见 [31-运行日志与诊断](./31-运行日志与诊断.md)）：
审计是**业务事实**、长期保留、可查询；运行日志是**技术过程**、只留 Warning+、按需读取。

## 一、唯一存储

| 表 | 作用 |
|---|---|
| `AUDIT_EVENT` | 事件主表 |
| `AUDIT_FIELD_CHANGE` | 字段级变更明细（挂在事件下） |

**这是唯一在写的操作日志存储。** 历史表 `SYSDF` 只读、不再写入，
排查时不要指望它有你今天的操作。

## 二、表结构（实测）

### `AUDIT_EVENT`

| 列 | 类型 | 含义 |
|---|---|---|
| `EVENT_ID` | bigint | 事件 ID |
| `OCCURRED_AT` | datetime2 | 发生时间 |
| `CORRELATION_ID` | nvarchar | 请求关联 ID，**与运行日志串联的键** |
| `TRACE_ID` | nvarchar | W3C trace id |
| `ACTOR_USER_ID` | nvarchar | 操作者用户 ID（**权限主体**；助手代表的写入也填真实用户） |
| `ACTOR_DISPLAY_NAME` | nvarchar | 操作者姓名 |
| `ACTOR_TYPE` | tinyint | `1` 用户 / `2` 系统任务 / **`3` Agent 代表用户** / `4` 集成 |
| `CLIENT_TYPE` | tinyint | 来源：`1` Web / `2` API / **`3` Agent** / `4` 集成 |
| `CLIENT_IP` | nvarchar | 客户端 IP |
| `USER_AGENT` | nvarchar | UA |
| `REQUEST_METHOD` / `REQUEST_PATH` | nvarchar | 原始请求 |
| `M_IDX` | int | 模块编号 |
| `RESOURCE_TYPE` | nvarchar | 资源类型 |
| `RESOURCE_KEY` | nvarchar | 资源键（记录主键等） |
| `ACTION` | nvarchar | 动作 |
| `RESULT` | tinyint | `1` 成功 / `0` 失败 |
| `ERROR_CODE` | nvarchar | 失败时的错误码 |
| `DEFINITION_VERSION` | nvarchar | 当时使用的定义版本 |
| `SUMMARY` | nvarchar | 人读摘要 |
| `DETAIL_JSON` | nvarchar | 明细（字段变更或额外上下文） |
| `CREATED_DATE` | datetime2 | 写入时间 |

### `AUDIT_FIELD_CHANGE`

| 列 | 含义 |
|---|---|
| `EVENT_ID` | 指向 `AUDIT_EVENT` |
| `FIELD_NAME` | 字段名 |
| `OLD_VALUE` / `NEW_VALUE` | 变更前后值 |
| `VALUE_HASH` | 新值的 **SHA-256**（用于比对而无需读明文） |

## 三、两种写入方式

| 方法 | 事务 | 失败行为 | 用在 |
|---|---|---|---|
| `WriteEventAsync`（事务内） | 与业务**同一事务** | 一起回滚 | 业务写操作：新增/修改/删除、批核、结案、效果执行 |
| `WriteBestEffortAsync`（尽力而为） | 独立连接 + 独立事务 | **忽略异常**，不影响主流程 | 读路径与留痕：导出、打印、权限拒绝、日志查询 |

选择原则：

- **改了业务数据** → 用事务内写入。审计与业务同生共死，不会出现"改了但没记录"；
- **只是读或试图操作** → 用 best-effort。审计写失败不该让用户查不了数据。

### 助手代表的写入怎么记

工作助手执行新增 / 修改 / 删除时，写的是**同一条业务管线**（`WorkbenchCommandHandler`），
身份靠一个请求作用域内的标记（`Data/Workbench/AgentWriteContext`）传下去：

| 列 | 值 |
|---|---|
| `ACTOR_USER_ID` | **真实用户**（助手没有独立身份，权限主体恒为使用者） |
| `ACTOR_TYPE` | `3`（Agent 代表用户） |
| `CLIENT_TYPE` | `3`（Agent） |

标记**只影响审计身份，不参与任何授权判定**；授权一律由策略层按当前用户重新求值、fail-closed。
预演（真实事务内执行后回滚）另写一条 **best-effort** 的 `ACTION='DRYRUN'` 审计——它必须落在回滚**之后**，
否则会被自己回滚掉；业务审计则随回滚消失，这正是"预演不留痕"的体现。

## 四、动作与资源类型的取值

`ACTION` 是自由字符串，但实际有几类约定写法（实测分布）：

| 类别 | 例子 |
|---|---|
| 业务记录动作 | `INSERT`、`UPDATE`、`DELETE`、`CREATE`、`SAVE` |
| 单据状态动作 | `APPROVE`、`DEAPPROVE`、`ENDCASE`、`UNENDCASE` |
| 管理与配置动作 | `PUBLISH`、`RIGHTS_SAVE`、`FORM_LAYOUT_SAVE`、`GROUP_SAVE`、`GROUP_DELETE`、`PARAM_SAVE`、`USER_CREATE`、`FLOW_SAVE`、`FLOW_DELETE`、`FLOW_SUBMIT` |
| 输出类 | `EXPORT`、`PRINT` |
| 被拒绝 | `DENY` |
| 查询留痕 | `LOG_QUERY` |
| **效果执行** | `EFFECT:` 前缀，如 `EFFECT:inventory-move`、`EFFECT:field-accumulate`、`EFFECT:completion-close`、`EFFECT:detail-rollup` |
| 库存动作 | `RESERVE`、`UNRESERVE` 一类、`FREEZE`、`UNFREEZE`、`RELEASE`、`RELOCATE` |

**效果执行带 `EFFECT:` 前缀**是个有用的约定：排查"这个字段为什么变了"时，
先按 `ACTION LIKE 'EFFECT:%'` 过滤，能看到是哪条效果链动的数据。

`RESOURCE_TYPE` 主要取值：`WORKBENCH_RECORD`（业务记录，占绝大多数）、`MENU`、
`FIELD_ADMIN`、`WORKBENCH_METADATA`、`DEPOT_STOCK_POLICY`、`FORM_LAYOUT`、
`REPORT_PRINT`、`PRINT`、`EXPORT`、`INV_FREEZE`、`INV_RESERVE`、`PERMISSION`、
`WORKFLOW_DESIGN`、`SYSTEM_PARAM`、`LOG_QUERY`。

新增审计点时**沿用这些写法**，不要各造一套。

## 五、字段级变更

- 明细写进 `AUDIT_FIELD_CHANGE`，主表的 `DETAIL_JSON` 也会带上同一份；
- **是否记录字段级变更受配置开关控制**（`AuditSettings.FieldChangesEnabled`）。
  开关关闭时只记事件、不记字段明细；
- **大字段与敏感字段只存摘要或哈希**，不存明文。

因此：**不要假设"每个 UPDATE 都能查到字段明细"**——字段明细是可选能力，事件才是必备的。

## 六、查询

接口：`GET /api/v1/audit`（`AuditController`，需登录；权限门 = 模块 `2313`（日志管理）的
`CanBrowse`，与日志管理页同一锚点）。

**查询本身也会留痕**：动作 `LOG_QUERY`，资源类型 `LOG_QUERY`。
所以"谁在什么时候查了审计"也是有记录的。

直连库查的常用姿势：

```sql
-- 某条记录的全部历史（按主键值找）
SELECT EVENT_ID, OCCURRED_AT, ACTOR_USER_ID, ACTOR_DISPLAY_NAME, ACTION, RESULT, ERROR_CODE, SUMMARY
FROM dbo.AUDIT_EVENT
WHERE M_IDX = 1405 AND RESOURCE_KEY LIKE '%SO2026%'
ORDER BY EVENT_ID DESC;

-- 某次请求的完整链路（把运行日志里的 correlationId 拿来）
SELECT EVENT_ID, ACTION, RESOURCE_TYPE, RESOURCE_KEY, RESULT, ERROR_CODE, SUMMARY
FROM dbo.AUDIT_EVENT
WHERE CORRELATION_ID = '<correlationId>'
ORDER BY EVENT_ID;

-- 某条事件的字段变更
SELECT c.FIELD_NAME, c.OLD_VALUE, c.NEW_VALUE
FROM dbo.AUDIT_FIELD_CHANGE c
WHERE c.EVENT_ID = <eventId>;

-- 失败操作（含被拒绝的）
SELECT OCCURRED_AT, ACTOR_USER_ID, M_IDX, ACTION, ERROR_CODE, SUMMARY
FROM dbo.AUDIT_EVENT
WHERE RESULT = 0
ORDER BY EVENT_ID DESC;

-- 效果链动了哪些数据
SELECT OCCURRED_AT, M_IDX, ACTION, RESOURCE_KEY, SUMMARY
FROM dbo.AUDIT_EVENT
WHERE ACTION LIKE 'EFFECT:%'
ORDER BY EVENT_ID DESC;
```

## 七、串联前后端

`AUDIT_EVENT.CORRELATION_ID` 与运行日志里的 `correlation` 是同一个值，
`TRACE_ID` 与运行日志的 `trace` 对应。

> **口径已统一（2026-09-29）**：异常出口、业务拒绝映射、助手会话落库、登录限流与诊断打包
> 等处写 `correlation` 的地方**全部改读 `RequestContext`**，因此上面这条"同一个值"对**所有**
> 运行日志行都成立，不需要再拿 `TRACE_ID` 兜。
>
> 历史注记（仅供考古）：2026-09-29 之前，异常行取的是 `context.TraceIdentifier`，
> 于是在"请求带了 `X-Correlation-Id` 且抛了未处理异常"时审计与日志对不上——
> 而且**不传该请求头时两者恰好同值**，所以表面看不出差异。口径依据见
> [`docs/decisions/ADR-025`](../decisions/ADR-025-关联键单一真源与日志脱敏接入.md)。

排障顺序：

1. 用户报"这个单子数据不对" → 问操作时间与单据号；
2. 按 `M_IDX` + `RESOURCE_KEY` 查 `AUDIT_EVENT`，定位到具体事件；
3. 拿 `CORRELATION_ID` 去运行日志里找那次请求的完整技术过程（耗时、DB 耗时、错误码）；
4. 若 `RESULT = 0`，用 `ERROR_CODE` 对照 [04-API契约与前后端协作](./04-API契约与前后端协作.md) 的错误码表。

## 八、注意事项

- **审计按设计保留，不得删除**。真库测试用例也不允许 `DELETE FROM dbo.AUDIT_EVENT`——
  测试数据会混在生产审计里，靠 `CORRELATION_ID` 与时间区分，不要靠删；
- **不要用审计当业务数据源**。它是记录，不是状态；单据当前状态看单据表；
- **`DEFINITION_VERSION` 是排障利器**：单据行为看起来"不一致"时，先确认两次操作是否跑在同一版定义上；
- **测试脚本也会写审计**：看到来源可疑的记录（如探针类动作）先确认是不是验收脚本留下的。

## 收口（迁移 325）：`SYSDF` 已整表退役

- 旧操作日志表 `SYSDF`（11134 行，2007-11-14 ~ 2026-09-05）**已从库中删除**：`AUDIT_EVENT` 上线后
  `WorkbenchAuditWriter` 就已停写它、`AuditController` 也不再查它。删表前按 RFC 4180 导出了 CSV 备查
  （留档在部署机的 `logs/archive/retire-324/`，**不入版本库**；迁移里的守卫要求库内行数与归档逐数字一致）。
- 于是**审计的唯一存储就是 `AUDIT_EVENT` / `AUDIT_FIELD_CHANGE`**，不再有"兼容查询来源"那一层；
  要查 2007~2026-09 的历史，只能找上面那份归档 CSV。
- 退役模块（2205 / 2308 / 2202 / 2203 / 2204 …）在 `AUDIT_EVENT` 里的历史行**按惯例保留**——删审计行等于
  抹掉痕迹，退役迁移的后置自证里也专门断言"该模块的审计行仍在"。
