# 05 数据库迁移与建库

## 一、两套脚本，别混

| | 建库脚本 | 迁移脚本 |
|---|---|---|
| 位置 | `db/bootstrap/` | `EOS.API/Data/Migrations/` |
| 何时执行 | 建新环境时**手工执行一次** | 应用**启动时自动执行** |
| 作用 | 从空库建成可用库（结构 + 元数据种子 + 账号） | 增量演进已建好的库 |
| 谁改 | 只在结构基线更新时整体重生成 | 日常开发随手加 |

日常开发**只写迁移脚本**。建库脚本是基线快照，由维护者在结构收敛时统一重生成——
不要为了一个新表去改 `10_schema.sql`。

## 二、迁移怎么跑起来的

`EOS.API/Data/ErpDatabaseInitializer.cs` 在启动时用 DbUp 执行迁移：

- 脚本以**嵌入资源**方式编译进程序集（资源名形如 `EOS.API.Data.Migrations.271_xxx.sql`）；
- 台账表为 `dbo.ERP_SCHEMA_JOURNAL`，DbUp **只按资源名（即文件名）判断脚本是否已执行**；
- **每个脚本一个事务**（`WithTransactionPerScript`）：脚本自身失败会整体回滚；
- **迁移失败即启动失败**（直接抛异常），并反映到健康检查 `/health/ready`。

因此：

- 已执行过的脚本再改内容**不会重新执行**——要让改动生效必须新增一个脚本；
- 相反，**改文件名会让已建库把它当成新脚本再跑一次**，可能造成重复插入或报错。

## 三、编号与命名

```
EOS.API/Data/Migrations/283_inventory_freeze_index.sql
                         └┬┘ └──────────┬──────────┘
                      编号           小写下划线描述
```

规则：

- **编号是排序键，不是身份**。DbUp 按文件名字典序执行，编号只决定先后，**不要求连续**
  （历史上有空号，不要回收）。
- **文件名是判重身份**，记录进台账。**新增一律取当前最大编号 +1**，不插入中间。
- **编号冲突时改内容，不改文件名**。两个人同时拿到 283 时，后来者改成 284 即可，
  千万不要把已提交脚本改名。
- 建库基线 `db/bootstrap/40_journal_baseline.sql` 登记了某个编号之前的全部脚本。
  它必须与 `10_schema.sql` 来自同一结构版本，两者不匹配会导致启动时重复执行或报缺对象。
- **新库靠"基线 + 启动时补齐"落地**：基线登到 268，而 `Data/Migrations` 已有 285+ 个脚本，
  差额由 `EOS.API` 启动时的 DbUp 执行；重建基线的工具已随双仓发布清理删除，暂无替代。
- **新迁移在你下次启动 `EOS.API` 时才落库**：加了脚本却不重启，库里就没有它
  （`check-migration-journal.ps1` 会如实报"未落库 N 个"）。判断以 `dbo.ERP_SCHEMA_JOURNAL` 与
  `sys.columns` 为准，不要以"启动日志看着正常"或健康检查为据。
- **别照抄旧迁移的列清单**：`SYSDH`/`SYSDD` 这类授权表会随 ADR 演进增删列
  （如 `FORM_ADJUST_TAG` 已按 ADR-022 退役、代之以 `MODULE_CONFIG_TAG`）。
  照抄旧迁移会在**干跑阶段**就报"列名无效"——这也是先跑
  `pwsh scripts/test-migration-dryrun.ps1` 的价值所在。

## 四、新增一个迁移

1. 看当前最大编号：

   ```powershell
   Get-ChildItem EOS.API/Data/Migrations -Filter '*.sql' | Sort-Object Name | Select-Object -Last 1 -ExpandProperty Name
   ```

2. 新建 `NNN_描述.sql`，编号取最大 +1；
3. **对象命名全大写**（表、列、索引、约束）；
4. 需要写入元数据（模块、字段、列配置）时，一并写在同一个迁移里——
   界面形态由元数据驱动，元数据不跟着走，别人拉下代码界面就是残缺的；
5. 在本地启动应用，确认迁移执行成功（看启动日志与 `/health/ready`）；
6. 用 `sys.*` 核对落库结果（例如 `sys.columns` 里新列确实存在），
   **不要只凭"启动成功 + 健康检查 Healthy"下结论**。

## 五、写迁移的注意点

### 幂等

元数据种子类脚本要写成幂等的（先判断存在性再 INSERT/UPDATE），
因为同一个库可能被不同分支的代码反复启动。

### 改表要连迁移一起改（否则真库用例先红）

`Data/Migrations/` 是库结构的唯一来源，但**代码不会自己去核对它**。曾有一列
（`ASSISTANT_MESSAGE.TOOL_CALLS_JSON`）在仓库里"到处都被当成存在"——ADR 的建表记录、
仓储的写入与查询、服务端编排都在用它——而建表脚本里根本没有、此后也没有迁移补上；
直到**真库用例**跑出 `列名 '…' 无效` 才暴露（而它在 done 事件之前断流，用户看到的是"回答没回完"）。

两条教训：

- 写 `SELECT/INSERT/UPDATE` 用到某列前，先确认**建它的迁移在仓库里**（不是"印象里应该有"）；
- 依赖库结构的代码，**真库用例必须跑**：单测用的是假仓储，这类"代码有、库没有"的不一致在单测里永远看不见。

### 事务配平

如果脚本内自带 `BEGIN TRANSACTION`，必须配对 `COMMIT`。DbUp 会给每个脚本再套一层事务，
自身事务没配平会让 `@@TRANCOUNT ≠ 1`，随后报错。**没有特别理由就不要自己开事务**。

### 不自带 `USE`

连接已指定库（`EOS.ERP`），脚本里不要再写 `USE`。

### 脚本编码

迁移脚本是 UTF-8。要手工用 `sqlcmd` 执行历史脚本时，必须带 `-f 65001`，
否则中文内容在部分区域设置下会解析失败。

### 删除库对象前先查引用

准备 DROP 表/列/存储过程前，至少核查三类引用方，缺一类就可能删掉还在用的东西：

1. **库内依赖**：查 `sys.sql_expression_dependencies`。注意**未限定 schema 的引用
   `referenced_schema_name` 为 NULL**，只按 `= 'dbo'` 过滤会把它们整批漏掉；
2. **运行时配置**：已发布快照里的同名引用、报表排序等元数据字段；
3. **代码与脚本按名调用**：C# 里的直接调用，以及测试脚本、夹具 SQL 里的
   `EXEC P_*` / `CommandText = 'P_*'`。

漏掉第 3 类是最常见的翻车方式：编译通过、单测通过，但某个验收脚本一跑就挂。

### 已落库的登记改错了：另出一个脚本，别改原文

「已执行过的脚本再改内容不会重新执行」的反面同样成立：**内容改对了，库也不会变**。
所以当一个**已落库**的迁移把元数据登记错了（模块号挂错层级、权限镜像错了对象、
字段口径写反），正确处置是**新增一个脚本做订正**，而不是回头改原文：

- 原文已进台账，改它既不重跑，也让"脚本内容与台账"对不上，后来人照原文理解现状会得出错结论；
- 订正脚本要**对历史库形态幂等**——它面对的是"原文跑过、原文没跑、以及全新库先跑原文再跑它"
  三种状态，因此每一步都判断存在性（存在即跳过），并在收口处断言目标状态成立、
  旧登记已无残留；
- **作废旧标识符前先查外键**：`MODULES.M_IDX` 被 `REPORT` / `MODULE_VALIDATION_RULE` /
  `MODULE_BUSINESS_ACTION` 引用，仍被引用时**中止迁移并报错**，不要连带删除别人的行；
- **重编号不得少授权**：`SYSDH`（组）/`SYSDD`（个人）的授权行要**逐主体复制**，
  且以"新编号的主体集合 ⊇ 参照模块的主体集合"作为收口断言。注意**个人权限整表覆盖组权限**，
  只搬组权限会让原本有个人权限行的用户静默失去权限。

实例：日志管理页初版由迁移 `283` 登记为模块 `110112`（挂在基本参数下），
与"定制页都在 23 系统管理"的惯例不符；由迁移 `284` 重编号为 `2313`（根 23 / 父 2311）
并把 `110112` 从 `MODULES`/`SYSDH`/`SYSDD` 三处退役，授权取原两套授权的并集。
判定仍以**干跑 + 落库后查 `sys.*` 与台账**为准。

## 六、诊断

| 现象 | 原因与处理 |
|---|---|
| 启动报"迁移失败" | 看启动日志里的脚本名；常见是 SQL 语法错、对象已存在、事务未配平 |
| 改了脚本但没生效 | 文件名没变 → DbUp 认为它执行过了。新增一个脚本，不要原地改 |
| 同一个脚本执行了两次 | 脚本被改过名，或台账被手工清理过。检查 `ERP_SCHEMA_JOURNAL` 里的资源名 |
| 新环境启动报缺表/缺列 | `10_schema.sql` 与 `40_journal_baseline.sql` 版本不匹配；按 [02-本地环境与运行](./02-本地环境与运行.md) 重新建库 |
| 想确认某个迁移是否真落库 | 查 `sys.columns` / `sys.objects`，或查 `ERP_SCHEMA_JOURNAL` 的资源名，别只看健康检查 |
