# 05 数据库迁移与建库

## 一、两套脚本，别混

| | 建库脚本 | 迁移脚本 |
|---|---|---|
| 位置 | `db/bootstrap/` | `EOS.API/Data/Migrations/` |
| 何时执行 | 建新环境时**手工执行一次** | 应用**启动时自动执行** |
| 作用 | 从空库建成可用库（结构 + 元数据种子 + 基础资料 + 账号） | 增量演进已建好的库 |
| 谁改 | 只在结构基线更新时整体重生成 | 日常开发随手加 |

日常开发**只写迁移脚本**。建库脚本是基线快照，由维护者在结构收敛时统一重生成——
不要为了一个新表去改 `10_schema.sql`。

建库脚本按编号顺序执行，各自的职责是：

| 脚本 | 内容 |
|---|---|
| `00_create_database.sql` | 建库 |
| `10_schema.sql` | 结构（表、视图、函数、过程），无数据 |
| `20_metadata.sql` | 元数据种子（模块、字段、报表、版式、流程） |
| `25_base_data.sql` | **基础资料种子**：供其它表单引用的主档（公司与部门、员工、币别、税别、银行、价格/付款条件、结算方式、帐款类型、产品类别/颜色/单位/材质、仓库/库位/库存策略，以及电子元器件行业的示例客户与厂商；全部为脱敏示例数据，不含真实企业信息） |
| `30_admin.sql` | 初始账号（`admin` 管理员、`larry` 普通用户）与权限 |
| `40_journal_baseline.sql` | 登记已固化的迁移编号 |

基础资料**随建库生成、clone 后即可引用**；它对其它测试脚本是"既存事实"——模块清单见
`EOS.API.Tests/base-data-modules.json`，CRUD 验收见 `EOS.API.Tests/E2eBaseDataCrud.ps1`，
三者与库内实际的一致性由 `scripts/check-base-data.ps1` 把关（见 [06-测试与质量门禁](./06-测试与质量门禁.md)）。

**种子与存量库要各落一笔**：`db/bootstrap/` 只对「从零建库」负责，已建好的库读不到它的后续修改。
因此改一处元数据或基础资料通常要提交两份——种子（供新库）与迁移脚本（供存量库），两者内容须一致。
例：`20_metadata.sql` 去掉表描述里的客户定制模块条目，配套迁移
`312_prune_stale_module_entries_from_table_remark.sql` 同步存量库；只改种子会让存量库与新库的元数据长期分叉。

## 发版收口：把现状固化回种子

日常开发只写迁移；**版本发布时收口**——把库的现状回灌种子，并把已固化的迁移登记进基线，
让新克隆的库一步到位等于当前版本。三个导出脚本（都在 `scripts/`）：

| 脚本 | 重建 | 说明 |
|---|---|---|
| `export-bootstrap-schema.ps1` | `10_schema.sql` | 表 / 视图 / 函数 / 过程，由 SMO 导出（PowerShell 7 加载不了 SMO，脚本内部转用 Windows PowerShell 5.1 子进程）；排除历史备份表与已坏死对象 |
| `export-bootstrap-metadata.ps1` | `20_metadata.sql` | 元数据段，按**通用基线**口径排除客户私有数据 |
| `export-bootstrap-baseline.ps1` | `40_journal_baseline.sql` | 把库台账里已有的迁移全部登记，新库不再重跑它们 |

三者**必须同批提交**：只补种子不扩登记，迁移会在已对齐的库上重跑，而多数迁移的守卫是按
「有事可做」写的（例如 `274` 要求删除集恰为 181），空集会直接抛错、应用起不来；只扩登记不补种子，
新库会因为「迁移不跑、种子又没有」而缺表缺数据。

**收口后必须在临时库上验一遍**：按 `00 → 10 → 20 → 25 → 30 → 40` 全部执行，再逐项对比对象与列清单。
`10_schema.sql` 由工具生成，格式与内容都可能出错——实测踩到过三类：外键引用了尚未建的表（对象顺序）、
函数被排到表之前（SQL Server 不把函数体里的引用登记为依赖）、IDENTITY 列没有 `SET IDENTITY_INSERT`。
不验证就等于把「建不了库」推给所有人。

**已坏死的遗留对象不进基线**：个别老函数引用的是改名前的老列（如 `f_get_form_desc` 引用
`WFFORM.FORM_IDX`），它们当初能创建成功只是因为引用的表还不存在（延迟名称解析），此后一直在报错。
清单由 `sp_refreshsqlmodule` 全库扫一遍得出，维护在 `export-bootstrap-schema.ps1` 的 `$skipObjects` 里。

### 库对象命名与退役登记

**库对象一律大写**，视图再加 `V_` 前缀、存储过程加 `P_` 前缀。表与列本来就是全大写；
历史遗留的 `vw_Client`、`VW_ORDER_SHEET`、`MOC_GET_SHOWSUM` 一类已由迁移 `317` 对齐
（顺带把 `ORDER_COUNT`、`YEAR`/`MONTH`/`TOTAL` 等视图列名一并规范）。新增对象按此命名。

存量里**函数仍是小写** `f_xxx`（58 个标量 + 13 个表值），是尚未收口的部分：改它们要连带
引用它们的视图与函数、`FIELDS.CONVERT_FUNCTION` / `FIELD_DATASOURCE.FILTER_STRUCT` 这类
**活元数据表达式**、以及调用它们的代码一起动。审计表里也有历史留存的旧名，那是记录，不该改。

**退役库对象要登记**：`scripts/check-retired-db-objects.ps1` 把退役清单固化在脚本里。
库对象删掉而代码漏改时，编译与单测都不会报，只在运行时炸成 500——退役对象时把条目一并
加进清单并写明迁移文件与原因。注意清单条目与邻近注释都**不能直接点名**对象，因为
`scripts/**/*.ps1` 本身就在该门禁的扫描范围内，点名即自命中。

**脱敏**：库里有真实企业名与客户资料。词表 `$HOME/.eos/sensitive-terms.txt` 与替换表
`$HOME/.eos/desensitize-map.txt` **刻意放在版本库之外**（提交它们等于制造新的泄露源）。
导出时命中词表的值必须能在替换表里找到对应项，否则脚本中止并列出；客户私有的**整行**
（如 `REPORT_LAYOUT` 里 `companyName` 非空的公司抬头版式）按通用基线口径直接不导出。

**模块下线时别忘 `TABLES.T_REMARK`**：该列记录「这张表被哪些模块当作主表」，是纯备注。
`274` 的前置引用检查覆盖了 `REPORT` / `SYSQR` / `SYSDD_REPORT` / `FIELDS.BROWSE_M_IDX` 等元数据面，
**没有覆盖它**，于是 205 张表的描述里留下了一批指向已删模块的悬空条目
（`313_purge_retired_module_refs_from_table_remark.sql` 按模块号清理）。今后再有模块下线，
把 `T_REMARK` 一并纳入清理面。

## 二、迁移怎么跑起来的

`EOS.API/Data/ErpDatabaseInitializer.cs` 在启动时用 DbUp 执行迁移：

- 脚本以**嵌入资源**方式编译进程序集（资源名形如 `EOS.API.Data.Migrations.271_xxx.sql`）；
- 台账表为 `dbo.ERP_SCHEMA_JOURNAL`，DbUp **只按资源名（即文件名）判断脚本是否已执行**；
- **每个脚本一个事务**（`WithTransactionPerScript`）：脚本自身失败会整体回滚；
- **迁移失败即启动失败**（直接抛异常），并反映到健康检查 `/health/ready`。

因此：

- 已执行过的脚本再改内容**不会重新执行**——要让改动生效必须新增一个脚本；
- 相反，**改文件名会让已建库把它当成新脚本再跑一次**，可能造成重复插入或报错。

## 三、编号与命名

```
EOS.API/Data/Migrations/283_inventory_freeze_index.sql
                         └┬┘ └──────────┬──────────┘
                      编号           小写下划线描述
```

规则：

- **编号是排序键，不是身份**。DbUp 按文件名字典序执行，编号只决定先后，**不要求连续**
  （历史上有空号，不要回收）。
- **文件名是判重身份**，记录进台账。**新增一律取当前最大编号 +1**，不插入中间。
- **编号冲突时改内容，不改文件名**。两个人同时拿到 283 时，后来者改成 284 即可，
  千万不要把已提交脚本改名。
  **判别在于"有没有入过台账"**：「不改文件名」针对的是**已提交、或已入台账**的脚本——改名会被
  DbUp 当成新脚本重跑一次；而**尚未提交、也没进台账**的新脚本遇到同编号时反过来——**改文件名到
  当前最大 +1**，改内容解决不了重名。多会话并行时撞号很常见，落笔前先看一眼目录里是否已有人
  占了该号（别人的**未跟踪脚本**也要算进去）。
- 建库基线 `db/bootstrap/40_journal_baseline.sql` 登记了某个编号之前的全部脚本。
  它必须与 `10_schema.sql` 来自同一结构版本，两者不匹配会导致启动时重复执行或报缺对象。
- **新库靠"基线 + 启动时补齐"落地**：基线登到 268，而 `Data/Migrations` 已有 311 个脚本，
  差额由 `EOS.API` 启动时的 DbUp 执行；重建基线的工具已随双仓发布清理删除，暂无替代。
- **"新页面"类迁移不只插一行 `MODULES`**：页面路径还要进后端 `ModuleRouteValidator.ExactRoutes`
  （否则菜单点开是 `/fallback/modules/{id}` 占位页，菜单管理后台也保存不了这个 URL）与前端路由表，
  可照抄 `288_assistant_admin_module.sql`——它同时登记根组 31、子模块 3101，并**镜像 `SYSDH`/`SYSDD`
  授权行**（不镜像的话连 admin 都看不见新菜单，导航查询硬性要求 `EXEC_TAG <> 'A'`），还带幂等与收口断言；
  `289_assistant_mechanism_module.sql`（3104）与 `290_assistant_kb_module.sql`（3103）是同一套的更简版本
  （只登记一个子模块并镜像授权），补挂模块时照它们改最省事——290 就是从 289 复制改编号与路径生成的。
  `310_business_flow_module.sql`（2314「业务流程图」，挂在 23 系统管理 › 2311 数据表维护下）是
  **补挂到既有父目录**的同类例子：同样三处同改（库内 `M_URL`、后端 `ExactRoutes`、前端路由表）并镜像授权。
- **建业务表 + 登记模块可以放同一条迁移里**：`291_assistant_model.sql` 既建 `dbo.ASSISTANT_MODEL`
  （照 044 的写法：`IF OBJECT_ID(...) IS NULL` + `dbo.` 前缀 + 具名约束 + `DEFAULT (SYSUTCDATETIME())`），
  又登记模块 3102 并镜像授权。它还留了一条**意图断言**——表里一旦出现疑似密钥列（`API_KEY`/`SECRET`/`TOKEN`）
  就直接 `THROW`：把"密钥不入库"从一句约定变成后人不小心就会撞到的墙。
- **同一件事分两条迁移、且要能对"已迁移过的库"重复执行**：`291` 建的是助手模型表的一级形状，
  `292` 立刻把它改成两级（供应商 / 模型）。两条同批交付，所以 292 里有这么一段——**检测到已是新形状就
  跳过重建**（`GOTO` 到收口断言之前）：
  ```sql
  IF COL_LENGTH(N'dbo.ASSISTANT_MODEL', N'PROVIDER_ID') IS NOT NULL
  BEGIN
      PRINT N'== 已是两级形状（292 已执行过），跳过重建 ==';
      GOTO RebuildDone;
  END
  ```
  这  不是洁癖：`scripts/test-migration-dryrun.ps1` 干跑门禁**正是在已迁移的库上重放脚本**，不跳过的话，
  管理员配好的模型会被误判成"有数据的旧库"而让门禁永远红着。而真遇到**旧形状且有数据**时仍然
  **大声 `THROW`**（附带"改用逐列搬迁"的指引），不静默抹掉别人的配置——**门禁要能过，危险要能喊**，
  这两件事不冲突。
- **纵向参数表是"加参数不改表"的既有范式**：`207_system_parameter_verticalization.sql` 把三张单行宽表
  合成了 `dbo.SYSSS`——一行一个参数、值统一存文本、用 `VALUE_TYPE` 说明怎么解析，`VALUE_TYPE`
  上有一条 `CHECK` 白名单（写进来别的类型会静默变成"用默认值"而没人发现）。**加参数不改表结构**。
  注意迁移里的**列名要逐字核对**：`FILE_UPDA_TAG` 这种名字写成 `FILE_UPA_TAG`，干跑会当场报错
  （那一批就是这么抓出来的——这类错在别处会一路活到运行期）。
- **新迁移在你下次启动 `EOS.API` 时才落库**：加了脚本却不重启，库里就没有它
  （`check-migration-journal.ps1` 会如实报"未落库 N 个"）。判断以 `dbo.ERP_SCHEMA_JOURNAL` 与
  `sys.columns` 为准，不要以"启动日志看着正常"或健康检查为据。
- **新增迁移后的第一次测试跑，迁移台账可能出现重复行**（实测）：多个真库用例夹具各自跑一次 DbUp
  应用迁移，而台账的 `ScriptName` 上没有唯一约束——谁都看到"还没应用"，于是并行插了多行、脚本也被
  并行执行（加迁移 `307` 那一次一口气留下 **4 行**，同一次运行还带崩了一条**看起来毫不相关**的用例：
  "名下还有模型的供应商不可删"，重跑即绿）。两个后果：`check-migration-journal.ps1` 报
  `xxx.sql xN`；排查时容易误以为迁移写错了。处理：先确认脚本确实生效（查 `sys.columns` / `sys.indexes`
  而不是看日志），再按 `ScriptName` **保留最早一行**删掉其余，复跑门禁即绿。
  想让这类重复**当场失败**而不是静默留下：给 `ERP_SCHEMA_JOURNAL.ScriptName` 加唯一索引（未做，属于
  可选的加固）。
- **同批次里引用刚 `ALTER TABLE … ADD` 的列会报 `Msg 207`**：SQL Server 对同一批次的语句是**编译期**
  解析列名的，`ADD FEEDBACK` 之后紧接着写 `CHECK (FEEDBACK IN (-1, 1))` 会报"列名无效"——
  看着像列没加上，其实是那句没等它（303 就是这么撞上的）。两种改法：约束语句改成动态执行
  （`EXEC(N'ALTER TABLE … ADD CONSTRAINT … CHECK (…)')`）或**切一个批次**（`GO`）。
  干跑门禁会如实报出来，所以这类错不会活到启动阶段。
- **已落库的参数行序号不要"顺手"重排**：纵向参数表（`SYSSS`）的组内 `SEQ_NO` **由代码里参数的声明顺序推导**
  （按 10 递增）。默认做法是**追加在各自域的末尾**——把一条新参数插回声明清单中间，会让它之后
  所有参数的序号整体后移，与**已经落库的行**对不上（连库门禁逐字段比对序号，正是为此存在）。
  工具的开关参数还多一层：能力面组的声明顺序是"工具开关 → 动作族开关"，所以批后新增的工具开关
  声明排在**动作族之后**（见 `AssistantToolKeys.AppendedToolNames`），而不是插回工具清单中间。
  可参照的实例：`304` 报表工具、`305` 单据历史、`306` 附件清单（三个都是"开关 + 输出上限"的追加批次）。
- **确有语义理由要插在中间时，就在同一条迁移里把序号改到位**：`308`（知识库检索的相关性截断幅度）
  就属这种情形——它与另外两条"检索侧"参数是同一组相邻语义，硬追加到组末会让 3105 页面的顺序读着不对。
  做法：目录里插在它该在的位置，迁移里用**按参数键写死目标值**的 `UPDATE` 把同组后续几行改到位
  （不是"整体 +10"：迁移可重复执行，递增式重排第二次会把序号再推一遍），并断言整组序号。
  判断标准是**爆炸半径**：工具开关一动会推后动作族及其后的所有参数（所以只能追加）；
  单组内只影响三五条（所以可以就地重排）。两种做法都得让"目录推导出的序号 = 库里的序号"那条断言继续绿。
- **别照抄旧迁移的列清单**：`SYSDH`/`SYSDD` 这类授权表会随 ADR 演进增删列
  （如 `FORM_ADJUST_TAG` 已按 ADR-022 退役、代之以 `MODULE_CONFIG_TAG`）。
  照抄旧迁移会在**干跑阶段**就报"列名无效"——这也是先跑
  `pwsh scripts/test-migration-dryrun.ps1` 的价值所在。

## 四、新增一个迁移

1. 看当前最大编号：

   ```powershell
   Get-ChildItem EOS.API/Data/Migrations -Filter '*.sql' | Sort-Object Name | Select-Object -Last 1 -ExpandProperty Name
   ```

2. 新建 `NNN_描述.sql`，编号取最大 +1；
3. **对象命名全大写**（表、列、索引、约束）；
4. 需要写入元数据（模块、字段、列配置）时，一并写在同一个迁移里——
   界面形态由元数据驱动，元数据不跟着走，别人拉下代码界面就是残缺的；
5. 在本地启动应用，确认迁移执行成功（看启动日志与 `/health/ready`）；
6. 用 `sys.*` 核对落库结果（例如 `sys.columns` 里新列确实存在），
   **不要只凭"启动成功 + 健康检查 Healthy"下结论**。

## 五、写迁移的注意点

### 幂等

元数据种子类脚本要写成幂等的（先判断存在性再 INSERT/UPDATE），
因为同一个库可能被不同分支的代码反复启动。

**加列/加索引同样要守卫**：`IF COL_LENGTH('dbo.表', '列') IS NULL ALTER TABLE … ADD …`，
重复执行为空操作（`287_assistant_session_archive.sql` 即是此形）。

顺带一条踩过的坑：**取编号时别只按前缀筛**。我曾用 `-Filter '1*.sql'` 找最大号，
只看到 100~199，而实际已经排到 28x —— 结果新迁移撞上别人的号（`200_depot_stock_policy…`）。
按"四、新增一个迁移"里那条命令取**全部** `*.sql` 的最大值。

### 改表要连迁移一起改（否则真库用例先红）

`Data/Migrations/` 是库结构的唯一来源，但**代码不会自己去核对它**。曾有一列
（`ASSISTANT_MESSAGE.TOOL_CALLS_JSON`）在仓库里"到处都被当成存在"——ADR 的建表记录、
仓储的写入与查询、服务端编排都在用它——而建表脚本里根本没有、此后也没有迁移补上；
直到**真库用例**跑出 `列名 '…' 无效` 才暴露（而它在 done 事件之前断流，用户看到的是"回答没回完"）。

两条教训：

- 写 `SELECT/INSERT/UPDATE` 用到某列前，先确认**建它的迁移在仓库里**（不是"印象里应该有"）；
- 依赖库结构的代码，**真库用例必须跑**：单测用的是假仓储，这类"代码有、库没有"的不一致在单测里永远看不见。

### 改元数据（FIELDS）的迁移要顺带标脏

批量改 `FIELDS`（类型、显示格式、只读/必填…）的迁移**必须同时把受影响的模块写进
`dbo.WORKBENCH_MODULE_DIRTY`（`DIRTY_TAG=1`）**：工作台读到的是已发布快照、不是实时 `FIELDS`，
不标脏就表现为"改了元数据、界面没变"的静默落后，只有重发布之后才消失。

- 脏标记按键取**模块**（`M_IDX`）；"受影响表 → 模块"的映射与 `WorkbenchDirtyMarker` 同源
  （`MODULES.MASTER_TABLE` / `MODULES.DETAIL_TABLE`）；
- **改显示口径不等于改物理列**：`F_TYPE` 由 `datetime` 家族改成 `date` 只影响录入控件与显示格式，
  物理列不动（既有时间值不截断、存储过程按 datetime 比较与赋值也不受影响）——
  实例见 `309_date_only_fields_to_date_type.sql`；
- 脚本末尾要**断言**"目标行已达标 + 受影响模块已标脏"，把"漏标脏"变成启动即失败，
  而不是等人在界面上发现。

### 事务配平

如果脚本内自带 `BEGIN TRANSACTION`，必须配对 `COMMIT`。DbUp 会给每个脚本再套一层事务，
自身事务没配平会让 `@@TRANCOUNT ≠ 1`，随后报错。**没有特别理由就不要自己开事务**。

### 不自带 `USE`

连接已指定库（`EOS.ERP`），脚本里不要再写 `USE`。

### 脚本编码

迁移脚本是 UTF-8。要手工用 `sqlcmd` 执行历史脚本时，必须带 `-f 65001`，
否则中文内容在部分区域设置下会解析失败。

### 删除库对象前先查引用

准备 DROP 表/列/存储过程前，至少核查三类引用方，缺一类就可能删掉还在用的东西：

1. **库内依赖**：查 `sys.sql_expression_dependencies`。注意**未限定 schema 的引用
   `referenced_schema_name` 为 NULL**，只按 `= 'dbo'` 过滤会把它们整批漏掉；
2. **运行时配置**：已发布快照里的同名引用、报表排序等元数据字段；
3. **代码与脚本按名调用**：C# 里的直接调用，以及测试脚本、夹具 SQL 里的
   `EXEC P_*` / `CommandText = 'P_*'`。

漏掉第 3 类是最常见的翻车方式：编译通过、单测通过，但某个验收脚本一跑就挂。

### 已落库的登记改错了：另出一个脚本，别改原文

「已执行过的脚本再改内容不会重新执行」的反面同样成立：**内容改对了，库也不会变**。
所以当一个**已落库**的迁移把元数据登记错了（模块号挂错层级、权限镜像错了对象、
字段口径写反），正确处置是**新增一个脚本做订正**，而不是回头改原文：

- 原文已进台账，改它既不重跑，也让"脚本内容与台账"对不上，后来人照原文理解现状会得出错结论；
- 订正脚本要**对历史库形态幂等**——它面对的是"原文跑过、原文没跑、以及全新库先跑原文再跑它"
  三种状态，因此每一步都判断存在性（存在即跳过），并在收口处断言目标状态成立、
  旧登记已无残留；
- **作废旧标识符前先查外键**：`MODULES.M_IDX` 被 `REPORT` / `MODULE_VALIDATION_RULE` /
  `MODULE_BUSINESS_ACTION` 引用，仍被引用时**中止迁移并报错**，不要连带删除别人的行；
- **重编号不得少授权**：`SYSDH`（组）/`SYSDD`（个人）的授权行要**逐主体复制**，
  且以"新编号的主体集合 ⊇ 参照模块的主体集合"作为收口断言。注意**个人权限整表覆盖组权限**，
  只搬组权限会让原本有个人权限行的用户静默失去权限。

实例：日志管理页初版由迁移 `283` 登记为模块 `110112`（挂在基本参数下），
与"定制页都在 23 系统管理"的惯例不符；由迁移 `284` 重编号为 `2313`（根 23 / 父 2311）
并把 `110112` 从 `MODULES`/`SYSDH`/`SYSDD` 三处退役，授权取原两套授权的并集。
判定仍以**干跑 + 落库后查 `sys.*` 与台账**为准。

## 六、诊断

| 现象 | 原因与处理 |
|---|---|
| 启动报"迁移失败" | 看启动日志里的脚本名；常见是 SQL 语法错、对象已存在、事务未配平 |
| 改了脚本但没生效 | 文件名没变 → DbUp 认为它执行过了。新增一个脚本，不要原地改 |
| 同一个脚本执行了两次 | 脚本被改过名，或台账被手工清理过。检查 `ERP_SCHEMA_JOURNAL` 里的资源名 |
| 新环境启动报缺表/缺列 | `10_schema.sql` 与 `40_journal_baseline.sql` 版本不匹配；按 [02-本地环境与运行](./02-本地环境与运行.md) 重新建库 |
| 想确认某个迁移是否真落库 | 查 `sys.columns` / `sys.objects`，或查 `ERP_SCHEMA_JOURNAL` 的资源名，别只看健康检查 |

## 收口（迁移 319~329）：退役类迁移的五条约定

本周期连写了一批判列、退役模块、删表、清悬空登记的迁移（319~329），惯例固化如下：

- **删数据前先证明"删的是同一批"**：删表前要求行数为 **0（新库）或与归档逐数字一致**（`SYSDF` 要求 11134 行
  且最新时间戳一致，否则报错让你先重新归档）；删列前要求"这些列没有任何实质内容"（`324` 逐列验过
  `CONFIRM_DATE` 全是 `1900-01-01`、`CI` 全是 `DEFAULT`、`CONFIRM_PERSON` 全是空白才删）。
- **按 `M_IDX` 动态扫全库**：退役模块时游标扫"所有带 `M_IDX` 列的表"，除白名单（本次要清的那几张 +
  `AUDIT_EVENT` 审计痕迹）外任何一张有该模块的行就报错——将来新增按模块存数据的表，守卫自动覆盖到它。
- **退役要连元数据登记一起清**：`TABLES` / `FIELDS` / `FIELD_DATASOURCE` / `SYSQL_DEFAULT` / `SYSQL_FIELDS`
  里描述已不存在对象的行是"坏条目"（字段维护页会列出点不开的表）。`328` 按谓词把这类悬空登记清扫干净并
  留下不变量：**清完之后不得再有指向不存在对象的登记行**；被模块当主/副表引用的那几条**刻意不删**、
  报告给人定夺（本周期据此查出并退役了 2202/2203/2204 三个下线管理页）。
- **带筛选索引的表做 DML 要显式 `SET QUOTED_IDENTIFIER ON`**：`WORKBENCH_DEFINITION_SNAPSHOT` 上有
  `IS_CURRENT=1` 的筛选唯一索引，DbUp 走 ADO.NET 默认 ON 没事，但 sqlcmd（默认 OFF）干跑会报 Msg 1934。
  新迁移照 319~329 的样子把 `SET QUOTED_IDENTIFIER ON` / `SET ANSI_NULLS ON` 写在开头。
- **落地前先干跑**：`pwsh scripts/test-migration-dryrun.ps1 -Path <绝对路径> -CheckSql "<探针>"`（外层事务包住
  再整体回滚）。它抓出过真缺陷：`PRINT` 里嵌子查询（Msg 1046）、临时表主键重复、上面的 Msg 1934，
  以及一条把"把 `MODULES` 当主表的模块数量"写错的断言——**干跑不是走过场**。
