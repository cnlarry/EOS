# 45 受限表达式与虚拟字段

字段元数据里可以存表达式。表达式最终会影响取数，所以**不能未经解析直接进入 SQL**。
实现：`EOS.API/Data/RestrictedExpressionService.cs` + 一组受控解析器。

## 一、两类表达式

| 类型 | 字段列 | 作用 |
|---|---|---|
| 虚拟列表达式 | `FIELDS.VIRTUAL_EXP` | 该字段的值由表达式算出，库里没有对应物理列 |
| 转换函数 | `FIELDS.CONVERT_FUNCTION` | 该字段的值经注册表函数转换后展示 |

## 二、保存即生效，没有发布流程

> 表达式**随字段一起保存**，保存路径在写库前调用受控校验；
> **空值 = 清空**（保存后把表达式列写回 NULL）。
> 校验不通过则整单拒绝，不做部分保存。

**没有「校验 → 预览 → 发布」三步流**，也没有对应的端点。看到有人要加"发布表达式"，
先确认不是把已废除的设计带回来。

为什么可以不发布：运行时字段视图**每次查询实时重建**，所以保存完立即生效。

## 三、校验的四道门

`ValidateAsync` 按顺序检查，任一失败即拒绝：

| 顺序 | 检查 | 失败信息 |
|---|---|---|
| 1 | 长度 ≤ **2000** 字符 | 表达式长度超出限制 |
| 2 | 字段必须是虚拟字段（仅 `VIRTUAL_EXP`） | 非虚拟字段上的虚拟表达式不会进入运行时，直接拒绝并提示 |
| 3 | 语法解析（引用 / 算术 / 注册表函数） | "虚拟表达式不支持：…" |
| 4 | 引用的表列**物理存在**；跨表引用必须在 `QUERY_RELATION` 白名单内 | 列在物理表中不存在 / 未配置 QUERY_RELATION |

第 2 道门值得展开：`VIRTUAL_EXP` **只在 `IS_VIRTUAL=1` 的字段上生效**。
读取侧按这一位决定是否解析，所以非虚拟字段上写了表达式是"看着配了、实际不工作"。
校验在这里拦下它，避免配置与行为脱节。

字段本身不存在（元数据没登记）时同样拒绝。

## 四、虚拟表达式支持的形态

| 形态 | 例子 | 说明 |
|---|---|---|
| **单引用** | `表.列` | 直接取另一列的值 |
| **受控表达式子集** | `COP_ORDER_D.QTY-COP_ORDER_D.FINISHED_SEND_QTY`、`CASE WHEN A.X=1 THEN 1 ELSE 0 END` | 列引用 + 数值/字符串字面量 + 四则运算 + 括号 + 一元正负 + 比较（`=` `<>` `<` `<=` `>` `>=`）+ `AND/OR` + `CASE WHEN`（可嵌套）+ 字符串拼接 |
| **受控标量函数** | `ROUND(A.X,2)`、`DATEDIFF(MM,IN_DATE,GETDATE())`、`CAST(A.X AS char(20))` | 只能调用白名单函数，见下表 |
| **`dbo.` 单函数形态** | `dbo.f_get_unit_type_desc(A.UNIT_TYPE)` | 除语法白名单外，还须登记在 `VirtualColumnResolver.ControlledScalarFunctions` |

函数白名单在 `VirtualArithmeticParser.Functions` 一处声明，**参数个数与首参类型也在那里定**：

| 函数 | 参数个数 | 说明 |
|---|---|---|
| `ROUND(x,n)` | 2 | 四舍五入到 n 位 |
| `CEILING(x)` | 1 | 向上取整 |
| `CAST(x AS 类型[(长度)])` | 2 | 目标类型另有白名单（`char/varchar/nvarchar/int/decimal/date/...`） |
| `RTRIM(x)` / `LTRIM(x)` | 1 | 去右/左空格 |
| `DATENAME(单位,x)` | 2 | 首参须为字符串字面量或日期单位关键字（`WEEKDAY`、`MM` 等） |
| `DATEDIFF(单位,x,y)` | 3 | 同上 |
| `GETDATE()` | 0 | 当前时间 |
| `f_get_unit_type_desc(x)` | 1 | 计量单位类型 → 中文描述 |

超出这些形态的一律拒绝。**不要指望它能写任意 SQL 片段**——这是刻意的。

### 聚合函数不在支持范围（`SUM` / `COUNT` / `AVG`）

写 `SUM(明细表.列)` 会在语法层被拒，错误信息是
`虚拟表达式不支持：未知函数：SUM（受控函数白名单：…）`；
`EOS.API.Tests/RestrictedExpressionServiceTests.cs` 的 `VirtualArithmetic_InvalidForms_Rejected` 钉着这条。

这不是"还没来得及加"，而是形态装不进去：

1. 虚拟字段在运行时是**逐行标量片段 + LEFT JOIN**（`WorkbenchQueryComposer.BuildListSelectionAsync`），
   SELECT 里没有 GROUP BY 层。把聚合塞进去，SQL Server 要么报"列不在聚合函数或 GROUP BY 子句中"，
   要么把整个结果集塌成一行。
2. 主表常常已经把明细 JOIN 进来了（`COP_ORDER_M` 的 `QUERY_RELATION` 就含 `LEFT JOIN COP_ORDER_D`），
   引用明细列会让主表行按明细行数重复展开；虚拟字段机制没有去重或聚合保护。
3. 虚拟字段**不可排序、不可查询**（`WorkbenchQueryComposer.ResolveOrder` 只收非虚拟字段，
   `AddQueryPredicates` 直接抛"虚拟字段不可查询"），行级筛选白名单也只收 `IS_VIRTUAL=0`。
   金额这类要排序、筛选、导出的列放不进来。

主表的"合计"因此走**服务端汇总**：保存管线在效果链之后用 `SUM(明细列)` 回写主表的
`AMOUNT` / `AMOUNT_TAX` / `TAX_SUM`（`WorkbenchCommandHandler.RecalculateMasterAmountsAsync`），
金额以它为准。只想"多展示一个合计"时用聚合视图承载（视图按主键 GROUP BY，主表 `QUERY_RELATION`
JOIN 它，虚拟字段只引用视图的一列）；跨表聚合报表的出口是 `ReportAggregateRegistry`。

### 跨表引用必须走 `QUERY_RELATION`

如果表达式引用了**别的表**的列：

1. 基表必须配置 `TABLES.QUERY_RELATION`；
2. 被引用的表必须能在该关系里解析出唯一的关联段（别名优先；物理表名必须唯一命中，
   重复命中会因无法确定关联段而拒绝）；
3. 解析器与运行时**共用同一份引用名口径**，所以"校验通过"即意味着"运行时能渲染"。

这条规则的效果是：**跨表取数不会变成隐式笛卡尔积**——能用哪些表、怎么关联，
都在 `QUERY_RELATION` 里写死了。

**同一条 FROM 里两路 JOIN 必须按别名去重**：`VirtualColumnResolver.ResolveAsync` 的
`alreadyJoined` 参数接收"调用方已经拼进这条 FROM 的 JOIN 别名"（例如选择器过滤条件那一 JOIN 段），
命中这些别名的关联段不再重复输出。带别名的 JOIN 在同一 FROM 里出现两次时，SQL Server 直接报
`在 FROM 子句中多次指定了相关名称` ——这是**执行期**错误，只拼字符串看不出来。
两侧别名同源同一张 `QUERY_RELATION`，所以让出去的那一段必然已存在，`SelectFragments` 照常引用得到。
回归用例：`EOS.API.Tests/ChooserJoinCompositionLiveTests.cs`（把两段拼好后真的执行一次）。

## 五、转换函数注册表

`RestrictedExpressionService.ConvertFunctionRegistry` 是**唯一来源**，当前登记三项：

| 函数名 | 语义 |
|---|---|
| `f_get_table_kind_desc` | `T_KIND` 代码 → 中文描述（参数 = 字段值） |
| `f_get_emp_name_by_id` | 员工编号 → 姓名（参数 = 字段值） |
| `f_get_approve_state_desc` | 批核状态 → 中文描述（参数 = 字段值） |

约定：**参数就是该字段当前值**，函数是一元的。

新增流程：

1. 先在注册表登记函数名与取值语义（含参数/返回）；
2. 确认目标库函数确实存在；
3. 前端下拉**只认服务端下发的注册表**，不得硬编码函数名。

未登记的函数名会被拒绝，错误信息明确提示"新增函数须先登记注册表"。

## 六、构建器怎么回读已有表达式

前端表达式构建器需要把已存的文本还原成可编辑模型。服务端提供结构回读
（`ParseStructure`，与校验**同源解析器**，不触库、不执行）：

| 模式 | 含义 | 构建器行为 |
|---|---|---|
| `reference` | 单引用 `表.列` | 可结构化编辑 |
| `arithmetic` | 受控算术子集 | 构建器不覆盖，只能原始文本编辑 |
| `registry` | 命中转换函数注册表 | 按注册表函数编辑 |
| `raw` | 语法非法或构建器不覆盖的形态 | 原始文本编辑 |

转换函数回读时会**统一给出注册表内的规范名**，避免同一函数出现多种大小写写法。

> 前端不要另立一套语法解析——判"能不能结构化编辑"的答案由服务端给。

## 七、全量重校验

白名单会随解析器/注册表变更而升级，老表达式可能因此失效。两个巡检入口：

| 方法 | 作用 |
|---|---|
| `RescanAsync` | 对全部可见字段的表达式按**当前白名单**重校验，列出失效项（类型/表/字段/原文/错误） |
| `OverviewAsync` | 版本 + 可见/隐藏计数 + 两类表达式计数 + 失效项（供表达式审计面板） |

白名单版本**存在库里**（`EXPRESSION_WHITELIST_VERSION` 的 `MAX(VERSION)`），
读不到时回退到服务端常量 `WhiteListVersion`。

## 八、常见错误与边界

| 现象 | 原因 |
|---|---|
| 提示"不是虚拟字段（IS_VIRTUAL=0）" | 想在物理列字段上配虚拟表达式。要么改登记为虚拟字段，要么直接用列值 |
| 提示"未配置 QUERY_RELATION" | 跨表引用但基表没有关系定义 |
| 提示"不在 QUERY_RELATION 白名单内，或该表名在关系里重复" | 关系里的表名不唯一，无法确定关联段 |
| 提示"列在物理表中不存在" | 表达式里写错了列名，或元数据与物理库不一致 |
| 提示"不在受控注册表内" | 转换函数没登记 |
| 提示"未知函数：SUM" | 聚合函数不在受控子集里；合计走服务端汇总或聚合视图（见第四节） |
| 配了表达式但界面没变化 | 字段不是虚拟字段（见上）；或该字段被 `IS_VISIBLE=0` 过滤 |
| 列编辑器里看不到该虚拟列 | 表达式解析不通过，读取列配置时被剔除（见 [12-元数据消费](./12-元数据消费.md)） |

## 九、注意事项

- **表达式是配置数据，不是代码**：改它不需要发版，但要过校验，且改动是即时的；
- **不要在表达式里追求表达力**：能做的是引用、四则、条件与白名单函数，遇到"想算更复杂的东西"，
  正确做法是在库里建函数并登记注册表，而不是放宽解析器；聚合更不属于这一层（见第四节）；
- **`DATA_FILTER` 也属受限表达式**：它是行级权限的表达式，注入到查询时同样受控解析，
  不要拿它当自由 SQL 用。

## 收口（框架表改名波及表达式与条件白名单）

- 迁移 436–438 把框架表改为 `SYS_` 前缀（`SYSDD` → `SYS_USER_MODULE_PERMISSION`、
  `SYSDG_USER` → `SYS_USER_GROUP_MEMBER`、`SYSDH` → `SYS_GROUP_MODULE_PERMISSION`、
  `SYSDN` → `SYS_EMPLOYEE`、`SYSSS` → `SYS_PARAMETER`），库内 `VIRTUAL_EXP` 与 `DATA_FILTER`
  里的表名同批改过；**新写表达式一律用新名**，旧名会因"表列物理不存在"被第 4 道门拒绝（fail-closed），
  不会静默取空。
- `DATA_FILTER` 的权限表白名单同步换名（如 `SYS_USER_MODULE_PERMISSION` / `SYS_USER_GROUP_MEMBER` /
  `SYS_GROUP_MODULE_PERMISSION`），仍只允许「单表 + 登记列」的形态；`表.列` 前缀仍只在该表恰为主表时合法。
- 表达式语法、受控函数白名单、`QUERY_RELATION` 门槛与"虚拟列不可排序/过滤"的口径均未变。
