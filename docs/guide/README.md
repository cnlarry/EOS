# EOS 开发手册

面向参与 EOS 开发的工程师：讲清系统有哪些能力、怎么用、怎么扩展、边界在哪。

与 `docs/eos-development/` 的分工：

| 目录 | 内容 | 读者 |
|---|---|---|
| `docs/eos-development/` | 生成型业务知识库（模块树、表清单、字段字典），由脚本从库导出 | 模型、检索、查数据时用 |
| `docs/guide/`（本目录） | 手写开发手册（机制、契约、扩展方式） | 开发工程师 |

> **"AI 助手"有两个，不要混**：
> 本手册服务的 AI 助手是**写代码的助手**（读仓库、改代码，靠检索与上下文干活），
> 本目录正是它的上下文来源之一。
> 而产品内的**工作助手**（`EOS.API/Features/Assistant`，用户在界面上对话的那个）是另一套机制：
> 它**不读仓库**——机制问题走能力目录 `describe_mechanism`（真值来自元数据与代码注册表），
> 规范、坑与设计动因走知识库检索（`kb_search`），文档由 `scripts/sync-guide-to-kb.ps1`
> 经既有入库端点投递。两套机制不共用提示词、也不共用检索结论。

### 给 AI 助手的读法

本手册同时作为**写代码的 AI 助手**的上下文（不是产品内的工作助手，见上节的区分），
按下面的顺序用命中率最高：

1. 先读 [`_map.md`](./_map.md)，定位「要改的能力」对应哪篇文档、哪些源码路径；
2. 读该篇及其标注的前置篇目，弄清约定与边界；
3. 再去读 `_map.md` 里登记的具体源码——**文档只讲约定，实现细节以代码为准**；
4. 动手前确认该篇里的「禁止 / 不要」条目，以及 [03-工程规范与硬约束](./03-工程规范与硬约束.md) 的硬约束；
5. 改完按第三节判断要不要同步文档，并跑一次陈旧检测。

写代码时可直接拿文档里出现的**表名、列名、文件路径、类名**当检索词——
本手册刻意保留这些精确标识符，就是为了让检索直接命中。

## 二、写作约定

- **每篇统一开头**，写清读者与前置：

  ```markdown
  > 读者：后端 ｜ 前置：03-工程规范与硬约束
  ```

- **只写"怎么用 / 怎么扩展 / 边界在哪"**，不做逐行代码解读、不抄实现细节。代码能直接回答的不要写进文档——那部分一定先过时。
- **能生成的不手写**：接口清单、元数据清单、效果清单、报表清单一律由脚本导出，文档只引用导出结果，不手工维护副本。
- **一事实一处**：同一结论只在一个地方写全，其他篇目链接过去，不复制粘贴。
- 文档里不写日期与版本号，新鲜度由检测脚本判断（手写的日期一定会假）。

## 三、功能变更时怎么保证文档不烂

靠两件事配合，不靠自觉：

1. **映射表 [`_map.md`](./_map.md)**：每篇文档登记它对应的源码路径。写文档时同步登记；漏登记会被脚本报出来。
2. **陈旧检测 `_tools/check-freshness.ps1`**：对每篇文档比较「该文档最后一次提交」与「其对应源码最后一次提交」。源码更新而文档没跟上，就报 STALE。

```powershell
pwsh docs/guide/_tools/check-freshness.ps1            # 只报告
pwsh docs/guide/_tools/check-freshness.ps1 -Strict    # 有 STALE 即退出码 1
```

哪些变更必须同步文档：

| 变更类型 | 要求 |
|---|---|
| 接口、路由、错误码、配置项、权限键、公共组件 props、数据库对象结构 | **必须**同步对应文档 |
| 已有能力的内部重构、性能优化 | 建议同步（对外行为没变可不动） |
| 缺陷修复、样式调整、测试补充 | 不必同步 |

脚本无法判断"这次改动属于哪一类"，所以它只负责提醒「源码动了、文档没动」，由改代码的人判断要不要动文档。这样不会因为无关改动而被迫改文档。

## 四、目录边界

- `docs/` 下**纳入版本控制**的只有两棵子树：本目录（开发手册）与 `docs/decisions/`（ADR 决策记录）。
  `.git/info/exclude` 中写 `docs/*` 排除全部，再以 `!docs/guide/`、`!docs/decisions/` 放行这两处。
  **新文档必须放在这两棵子树内**，放在 `docs/` 其他位置（`plans/`、`blueprint/`、`business/` 等）不会进仓库。
- 本目录面向开发工程师。面向使用者的说明仍在根目录 `README.md`、`ARCHITECTURE.md`、`QUICKSTART.md`、`CONTRIBUTING.md`。
- 本地忽略规则的恢复副本在仓库根 `.local-exclude.txt`（自身不跟踪），
  改动 `.git/info/exclude` 时需同步该文件，否则换机恢复后规则丢失。

## 五、内容三分与知识通道

本目录的篇目按**内容类型**分三份处置，只有其中两类进产品内工作助手的知识库：

| 内容类型 | 例子 | 去处 |
|---|---|---|
| **机制事实**（系统怎么运作、数据怎么存、字段从哪来） | 元数据模型、权限模型、统一工作台/表单/选择器/报表、效果引擎、审批流、API 契约 | **不进知识库**：真值在元数据与代码注册表里，进库就是第二真源；助手问机制走能力目录 `describe_mechanism`（现算） |
| **规范 / 边界 / 坑** | [`03-工程规范与硬约束`](./03-工程规范与硬约束.md) 全文 + 其余篇目的「禁止 / 不要」节 | 知识库集合 `kb_guide_conventions` |
| **设计动因** | `docs/decisions/` 下的 ADR（为什么要这么设计、否掉了什么） | 知识库集合 `kb_guide_rationale`（强制标注来源与版本） |

推送与重灌：

```powershell
pwsh scripts/sync-guide-to-kb.ps1 -Plan     # 只算：会推哪些、内容哈希、新增还是重灌
pwsh scripts/sync-guide-to-kb.ps1           # 推送（幂等：内容哈希未变的文档跳过）
pwsh scripts/sync-guide-to-kb.ps1 -Verify   # 断言库里没有机制篇目、没有混灌业务知识
```

两集合的可见性都是 `CONSULTANT`（与知识库入库门同档），**未获配置维护权限的账号检索不到**。
写新篇目时按上表判断归属：**讲机制不要写进"规范"里**，讲约束也不要写成机制叙述——
混着写的篇目会被整篇排除在知识库之外（宁缺勿混）。

`docs/eos-development/` 的生成型业务知识是**另一档受众**（模型与检索查数据用），不与本目录合并投放。
