# 41 定义快照与发布

模块定义（表、字段、列、按钮、规则……）是**按请求实时推导**的。为了不每次都重新推导，
系统把推导结果序列化落库，叫**定义快照**。

这篇解释三件事：快照怎么产生、运行时用哪一份、**以及"改了配置为什么不生效"**。

实现：

| 文件 | 职责 |
|---|---|
| `EOS.API/Data/WorkbenchDefinitionBuilder.cs` | 按当前代码 + 当前元数据**重建**定义 |
| `EOS.API/Data/WorkbenchDefinitionProvider.cs` | 加载并缓存已发布快照（运行时基线） |
| `EOS.API/Data/WorkbenchDefinitionSnapshotService.cs` | 状态、校验、发布、回填、落后检测 |
| `EOS.API/Data/WorkbenchDirtyMarker.cs` | 元数据写路径上的**脏标记** |
| `EOS.API/Data/Definitions/WorkbenchDefinitionContentComparer.cs` | 判定两份定义是否**语义等价** |
| `EOS.API/Controllers/WorkbenchDefinitionController.cs` | 管理端点 |

## 一、两张表

| 表 | 作用 |
|---|---|
| `WORKBENCH_DEFINITION_SNAPSHOT` | 快照本体。`IS_CURRENT=1` 的那一行是该模块的当前基线；旧版本保留但置 `IS_CURRENT=0` |
| `WORKBENCH_MODULE_DIRTY` | 脏标记。`DIRTY_TAG=1` 表示"元数据改过，快照可能已过期" |

快照行的关键列：`M_IDX`、`VERSION`、`DEFINITION_JSON`、`SOURCE_METADATA_VERSION`、
`VALIDATION_STATUS`、`VALIDATION_REPORT_JSON`、`PUBLISHED_BY`、`PUBLISHED_AT`。

**版本号格式**：`module-{模块号}-v{版本}`，例如 `module-1405-v3`。

## 二、运行时用哪一份

```
该模块有 IS_CURRENT=1 的快照，且未被标记为脏？
├─ 是 → 以快照为**不可变基线**，在其上叠加按用户的部分（字段级权限、列偏好、数据范围）
└─ 否 → 回退：按当前代码 + 当前元数据实时重建
```

所以"配置改了"不等于"运行时就变了"——**未重新发布时，运行时仍按旧快照跑**，
而且不会报错。这就是所谓的**静默落后**。

发布完成后，服务会**只刷新该模块**的缓存（`RefreshModuleAsync`）；
库里已无当前快照时把该模块从缓存移除，回退实时重建，避免陈旧基线继续生效。

## 三、脏标记什么时候产生

元数据写路径**只标脏，不逐次生成快照**：

| 写路径 | 效果 |
|---|---|
| 字段维护（2302）、工作台列设置 / 列宽保存、菜单默认列 | 标脏**所有把该表当作主表或明细表的模块**——这几条写的都是按 `T_ID` 的**表级**元数据（`FIELDS.DISPLAY_LENGTH` / `SYSQL_DEFAULT`），主表或明细表等于该表的模块，其定义也会跟着变（走 `MarkDirtyForTableAsync`）。只标本模块会让那些模块静默落后 |
| 模块自身的配置（业务动作与校验规则、表单版式、菜单形态与编号） | 标脏该模块（这些按 `M_IDX` 存，走 `MarkDirtyAsync`） |

**只标统一工作台模块**（判据取自视图 `dbo.V_MODULE_NODE`，两个入口同一处过滤）：目录节点与自定义承载页
不装配工作台定义、发布门会直接拒绝它们，标脏只会在"待发布"清单里挂上永远发布不出来的条目。
形态从工作台切走的节点，其残留脏标记在菜单保存时被撤掉（`WorkbenchDirtyMarker.ClearDirtyAsync`）；
发布状态清单（`GetStatusAsync`）的候选集同样按这个视图取，不再各处自己写 `M_URL` 谓词（迁移 340）。
菜单编号变更后旧编号已不存在，也不再给旧编号补一笔（那只会留下孤儿行）。

两种调用方式：独立连接，或**传入业务事务**（与业务写入同生共死）。

## 四、发布流程

`PublishAsync` 逐模块执行，`PublishOneAsync` 是真正的一步：

```
1. 校验（WorkbenchDefinitionValidator）
   不通过 → 不发布，脏标记保留，返回失败与逐项检查结果
   ↓
2. 读当前快照（UPDLOCK, HOLDLOCK，与并发发布互斥）
   ↓
3. 清脏标记
   ↓
4. 内容比较：
   与当前快照**语义等价** → 复用当前版本号（不递增）
   否则 → VERSION = MAX+1，旧快照 IS_CURRENT=0，插入新快照（IS_CURRENT=1）
   ↓
5. 提交事务
   ↓
6. 提交后（非事务）：刷新该模块缓存 → 写审计（动作 PUBLISH）→ 记日志
```

### 第 4 步为什么重要

> **内容未变即复用版本号。**

因为验收证据（对拍报告）是按**定义版本**判定新鲜度的。如果每次"重发一遍"都递增版本，
所有既有证据会被判成过期——而实际上什么都没变。

比较用的是**语义等价**而非字节相等：忽略运行期看不见的差异（如清掉占位公式行、
把空串写成缺省）。所以整理配置不会顶掉版本号、连带作废该模块的对拍证据。

### `SOURCE_METADATA_VERSION`

发布时记录"来源元数据版本"：模块行、主表与明细表字段的 `LAST_UPDATE_DATE` 最大值
（ISO-8601）。用于回答"这份快照是基于哪一版元数据生成的"。

## 五、落后检测

`DetectStalenessAsync` 把定义按**当前代码 + 当前元数据**重建，与已发布快照的
`DEFINITION_JSON` 比较。**只读**：不写快照、不动脏标记。

判据与发布时的"内容未变即复用版本"**同源**（同一个 `WorkbenchDefinitionContentComparer`）——
否则会出现"发布说复用、检测说落后"的自相矛盾。

### 两条必须知道的规则

**1. 重建必须用快照记录的发布者身份（`PUBLISHED_BY`）**

因为字段清单是**按用户**解析的（`WorkbenchDefinitionBuilder.ReadFields` 会读
`SYSQL_FIELDS` 里该用户保存的选择列）。拿另一个身份去重建，字段集合与顺序必然不同，
**对每个有列偏好的用户都会误报"落后"**。用发布者身份重建，检测结论才与
"该用户现在点一次发布会不会产生新版本"一致。

**2. `Stale && !Dirty` 才是静默落后**

| 组合 | 含义 |
|---|---|
| `Stale && Dirty` | 已知的**待发布积压**——配置改过、脏标记在，属正常状态 |
| `Stale && !Dirty` | **静默落后**——配置变了却没有任何标记提示需要重发布，运行时仍按旧定义跑，**这才是异常** |
| `!Stale` | 一致 |

输出里还会带**首个差异位置的上下文片段**（两侧各 60 字符），
一眼能看出是字段元数据、业务动作还是别的东西变了。

## 六、管理端点

路由前缀 `api/v1/workbench-definitions`：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/status` | 各模块状态：是否启用、脏、版本、发布人/时间、校验状态 |
| `GET` | `/staleness` | 落后检测结果 |
| `POST` | `/validate` | 试校验（不发布），返回逐项检查与将要生成的 `DefinitionJson` |
| `POST` | `/publish` | 发布指定模块 |
| `POST` | `/backfill` | **回填**：对统一表单白名单（已启用）的全部模块发布 |

"启用"的定义是**运行期有统一表单**（写名单可编辑，只读名单只能浏览）。
只读模块同样需要快照与发布管理。

## 七、排障

| 现象 | 原因与处理 |
|---|---|
| 改了字段标签，界面没变 | 未重新发布；或该模块没有快照（实时重建，改完应立即生效——那就要查别处） |
| 发布后版本号没涨 | **内容语义等价，复用了版本**。这是设计如此，不是失败 |
| 发布被拒 | 看返回的逐项检查（`VALIDATION_REPORT_JSON`）；脏标记会保留，改完再发 |
| 检测报落后但脏标记为 0 | **静默落后**，需要重发布；先看差异片段定位改了什么 |
| 检测报告大量误报 | 检查是否用了非发布者身份重建（见第五节） |
| 新环境没快照 | 快照不随建库脚本走，需要发布或回填一次 |

## 八、注意事项

- **不要手工改 `IS_CURRENT`**：当前版本由发布流程维护，手工切换会让缓存与库不一致；
- **不要在元数据写路径里顺手生成快照**：写路径只标脏，快照由发布动作批量生成；
- **发布失败要修根因**：校验拦下说明配置有问题，绕过校验（如直接改 `VALIDATION_STATUS`）
  只是把问题推到运行时；
- **改了元数据记得跑一次落后检测**，把 `Stale && !Dirty` 清零。

## 收口（迁移 321 起）：判据统一之后怎么收口落后快照

- **写权限判据换了真源**：`HasAdd` / `HasEdit` 现在由"写名单 / 只读名单"算出（不再是动作路由）。判据统一
  **之前**发布的快照与按当前代码重建的结果因此会不一致——差异集中在 `HasAdd` / `HasEdit` 这类布尔位
  （每个模块 44~89 字节不等）。
- **收口两条路**：① **重新发布**受影响模块（`pwsh scripts/republish-all-whitelist.ps1`，默认覆盖
  统一表单写名单 **∪** 库内所有带当前快照的模块——只读名单模块同样有快照、同样要与配置同步，
  只按写名单枚举会让它们永远重发布不到）；
  ② **标记为脏**（`WORKBENCH_MODULE_DIRTY`）让积压可见。`check-snapshot-staleness.ps1` 对
  `Stale && !Dirty` 判失败、对 `Stale && Dirty` 只提示——"知道它落后"也算一种合法收口，但别让它悄悄落后。
- **重发布走运行中的 `EOS.API`**（端点 `POST /api/v1/workbench-definitions/publish`）：落
  `WORKBENCH_DEFINITION_SNAPSHOT` 的新版本行并切换 `IS_CURRENT`。模块元数据改动（含模块退役）后，
  **旧快照会被重建判据判为落后**，属于"改完要重发布"的正常后果。
- **改定义契约的迁移不会标脏**：脏标记只由元数据写路径维护，迁移（如退役行归属三列）改掉的定义字段
  既标不出脏、也可能不动 `LAST_UPDATE_DATE`，只能靠落后检测的"重建再比对"发现。故改定义契约的迁移
  落地后跟一次全量重发布；重发布前先跑 `scripts/adr012-acceptance-ledger.ps1` 取基线，确认没有 A 类
  等价证据会被顶起的版本降级（内容未变的模块复用版本，纯退役键残留仍被判"有变"而顶版本）。
- **发布这条路本身**（版本真源 `version.json`、`release.ps1` 两步走、`-TagOnly` 断言、MANIFEST 里的迁移区间
  与基线覆盖行）见 [`docs/decisions/ADR-026-版本管理与发布流程.md`](../decisions/ADR-026-版本管理与发布流程.md)
  与发布技能 `.agents/skills/eos-release/`。
