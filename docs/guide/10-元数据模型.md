# 10 元数据模型

EOS 的界面形态由库内元数据决定：**加一个模块 = 往元数据里加数据，不是写一个新页面**。
三张核心表是这套机制的根：

| 表 | 主键 | 作用 | 当前规模 |
|---|---|---|---|
| `MODULES` | `M_IDX` | 菜单节点树：模块 / 自定义承载页 / 目录节点，兼权限锚点与主·明细表绑定 | 357 行 |
| `TABLES` | `T_ID` | 表登记：哪些物理表可供界面使用 | 488 行 |
| `FIELDS` | `T_ID` + `F_ID` | 字段登记：每个列怎么显示、怎么校验、怎么选值 | 12104 行 |

> 行数是本文写作时的实测值，会随开发变化，不必当常量记。

## 一、`MODULES`：菜单节点

一行是**菜单节点**，不全是"模块"。它同时承担四件事：菜单节点、权限锚点、单据结构声明、界面配置入口。

### 节点形态（迁移 340）

承载页（`M_URL`）与操作主表（`MASTER_TABLE`）的组合决定这一行**是什么**：

| 形态 | 判据 | 实测规模 |
|---|---|---|
| 统一工作台模块 | `M_URL` 是 `/workbench`，或留空但有主表（留空有主表即默认落统一工作台） | 282 |
| 自定义承载页 | `M_URL` 是非 `/workbench` 的精确路径 | 28 |
| 目录节点 | `M_URL` 留空且无主表（既无承载页也无数据源，只剩层级与权限锚点） | 47 |

判据**只有两处实现，且必须逐字一致**：SQL 视图 `dbo.V_MODULE_NODE`（查询侧，取值
`WORKBENCH` / `CUSTOMPAGE` / `DIRECTORY`）与 `ModuleRouteValidator.ResolveKind`（代码侧，值为已在内存里的行）。
此前同一条判据散在多处 SQL 里各写一遍（`M_URL LIKE '/workbench%'`、
`MASTER_TABLE IS NOT NULL AND M_URL IN ('','/workbench')` ……），写法已经出现分歧——同一行在不同路径上
会被判成"是/不是模块"，而工作台定义装配、字段级权限、报表可见性、助手模块清单都按模块号判定。
迁移 340 把它收口，并清掉非工作台节点上**没有消费方**的工作台配置残留：排序字段、不可解批、
自动批核、可以复制、异常记录不可保存、明细必需字段、无明细资料不可保存、效果引擎开关、分组表达式、
表单打开方式。`scripts/check-module-node-kind.ps1` 守住这次收口（判据存在且取值封闭、统一表单名单全是
工作台模块、形态外无残留、脏标记只属于工作台模块）。

**刻意不随形态清掉的三类**（都有真实消费方，与"由谁承载"无关）：

- `MASTER_TABLE` / `DETAIL_TABLE`——报表数据集（`REPORT.M_IDX → MODULES.MASTER_TABLE`）、搜索中心、
  统一选择器、业务流"表↔模块"映射、助手指标都按它取数；实测 11 个自定义承载页模块挂着 20 张报表，
  清掉主表等于让那些报表当场变空数据源。**所以 2301 在自定义承载页上把主表/副表显示为只读**：
  它们是数据源锚点，由开发团队定义。
- `FILTER`——同时是报表的数据范围与选择器的数据范围，被**实时**读取（不经快照）；
- `SEARCH_1/2`——搜索中心是独立于承载页的可达面（`/search-center`），有主表就仍然可用。

|---|---|
| `M_URL` | **承载页（唯一路由字段）**：空 = 目录节点 / 未声明承载页（单据模块按主表判定，默认落统一工作台）；`/workbench` = 统一工作台；精确路径 = 自定义承载页 |

### 表单打开方式（迁移 319）

| 列 | 含义 |
|---|---|
| `FORM_OPEN_MODE` | 统一表单打开方式：`TAB` 本页签（默认）/ `NEWTAB` 新页签 / `DIALOG` 弹窗 |
| `FORM_DIALOG_WIDTH` / `FORM_DIALOG_HEIGHT` | 弹窗方式的窗体宽高（px）；只有弹窗方式消费，留空按 720×560 |

**配置入口是表单设计器**（`?design=1`：在单据表单页的字段设置菜单里点【表单设计】，需 `FORM_DESIGN_TAG`；
模块管理不提供这个入口——它只管模块自身的字段）：打开方式与窗体尺寸在
页签行右端的【表单呈现】里改；**一行几列不在这里**（它是页签级事实，见下）。
它随版式**同一笔保存、同一次重发布**，所以**保存即生效**——不走模块管理那条"存草稿 → 人工点发布"的链。
取值两侧把关——库内 CHECK 约束（迁移 319）+ 设计器保存端点白名单（`FormLayoutSubmission`，
非法打开方式/越界尺寸/越界页签列数即 400，不会放到库里撞约束变 500）。

### 页签级列数（迁移 319）

| 列 | 含义 |
|---|---|
| `MODULE_FORM_TAB.LAYOUT_COLUMNS` | 该页签的栅格列数 1..4，**NOT NULL DEFAULT 4**：一行几列只此一处真源 |

同一表单的不同页签可以一行几列各不相同（页签 1 两列、页签 2 一列）。
列数挂在页签表上而不是 `MODULES`：一个模块常常只有一个页签，而字段疏密差异恰恰落在**页签之间**，
模块级单值表达不了；且"页签未声明时回落模块默认"会让同一语义有两个名字、其中一处空转。
本表挂在版式上也顺带解决生命周期——它随页签行一起增删（重置版式/套用模板都不会留下无主的列数），
而打开方式是模块自己的开关，不该被"重置版式"带走。

### 其它

- `M_TAG`：模块标记；
- `SEARCH_1` / `SEARCH_2` / `FILTER` / `SORT_FIELDS`：列表检索与排序配置；
- ~~`GROUP1`~`GROUP5` + `GROUP_EXP1~5` + `GROUP_DESC1~5`~~：列表分组配置，**迁移 341 已下线**，
  改建独立表 `MODULE_GROUPS`（配一个模块任意多组），见本文末「收口（迁移 341）」；
- `REMARK`：**模块备注**（`nvarchar(1000)`）——写"这个模块是干什么的、有什么口径约定"，给后来接手的人看。
  2301「基础」页签里是个多行文本域，保存随模块行一起落库（空串落成 `NULL`）；它**不参与任何运行期契约**
  （不装配工作台定义、不进快照），纯粹是给人看的说明。2026-10-06 用户拍板把它从"顺带留着"变成"明确放出来可编辑"。
- `LAST_UPDATE_BY` / `LAST_UPDATE_DATE`：修改人与修改时间（2301 保存时由服务端写入）。
- 已退役的模块级遗产列（`CI` / `OWNER` / `OWNER_G` / `CREATE_PERSON` / `CREATE_DATE` /
  `CONFIRM_TAG` / `CONFIRM_PERSON` / `CONFIRM_DATE`）：迁移 324 物理删除，见下方「已退役列」表。

## 五、列配置：`SYSQL_FIELDS` 与 `SYSQL_DEFAULT`

| 表 | 键 | 含义 |
|---|---|---|
| `SYSQL_DEFAULT` | `T_ID` + `T_ID_R` + `F_ID`（+ `F_IDX`） | **系统默认列**：用户没自定义时显示哪些列、什么顺序 |
| `SYSQL_FIELDS` | `USER_ID` + `T_ID` + `T_ID_R` + `F_ID`（+ `F_IDX`） | **用户自定义列** |

- `T_ID` 是主表，`T_ID_R` 是目标表——主子表场景下用同一张配置表区分主表列与明细列；
- `F_IDX` 是顺序号；
- 优先级规则见 [12-元数据消费](./12-元数据消费.md)：**用户有配置就完全采用用户配置**。

`SYSQL_CONDITION` 是另一类：用户保存的查询条件（见 [44-受控查询与条件模板](./44-受控查询与条件模板.md)）。

## 六、你该知道的两处现存数据问题

改动元数据时留意，别把它们扩散。

**1. `FIELDS.F_TYPE` 混有非类型名的值**

实测分布（部分）：`nvarchar` 5895、`float` 2252、`datetime` 1281、`nchar` 1147、`bit` 821……
但另有 **`String` 14 行、`Integer` 1 行、NULL 13 行**。

`F_TYPE` 的约定是 SQL 类型名。新增/修改时用正确类型名；遇到这几行按需订正，不要照抄。

**2. `F_DESC` 曾出现占位文本**

历史上把"无说明"写成了非空占位文本 `'NULL'` 与 `'&nbsp;'`，读取侧"空则回落字段代号"的兜底拦不住，
于是标签上直接显示字面量 `NULL`。现读取侧已显式剔除这两个值，
`F_DESC` 的合法值就是**真描述或 NULL/空串**，不要再写占位文本。

## 收口（迁移 341）：列表分组独立成 `MODULE_GROUPS`

分组原是 `MODULES` 上的固定 5 组列（`GROUP1..5` / `GROUP_EXP1..5` / `GROUP_DESC1..5`）：上限由列数写死，
读取侧一律按下标偏移取值（`9 + i*2`、`11 + i*3`、错误码 `GROUP{i+1}`），于是"第几组"同时是排序与身份。
迁移 341 把这 15 列下线，改建 `MODULE_GROUPS`：**一个模块任意多组**。

| 列 | 说明 |
|---|---|
| `GROUP_ID` | 自增主键，**分组的身份**（列表分组的深链按它定位，见 [40-统一工作台](./40-统一工作台.md)） |
| `M_IDX` | 归属模块（`MODULES.M_IDX`；模块编号变更时随 `MenuAdminRepository` 的级联语句一并改指） |
| `SORT_IDX` | 同一模块内的先后顺序——**只是排序，不是身份**（与迁移编号同一条纪律） |
| `GROUP_DESC` | 分组下拉上显示的名字 |
| `GROUP_EXP` | 分组表达式（受控子集，字段白名单 = 模块主表的物理字段 + 禁止/成本/保密约束） |

三条口径：

- **有行即生效**：原"启用位 + 表达式 + 描述三者齐备"的三道门收敛为"行存在且两列非空"。未启用的行
  本来就不产生任何界面效果，留着启用位等于让同一件事有两个真源；搬迁口径也随之明确——只搬当时
  **真正生效**的行（启用位=1 且表达式与描述都非空，实测 2 个模块共 4 行），界面从未显示过的那批
  历史残留不搬（搬过去会因为"有行即生效"而突然出现）；
- **保存即生效、不进快照**：`WorkbenchDefinition.GroupExpressions` 带 `[JsonIgnore]`，组装定义时
  实时读取，故它与 `FormLayout` 那类随快照冻结的段不同——改分组**不需要重新发布**；
- **配置面是 2315「模块分组」**——一个**定制承载页**（`/admin/module-groups`，迁移 342 定形态）：
  它要办的是"选一个模块 → 维护**它的**分组"，通用表单只能维护 `MODULE_GROUPS` 自己那些行，
  表达不了这件事；也不该走发布（分组本就是保存即生效的配置，见下条）。所以 2301 的「分组」页签与
  那 15 行 `FIELDS` 元数据随 341 删除，`MODULE_GROUPS` 的字段登记与字段数据来源随 342 一并清掉——
  **系统配置表不进字段目录**（先例：`MODULE_FORM_TAB`）。顺带补上 `MODULES` 剩余 bit 标志列（`M_TAG` /
  `DETAIL_NO_SAVE` / `SEARCH_1` / `SEARCH_2` / `IF_COPY`）的 `DEFAULT`：分组列下线后，它们就是
  L27 那类"NULL 变 500"的仅剩风险面。

模块号取 **2315**（23xx 段当前最大 2314 的下一个）：**编号不回收、不复用**——2308 是旧开发团队已退役的
「工作任务记录」（迁移 327），它虽然空着也不能拿来用，否则同一编号在 git 历史里会有两个互不相干的身份。
