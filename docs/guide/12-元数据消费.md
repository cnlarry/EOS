# 12 元数据消费

库里的元数据不会自己生效——它由服务端的**定义（Definition）**层解释成运行时可用的结构。
理解这一层，才能回答"我明明改了元数据，界面为什么没变"。

主要实现：`EOS.API/Data/WorkbenchDefinitionBuilder.cs`（组装定义）、
`EOS.API/Data/WorkbenchFieldMetaMapper.cs`（字段与列配置）、
`EOS.API/Data/FieldAdminRepository.cs`（字段读写）。

定义层还负责把元数据的**模式相关**语义算出来，这类语义 `FIELDS` 里的位表达不了。例如主档编号
（主表主键）在**编辑态**一律只读（`FormFieldSelector.LockPrimaryKeysOnEdit`）：`IS_READONLY` 与模式无关，
置 1 会把新增态一起禁掉（手填编号的主档就建不了档）。口径与边界见 [42-统一表单](./42-统一表单.md)。

> **不是所有模块都走工作台**：像"会话管理"这类**定制页**，`MODULES.MASTER_TABLE` 为空，
> 它进不了统一表单白名单，前端也不由定义层渲染。这类模块的 `M_URL` 必须**同时**登记在后端
> `EOS.API/Data/ModuleRouteValidator.cs` 的 `ExactRoutes` 与前端路由表里，否则菜单点开只会落到
> `/fallback/modules/{id}` 占位页（登记链路见 [70-后台配置面总览](./70-后台配置面总览.md)）。
> 菜单组 31「工作助手管理」下的 `会话管理`（3101）、`机制与工具总览`（3104）、`知识库管理`（3103）、
> `模型与用量`（3102）与 `助手设置`（3105）都是这类页面：`MASTER_TABLE` 为空，数据来自各自的管理端点，
> 与工作台定义无关。**注意这些页面的数据源不是工作台**：模型与供应商读 `ASSISTANT_MODEL/PROVIDER`、
> 设置读 `ASSISTANT_SETTING`，都是"管理面自己的表"，所以别指望从工作台定义里推导出它们。
>
> **定制页不限于助手域**：系统管理 › 数据表维护 › `业务流程图`（2314）同样是定制页——`MASTER_TABLE` 为空，
> 数据来自 `FIELD_DATASOURCE`（字段取值来源）与 `FIELD_RELATION`（已登记单据关系），与工作台定义无关。
>
> **另一类是"参数化承载页"**：`M_URL` 只写基路径（`/workbench`、`/reports`、`/search-center`），
> 服务端渲染菜单时追加 `/{moduleId}`（`ModuleRouteValidator.ParameterizedBases`），模块照常走定义层。
> **新增模块优先选这条路**——页面形态由元数据决定，不必写前端页面；只有页面确实无法由定义层呈现时，
> 才去登记定制页（两者都要同改三处，见 [06-测试与质量门禁](./06-测试与质量门禁.md)）。
> **`/workbench` 承载的模块，主表也可以是一个视图**：把跨表口径（JOIN、派生列、固定条件）封进视图后，
> 通用单表查询就够用——`14993` 与 `14996`/`14998`/`170297` 都是这种形态，此时模块留空 `FILTER`、
> 排序写 `视图名.列` 进 `SORT_FIELDS`（视图取不到物理主键，排序只能靠它）。
>
> **节点形态是三分，不是二分**：判据只有 SQL 视图 `dbo.V_MODULE_NODE` 与
> `ModuleRouteValidator.ResolveKind` 两处（口径与三形态见 [10-元数据模型](./10-元数据模型.md) 第一节）。
> 消费元数据时**不要再自己写** `M_URL LIKE '/workbench%'` 之类的谓词——写法分歧正是迁移 340 收掉的东西。

## 一、定义里有什么

一次模块读取会组装出 `WorkbenchDefinition`，大意包含：

| 项 | 来源 |
|---|---|
| 模块标识与标题 | `MODULES` |
| 主表 / 明细表 | `MODULES.MASTER_TABLE` / `DETAIL_TABLE` |
| 主表字段清单、明细字段清单 | `FIELDS` |
| 主键列及键序 | `FIELDS.IS_PK` + 物理库主键 |
| 是否可新增 / 可修改 | **不来自元数据列**：由统一表单写名单（`UnifiedFormEditor.EnabledModuleIds`）与权限裁决（迁移 321 删掉了那两条路由列，`M_URL` 只管落点） |
| 单据级动作集 | **不来自元数据列**：由能力（工作流/结案/权限位）+ 单据状态决定；自定义按钮走 `MODULE_BUSINESS_ACTION` |
| 查询与排序配置 | `MODULES.SEARCH_*` / `SORT_FIELDS` |
| 分组配置 | `MODULES.GROUP*` / `GROUP_EXP*` / `GROUP_DESC*` |
| 表单版式 | `MODULE_FORM_LAYOUT` / `MODULE_FORM_TAB` |
| 数据范围 | 当前用户的权限（不是元数据）：`DATA_FILTER` 条件；按执行范围（`OWNER`/`OWNER_G`）过滤已随行归属三列下线退役（迁移 334） |

**定义是"按模块 + 按用户"实时推导的**（并可能落到快照，见 [41-定义快照与发布](./41-定义快照与发布.md)）。

## 二、`FIELDS` 列怎么变成运行时字段

字段元数据从库到运行时的对应关系（`WorkbenchFieldMetaMapper.MapMetadata`）：

| `FIELDS` 列 | 运行时字段 | 说明 |
|---|---|---|
| `T_ID` | 所属表 | |
| `F_ID` | `Key` | 字段标识，前后端都用它 |
| `F_DESC` | `Label` | 显示名 |
| `F_TYPE` | `DataType` | 数据类型 |
| `DISPLAY_LENGTH` | `Width` | 列宽 |
| `ITEM_ALIGN` / `HEADER_ALIGN` | `Align` / `HeaderAlign` | 对齐 |
| `DISPLAY_FORMAT` | `Format` | 显示格式 |
| `IS_VISIBLE` | `IsVisible` | 可见性 |
| `IS_DEFAULT_FIELDS` | `IsDefault` | 是否进系统默认列 |
| `IS_QUERY` | `IsQueryable` | 可作查询条件 |
| `IS_READONLY` | `IsReadonly` | 只读 |
| `IS_VERIFY` | `IsRequired` | 必填 |
| `IS_COST` / `IS_SECRECY` | `IsCost` / `IsSecrecy` | 成本 / 机密（受权限位控制） |
| `DFT_VALUE` | `DefaultValue` | 默认值（**两处消费、判据同源**：保存态由服务端补齐；新增态在下发给客户端**之前**就把日期哨兵 `D`（今天）展开成实际日期。客户端只会原样套用默认值，"哨兵只被服务端认识"会让它把哨兵当普通值提交、保存时被判格式错，详见 [42](./42-统一表单.md)） |
| `VERIFY_INDEX` | `VerifyIndex` | 校验与排序序号 |
| `REGEX` | `Regex` | 校验正则 |
| `F_REMARK` | `Remark` | 备注 |
| `BROWSE_URL` / `BROWSE_M_IDX` | `BrowseUrl` / `BrowseModuleId` | 选单入口 |
| `ONLY_CHOOSE` / `CHOOSE_MULTI` / `CHOOSE_PAGE` | 同名 | 选单行为 |
| `IS_VIRTUAL` / `VIRTUAL_EXP` | `IsVirtual` / `VirtualExpression` | 虚拟字段 |
| `CONVERT_FUNCTION` | `ConvertFunction` | 转换表达式 |
| `CAN_COPY` | `CanCopy` | 复制时是否携带 |
| `IS_AUTOINC` | `IsAutoIncrement` | 自增 |
| `FORM_OPTIONS` | `FormOptions` | 下拉选项 |
| `LAST_UPDATE_BY` / `LAST_UPDATE_DATE` | `LastUpdatedBy` / `LastUpdatedAt` | 审计 |

### 标签的回落规则

```sql
COALESCE(NULLIF(NULLIF(NULLIF(F_DESC, ''), 'NULL'), '&nbsp;'), F_ID)
```

即 `F_DESC` 为空串、`'NULL'`、`'&nbsp;'` 或 NULL 时，**回落显示列名 `F_ID`**。

这三个占位值是被显式排除的——历史数据里出现过，会让标签上直接显示字面量 `NULL`。
新写元数据时只需记住：`F_DESC` 要么是真描述，要么留空。

### 字段名的白名单校验

读出来的 `F_ID` 必须匹配标识符正则（`WorkbenchSql.Identifier`），不匹配的**直接丢弃**，
并按大小写不敏感去重。所以：

- 字段名必须与物理列名一致；
- 大小写不影响匹配，但建议全大写（见 [03-工程规范与硬约束](./03-工程规范与硬约束.md)）。

## 三、列配置的优先级

这是最容易出错的一环。规则是**二选一，不合并**：

```
该用户在该表上有 SYSQL_FIELDS 记录？
├─ 有 → 完全采用用户配置：只有用户选中的列被勾选，顺序按用户的 F_IDX
└─ 无 → 采用系统默认：IS_DEFAULT_FIELDS = 1 的列被勾选
```

实现上先判断存在性（`HasConfig`），再决定勾选来源：

```sql
CASE WHEN (HasConfig = 1 AND 用户配置里有该字段)
       OR (HasConfig = 0 AND f.IS_DEFAULT_FIELDS = 1)
     THEN 1 ELSE 0 END AS IsChecked
```

排序键是三级回落：

```
用户配置的 F_IDX  →  字段的 VERIFY_INDEX  →  列名 F_ID
```

**两端过滤不同**，这也是容易困惑的地方：

| 场景 | 过滤条件 |
|---|---|
| 列编辑器与列表列 | `IS_VISIBLE = 1` |
| 默认列 | `IS_VISIBLE = 1` **且** `IS_COST = 0` **且** `IS_SECRECY = 0` |

原因：成本与机密字段需要额外权限位才可见，不应混进"给所有人的默认列"。

### 虚拟列会被二次筛选

读取列配置时，虚拟字段会先尝试解析表达式；**解析不了的虚拟列会从列配置里剔除**。
这样列编辑器不会出现一个"勾得上、列表却渲染不出来"的列。

判定用的解析器与列表读取是同一套（`VirtualColumnResolver`），
所以"编辑器里能看到"与"列表能渲染"始终一致。

### 写入侧的约束

保存用户列配置时：

- 列数上限 **200**，且不得重复；
- 每个字段都要在该表 `IS_VISIBLE=1` 的字段白名单内，否则整个请求被拒（`ArgumentException`）；
- 写入是"先删后插"，整个操作在一个事务里。

## 四、字段写入与脏标记

在字段设置页保存字段元数据时：

1. `FieldAdminRepository.UpdateAsync` 写回 `FIELDS`；
2. 记一条审计事件（动作类型 `WORKBENCH_METADATA`）；
3. **标记受影响的模块的定义已过期**（`WorkbenchDirtyMarker`）——覆盖面取决于写的是哪一级元数据：
   按 `M_IDX` 存的（业务动作、校验规则、版式、菜单形态）标该模块；按 `T_ID` 存的（`FIELDS`、`SYSQL_DEFAULT`）
   要标**所有把该表当作主表或明细表的模块**（`MarkDirtyForTableAsync`）。

第 3 步是关键：配置变了但快照没重发布，运行时仍按旧定义工作，
表现为"改了没生效"却不报错——即所谓**静默落后**。

列宽的批量保存同样走"写回 + 标脏 + 审计"，并在一个事务里完成。列宽写回的是按 `T_ID` 的
`FIELDS.DISPLAY_LENGTH`（表级），所以标脏的是**用这张表的模块全集**而不是当前模块——一张表既可能是
某模块的主表、又是另一个模块（或某个单据的）明细表，只标当前模块会让后者的定义静默落后。

## 五、数据范围的注入

模块的数据范围过滤（权限侧）会在查询组装时注入到条件里，与前端提交的查询条件合并。
它来自**当前用户的权限**，不是元数据——所以同一个模块、同一条查询，
不同用户看到的数据行可能不同。

详见 [21-授权模型](./21-授权模型.md)。

## 六、排障速查

| 现象 | 大概率原因 |
|---|---|
| 改了 `F_DESC`，界面标签没变 | 模块定义未重发布（快照落后）；或该字段走的是别处的标签来源 |
| 字段在界面上消失了 | `IS_VISIBLE=0`；或 `FIELDS` 缺行；或字段名不匹配标识符正则被丢弃 |
| 列表少了几列 | 该用户有 `SYSQL_FIELDS` 配置 → **完全采用用户配置**，与默认列无关 |
| 成本/机密字段没进默认列 | 这是设计如此（默认列排除它们） |
| 某个虚拟列哪里都不出现 | 表达式解析不通过，已在读取时剔除 |
| 列宽拖到很小又弹回 | 服务端与前端都把列宽钳制在 `[40, 300]` |
| 新增按钮不见了 | `MODULES.NEW_URL` 为空即不开放新增 |
| **新增定制页后菜单点进去是空壳页** | `ModuleRouteValidator.ExactRoutes` 是**精确路径白名单**：新页若只登记了库内模块与前端路由，菜单会退化成 `/fallback/modules/{id}` 占位页。**三处必须同改**：库内 `M_URL`、后端 `ExactRoutes`、前端 `workspaceRoutes.tsx`；`ModuleRouteValidatorTests` 有对应用例拦这条（编译与界面都不报） |
| **同一行在不同路径上被判成"是/不是模块"** | 形态判据（统一工作台模块 / 自定义承载页 / 目录节点）曾散在多处 SQL 里各写一遍，写法已分歧。**只认 `dbo.V_MODULE_NODE`**（代码侧 `ModuleRouteValidator.ResolveKind`，两者取值逐字一致）；`scripts/check-module-node-kind.ps1` 守这条（迁移 340） |

## 收口（无副作用批核能力的判据：不再看 AUTO_APPROVE）

- `WorkflowStates.IsStatelessApproveCapable` 现在是 `!效果链 && !流程`（原先还要求 `AUTO_APPROVE=1`）。这是一处**元数据消费口径的修正**：`MODULES.AUTO_APPROVE` 只回答"保存之后要不要自动翻转确认状态"，不回答"这个模块能不能手工批核"。把它当后者的前置，会让"关掉自动批核"顺手关掉手工批核入口（服务端 404 `WORKFLOW_NOT_SUPPORTED`、前端工具栏不显示按钮）。
- 消费方两处共用同一判定、不得分叉：服务端分支（`WorkbenchApprovalService`）与表单定义（`WorkbenchDefinitionBuilder` 的 `hasStatelessApprove`，前端据此显隐按钮）。
- 顺带记住**批核能力的三条互斥来源**：效果链（引擎接管）、审批流程（送审）、无副作用状态翻转；前两条都没有时第三条必须成立，否则模块会"能录不能审"。
