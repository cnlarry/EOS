# 62 嵌入模型与知识库接线

> 读者：部署方与二次开发者 ｜ 前置：[60-AI工作助手](./60-AI工作助手.md) 第八节（知识库）、
> [ADR-031](../decisions/ADR-031-嵌入模型接入与检索接线.md)

## 一、这一篇解决什么

工作助手有两条知识通道：**机制**（`describe_mechanism`，从元数据与代码注册表现算）与**知识库检索**
（`kb_search`，从 `KB_COLLECTION` / `KB_DOCUMENT` / `KB_CHUNK` 三表里检索手册、规范与业务规则）。

机制通道不依赖任何外部服务；**知识通道要先把文本变成向量**，那需要一个嵌入模型。本篇说明：
接入形态怎么定、怎么配、怎么入库，以及**在意语料外发时怎么改成完全本地**。

> **当前实施状态（务必先读）**：接入形态与本篇的操作口径**已定**（ADR-031），**接线已完成**：
> 模型表按**用途**区分对话与嵌入（`KIND` / `DIMENSION`，"当前模型"按用途各一条）、
> 供应商行可表达"无密钥端点"、预设目录带**认证头样式**与各家"有没有嵌入端点"的核实结论、
> 3102 界面按用途分区且**从目录里选型号**（选中的连同参数落库），嵌入客户端
> （OpenAI 兼容 `/v1/embeddings`，含分批、维度校验、fail-closed）与检索的相对截断也都已落地。
> **仍未做的**：语料入库与检索评估尺子（批 D，需要 API 在线、2302 `CanSetup` 账号与密钥），
> 以及"各家真端点连一次"的实测。所以**没配嵌入模型**时检索侧的可读失败是正常状态
> （`KB_EMBEDDING_NOT_CONFIGURED` 家族）；配好之前，知识库看不到内容的正确解释是"未配置嵌入模型"，
> 不是"库里没东西"。

## 二、接入形态：云端优先，本地可选

| | 云端 API（默认） | 本地自建（可选） |
|---|---|---|
| 接口 | OpenAI 兼容 `POST /v1/embeddings` | **同一协议**（TEI 等自建服务同样暴露该端点） |
| 前置 | 一家提供嵌入端点的厂商 + 一个密钥 | 本机跑一个模型进程（运维启停，本系统不代管） |
| 语料 | **出网**（手册、ADR、业务规则会发给厂商） | 不出网 |
| 检索延迟 | 含一次网络往返（`kb_search` 每次都要） | 本机回环 |
| 换模型 | 改一行数据 | 改一行数据 |
| 波动源 | 厂商限流与网络抖动 | 本机 CPU 与内存 |

**为什么不默认本地**：本地路线把成本押在"这台机器能不能跑起来"（CPU/内存/依赖/量化档位/长驻进程），
而接线批的目的是让知识通道**可用**，不是证明某台机器能跑模型。云端把这条不确定性交给了厂商，
代价是语料出网与每次检索的网络往返——这是部署方的取舍，不是技术优劣。
完整理由与推翻过程见 [ADR-031](../decisions/ADR-031-嵌入模型接入与检索接线.md) §2。

## 三、怎么配（管理面 3102）

配置全部在**管理面**，不进 `appsettings.json`（ADR-030 §8）。两级形状与对话模型一致：

```
供应商（端点 / 协议 / 密钥环境变量名 / 默认超时）
   └── 模型（型号标识 / 用途=对话|嵌入 / 维度 / 超时 / 单价 / 启用 / 当前）
```

界面上这一页分**模型 / 用量**两个页签；「模型」页签是**上下主子表**：上面选供应商，下面是它的模型表，
用途用一个小切换器分开（**对话 / 嵌入各一套列**——嵌入看维度、对话看窗口与输出；混在一张表里必然有
一半的行在某些列上是空的，读的人分不清"这项没有"与"这项没填"）。

卡片头**两个"当前"各说一句**，缺哪个在哪个后面挂一条「尚未配置」徽标：助手能不能聊天看对话模型，
知识库能不能用看嵌入模型——两者坏掉的表现完全不同（"助手不回话"对"问制度类问题没答案"），
合起来说会让人去查错方向。**"尚未配置"是正常但必须一眼看见的状态**，所以用徽标而不是灰字。

> 页签直接贴着内容面板，中间不放提示条：横幅会把页签与内容在视觉上割开，
> 而它想说的那件事（哪个用途还没配）就写在卡片头那一行上，本不用占两行位置。

四个要点：

1. **密钥不入库**：库里只存**环境变量名**（如 `DASHSCOPE_API_KEY`），密钥本身由部署方放进进程环境变量。
   备份与导出因此不含任何密钥。这条与对话模型**完全同一套口径**，没有第二条路径。
   变量名**可以留空**——那表示**这个端点不需要凭据**（自建/内网嵌入服务），界面显示"无需凭据"
   而不是红色的"未配置"：把合法的配置显示成缺配置，会让人去找一把根本不存在的密钥；
2. **型号从目录里选，不靠硬编码也不靠手填**（**对话与嵌入共用同一机制**）：供应商配好之后点
   「**添加模型**」，这家的型号（含用途、维度、窗口与参考单价）会列出来，**勾选即落库**——
   参数一起进去，落地就能用。三个提醒：
   ① 目录里那些型号名是**会过期的副本**（仓库里旧的 DeepSeek 型号名就与厂商当前文档对不上），
   所以目录外的型号要能加——走对话框里的次要出口「**目录里没有，手工填**」。这条路必须在，
   否则"换回本地"（自建端点）在界面上无路可走；
   ② **已在库里的型号不再列出来**——勾了也会被唯一约束拒，而拒在逐条提交的中途会留下半截结果；
   ③ 参数落地之后仍可**逐条调**（行内「参数」）：那是高阶操作，只给极个别情况
   （某条要单独调大超时、某个型号的价格与目录不同）；
   > **2026-10-02 推翻**：原口径是"填好密钥后向厂商拉取型号、勾选后**逐条指定用途与维度**"。
   > 那条把已知信息又推回去问了一遍，而且拉取根本给不全（多数厂商只给型号标识，单价与用途都拿不到）。
   > 定案与理由见 [ADR-030](../decisions/ADR-030-工作助手管理面.md) §12.3；

3. **不是每家都同时提供对话与嵌入**：预设里记着每家有没有嵌入端点（三态：已核实支持 / 已核实不支持 /
   未核实），界面会明说不同的话——不会让你在一个注定失败的端点上反复试。
   已知实测：DeepSeek / KIMI / 小米**都没有**嵌入端点（见下表）；
4. **两个用途各有一条"当前"，取消当前要指明用途**：界面上分成两个按钮（取消对话当前 / 取消嵌入当前）。
   不指明用途时服务端按对话处理，那会把对话那条清掉而嵌入那条照旧——**清错的那一个不会有任何报错**。

**选哪家做嵌入**（2026-10-02 逐家核官方文档）：

| 供应商 | 嵌入端点 | 能对齐现有 1024 维 | 备注 |
|---|---|---|---|
| 阿里百炼（千问） | ✅ | ✅ 支持指定维度，**默认就是 1024** | 有免费额度；批量上限每次 10 条（qwen3.7 系列 20 条） |
| 智谱（BigModel） | ✅ | ✅ 可指定 256/512/1024/2048 | `embedding-3` 默认 2048，要**显式给 1024** |
| OpenAI | ✅ | ✅ 指定 1024 即可 | 默认 1536（small）/ 3072（large） |
| DeepSeek / KIMI（Moonshot）/ 小米 MiMo | ❌ | — | 官方文档未见嵌入端点（小米的模型清单里只有文本生成与语音模型） |

**三家能对齐 1024，所以选它们不必重建现有集合**。DeepSeek 可继续做对话模型——它的模型列表接口
还返回窗口与最大输出，落库时省一次手工填。

> 认证头因厂商而异（例如小米用 `api-key` 头而不是 `Authorization: Bearer`），这属于供应商预设要带的
> 数据；若某家填好密钥后一直 401，先怀疑这一项。

**预设里已经带了这三家的嵌入型号**（百炼 `text-embedding-v4` / `v3`、智谱 `embedding-3` / `embedding-2`、
OpenAI `text-embedding-3-small` / `-large`，维度都按现有集合写成 1024），并带**单请求条数上限**
（百炼 10、智谱 64、OpenAI 取保守值 64、目录外的 CODE 与"自定义"取 10）。上限是**厂商事实**，
所以落在预设数据里：写死在客户端会让"换一家"变成改代码，抄错一家则会在第一次真入库时撞限流。

**客户端已接线**（打开 `EOS.API/Features/Assistant/ModelAccess/`）：`IAssistantEmbeddingResolver`
回答"当前该用哪个嵌入模型"（库里那条"嵌入当前"），`OpenAiCompatibleEmbeddingModel` 负责出网。四条口径：

- **`dimensions` 总是显式发**：智谱 `embedding-3` 默认 2048、OpenAI 默认 1536/3072——不指定就拿回一个
  与集合列宽不符的向量，而那时报出来的是"维度不符"，看不出是"没告诉它要几维"；
- **分批在客户端**（上限见上），并**逐批验条数与维度**：条数对不上会把向量与内容错位配对，故整批作废；
  返回顺序按 `index` 校正（厂商可能重排）；
- **认证头按预设样式发**；密钥为空就**不带认证头**（自建端点不需要凭据是合法配置）；
- **失败与对话共用一张映射表**，错误码是 `AI_MODEL_*` 家族（见 §七）；**不做自动重试**（§2 的"接受抖动"）。

**同一时刻全库只有一个嵌入模型**。理由很实际：若允许多个模型并存，"一个提问"要针对每个集合分别嵌入
（1 次出网变 N 次）。所以换嵌入模型 = **相关集合重建**。

## 四、维度与集合

集合行上记着 `EMBEDDING_MODEL` 与 `DIMENSION`（如 `bge-m3@1` / `1024`），切块表 `KB_CHUNK.EMBEDDING`
是 SQL Server 原生 `VECTOR(1024)` 列。规则三条：

- **维度必须与集合登记一致**：不一致时**拒绝写入**并给出可读原因，不静默降级（写坏向量比报错糟得多）。
  两道都验：调用方送来多少维（仓库层）与**厂商实际返回多少维**（客户端层，见 §三）——
  后一道能指出"是厂商没照 `dimensions` 返回"，而仓库层只会说"与集合不符"；
- **换模型 = 重建**：向量是派生索引，不是事实源。模型（含部署实现与归一化方式）一变，旧向量与新向量
  不在同一空间，检索质量会悄悄变差而不是报错；
- **换维度 = 改表**：列类型写死了维度，改它要连带重建整个集合。

> **一条诚实的现状（待批 D 收口）**：集合行上的**向量空间标签**（`EMBEDDING_MODEL`）目前**只插不改**
> （`EnsureCollectionAsync` 是 insert-only），所以"换了嵌入模型之后往同一个集合重灌"这条路径
> **不会被拦**——同维度下两套空间的向量会静默混进一个集合，表现是"检索结果忽好忽坏"。
> 在重建/改登记的动作落地之前，请把"换嵌入模型"当作**建新集合并重灌**来做。

> 只锁定"模型名"是不够的：同一个模型换成不同推理实现或量化档位，向量数值也可能不同。
> 集合行上的标签语义应是"**模型 + 实现 + 归一化约定**"。

## 五、入库怎么做

入库是**推入式**的：正文由请求体传入，服务端不会自动扫描某个目录。仓库文档由
`scripts/sync-guide-to-kb.ps1` 在仓库侧读盘、补标题前缀后经**同一个入库端点**推入。

```powershell
pwsh scripts/sync-guide-to-kb.ps1 -Plan      # 先看分类与"哪些篇目不入库"
pwsh scripts/sync-guide-to-kb.ps1            # 真灌（需 API 在线）
pwsh scripts/sync-guide-to-kb.ps1 -Verify    # 复核
```

三条前置：

1. **EOS.API 在线**（脚本先探 `/health/live`，**不代你启停服务**）；
2. 一个**有 2302 `CanSetup`** 的账号（入库是运维域动作，权限门锚在 2302，不在管理面另开入口）；
3. 嵌入模型已配好且密钥环境变量已生效。

**幂等**：按内容哈希跳过未变的文档；首跑入库、再跑全跳过是预期现象（两次输出都值得留档）。
**失败要如实报**：嵌入不可用时入库失败就是失败，不要把它写成"已打通"。

**哪些不进库**（既有约定，接线后不变）：机制类篇目（机制事实走 `describe_mechanism` 现算，写进文档再检索
就是第二真源）；字段字典类大文件（字段事实走内省工具）。

## 六、改成完全本地（在意语料外发时）

1. 在本机起一个提供 **OpenAI 兼容 `/v1/embeddings`** 的服务（常见两条路：TEI 的 Linux 二进制，
   可在 WSL2 里直接跑，无需 Docker；或 ONNX Runtime + 分词器自建一个极小的 HTTP 服务）；
2. 先确认它返回的**维度与集合登记一致**（不一致就重建集合）；
3. 在 3102 把嵌入模型的**供应商端点**改成自建地址（如 `http://127.0.0.1:8080/v1`），
   **密钥环境变量名留空**（空 = 该端点不需要密钥，请求不带 `Authorization`）；
4. 启停自己管（本系统不自启、不代管长驻进程）；模型权重 / tokenizer / venv **不入库**，
   把"从哪里取、放哪里、怎么换"写进你的部署记录。

**不需要**改代码、改表结构或改检索 SQL——协议与形状都没变。这是"云端优先"仍值得选的关键：
它把回本地的成本压到**改一行数据**。

## 七、排障

| 现象 | 原因 |
|---|---|
| 入库返回 `KB_EMBEDDING_NOT_CONFIGURED` | **没配**（不是服务坏了）：没有当前嵌入模型、模型行没填维度、或该供应商的密钥还没配。三种情况的话里分别指出"去哪儿配 / 补维度 / 哪个环境变量是空的" |
| 入库或检索返回 `AI_MODEL_UNAUTHORIZED` / `INSUFFICIENT_BALANCE` | 密钥被拒 / 余额不足——**厂商侧的问题**，与"未配置"分开报：混进未配置里，管理员会去 3102 反复确认模型配好了没有，而问题在密钥 |
| 返回 `AI_RATE_LIMITED` | 撞了厂商限流。单请求条数按各家上限分批（见 §三），但**并发与总速率没有做退避**（§2 的取舍）：等一会儿重跑 |
| 返回 `AI_MODEL_TIMEOUT` / `AI_MODEL_UNAVAILABLE` | 端点不可达 / 超时；检索按不可用**如实报**，不返回空结果假装"没有相关内容" |
| 入库报"嵌入维度不符：模型行上写的是 N 维，端点返回 M 维" | 厂商没按请求里的 `dimensions` 返回（自建端点还可能不认这个字段）：改模型行上的维度，或按它实际支持的维度重建集合 |
| 入库报"向量维度与集合不一致" | 送进仓库的向量与集合登记的维度不同（模型行的维度与集合登记不一致）——改维度要连带重建集合 |
| `KB_CHUNK` 为 0 | 从未成功入库过（或文档全是退役墓碑）；文档行数**从来不是**检索面的证据 |
| 检索召回很差 | 知识库里满是参数键、错误码、模块号，纯向量对专有标识符最弱；调大**相关性截断幅度**（`KB_SEARCH_RELEVANCE_MARGIN_PCT`，默认 15 个百分点）能把尾巴放回来 |
| 答案里混进无关片段 | 调小**相关性截断幅度**（0 = 只留最佳命中）。它只作用于进模型的路径，REST 检索端点不受影响 |
| 助手答"为什么要这么配"拿不到内容 | 规范 / 动因走知识通道，通道未接线就是答不了；机制问题才走 `describe_mechanism` |
