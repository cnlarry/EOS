## 1. 问题

**有一类需求今天在系统里没有落点**：用户打开一张单据，点一下按钮，要求**服务端就这张单据做一次动作**（重算、代入、生成下游单据……）。

同时满足两条才算（沿用需求清单的判据）：
1. **由用户在单据上主动触发**——不是保存/批核/删除这类固定事件顺带发生的；
2. **服务端要就当前这张单据做一次动作**——纯前端能力（排序、筛选、导出、列宽）不算。

**已确证 4 条需求**（需求清单 §2）：

| # | 模块 | 场景 | 旧系统证据 | 今天的处境 |
|---|---|---|---|---|
| 1 | 130101 库存盘点单 | **重算账面数量** | `ERP/INV/Check_Stock.aspx.cs` 的 `btnReCount`（只重算已有明细行，不生成行） | **无落点** |
| 2 | 130101 库存盘点单 | **按差异生成库存调整单（130107）** | 同页面 `btnAdjust` | **无落点**（ADR-014 的 P2-12 因此挂起） |
| 3 | 130101 库存盘点单 | **换库区重盘 / 同区重取明细** | 本轮 P2-11 讨论 | 只能手工清空明细再保存 |
| 4 | 库存策略 110310 | **哨兵行存量归位到指定库位** | 本轮 P2-14 | 被迫挂在"保存策略"这个动作上 |

**旧系统侧的证据强度**：188 个页面共 300 个 `btnXxx_Click` 处理器，去掉标准动作与纯前端排序后，服务端主动动作族为——代入/取数 24 页、重算/试算 27 页、生成子单/明细 13 页、生成调整单 1 页、批量导入/发卡 4 页。
**但是**：这不等于都要做。"代入取数"多数已被保存期效果与选择器回填覆盖，"批量发卡"已走 `/jobs/*` 批量作业页——立项只解决**确实没有落点**的那些。

**为什么不能塞进既有机制**（这就是要新机制的原因）：

| 既有能力 | 能覆盖 | 为什么不够 |
|---|---|---|
| `MODULES.FORM_BUTTONS`（**已随迁移 320 退役**） | 从固定按钮集里挑显示哪几个（`1=copy;2=approve;3=print`，前端 28 个标准动作） | **加不了新动作** |
| 效果目录事件（`SAVE`/`APPROVE_EFFECT`/`DEAPPROVE`/`ENDCASE`/`UNENDCASE`/`DELETE`） | 固定事件顺带做副作用 | 封闭集，且**没有"用户此刻想要"这个信息**——这正是 P2-12 不能挂批核的原因：挂上去就变成"每次批核都自动生成调整单" |
| 批量作业页 `/jobs/*` | 批处理作业（如员工批量发卡） | 独立页面作业，**没有单据上下文** |
| 选择器回填（`CHOOSE_RETURNVAL`） | 逐字段取数 | 不是"整单一次动作" |

## 2. 目标形态（v2 提案，供讨论）

**一句话**：操作是**代码注册的闭集**，按钮是**既有业务动作配置的一种形态**，入口是**一个受控端点**，元数据**随定义快照下发**。

```
                 ┌────────────────────────────────────────────┐
   配置面        │ MODULE_BUSINESS_ACTION  (EVENT_CODE='MANUAL')│  哪个模块显示哪些操作、顺序、标题
                 │  迁移 053 既有；SEQ/ENABLED/FAIL_MODE/CONDITION_STRUCT/PARAM_STRUCT 现成 │
                 └────────────────────────┬───────────────────┘
                                          │ 发布时校验：效果键必须已注册（复用既有 fail-closed 钩子）
                 ┌────────────────────────▼───────────────────┐
   定义面        │ WorkbenchDefinition（已有快照体系）         │  随快照发布（按钮元数据 + 版本号）
                 │  userActions: [{key,label,confirmTag,failMode,requiredPermission}] │
                 └────────────────────────┬───────────────────┘
                                          │ 前端只按元数据渲染（不硬编码操作）
                 ┌────────────────────────▼───────────────────┐
   入口          │ POST /document-workbench/{moduleId}/action/{actionKey} │
                 │  范围过滤 + 权限门 + 幂等 + 审计 + 独立事务 │
                 └────────────────────────┬───────────────────┘
                                          │
                 ┌────────────────────────▼───────────────────┐
   操作面        │ 操作处理器注册表（代码闭集，形状照 EffectRegistry）│  key → 处理器
                 │  处理器只调 WorkbenchCommandHandler / 既有服务处理器，不自己拼 SQL │
                 └────────────────────────────────────────────┘
```

**为什么操作必须是代码闭集**（而不是配置化脚本/公式）：配置化等于再造一套解析器与沙箱，与项目"高风险表达式（`VIRTUAL_EXP`/`DATASOURCE_SQL` 等）不直接进运行时"的原则冲突；且操作会改数据、生成单据，出错代价高于校验规则。**这不是类比——`EOS.API/Data/Effects/EffectRegistry.cs` 就是同一形状**：静态字典登记可执行的效果键，`IsImplemented()` 决定"这个键能不能跑"，40 个处理器在 `Effects/ServiceEffectHandlers/` 下。本机制照它的形状再建一个，注册与发布校验的做法一并沿用。

> **术语（v2 新增，§8 第 8 题已定）**：为避免与既有的"业务动作/效果"撞词，
> 本文把**用户主动触发**的这一类暂称**「单据操作」（user action）**，
> 与"事件发生顺带跑的效果动作"区分；界面用词建议也用"操作"。

## 3. 关键设计点（逐条给出提案与理由）

### 3.1 操作注册表（后端）

- 形状（§8 第 8 题已定）：`IDocumentUserAction { string Key; string Label; DocumentActionPermission Required; Task<DocumentActionResult> ExecuteAsync(DocumentActionContext, CancellationToken); }`
  ——`RequiresConfirm`/`FailMode` 不再由代码声明，改由配置行（`CONFIRM_TAG` / `FAIL_MODE`）提供，与效果引擎一致的"代码给能力、配置给开关"；
- 注册：集中一处（同 `EffectRegistry` 的做法），**未注册的操作键一律拒绝**；
- 上下文：`DocumentActionContext` 提供 `ModuleId`、单据主键、**当前库内单据状态**（服务端自取，不信前端）、连接/事务、当前用户与权限、数据范围谓词、幂等键。
- 【已决 3.1】操作允许**带参数**（2026-09-23 已定，§8 第 3 题），不再自己造参数表——
  走既有 `MODULE_BUSINESS_ACTION.PARAM_STRUCT`，前端按其中声明的项生成简单表单；
  v1"先用 1–2 个固定参数验证"的限制取消，因为保存期按物理列白名单校验参数的 `EffectParamPhysicalValidator` 已经是现成的。

### 3.2 按钮配置落点（v2：**复用 `MODULE_BUSINESS_ACTION`**，不再新建表）

> v1 提案的 `MODULE_DOCUMENT_ACTION` 降级为备选；理由是它的属性已经躺在既有表里了。

**既有资产**：`EOS.API/Data/Migrations/053_module_business_action.sql` 建的 `MODULE_BUSINESS_ACTION`
（单据业务动作配置表：模块 × 事件 × 顺序一行，今天服务于效果引擎），既有列取值：

```sql
-- 既有（节选）
MODULE_ID, EVENT_CODE NVARCHAR(30), SEQ INT, EFFECT_KEY NVARCHAR(50), EFFECT_NAME NVARCHAR(200),
ENABLED BIT DEFAULT(1), FAIL_MODE NVARCHAR(10) DEFAULT(N'BLOCK'),
CONDITION_STRUCT, PARAM_STRUCT, REVERSE_STRUCT, REMARK, SOURCE_REF, CREATE_PERSON, CREATE_DATE, ...
-- 既有约束
UQ(MODULE_ID, EVENT_CODE, SEQ)                        -- 同一事件内按 SEQ 排序，天然支持"多个按钮排顺序"
FK(MODULE_ID) REFERENCES MODULES(M_IDX) ON DELETE CASCADE
```

这张表**已经在快照体系内**：053 迁移注释写明它是模块的工作区配置，`2301` 保存后标 `WORKBENCH_MODULE_DIRTY`，
发布时随 `WORKBENCH_DEFINITION_SNAPSHOT.DEFINITION_JSON` 版本化——§3.7 想要的"随快照生效"是**现成**的，不用再发明一套。

**v2 提案**：给受控枚举 `EVENT_CODE` 增加一个值 **`MANUAL`**（语义：不由任何单据事件触发，由用户在单据上点击触发）：

| 想要的属性 | 落在哪 | 备注 |
|---|---|---|
| 哪个模块显示哪些操作、什么顺序 | `MODULE_ID` + `EVENT_CODE='MANUAL'` + `SEQ` | `UQ(MODULE_ID, EVENT_CODE, SEQ)` 已保证 |
| 处理器键 | `EFFECT_KEY` | 复用 §2 的代码闭集 |
| 失败语义 BLOCK/WARN | `FAIL_MODE`（默认 `BLOCK`） | §3.3 的"以后再加"可以直接取消 |
| 执行前置条件（如"已批核不许再点"） | `CONDITION_STRUCT` | 复用 `EffectConditionCompiler` |
| 参数 | `PARAM_STRUCT` | 复用 `EffectParamPhysicalValidator`（保存期按物理列白名单校验） |
| 是否启用 | `ENABLED` | 现成 |

**需要补的**（新表方案也躲不掉，量少）：

- 按钮标题 `LABEL`：既有 `EFFECT_NAME` 是整类效果的命名，不足以当按钮文案——加一列；
- 二次确认标记 `CONFIRM_TAG`：加一列。（两列都不足以动摇"复用"的结论）

**代价要写清**（不是免费的）：

- `EffectEventMapper` 与 `EffectPipeline.StageFor` 要认识新事件，但两者已经是查表/switch，加一格成本很低；
- `EffectEngineInvoker.DeclaresDetailGenerator`（判断某模块是否在保存期自带明细生成）一类逻辑要**显式跳过** `MANUAL` 行，
  否则"用户点的操作"会被当成"保存期自带的东西"参与空明细放行判定；
- 既有业务动作配置界面要能区分两类行，否则配置人员会困惑同一张表里混了两种触发源。

**为什么不复用 `FORM_BUTTONS`**（v1/v2 一致）：它的编码是 `1=copy;2=approve;3=print`——**固定集编号**，
后端解析与前端 `commandActions.tsx` 的 28 个动作注册表都建立在"数字→标准动作"的映射上，塞自定义键要么破坏既有解析、
要么再造一层映射；而且 `MenuAdminPage` 现在把它当自由文本输入框处理，再加编码会直接变成小型 DSL。

- 【已决 3.2】取 ⒞（复用 `MODULE_BUSINESS_ACTION` + `EVENT_CODE='MANUAL'`，2026-09-23 用户拍板）。⒜ 备选归档，⒝ 已否决，理由见上。

### 3.3 端点契约

```
POST /api/v1/document-workbench/{moduleId}/action/{actionKey}
Header: X-Idempotency-Key: <强制，与保存路径同款>
Body:   { "key": ["...", "..."],          // 单据主键（与读取/保存同格式）
          "params": { "relocateTo": "A-R1-B1" },  // 可选，按 PARAM_STRUCT 声明
          "confirm": false }              // CONFIRM_TAG=1 时先 false 探路、true 执行
Response 200: { "outcome": "refreshed" | "navigated" | "message",
                "message": "...", "targetModuleId": 130107, "targetKey": ["..."],
                "warnings": [{ "code": "...", "message": "..." }] }
```

- **失败语义**（v2 修订）：承接 §3.2 既有的 `FAIL_MODE`（默认 `BLOCK`）——**不再"以后再加"**，
  因为列已经在 `MODULE_BUSINESS_ACTION` 里。`BLOCK` = 返回 400 + 可读文案、事务整体回滚、不留半成品；
  `WARN` = 记入响应的 `warnings[]` 并继续执行。
- **二次确认**：`CONFIRM_TAG=1` 的操作，前端先提示确认；服务端在 `confirm=false` 时**只做预检并返回将发生什么**（不写库），
  `confirm=true` 才执行。既有先例：`DepotStockPolicyService.SaveAsync(..., confirmDestructive, relocateTo)`
  已经是"先算影响 → 返回 `RequiresConfirmation=true` 与说明文案 → 客户端带确认标志重发"这同一口径。
  ⚠ **探路不得消耗幂等键**（见 §3.5）——否则真正执行那次会被自己挡掉。
- 【已决 3.3】**操作不保存界面改动**（2026-09-23 已定，§8 第 4 题）——操作只作用于**已落库**的单据状态，
  前端在有待保存改动时禁用按钮并提示"请先保存"。理由补一句更强的说法：操作应当在**一致且可见的库内状态**上执行，
  而"界面脏了、用户心里期望的和库里不一样"这件事服务端永远看不见；同时混做保存会把两套校验/审计糊在一起，出问题无法归因。

### 3.4 权限与授权（v3：**按钮级授权，fail-closed 授权名单**）

> v1/v2 的"先不做动作级授权"被本轮推翻。用户口径（2026-09-23，见 §9）：
> **按钮配上并发布后，全场无人可点；管理员显式授权给谁，谁才能点。**

**授权模型**：沿用系统既有的**个人 / 组双通道赋权机制**，不新发明：

| 维度 | 既有范例 | 本机制照做的形态 |
|---|---|---|
| 个人 override | `SYSDD_REPORT`（`USER_ID + M_IDX + REPORT_ID` + 标记） | `SYSDD_BUTTON`（`USER_ID + M_IDX + BUTTON_KEY` + 允许位） |
| 组 override | `SYSDH_REPORT`（`G_IDX + M_IDX + REPORT_ID`，经 `SYSDG_USER` 落到人） | `SYSDH_BUTTON`（`G_IDX + M_IDX + BUTTON_KEY`） |
| 聚合规则 | 既有：个人权限覆盖组权限；多组布尔取 OR（`ModuleRightsRepository` / `RightsAggregator`） | 同款，不另写一版聚合 |

参照实现：`EOS.API/Data/ModuleRightsRepository.cs` 的 `GetReportAsync`（模块级开关 → override 行 → 聚合），
与迁移 `022_report_rights_override.sql` 里登记的语义变化。

**（唯一有意不同的一处）默认值相反**：

| 机制 | 无 override 行时 |
|---|---|
| 报表 override | 沿用模块 `REPORT_TAG`，预览/打印/导出**全开** |
| **本机制的按钮** | **拒绝（fail-closed）**——这正是用户定的规则 |

结构与查询可参考报表，**默认值必须按本表执行**；代码与界面都要显式写明，免得后来人按报表习惯理解成"不配就是全开"。

**配套四条（缺一条就会咬人）**：

1. **可见性**：未获授权的用户，前端**不渲染**该按钮；服务端仍对每一次请求独立鉴权（**API 是最终边界**，前端判断只是体验）。
2. **无豁免**：包括管理员在内的所有账户一视同仁——管理员想点，就给自己加授权；不想点就不加，或撤掉。（用户 2026-09-23 确认）
3. **配置侧要有一面镜子**：按钮配置页与发布校验清单里要显示"当前授权：N 个用户 / M 个组"，
   并在 N=M=0 时给显眼提示。既然"配了没人能用"是**正常状态**，它就不能是无声的——否则没人知道按钮为什么消失。
   建议发布校验新增检查项 `button_authorization_registered`，当前定为 **WARN（不拒发布）**。
4. **范围过滤照旧必做**（v2 结论，与本授权并列）：入口必须过 `WorkbenchScopeFilter.TryBuildRecordScopePredicate(...)`（fail-closed）。
   缺了它会出现这样的口子：用户对某张单据有按钮授权但数据范围受限，拿范围外的单据主键 POST 过来，服务端仍读到行并跑掉。
   **授权回答"能不能点这个按钮"，范围过滤回答"这张单是不是你的"，两者必须同时成立。**

> 说明：原"操作在 `Edit`/`Setup` 两档里挑一档"的做法随之作废——它是 v1/v2 在"不做按钮级授权"前提下的折中，
> 有了明示授权名单就不再需要。（保留此行以免后来人回头问为什么两种方案都出现过。）

### 3.5 幂等、并发、审计、事务

| 维度 | v2 提案 | 理由 |
|---|---|---|
| 技术幂等 | **强制** `X-Idempotency-Key`，复用 `WorkbenchIdempotency.TryClaimAsync` | 用户主动点的按钮最容易连点。注：`003_workbench_idempotency.sql` 的 `ACTION NVARCHAR(20)` 无 CHECK 约束，加一个 `"ACTION"` 类型不必改 Schema |
| **业务幂等**（v2 新增） | 会**生成下游单据**的操作必须自带业务口径：同一张单允许转出几次？（例如：重复执行只允许补未转出的差异） | 技术幂等只挡"同一个键的连点"，挡不住"换个键／隔天再点一次"。P1「按差异生成调整单」一旦缺这条，就是一个可无限次过账的口子（见 §4 P1 前置） |
| 探路与幂等 | `confirm=false` 的预检请求**不得 Claim** 幂等键 | 否则真正 `confirm=true` 那次会被自己挡掉。既有先例一致：`DepotStockPolicyService` 的探路不消耗任何键 |
| 并发 | 复用既有**乐观并发**口径（与保存路径一致：基于版本/字段快照判冲突，冲突返回 `CONCURRENT_MODIFIED`） | 不能让操作把别人刚改的数据覆盖掉 |
| 审计 | 一次操作**一条** `AUDIT_EVENT`（`ACTION` 记操作键，`RESULT` 记成败，`CORRELATION_ID` 串链路）；处理器内部若调用统一写路径（改单/建单），其自身的审计照旧 | 与既有审计口径同源，不另立一套 |
| 事务 | 操作在**自己的事务**里执行，失败整体回滚 | 与保存路径一致（`WorkbenchCommandHandler` 的 Create/Update/Delete 就是这个骨架） |

### 3.6 操作内部怎么改数据（重要约束）

**操作处理器不得直接拼 SQL 改业务表**，必须复用既有路径（v2 把"既有路径"落成具体名字）：

- 改本单 → 走 `WorkbenchCommandHandler`（它的构造里已经带齐 `WorkbenchAuditWriter` / `WorkbenchScopeFilter` /
  `WorkbenchIdempotency` / `EffectEngineInvoker` / `WorkbenchApprovalService`），于是校验、幂等、范围、审计与效果链自动一致；
- 生成下游单据 → 走同一套记录创建路径（`CreateRecordAsync`），这样下游单据的权限、校验、效果链一并生效；
- 需要过账 → 调用既有 `InventoryMoveHandler` 一类的服务处理器，不绕过。

**（v2 新增，写入强约束）回写明细一律逐行 MERGE，不得整表 UPDATE。**
重算类操作最容易做坏的地方就在这里：整表 UPDATE 会把用户已录入的值一并推平。
P0「重算账面数量」的验收断言就是这条的直接后果——**盘点数不变、明细行数与位置/批次不丢**。

【已决 3.6】操作必须可被审计还原（v2 结论，v7 落实）：操作造成的每一处数据变化都能追到这张单与这次操作，见操作注册表验收清单。

### 3.7 元数据下发与发布门禁

- 按钮元数据进 `WorkbenchDefinition`（随快照发布），前端**只按元数据渲染**；若按 §3.2 取 ⒞，
  这一步是**现成的**——`MODULE_BUSINESS_ACTION` 本来就在 `2301` 保存后标脏、随 `WORKBENCH_DEFINITION_SNAPSHOT.DEFINITION_JSON` 发布；
- 发布期新增校验：**操作键必须已在注册表中登记**（否则拒发布）——这是 ADR-012 的教训（快照指向已删族名会在运行期整批拒存，只有发布门禁能拦）。
  好消息是**钩子已经在那儿**：`WorkbenchDefinitionValidator.cs` 的 `effect_engine_keys_implemented` 检查项已经在逐个调
  `EffectRegistry.IsImplemented(effectKey)` 做 fail-closed，本机制是往同一份校验集合里加一项（事件为 `MANUAL` 的行的键也要是已登记的操作键）；
- 【已决 3.7】按钮元数据进“变化即需重发布”的范围（v2 结论，v7 落实，即改按钮顺序/标题要重发布），
  与字段清单同源同待遇，避免两套生效时机。

### 3.8 按钮位置与可见性（v3 新增；用户 2026-09-23 定）

**两个落点，且只在浏览态出现：**

| 落点 | 承载 | 位置 |
|---|---|---|
| **单据级** | 作用于整单的操作 | 浏览态单据工具条**尾部**（标准动作"帮助"之后），按 `SEQ` 排列 |
| **明细级** | 作用于子表的操作（重算明细、按差异生成单据……） | **子表标题栏右侧**——该位置在编辑态显示"新增一行/删除所选"，浏览态改为显示自定义按钮 |

- 位置**不受 `FORM_BUTTONS` 配置影响**（沿用既有约定：配置只决定动作有无，不决定位置）。
- 旧系统证据支持这个落点：`ERP/INV/Check_Stock.aspx:377-385` 的「重算帐面数量」「生成调整单」就在明细工具条那一排，
  与「新增单条 / 删除选定 / 保存明细 / 查询」并列；同页 `:76` 让它们的可用性与"编辑"按钮同步（不可编辑即禁用），
  等价于今天的"只在浏览态出现"。
- 前端落点：`FormEditorPage.tsx` 的明细工具条在浏览态目前渲染 `null`，本条就是把那个空位填上。
- **只有主表、没有子表的模块用单据级落点**，不因此不支持自定义按钮——否则 P2-14 这类（库存策略）场景无处可放。
- 未获授权 ⇒ 不渲染（§3.4 配套 1）。本项目前端规范（AGENTS.md「工具栏分两类」）已同步补入本条。

## 4. 落地阶段（提案；可执行拆分见 §11）

> 本节只保留 P0…P3 的验收方向；谁先做、谁后做、每段的出入口与验收以 §11 为准，不另起一套。

| 阶段 | 交付 | 验收 |
|---|---|---|
| **P0 机制 + 第一个真实用例** | 注册表 + 按钮配置（复用 `MODULE_BUSINESS_ACTION`） + 端点 + 定义下发 + 前端渲染；**用例：130101「重算账面数量」** | 真库用例：构造一张有明细的盘点单，改库存后点操作 ⇒ 账面数按最新库存重算、**盘点数不变**、明细行数与位置/批次不丢；重复点击幂等；无权限者 403；**范围外的单据 403/404**（§3.4 新验收项）；操作失败不改任何数据 |
| **P1 生成下游单据** | **用例：130101「按差异生成库存调整单 130107」**（顺带关闭 ADR-014 P2-12） | 逐行携带**位置与批次**生成 130107 并**过账**；差异为 0 的行不生成；生成结果可追溯（操作审计 + 下游单据来源字段）；解批/删除的补偿语义写清 |

**P0 的一条口径提醒**：`stocktake-scope-generate`（保存期效果）已经在做"按库区生成盘点明细"，且已显式保护"明细已存在就不动"。

否则半年后没人说得清"账面数什么时候该重算、会不会覆盖人填的数"。

**P1 的两条前置**（v2 新增，不解决不许开工）：

1. **来源追溯字段**：130107 上有没有"由哪张盘点单生成"的可落之列？没有就先走 DbUp 迁移加列，
   否则"生成结果可追溯"这条验收无法实现；

## 5. 明确不做（v2 边界）

- **不做配置化操作脚本**（公式/表达式/**存储过程名进配置**，2026-09-23 已拍板弃用，见 §10）——见 §2 理由；
- ~~不做操作级单独授权~~（已推翻：改为按钮级单独授权 fail-closed 名单，2026-09-23 已定，见 §3.4）；
- **不做"操作顺带保存"**（见 §3.3）；
- **不做列表批量操作**（选中多张单据执行一次）——批处理走既有 `/jobs/*` 范式；
- **（v2 新增）不为单个按钮承载长耗时作业**：同意"批量走 `/jobs/*`"，但要注意**单张单据**也可能很重
  （大范围盘点单重算、一次性生成并过账一批调整单）。在"同步端点 + 一个事务"里做这些会长时间占连接。
  v2 加一条判据：**预期超过 N 秒、或执行会生成多张单据的操作，不得占用本端点，必须走既有批量作业范式**
  （顺带一提，`EffectRegistry` 里 `job-enqueue` 今日状态是 `Reserved`，说明这条路本来就被预留过）；
- **不为旧系统 300 个按钮做机制**——只做"确实没有落点"的需求，逐条登记。

## 6. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 机制做出来没人用 | 只确证了 4 条需求，旧系统按钮多但多数已被覆盖 | P0 就绑一个真实用例（重算账面数），机制与用例一起验收 |
| 操作成为绕过校验的后门 | 手写 SQL 改表、跳过权限/审计 | §3.6 强制复用 `WorkbenchCommandHandler` + 操作审计可还原 + 发布门禁 |
| **（v2 新增）重复触发造成重复写库** | 技术幂等只挡同一个键的连点；P1 这类"生成下游单据并过账"的操作，"隔天、换个键、换个人再点一次"就会再生成一单 | §3.5 的业务幂等口径 + §4 P1 前置 2；必要时 `MANUAL` 行配置执行后自锁（如单据转已批核/已转单即拒） |
| **（v2 新增）范围的口子** | 有模块权限但数据范围受限的用户，拿范围外单据主键 POST 操作也能执行 | §3.4：入口必须以 `WorkbenchScopeFilter` fail-closed 过滤，缺一不可 |
| 与效果引擎职责重叠 | 都"在服务端做点事" | 边界写死：**效果引擎＝固定事件顺带发生；本机制＝用户此刻主动触发**。同一个操作若要"保存时也做"，那是两条配置，不共用入口 |
| **（v2 新增）两类行在同一张表里混着** | 复用表后，`MODULE_BUSINESS_ACTION` 同时装"事件发生触发"与"用户点击触发"两种行 | 配置界面与发布校验必须按 `EVENT_CODE` 明确区分；`MANUAL` 行禁用不适用的 `REVERSE_STRUCT` 等字段（§3.2 代价清单） |
| 按钮配置与权限/快照不同步 | 配了操作但没发布、或操作键被删 | 发布门禁校验操作键 + 快照落后检测（既有门禁） |

## 10. 已决：不允许按钮直接绑定一段 SQL / 存储过程（2026-09-23 弃用）

**用户顾虑（2026-09-23）**：闭集 handler 覆盖不住五花八门的按钮怎么办？旧系统的形态就是如此——
`INV/Check_Stock` 的 `btnReCount` 处理体只有 13 行，就是 `ExecStoredProcedure("P_INV_CHECK_RECALC_ACCOUNT")` 后重载页面。

**反方意见（Agent，未说服对方前留档）**：

1. **与既定清理方向相反**：迁移 `173_drop_legacy_hook_columns.sql` 已按用户指示物理删除 `MODULES.UPDATE_SP` 与
   `MODULES.AFTERSAVE_SP`（即"在库表字段里挂一段服务端执行物"的前身）。把它挪到"点击按钮"上触发，只是换个入口，性质未变。
2. **丢掉受控写路径的既有保障**：参数化、数据范围（`EXEC_TAG` / `DATA_FILTER`）、审计可还原、探路预览
   （任意 SQL 无法回答"将会发生什么"）、版本管理（落进库列后无 git / review / lint / diff）。
3. **不减少"写逻辑"的工作量**——只改变产出物放在哪（库列 vs git）。`INV/Check_Stock.btnAdjust` 那 97 行正好说明：
   省事的是"外壳"，难的部分（差异行怎么取舍、转出的单怎么回填、没有流程时怎么批核）一样要有人写清楚并验证。
4. **实证风险**：`CUS/Cancel.aspx.cs` 的按钮调的是 `P_COP_UPDATE_QUOTE_PARA`（**报价参数**过程）——客户取消页粘错了过程名，
   而"过程名只是一段配置字符串"时，这类错误无法被自动发现。

**清点给出的覆盖率回答**（见 `docs/plans/自定义按钮覆盖率清点.md` §2 / §5）：本机制真实射程只有 **8 个**单据级按钮，
且集中在两类——"按最新数据重算本单（或明细）字段"、"按本单生成另一张单"；覆盖不住的另有明码出口：
**参数化调节 → 新写一个 handler → `/jobs/*` → 逐条登记另议**。

**工程承诺（若取代码闭集）**：新增一个按钮 = **1 个 handler 文件 + 注册表 1 行 + 配置若干行**，框架与其它模块都不动。
这条守不住时，应回来重开本节的讨论，而不是悄悄放宽。

**若将来确需保留 SQL 通道**：建议集中在 `/jobs/*` 的受控作业上（单独权限、单独审计、单独白名单），
而不是分散到各模块的按钮配置里——风险宁愿集中在一个有门的房间，也不要撒到几百个模块的配置中。

### 11.1 WS-0 冻结记录（2026-09-23，v8）

四样冻结内容与实现落点（后续改契约必须先改本节并升小版本）：

1. **操作接口形状** —— `EOS.API/Data/DocumentActions/DocumentActionContracts.cs`：
   `IDocumentUserAction { Key; Label; ExecuteAsync(DocumentActionContext, CancellationToken) → DocumentActionResult }`；
   `RequiresConfirm` / `FailMode` **不在代码里声明**，由配置行（`CONFIRM_TAG` / `FAIL_MODE`）提供。
   上下文里给处理器的是**已按声明校验过的参数键值对**（`IReadOnlyDictionary<string,string?>`），不是原始 JSON——
   处理器不做第二次解析，校验只有一处（实施修正，2026-09-23）。
2. **端点契约** —— `POST /api/v1/document-workbench/{moduleId}/action/{actionKey}`；
   头 `X-Idempotency-Key` 强制（≤128 字符）；体 `{ key: string[], params?: object, confirm?: bool }`；
   200 → `{ outcome, message?, targetModuleId?, targetKey?, warnings[], requiresConfirmation }`，`outcome` 三态 `refreshed | navigated | message`。
   - **探路口径（写死，实施时不再各写一版）**：`CONFIRM_TAG=1` 且 `confirm=false` ⇒ 执行器**照常在同一事务内调用处理器，随后回滚该事务**，
     把处理器返回的 `message` 当作"将会发生什么"回传并置 `requiresConfirmation=true`；探路**不 Claim 幂等键**（回滚本身也不留痕），
     因此真正执行那次不会被自己挡掉。代价写明：处理器不得在事务外产生副作用（否则探路会留下痕迹）。
3. **定义下发形状** —— `definition.userActions[]`：`{ key, label, confirmTag, failMode, placement, params? }`；
   `placement ∈ master | detail`（`master` 贴浏览态工具条"帮助"之后，`detail` 占子表标题栏右侧）；
   `params` 下发该行 `PARAM_STRUCT` 的**字段声明**（前端只按声明生成简单表单，不硬编码操作）；
   **未获授权的操作不下发**（服务端仍独立鉴权）。
   `placement` 由**处理器声明**（可选接口 `IDocumentActionPlacement`，缺省 `master`）——"按钮作用在整单还是子表"
   是动作自身的属性，不再新增一列配置去和处理器对齐（实施修正，2026-09-23）。
4. **错误码** —— 只新增 3 个：`ACTION_NOT_FOUND`（键未登记／模块无启用中的操作行）、
   `ACTION_FORBIDDEN`（无按钮授权或单据超出数据范围）、`ACTION_FAILED`（`BLOCK` 失败，事务已回滚）；
   其余复用既有码（`IDEMPOTENCY_KEY_REQUIRED` / `INVALID_RECORD_KEY` / `RECORD_OUT_OF_SCOPE` /
   `DATA_FILTER_UNSUPPORTED` / `CONCURRENT_MODIFIED`）。

**MANUAL 行与效果链的边界（实施口径）**：`MODULE_BUSINESS_ACTION` 里 `EVENT_CODE='MANUAL'` 的行**不参与效果链**——
`EffectPlanLoader` 加载计划时跳过；`EffectParamPhysicalGate` 不对其做物理列校验（参数是操作入参声明，物理列由处理器自己的白名单负责）；
`EffectEngineInvoker.DeclaresDetailGenerator` 显式跳过；发布校验 `effect_engine_keys_implemented` 也跳过；
MANUAL 行的键由**操作注册表**（`DocumentActionCatalog`）单独把关（新增发布校验项 `document_action_keys_registered`，未登记即拒发布）。
MANUAL 行禁止携带公式行（`OPS`）与 `REVERSE_STRUCT`，`PARAM_STRUCT` 按操作参数声明的闭式结构校验。

### 11.3 实施补充口径（WS-1 / WS-2 落地时定，同属契约的一部分）

- **未获授权的点击也留痕**：拒绝发生在写事务之前，但会写一条**失败审计**（`RESULT=0`）——授权后来补上时，
  "当时为什么点不了"只剩这一条线索。按钮级授权不豁免任何人，管理员按同一名单判定。
- **授权键必须来自配置**：保存名单前校验 `(模块, 按钮键)` 确实是该模块启用中的 `MANUAL` 行，
  不能凭空授权一个未配置的键（与"发布校验只放行已登记键"同一道纪律）。
- **目标列宽度与既有权限表一致**：`SYSDD_BUTTON.USER_ID` / `SYSDH_BUTTON.G_IDX` 取 `NCHAR(10)`，
  与 `SYSDD_REPORT`/`SYSDH_REPORT` 同宽（写超长会 `截断`，属实测踩过的坑）。
- **个人名单"存在即接管"**：只要该用户在该模块有任一 `SYSDD_BUTTON` 行，就完全采用个人名单；
  其中 `ALLOW_TAG=0` 的行表达**显式拒绝**，组授权不再兜底。
- **授权在哪配**：沿用既有个人/组双通道的落点——用户权限设定 / 用户组管理的「按钮权限」页
  （`/admin/users/{id}/button-rights`、`/admin/groups/{id}/button-rights`）；
  2301 的按钮配置区只提供**授权镜子**（`GET /admin/module-business-config/{id}/action-authorization`），
  显示每个按钮当前的 N 用户 / M 组，`N=M=0` 时显式提示。
- **模块删除的连带清理**：菜单删除同时清 `SYSDD_BUTTON`/`SYSDH_BUTTON`，组删除清 `SYSDH_BUTTON`，
  避免模块/组没了名单还留在库里。
- **P0 用例的回写方式（对 §3.6 的落地解释）**：`recalc-account` 处理器**逐行 UPDATE**（每行一条参数化语句，
  只写 `ACCOUNT_QTY` 一列），不整表 UPDATE，也**不**经 `WorkbenchCommandHandler` 重写整单。
  理由有二：① 整单写路径是"明细整表删 + 按提交顺序重插"，那正是 P0 要防的"把用户录的盘点数推平"；
  ② 表单定义是按权限裁剪的投影，反向重建提交会把未投影的列写空——处理器看到的是库里的事实，不是用户的界面。
  同一文件里表名/列名取自代码常量并先过物理列白名单（fail-closed），用户输入只作参数值。
- **明细行的定位尺子**：重算按（库别, 料号, 库位, 批号）四列找库存行，与 `stocktake-scope-generate`
  写进明细的四列一致；比较两侧都做 `ISNULL`/`TRIM` 归一（空串与 NULL 在这几列语义相同，不归一会静默算成 0）。
  该四列在库存表上唯一，`LEFT JOIN` 不会放大明细行。
- **前置条件的前端表现（遗留）**：`CONDITION_STRUCT`（如"已批核才能点"）由服务端每次点击复核，
  探路也会跑一遍条件；前端目前**不禁用**按钮，而是把服务端的拒绝文案提示出来。
  "前端未批核禁用"需要把前置条件的当前取值随单据下发（按单据而非按定义算），留待 P3 按需做。
- **探路遇到"写在事务外"的操作：处理器自己预检**。框架默认的探路口径是"同事务执行后回滚"，
  但生成下游单据必须走统一创建路径（`CreateRecordAsync`，自带事务），回滚兜不住它。
  因此上下文集里多了 `Preview`（探路标志）：这类处理器在 `Preview=true` 时只算不写、返回将发生什么；
  其余处理器（写都在调用方事务里，如 P0 重算）继续由框架回滚兜底。
- **P1 的两阶段与补偿（写清，不是遗漏）**：`generate-adjustment` 先算差异 →（②）在自己的事务里
  创建并批核下游单据（过账）→（③）回到外层事务写回 `ADJUST_TYPE/ADJUST_NO` 与 `FINISHED_TAG=1`。
  ②③ 不在同一事务里是 ADR §3.6（必须走统一创建路径）与 §3.5（一次操作一个事务）的取舍结果；
  若 ③ 失败，动作返回失败并**带上已生成的调整单号**，由人工按号核对（审计同时留有记录）。
  调整单自身的解批/删除由它的生命周期规则管（库存由 `inventory-move` 的反向语义回退）；
  盘点单上的 `ADJUST_TYPE/ADJUST_NO` 不随解批自动清空——它记录的是"这张盘点单转过单"这个事实。
- **P1 追溯落点（回答 §4 的前置 1）**：不新增列——`INV_CHECK_STOCK_M.ADJUST_TYPE/ADJUST_NO`
  就是"由哪张盘点单转出了哪张调整单"的既有落点（旧系统即写这两列），再加 `FINISHED_TAG` 结案锁死。
  迁移 220 因此只做配置，不动表结构。
- **结案锁死的服务端守卫（补 §11 WS-5 记的缺口）**：`WorkbenchApprovalService.WorkflowCoreAsync`
  在解批前读 `FINISHED_TAG`，已结案直接拒绝（`FINISHED_RECORD_NOT_DEAPPROVABLE`）——
  此前只拦删除与编辑，直接调解批端点可绕过。
- **提交给下游的字段只取目标表单认得的列**：处理器按目标模块 `FORM`（按权限裁剪）过滤一遍再提交，
  否则创建路径会以"字段不在表单定义中"整单拒绝；被权限剔除的列（如无成本权限时的单价）不下发，
  与手工新建同一口径。
- **P2 的口径：把"哨兵存量归位"独立成一个操作，而不是删掉保存路径上那一处**：
  `relocate-sentinel`（110310）把某库别记在『未指定位置』上的存量整批改记到目标库位，

  差别只在谁触发）。本段做的是**独立**——想换个目标库位再归一次，不必先去改一遍策略配置；
  保存时的"升档即代搬"是已过审的口径，两边共用实现、不会分叉。
  "带着目标库位再存一次"那条路因此保留，按钮只是多了一条不用改配置的入口。
