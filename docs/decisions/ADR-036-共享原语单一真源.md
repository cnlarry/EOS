## 1. 问题

### 1.1 原语已经抽出来了，但旧调用点没有回接

仓库存量里已经有一批写得对的**共享原语**（例如 `Data/WorkbenchSql.cs` 的标识符白名单、物理列查询、主键定位与整行读取）。问题不在"没有原语"，而在**原语建成之前的就地实现没有跟着改过来**，于是同一语义长期存在两份，且会各自漂移。

同一查询真写成两份的实例（`WorkbenchSql` 的抽取意图明确，`WorkflowEngine` 未回接）：

### 1.3 分层越界：控制器写 SQL、控制器做权限决策

**A. 控制器内联 SQL**（实测 8 个控制器命中 `new SqlCommand` / 内联 SQL 字面量）：`ReportCenterController`(15 处)、`TableDataController`(9)、`BomExpandController`(6)、`AuditController`(4)、`ReportMetricController`(3)、`WorkflowController`(3)、`JobsController`(1)、`CarSummaryController`(1)。这些数据访问应落在 `Data/`，控制器不做业务决策与数据访问是本仓库既定的分层（见 `ARCHITECTURE.md`"分层"节）。

**B. 权限决策未收敛到声明的位置**：

```3:7:EOS.API/Security/IPermissionService.cs
/// EOS.API 内唯一模块权限判断入口：
/// 控制器与仓储不再直接调用 ModuleRightsRepository 做模块级权限决策；
/// 个人覆盖组、组布尔 OR、EXEC_TAG 最大值规则由底层聚合保持不变。
```

而实测**有 28 个控制器直接引用 `ModuleRightsRepository`**，经 `IPermissionService` 的只有 9 个（报表系、`AttachmentController`、`FormLayoutController`、`LayoutDesignerController`、`PrintController`、`WorkbenchDefinitionController`）。**声明与事实不一致**——这类不一致比重复本身更危险：它让下一位维护者按注释行事，却在注释所在的位置找不到真相。

**B. 常量三处各定义一份**：`ModuleRouteValidator.cs:55` 的 `WireName` 与 SQL 视图 `dbo.V_MODULE_NODE` 的取值；`Models/FormOpenModes.cs` 与 `EOS.Web/src/features/document-workbench/formOpenMode.ts` 与迁移 `319` 的 CHECK 约束；`Errors/ApiErrorCodes.cs` 与前端多处字面量。

**C. 建库种子与迁移两份**（既有约定，非缺陷，此处只记录代价）：

### 1.5 现有的防线只守住了"不变胖"

`scripts/check-data-layer-boundary.ps1` 已经把根因写在脚本头部，但它**明确不做**该做的判断：

```20:21:scripts/check-data-layer-boundary.ps1
    刻意不做的事：本脚本不判断"某个文件该不该是领域服务"（那需要语义理解，会误报）。
    它只守"根目录不再变胖"这一条**确定性**事实。
```

它的取舍是对的（语义判断会误报），代价是"同一件事再写一份"这一条**没有任何机械防线**：新增文件会被拦，新增 `if` 分支里的就地副本不会被拦。

## 2. 决策

**决定一（真源指定）**：为第 3 节列出的每项语义指定**唯一权威实现**，位置固定。此后**同一语义的第二种实现即视为缺陷**，评审阶段即拒，不以"临时"或"性能"为理由放行；确需第二实现时，先改本 ADR。

**决定二（回接优先）**：调用点改动的一律方向是"**旧调用点改指权威实现**"，不是"把权威实现改成旧写法"。回接按第 4 节分批，每批的靶子**逐处具名、结果可机械验证**。

**决定三（分层收口）**：`Controllers/` 不写数据访问 SQL、不做模块级权限决策；数据访问下沉 `Data/`，权限决策统一经 `IPermissionService`。新代码落位沿用 `check-data-layer-boundary.ps1` 的落位规则（领域能力 → `Features/<域>/`；共享原语 → `Data/` 子目录）。

**决定四（门禁升级，只加确定性断言）**：把可以机械判定的部分变成断言（第 5 节），**不写需要语义理解的启发式**——与 `check-data-layer-boundary.ps1` 已确立的取舍一致。语义相同但形式不同的两份 parser 之类，靠本 ADR 约束 + 评审，不靠脚本误报。

## 4. 回接批次与具名靶子

### 批 1（可机械验证，先做）

1. **标识符白名单回接并统一口径**：助手侧 4 处的正则删掉、改引 `WorkbenchSql.Identifier`；`DiagnosisRuleParser` 的松口径收紧到同一正则。完成后全仓只应剩一处 `^[A-Za-z_][A-Za-z0-9_]{0,127}$` 字面量。
2. **物理列查询回接**：先改两处**与权威同形**的（`WorkflowEngine.cs:616` 直接调用 `WorkbenchSql.GetPhysicalColumnsAsync`；`PrintService.cs:256` 的 EXISTS 改为原语判断），再逐个处置其余内联 EXISTS。
3. **主键与读行回接**：`PrintService.cs:276`/`:293` 改为 `WorkbenchSql.BuildKeyWhere` + `ReadRowsAsync`。
4. **分页钳制提升为共享原语**：`NormalizePage`/`NormalizePageSize` 移出 `ChooserRepository`（公共位置），7 处调用点改引；**阈值统一为一个值**（见 §8 待拍板 2）。
5. **控制器内联 SQL 下沉**：8 个控制器按域落到 `Data/` 下对应仓储；`ReportCenterController` 的目录/收藏 SQL 与权限口径同源的 `ModuleRightsRepository.GetModuleReportTagAsync` 合并为一处。

批 1 完成后，第 1、2、3 项应满足"全仓该语义的实现只剩一处"这一可 grep 验证的判据。

### 批 2（结构性，面广）

6. **权限门收敛**：28 个控制器改经 `IPermissionService`（或一个授权过滤器），让 `IPermissionService.cs:3-7` 的声明成为事实。典型靶子：`Controllers/AssistantAdminController.cs` 内 9 个私有 `CanBrowse`/`CanSetup` 包装、`Controllers/ReportController.cs` 内重复 7 次的"取 userId → 判 CanBrowse → Forbid"。
7. **异常 → 错误码收敛**：`Errors/ApiExceptionFilter.cs:20` 的 `switch` 表扩充业务异常类型，删除各控制器手工 `catch` + `ApiProblem.Create`（`AssistantAdminController` 48 处、`DocumentWorkbenchController` 25 处）。同时把 `ApiExceptionFilter` 里的字符串码（如 `"DATA_FILTER_UNSUPPORTED"`）并入 `ApiErrorCodes` 常量，消除两套错误码来源。
8. **`FIELDS` 读取原语**：为第 3 节第 4 项建一个共享实现（含成本/保密/禁止字段过滤的入参语义），三处调用点回接，各自的返回类型收敛。
9. **分页响应形状统一**（见 §8 待拍板 3）：`{ Rows, Total, Page, PageSize }` 与 `{ items, total }` 二选一，同批改前端。

### 批 3（另案评估，不在本 ADR 承诺范围内）

## 5. 门禁（只加确定性断言）

新增三条**具名棘轮**断言（模式沿用 `check-live-fixture-hygiene.ps1` / `check-retired-db-objects.ps1`：存量逐文件具名冻结、只减不增、新增即 FAIL、`-SelfTest` 做正反自检）：

| B | `EOS.API/Controllers/**/*.cs` 不得直接引用 `ModuleRightsRepository`（存量 28 个文件具名冻结） | 引用名匹配，零语义判断 |

## 6. 影响面

- **决策一/二**（回接）：只动内部调用点，**不改对外契约**（HTTP 路径、请求/响应字段不变）。批 1 的第 1–4 项属此列。
- **批 2 第 8 项（分页响应形状）**：**改对外契约**，需前端同批跟改；是否本轮做见 §8。
- **批 1 第 5 项（控制器内联 SQL 下沉）**：`ReportCenterController` 的 SQL 与 `ModuleRightsRepository` 权限口径同源，合并时须保持"防探测 404"行为不回归（助手侧与选择器侧的 404/403 边界见 `AGENTS.md`）。
- **`PrintService` 回接**（第 2、3 项）：影响 24 个单据版式的 PDF 取数，回归面是 `EOS.API.Tests/VerifyPrintLayouts.ps1` 与 `scripts/check-print-layouts.py`。
- **识别符收紧**（批 1 第 1 项）：助手侧若此前依赖松口径接受过某些键名，收紧后可能在运行期拒绝——需在真库用例上确认助手度量/诊断路径不回归。

## 7. 刻意不做

- **不合并 `EffectPipeline` 与 `DocumentActionExecutor`**：两者触发源不同（事件驱动 vs 用户点击），且已共用 `WorkbenchScopeFilter` / `WorkbenchIdempotency` / `WorkbenchAuditWriter`；合并前必须先证明语义等价，属另案（§4 批 3 第 11 项）。
- **不重构前端巨型组件**（`FormEditorPage.tsx` 等）：那是"一个组件承担多职责"的 UI 结构议题，与本文的"同一语义多份实现"不同类，另案。
- **不做 `Data/` 根目录整体重排**：沿用 `check-data-layer-boundary.ps1` 的"只减不增"，不为整理目录而搬文件。
- **不追改 350 个历史迁移与 `db/bootstrap` 双份机制**：DbUp 按**文件名**判重（改名会让已建库重跑），历史不追改；**新增**元数据仍须种子与迁移同改（既有约定，见 `docs/guide/05`）。
- **不清理已合规项**：如 `UnifiedChooser` 的 `loader` 分支（生产代码 0 处调用，规范"不得新增"已遵守）、`ReportPdfService`（类注释已写明保留作对拍基线，不得接回生产路径）。
- **不为"看着像重复"但职责不同的东西动手**：如 `MonthCloseSnapshotHandler` → `MonthCloseSnapshotService` 的转交（正确分层）。
