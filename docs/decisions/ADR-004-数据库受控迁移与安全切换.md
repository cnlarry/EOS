# ADR-004：数据库受控升级与认证系统一刀切（安全升级 cut-over）

- 状态：已接受
- 日期：2026-08-08
- 决策者：项目团队

## 背景

项目原先遵守"不修改数据库中的任何字段、任何一条数据"的原则。随着现代化重构深入，该原则过于苛刻：

- 菜单渲染依赖对 `MODULES.M_URL` 的运行时条件判断（见 ADR 相关实现 `ApplicationController.RouteFor`），
  正确的做法是把数据改对、把条件收敛为显式契约；
- 旧登录/密码系统安全性弱：`SYSDL.USER_PWD` 使用固定 key（`A9>^`）+ MD5 派生 + Base64/XOR 的
  可逆算法（`EOS.API/Security/LegacyPassword.cs` 为现代兼容实现），不符合现代安全要求；
- 若升级采用"双算法并行 + 登录时升级"的渐进迁移，会长期保留旧算法分支与兼容代码，形成技术债。

## 决策

### 1. 数据库可受控升级，维护一键升级脚本

推翻"不修改数据库"的绝对原则，改为**受控、可审计、可回滚**的升级方式：

- 维护 `docs/migrations/update.sql` 作为**唯一**一键升级脚本（2026-08-10 起不再在
  `docs/migrations/` 散落独立脚本；历史脚本已归档到 `docs/migrations/archive/`，所有迁移
  以幂等 SQL 追加进 `update.sql` 对应小节，可重复执行）；
- 优先只改**元数据**（`MODULES`、`FIELDS`、`SYSQL_*` 等配置表）与**认证/安全相关**内容；
  确为解决旧系统设计缺陷时允许扩充表/字段/修改结构，但必须评估旧系统消费链后纳入
  `update.sql`；
- **业务单据数据不修改**（除非另行明确授权）；
- 脚本要求：影响行备份（导出或 `SELECT INTO`）、幂等更新（按 `M_IDX` 等白名单定位）、
  末尾校验核对、附回滚说明；脚本中不得包含真实密码/密文等敏感数据。
- **开发期无新旧并行交付约束**：当前为开发环境，完成全部开发前不会交付给客户；升级是
  一次性干净的 cut-over，不为兼容旧系统保留任何分支或兼容代码。交付前执行 `update.sql`
  完成数据升级即可。`MODULES.M_URL` 等元数据可直接按白名单修正（如改为
  `Comm/view_frame.aspx` 把模块切换到现代工作台），无需顾虑旧系统菜单/页面被影响。
- **执行 `update.sql` 必须用 `sqlcmd ... -f 65001`（UTF-8 代码页）**：文件含中文注释，
  默认代码页读取会乱码导致批处理解析失败（如 `ALTER PROCEDURE` 静默不生效）。
  推荐命令：
  ```bash
  sqlcmd -S <server> -U <user> -P <pwd> -d EOS.ERP -b -f 65001 -i update.sql
  ```
  （`-b` 遇错返回非零；`-f 65001` 让 sqlcmd 按 UTF-8 读取输入文件；SSMS 打开执行亦可。）

### 2. 认证系统一刀切升级（cut-over），不保留旧算法兼容

- **不新增任何字段**：现代哈希直接写入现有 `SYSDL.USER_PWD`（`nvarchar(50)`，采用紧凑编码的
  带盐 PBKDF2，如"盐+摘要 Base64"，长度控制在 50 字符内）；
- **所有用户密码置空**（`USER_PWD = ''`）：空密码在 API 层即被拒绝（现有校验拒绝空输入），
  空哈希也无法通过校验，因此用户无法自行登录，只能主动联系管理员分配密码；
- `admin` 账号在升级脚本中按新算法预置初始密码 `admin`（脚本内固定、文档注明，
  上线后管理员应尽快更换）；
- 管理员通过用户管理能力（列用户/设置密码，随安全升级一并建设）逐个为用户分配密码；
- 代码侧删除 `LegacyPassword.cs` 与旧算法验证分支，只保留现代哈希验证
  （带盐 PBKDF2 或 Argon2）；
- 旧系统（ASP.NET Web Forms）登录将因 cut-over 失效——这是**预期后果**，不是缺陷；
  在交接文档与 README 中明确记录，避免后续误判为回归。

## 选择理由

- **无长期兼容负担**：不保留双算法、不做"登录时升级"的渐进迁移，代码只有一条现代验证路径；
- **操作量可控**：企业 ERP 用户规模小（当前 `SYSDL` 约 33 个账号），管理员逐个改密可在短时间内完成；
- **不留安全空窗**：空密码天然拒登（API 拒绝空输入 + 空哈希校验失败），无需停用开关；
  admin 初始密码 `admin` 为已知默认值，上线后应立即更换；
- **与"菜单渲染条件收敛"一致**：把运行时魔法条件替换为数据修正 + 显式契约，方向一致、可审计。

## 后果与影响

- 升级窗口期需要管理员完成逐个分配密码；`admin` 初始密码 `admin` 上线后必须立即更换；
- 旧系统登录、旧密码算法相关代码与文档（`ERP_REFACTOR_HANDOFF.md` §8、README"兼容旧账号体系、
  密码算法"）需同步更新，明确"已改为受控升级 + 现代哈希，旧算法不再兼容"；
- 用户管理能力（列用户/设密码/启用）属于本次安全升级范围，随实施一并建设；
- 登录加固（速率限制/锁定、审计、CSRF、HTTPS/Cookie 策略、Data Protection 密钥持久化）
  作为安全升级的配套项评估实施。

## 不做的事

- 不实现旧密码算法的长期兼容或渐进迁移；
- 不在升级脚本中写入任何真实密码、密文或哈希数据；
- 不修改业务单据数据；不因本次决策放开对业务数据的无约束修改。
