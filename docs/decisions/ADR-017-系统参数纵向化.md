# ADR-017：系统参数纵向化（单行宽表 → 一张参数表）

- 状态：**已实施**（2026-09-20 用户拍板：按方案 B 纵向化、**就地改造 `SYSSS` 不新建表**、`HR_SETUP`/`HRM_SETUP` 一并收、`/settings/system` 页面按分组选项卡呈现。同日完成实施与验证：迁移 `208`/`209` 已落库、真库单测 1503/1503 通过、常态门禁全绿；实施中对 §3/§4/§5/§6 的修订见 §10，冲突时以 §10 为准。**待办**：真机（页面/接口/开关行为）需重启 `EOS.API` 后补验；备份表收口与 SSDT 快照重导见 §6 步骤 8）
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-012（效果引擎与校验目录——开关门控 `switch.gates` 的数据来源）、ADR-013（单据生命周期列规约——生命周期列口径）、ADR-014（库存策略——"有作用域的参数另立领域表"的先例）、`docs/plans/批次效期立项方案.md`（本 ADR 的第一个受益者：`EXPIRY_MODE` 进领域表、近效期阈值进本表）

## 1. 背景与问题

系统参数今天住在**三张"单行宽表"**里（实测 2026-09-20）：

| 表 | 模块 | 页面 | 行数 | 字段数 |
|---|---|---|---|---|
| `SYSSS` | 110111 系统参数设置 | `/settings/system` | 1 | **38** |
| `HR_SETUP` | 180213 考勤数据设置 | `/settings/hr-setup` | 1 | **45** |
| `HRM_SETUP` | 180662 考勤数据设置 | `/settings/hrm-setup` | 0 | **44** |

三张表共用同一套机制（`SettingsRepository` 读取字段元数据 + 唯一一行、按列名白名单更新），页面由 `FIELDS` 元数据渲染。

**这条路已经走不动了**，五个问题按严重度排列：

1. **加一个参数 = 一次 DDL 迁移 + 一条 `FIELDS` 登记**。参数只会越来越多（本次排期里"批次效期"就要加 2 个），迁移文件会持续堆积。
2. **参数本身没有定义**：只有列名 + 一个短描述，没有类型、默认值、**改完是即时生效还是要重启**、归属。38 个还能靠记忆，80 个就没人敢改。
3. **改参数不留痕**：保存路径（`SettingsRepository`）连审计依赖都没有——谁在什么时候关掉了某个开关，事后查不到，而 `SYSSS` 的开关直接决定单据行不行。
4. **表达不了作用域**：所有参数都是"全库唯一值"。一旦出现"按库别/按公司"的参数就只能另建表——`DEPOT_STOCK_POLICY`（库存策略）就是这么被逼出来的。宽表会持续逼出第二张、第三张表。
5. **同一套机制复制三份**（SYSSS / HR_SETUP / HRM_SETUP），页面、仓储、权限映射各写一遍。

## 2. 决策

### 2.1 把 `SYSSS` **就地**改造成纵向参数表，不新建 `SYS_PARAM`

**理由**：新建表意味着两套机制并存（旧列有人读、新表有人写），"这个开关在哪"变成必须记忆的事；本项目处于开发期、无真实用户（AGENTS「兼容性决断边界」），没有理由为迁移期做双轨。就地改造后**只有一张参数表、一套读写路径**。

**表名保留 `SYSSS`**，不重命名：51 处引用（C# / 迁移 / 配置 JSON）与运行期配置里的 `{"scope":"SYSSS","key":"…"}` 都按这个名字走；重命名只带来改动面，不带来收益。名字此后按"系统参数表"理解，语义以本 ADR 为准。

### 2.2 `HR_SETUP` / `HRM_SETUP` 一并收进同一张表

三张表都是"单行 + 全局唯一值"，形状完全同构 ⇒ 收敛成一张表，用 **`OWNER_MODULE`** 区分归属（110111 / 180213 / 180662）。这同时消掉了"同一套机制复制三份"。

**代价（实测，必须一并处理）**：`HR_SETUP` 被库内三个对象引用——

| 对象 | 类型 | 引用方式 |
|---|---|---|
| `f_get_rest_days` | 函数 | 未限定 schema（`referenced_schema_name` 为 NULL） |
| `f_get_work_days` | 函数 | 同上 |
| `P_HRM_WAGE_CALC` | 存储过程 | 同上；**这是库内最后一条遗留过程**（工资引擎，运行期按名调用） |

⇒ 本 ADR 必须包含**改写这三个对象**，与表改造同一批交付（见 §6）。

> 2026-09-20 实施修订（详见 §10）：① 两表列名几乎完全重叠（44 个同名），主键必须改为
> **`(OWNER_MODULE, PARAM_KEY)`**；② 两个函数实测**零调用方**（库内、C#、脚本、测试均无引用），
> 按用户拍板改为 **DROP 退役**，只有 `P_HRM_WAGE_CALC` 按本 ADR 改写。

### 2.3 一条参数一行：定义与取值同行

不做"定义表 + 取值表"两分。所有参数都是全局单值，取值无需多行；分行只会让页面多一次 join。

### 2.4 值以文本存储 + 类型列解释

`PARAM_VALUE nvarchar(4000)` + `VALUE_TYPE`（`bit`/`int`/`decimal`/`string`）。理由：参数表若按类型分列（VALUE_BIT/VALUE_INT/…）等于把宽表换个方向重建；文本 + 类型是参数表的常规做法，转换收口在一个服务里，类型不符即拒绝保存（fail-closed）。

## 3. 目标结构（DDL）

```sql
-- 就地改造：先把 38 列的值搬到临时表，再重建
CREATE TABLE dbo.SYSSS (
    PARAM_KEY      NVARCHAR(64)  NOT NULL,   -- 主键：沿用现有列名（SEND_TAG / CLIENT_DAYS / PRO_MRP …）
    PARAM_VALUE    NVARCHAR(4000) NULL,      -- 取值（文本存储，按 VALUE_TYPE 解释）
    VALUE_TYPE     NVARCHAR(16)  NOT NULL,   -- bit / int / decimal / string
    DEFAULT_VALUE  NVARCHAR(4000) NULL,      -- 代码默认值：NULL 取值一律解释为它
    GROUP_CODE     NVARCHAR(32)  NOT NULL,   -- 页面分组（选项卡）
    GROUP_LABEL    NVARCHAR(50)  NOT NULL,   -- 分组显示名（冗余，便于分组本身也在数据里）
    DESC_TEXT      NVARCHAR(300) NOT NULL,   -- 这个参数做什么（迁移时取自 FIELDS.F_DESC）
    EFFECT_SCOPE   NVARCHAR(16)  NOT NULL,   -- immediate / restart
    OWNER_MODULE   INT           NOT NULL,   -- 归属模块（权限与页面过滤）：110111 / 180213 / 180662
    SEQ_NO         INT           NOT NULL,   -- 组内排序
    OPTIONS        NVARCHAR(500) NULL,       -- 枚举型（如 "0=否;1=是"）时给下拉；空 = 按类型渲染控件
    REMARK         NVARCHAR(1000) NULL,
    CREATE_PERSON  NCHAR(10)     NOT NULL CONSTRAINT DF_SYSSS_CREATE_PERSON DEFAULT (N''),
    CREATE_DATE    DATETIME      NOT NULL CONSTRAINT DF_SYSSS_CREATE_DATE DEFAULT (GETDATE()),
    LAST_UPDATE_BY NCHAR(10)     NULL,
    LAST_UPDATE_DATE DATETIME    NULL,
    CONSTRAINT PK_SYSSS PRIMARY KEY CLUSTERED (OWNER_MODULE, PARAM_KEY),  -- 见 §10 R1
    CONSTRAINT CK_SYSSS_VALUE_TYPE CHECK (VALUE_TYPE IN (N'bit', N'int', N'decimal', N'string')),
    CONSTRAINT CK_SYSSS_EFFECT_SCOPE CHECK (EFFECT_SCOPE IN (N'immediate', N'restart'))
);
```

**生命周期列口径**遵循 ADR-013：建立组 `NOT NULL + DEFAULT`、经办人/日期列保持可空。
**全大写命名**（AGENTS 数据库对象命名规范）。
`GROUP_LABEL` 冗余是刻意的：分组名也是数据，新增分组不必改代码。

## 4. 迁移映射（键名不变，是第一原则）

- **参数键 = 原列名**（`SEND_TAG`、`CLIENT_DAYS`、`MACHINE_START`…）。这样：
  - 运行期配置里的 `{"scope":"SYSSS","key":"FITOUT_TAG"}`、`{"table":"SYSSS","clientDaysField":"CLIENT_DAYS"}` **一个字都不用改**；
  - 效果引擎的开关语义（键不存在 = 0，fail-closed）原样保留。
- **`VALUE_TYPE`**：由原列类型映射（`bit`→bit、`int`/`smallint`→int、`decimal`/`float`→decimal、其余→string）。
- **`DEFAULT_VALUE`**：优先取 `FIELDS.DFT_VALUE`；无则取 `sys.default_constraints.definition` 中的常量；再无则为 NULL（NULL 表示"代码内默认"）。
- **`DESC_TEXT`**：取 `FIELDS.F_DESC`（现有 38+45+44 条已基本齐全），空的必须人工补齐（门禁强制）。
- **`GROUP_CODE` / `SEQ_NO`**：迁移脚本内置分组表，初版分组建议：

| GROUP_CODE | 分组名 | 覆盖（初版） |
|---|---|---|
| `PARTNER` | 往来与账期 | `SUPPLIER_DAYS`/`CLIENT_DAYS`/`PRODUCT_DAYS` |
| `MRP` | MRP 与可用量 | `MRP_DAYS`/`MRP_WEEKS`/`MRP_MONTHS`/`PRO_MRP` |
| `DOC_LINK` | 单据联动开关 | `FITOUT_*`/`SEND_*`/`RETURN_*`/`PRODUCE_*`/`COP_RETURN_DEPOT_TAG`/`PUR_*` |
| `QTY_RULE` | 数量阈值 | `QTY_LINE1..3`/`QTY_PS_WIDTH` |
| `UI` | 界面与操作 | `LOGIN_F12`/`QUICK_SEARCH_ALL` |
| `PRODUCT` | 料件与版次 | `PRO_EDITION_TAG` 等 |
| `ATT_CARD` | 考勤卡号解析（HR） | `MACHINE_START/LENGTH`、`TYPE_*`、`CARD_*`、`YEAR_*`、`MONTH_*`、`DAY_*`、`HOUR_*`、`MINUTE_*`、`SECOND_*` |
| `ATT_CALENDAR` | 考勤日历（HR） | `SAT_REST_DAY`/`SUN_REST_DAY`/`SAT_ABSENT`/`SUN_ABSENT`/`HOLIDAY_ABSENT` |
| ~~`MISC`~~ | ~~其它~~ | 实施后为空：唯一候选 `REMARK` 经复核认定**不是参数**（§10 R10），该分组已取消 |

分组是可执行数据，实施时可按实际观感微调（只改 seed 数据，不改代码）。

## 9. 明确不做

- **不新建 `SYS_PARAM`**：就地改造 `SYSSS`，避免两套机制并存（用户 2026-09-20 拍板）。
- **不重命名 `SYSSS`**：51 处引用 + 配置 token，重命名只有成本没有收益。
- **不做作用域/继承**：需要"按库别/按公司"的参数一律另立领域表（`DEPOT_STOCK_POLICY` 是先例），本表只装**全库唯一值**的参数。
- **不做参数版本历史表**：留痕走既有 `AUDIT_EVENT`/`AUDIT_FIELD_CHANGE`，不为此单建历史表。
- **不做参数热更新**：`EFFECT_SCOPE=restart` 的参数只标注、不实现自动重载（进程内缓存由重启刷新）。

## 10. 实施修订（2026-09-20 开工时实测得出，用户逐项拍板）

> 以下四条是对 §3 / §4 / §6 的**修订**，冲突时以本节为准。

### R1｜主键改为 `(OWNER_MODULE, PARAM_KEY)`

实测：`HR_SETUP` 与 `HRM_SETUP` 的列名**几乎完全重叠**——`MACHINE_START`…`WAGE_ADD` 共 44 个同名，
仅 `DIMISSION_NO_WAGE` 是 `HR_SETUP` 独有。§3 的单列主键 `PARAM_KEY` 在两表合并后**必然主键冲突**，
物理上不可实现。

**决定**：主键 `(OWNER_MODULE, PARAM_KEY)`，`PARAM_KEY` 仍严格等于原列名（"键名不改"第一原则不变），
所有读取一律按 `OWNER_MODULE` 限定；并加 `IX_SYSSS_GROUP (OWNER_MODULE, GROUP_CODE, SEQ_NO)` 供页面分组读取。

### R2｜只迁业务参数：36 / 34 / 33（合计 103 行）

> 实施当时的数字是 37/35/34（合计 106）；真机复核又剔除了行级备注列 `REMARK`，见 §10 R10。

**决定**：逐列做减法——业务参数一个不漏地迁，**21 个技术/生命周期列一律丢弃**（在新表里它们就是行级元数据）：

| 表 | 丢弃列 |
|---|---|
| `SYSSS`（1） | `CREATE_DATE` |
| `HR_SETUP`（10） | `CREATE_PERSON` `CREATE_DATE` `LAST_UPDATE_BY` `LAST_UPDATE_DATE` `CONFIRM_PERSON` `CONFIRM_DATE` `CONFIRM_TAG` `CI` `OWNER` `OWNER_G` |
| `HRM_SETUP`（10） | 同上 10 个 |

迁移脚本把 21 列**显式枚举**（不吃排除法），断言：
`业务参数数 + 显式技术列数 = 备份表列数（38/45/44）`，且备份表每一列**恰好**落在"已迁"或"显式丢弃"之一。

### R3｜`f_get_rest_days` / `f_get_work_days` 改为 DROP 退役

实测：两函数在**库内无对象引用**（`sys.sql_expression_dependencies` 无指向）、**C# / 脚本 / 测试中零提及**
（C# 侧 `AttendanceCalcService` 已自行实现考勤日历判断）。按 AGENTS「兼容性决断边界」，
本项目无真实用户、无存量，为两个死对象保留改写成本不合理。

**决定**：`DROP FUNCTION dbo.f_get_rest_days, dbo.f_get_work_days`，不迁不改。
连带影响：`EOS.Database` SSDT 快照少两个函数、OSS 建库种子少两个函数（均由用户重导/重跑脚本生成）。

> **订正（2026-09-27）**：该快照已退役（见本 ADR §6 步骤 8 的订正）⇒"少两个函数"的记账失去载体；OSS 建库种子仍由 `scripts/export-oss-seed.ps1` 从本机库重出，不受影响。
本 ADR §6 步骤 5 中"两函数改写 + 跑调用方用例"的要求**作废**；`P_HRM_WAGE_CALC` 仍按原计划改写。

### R4｜迁移拆两条：208 建表搬数 + 209 库内对象

**决定**：`208_system_parameter_verticalization.sql`（备份 → 参数定义 → 建表 → 搬值 → 断言）、
`209_system_param_db_objects.sql`（新增 `dbo.f_sys_param` → 改写 `P_HRM_WAGE_CALC` → DROP 两个函数 → 断言）、
`210_system_param_group_order.sql`（§10 R9：分组显示顺序）。
DbUp 以 `WithTransactionPerScript()` 顺序执行，脚本之间无运行窗口；失败回滚粒度清晰。

### R5｜SQL 侧取值口径收口到一个函数

为避免"NULL ⇒ `DEFAULT_VALUE`"这条口径在三个库内对象里各写一遍，新增：

```sql
CREATE FUNCTION dbo.f_sys_param (@owner_module int, @param_key nvarchar(64)) RETURNS nvarchar(4000)
-- 返回 ISNULL(PARAM_VALUE, DEFAULT_VALUE)；返回 NULL = 参数不存在或取值与默认值皆空（fail-closed）
```

`P_HRM_WAGE_CALC` 与 C# 侧 `SystemParameterService` 使用**同一条规则**，口径只解释一次。

### R6｜`scope` token 与 HTTP 路径段并存（不冲突，但需明确）

- **配置与代码内部**的 `scope` 沿用**表名**：`"scope":"SYSSS"`、`{"table":"SYSSS",…}`、`{"table":"HR_SETUP","flagField":…}`
  ——这是"运行期配置零改动"的前提，**一个字不改**；
- **HTTP 路径段**按 §5#6 用 `system` / `hr-setup` / `hrm-setup`（菜单 URL 不变），由控制器映射到 `OWNER_MODULE`。

### R7｜备份表放 `bak` schema，不落在 `dbo`

取样备份是回滚用的**数据快照副本**，不是业务结构：它的列是 `SELECT * INTO` 的产物，没有默认约束与
生命周期列口径。留在 `dbo` 会让 `check-lifecycle-columns.ps1` 这类按 `s.name = N'dbo'` 全表巡检的
常态门禁把备份表判成"结构漂移"。

**决定**：迁移 `208` 建 `bak` schema（不存在才建）并把三张备份表放进去；收口时连同 schema 一起清理。

### R8｜"参数键存在性"的落点（对 §5#2/#3 的实现说明）

§5#2/#3 要求把开关的"列白名单校验"改成"参数键存在性校验（查参数键集合，缓存）"。实施后的实际落点：

| 层 | 做法 |
|---|---|
| 运行期 | 开关一律按**参数键**取值（键作为 SQL 参数，绝不拼进 SQL）；**缺键读 0**，即"未登记开关 = 关闭"，fail-closed |
| 配置校验（保存 / 发布，两个入口同一份判断） | `EffectPhysicalColumns.LoadWithParametersAsync` 把参数键以 `<scope>.<KEY>` 折进**同一份白名单**，于是 `("SYSSS", gateFlag)` 这类既有校验代码**一行不改**就改为校验参数键 |
| 常态门禁 | `scripts/check-system-params.ps1` 全量扫描校验规则 / 效果动作 / 已发布快照 / 源码里点名的参数键，逐键按归属模块核对 |

**偏离说明**：`EffectConditionCompiler.IsSysssKey` 这个编译期委托在部分调用点仍传 `_ => true`
（那些点没有现成的键集合，且为它们注入依赖会波及大量单测）。因此"未知开关"在运行期表现为
**安全地读 0（开关关闭）**而不是抛配置错；真正的拦截由上面"配置校验 + 常态门禁"两层承担。
若日后要让编译期也 fail-closed，把键集合接进 `EffectPipeline` / `EffectFormulaExecutor` 的构造即可。

### R9｜分组显示顺序也是数据：新增 `GROUP_SEQ`（迁移 `210`）

真机验证暴露的问题：§3/§4 只登记了 `GROUP_CODE`（分组键）与 `SEQ_NO`（**组内**排序），
**组间顺序**无处表达，页面只能按 `GROUP_CODE` 字母序排——实测呈现为
「单据联动开关 → 其它 → MRP 与可用量 → 往来与账期 → …」，与业务分区顺序无关。

**决定**：`ALTER TABLE dbo.SYSSS ADD GROUP_SEQ INT NOT NULL DEFAULT (900)`，读侧按
`(GROUP_SEQ, SEQ_NO, PARAM_KEY)` 呈现，顺序 seed 对齐既有阅读顺序：
`往来与账期 → MRP 与可用量 → 料件与版次 → 单据联动开关 → 采购流程开关 → 生产流程开关 →
数量阈值 → 界面与查询 → 其它`（考勤侧：`考勤卡号解析 → 考勤日历 → 考勤其他 → 工资字段映射 → 其它`）。
未登记的新分组默认排在已知分组之后（900），由 `check-system-params.ps1` 的分组顺序断言提醒补齐。

这保持了 §3"分组名也是数据"的取向：新增/重排分组只改数据，不改代码。

### R10｜`REMARK` 不是参数：备注参数行退役（迁移 `211`）

§4 的分组建议表把"无法归类者"放进 `MISC`，实施时把三张表的 `REMARK` 列一并搬成了参数行。
**真机复核判定这是错的**：

- `SYSSS.REMARK` / `HR_SETUP.REMARK` / `HRM_SETUP.REMARK` 是旧"单行宽表"给**那一行**留的自由文本备注
  （现值分别是 `'0'`、一段卡号位置草稿、`NULL`），**全系统没有任何读取方**——`FIELDS` 只登记了描述"备注"；
- 纵向化后新表每行自带 `REMARK` 列，承担的是"**这个参数**的说明"，旧的行级备注没有去处；
- 于是它成了页面上唯一一个"改了也没有作用"的项，属于把"宽表的列"误当"参数"的机械迁移。

**决定**：迁移 `211_retire_remark_parameter.sql` 删除这三行，`MISC`（其它）分组随之消失；
参数条数 **103**（110111=36 / 180213=34 / 180662=33）。

**判据（后续沿用）**：参数 = **有读取方按类型解释其取值**的值。纯说明/备注文本不进参数表——
它的去处是表结构里的 `DESC_TEXT`/`REMARK` 列，或配置项自身的备注字段。
