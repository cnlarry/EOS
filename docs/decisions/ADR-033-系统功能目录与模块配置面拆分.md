# ADR-033：系统功能目录与模块配置面的职责拆分

- 状态：**已拍板（未实施）**——十项决定见第 13 节；其中两项在讨论中被推翻（校验规则不再独立成模块、2304/2305/2306 不改挂），理由分别见第 5、12 节
- 日期：2026-10-10
- 相关：ADR-019（模块管理拆分）、ADR-021（配置面白箱化）、ADR-022（模块级表单版式）、ADR-023（对拍证据按语义等价判定）、ADR-032（模块分组独立成表与配置面）、迁移 012/026 的快照口径、迁移 284（模块重编号先例）、迁移 340/341/342、`LESSONS.md` L27 / L72 / L87

> 本文只回答"为什么这样切"与"为什么不那样切"，不回答"怎么改代码"。实施细节（迁移编号、文件清单）在落地时按第 10 节展开。

## 1. 问题

模块 **2301「模块管理」**是一个页面办五件事的形态：左侧是整棵模块树，右侧表单有**六个页签**——基础 / 主表 / 子表 / 行为动作 / 校验规则 / 自定义按钮（`EOS.Web/src/features/menu-admin/MenuAdminPage.tsx:49-57`，三个行为页签共用一份草稿与容器，`:60`、`:1348`）。四个具体问题：

1. **一页两职责**：前三个页签在"**定义**一个模块"（`MODULES` 的字段），后三个在"**配置**某个模块的行为"（`MODULE_BUSINESS_ACTION` / `MODULE_VALIDATION_RULE` / `SYSDD_BUTTON`）。它们的目标对象、受众、改动频率都不同，却挤在同一个表单里，且后三个页签的保存必须与前三个**同一事务**提交（`ModuleBusinessConfigRepository.SaveScopedAsync`）。
2. **上手成本**：使用者要理解"我现在编辑的是这个模块自己，还是这个模块的行为"，还要理解"保存了但不发布等于没生效"。当前页面用形态（`NODE_KIND`）与权限（`canModuleConfig`）层层裁剪页签可见性，裁剪逻辑本身已经是一处需要维护的复杂度。
3. **权限粒度太粗**：三个配置面共用一个开关——2301 上的 `MODULE_CONFIG_TAG`（ADR-019 引入）。想授权"只能配自定义按钮"的人做不到，只能要么全给、要么全不给。
4. **导航语义混乱**：`23 系统管理` 下平铺着 2301 模块管理、2304 单据性质设定、2305 用户组管理、2306 用户权限设定、2309 数据维护、2311 数据表维护、2315 模块分组（实测同级 7 项，`SORT_IDX` 1/2/10/15/40/50/60）。**配置工具**（模块管理、模块分组）与**基础资料**（单据性质设定）混在一层。

## 2. 决策

引入一个纯目录节点承载"系统功能"这一族配置面，把原 2301 的内容与三个待拆的配置面各自独立成模块：

| 编号 | 名称 | 形态（`NODE_KIND`） | `M_URL` | 主表 | 由谁而来 |
|---|---|---|---|---|---|
| **2301** | 系统功能 | **DIRECTORY**（纯节点） | 空 | 空 | 2301 原地改判（内容搬走） |
| **230101** | 模块管理 | CUSTOMPAGE | `/admin/menus` | `MODULES` | 原 2301 的模块行（重编号） |
| **230102** | 模块分组 | CUSTOMPAGE | `/admin/module-groups` | `MODULE_GROUPS` | 原 2315（重编号） |
| **230103** | 自定义按钮 | CUSTOMPAGE（新定制页） | `/admin/module-buttons` | 空 | 新模块，内容来自 230101 的「自定义按钮」页签 |
| **230104** | 行为动作 + 校验规则 | CUSTOMPAGE（新定制页） | `/admin/module-actions` | 空 | 新模块，页面内两个页签，分别来自 230101 的「行为动作」「校验规则」页签 |

两个边界（都经过一轮推翻，理由见第 5、12 节）：

- **只拆两个模块，不是三个**：校验规则与行为动作同住 230104（页内两个页签）——它们在同一条执行链、同一个事务、同一个发布门上，拆开只会让"拦什么 + 做什么"分居两地；
- **`2304 单据性质设定` / `2305 用户组管理` / `2306 用户权限设定` 不改挂**，留在 23 段——把它们收进 2301 会让访问这三个页面多一层点击，整齐换不来这个代价。

六条附带决定：

- **230101 的页签收敛为三个**：基础 / 主表 / 子表。三个行为页签全部迁出——**230101 只定义"模块是什么"，不定义"模块怎么动"**；且**不留只读视图**——留一份只读等于把"改完要回哪一面"再讲一遍，发布结果与版本历史仍在 230101 可见（它们是模块级事实）。
- **权限随配置面走**：230101 / 230102 / 230103 / 230104 各自持有 `SYSDH` / `SYSDD` 行，2301 作为目录保留镜像行。见第 8 节。
- **发布对用户隐式（方案 B）**：三个行为配置面的按钮就叫「保存」，服务端保存成功后自动发布一次；校验不通过时提示"已保存，但未生效 + 逐条原因"。拆开的是**界面与权限**，**快照与发布门一个都不拆**。见第 7.3 节。
- **新增模块的编号分配改为"父编号 + 两位序号"**：见第 4 节末。
- **不做"待发布清单"页面**：先把拆分落地，理由见第 12 节。
- **不复用 2308**（已退役的「工作任务记录」），编号一律不回收。

## 3. 为什么 2301 要变成纯目录节点

不是"为了好看"，而是三个具体机制问题：

- **目录是唯一没有隐藏语义的容器**。2301 现在是 CUSTOMPAGE（`M_URL=/admin/menus` + `MASTER_TABLE=MODULES`），它同时是"一个可打开的页面"和"一个承载配置面的节点"。改判为 DIRECTORY 后，它的全部含义只剩"展开"——判定规则在 `dbo.V_MODULE_NODE`（迁移 340：`M_URL` 空且无主表 = 目录；`M_URL` 空**且有**主表 = 默认统一工作台），代码侧同一判据在 `ModuleRouteValidator.ResolveKind`。
- **同层已经有两条纯目录先例**：`2309 数据维护`（`SYSDH` 0 行 / `SYSDD` 2 行）与 `2311 数据表维护`（`SYSDH` 1 行 / `SYSDD` 2 行）。目录节点在库里是**一等公民**，不是新构造。
- **实测 2301 改判的代价极小**：它的形态外配置本来就全空——`SORT_FIELDS` / `NOT_BACK_FIELDS_M` / `NOT_BACK_FIELDS` / `DETAIL_NO_FIELDS` / `FORM_OPEN_MODE` / `FILTER` 全为空串，`AUTO_APPROVE` / `IF_COPY` / `ERROR_NO_SAVE` / `DETAIL_NO_SAVE` / `EFFECT_ENGINE_TAG` / `SEARCH_1` / `SEARCH_2` 全为 0，`MODULE_FORM_TAB` 0 行、脏标记 0 行。改判只需清 `M_URL` 与 `MASTER_TABLE`，不需要像迁移 340/342 那样另写一段"形态外配置回落"。

一条**必须记住的可见性事实**：目录节点的显示**不依赖它自己的权限行**——`NavigationRepository.GetForUserAsync` 的 `Included` 集合会把"有权限子模块的祖先"自动带出（`EOS.API/Data/NavigationRepository.cs:39-45`）。但先例（2309/2311）都是显式配行，我们照做：**别把"看得见目录"这件事交给推导**，否则一旦祖先推导口径出问题（`LESSONS.md` L72 记的就是父节点编号出问题导致菜单静默消失），表现是"整族菜单消失"。

## 4. 为什么用 230101 / 230102 / 230103 / 230104 这种编号

这套编号是"**父编号 + 两位序号**"，本库已有大量同类先例，且**同一段内**就有：

| 先例 | 目录 | 子模块 |
|---|---|---|
| 23 段 | `2309 数据维护`（DIRECTORY） | `230901 产品可用库存重计`、`230902 基本资料导入` |
| 11 段 | `1101 系统参数`（DIRECTORY） | `110101`…`110111` |
| 18 段 | `180101 人事基本设定`（DIRECTORY） | `18010101`…`18010119`（再下一层，8 位） |

即：本库的编号**并非**"段内平铺"，前缀式编号是既有惯例（6 位以上编号现存约 150 个）。这与迁移 284 把 `110112` 重编号为 `2313` 不矛盾——284 修的是一个**孤号**（既不在 11 段语义里、也不在 23 段语义里），不是否定前缀式编号。

选这套编号的三个理由：

1. **承接语义写在编号上**：230101 一眼看出"这是原 2301 的模块管理"，2301xx 一族一眼看出"都属于系统功能"。若改选 2316/2317，这层线索只能靠 `M_P_IDX` 查。
2. **给这一族留足位置**：五个配置面 + 可能的后续（待发布清单等），"父编号 + 两位"留出 100 个位置，不必在 23xx 段里与其他分支抢号。
3. **纪律不变**：编号一旦退役不复用（guide/05 §三；迁移 341 头注释）；`230101`…`230104` 现均空闲（实测 230100–230199 无占用；`230105` 同样空闲，本次不使用）。

**编号分配器的同批改造（已拍板）**：新增模块的编号分配器是 `MenuAdminRepository.NextModuleIdAsync = MAX(M_IDX)+1`（`:898-902`）。当前 `MAX(M_IDX)=18010119`，也就是说**今天新增一个模块会得到 18010120**——看着像 18 段某模块的子节点；本次引入 230101…230104 后，它会给出 230105，同样"看着像 2301 的子节点"。同批改为"**父编号 + 两位序号**"：

- 有父节点：取 `父编号 × 100 + 下一个空序号`（父 2301 下依次 230101…230106…，新增取 230106）；
- 无父节点（根级）：按"段内当前最大 + 1"取号（维持 `NextModuleIdAsync` 今天的语义，但限定在同段内，不再被别的段的大号带跑）。

这条改造是**编号可读性**的修复，不改"编号是排序键、不是身份"这条纪律：排序永远由 `SORT_IDX` 决定（`NextSiblingSortAsync` 步进 10），编号只是身份与归属线索。

## 5. 拆分的判据：什么该独立成模块

"减轻上手难度"不能靠感觉切。用四问筛：

| 候选 | 受众（谁配） | 改动时机 | 能否单独授权 | 发布语义 | 结论 |
|---|---|---|---|---|---|
| 自定义按钮 | 单据操作维护者 | 随业务迭代，较频繁 | 应当可以 | 进快照，需发布 | **独立（230103）** |
| 行为动作 | 流程/效果配置者 | 少动，动则影响面大 | 应当可以 | 进快照，需发布 | **独立（230104）** |
| 校验规则 | 与行为动作是同一批人（见下） | 随模块行为一起改 | 四问会说"可以分"，但**没有证据**表明存在"只该配校验、不该配动作"的人 | 进快照，需发布 | **并入 230104**（页内两个页签） |
| 发布 | 与配置同一批人 | 每次配置后 | —— | 它**就是**生效动作 | **不独立** |

判据用法：**四问里任意两问答"是"就值得独立**；但四问只判"值不值得分权"，还要过**第二关：分出去之后，剩下的那部分会不会被劈成"两处编辑 + 一处例外"**。

校验规则就卡在第二关：

- 它与行为动作在**同一条链**上——同一事件的 `ValidateStageAsync`（拦）→ `TryRunAsync`（做），同一个数据库事务，"先拦后做"；**同一个发布门**（同一份快照、同一批校验码一起过）；**同一次保存**（`SaveScopedAsync` 一次删两张表）；
- 我原先给它填的受众"数据质量/合规维护者"**是假设，不是证据**。实测反驳：那 16 个"只配校验、没有动作"的模块（货币资料、员工基本资料、证件资料、保险投保、排班……）**分闸本来就是关的，而校验根本不受分闸约束**——所谓"只配校验的那批人"并不作为独立群体存在；
- 拆出去的真实收益只落在 16 个模块（13%），代价（写路径按域切分、多一套模块号/权限行/路由三处登记/一个页面）落在**全部**模块上；而 97 个有校验的模块里 **81 个（83.5%）同时有动作**，拆开只会让"拦什么 + 做什么"分居两地；
- **可逆性不对等**：编号不回收——拆出 230105 再合回去，就永久多一个退役号、还得清它那套权限行；而"先合、需要再切"只加一个新号。**同样能达成目标时，选修起来更便宜的那条。**

**故校验规则并入 230104**，页内保留「行为动作」「校验规则」两个页签（与今天 230101 里的两个页签一一对应）。**230105 编号不使用。**

"发布"不独立：它不是一类配置，而是**所有配置的生效动作**；把它拆成独立页面会让"改完要发布"变成"改完要去另一个地方发布"。若将来真需要"待发布清单"，应是独立模块（见第 13 节），理由要写成"跨模块批量发布"。

## 6. 关键机制障碍：两类配置共用一张表与一个"整模块替换"写路径

这是本次拆分最大的技术风险，**必须先解决再拆页**。

事实（`EOS.API/Data/ModuleBusinessConfigRepository.cs`）：

- 自定义按钮与行为动作**同表**：`MODULE_BUSINESS_ACTION`，按钮是 `EVENT_CODE='MANUAL'` 的行（判据在 `BusinessActionCatalog.ManualEvent`，`:24`、`IsManualEvent` `:157-158`）。
- 写路径是**整模块全删全插**：`SaveScopedAsync` 先 `DELETE FROM dbo.MODULE_VALIDATION_RULE WHERE M_IDX=@ModuleId`（`:267-273`）、再 `DELETE FROM dbo.MODULE_BUSINESS_ACTION WHERE M_IDX=@ModuleId`（`:274-280`），然后按请求体插入。
- 请求体是一个整体：`SaveModuleBusinessConfigRequest{ Actions, ValidationRules }`，页面只提交它打开的那部分。

**如果直接把两个页面指向同一个 `PUT /admin/module-business-config/{moduleId}`，230103 保存按钮会删光该模块的行为动作与校验规则，反之亦然——静默数据损失，而且两边都会标脏、都会写审计"保存成功"。** 这类缺陷不会被单测发现（各自测各自的域），只会在真库上表现为"另一面的配置莫名消失"。

方案（落地时必须做到）：

- 写路径引入**显式作用域**：`scope = MANUAL | ACTIONS | ALL`——**只需切两刀**：只有两个配置面各自保存（230103 存 `MANUAL` 按钮；230104 存非 `MANUAL` 的动作 + 全部校验规则，页内两个页签仍是一次提交），所以不必按"三类"切。删除语句按作用域加谓词（`= 'MANUAL'` / `<> 'MANUAL'`），请求体只带该域的行；`ALL` 保留今天的全量替换语义（供同事务合成保存使用）。（原先按三面切四刀——这是"少拆一处"顺带省下的一笔机制成本。）
- **显式优于推导**：不要让服务端"看 payload 里出现了哪个域就替换哪个域"——空列表与"未提交此域"在 JSON 上是同一件事，推导必然出错。
- `SaveScopedAsync` 的"模块 + 配置同事务"路径要保留（供发布前的合成保存使用），作用域作为参数透传。
- 新增回归用例：**保存按钮域后，该模块非 `MANUAL` 行数与校验规则行数都不变**（反向同理）。这是本次拆分唯一"防静默损失"的用例，必须进真库用例集。

## 7. 生效时机：为什么不能"保存即生效"，以及怎么让用户看不见"发布"

### 7.1 事实：三类配置为什么进快照

运行期用的是**已发布的整份定义**，不是这三张表：

- `WorkbenchDefinitionBuilder` 的运行期只有两个分支——有当前快照（`IS_CURRENT=1`）→ 用快照做不可变基线；无快照 → 实时重建（`:81-89`）。且**已不再按脏标记回退**（`:78-80` 注释：回退会让快照内的效果引擎配置段丢失，使引擎静默退出）。
- 实时重建路径 `BuildFromMetadataAsync`（`:224-246`）**根本不装配** `BusinessActions` / `ValidationRules` / `EffectEngine`——今天只有发布校验器与 2301 草稿预演才填这三段。
- 消费方是**单据写入路径**，不只是"点按钮"：
  - 保存新增/修改/删除时跑 SAVE / DELETE 阶段的校验与动作（`WorkbenchCommandHandler.cs:327,333,582,587,706`）；
  - 批核/解批/结案时跑对应阶段（`WorkbenchApprovalService.cs:328,369,623,761`）；
  - 用户点击类按钮走 `DocumentActionExecutor`（`DocumentActionExecutor.cs:73`）；
  - 统一表单按钮渲染读 `BuildUserActionsAsync`（`DocumentWorkbenchRepository.cs:71-82`）。

### 7.2 为什么不建议真的改成实时读

四条机制层面的理由，每条都有代码依据：

1. **写路径是"DELETE + 重插"，读侧是 NOLOCK 脏读**（`SaveScopedAsync:267-290`；读侧 `MODULE_BUSINESS_ACTION WITH (NOLOCK)` `:88`、`MODULE_VALIDATION_RULE WITH (NOLOCK)` `:158`）。今天这个撕裂窗口不可见，因为运行期不读这两张表。改成实时读 = 把"行已删、未插回"的中间态暴露到**每张单据的保存与批核路径**上。
2. **失败是 fail-open，不是报错**。`EffectPlanLoader` 解析不到规则 → 该阶段 `applicable=false` → 校验静默通过（`EffectEngineInvoker.cs:196-199`）；动作读成空 → `Ran=false` 静默不接管（`:138-141`）。也就是说撕裂窗口的后果是"**校验全部失效、脏数据照常落库**"。这比抛异常危险得多——后者会被拦住，前者不会。
3. **要新增一条实时装配分支**：现在实时重建根本不填这三段，改实时读不是改开关，而是新增装配 + 让解析器在每次请求上实时打库解析（`EffectPlanLoader.Load` 每次调用都重新解析，这会变成每张单据的固定开销）。
4. **发布门上的四道校验只在发布期 fail-closed**：`lifecycle_columns`（有批核能力的主表必须有 `CONFIRM_TAG`）、`document_action_keys_registered`（用户点击类动作键必须在注册表）、`effect_engine_keys_implemented`（引擎开启时动作键必须有实现）、`effect_reverse_kind_supported`（反向 kind 必须在支持闭集内），以及专门补"经迁移或直写落库、保存路径没跑过"的 `effect_params_physical`（`WorkbenchDefinitionValidator.cs:250-404`）。撤销发布 = 把这些闸从"发布时拦下"移到"运行期真单据上炸"。

还会失去：整份定义同一代的**一致性视图**（快照把字段/动作/校验一起冻结）、验收证据的**新鲜度锚点**（`module-{id}-v{n}`，ADR-012 #109 / ADR-023）、**静默落后的可观测性**（`/workbench-definitions/staleness`、`check-snapshot-staleness.ps1`、`PUBLISH` 审计）、**回滚到旧版本**的能力。

对照：列表分组能"保存即生效"，是因为它三条前提全占——不进快照（`GroupExpressions` 带 `[JsonIgnore]`，组装定义时实时读）、没有"整模块 DELETE + 重插"的撕裂窗口、也没有发布门（guide/12 §收口 341）。**这三类配置一条都不占，所以不能照搬。**

### 7.3 决定：把"发布"做成用户看不见的一步（方案 B）

用户要的是"改完就生效"这个**观感**，而这个观感不必靠拆掉快照来换。**采用方案 B**；方案 A 作为被否方案一并留在这里：

- **方案 A（用户已选，显式）**：各配置面自带"保存并发布"按钮——一次点击里先保存再发布，复用同一发布端点（`POST /admin/module-business-config/{moduleId}/publish`）与同一权限、同一审计（保存与发布各留一条审计，便于追溯）。用户仍看到"发布"这个词与逐条校验结果。
- **方案 B（建议）**：按钮就叫「保存」，服务端在保存成功后**自动走一次发布**。机制完全没变（同一校验门、同一快照写入、同一条 `IS_CURRENT` 切换、同一条审计），变的只是"用户要不要理解发布这一层"。校验不通过时，语义是"**已保存，但未生效**" + 逐条原因（发布响应里的 `checks[]` 已经带明细，前端已有 `publishResult` 展示位）。
  - 代价：保存的延迟从"写两张表"变成"写两张表 + 全量发布校验（含物理列/效果键/生命周期列打库核对）+ 写快照"。配置是低频操作，这个代价可接受。
  - 代价：一次提交产生两条审计（保存 + 发布）。不建议合并成一条——"改了"与"生效了"是两件事，分开留痕才能回答"这条配置是什么时候开始生效的"。
  - 不适用：230101 的模块定义保存（走 `/admin/menus` 那个表单）**不要**自动发布。它改的是主/副表这类结构性字段，发布校验要打库核对物理列，且结构性改动常常需要一次改多项后统一发布。**自动发布只给三个行为配置面。**
- 两方案都**不改变**：发布仍是同一动作、同一端点、同一权限、同一审计；`/staleness`、脏标记、版本历史、回滚全部保留。

## 8. 权限：从"一个 2301 管全部"改为"各配置面自己持权限"

现状：三个配置面的门都落在 2301 上——`MenuAdminController` 与 `ModuleBusinessConfigController` 各自持有常量 `MenuAdminModuleId = 2301`，且后者额外要求 `CanModuleConfig`（= 2301 权限行上的 `MODULE_CONFIG_TAG`）。实测 2301 的权限行：`SYSDH` 1 行（`G_IDX=1`）、`SYSDD` 2 行（`admin` / `larry`），`MODULE_CONFIG_TAG` 仅 `admin` 为 1。

决定：

- 各配置面按**自己的模块号**判权：230101（模块定义读写）、230102（分组）、230103（按钮）、230104（动作 + 校验规则）。
- 迁移把 2301 的 `SYSDH` / `SYSDD` 行**逐主体镜像**到上述五个模块，并对新 2301 目录也镜像一份（先例：迁移 341 把 2301 的权限行镜像到 2315，并带"新编号主体 ⊇ 参照模块主体"的收口断言）。**镜像必须逐列复制**，不要照抄旧迁移的列清单——`SYSDH`/`SYSDD` 的列随 ADR 演进（`CI` 列已下线、`FORM_ADJUST_TAG` 已被 `MODULE_CONFIG_TAG` 取代，guide/05 §三有这条警告）。
- **顺带把权限粒度做细**：`MODULE_CONFIG_TAG` 从"2301 上一个总开关"变成"每个配置面一个"。这是拆分的**收益**而非代价：可以授权"能配按钮、不能改动作"。
- 两处仍需指定落点的常量：`ChooserRepository.MenuAdminModuleId`（`module-admin.*` 选择器数据源的门）与 `Features/Assistant/Config/ConfigWriteService.cs` 的同名常量（助手配置写门）。它们描述的是"**模块定义**配置面"的能力，应改指 **230101**。
- 刻意不动：`SYSDD_BUTTON` / `SYSDH_BUTTON`（按钮的**运行期**授权，按 `USER_ID`/`G_IDX` + `M_IDX` + `BUTTON_KEY` 落行，fail-closed）。配置面权限 ≠ 按钮可用权限，两张表不混。

## 11. 验证（落地时的口径）

- 迁移干跑：整库回滚、探针前后一致；重编号后按 14 个（表.列）逐一断言旧编号归零。
- 级联基线用例 `MenuAdminModuleIdCascadeLiveTests` 保持有效（它守的是 `ChangeModuleIdAsync` 的移植实现，与迁移里重写的语句互为对照）。
- 真库回归：**保存按钮域后动作域与校验域的行数都不变**；三面各自标脏、各自留审计。
- 页面级：230103 选目标模块 → 增删改按钮 → 保存并发布 → 工作台按钮出现/消失；230104 同构（动作与校验两个页签各改一次，互不覆盖）；230101 不再显示那三个页签。
- 权限回归：只有 230103 权限的人进不去 230104（这是拆分的收益，要有用例钉住）。
- 门禁：`check-module-node-kind`、`check-di-registrations`、`check-snapshot-staleness`、`check-lifecycle-columns`、手册新鲜度。

## 12. 刻意不做

- **不拆发布**：见第 5 节。
- **不把这三类配置改成运行期实时读**：见第 7 节（四条机制理由）。
- **不动按钮的运行期授权表**：`SYSDD_BUTTON` / `SYSDH_BUTTON` 语义不变。
- **不抽"配置面通用框架"**：三个新配置面形状相似（选目标模块 → 列表 → 弹窗），但先各写一次；等第三处真出现重复再抽，避免过早抽象。
- **不做"待发布清单"页面**：三个面都喂同一份快照后，"哪些模块改了没发布"确实会成为一个问题，但先把拆分落地、看真实操作路径；真需要时独立成模块，理由要写成"跨模块批量发布"，而不是顺手塞进某一面。
- **不把 2304 / 2305 / 2306 改挂 2301**：它们留在 23 段。**排列整齐不值得多一层点击**——访问"用户权限设定"从 `23 系统管理 → 2306` 变成 `23 系统管理 → 2301 系统功能 → 2306`，是每天都要多付一次的代价。若将来真要收，是一次纯 `M_P_IDX` + `SORT_IDX` 调整，随时可做。
- **不把校验规则独立成 230105**：见第 5 节（可逆性不对等，且机制成本会摊到全部模块）。
- **不复用 2308**：它是已退役的「工作任务记录」，编号不回收。
