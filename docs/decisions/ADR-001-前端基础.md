# ADR-001：使用 Tabler 作为可隔离的前端视觉基础

- 状态：已接受
- 日期：2026-08-02
- 决策者：项目团队

## 背景

ERP 需要大量布局、导航、表单、表格、弹窗、状态反馈和响应式能力。完全从零设计和实现基础 UI 会消耗大量资源，同时不能直接形成采购、销售、库存和财务等核心业务价值。

项目评估了两套开源后台方案：

- Tabler
- Gentelella

同时考虑了完全自行设计基础 UI 的方案。

## 决策

采用以下方案：

> 使用 Tabler 作为 UI 与视觉基础，通过项目自有 React 组件层进行封装，并自行设计 ERP 通用组件和领域组件。

具体约束：

1. Tabler 负责基础视觉语言、排版、色彩、布局和常用控件外观；
2. `components/ui` 封装 Tabler 的 class 和 DOM 结构；
3. 业务页面优先使用项目组件，不复制 Tabler 演示页面作为长期实现；
4. ERP 表格、搜索、状态、权限、单据和审批组件根据真实业务场景设计；
5. 不深度修改 Tabler 源码，主题覆盖集中管理；
6. 引入和升级前检查 Tabler 及第三方依赖的许可证和兼容性；
7. 若未来替换视觉基础，领域层不应因此整体重写。

## 选择理由

### 相比完全从零设计

- 更快建立一致且成熟的应用骨架；
- 减少响应式、基础状态、浏览器兼容和视觉规范的重复工作；
- 将资源集中到复杂表格、单据录入、权限和审批等 ERP 核心问题。

### 相比 Gentelella

- Tabler 的视觉和交互基础更现代；
- 更适合作为长期产品的设计基础；
- 更容易通过组件封装形成项目自己的设计语言；
- Gentelella 可作为传统后台信息布局参考，但不作为新系统核心底座。

## 考虑过的替代方案

### 方案 A：完全自行设计和实现

优点：控制力最高，不依赖模板风格。

未选择原因：初期成本和持续维护成本高，会推迟业务闭环验证。项目仍会自行设计领域组件，而不是放弃产品差异化。

### 方案 B：直接使用 Tabler 演示项目和页面

优点：短期页面产出快。

未选择原因：容易让业务逻辑依赖模板 DOM 和 class，造成样式覆盖、架构混乱及升级困难。

### 方案 C：以 Gentelella 为应用模板

优点：传统后台示例较丰富，适合快速拼装内部工具。

未选择原因：整体视觉和部分实现方式较传统，不符合长期现代化 ERP 的技术与体验目标。

## 结果与影响

### 正面影响

- 可以快速获得统一的基础视觉；
- 自有组件 API 能稳定业务代码；
- 允许按 ERP 场景逐步形成设计系统；
- 降低未来升级或替换 Tabler 的影响范围。

### 成本与风险

- 需要维护一层项目组件，而不能直接照搬模板；
- 封装过薄会导致 Tabler 细节泄漏，封装过度则会增加开发成本；
- Tabler 不是 ERP 框架，权限、工作流、表格、单据和领域规则仍需自行建设；
- 复杂 Data Grid 可能需要独立技术选型；
- 上游升级和许可证变化需要持续关注。

## 执行准则

- 组件只在真实页面需要时创建；
- 至少出现第二个复用场景后，再将领域组件提升为通用组件；
- 主题变量与 Tabler 覆盖集中在 `styles`；
- 业务状态颜色由 `StatusBadge` 等统一组件管理；
- 若要更换 UI 基础或引入专业 Data Grid，应新增 ADR 记录原因和迁移影响。

## 复审条件

出现以下情况时复审本决策：

- Tabler 停止维护或许可证不再适用；
- 可访问性、性能或浏览器兼容性不能满足要求；
- 项目组件层无法有效隔离 Tabler；
- 产品形成完全不同的品牌设计体系；
- 基础视觉升级成本开始显著阻碍业务迭代。
