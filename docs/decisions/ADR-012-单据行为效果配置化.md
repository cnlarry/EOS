## 摘要（先读我，写给人类）

这份 ADR 决定给 EOS 装一台"单据动作加工台"。

**要解决的问题**：过去每张单据批核后"发生了什么"（库存增减、已收/已送数量回写、自动结案、应收应付联动…）是写在各自存储过程或 C# 代码里的。想调整 = 找开发改代码；换一个客户场景 = 再改一遍。旧系统试图用"模块里填存储过程名"来解决，结果把危险当成了灵活。

**本 ADR 的决定，用一句话说**：

> 把"单据动作"拆成 **事件 → 一长串可解释的字段公式**。公式以结构化数据落库、可版本化、可审计；事件发生时，整串公式在**同一个数据库事务**里按顺序执行，任一步失败全部回滚；解批时按每条公式的反向规则执行。校验（能不能存、能不能批）是安全闸门，不开放配置。

**打个比方**：

- 每张单据是一台机器，机器上有固定的"开机按钮"：保存、批核生效、解批、结案；
- 机器内部不是写死的，而是插一张"加工单"（配置数据）：第 1 步把本单数量加进采购单的已收数量、第 2 步盖日期、第 3 步看是否收满自动结案…
- "加工单"上的每一步都长这样：`目标表.字段 运算 本单.字段 @定位键 ?条件`。这行字业务能看懂、数据库能存、程序能执行、将来 AI 也能照着旧存储过程翻译。
- 某客户要不一样的行为 = 换一张加工单，不换机器；真遇到机器上所有零件都做不了的动作，才让开发造一个新零件（登记一次，全系统可用）。

**本 ADR 已定与待做**：

- ✅ 已定：三层拆分（校验闸门 / 默认收尾 / 可配置效果）；事件点（保存、批核生效、解批、结案占位）；效果注册表；库存助手 C# 化；旧存储过程作为过渡桥、白名单只减不增；失败按"整链回滚 + 审计"新语义。
- ✅ 已定（v4）：校验与业务动作同样目录化（通用校验模板）；所有走统一工作台/统一表单的单据进**同一运行时管线**，行为差异只来自模块配置数据，运行时代码不做 moduleId 分支；`ModuleBusinessMap`/`DomainRuleMap` 是过渡桥，最终退役——**两座桥均已退役**（`DomainRuleMap` 及其分派服务、定义字段于 2026-09-18 整体拆除；`ModuleBusinessMap` 现只保留"单据号/预付冲抵表"配置与目录承接登记表）。

## 1. 背景与调研事实

### 1.1 旧系统钩子模型

旧系统 MODULES 只有两个业务钩子字段：

- `AFTERSAVE_SP`（存盘后运行）：由调度过程 `P_Run_After_Save` 在每次保存后执行，输入为 `@pri_idx`（主键条件串）与 `@module`；调度器同时内建明细重复校验（`TABLES.DF_VERIFY`）。
- `UPDATE_SP`（数据更新，实际兼作批核生效过程）：工作流末步/直接批核时按 `P_WF_*` 语义调用，输入为 `@key_value`（主键条件串）、`@approve_tag`（1=批核、-1=解批）、`@msg`（输出）。

2301 菜单管理页面上只有这两个文本框（`ERP/Admin/MenuBuilder.aspx`）；没有"删除后"钩子；新增与修改共用保存后钩子（旧保存管线为删主表重建 + `P_Run_After_Save`）。

> **范围说明（2026-09-18 用户拍板确认）**：本 ADR 的范围就是上面两个钩子字段（及其批核侧桥 `P_WF_*`）所承载的**单据行为**——校验闸门、保存期目录规则、批核/解批效果链。**"库内不留旧 SP"不属于本 ADR 的范围**，它是与 ADR-012 并行的独立收尾目标（登记在 `docs/plans/ADR-012收敛交接提示词.md` §七"收口后剩余项"与 `docs/plans/decision-ledger.md` #116：报表族 `P_RPT_*`、运行期按名调用点、`CompareAfterSave` 验收基准）。
>
> 两类对象的**下线判据不同**，不可互相类推：
>
> - **钩子消费点**（`UPDATE_SP`/`AFTERSAVE_SP`/`P_WF_*` 及其翻译来的 C# 族）：按本 ADR 的"翻译一域、退役一域"执行，先落目录/效果再删码；
> - **非钩子遗留对象**（报表过程、系统 `xp_*`、被牵连的辅助过程等）：只允许"先证后删"——必须同时满足 ⒜ 三方核查**零引用**（`sys.sql_expression_dependencies` 含未限定 schema 的引用 / `MODULES`·`REPORT_SORT` 等运行期元数据 / 代码与脚本按名字面量）、⒝ 对象本体在 `EOS.Database` SSDT 快照中可还原（回退路径明确）、⒞ 迁移内置同样的守卫且失败即 THROW、⒟ **逐个登记**到 `docs/plans/ADR-012两级覆盖率报告.md` §八的"非钩子遗留对象下线登记"表（含证据与还原方式）。**报表族的在册对象（仍被 `REPORT_SORT.SORT_FIELDS` 引用者）必须先移植到 API 查询/报表定义，再退役。**

### 1.2 全量扫描统计（EOS.Database schema 快照）

对 `EOS.Database/dbo/Stored Procedures` 全部相关过程做了写语句/EXEC/事务/动态 SQL 扫描：

| 类别 | 数量 | 观察 |
|---|---|---|
| `*_After_Save`（含调度器本身） | 96 | 72 个过程体无直接写语句，本质是校验/查重门禁；24 个有写，多为本单汇总清理（采购/请购/领料把明细合计写回主表或 MORE 表）与元数据联动（权限、工资项目、员工卡），少量跨表（如员工卡旧卡失效联动） |
| `P_WF_*` | 117 | 113 个采用 `@key_value/@approve_tag/@msg` 签名；93 个过程体直接写表；26 个显式调用 `P_UPDATE_PRO_DEPOT`（库存）；**全部无 `BEGIN TRAN`**（逐条自动提交） |

批核过程直接写目标表频次前列：`PRODUCT`(24)、`COP_ORDER_D`(19)、`MOC_PRODUCE_M`(17)、`CLIENT`(7)、`SUPPLIER`(6)、`BANK`(6)、`MOC_PRODUCE_D`(6)、`COP_ORDER_MORE`(5)、`PUR_PURCHASE_D`(5)、`MOU_MOULD`(4)、`HR_EMPLOYEE`(4) 等——**几乎没有本模块自己的主表**。

代表样例（`P_WF_COP_SEND` 送货单批核）：

1. 校验 `P_COP_SEND_CHECK`；
2. `COP_ORDER_D`：累加 `FINISHED_SEND_QTY/FINISHED_SPARE_QTY`、回写实交日期；
3. `COP_SHIPMENT_D`：累加排程已送量；
4. `CLIENT`/`PRODUCT`：最近交易日期；
5. `MOC_PRODUCE_M`/`COP_FITOUT_D`：按 SYSSS 开关累加工单/备货已送量；
6. `P_COP_ORDER_FINISHED`：满足条件则自动结案（置 `FINISHED_TAG`）；
7. `P_UPDATE_PRO_DEPOT`：库存、批号、流水；
8. `PRODUCT.NOT_SEND_QTY`：MRP 未交量。

`@approve_tag=-1` 解批时先做 NOT_BACK 校验，再把上述累加全部反向。

库存公共助手 `P_UPDATE_PRO_DEPOT` 实际写入：`INV_PRO_DEPOT`（余额+移动平均成本）、`INV_BATCH_M/D`（批次进出）、`INV_DEPOT_LOG`（流水，删除守卫引用）、`PRODUCT`（汇总数量/金额/最近进价）。其入参 `@sql` 是**调用方拼好的整段 SELECT 文本**，由助手 `exec(@sql)` 消费。

### 1.3 现代系统状态

- 保存侧：`AFTERSAVE_SP` 等价逻辑已大体 C# 化（`DomainRuleMap`/`ModuleBusinessMap` + `DomainRuleService`，同事务、参数化 SQL、100+ 模块登记）。
- 批核侧：仍经 `ControlledSprocInvoker` **受控调用旧 `P_WF_*` 黑盒**（白名单 + 参数化包装，但过程体内仍是动态 SQL 与逐条自动提交）；失败时只还原 `CONFIRM_TAG`，已写副作用不随事务回滚。
- 库存写入：EOS.API 目前**没有任何 C# 代码写 `INV_PRO_DEPOT`/`INV_BATCH_*`/`INV_DEPOT_LOG`**，`INV_DEPOT_LOG` 仅被删除守卫读取。
- 手动结案/取消结案：现代 `WorkbenchApprovalService.FinishCoreAsync` 只更新 `FINISHED_*` 状态列，**无效果钩子**；自动结案（`FINISHED_TAG` 联动）是批核效果的一部分，由 `P_*_FINISHED` 实现。
- AUTO_APPROVE 模块保存即批核：保存成功后进入批核效果。

### 1.4 调研结论

1. 旧系统"流程自定义"的真相：保存后钩子 = 门禁校验为主；**批核钩子 = 单据状态生效时的跨表效果传播**。用户记忆中的"过账、成本、库存、应收应付埋在存储过程里"准确对应批核类 `P_WF_*`。
2. 效果不是发散裸 UPDATE，可归纳为有限原语：量额累加回填、状态传播（自动结案）、库存/批次/流水、主档戳记（最近交易日期/MRP）、应收应付冲抵、元数据联动、触发后续流程。
3. 技术债：`@key_value` 文本拼入 `sp_executesql`（定位"其它行"的旧式做法）；批核 SP 无内建事务；解批对 `INV_DEPOT_LOG` 是 DELETE 而非反向流水（审计不可追溯）；移动平均成本部分口径粗糙。

## 2. 决策

### 2.1 分层：固有约束/默认行为 vs 可配置效果

保存链路拆成三层，只有第三层向 2301 配置开放：

1. **固有约束（零配置、代码实现、不可关闭）**：字段类型/必填/只读、服务端金额复算、明细查重（DF_VERIFY 类）、域校验（现 `DomainRuleService` 中校验类规则）。校验一旦可配置 = 可被关掉 = 脏数据入口。
2. **默认收尾（零配置、代码内建）**：本单汇总/清理、审计列/幂等键填充、OWNER 回填。
3. **可配置效果（行为目录 + 参数，由事件触发）**：跨表/跨主档传播、库存、状态传播、主档戳记、触发流程/作业、元数据联动。

### 2.2 事件模型修正

用户动作/流程迁移与业务效果是两个维度，效果只挂在"状态生效点"：

- **用户动作/流程迁移**：新增、修改、保存、送审、逐级审批同意/驳回、撤回、批核（无流程）、解批、结案、取消结案、删除。
- **效果触发点（v1）**：
  - `SAVE`（新增/修改不拆为两个事件，维持单一触发点；个别差异用条件表达，见 §7 已决结论 1）；
  - `APPROVE_EFFECT`（无流程直接批核的生效点 与 有流程末步通过后的生效点，**同一触发点**——解决当前 `WorkbenchApprovalService` 与 `WorkflowEngine` 两处重复执行 `WorkflowSproc` 的问题）；
  - `DEAPPROVE`（解批，正向效果的反向配对）；
  - `ENDCASE`/`UNENDCASE`（事件先占位定义、效果留空，见 §7 已决结论 3）；
  - `DELETE`（v1 不纳入效果；已批核/已结案禁删守卫属固有约束层，见 §7 已决结论 2）。
- AUTO_APPROVE：保存效果链执行后紧跟 `APPROVE_EFFECT` 效果链；顺序系统固定，不开放配置排序（见 §7 已决结论 4）。
- 自动结案不是按钮事件，是 `APPROVE_EFFECT` 中的"状态传播"效果；与手动结案事件语义分离。

### 2.3 效果注册表与目录（不开放任意 SQL/脚本）

采用与 `ChooserRepository`（sourceKey）、`ModuleBusinessMap`（领域规则）同构的**服务端注册 + 配置引用**模式：

- 效果实现 = 注册的 C# 能力（`EffectRegistry`），每个效果有固定 Key、参数 Schema、事务/补偿/审计契约；新增效果类型 = 代码注册 + 单测，禁止运行期写 SQL/脚本。
- 目录初版原语（按调研分解）：
  - `field-accumulate`：量额累加/覆盖回填，参数含目标模块/表、关联键来源、目标字段、方向、条件；自动生成反向；
  - `state-propagate`：自动结案/状态传播；
  - `inventory-move`：C# 化封装 `P_UPDATE_PRO_DEPOT` 语义（见 2.4）；
  - `master-stamp`：最近交易日期/MRP 计数等主档戳记；
  - `meta-link`：权限/字段元数据联动（现 `sysdg`/`hr-wage-item` 类）；
  - `flow-trigger`：触发后续流程/作业；
  - `job-enqueue`：过账、成本核算等批量作业入队（作业本体仍在作业服务，不入同步效果链）；
  - `legacy-sproc`：过渡桥（白名单 = 现受控 `P_WF_*`/`*_After_Save`），逐域迁移后退役——**已退役（2026-09-18）**：白名单（`IsKnownSproc`）、执行器（`ControlledSprocInvoker`）与注册表保留键均已删除。
- 目录种子 = 批核 SP 效果分解台账（见 §5 Phase A），不是拍脑袋清单。

**配置化边界与期望管理**：本 ADR 的"配置化"指**有限原语的编排配置**，不是可视化编程任意业务逻辑。`P_WF_COP_SEND` 这类带 SYSSS 开关分支、条件自动结案的复杂流程，配置层只承载其规律性部分，其余以定制 C# 效果承载。验收采用两级口径：**主口径 = 统一管线覆盖率**（配置效果 + 代码注册的定制效果合计）≥90%，最终目标 100%；**次口径 = 可视化配置覆盖率**约 70% 即视为成功，其余复杂逻辑走定制 C# 效果（`EffectRegistry` 本就允许代码注册）。

**条件模型表达边界（封闭算子集合）**：条件结构 JSON 的算子必须是封闭集合，仅允许：字段与常量比较（`=`/`<>`/`>`/`>=`/`<`/`<=`）、枚举/布尔判断、跨表存在性（只引用已注册关系边，见 §2.5）、SYSSS 系统开关引用、单据状态守卫。条件只表达"规律性部分"，表达不了的效果一律用定制 C# 效果承载。

**条件 JSON 算子符号 ↔ 代码枚举映射（2026-09-07 登记，封闭集）**：

| CONDITION_STRUCT type / op | 语义符号（§2.3） | 代码枚举（EffectConditionCompiler / EffectStructSchemas） |
| --- | --- | --- |
| `field-compare` + `EQ` | `=` | 左项字段/参数 = 右项字段/常量 |
| `field-compare` + `NEQ` | `<>` | ≠ |
| `field-compare` + `GT` | `>` | > |
| `field-compare` + `GE` | `>=` | ≥ |
| `field-compare` + `LT` | `<` | < |
| `field-compare` + `LE` | `<=` | ≤ |
| `value-eq` | 字段=常量 | `=` |
| `value-neq` | 字段≠常量 | `<>` |
| `not-exists` | 跨表存在性（引用已登记关系边或 match 关联） | 内层表 NOT EXISTS + 条件 |
| `switch` | SYSSS 系统开关 | `COALESCE((SELECT MAX(CAST(key AS int)) FROM SYSSS),0) =/<> 1` |

符号只在文档层使用；落库与执行一律用上表 JSON 枚举，注册表与条件编译器按此封闭集 fail-closed 校验。

### 2.4 库存公共助手 C# 化

同意封装方向，但**反对"通用工具类 + 配置传 SQL/表名/字段名"**（旧 `P_UPDATE_PRO_DEPOT` 的 `@sql` 正是整段 SELECT 文本，属最危险形态）：

- 落点为受控能力 `inventory-move`：结构化入参（单据类型/号/日期 + 明细行：品号/库别/数量/单位/单价/币别/汇率/金额/批号），由服务端定义装配；表名/列名只来自注册白名单；
- 必须保持既有不变量：库存单位换算（BASE_QTY）、移动平均成本重算、品号/库别/批号存在性检查、批号管理检查、库存不足检查、`INV_DEPOT_LOG` 流水、`PRODUCT` 汇总；
- 同事务执行（与批核状态更新一起提交或一起回滚）；
- 借机修正项：解批流水由 DELETE 改为写反向记录——**已拍板接受**（验收口径 = 库存余额一致 + 流水语义改良，不逐行对拍 `INV_DEPOT_LOG`，见 §7 已决结论 6）；成本口径与分支结构缺陷对拍确认后按意图修正（对齐 `SP领域等价移植设计` 先例，仍需顾问逐项确认）。

### 2.5 配置存储与 2301 管理入口

- DbUp 版本化建表（对象名全大写，命名与列细节评审后定）：模块 + 事件 + 效果链行（顺序、效果 Key、参数结构 JSON、条件结构 JSON、失败模式、启用、反向配对、审计列）；**纳入 Definition 快照/发布/回滚体系**（已决，见 §7 已决结论 7）——配置变更产生新版本，执行记录引用版本号。
- 管理入口：**2301 模块管理内嵌"行为动作"配置区**（已决，见 §7 已决结论 5；配置按模块归属、管理语境在 2301）；服务端 CanSetup 再授权；保存即校验：效果 Key 已注册、参数符合 Schema、条件可解析、目标表/字段在物理元数据与关联关系白名单内、顺序 lint 通过（见 §2.6），**fail-closed，不留 SQL 后门**。参数编辑器按效果注册的参数 Schema 渲染表单，**不以 JSON 文本框为主要编辑形态**（细节 MVP 定）。
- 关联键表达**复用 `FIELD_RELATION`，不另建第二套关系事实源**：`FIELD_RELATION` 为 M10c 已落地设施（DbUp 迁移 051，FROM/TO 表+列四元组主键，已种 7 条种子关联：订单明细→产品、库存→产品/仓库、订单/收款→客户、采购/应付→供应商）；效果配置只引用已登记关系，需新关联边先登记再引用。当前 `FIELD_RELATION` 是 assistant 读侧设施，效果侧复用时按需扩展列（如方向语义、效果所需键映射），扩展走 DbUp 迁移。

### 2.6 运行时

- 新增统一效果执行器 `EffectPipeline`，接入点：
  - `WorkbenchCommandHandler` 保存事务内（SAVE）；
  - `WorkbenchApprovalService` 批核/解批（APPROVE_EFFECT/DEAPPROVE）；
  - `WorkflowEngine` 末步通过（与直接批核同一 APPROVE_EFFECT 点，消除双实现）。
- 效果执行带：顺序、条件、失败模式（阻断/警告）、幂等键、状态守卫、效果粒度审计（`AUDIT_EVENT` 动作区分效果 Key）、反向配对。

**顺序依赖治理（顺序 lint）**：旧 SP 步骤顺序承载语义（如 `P_WF_COP_SEND`：先累计完成量 → 再判自动结案 → 再写库存），配置开放顺序自由度即开放配错自由度。治理措施：Phase A 台账为每个模块记录**规范顺序**并标注步骤间数据依赖；依赖模式随原语目录一起登记（如 `state-propagate` 依赖同链 `field-accumulate` 先行、`inventory-move` 依赖量额回填先行）；2301 保存即校验增加**顺序 lint**，依赖不满足即拒绝保存；配置界面展示依赖提示可推迟至 MVP，服务端 lint 即刻生效。

**效果执行快照入审计**：每次效果链执行把"效果链配置版本 + 各效果参数快照"随审计落盘（承载形态：`AUDIT_EVENT` 事件体扩展或专用快照结构，评审后定），保证"该单当时按什么规则生效"可回放；与 Definition 快照/版本体系衔接——配置变更产生新版本，执行记录引用版本号（见 §2.5/§7 已决结论 7）。
- 权限：配置修改 CanSetup；效果执行在操作者权限内完成授权后的服务端动作；`legacy-sproc` 过渡期维持现状还原语义（SP 无内建事务），直至迁移完成——**该过渡期已结束**（钩子列、定义字段、执行器三层均已删除）。
- 与工作流路由正交：2101 流程设计器继续管"谁批、按什么条件批、何时生效"；2301 行为配置管"生效后做什么"。两页责任边界写入各自 README/文档。

## 3. 明确不做 / 边界

- 不提供任意 SQL/脚本/表达式配置；不把校验门禁做成可配置项；不允许配置绕过 API 权限边界；
- 条件 JSON 不得发展为表达式/脚本语言：无算术组合、无嵌套查询、无自由文本表达式；条件表达不了的效果用定制 C# 效果承载，不得通过扩条件语言迁就个别 SP；
- 成本核算、工资计算、MRP 等批量作业不进同步效果链本体（仅可经 `job-enqueue` 入队）；
- 本 ADR 不拍板表结构命名、UI 交互细节、效果 Key 全集——由效果分解台账与 MVP 评审产出；
- 不重建旧系统的"保存即整单重建"等已被替代语义。

## 4. 风险与权衡

- **配置能力的信任边界**：效果链可配置后，误配影响面大——用注册表 + Schema 校验 + 保存即校验 + 版本快照控制；
- **可调试性**：效果链需要效果级日志、dry-run/试算、审计追溯；
- **回归面**：批核副作用跨域，必须分域放量 + 对拍（含正向、失败、解批反向三态）；
- **失败态语义变更（有意为之）**：旧批核 SP 无事务、逐条自动提交，中途失败会留下"效果写一半"的脏状态；新管线同事务全回滚是**有意的行为变更**。因此三态对拍中**失败分支不与旧库逐字段对拍**，比对标准按新语义定义：阻断点、失败消息、`CONFIRM_TAG` 还原、库内零残留（效果零写入）+ 效果级审计可查。Phase C 扩展 `CompareAfterSave.ps1` 按此口径实现失败分支；
- **旧 SP 缺陷修正**：移动平均成本口径、分支结构缺陷等迁移中修正属行为变更，需顾问逐项确认（解批流水 DELETE→反向已拍板接受，见 §7 已决结论 6）；
- **双实现收敛**：`WorkbenchApprovalService` 与 `WorkflowEngine` 的 WorkflowSproc 执行必须收敛到同一触发点，防止迁移期行为分叉。

## 7. 已决结论（评审拍板，2026-09-05，决策人 Larry）

1. **新增/修改不拆为两个事件**：维持单一 SAVE 触发点，个别差异用条件表达。
2. **DELETE 不纳入 v1 效果**：删除只发生于未生效单据，无业务传播语义；"已批核/已结案禁删"守卫属固有约束层。
3. **ENDCASE/UNENDCASE 先占位、效果留空**：事件在事件模型中先占位定义，避免日后改事件枚举；台账证明有需求后再配效果。
4. **AUTO_APPROVE 顺序系统固定**：保存链→批核链顺序不开放配置排序。
5. **配置入口 = 2301 内嵌"行为动作"配置区**：配置按模块归属，管理语境在 2301；参数编辑器按效果注册的参数 Schema 渲染表单，不以 JSON 文本框为主要编辑形态（细节 MVP 定）。
6. **解批流水改为写反向记录：接受**；验收口径为"库存余额一致 + 流水语义改良"，不逐行对拍 `INV_DEPOT_LOG`。
7. **效果配置纳入 Definition 快照/发布/回滚体系：纳入**（由原建议改为已决，与 ADR-005 一致）。
8. **legacy-sproc 白名单冻结、只减不增**：新模块禁止登记 SP 效果；退役以域为单位，域迁移完成后清理对应 `UPDATE_SP/AFTERSAVE_SP` 消费点——**已收口（2026-09-18）**：两个钩子列的引用清零后已**物理删除**（迁移 173），运行期不再存在"按模块元数据调用存储过程"的入口。

**实施现状补充（2026-09-14，D11）**：
- **`SAVE` 事件：本期不启用**——统一管线对 SAVE 有实现，但库内 `MODULE_BUSINESS_ACTION` 的 `SAVE` 配置为 0 条；
  不翻译占位场景，事件保留为触发点定义（未来有本单汇总回写等真实需求时再配效果），避免"看着能用其实没数据"的误判；
- **`ENDCASE`/`UNENDCASE`：已知未实现（已拍板留空）**——事件在事件模型中占位定义、效果留空（见结论 3），
  手动结案/取消结案只更新 `FINISHED_*` 状态列 + 审计，无效果钩子；这是**有意留空**而非"不需要"，
  有需求时按结论 3 先补台账证据再配效果。

**实施现状补充（2026-09-17，AUTO_APPROVE 接入）**：
- **自动批核与手工批核共用同一条生效链**（`WorkbenchApprovalService.RunEngineApprovalAsync`）：引擎接管时，
  两者都走「同一事务内：阶段校验闸 → 守卫翻转 CONFIRM_TAG → 效果链 → 审计」，失败整链回滚
  （CONFIRM_TAG 还原 + 效果零写入），不再有"状态先自动提交、效果另事务、失败靠补偿写"的残留窗口；
  判定是否接管统一走 `EffectEngineInvoker.IsEnabledFor`（全局开关 + 快照 `effectEngine.enabled`），
  运行时代码不按模块号分支；未接管模块继续走遗留过程过渡桥（§15.3，独立连接 + 补偿语义）。
- **触发点**：新增与修改两条保存路径在提交后都紧跟 `APPROVE_EFFECT`（§2.2 顺序不开放配置）；
  保存已落库，自动批核失败以 warning 回传并让单据停在未批核态可重试（不在本次改变）。
- **重复触发口径**：保存触发的自动批核幂等成功（重复保存不重复累计）；用户手工重复批核仍返回
  `WORKFLOW_STATE_CONFLICT`（保留显式冲突提示，与 E2E 契约一致）。
- **经办人 = 保存人（2026-09-17 用户拍板，推翻 SYSTEM 占位）**：保存时判断是否自动批核模块——是则自动批核、
  否则只保存；新增记新增人、修改记编辑人。`CONFIRM_PERSON` 是经办人列，语义是"谁让这张单生效"，
  写 `SYSTEM` 会抹掉责任主体且与手工批核口径分叉；"是自动批核还是手工批核"改由**审计摘要**承载
  （`SUMMARY=N'自动批核'` vs `批核`），状态列不再承担该区分。存量 `SYSTEM` 行不迁移。

**实施现状补充（2026-09-18，批 4 退役与两级覆盖率口径）**：
- **`SAVE` 事件已启用**（推翻上条 D11 的"本期不启用"）：批 4 逐族退役把"保存后 C# 领域规则"改为 **SAVE 期效果步骤**，
  现库内 `MODULE_BUSINESS_ACTION` 的 `SAVE` 配置 **26 条**。它们的共同形态是**有序多步写 / 门控写 / 写后校验链**：
  SAVE 期目录校验先于效果执行，把写与随后的校验拆成两处会读到陈旧的计算列，故整链由**一个服务处理器**承载
  （必要时在链内抛 `EffectValidationException` 阻断）。
- **次口径的分母口径（建议，见决策清单 #121）**：ADR §6 的"可视化配置覆盖率 ≈70%"期望值是对**批核/解批生效链**定义的
  （基线 279 步）；批 4 退役新增的 26 条 SAVE 期写型步骤并入分母会把比例稀释为 64.6%。故覆盖率报告并列给出两个读数：
  批核/解批口径 **197/279 = 70.6%（达标）** 与全量口径 **197/305 = 64.6%**，不隐藏差异。

## 8. 通用单据元模型与模块形态（v2 补充）

### 8.1 任何单据都是同一个骨架

不管收料单、送货单还是将来的新单，抽象后都是五部分：

1. **主档**：单据号（可能是"单别 + 单号"）、抬头（客户/供应商）、生命周期状态；
2. **明细行**：行号、料号/品号、数量金额，以及指向其它单据行的关联字段；
3. **生命周期状态机**：保存 → 批核 → 结案（含反向：解批、取消结案）；
4. **单据关系**：本单 ↔ 其它单的键映射，复用 `FIELD_RELATION`（ADR-012 评审已决），效果靠它定位"要改哪一行"；
5. **行为配置（加工单）**：事件 → 效果链（模板/算子 + 参数 + 条件 + 顺序 + 反向）。

部分模块除主/明细外还有**模块上下文表（MORE 类）**（如 `PUR_PURCHASE_MORE` / `PUR_APPLY_MORE` / `MOC_GET_MORE`）：它们随单据存在、承载扩展行数据；作为公式源时须在模块注册表中登记，不是自由表（见 §13.3 SOURCE_TABLE）。

引擎不"认识"收料单或送货单，只认识这个骨架：**"某张单发生某事件，按它的加工单执行"**。

### 8.2 模块形态判定（2301 三种形态）

2301 新增模块时主表/明细表可选，行为规则按形态判定：

| 形态 | 是否参与 | 说明 |
|---|---|---|
| 主表 + 明细 | ✅ 完整 | 全部效果可用（含按明细行聚合） |
| 仅主表 | ✅ 有限 | 保存/批核可配效果；按明细行的模板不适用 |
| 两表皆空 | ❌ 不参与 | 菜单组/特殊页，无行为规则 |

判定依据 `MODULES.MASTER_TABLE/DETAIL_TABLE`，运行时判空即可，无需额外登记。

## 9. 结构化公式与算子目录（v2 补充）

### 9.1 为什么必须是"结构化公式"

只有结构化的"目标.字段 运算 源.字段"数据才能落库、版本化、被 AI 翻译、被 lint 校验、被执行器解释。**任何"整段 SQL / 整段脚本"都不允许进入配置**（见 §3）。

公式文法（一行一条，可落库）：

```
目标表.目标字段  运算符  本单来源（MASTER / DETAIL / 已登记上下文表 TABLE + 聚合）  @定位键  ?条件   反向：…
```

### 9.2 运算符目录 v0.1（封闭集）

| 运算符 | 含义 | 实例 | 解批反向 |
|---|---|---|---|
| `+=` | 累加 | `PUR_PURCHASE_D.RECEIVE_QTY += SUM(this.D(QTY))` | `-=` |
| `-=` | 减 | 计划量扣减 | `+=` |
| `=` | 覆盖 | `PUR_PURCHASE_D.REAL_DELIVERY_DATE = this.M(RECEIVE_DATE)` | 默认不回滚 |
| `=MAX()` | 取较晚/较大值 | `SUPPLIER.LAST_TRADE_DATE =MAX(已有, this.M(RECEIVE_DATE))` | 不回滚 |
| `=MIN()` | 取较早/较小值 | `MOC_PRODUCE_M.FIRST_SEND_DATE =MIN(已有, this.M(CREATE_DATE))` | 不回滚 |
| `+=UNIQ()` | 去重追加 | `MOC_PRODUCE_M.DEPOT_PLACE +=UNIQ(this.D(DEPOT_PLACE))` | 默认不回滚，可配移除 |
| `APPEND` | 字符串直接追加（不去重） | `COP_ORDER_D.REMARK = REMARK + this.D(REMARK)` | 默认不回滚，可配移除 |
| `:=` | 条件满足才置为 | `PUR_PURCHASE_D.FINISHED_TAG := 1` | 按规则重算/清空 |

源侧聚合是参数不是运算符：`单值 / SUM / MAX / MIN / DISTINCT / PICK`；源范围含 `TABLE`（模块已登记上下文表，如 MORE 类表），配合 `SOURCE_TABLE` 使用（见 §13.3）。源为**字段加减组合**时使用 `SOURCE_TERMS_STRUCT`（闭式：仅字段的 +/− 组合，如 `SUM(QTY+SPARE_QTY−FINISHED_SEND_QTY)`；禁止乘除/函数/自由表达式，见 §13.3）。库存移动（`inventory-move`）是**服务级效果**：内部固定子流程（校验/单位换算/均价/批次/流水）不摊到模块配置；模块只传方向与字段映射。

> 2026-09-18 增补：`PICK` ＝"按定位键唯一相关行的**原值**取值"——用于把某单（如明细行）的字段整值回写到被引用单据（`link-stamp` 的明细取值形态）。与 `MAX/MIN/DISTINCT` 的区别只有一点：**不做数值默认**（那三者对来源列一律 `ISNULL(col,0)`，用于量额投影；对可空字符/日期列会写成 `'0'`/1900-01-01）。配合 `SOURCE_SCOPE=TABLE` + 显式 `SOURCE_TABLE` 使用时，定位键在 `EXISTS` 内 JOIN 主表并带主键过滤，**目标行选取天然限定本单**（对应旧处理器 `JOIN 明细 … JOIN 主表 WHERE 主键`）。新增算子/聚合仍需"多单据证据 + 代码注册 + 单测"：本轮证据 = 1404/1418/1606/1615/1616 五条 `link-stamp` 的明细取值（旧 `LinkStampHandler` 的 `fromDetail` 形态）。

扩展规则：新增运算符需"多单据证据 + 代码注册 + 单测"。已转正记录：`APPEND`（证据 = 1606 采购单与 1609 采购变更单两处备注追加）；`=JOIN_UNIQ()` 仍待证据。单个单据的特殊逻辑一律走 custom 效果，不得为它发明新算子。

### 9.3 执行与落库

- 每个事件的所有公式行按顺序组装进**同一数据库事务**：失败整链回滚（零残留 + 效果级审计），不再出现旧 SP 那种"写一半"；
- 每行配置建议存 `op` 与 `reverseOp` 两字段（允许覆盖默认反向，解决"批核按数量判断、解批无条件清"这类不对称）；
- 配置版本随 Definition 快照体系发布/回滚，执行记录引用版本号（§7 已决结论 7）。

已用真实单据拆解验证（公式全量见 `docs/plans/单据行为元模型与效果模板草案.md` §11）：

| 单据 | 结论 |
|---|---|

1. 生产入库单 `FINISHED_IN_DATE` 旧 SP 取 `CREATE_DATE`（建立日期）——业务上是否应为入库日期 `PRODUCT_IN_DATE`？

## 11. 从旧 SP 到公式的翻译路线（v2 补充）

目标是**旧存储过程能"很容易"被翻译成新公式，且不丢业务意图**：

1. **中间产物 = 公式台账**：旧 SP → 一行行结构化公式（事件/目标/运算/源/定位/条件/反向），人看得懂、AI 填得了；
2. **AI 助手做机械翻译，人类做意图评审**：AI 产出草稿，顾问逐行确认"这里做不做、条件对不对"；禁止 AI 未经评审直接落配置；
3. **意图 = 业务规则，不是代码行为**：旧 SP 的缺陷（NULL 累加失效、解批删流水等）按业务意图修正并显式标注，不机械照搬；
4. **对拍验证三态**：成功路径落库一致、失败按新语义（阻断点/消息/`CONFIRM_TAG` 还原/零残留 + 审计）、解批反向一致（库存流水按 §7 结论 6 口径）；
5. **过渡桥**：未翻译模块继续走 `legacy-sproc`（白名单冻结、只减不增），翻译一个域、退役一个域。

## 13. 配置存储设计（MODULE_BUSINESS_ACTION，v3 补充）

### 13.1 命名与术语

- 表名 `MODULE_BUSINESS_ACTION`，中文"业务动作"：模块 × 事件 × 顺序下的一条可配置动作（即效果链中的一行）；
- 子表 `MODULE_BUSINESS_ACTION_OP`，中文"公式行"：业务动作展开后的字段级运算（`目标表.字段 运算 源`），是 AI 翻译、对拍、lint、执行的最小单元；
- 公式型效果（`field-accumulate`/`completion-close`/`stamp-last-activity`/`adjust-projection`/`set-state`）以公式行为主存储；服务型效果（`inventory-move`/`meta-link`/`flow-trigger`/`legacy-sproc`）无公式行，参数存 `PARAM_STRUCT`。

### 13.2 MODULE_BUSINESS_ACTION（业务动作表）

| 字段 | 类型 | 含义 |
|---|---|---|
| ACTION_ID | BIGINT IDENTITY PK | 业务动作行主键 |
| MODULE_ID | INT NOT NULL | 模块号（MODULES.M_IDX）；两表皆空模块禁止有行 |
| EVENT_CODE | NVARCHAR(30) NOT NULL | 触发事件：SAVE / APPROVE_EFFECT / DEAPPROVE / ENDCASE / UNENDCASE |
| SEQ | INT NOT NULL | 同一事件内执行顺序（1 起） |
| EFFECT_KEY | NVARCHAR(50) NOT NULL | 注册效果键（field-accumulate / completion-close / …，服务端注册表校验） |
| EFFECT_NAME | NVARCHAR(200) NULL | 人类可读名称（缺省取注册目录默认） |
| ENABLED | BIT NOT NULL DEFAULT 1 | 是否启用 |
| FAIL_MODE | NVARCHAR(10) NOT NULL DEFAULT 'BLOCK' | BLOCK=失败整链回滚；WARN=警告继续 |
| CONDITION_STRUCT | NVARCHAR(MAX) NULL | 步骤级共享条件（结构化 JSON：SYSSS 开关 / 状态守卫 / 字段比较，封闭算子集） |
| PARAM_STRUCT | NVARCHAR(MAX) NULL | 服务型效果参数（结构化 JSON，按 EFFECT_KEY Schema 校验）；公式型效果可空 |
| REVERSE_STRUCT | NVARCHAR(MAX) NULL | 整步反向覆盖（不对称语义，如"批核按数量判断、解批无条件清完工码"） |
| REMARK | NVARCHAR(500) NULL | 给业务看的说明 |
| SOURCE_REF | NVARCHAR(100) NULL | 溯源：来自哪个旧 SP / 台账行 |
| CREATE_PERSON / CREATE_DATE / LAST_UPDATE_BY / LAST_UPDATE_DATE | NVARCHAR(40) / DATETIME2(3) | 审计列 |

约束：`UQ (MODULE_ID, EVENT_CODE, SEQ)`。

### 13.3 MODULE_BUSINESS_ACTION_OP（公式行表）

| 字段 | 类型 | 含义 |
|---|---|---|
| OP_ID | BIGINT IDENTITY PK | 公式行主键 |
| ACTION_ID | BIGINT NOT NULL FK → MODULE_BUSINESS_ACTION.ACTION_ID（ON DELETE CASCADE） | 所属业务动作 |
| OP_SEQ | INT NOT NULL | 动作内公式行顺序 |
| TARGET_TABLE | NVARCHAR(64) NOT NULL | 目标表（必须物理存在） |
| TARGET_FIELD | NVARCHAR(64) NOT NULL | 目标字段（必须物理存在） |
| OP_CODE | NVARCHAR(20) NOT NULL | 运算：ACCUM / DEACCUM / ASSIGN / ASSIGN_MAX / ASSIGN_MIN / APPEND_UNIQ / SET_WHEN |
| SOURCE_SCOPE | NVARCHAR(10) NOT NULL | 源范围：MASTER / DETAIL / TABLE（已登记上下文表）/ CONSTANT |
| SOURCE_FIELD | NVARCHAR(64) NULL | 源字段（CONSTANT 时 NULL） |
| SOURCE_TABLE | NVARCHAR(64) NULL | 源表（SOURCE_SCOPE=TABLE 时必填；必须是模块已登记的上下文表，迁移 054 新增） |
| SOURCE_AGG | NVARCHAR(10) NULL | 源聚合：NONE / SUM / MAX / MIN / DISTINCT / PICK（PICK＝唯一相关行原值，不做数值默认） |
| SOURCE_TERMS_STRUCT | NVARCHAR(MAX) NULL | 源加减项 JSON：闭式字段 +/− 组合（迁移 055 新增）；与 SOURCE_FIELD 二选一，如 `[{"field":"QTY","coef":1},{"field":"SPARE_QTY","coef":1},{"field":"FINISHED_SEND_QTY","coef":-1}]` |
| SOURCE_CONSTANT | NVARCHAR(MAX) NULL | 常量值（CONSTANT 时使用，如 'SYSTEM'、当前时间标记） |
| MATCH_STRUCT | NVARCHAR(MAX) NULL | 定位键 JSON：`[{"target":"PURCHASE_TYPE","source":{"scope":"DETAIL","field":"PURCHASE_TYPE"}}]` |
| CONDITION_STRUCT | NVARCHAR(MAX) NULL | 公式行级条件（如完成判定"数量与备品分别达到"） |
| REMARK | NVARCHAR(200) NULL | 给业务看的行级说明 |

### 13.4 版本与发布（复用 WORKBENCH 快照，用户已决）

## 14. 通用校验模板目录（v4 补充）

### 14.1 原则：校验与业务动作同哲学

保存侧"校验已 C# 化"不是逐张单据 C# 化，而是按**规则族**实现（`DomainRuleService` 81 个规则族、125 条模块映射、移植台账 107/109）。这套"模块号 → 规则名 → C# 方法"是过渡品，不是终点。

目标：校验与业务动作一样，采用"**代码 = 通用模板；模块 = 引用 + 参数**"的目录化模型：

- **核心默认校验（内建、无条件、不可配置）**：字段类型/必填/只读、服务端金额复算、明细查重（DF_VERIFY 类）、状态守卫（已批核/已结案/在途禁编辑删除）、OWNER 回填；
- **通用校验模板（模块按需引用 + 参数化）**：模块配置声明"用哪几个校验、参数是什么"；校验内容不可被配置绕过，但某类校验是否适用于该模块由模块数据决定；
- **定制校验**：目录表达不了的域特殊规则，注册为 `custom-validation`（代码 + 单测），登记后全模块可用，不是某单据专属。

### 14.2 校验模板目录 v0.1（从 11 页翻译 + 81 个域规则族归纳）

| 校验模板 | 语义 | 典型实例（不限于） |

| qty-not-exceed 不超量 | 目标单行剩余量 ≥ 本单数量（支持数量+备品、抵减字段组、允差） | 收料不超采购、送货不超订单、生产入库/出库不超制令、领料不超制令 |

> 2026-09-18 增补：`qty-not-exceed` 的 check 支持 **`dimensions`**——同一 check 内多个量纲（各含 `thisQty`/`usage`/`limit`/`offset`）按 **OR 合并**成一条违规判据、诊断行只输出一次，正对旧实现那句 `WHERE a OR b`（如备货单"数量"与"备品"两类判据）；各量纲必须一致地使用（或不使用）`thisQty.agg=SUM`，且 `dimensions` 与 check 上的单量纲块互斥（配置侧 fail-closed）。诊断里的"本单量"用 `{"scope":"THIS","dimension":N}` 指定第几组量纲（省略即第一组）。证据 = 1411 备货单"已备货不超订单/工单完工"的忠实移植。

> 2026-09-18 增补：`line-require` 从"行必填"扩展为**行字段约束**——新增 `assert`（数值比较断言，未命中即违规；给出后触发器可省略）与 `scope=MASTER`（断言行是当前主表行，供无明细表的模块使用），触发器/条件的 `scope` 必须与同一 check 一致（错域即配置失败，不静默取错别名）。证据 = 110103 货币资料（主表行：`IS_BASE=1 → CURR_RATE=1`）与 130101 库存盘点（明细行：`CHECK_QTY>=0` + 序号诊断）两条保存期判据的忠实移植。

## 15. 运行时统一管线契约（v4 补充，零 moduleId 分支）

### 15.1 适用范围与前提

- 凡是**走统一工作台/统一表单且具备单据形态**（主表非空）的模块，保存/批核/解批/结案全部走同一管线；
- 模块形态按 §8.2 判定：两表皆空模块不进工作台管线；仅主表模块进同一管线但按元数据裁剪明细相关能力；
- "一视同仁"的落点：**引擎不认识任何具体模块**，行为差异只来自模块定义数据（MODULES / FIELDS / 单据关系 / 校验配置 / 业务动作配置）。

### 15.2 管线步骤

1. **保存**：加载已发布 Definition（含校验配置与业务动作）→ 核心默认校验 → 模块校验模板链 → 主子表落库（同事务）→ SAVE 业务动作链（同事务）→ 审计/幂等；
2. **批核生效**：APPROVE 前置校验（校验模板链）→ CONFIRM 状态更新（同事务）→ APPROVE_EFFECT 业务动作链（同事务）→ 审计；
3. **解批**：反向守卫（state-guard/not-back）→ 状态更新 → 业务动作按 REVERSE 执行（同事务）→ 审计；
4. **结案/取消结案**：同构接入（事件占位，效果留空，见 §7 已决结论 3）。

### 15.3 无 moduleId 分支契约

- 运行时代码**禁止按 M_IDX 分支**；注册表只注册"能力"（校验模板 / 效果 / 服务），不注册"模块"；
- 行为差异全部来自 Definition 数据：模块配置引用哪个校验、哪个业务动作、什么参数；
- `ModuleBusinessMap` / `DomainRuleMap` / `WorkflowSproc` 白名单 = **过渡桥（BridgeRegistry）**：由模块数据标记（如 legacySproc 引用）驱动，同样不是代码分支；Definition 数据迁移完成后整桥退役；
- 校验：新增模块 = 填配置数据 + 必要时注册新通用模板/定制校验；不写 moduleId 特例。

### 15.4 验收口径

- 抽查任意工作台单据，其保存/批核行为由同一引擎与同一组代码路径解释；
- 静态检查：运行时代码无 moduleId switch/映射分支（纳入 eos-verify 类质量门）；
- 两级覆盖率（§2.3/§6）：统一管线覆盖 = 所有工作台单据可被引擎解释（目标 100%）；可视化配置覆盖 ≈70%，其余走注册的定制效果/校验。

## 16. 业务语义拍板（2026-09-06，决策人 Larry）

**总原则**：单据"生效/反悔"后的状态应反映**当前事实、可重算**；历史痕迹交给审计，不作为主表字段的"不擦除"理由。

1. **状态标志按当前量重算**：完工码 / 行完成标志（1505 入库、1515 出库、1606 请购行 FINISHED_TAG 等）在批核与解批后一律按当前累计数量重新判定，不再"解批无条件擦"；
2. **预交日期与备注回写（1606/1609）**：多明细行回写客户订单 `PRE_LASTPLAN_DATE` 取**最晚**预交日期；备注按**同源单据去重追加**；解批不回滚（计划痕迹，审计留底）；
3. **`FINISHED_IN_DATE` 取业务日期**：生产入库回写制令的最近入库日期用 `PRODUCT_IN_DATE`（为空回退 `CREATE_DATE`）；
4. **客户订单计划量解批重算（1405）**：`PLAN_QTY/DEPOT_QTY` 解批时按与批核同一逻辑重算；
5. **`PRE_RECEIVE_DATE` 解批清空（170101）**：对账单解批即清空预计收款日，再批核时重算；
6. **信用字段语义统一为"可用额度"**：`CREDIT_LIMIT_NUM` = 可用额度；订单/采购批核 = 占用（减）、收款/付款批核 = 释放（加），解批相反；客户订单方向需按拍板改为"减"，以真实样例对拍确认。
