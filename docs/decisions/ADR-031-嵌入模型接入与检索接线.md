# ADR-031 嵌入模型接入与检索接线（云端优先）

- 状态：**已接受**（2026-10-02）
- 日期：2026-10-02
- 相关：ADR-011（认知层与语义接口——知识通道与 embedding 决策标准）、ADR-016（知识通道接线缺口）、
  ADR-030（管理面：配置归属 §8、领域表 §6.1、密钥 §3）、ADR-002（网关与 RAG 边界，大部分已作废）

> **本 ADR 推翻一项既有拍板**：`docs/plans/RAG-选型.md` 的"本地优先、默认 bge-m3 sidecar"。
> 该文件与 `docs/plans/ADR-016-嵌入接线批-执行提示词.md` **未纳版本控制**（`git ls-files docs/plans` 为空），
> 所以定案必须记在这里——否则换一台机器就只剩"计划书里写着本地 sidecar"这一条线索。

---

## 1. 决定

| # | 决定 | 内涵 |
|---|---|---|
| 1 | **接入形态：云端 API 优先**，本地自建后置为"可选部署" | 不再要求在同一台机器上跑本地模型进程；架构上必须保留"换成自建端点"的切换点 |
| 2 | **接口口径：OpenAI 兼容 `POST /v1/embeddings`** | 与 chat 的 `/chat/completions` 同族；本地 sidecar（TEI 等）也走这个协议，于是"云端 ↔ 本地"只是换端点，不是换代码路径 |
| 3 | **配置归属仍走 3102**（供应商 → 模型 → 环境变量密钥） | 不新开配置节、不进 `appsettings`（ADR-030 §8）；模型表按**用途**区分对话 / 嵌入 |
| 4 | **同一时刻全库只有一个嵌入模型** | 换模型 = 相关集合重建；否则检索要按集合分别嵌入查询向量（1 次出网变 N 次） |
| 5 | **维度必须与集合登记一致** | 集合行记 `EMBEDDING_MODEL` / `DIMENSION`；两者与当前嵌入模型不符时**拒绝写入/激活**，不静默降级 |
| 6 | **fail-closed 不变** | 没配嵌入模型 ⇒ 维持 `PendingEmbeddingModel` 的可读失败（`KB_EMBEDDING_NOT_CONFIGURED` 家族），**不得**退化成空向量或"没有相关内容" |
| 7 | **预设目录扩容 + 型号清单由拉取得到** | 供应商预设只保证"入口可发出去"（端点 / 协议 / 密钥环境变量名）；型号由管理员填密钥后向厂商拉取候选再落库。**这条是模型面（3102）的通用能力，对话与嵌入同一机制**——定案记在 ADR-030 §12.3 |

## 2. 为什么推翻"本地优先"

原决策把成本放在**运维前置**上：一次性探针、权重获取、量化档位、与 SQL Server 抢内存、长驻进程启停。
换成云端后这些全部消失，代价换到两处：

1. **语料出网**：入库的是内部开发手册、ADR、业务规则、字段考古笔记。**这是部署方的合规判断，不是技术判断**——
   本系统的立场是"默认云端、本地随时可换"（§5 给了切换清单），在意语料外发的部署方自行切本地；
2. **检索路径每次出网**：`kb_search` 每次调用都要请求厂商，网络抖动与限流会直接体现在用户等待上。
   这一条**接受**，不做额外机制（不加重试风暴、不缓存查询向量去掩盖抖动）——真在意就切本地。

还有一层工程理由：本地优先把"能不能跑起来"押在**这台机器的 CPU/内存/依赖**上（无 CUDA、Windows Python 版本、
Docker 未装、WSL 才有 Linux 二进制），而云端把这条不确定性交给了厂商的可用性。**两者都是不确定性，
但后者不阻塞开发与验收**——接线批的价值在于让知识通道可用，而不是证明某台机器能跑模型。

## 3. 配置形状（落地细节）

### 3.1 复用"供应商 → 模型"两级，不新开第四档（ADR-030 §6.1）

```
ASSISTANT_PROVIDER  端点根 / 协议 / 密钥环境变量名 / 默认超时 / 启用
      └── ASSISTANT_MODEL  型号标识 / **用途** / **维度** / 超时 / 单价 / 启用 / **当前**
```

模型表新增两列：

| 列 | 用途 |
|---|---|
| `KIND` | `CHAT` / `EMBEDDING`（默认 `CHAT`，历史行不动） |
| `DIMENSION` | 仅嵌入用（如 1024）；对话模型为 `NULL` |

配套两处**必须一起改**的约束：

1. `UX_ASSISTANT_MODEL_ACTIVE` 是 `WHERE IS_ACTIVE = 1` 的筛选唯一索引 ⇒ **全表至多一条"当前模型"**，
   嵌入与对话无法各有一条。索引改为**按用途各一条**：`WHERE IS_ACTIVE = 1` 之上加 `KIND`。
2. `API_KEY_ENV_VAR` 在供应商表与模型表都是 `NOT NULL` + `LEN > 0` 检查 ⇒ **"无密钥端点"（本地自建）表达不出来**。
   放宽为可空（空 = 该端点不需要密钥，请求不带 `Authorization`）。
   这一条不是为了现在，而是为了让 §5 的"换回本地"**只改数据、不再改 schema**。

### 3.2 型号清单由拉取得到（**通用机制**；本 ADR 只补嵌入侧两条）

"型号不硬编码、由管理员填密钥后向厂商拉取候选再落库"是**模型面（3102）的通用能力，
对话与嵌入同一套机制**——定案记录在 ADR-030 §12.3，本 ADR 不重复。

嵌入侧只多两条：

- 拉回来的候选**由管理员指定用途**，嵌入还要**同时给出维度**（§3.1）——不靠型号名猜，
  猜错会得到一个永远打不通的行；
- **"这家有没有嵌入端点"也落在预设数据里**（与"能不能列出型号"同属能力差异）：界面据此明说
  "这家没有嵌入端点"，而不是让管理员配出一个必定 404 的行。

### 3.3 每个厂商都要有一条真值（2026-10-02 逐家核官方文档的结论）

预设里的每一行都必须是**能发出去的真值**（端点、协议、认证头、密钥环境变量名），**核过才写进目录**：

| 供应商 | OpenAI 兼容端点 | 嵌入端点 | 嵌入模型与维度 | **能对齐现有 1024 维？** | 列出模型 | 认证 |
|---|---|---|---|---|---|---|
| **阿里百炼（千问）** | `https://dashscope.aliyuncs.com/compatible-mode/v1`（新文档改用 `{WorkspaceId}.cn-beijing.maas.aliyuncs.com/...` 这种带业务空间的 host） | ✅ `/compatible-mode/v1/embeddings` | `qwen3.7-text-embedding` / `-flash` / `text-embedding-v4` / `v3`，**默认都是 1024**，可选 256~2560 | ✅ **支持 `dimensions`** | 待实测 | Bearer（`DASHSCOPE_API_KEY`） |
| **智谱（BigModel）** | `https://open.bigmodel.cn/api/paas/v4` | ✅ `/api/paas/v4/embeddings` | `embedding-3`（默认 2048，可 `256/512/1024/2048`）、`embedding-2`（固定 1024） | ✅ **支持 `dimensions`** | 待实测 | Bearer |
| **OpenAI** | `https://api.openai.com/v1` | ✅ `/v1/embeddings` | `text-embedding-3-small`（1536）、`-large`（3072），支持 `dimensions` 缩短 | ✅ 指定 1024 即可 | ✅ `GET /models` | Bearer（`OPENAI_API_KEY`） |
| **DeepSeek** | `https://api.deepseek.com` | **倾向无**（模型页的能力清单与列出模型页均未见嵌入端点；实现时拿密钥实测一次定案） | — | — | ✅ `GET /models`，**且返回窗口与最大输出、模态、effort** | Bearer（库内现值 `DEEPSEEK_APP_KEY`） |
| **KIMI（Moonshot）** | `https://api.moonshot.cn/v1` | **官方文档未见**（第三方 API 目录声称有，那类目录是自动生成的，**不可采信**） | — | — | ✅ `GET /v1/models` | Bearer |
| **小米 MiMo** | `https://api.xiaomimimo.com/v1`（另有批量与套餐 host；Anthropic 兼容 `/anthropic`） | **无**：官方模型清单里只有文本生成 / ASR / TTS，**没有嵌入模型** | — | — | 待实测 | **`api-key` 头**，不是 `Authorization: Bearer`（`MIMO_API_KEY`） |

**两条结论**：

1. **能当嵌入源的是百炼、智谱、OpenAI**（三家都支持 `dimensions`，**可以直接对齐现有集合的 1024 维**）；
   DeepSeek / KIMI / 小米不提供嵌入端点，配了也发不通；
2. **现有集合不必重建**：既然可指定 1024，`KB_COLLECTION` 里那几行的 `DIMENSION` 不用改——
   只有真的改维度才要重建。

**顺带暴露的一个预设字段缺口**：小米用的是 `api-key` 头而不是 `Authorization: Bearer`。
所以"认证头样式"必须与端点、协议一样落在**预设数据**里，不能由客户端写死——否则那家永远 401。

**入库分批参数按厂商上限设**：百炼 v3/v4 每次 10 条（qwen3.7 系列 20 条）、智谱 `embedding-3`
每次 ≤ 64 条且单条 ≤ 3072 token。分批与退避的具体值在实现时按实测。

## 4. 检索侧的配套约束

接线把知识通道从"空"变成"真的会注入"，因此下面两条与接线**同批**处理，不留到以后再补：

1. **相似度下限**：当前检索是 `VECTOR_DISTANCE('cosine')` + `TOP(@Top)`，**没有阈值**。
   知识库里满是参数键、错误码、模块号这类专有标识符——纯向量对它们最弱，且"凑得上的都注入"会污染回答。
   至少给一个"低于阈值不注入"的下限（宁可少报）。
   **2026-10-02 拍板：用相对截断**——只注入与"最好那条"差距在给定范围内的片段。
   不采用绝对阈值：`cosine` 的分值分布逐模型逐厂商不同，写死一个数会在换模型那天静默失效，
   而且失效的样子是"某天开始答案变差"，不会有任何报错。
   **已落地**（本批）：参数 `KB_SEARCH_RELEVANCE_MARGIN_PCT`（KB 域，默认 15 个百分点，
   0 = 只留最佳命中，100 = 基本不截断），截断由 `KbRelevance.Cut` 做在 `kb_search` 路径上。
   三条实现口径：① **永远保留最佳命中**（阈值配错也不会让知识通道整体失声，代价是"整批都不相关"时
   仍带一条，由工具输出开头那句"未必都与问题相关"交给模型判断）；② 工具输出会说出**被丢掉的条数**
   （"另有 N 条相关性明显更低未列出"）——不说的话，模型会把"只看到 3 条"当成"库里就这 3 条"；
   ③ **只作用于进模型的那条路径**，REST 检索端点不截断（它是给人翻的，条数另有 `KB_ENDPOINT_MAX_HITS`）；
2. **不可用的用户可见语义**：嵌入调用失败现在会被对话层统一兜成"工具执行出现内部错误，请换一种问法或稍后重试"——
   既没说清是向量服务不可用，还引导用户去重试一个重试不好的动作。
   **2026-10-02 拍板：告知不可用并继续回答**——说清知识库暂不可用（机制通道不受影响，其余照常答），
   不引导用户重试一个重试不好的动作。
   **已落地**（本批）：`kb_search` 的拒答正文就是**发给模型的指令**（`Deny` 的正文会回喂模型）——
   "知识库当前不可用（…）——本次回答没有用到知识库内容。请如实告诉用户这一点，并照常回答其余问题，
   不要让用户反复重试。"，后面附一段给管理员的原因（用户可转述）；"没配"与"厂商失败"分开说，
   后者带 `AI_MODEL_*` 原因码；

## 5. 将来换回本地要动什么（一处清单）

1. 3102 里把嵌入模型的**供应商端点**改成自建地址（如 `http://127.0.0.1:8080/v1`），
   密钥环境变量名**留空**（约束已在 §3.1 放宽）；
2. 保证自建端点返回的**维度与集合登记一致**（不一致就重建集合）；
3. 自建进程的启停归运维（本系统不自启、不代管）；
4. 模型权重 / tokenizer / venv **不入库**，把"从哪里取、放哪里、怎么换"写进部署文档。

**不需要**：改代码、改 schema、改检索 SQL（协议与形状都没变）。

## 6. 未决与风险（如实登记）

| # | 事项 | 现状 |
|---|---|---|
| 1 | 各厂商嵌入端点的**逐家核实** | **已完成**（2026-10-02 逐家对官方文档，结论见 §3.3）：百炼 / 智谱 / OpenAI 有嵌入端点且支持指定维度；DeepSeek / KIMI / 小米没有。**剩下一件是"选哪家 + 给密钥"**（批 B 已把客户端配好，配完即可用） |
| 2 | **限流与批量入库** | 各家的单请求批量上限已核（百炼 10 条、智谱 ≤64 条且单条 ≤3072 token，见 §3.3），并已落进预设数据（`AssistantProviderPreset.EmbeddingBatchMax`）与客户端分批；**退避与并发未做**——按 §2 的"接受抖动、不加重试风暴"，不做重试（失败如实报，由人重跑） |
| 3 | **网络抖动** | 接受（§2），不做额外机制 |
| 4 | 维度不一致时的**重建流程** | 维度不符会**拒绝写入**（`KnowledgeRepository` 硬校验 1024 与逐块维度），客户端也验厂商返回的维度；但**"换嵌入模型后重灌同一集合"目前不会被拦**：集合的向量空间标签（`KB_COLLECTION.EMBEDDING_MODEL`）只插不改（`EnsureCollectionAsync` 是 insert-only），同维度下两套空间的向量会静默混进一个集合。修它要先有"改登记 / 重建"的动作或手工路径，与批 D（语料入库）同批 |
| 5 | 嵌入用量是否进成本台账 | **2026-10-02 拍板：记量不计日限额**——嵌入 token 进用量台账（看得见花了多少），但不占用用户的日限额（它由系统触发，不该把某个人当天的额度吃掉） |
| 6 | 检索评估尺子（20–30 条中文问答的应命中文档） | 需要人工给正确答案，与黄金集同类工作 |
| 7 | **选哪家嵌入供应商 + 密钥** | 待部署方决定（三家都能对齐现有 1024 维，选谁不影响集合）。批 B 已落地：**配好即可用**，不依赖别的批次 |

## 7. 实施进度

| 批 | 内容 | 状态 |
|---|---|---|
| A | 3102 界面按用途分区 + 从厂商拉取型号后勾选落库 + 手工新增模型 + 无凭据端点可表达 | **已落地** |
| B | 嵌入客户端（OpenAI 兼容 `/v1/embeddings`）+ 维度校验 + fail-closed 保持 + 嵌入型号预设入库 | **已落地**（还差"各家真端点连一次"的实测，需密钥） |
| C | 检索阈值（相对截断）+ `kb_search` 不可用语义（告知并继续） | **已落地**（阈值参数 + 截断 + 工具输出口径；截断幅度是按"相对口径"给的经验初值，实际效果要等批 D 的评估尺子校准） |
| D | 语料入库 + 检索评估尺子 | 待做（需 API 在线、2302 `CanSetup` 账号与密钥） |

批 A 顺带落实的两条（都在 §3.1 的"配置形状"里，界面此前表达不出来）：**供应商的密钥环境变量名可留空**
（无凭据端点）；**两个用途各有一条"当前"**（取消当前必须指明用途，否则会把另一条静默清掉）。

批 B 落地的形状（细节见 [62](../guide/62-嵌入模型与知识库接线.md)）：

- **解析与调用分开**：`IAssistantEmbeddingResolver` 回答"当前该用哪个嵌入模型"（读库里那条"嵌入当前"，
  每次作用域解析一次并缓存，失败不缓存），`OpenAiCompatibleEmbeddingModel` 只负责出网与解析。
  这样"没配 / 模型没维度 / 密钥没配"三种拒答都是**纯函数**，能离线断言——fail-closed 是本批最该钉的性质；
- **三种拒答分开说**：没配模型指路去 3102 配并设为当前；模型没维度说清"维度决定向量多宽、要与集合一致"；
  密钥没配给出**环境变量名**。合成一句"知识库不可用"，管理员只能来回猜；
- **`dimensions` 总是显式发**：智谱默认 2048、OpenAI 默认 1536/3072，不指定就拿回一个与集合列宽不符的向量，
  而那时报出来的是"维度不符"，看不出是"没告诉它要几维"；
- **分批在客户端**（上限来自预设数据）+ **逐批验条数与维度**（条数对不上会把向量与内容错位配对，
  因此整批作废），按 `index` 校正顺序（厂商可能重排）；
- **失败映射与对话共用一张表**（`OpenAiCompatibleChatModel.FromResponse`）：分成两份，早晚出现
  "同一个 402 在这边叫余额不足、在那边叫未识别"；
- **认证头按预设样式发**，密钥为空则不带认证头（无凭据端点是合法配置）。
