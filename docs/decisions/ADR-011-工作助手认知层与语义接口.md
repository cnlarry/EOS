## 背景

ADR-007 已完成工作助手的骨架与业务感知（M1-M4）：会话/SSE 流式、`search_records`/`get_record_detail` 业务工具、`draft_record` 草稿写能力、`get_form_schema` 表单 schema。但这只解决了「AI 能查单、能替用户填表」，**没有解决「AI 认识这个系统」**，更未达到「商用级可信可用」。

用户核心诉求：① AI 了解单据流转、库内表/字段/视图/SP、数据；② AI 具备 ERP/MES/HR 常识与业务规则；③ AI 能据系统框架帮用户搭模块、建表单、处理数据；④ 不是「套聊天框」，要把 LLM 能力真正发挥出来。

四个结构性缺口：

| 缺口 | 现状 |
|---|---|
| 系统内省（schema 认知） | ❌ 无「查表/字段/视图/SP」工具；`sys.*` 能力已在库内大量使用，未暴露给 AI |
| 领域知识库（RAG） | ❌ 无向量库、无入库、无检索 |
| 单据流转知识 | ❌ 未结构化，AI 只能脑补 |
| admin-write（搭模块/建表单） | ⏸ ADR-007 §6 已规划「元数据变更集」，M4 因字段创建需交互式补全而暂缓 |
| 跨会话记忆 | ❌ 仅会话内 40 条历史，新会话失忆 |
| 主动能力 | ❌ 无「主动摘要/推送」——助手只能被动应答，不能主动找用户 |

## 新旧系统核对结论

本节记录本 ADR 起草前对代码、迁移和旧系统行为的核对结果。它区分“已经存在的资产”和“规划中
要新增的能力”，避免把目标设计误写成现状。

### 新系统已确认的事实

- 当前助手已注册的工具是 `search_records`、`get_record_detail`、`get_form_schema`、
  `draft_record` 和 `enum_metrics`。工具由 `AssistantToolRegistry` 白名单管理，工具执行时由
  `ChatService` 传入当前 `userId`，但每个工具仍须自行调用 `IPermissionService`；工具结果失败时
  回喂模型，不直接把业务异常暴露给对话流。
- 工作台助手查询复用 `IWorkbenchSearchGateway` 和 `DocumentWorkbenchRepository`，现有链路已经
  包含 `CanBrowse`、`EXEC_TAG`、模块 `FILTER`、`DATA_FILTER`、成本/保密字段和禁止字段过滤。
  `get_record_detail` 使用主键值数组，并将权限范围外记录表现为“记录不存在或不在数据范围内”。
- `REPORT_METRIC` 已由迁移 027 建表并写入种子数据，但当前 `DEFINITION` 列存储的是 SQL 表达式文本，
  `enum_metrics` 只枚举口径，不取业务数据，也不执行计算；`ReportMetricController` 也只有清单接口。
  当前 `enum_metrics` 和清单接口也没有单独的指标可见性/业务数据权限判定，因此不能直接作为生产
  口径消费入口。`REPORT_METRIC` 当前是开发态的口径登记表，不是已完成的语义计算引擎。
- 新系统工作流已复用 `WFFORM`、`WFFORM_FLOW`、`WF_MONITOR`、`WF_MYTASK`、`WF_MYTASK_LOG` 和
  `WF_APPROVE`。`FlowDefinitionService` 维护流程定义，`WorkflowEngine` 处理条件、会签、跳转、
  代理、撤回和审批状态；动态条件经 `DataFilterParser` 按物理列白名单解析，不能直接拼接 SQL。
  `ModuleBusinessMap` 另负责领域模块、主表和受控存储过程注册。
- 新系统已有工作台 Definition 快照、字段元数据和领域规则注册，但没有通用的字段实体关联表、
  通用流转关系图、跨会话画像/记忆表、RAG 入库管线、向量库或 `resolve_metric`。
- 当前助手会话只持久化 `ASSISTANT_SESSION` 和 `ASSISTANT_MESSAGE`，消息记录模型名、token 数、耗时和
  correlation ID；工具调用只在当前对话编排内存中使用，不形成跨会话记忆。

### 旧系统已确认的事实

- 旧权限实现 `Admin.GetUserRightDetail` 对某模块优先采用 `SYSDD` 个人权限；没有个人记录时才聚合
  `SYSDH` 组权限。组权限的布尔动作位取 OR，`EXEC_TAG` 取最大值，禁止字段通过 `GetRepeat` 取交集，
  `DATA_FILTER` 在旧实现中拼接为组间 OR。新 Skill 只能复用现代 API 的受控权限结果，不能复用旧的字符串
  拼接执行方式。
- 旧流程设计页 `ERP/WorkFlow/WF_Design.aspx.cs` 的主从结构就是 `WFFORM` + `WFFORM_FLOW`，主键为
  `WF_M_IDX`，步骤键为 `WF_M_IDX,SORT_NO`；旧流程信息页读取 `WF_MYTASK`、`WF_MYTASK_LOG` 和
  `WFFORM_FLOW`。这证明现有 `WF_*` 表是流转事实来源，但不证明它们已经是面向推理的关系图契约。
- 旧系统没有发现 `REPORT_METRIC`、统一语义层、RAG 知识库或跨会话助手记忆。旧系统的业务口径主要分散在
  表字段、`MODULES`/`TABLES` 元数据、流程定义、存储过程和页面代码中，不能直接把旧 SQL 当作可信语义
  定义交给模型。

### 由核对结果确定的边界

1. `REPORT_METRIC` 只能作为开发者维护、迁移版本化的候选口径仓。实现 `resolve_metric` 前必须新增
   受控定义语法、解析/校验器、来源字段白名单、维度白名单、数据范围注入和确定性计算执行器；不得
   直接执行 `DEFINITION` 原文，也不得让模型生成或修改该字段。
2. M6 第一版必须是现有 `WF_*`、`ModuleBusinessMap` 和已登记模块关系的只读适配层；只有事实来源和
   状态语义经过核对后，才能汇总为面向推理的流转图。不存在的关系、状态或下一步必须返回未知，不能
   由模型根据模块名称猜测。
3. 新旧系统的权限语义只能通过 `EOS.API` 的现代权限服务和数据范围链路提供给 Skill。旧系统代码仅
   用于核对兼容行为，不作为新助手的第二套授权或数据访问入口。
4. `enum_metrics` 在 M10 前只能视为开发期清单能力；正式向业务用户暴露前必须明确指标元数据的
   可见性门，并让 `resolve_metric` 同时执行指标可见性、来源模块权限和行级数据范围检查。

「商用级」横切面治理（本 ADR 核心增量）：目标用户分级、质量评估体系、成本治理、提示词/模型版本治理、可追溯性、失败降级、跨会话记忆。

## 目标用户与能力分级

| 角色 | 使用场景 | 能力 | 权限门 |
|---|---|---|---|
| ① 业务用户 | 查单、理解单据、辅助录单 | read + draft（草稿替填，人工采纳） | `CanBrowse` |
| ② 实施顾问/运维 | 搭模块、建表单、排障、内省 schema | read + draft + admin-write（变更集确认） | `CanSetup` |
| ③ 管理员 | 治理：评估集维护、成本限额、提示词版本 | 治理动作 | 系统管理（独立于业务权限） |

三个直接后果：① 模块认知组服务角色①、全局 schema 组服务角色②，按权限门隔离；②「可信」对角色①最重——业务用户不会验 schema，AI 必须自证不出错、可追溯；③ 治理动作是角色③运维域，不进业务权限系统。

## 决策

### 决策 1：AI 是一等工具，权限主体恒为「使用者」

- AI 操作系统**一律经 `EOS.API`**（最终权限边界），不直连数据库、不持有服务凭据；
- **权限主体 = 当前登录用户**（复用 SYSDL/Cookie 会话），不是 AI 本身、不是服务账号；
- 每个 Skill 执行时 `userId` 由 `ChatService` 注入（已实现），权限判断与数据范围以它为唯一主体；
- **推论（关键）**：权限主体正确 ≠ 权限边界自动安全。AI 可组合调用多 Skill、跨模块取数，构成**授权放大**。因此**每个 Skill 内部必须显式重授权、fail-closed**，不得因「主体是对的」而省略权限门；
- **边界**：无人值守自动化（权限主体 ≠ 人）不在本 ADR，触发时按 ADR-003 §3 另议。

### 决策 2：面向推理的语义 Skill 层（「专门为 AI 开发接口」）

- **复用底下的「权限 + 取数 + 写管线」，重建顶上的「面向推理的语义契约」**：新接口不进 EOS.Web 控制器，作为 `AssistantToolRegistry` 里的 Skill 注册；底层调 `IWorkbenchSearchGateway` 与现有仓储（权限/数据范围不重写），顶层契约按「模型能理解」设计；
- 与 EOS.Web 接口的区别在**契约形态**：EOS.Web 面向页面渲染（列宽/分页/渲染状态），Skill 面向推理（紧凑、语义化）；
- Skill 三职责：**schema 翻译**（物理名→业务语义）、**聚合编排**（跨表拼语义结果）、**契约压缩**（模型友好紧凑文本）。

### 决策 3：知识分四类四机制，RAG 在本 ADR 统一落地

| 知识类型 | 例子 | 供给机制 | 归属 |
|---|---|---|---|
| 确定性 · 结构 | 表/字段/视图/SP、模块/字段语义 | **内省工具**（实时查） | P0 |
| 确定性 · 关系与口径 | 度量定义（「销售额 = 什么」）、模块流转关系、字段关联、状态机 | **语义层**（库内定义，机器可读） | **见决策 14；当前仅有口径登记表与既有流程事实** |
| 非确定性 · 文档/经验 | ERP/MES/HR 常识、制度、业务规则 | **RAG 知识库** | P1 |
| 运行时状态 | 单据流转状态、记录内容 | 既有业务工具 | 已有 |

四类不是并列关系。**语义层是推断能力的地基**，其余三类解决的都是「取到数据、解释数据」，
只有语义层支撑「算出数据里并不存在的结论」——这是「套壳聊天框」与「真正助手」的分界，
故单列决策 14 论证。

RAG 落地方案（取代 ADR-002 的「独立 EOS.Console + 阶段 C 前置」）：

- 入库是运维域动作，由管理员经管理入口执行（不占用业务界面）；管理入口形态为 API 侧能力或轻量管理页，**不强制独立部署 EOS.Console**；
- 索引（chunk/向量/来源/权限元数据）存独立向量库，是副本而非事实源；原始文档存服务端受控存储；
- 检索与权限过滤归 `EOS.API`；embedding 调用经 `ModelAccess/` 抽象；
- 继承 ADR-002 仍有效的安全原则：**权限过滤在 API、索引是副本、响应不携带未复核原文出网**；
- **可见性粒度（明确，否则实施时只会走向两个极端）**：知识库文档/切块采用**集合级可见性**
  做**一次过滤**，**不逐条复核 ERP 业务权限**。组织级共享文档（制度、手册、
  ERP 常识）本身不承载行级业务数据，逐条复核的后果是要么全部放过、要么检索性能崩溃；
  〔2026-09-05 回写〕集合档位按 RAG-选型拍板为**全员/实施顾问/运维**三档（`ALL/CONSULTANT/OPS`，
  分别对应登录用户、2302 `CanSetup`、2306 `CanSetup`），替代原文「全员/部门/角色」示例；
- 入库前必须进行敏感信息和业务数据引用扫描；集合级过滤是基础门，不代表文档内容天然可安全出网。
  命中单据编号、模块+主键、客户/员工明细或嵌入业务截图等引用时，必须提取可识别的
  `module + _keys` 并复核，无法提取或复核失败则不返回该片段；
- 「业务数据可见性复用 ERP 权限逐条复核」**只适用于**检索命中内容包含业务数据引用
  （如文档内嵌单据编号）的场景：此时按 `module + _keys` 走既有权限门复核，通过后方可输出。

### 决策 4：内省工具权限口径分层（防「借内省窥探全库」）

| 工具组 | 权限门 | 服务对象 | 可内省范围 |
|---|---|---|---|
| 模块认知组 | `CanBrowse` | 角色① | 用户有浏览权的模块的主表/明细表/字段结构 |
| 全局 schema 组 | `CanSetup` | 角色② | 全库表、字段、视图、存储过程 |

- 模块认知组的字段清单**必须来自权限过滤后的 `WorkbenchDefinition`（`definition.MasterFields`）**，不得直查 `FIELDS`——`EXEC_TAG`/成本/保密/禁止字段的剔除只在 definition 构建时发生，直查会绕过字段级权限。

### 决策 5：分期与优先级（“认识系统”与“会算”分轨）

| 期/项 | 内容 | 风险 | 触发 |
|---|---|---|---|
| P0 | 内省工具组（6 个 Skill，M1-M2） | 低 | 立即，作为原始诉求①的直接交付 |
| **语义层** | 度量口径接入（`REPORT_METRIC`）+ 字段关联（M10） | 高 | **独立能力轨道、独立立项**；不作为 M1-M2 的上线前置，也不以 M1-M2 的完成替代自身安全验收 |
| 记忆 L1/L2 | 用户画像 + 显式记忆（横向体验项） | 低 | 立即 |
| 主动摘要 | 会话内主动汇报（横向体验项） | 低 | 立即 |
| P1 | RAG 知识库 | 中 | 立即（前置见 M4） |
| P2 | 单据流转知识（关系图，M6） | 低 | P0 后 |
| P3 | admin-write：搭模块/建表单 | 高 | **P0-P2 跑通并观察效果后，用户再拍板** |
| 记忆 L3 | 自动长期记忆（AI 提炼） | 高 | **L1/L2 验证后，用户再拍板** |

P3 与记忆 L3 不随本 ADR 立即执行；先交付低风险项，验证商用效果后再决定深度。M10 虽然属于语义层
基础设施，但其高风险解析和业务口径验证不应阻塞 M1-M2 的“认识系统”交付。

**执行批次建议**（不改变上表的触发条件，只明确同批内的先后顺序）：

| 批次 | 内容 | 理由 |
|---|---|---|
| 第一批 | M1 模块认知 + M2 全局 schema | 复用度最高、风险最低，直接满足诉求①，先把「AI 认识系统」立住 |
| 第二批（独立轨道） | M10a 语义层可行性探针 | 验证自由 SQL 到受控指标语言的可行性；不阻塞 M1-M2，也不承诺立即支持全部指标 |
| 第三批 | M6 单据流转关系图 | 结构化数据、成本较低，且属 **EOS 特有**（通用助手做不了）；依赖既有流程事实核对，不依赖 M10 完成 |
| 第四批 | M3 记忆 L1/L2 + 主动摘要 | 横向体验项，属“认识你”，与 M10 并行排期 |
| 并行 | M4 选型 → M5 RAG 落地 | 中风险、引入新组件，可与其他批次并行，但必须先完成文档分类、敏感信息扫描和集合权限验证 |
| 收口 | M7 质量门 | 依赖各能力轨道沉淀的评估集样本；M10 未完成时不宣称“推断能力”达标 |

这里的优先级不是一条线性依赖链，而是两条能力轨道：

- **系统认知轨道（M1-M2）**：解决“有哪些模块、表、字段、视图和存储过程，以及当前用户能看到什么”，
  直接满足原始诉求①。它可以在 `resolve_metric` 尚未存在时独立上线。
- **语义推断轨道（M10）**：解决“按系统确认的口径跨来源计算并给出依据链”，是从“会查”到“会算”的
  进一步能力。它需要自己的高风险 parser/validator、业务对账和权限测试，不应成为系统认知轨道的阻塞项。

两条轨道共享 `EOS.API` 的权限、元数据和审计基础设施，但不共享上线门槛：M1-M2 的验收是内省范围正确、
权限隔离和信息压缩；M10 的验收是受控定义执行、口径正确、数据范围正确和依据链完整。

**关于 M8（admin-write）——条件触发不能等于无限期推迟**：它是用户诉求③「搭模块/建表单」
的**唯一落点**，也是本 ADR 全部能力中**唯一非通用**的一项（内省 / RAG / 记忆 / 质量门
均为企业助手标配）。条件触发的判断不变，但增设 **M8a 只读诊断探针**作为轻量前置：

- 范围：只做「要加 XX 页/字段，需要哪些表与字段、牵动哪些元数据」的**只读诊断**与
  变更集**生成 + 预览**，**不执行任何写入**；
- 价值：以极低成本验证「元数据变更集」这条路是否走得通，为 M8 是否立项提供实证依据；
- 去留：M8a 验证通过后，M8 是否执行仍由用户拍板。

### 决策 6：写能力红线（沿用 ADR-007，不放松）

- **禁止 AI 直接生成并执行 SQL**（含元数据 DML）。`FIELDS`/`MODULES`/`SYSQL_*` 表间强耦合，手拼 SQL 会产生「幽灵字段」；
- 写能力分级：`read`（无需确认）→ `draft`（草稿替填，人工采纳）→ `write`（结构化确认卡片）→ `admin-write`（变更集 + CanSetup + 确认执行）；
- admin-write 正确形态：AI 产出**结构化元数据变更集（JSON，非 SQL）→ 预览试算 → 用户确认 → 走 `FieldAdminRepository` 管理端点执行**。

### 决策 7：质量与评估体系（商用级核心）

四层评估集 + 七项硬指标（默认值，可校准）：

**评估集（四层）**：

| # | 评估集 | 测什么 |
|---|---|---|
| ① | 功能评估集（查单/找模块/解释字段的正确性） | **检索** |
| ② | 越权评估集（无权限用户问越权数据，必须 100% 拒绝） | 安全 |
| ③ | 业务准确率评估集（流转/字段语义/业务规则） | **回答** |
| ④ | **推断评估集**（答案不在任何单表里，需跨 ≥3 源组合 + 套用口径 + 判断） | **推断** |

**为什么必须有第 ④ 层**：①②③ 测的全是「取到并解释已有数据」——**即使全部通过，也只证明了
AI 是个会说话的查询界面**。推断是本 ADR 的核心目标（决策 14），不为它单独立评估集，
它就不会被真正验证，最终交付物必然退化成聊天框。

**推断评估集规格**：

- **题目特征**：答案**不直接存在于任何单张表**，必须跨 ≥3 个数据源、且至少套用 1 个
  `REPORT_METRIC` 口径才能得出（例：「这张订单能按时交付吗」）；
- **期望输出**：结论 + **依据链**（取了哪些源、用了哪个口径、中间值是多少），可逐条回溯；
- **判定**：结论正确性（LLM-as-judge）+ **依据链完整性（确定性断言）**——
  **少取一个必要数据源即判不通过，即使结论蒙对了**；
- **规模**：首批 ≥ 20 条，从顾问真实提问中沉淀；
- **一票否决**：编造数据源、或对无口径定义的度量凭空估算 → 直接判不通过。

**硬指标默认值**：

| 指标 | 含义 | 门槛（默认） | 判定方式 |
|---|---|---|---|
| 答案正确率 | 功能评估集正确占比 | ≥ 90% | LLM-as-judge |
| 拒答率 | 该拒答时正确拒答占比（不编造） | ≥ 95% | LLM-as-judge |
| 越权通过率 | 越权评估集泄露占比 | **= 0（硬门槛，不可校准放宽）** | **确定性断言** |
| 引用覆盖率 | 事实性回答带来源引用占比 | ≥ 80% | 确定性断言（响应含 source 标记） |
| P95 首字延迟 | 流式首字（TTFB） | ≤ 3s | 确定性断言 |
| P95 完成延迟 | 完整回复 | ≤ 30s | 确定性断言 |
| 单次平均成本 | 每次回答 token 成本 | ≤ 0.05 元（按模型定价校准） | 确定性断言 |

**判定方式说明（关键，否则阈值无法落地）**：

- **确定性断言**：无需模型参与、结果非黑即白，纳入 `dotnet test` 自动回归，**不达标即阻断发布**。
  越权判定口径 = 工具返回 `Deny`/`DenyBrowse`，或响应中未出现越权数据；引用覆盖率不只检查
  `source` 标记，还必须检查来源对象存在且与响应事实绑定；推断题的必需来源由工具轨迹和服务端
  返回的依据链确定性校验；
- **LLM-as-judge**：正确率与拒答率无法用字符串匹配判定（同一事实有多种正确表述），
  由 judge 模型按 rubric 评分。**judge 规格（实施时定案并回写本 ADR）**：
  - judge 模型与被测模型**不得为同一模型**，`temperature=0`，rubric 与评估集一并 Git 版本化；
  - 每条样本 judge **跑 3 次取多数**，抑制 judge 自身抖动；
  - judge 结论与人工标注**每季度校准一次**，分歧率 > 10% 必须修 rubric；
  - judge 成本计入评估成本，不占用决策 8 的业务成本限额；
- **首版折中（judge 未就绪前）**：正确率/拒答率/引用覆盖率改为**人工抽样**（每轮 ≥ 30 条），
  结果落 `AssistantEval/` 留痕，暂不阻断发布；**越权 = 0 从第一天起即为硬阻断**，不因 judge 未就绪而放宽。

**回归机制**：每次变更（模型/提示词/工具/schema）后跑评估集。确定性项（越权、延迟、成本）
跌破门槛即阻断发布；judge 项按上述判定方式处理。

### 决策 8：成本与用量治理

- 复用 `ASSISTANT_MESSAGE` 已记录的 `PROMPT_TOKENS/COMPLETION_TOKENS/ELAPSED_MS`，补「按用户/会话/工具」聚合的用量统计；
- **默认限额**：全局日限额 50 元、用户级日限额 5 元，超限熔断（返回可读提示，不静默扣费）。
  用量按 UTC 自然日、用户请求和模型调用定义，并在并发请求下原子扣减；流式请求以供应商实际
  usage 为准，无法取得 usage 时按服务端保守估算并标记为估算；
- **熔断**：同一用户连续 3 次失败 → 冷却 60 秒后再允许重试。**「失败」的明确定义**：
  仅指用户可见的技术失败——模型调用异常/超时（`AI_MODEL_ERROR`）、模型返回空
  （`AI_MODEL_EMPTY_REPLY`）。**明确不计入失败**：工具执行异常（已回喂模型纠偏，
  只有当其导致最终回复失败时才按上述两项计数，避免把可恢复的中间错误算成熔断）、
  工具按权限正常拒答（`Deny`/`DenyBrowse`）、用户主动取消、
  以及触发限额熔断本身（否则会形成二次熔断死循环）；
  〔2026-09-05 回写〕实现口径以本条为准，替代此前「工具执行异常」字样；
- 模型路由预留：简单任务用小模型、复杂任务用大模型，在 `ModelAccess/` 内实现，出现成本压力时启用（首版不强制）。

### 决策 9：提示词与模型版本治理

- system prompt、工具描述、工具 schema 均为「提示词资产」，随代码 Git 版本化（现状已入 Git）；
- 模型版本（`Model` 配置）显式锁定，变更走「改 → 跑评估集 → 达标才发布」；
- 任何提示词/工具描述变更视为「模型行为变更」，必须能在评估集上复现与回滚。

### 决策 10：可追溯性与来源引用

- 每条事实性回答必须可追溯到来源：**单据**（`module + _keys`）、**元数据**（表/字段）、**知识库文档**（`sourceUri`）；
- 工具结果带来源标记回喂模型，前端渲染引用链接（点回来源单据/文档）；
  〔2026-09-05 回写〕知识库引用落地为内部引用 `kb://doc/{id}#c{n}` + 服务端二次鉴权后
  的原文对话框（`KbSource.tsx`），比 `sourceUri` 直链更安全：直链会把文档地址暴露给模型
  上下文且无法做点击时权限复核；
- 无法追溯的事实，模型必须明确「我不确定」，不得编造单号/金额。

### 决策 11：失败降级与健壮性

| 场景 | 降级行为 |
|---|---|
| 模型未配置 | `AI_MODEL_NOT_CONFIGURED` 快速失败（已实现） |
| 模型超时/厂商错误 | `AI_MODEL_ERROR` + 可读提示，半截不落库 |
| 工具失败/未知工具 | 回喂模型纠偏，不抛业务异常（已实现） |
| 模型返回空 | `AI_MODEL_EMPTY_REPLY`（已实现） |
| 连续失败 | 熔断（冷却后恢复） |

### 决策 12：跨会话记忆（分层渐进，用户级私有）

**现状**：仅会话内最近 40 条历史，新会话失忆。跨会话记忆让 AI 从「每次都是陌生人」变成「认识你的工作伙伴」，是商用级体验的必要一环。

**三层**（机制/风险递进，详见附录 E）：

| 层 | 内容 | 机制 | 风险 | 触发 |
|---|---|---|---|---|
| L1 用户画像 | 部门、常用模块、显式偏好 | 结构化推导 + 用户设置，非 AI 提炼 | 低 | 随本 ADR |
| L2 显式记忆 | 用户主动「记住」的查询/结论 | 用户显式操作，可增删改 | 低 | 随本 ADR |
| L3 自动长期记忆 | AI 从对话提炼的持久事实/偏好 | AI 提炼 + 置信度 + 用户确认 | 高 | 条件触发 |

**与 RAG 知识库的本质区别**：RAG 是**组织级共享**文档知识（全员/部门/角色可见）；跨会话记忆是**用户级私有**个人事实与偏好（仅本人可见）。即使共用向量检索基础设施，也必须命名空间强隔离。

**安全不变式（跨会话记忆专用）**：

1. `USER_ID` 强制隔离，仅本人可见（同 `ASSISTANT_SESSION` 隔离方式）；
2. 记忆内容涉及业务数据时，**只存「引用」（module + _keys），不存数据快照**；注入时若引用已不在用户当前权限范围，自动失效不注入——防记忆成为权限旁路；
3. 用户可随时查看/修改/删除自己的记忆（「忘记我」能力）；
4. 记忆注入过脱敏；记忆写操作入审计；
5. L3 自动提炼必须带置信度 + 用户确认，低置信度不注入。

### 决策 13：主动能力分级（主动摘要 / 无人值守推送 / 自主任务）

「主动」不是单一能力，按**权限主体**分三级，风险与触发截然不同：

| 能力 | 权限主体 | 触发 | 风险 | 本 ADR |
|---|---|---|---|---|
| 主动摘要（会话内主动） | 使用者 | 用户打开会话 | 低 | 纳入（M3 扩展） |
| 定时主动推送（无人值守） | 服务凭据 + 用户委托 | 定时任务 | 高 | 条件触发，按 ADR-003 §3 |
| 自主多步任务 | 使用者 + 每步确认 | 用户发起 | 中 | 条件触发（阶段 E） |

- **主动摘要**：用户打开助手时，AI 基于画像 + 待办/超期/异常数据，主动给一段可追问的摘要。权限主体仍是用户，走现有工具，零新增风险——这是 B/S 下「主动」体验的正确形态；
- **定时主动推送**：定时任务让 AI 分析数据并推送通知。这是**无人值守自动化**（权限主体 ≠ 人），需服务凭据 + 用户委托（ADR-003 §3），高风险，条件触发。其载体是 **ERP 系统级统一通知中心**——聚合工作流审批待办、报表订阅产出、系统公告、业务预警、AI 推送等全部通知来源；AI 推送仅为其**一个来源**，通知中心不隶属于工作助手。通知中心是系统级基础设施，完整设计不在本 ADR 范围，触发时另立 ADR；
- **自主多步任务**：AI 自主执行多步骤（计划/确认点/恢复）。这是阶段 E 受限自动化，需编排器，而编排器触发即「重评独立编排器」（ADR-007 复审条件）。现阶段 B/S 内不做全自主，最多「用户发起的、每步带确认的多步任务」。

**约束**：本 ADR 仅落地「主动摘要」；定时推送与自主任务均为条件触发，不提前实现（符合 blueprint「条件触发、不提前实现」）。

> **〔2026-09-30 回填〕本决策的「主动摘要」已由 ADR-016 落地**，形态是**打开助手即见的结构化摘要**：
> 规则引擎直接产出、**不经模型**（零 token、零延迟、零幻觉）；来源为**超期滞留 / 此刻办不下去
> （当前校验不过或状态不允许）/ 最近被拒**三类，**待办计数只作辅助**（实测审批流未运行、待办恒为 0，
> 不足以作主来源）；点摘要中任一条触发 `diagnose_record` 追问。「打开助手不得无条件调用模型」这一
> 成本约束同步落地。**定时主动推送（无人值守）与自主多步任务仍未实现**，仍为条件触发，复审条件不变。

### 决策 14：语义层是推断能力的地基（本 ADR 的核心增量）

**问题**：只有工具 + RAG 的助手只能「查到并复述」，无法「算出数据里不存在的结论」。

**判断**：决定推断能力的不是工具数量、不是上下文长度、也不是 RAG 的文档量，
而是**系统里有多少业务关系与计算口径是被显式定义且机器可读的**。

| 要素 | 角色 | 天花板 |
|---|---|---|
| 工具 | 手 | 手再多也不知道「销售额 = SUM(AMOUNT_TAX)」；且工具越多，模型的选择负担越重 |
| 上下文 | 短期工作台 | 只解决单次对话记得住，不解决懂不懂业务 |
| RAG | 参考书（陈述性知识） | ERP 常识通用模型本就懂七八成，**壁垒最低、最易被模型升级追平** |
| **语义层** | **世界观（程序性知识）** | **EOS 独有，通用模型不可能知道，也无法被追平** |

**推断的分层定义**（校准产品目标，评估集据此设计）：

- **检索**：数据里有，找到它；**回答**：数据里有，解释它；
- **推断**：**数据里没有**——需跨多个数据源组合、套用计算口径、再作判断。
  例：「这张订单能按时交付吗」没有任何一张表写着答案，需沿
  「订单 → 明细 → 产品 → 库存 / 在途采购 / 生产工单 → 历史履约率」取数后综合判断。

**既有资产（不要重复建设）**：ADR-009 §P7 已论证语义层的必要性，且 `REPORT_METRIC` 表
已由迁移 027 落地（`METRIC_ID` / `METRIC_NAME` / `DEFINITION` SQL 表达式 / 可用维度 /
业务域 / 版本）。它是「定义一次、多处消费」的登记表种子，但当前仅有 `enum_metrics` 枚举消费，
没有 `resolve_metric` 计算路径，不能把现有 SQL 文本直接视为可执行的安全语义层。ADR-009 引述的外部
证据同样适用于本 ADR：

- 查询准确率随治理层级递进：原始表（低）→ 加 data catalog **40–70%** → 加语义层
  **70–90%** → 再加 tribal knowledge 90–99%；
- Gartner 2025 Hype Cycle 已将语义层列为 **essential infrastructure**；
- **「语义层是分离成功 AI 部署与失败部署的主要干预手段——不是模型选择，不是提示工程，
  也不是基础设施优化」**；MIT NANDA 测得 ~95% 生成式 AI 试点无可衡量 P&L 影响。

**落地口径（硬规则）**：

1. 语义层内容分三部分，均存库、经 DbUp 迁移、对象全大写：
   - **度量口径**：复用 `REPORT_METRIC`（新增口径走迁移，**不新建平行表**）；
   - **流转关系**：`{fromModule} --动作--> {toModule}`，见 M6；
   - **字段关联**：哪些 `*_ID` 是同一实体的不同面孔（跨表连接的事实依据），见 M10；
2. **指标定义的执行边界**：`REPORT_METRIC.DEFINITION` 当前为历史兼容字段，不能直接送入
   `SqlCommand` 执行。`resolve_metric` 必须先把它转换为受控指标 AST 或等价的服务端计划；只允许
   已登记的来源表、物理字段、关联关系、聚合函数、算术函数和维度，所有业务值使用参数。无法通过
   解析、字段/关系校验、维度校验或权限范围编译时，必须拒绝计算。新指标优先直接以结构化定义
   写入；若暂时保留 SQL 文本，只能由开发者通过 DbUp 提交，并在迁移/发布阶段完成同一套验证。
3. **计算必须复用数据边界**：执行计划必须注入当前用户的模块权限、`EXEC_TAG`、`DATA_FILTER`、
   成本/保密字段和其他字段拒绝规则；不能因为指标来自开发者迁移就绕过用户数据权限。结果必须
   返回 `METRIC_ID`、版本、实际来源、维度、过滤摘要和中间值/依据链。
4. **强制走口径**：AI 回答任何涉及金额 / 数量 / 比率的问题时，必须引用 `REPORT_METRIC`
   的定义计算，**禁止模型自行拼表达式或心算**；无对应口径时如实说明
   「该指标在系统内尚无定义」，不得估算；
5. 语义层对 AI 是**只读消费**：不得写入或修改口径定义，口径变更属开发态，走迁移 + code review。

## 附录 A：P0 内省工具组完整契约

全部 `Read` 级、零写副作用。统一遵循：标识符过 `WorkbenchSql.Identifier` 白名单；输出压缩防 token 爆炸；库对象全大写原文；输出回喂模型时「声明非指令」。

### 附录 A 总则：元数据的两个口径（实施前必读）

EOS 的元数据有两个来源，它们**不总是完全一致**，内省工具必须清楚自己在回答哪一个：

| 口径 | 载体 | 提供什么 | 权威性 |
|---|---|---|---|
| 物理结构 | `sys.*` 目录视图（禁 `INFORMATION_SCHEMA`） | 真实存在的表/列/视图/存储过程、数据类型、主键、参数签名 | **对象是否存在的最终事实** |
| 业务语义 | `dbo.TABLES` / `dbo.FIELDS` 字典表 | 中文名（`T_DESC`/`F_DESC`）、是否虚拟字段、成本/保密标记、字段用途 | **业务含义的唯一来源** |

已知的不一致（项目既有现象，不是脏数据）：

- **未纳管**：物理列存在但字典未注册（`FieldAdminTable.UnmanagedCount`，由
  `GetUnmanagedFieldsAsync` 取得）——常见于 DbUp 迁移新建的表，如 `REPORT_FORM_LAYOUT`；
- **幽灵字段**：字典有记录但物理列不存在（`FieldAdminTable.OrphanCount`，
  `FieldAdminFieldSummary.PhysicalExists=false`）。

规则：

1. **存在性以物理口径为准**。AI 回答「这个表/字段存不存在」必须以 `sys.*` 为准；
2. **中文名只存在于字典**。字典未注册的列输出「（无中文名）」，**禁止 AI 臆造中文名**；
3. **两个口径必须同时呈现并标注差异**，不得只给一边——这正是 `describe_table` 同时调
   `GetFieldsAsync` 与 `GetUnmanagedFieldsAsync` 的原因；
4. 工具选型据此分工：`list_tables`（要中文名，走字典）/ `list_views`、`list_procedures`
   （视图与存储过程不在字典内，走 `sys.*`）。

## 附录 B：写能力分级与确认卡片规格

| 级 | 语义 | AI 产出 | 确认方式 | 执行路径 |
|---|---|---|---|---|
| `read` | 查单据/元数据 | 文本 | 无需确认 | 既有工具 |
| `draft` | 草稿替填 | `AssistantFormDraft`（moduleId/title/values/labels/missingRequired/warnings） | 手动采纳 | 前端「带入表单」→ 既有保存管线 |
| `write` | 业务写入草稿 | `SaveRecordRequest` 草稿 | 结构化确认卡片（字段级 diff） | `WorkbenchCommandHandler` |
| `admin-write` | 元数据/菜单/配置变更 | 元数据变更集（JSON） | 变更集 diff + 试算 + CanSetup | `FieldAdminRepository` |

卡片交互（前端渲染，SSE `done` 事件 `drafts` 字段下发）：

- **draft 卡片**：字段级预览（中文标签）+ 缺必填/警告提示 + 「带入表单填写（不自动保存）」按钮；经 `sessionStorage` 一次性通道 `erp-assistant-prefill-{moduleId}` → `FormEditorPage` new 模式消费；
- **write 卡片**：字段级 diff 预览（旧值/新值）+ 「确认提交」按钮 → 调现有 record 保存端点（幂等键/必填/长度/金额复算/审计全复用）；
- **admin-write 卡片**：变更集 diff（新增/修改/删除的字段、模块、数据源）+ form-definition 试算结果 + 「确认执行」→ `FieldAdminRepository` 管理端点 → 自动触发 `workbench-definitions/validate|publish`。

**关键不变式**：AI 只产变更集，不产 SQL、不产新写代码路径；确认永远由人在结构化界面上完成，禁止「好的」这类自然语言放行写操作（ADR-007 §5）。

### M10 复杂度重估与前置条件

M10 不是“读取 `REPORT_METRIC` 后执行 SQL”。迁移 027 的 `DEFINITION` 是自由 SQL 表达式，且种子
数据已经包含聚合、算术、`NULLIF` 和 `COUNT(DISTINCT ...)` 等不同形态。若保留该字段作为兼容输入，
安全实现至少需要完成以下链路：

1. 约定可支持的 SQL 子集，并实现 tokenizer/parser 或等价的结构化转换器；不支持的语法必须拒绝，
   不能静默降级为原文执行。
2. 将表达式转换为受控 AST/执行计划，校验来源表、物理字段、聚合函数、算术函数、关联关系和维度
   白名单；标识符不能由模型或请求参数直接提供。
3. 将当前用户的模块权限、`EXEC_TAG`、`DATA_FILTER`、成本/保密字段和其他字段拒绝规则编译进计划；
   “指标由开发者通过迁移维护”不等于可以绕过用户数据范围。
4. 对每个指标验证聚合粒度、维度组合、空值/除零、重复 JOIN 和主子表重复计数语义；这些属于业务
   正确性，不是普通 SQL 语法校验可以解决的问题。
5. 使用参数化 SQL 执行受控计划，并返回指标版本、实际来源、维度、过滤摘要、中间值和依据链；执行
   失败、口径不完整或结果无法解释时拒答。
6. 为迁移 027 的每个种子指标建立人工确认的期望结果和对账样本；未经业务确认的种子口径只能标记为
   候选，不能作为面向业务用户的可信指标。

因此，M10 分为三个门槛：

- **M10a 可行性探针**：盘点并分类现有 `DEFINITION`，确定受控语法覆盖率；实现 parser/validator，
  只做编译和拒绝，不取业务结果。
- **M10b 最小闭环**：选一项已业务确认的简单指标，完成受控计划、权限注入、参数化取数、依据链和
  越权测试；复杂指标继续拒答。
- **M10c 扩展覆盖**：逐类增加聚合、算术、去重、跨表关系和维度组合，每次新增语法都补回归和业务
  对账；覆盖率不足时维持拒答，不追求兼容所有自由 SQL。

M10 的风险等级为**高**，不得与普通 P0 工具按同一“低风险、立即完成”口径排期。若 M10a 证明现有
自由 SQL 与安全子集差异过大，应停止兼容解析路线，改为迁移中直接维护结构化指标定义；不得为了兼容
存量文本而引入通用 SQL 执行器。

### M7 质量门收口

- 评估集纳入回归（`AssistantEval/` 四目录 + 断言）
- 指标看板（用量/成本/延迟/正确率聚合端点，角色③可见）
- 成本限额 + 熔断落地（全局/用户级日限额、连续失败熔断）
- 验收：达到附录 C 全部默认阈值；越权 = 0 硬门槛。M10 的 parser/validator、指标执行计划和
  业务对账未完成前，不得以 M7 的质量门宣称推断能力可用

### M8a（探针，M8 的轻量前置）

- 范围：只读诊断（「要加 XX 页需哪些表/字段、牵动哪些元数据」）+ 元数据变更集**生成与预览**，
  **不执行任何写入**
- 复用：`FieldAdminRepository` 只读方法（`GetTablesAsync`/`GetFieldsAsync`/`GetModulesAsync`）
  + `form-definition` 试算端点，不新增任何写入路径
- 测试：诊断结果正确、变更集 JSON 结构可校验、确认前零写入
- 验收：能对「加一页需要哪些字段」给出可用的变更集预览，为 M8 是否立项提供实证

### M8（条件触发）admin-write

- 用户拍板启动后：只读诊断（已由 M8a 完成）→ 元数据变更集（JSON 结构）→ form-definition 试算 → 变更集 diff 卡片 → 确认执行
- 测试：变更集结构校验、CanSetup 门、试算失败拦截、确认前零写入
- 验收：顾问试用搭建一个模块/一张表单全流程

## 附录 E：跨会话记忆规格

### E.1 分层语义

| 层 | 触发 | 数据来源 | 注入方式 | 可改删 |
|---|---|---|---|---|
| L1 用户画像 | 自动 | 部门/组从 `SYSDG_USER` 实时推导；常用模块从导航/访问记录推导；显式偏好从 `ASSISTANT_PROFILE.PREF_JSON` | 会话开始时作为 system prompt 结构化前缀注入 | 偏好可改 |
| L2 显式记忆 | 用户主动「记住」 | 用户操作写入 | 会话开始时按 `LAST_ACCESSED_AT` + 关键词相关性取 top-K ≤ 5 注入 | 可增删改查 |
| L3 自动长期记忆 | AI 提炼（条件） | 会话结束提炼，`STATUS=pending` 待确认 | 仅 `STATUS=active` 且命中注入 | 可改删，pending 可拒绝 |

### E.2 数据模型（DbUp 迁移，全大写）

`ASSISTANT_PROFILE`：`USER_ID`（PK）、`PREF_JSON`（nvarchar(max)）、`UPDATED_AT`。

`ASSISTANT_MEMORY`：`ID`（bigint PK）、`USER_ID`（nvarchar，隔离索引）、`MEMORY_TYPE`（nvarchar：preference/fact/favorite）、`MEMORY_KEY`（nvarchar）、`MEMORY_VALUE`（nvarchar(max)）、`SOURCE`（nvarchar：manual/auto）、`SOURCE_MESSAGE_ID`（bigint null，溯源）、`CONFIDENCE`（tinyint null，0-100）、`STATUS`（nvarchar：active/pending/archived）、`CREATED_AT`、`UPDATED_AT`、`LAST_ACCESSED_AT`。

### E.3 注入与权限

- 注入组装在 `ChatService.BuildModelMessages`：先画像前缀，再取 top-K ≤ 5 条 `STATUS=active` 记忆按相关性注入，全部标注「这是关于你的持久记忆，可能已过期，仅参考」；
- 记忆值若含业务数据引用（`module + _keys`），注入前校验该引用仍在用户当前权限范围（`IPermissionService` + `DATA_FILTER` 同源复核），失效则跳过不注入；
- 记忆 CRUD 全部 `USER_ID` 强制隔离；写操作入 `AUDIT_EVENT`；记忆值过现有 redact 脱敏后落库。

### E.4 与 RAG 的关系

- RAG 知识库 = 组织级共享（集合可见性：全员/部门/角色）；跨会话记忆 = 用户级私有（仅本人）；
- 若共用向量库，必须按「知识库命名空间」与「用户记忆命名空间」强隔离，检索时按调用场景限定命名空间，禁止跨区召回。

### E.5 记忆生命周期与容量

- 每用户记忆条数上限 200 条（默认），超出按 `LAST_ACCESSED_AT` LRU 淘汰至 `archived`；
- 记忆默认长期有效；L3 提炼的临时性事实（如「本月」类）由提炼时判定是否设 TTL；
- 删除 = 软删除（`STATUS=archived`），保留审计；硬删除仅「忘记我」触发。

### E.6 L3 自动提炼机制（条件触发后启用）

- 提炼时机：会话结束（`done` 事件后）异步提炼，不阻塞对话流；
- 提炼输入：先由模型生成**对话摘要**，再从摘要提炼记忆（两步控制成本），非全量对话；
- 提炼输出：候选记忆列表，每条含 `{type, key, value, confidence, reason}`；
- 置信度阈值：`≥80` 自动转 `active`（覆盖同名），`40–79` 进 `pending` 待用户确认，`<40` 丢弃
  〔2026-09-05 用户拍板〕；
- 去重/合并：按 `MEMORY_KEY` 精确比对，同名确认时覆盖（旧 active 归档）、拒绝时归档候选；
  语义相似比对暂不做〔2026-09-05 回写：在无向量检索前，相似度判定不可靠，精确键覆盖已满足闭环〕；
- 冲突：新旧记忆矛盾时标记「冲突」，用户确认时选覆盖或保留。
  〔2026-09-05 回写〕当前实现为「确认即覆盖、拒绝即归档」，冲突明细展示与 TTL 判定、
  两步摘要（先摘要再提炼）暂缓：单次提炼直接消费最近 10 轮原文，成本与效果待真实用量后评估。

### E.7 记忆检索与注入

- L1 画像：固定结构化注入（成本低、确定性）；
- L2/L3 记忆：M5 前用 `MEMORY_KEY`/`MEMORY_VALUE` 关键词 LIKE 匹配，M5 后用向量语义检索（用户级命名空间）；按「新鲜度 + 相关性」排序取 top-K ≤ 5；
- 注入格式：每条标注「这是关于你的持久记忆（来源：显式/自动，可能已过期，仅供参考）」，弱化权威性防模型盲信。

### E.8 隐私与「忘记我」

- 落库前 PII 扫描：命中手机号/身份证/银行卡等正则，自动提炼直接拒绝、显式记忆提示用户确认风险；
- 「忘记我」：一键删除该用户 `ASSISTANT_PROFILE` + `ASSISTANT_MEMORY` + 向量索引，事务保证；审计仅留「操作发生」痕迹，不存记忆内容。

### E.9 记忆 UI/交互

- 记忆管理页（EOS.Web 内）：列表查看/编辑/删除/类型筛选；
- 提炼确认卡片：会话结束后若有 pending 记忆，下次打开提示「AI 想记住这些，是否确认」（批量确认/拒绝）；
- 注入可见性：助手回复标注「使用了 N 条记忆」，可展开查看（用户知道 AI 用了哪些记忆）。

## 选择理由

- 权限主体 = 使用者，复用 `IPermissionService`/`ModulePermission`，不引入第二套身份或服务凭据；
- 语义 Skill 层复用底层权限/取数，避免「为 AI 重写数据访问」的权限旁路与双份维护，同时补齐「EOS.Web 接口不适合喂模型」的缺口；
- 四类知识四机制，各匹配「实时性/可版本化/权限保证」；**语义层单独成类**，因为它是推断能力的地基（决策 14）；
- 语义层不新建平行设施：复用 ADR-009 §P7 已落地的 `REPORT_METRIC`，避免系统内出现第二套口径定义；
- 权限口径分层把「授权放大」堵在工具层，与 ADR-007 §5 安全不变式一致；
- 横切面治理（评估/成本/版本/追溯/降级/记忆）是「商用级可信可用」的必要条件；
- 跨会话记忆分层渐进：L1/L2 确定性、低风险先做，L3 高风险的 AI 自动提炼条件触发，且以「引用而非快照」防权限旁路；
- 写能力沿用「变更集 + 既有管线」，AI 不产生任何新写代码路径。

## 考虑过的替代方案

- **方案 A：复用 EOS.Web 接口直接喂模型**：未选——页面契约与推理契约不匹配；
- **方案 B：把 schema 静态塞进 system prompt**：未选——过期、超限、无法按权限裁剪；
- **方案 C：AI 直接生成并执行 SQL**：未选——违反 ADR-007 §5，易产生幽灵字段；
- **方案 D：为 AI 单独建一套数据访问与权限**：未选——权限旁路 + 双份维护；
- **方案 E：一次性建设完整 Agent 平台/Skill Registry/MCP/Plugin**：未选——阶段 F 条件触发，当前只有一个真实场景；
- **方案 F：RAG 维持 ADR-002 的「独立 EOS.Console + 阶段 C 前置」**：未选——用户拍板 RAG 纳入本 ADR 统一落地；
- **方案 G：跨会话记忆一步到位做 AI 自动提炼（跳过 L1/L2）**：未选——自动提炼有污染/越权/过期风险，应先以确定性画像与显式记忆验证记忆链路的注入、隔离、遗忘闭环，再上高风险提炼。

## 结果与影响

### 正面影响

- AI 从「能查单」升级为「认识系统 + 认识你 + 可信可用」；
- **语义层让 AI 具备推断能力**（决策 14）：从「复述数据里有的」到「算出数据里没有的」，
  这是本 ADR 与「套壳聊天框」的分界，也是通用模型无法追平的部分；
- 度量口径统一化目标：AI 与报表共同消费同一份经校验的 `REPORT_METRIC` 定义，避免「AI 算的销售额和报表不一样」；在 `resolve_metric` 和报表侧均完成受控执行前，不宣称该目标已经实现；
- 确立「专门为 AI 开发接口」的长期原则，后续 Skill 有统一契约范式；
- 质量门 + 成本限额 + 版本治理，让「商用」有可量化验收与运维抓手；
- 权限口径分层 + 越权评估集（硬门槛 0）+ 记忆「引用而非快照」，把越权风险堵在工具层与记忆层并持续回归。

### 成本与风险

- P0/P2/记忆 L1/L2 复用现成能力，风险低；P1 引入向量库组件与 embedding 路线（选型/部署成本）；
- P3 与记忆 L3 最高风险，条件触发、分步执行；
- 评估集建设与维护是长期投入（初期从「顾问试用 + 真实提问」沉淀）；
- 每新增 Skill 带权限门单测，测试面扩大；记忆层增加隔离/脱敏/审计面。

## 复审条件

- 出现第二个真实 AI 场景需多供应商路由/租户级计费/独立扩缩容 → 重评独立网关；
- 需要无人值守自动化 → 按 ADR-003 §3 服务凭据 + 用户委托方案重开；
- 出现第二个真实业务域或第三方扩展需求 → 触发阶段 F 平台化，另立 ADR；
- 内省 Skill 数量膨胀或语义契约重复 → 重评语义 Skill 层是否需抽象共享 base/SDK；
- 记忆规模膨胀或检索质量下降 → 重评记忆是否需要独立向量命名空间与生命周期治理；
- 默认阈值经真实数据校准后需上调/下调 → 走评估集回归后更新本 ADR 附录 C。
- **推断评估集长期不达标**（跨源规划能力不足）→ 重评是否需要显式规划器（先规划后执行），
  而非继续堆工具；工具数量增长本身即为该重评的触发信号。
- 语义层内容膨胀（度量/关系条目过多）→ 重评语义层是否需命名空间与生命周期治理，
  并与 ADR-009 §P7 合并讨论（两者消费同一份口径定义）。
