## 0. 现状实测（2026-09-24，连 `EOS.ERP` 直查）

### 0.1 页签实际承载的配置规模

| 项 | 实测 |
|---|---|
| `MODULES` 行数 | 544，其中 **88** 个是无主表也无副表的纯菜单节点 |
| `MODULE_BUSINESS_ACTION` | **341** 行 = 326 条效果动作 + **15 条自定义按钮**，覆盖 **110** 个模块 |
| `MODULE_BUSINESS_ACTION_OP`（公式行） | 633 行 |
| `MODULE_VALIDATION_RULE` | 187 行，覆盖 96 个模块 |
| 单模块最大 | `1406 送货单`：12 条效果 / 41 条公式行 / 4 条规则 |
| 自定义按钮分布 | 12 个模块（`130101` 三个，`1502` 两个，其余各一个） |

⇒ **"页太重"不是假想**：最大模块的配置区要在同一条竖向滚动链里呈现 12 条动作 + 41 条公式行 + 4 条规则，
且动作、规则、按钮三件不同心智的事挤在一起。

### 0.2 唯一键（决定 SEQ 口径，也决定误实现会怎么炸）

```
UQ_MODULE_BUSINESS_ACTION_EVENT (MODULE_ID, EVENT_CODE, SEQ)
```

⇒ 顺序号是**按 (模块, 事件)** 唯一的，不是按模块唯一。任何"新增按钮时接在动作列表最大序号之后"的实现
都会撞这个唯一键，并在保存时报数据库错误（见 §4.2-B3）。

### 0.3 权限现状（§5 选档位的依据）

| 项 | 实测 |
|---|---|
| 2301 直接授权 | `SYSDD` **1** 行（admin；`SETUP_TAG=1`、`FORM_DESIGN_TAG=1`） |
| 2301 组授权 | `SYSDH` **1** 行（组 1；`SETUP_TAG=1`） |
| 波及面 | 1 个用户 + 1 个组 |
| 2312 / 2313 是否空号 | `MODULES` / `SYSDD` / `SYSDH` **均 0 行** ⇒ v1 的空号结论成立 |
| 2301 同域兄弟 | 挂在 `23` 下：2304 / 2305 / 2306 / 2308 / 2309 / 2311；挂在 `2311` 下：2302 / 2303 / 2307 |
| 自定义按钮授权 | `SYSDD_BUTTON` 15 行 / 12 模块；`SYSDH_BUTTON` **0 行**；每个按钮恰好 1 个用户、0 个组 |

⇒ 授权面确实很小（§6.1 的判断成立），但也意味着**任何分权动作都要给 admin 补一次授权**，否则连自己也进不去。

### 0.4 既有的"模块内能力位"先例（§5.2 的依据）

`SYSDD` / `SYSDH` 上已经有两列**不是模块级动作、而是能力级**的权限位：

- `FORM_DESIGN_TAG`（完整版式设计）、`FORM_ADJUST_TAG`（微调）；
- 由 ADR-010 引入，迁移 `031_report_form_layout.sql`（加列 + 默认 0 + 说明）；
- 读侧门在 `ReportFormLayoutRepository.GetDesignerModeAsync`——**与其它位同一套语义**
  （个人行覆盖组行、组间布尔 OR），正是 §5 需要的形态；
- **但**这两个位目前只能直接改库授予：权限矩阵的写白名单 `RightsColumnWhitelist.BitColumns`
  不含这两列，前端 `rights-admin/types.ts` 的位清单也没有它们。

⇒ **"在模块内加能力位"这条路本仓已经走通过一次，缺的只是"授予通道"这一环。**这句话是 §5.2 的全部依据。

## 1. 问题

1. **页太重**：2301 一个页面承载菜单树、模块基本信息、ADR-012 的效果动作/公式行/校验规则、
   ADR-018 的自定义按钮、授权镜子、发布入口。**难找、难教**（规模见 §0.1）；至于"打开慢"——
   行为动作区是**按页签懒挂载**的（`MenuAdminPage.tsx` 只在 `formTab === 'actions'` 时渲染
   `BusinessActionsPanel`），页面打开成本主要来自左侧菜单树与模块列表，**本决策并不解决"打开慢"**，
   只在 §4.2-B4 顺手改善该页签内部的一次性请求。
2. **权限太粗**：上述能力的读写门全挂在 2301 的 `CanSetup` 上，要"一般管理员不给配置权、只给实施顾问"
   做不到——给了 2301 就是全给。本次不解决，但 §5 把可选路径补全。
3. **"拆模块"的成本远高于 UI 拆分本身**（实证见 §3）：v1 方案真正的成本不在三页界面，而在拆权限单元后
   被迫连带改造的三条隐藏写路径。

## 2. 决策（2026-09-24 改判）

**留在 2301，页签按"谁触发"划分**；模块号、权限门、写端点、表结构一律不动。

### 2.1 页签划分

现有页签：`基础 / 主表 / 子表 / 分组 / 统一表单 / 行为动作`（`MenuAdminPage.tsx:43-50`）。
前五个不动，最后一个拆成三个：

| 分组 | 页签 | 内容 | 落库 |
|---|---|---|---|
| 定义 | 基础 | 菜单名称、承载页 URL、图标、帮助、启用 | `MODULES` 行 |
| 定义 | 主表 / 子表 | 表名 + 默认查询列（现状"默认列"弹窗） | `MODULES` + `SYSQL_DEFAULT` |
| 定义 | 分组 | `GROUP1~5` 查询分组 | `MODULES` |
| 定义 | 统一表单 | `FORM_TABS` / `FORM_COLUMNS` / `FORM_BUTTONS` | `MODULES` |
| 行为 | **行为动作** | 非 `MANUAL` 的效果链 + 公式行 + 参数/条件/反向 + 影响面 + 克隆 | `MODULE_BUSINESS_ACTION`（非 `MANUAL`）+ `_OP` |
| 行为 | **校验规则** | 校验规则列表与编辑器（现状面板内第三个 section） | `MODULE_VALIDATION_RULE` |
| 行为 | **自定义按钮** | `MANUAL` 行 + 按钮参数表单 + 授权镜子 | `MODULE_BUSINESS_ACTION`（`MANUAL`） |

### 2.2 划分原则

1. **按触发者分**：系统触发的效果 / 拦截的校验 / 用户点击的按钮；三者心智、落点、授权模型都不同。
2. **不按技术分层分**：公式行、参数、条件、反向都依附于某个具体动作，独立成页签会失去上下文，反而难用。
3. **常一起改的相邻**：配了库存扣减通常紧接着配数量校验，故顺序为 行为动作 → 校验规则 → 自定义按钮。
4. **页签只切视图，不切保存单元**：三个行为页签共享同一份草稿，仍汇总到一次 `PUT /admin/menus/{id}`
   的 `businessConfig`（§4.2-A3）。这条别动——一动就回到 v1 的分段保存坑（§6.2）。
5. **命名不得与既有概念撞车**：`MANUAL` 行是"自定义按钮"，`FORM_BUTTONS` 是"内置动作（受控注册码）"，
   两者在单据工具栏上都会出现，但来源、授权模型完全不同（§4.2-B5）。

## 3. 为什么放弃"三分模块"（实证）

v1 的界面拆分只需搬组件，真正贵的是拆出权限单元后被迫连带改造的三条隐藏写路径（均已核实现状代码）：

1. **动作与按钮同表，替换语义要按事件范围重写**：二者都在 `MODULE_BUSINESS_ACTION`，
   由 `EVENT_CODE = 'MANUAL'` 区分；现有保存是按 `MODULE_ID` 全表 `DELETE` 再整插
   （`ModuleBusinessConfigRepository.cs:187-210`）。拆成两个写端点而沿用这套语义，
   **2312 保存会抹掉全部按钮、2313 保存会抹掉全部效果**。
   补一条硬事实：唯一键是 `UQ_MODULE_BUSINESS_ACTION_EVENT (MODULE_ID, EVENT_CODE, SEQ)`（§0.2），
   所以"按事件分段替换"是**物理上可行**的，但必须显式写进 SQL 条件，不能靠"顺手加个 WHERE"。
2. **第二条写路径**：`PUT /admin/menus/{id}` 也带 `businessConfig` 同事务写动作/规则/按钮
   （`MenuAdminRepository.cs:463-520`），且这才是 UI 唯一在用的写路径（独立
   `PUT /admin/module-business-config/{id}`（`ModuleBusinessConfigController.cs:139-148`）
   前端零调用——全仓检索只有 GET）。不摘掉它，拆了端点也还是假分离。
3. **模块选择口的门都写着 2301**：模块列表 `GET /admin/menus`（`MenuAdminController.cs:159`）与
   选择器 `menu-admin.modules`（`ChooserRepository.cs:15,226`）的门都硬编码 2301，
   收紧后只有 2313 权的人选不到模块，新页是死的。

回到单模块 + 页签：三条**全部不需要做**，权限门仍是 2301 `CanSetup`，写路径仍是"整份随模块保存"。
工作量从"迁移 + 端点拆分 + 权限门 + 三页"降为"一个页面内部的视图切分 + 组件拆分"。

## 4. 设计（多页签方案）

### 4.1 页签内容边界

- **行为动作**：`ActionSection`（非 `MANUAL`）+ 选中动作的公式行 `OpSection` + 影响面自检 + 克隆入口。
- **校验规则**：`RuleSection` 独立成页签（现状与动作列表垂直堆叠在同一滚动区，是"页太重"的直接来源）。
- **自定义按钮**：`MANUAL` 行专用表格，列建议 = 顺序号 / 按钮键（下拉，取 `DocumentActionRegistry` 键集）/
  标题 / 落点（单据级/明细级）/ 需确认 / 启用 / 可点人数·组数（授权镜子直接进表，不必再靠 alert）。
  授权镜子数据（`GET /{moduleId}/action-authorization`）**随本页签懒加载**，不要三个页签共享——
  实测每个按钮目前恰好 1 个用户 / 0 个组（§0.3），信息量小，没必要为它拖慢动作页签。
  > 实施口径（2026-09-24）：表格本身只读展示，新增/编辑仍走既有动作编辑器（`ActionSheet` 已支持
  > `MANUAL` 行的按钮键下拉、标题、二次确认与入参声明），工具条 + 弹窗而非表格内联控件——
  > 与"只搬家不重写"一致；按钮键与落点的下拉项来自服务端 `documentActions` 目录，前端不硬编码键集。

### 4.2 实施要点

v2 把下面两类混在一张清单里，并声称"只搬家不新增行为"——两者矛盾。现按性质分栏：
**A 类只搬不改行为，B 类会改行为，必须各自带用例。**

#### A. 纯搬家（不改行为，验收 = 既有用例全绿 + 快照无变化）

1. **组件拆分**：`BusinessActionsPanel` 拆成容器 + 三个页签视图，共用现有编辑器
   （`ActionSheet` / `StructuredParamsEditor` / `ConditionEditor` / `DocumentActionParamsEditor`），只搬家不重写。
2. **页签接入**：扩展 `MenuAdminPage` 的 `MENU_FORM_TABS`，按 §2.1 顺序排列。
3. **单一草稿源 + 容器常驻（关键约束）**：`configQuery` 与 `actions` / `rules` 两个 state 必须留在
   **不随三个行为页签卸载的容器**里，由三个页签共享；`enabled` 用"是否已进过任一行为页签"的布尔驱动，
   **不要用页签的挂载/卸载驱动**。理由：现状 `BusinessActionsPanel` 是被 `formTab === 'actions' &&` 条件渲染的
   （`MenuAdminPage.tsx:1223`），一旦卸载重挂，装载副作用会拿服务端缓存数据重置本地草稿
   （`BusinessActionsPanel.tsx:296-301` 之后紧接着 `309-316` 上报），**未保存的编辑会被静默清掉**。
   拆页签时如果照搬"一个页签一个组件、各自挂载"，等于把 B1 的缺陷复制三份。
4. **切换模块 / 关闭编辑时提示未保存**：`selectModule`（`MenuAdminPage.tsx:845-849`）现在直接切换、
   不提示；草稿脏时补确认。

#### B. 行为变化（每条都要有对应用例，不能只靠 A 类基线）

1. **切页签保草稿（其实是修缺陷，不是防新风险）**：见 A3。这条**与页签拆分无关，现在就是坏的**——
   从「行为动作」切到「基础」再切回来，未保存的动作编辑会被静默丢弃，且状态徽标会从"已修改未保存"
   退回"已保存未发布"，用户看不出发生了什么。建议**先独立修**（§7.1），再拆页签。
2. **克隆只带非 `MANUAL` 行**：按钮授权（`SYSDD_BUTTON`/`SYSDH_BUTTON`）不随配置跨模块带走，
   克隆过去就是一批没人能点的按钮，失败还很安静。现状确实没过滤：
   `CloneActionsModal.tsx:50-53` 取全部 actions，`BusinessActionsPanel.tsx:476-487` 原样追加。
   **同样是独立缺陷**，不拆端点也能修，先做。
3. **`MANUAL` 组内编号**：新增按钮的序号在 `MANUAL` 组里顺延，不要沿用动作列表的最大序号
   （依据 §0.2）。现状 `BusinessActionsPanel.tsx:428` 已经是"同 `eventCode` 取 max + 1"，**这条是"别改坏"**，
   不是"要做的事"；拆组件时最容易丢的就是这一行。
4. **影响面自检与关系边改懒查询**：现状 `BusinessActionImpact` 恒挂在面板里
   （`BusinessActionsPanel.tsx:705`），其 `/relations` 查询只按"草稿里有目标表"启用
   （`BusinessActionImpactPanel.tsx:60-73`）——也就是说，**用户根本没展开影响面，请求已经发了一轮**
   （每个目标表一个请求，再加大模块如 1406 的目标表数）。改为展开时才查。
   > 实施口径（2026-09-24）：展开前状态徽标不给出通过/失败结论（显示中性的「展开后自检」，
   > 并说明"定位键与系统开关的登记校验在展开后补做"），本地可判的阻断项照旧列出；
   > 远端数据到齐后才显示「N 项会拦住保存 / 无阻断项」。理由：`analyzeImpact` 在拿不到关系边与
   > 系统参数目录时会**跳过**对应检查，若照旧显示"无阻断项"就是让懒加载变成误报。
5. **两个"按钮"必须区分命名 + 交叉指引**：统一表单页签的 `业务按钮（FORM_BUTTONS）`
   （`MenuAdminPage.tsx:1213-1218`）是**受控注册码**（批核/结案等内置动作），与自定义按钮
   （`MANUAL` 行、键来自操作注册表、fail-closed 授权）是两套东西。前者改名"内置动作（受控注册码）"；
   另外**两处互加一句指引**（"另有 N 个自定义按钮，见 行为 › 自定义按钮"）——因为用户真正的问题是
   "这张单的工具栏上会有哪些按钮"，而答案在页签化之后被分到了两个不同的页签组。
6. **空态与禁用**：无主/副表的目录节点（实测 88 个，§0.1），三个行为页签禁用并说明原因
   （现状 `hasTables` 只在面板内判断，页签进得去但空转；拆成三个页签后会有三个空转页）。
7. **发布入口不变**：仍为页面内 `POST /admin/module-business-config/{id}/publish`（2301 `CanSetup`），
   不新增也不收紧发布门——v1 §8.1 的待决项随之作废。
8. **授权镜子只是只读**：真正的授予在「用户权限设定 / 用户组管理」的按钮权限页签写
   `SYSDD_BUTTON`/`SYSDH_BUTTON`，页面上要点明去向（现状文案已写，保留）。

### 4.3 保持不变

写端点与权限门（2301 `CanBrowse` / `CanSetup`）、保存语义（模块 + 业务配置 + 默认列同事务）、
配置表结构、发布机制、模块号与迁移——**本次一律不动**。

## 5. 权限分权：三档口径

v2 只讨论了头尾两档，把"放弃真分权"写成了终点；v3 补出中间档并**已拍板采用**（2026-09-24 晚，用户）。

| 档 | 形态 | 代价 | 状态 |
|---|---|---|---|
| **A** | 2301 一把锁：`CanSetup(2301)` 管全部配置能力 | 0 | 已被 B 取代 |
| **B** | 模块号不变，2301 上加能力位 `MODULE_CONFIG_TAG`，与 `SETUP_TAG` **各管一块** | 1 迁移 + 3 处清单 + 2 处门 | **已拍板并已实施（§5.2）** |
| **C** | 拆 2301 / 2312 / 2313 三个模块号 | 迁移 + 端点拆分 + 三处权限门 + 三页（§3、§6.2） | 已搁置（§6） |

### 5.1 拍板记录（2026-09-24 晚）

用户就 §5.2 的三项一次性拍板：① **加**这个开关；② 新老开关**各管一块**；③ 库里现有的
admin 与组 1 **全勾上**。A 档随之作废，C 档仍搁置。

### 5.2 B 档：模块内能力位 `MODULE_CONFIG_TAG`

**位定义**：`SYSDD` / `SYSDH` 各加一列 `MODULE_CONFIG_TAG BIT NOT NULL DEFAULT 0`，
语义 = "**可配置该模块的业务动作 / 校验规则 / 自定义按钮**"。与 `SETUP_TAG` 并列，互不替代。
形态照 ADR-010 的 `FORM_DESIGN_TAG`（迁移 `031`，读侧门 `ReportFormLayoutRepository.GetDesignerModeAsync`）
复制——那一次证明了这个形态在本仓的权限语义下是成立的（个人覆盖组、组布尔 OR）。

**分工（"各管一块"）**：

| 面 | 内容 | 门 |
|---|---|---|
| 基础信息 | 菜单名称/URL/图标/帮助、启用停用、排序、移动、删除、默认查询列 | `SETUP_TAG(2301)` |
| 配置面 | 效果动作 / 校验规则 / 自定义按钮 / 发布 | `MODULE_CONFIG_TAG(2301)` |

**端点 → 门 映射（实施口径）**：

| 端点 | 现有门 | 改为 |
|---|---|---|
| `GET /admin/menus`、`/tables`、`/fields`、`/{id}`、`/{id}/versions`、`/{id}/default-columns` | `CanBrowse` | 不变 |
| `POST /admin/menus`；`PUT /{id}` 的 `module` 段 | `CanSetup` | 不变 |
| `PUT /{id}/rename`、`/enabled`、`/sort`、`/move`、`/{id}/default-columns`；`DELETE /{id}` | `CanSetup` | 不变 |
| `PUT /admin/menus/{id}` 的 `businessConfig` 段 | `CanSetup` | `CanSetup` **AND** `MODULE_CONFIG_TAG` |
| `GET /admin/module-business-config/**`（含 `meta`/`schemas`/`field-labels`/`relations`/`action-authorization`） | `CanBrowse` | `CanBrowse` **AND** `MODULE_CONFIG_TAG` |
| `PUT /admin/module-business-config/{id}` | `CanSetup` | `CanSetup` **AND** `MODULE_CONFIG_TAG` |
| `POST /admin/module-business-config/{id}/publish` | `CanSetup` | `CanSetup` **AND** `MODULE_CONFIG_TAG` |

**为什么配置面写是"两门都要"**：写入口唯一，`PUT /admin/menus/{id}` 在**同一事务**里写
"模块行 + 业务配置 + 默认列"（`MenuAdminRepository.SaveAllAsync`），一个请求可能同时改两块，
故按**载荷分段**判权：`businessConfig` 段要新位、其余段要 `SETUP_TAG`。由于前端总是携带 `module` 段，
实际效果就是两门都要。**已知边界**：因此"只有配置权、没有设置权"的账号目前**能读不能存**。
要支持这个角色必须拆写端点——那正是 §6 C 档的成本，**当前无此需求，不提前做**。
（真要支持时的做法：把 `SaveMenuModuleRequest.Module` 改为可空 = "不动模块行"，端点门放宽为
`SETUP OR MODULE_CONFIG_TAG`，再按段判——与 `BusinessConfig`/`DefaultColumns` 现有可空语义一致。）

**"各管一块"正好满足原始诉求**：`SETUP=1, CONFIG=0` 的一般管理员能改菜单名/URL，动配置一律 403；
`SETUP=1, CONFIG=1` 的实施顾问全能。

**授予通道（ADR-010 当年漏掉的那一环，本次做齐）**：
- 后端：`RightsColumnWhitelist.BitColumns`、`ModuleRightsInput` / `ModuleRightsRow` /
  `EffectiveModuleRights` / `ModuleRights`、`RightsAdminLogic`（空值判定与聚合）、
  `RightsAdminRepository`（读写列）；
- 前端：`rights-admin/types.ts` 的位清单与标签（矩阵勾选框由该清单驱动）。
- 该位对其它模块是空转（服务端只在 2301 读它）；矩阵上仍会出现在每一行，与 `FORM_*_TAG` 同样处理。

**回填（拍板：全勾上）**：迁移把 2301 现有 2 行（`SYSDD` admin / `SYSDH` 组 1）的
`MODULE_CONFIG_TAG` 置为其 `SETUP_TAG` 值（实测当前均为 1）⇒ 迁移生效当天现有配置者不受影响。
其余模块行一律默认 0。

**页面行为**：无该位时，2301 的三个配置页签（行为动作/校验规则/自定义按钮）**不渲染**
（fail-closed，与 ADR-018 "未获授权不渲染"一致），而不是渲染出来、保存时才 403。
前端权限清单目前只有 `legacy-module.{id}.read`（`ApplicationController.cs:44`），
故实施时新增一处能力下发供页面判断。

## 6. 备选：三分模块（2301 / 2312 / 2313）——**已搁置**

> 已拍板后改判（2026-09-24）；保留的原因是这些结论来自实证，将来启用不必重查。
> **本节的编号与空号结论均为 2026-09-24 快照，启用时须重核**（迁移号已用到 227，且模块号会被
> 其它需求占用），不要照抄。

### 6.1 方案要点

| 模块 | 名称 | 路由 | 管辖 |
|---|---|---|---|
| 2301 | 模块管理 | `/admin/menus` | 菜单树 + 模块基本信息 |
| 2312 | 行为动作管理 | `/admin/module-actions` | 效果动作（含公式行）+ 校验规则 + 参数 Schema + 关系边 |
| 2313 | 自定义按钮管理 | `/admin/document-buttons` | `MANUAL` 按钮行 + 参数表单 + 授权镜子 |

- 2312/2313 为纯定制页（同 2301、2305/2306 形态）。**2312/2313 经核实为空号**
  （2026-09-24 实测：`MODULES`、`SYSDD`、`SYSDH` 均 0 行）；**启用时重核**。
  不用 2302/2303（已占用：2302 数据表/字段维护、2303 读写数据表信息）。
  同域现状（2026-09-24 实测）：2304 单据性质设定、2305 用户组管理、2306 用户权限设定、
  2307 数据库备份、2308 工作任务记录、2309 数据维护、2311 数据表维护。
- 父 `23` / 根 `23`，`NEW_URL`/`MODI_URL` 为空；bit 标志位逐列复制 2301（同域兄弟复制法，参考迁移 187）；
  `SORT_IDX` 按同级末尾追加。迁移编号**取启用当时的最新 + 1**（187 / 207 是写法参考）。
- 权限：`SYSDD`/`SYSDH` 复制 2301 现有行（**实测 2026-09-24：各 1 行，均带 `SETUP_TAG`**）；
  复制后须给现有 admin 补授权，否则连自己都进不去。

### 6.2 启用时必须同时做的三条（否则分离是假的）

1. 写端点按"动作 / 规则 / 按钮"拆开，且替换改为**事件范围**：动作段 `EVENT_CODE <> 'MANUAL'`、
   按钮段 `EVENT_CODE = 'MANUAL'`；三段各自保存与标脏（不能共用整份替换入口）。
   单测覆盖双向不穿透：2312 保存后 `MANUAL` 行数不变，2313 保存后非 `MANUAL` 行数不变。
   依据 §0.2 的唯一键，分段替换在物理上是合法的。
2. 摘除 `SaveMenuModuleRequest.BusinessConfig`（`PUT /admin/menus/{id}`），连带
   `WorkbenchDefinitionValidator` 中对应段落；审计动作名区分 `SAVE_ACTIONS` / `SAVE_RULES` / `SAVE_BUTTONS`。
3. 模块选择口补"任一门"（2301 / 2312 / 2313 任一 `CanBrowse` 通过）：模块列表与选择器
   `menu-admin.modules` 的门当前都硬编码 2301（`ChooserRepository.PermissionModuleId` 返回单个 `int?`）。
   验收：仅持 2313 权的账号能独立完成"选模块 → 改按钮 → 保存"。
4. 配套：删除整份 `GET {id}`/`PUT {id}` 时，`CloneActionsModal` 需改为读两个端点。

### 6.3 当时未决的三项（启用时再定）

1. **发布门归属**：`POST /api/v1/workbench-definitions/publish` 门为 `PermissionModules.SystemManagement`
   = 2306（`WorkbenchDefinitionController.cs:67`；2306 = 用户权限设定 `/admin/users`，
   该常量指"以 2306 为门的系统级管理动作"，不是模块名），前端无调用方（实测：全仓唯一发布调用是
   2301 页内那个，`MenuAdminPage.tsx:536`），实际由 `publish-workbench-snapshots.ps1`、
   `republish-all-whitelist.ps1` 等脚本使用。
   方案 A（推荐）保留入口、门统一为 2306；方案 B 页面内不发布只标脏；**不选**"2312 或 2313 `CanSetup`
   即可发布"（会新增一档可对任意 `moduleId` 的发布授权，与分权目标相反）。
2. **2313 是否独立成权限单元**：若现实里没有"只配按钮、不配效果链"的角色，可只拆 UI 与写端点、
   门复用 2312，省掉一整套长期维护（多一个模块号 = 多一行授权 + 菜单 + 路由 + 文档）。
3. **权限默认值**：全复制（连续性优先）vs 最小集合（新能力默认关闭，要给人是加法）。
   ——同一个问题在 §5.2 B 档回填能力位时还会遇到。

## 7. 落地步骤

> v2 是"测试基线 → 拆分 → 接入 → 草稿 → 细节 → 回归"一条链。问题是这条链里混着**独立缺陷**和
> **页签搬家**——前者与页签无关，后者才是本 ADR 的主体。混在一起做，一次改动既改行为又搬结构，
> 回归失败时定位成本翻倍。故拆成两段。

### 7.1 第一段：独立缺陷修复（与页签无关，可先做、可独立验收、各自一个提交）

1. **克隆过滤 `MANUAL`**（§4.2-B2）+ 用例：克隆后本模块 `MANUAL` 行数不变。
2. **切页签/切模块保草稿**（§4.2-B1、A3）+ 用例：改一条动作 → 切走 → 切回，草稿仍在且脏标记保持。
3. **影响面自检与关系边改懒查询**（§4.2-B4）+ 用例：不展开影响面时不发 `/relations`。
4. （可选，成本极低）**两个"按钮"的命名与交叉指引**（§4.2-B5）。

> 这四条的收益与页签方案完全解耦：无论页签最终拆不拆、怎么拆，它们都不白做。

### 7.2 第二段：配置权开关（B 档；2026-09-24 拍板，先于页签搬家落地）

1. **迁移**：`SYSDD` / `SYSDH` 加 `MODULE_CONFIG_TAG`（照 `031_report_form_layout.sql` 的写法）
   + 回填 2301 现有 2 行 + 断言；干跑回滚 PASS 后随重启落库。
2. **授予通道**：后端白名单与四个权限模型 + 聚合逻辑 + 读写列；前端 `rights-admin/types.ts` 位清单。
3. **门**：按 §5.2 的映射表改 `MenuAdminController` 与 `ModuleBusinessConfigController`。
4. **页面**：无该位时不渲染三个配置页签（fail-closed）。
5. **验收**：`SETUP=1, CONFIG=0` 的账号改基础信息 200、读写配置 403；`SETUP=1, CONFIG=1` 全通；
   `scripts/verify-permission-gate.ps1` 同类口径的门禁用例。

> 这一段独立于页签搬家：它只动一列、四处清单和两道门，不动写端点与保存语义（§3 的三条隐藏成本一条不涉及）。
> 先落它再搬页签，是为了让"页签拆完发现某类账号进不去"这类问题不与权限改动混在一起。
