# ADR-039：产品 BOM 的结构视图、版本维度与承载形态

- 状态：**已实施（2026-10-18）**——第 8 节六步全部落地（迁移 408–416）。**6.3 的选版规则在实施后修订**：由"锁根版次 + 逐层回退"改为"明细显式指定子件版本"，理由见该节
- 日期：2026-10-17
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-006（统一表单一次性重构）、ADR-012（单据行为效果配置化）、ADR-018（单据动作按钮）、ADR-022（模块级表单版式）、ADR-033（模块形态与配置面）、ADR-035（批核模型收敛）、迁移 159 / 340 / 355 / 407、`LESSONS.md` L98 / L100

> 本文回答三件事：**1204 的界面由谁画**、**阶层怎么读**、**版本放在哪一层**。
> 不回答"改哪个文件、用哪个迁移号"——那属于实施计划，随第 8 节的顺序展开。

## 1. 问题

### 1.1 已核实的缺陷

以下八项均已对着库内元数据与源码逐条核实，不是推测：

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | 算料按 `MAX(EDITION)` 在明细行上筛版次，`EDITION` 全空时 `= NULL` 恒不成立，静默展开 0 行 | `EOS.API/Data/DocumentActions/Handlers/ProduceCalcMaterialsHandler.cs:172-191` |
| 2 | 版次是字典序比较，`V9 > V10` | 同上，`MAX(EDITION)` |
| 3 | `TABLES.DF_VERIFY='ELEMENT_PRO_NO'` 按子件查重、不看版次，一单装不下两版同料 | `db/bootstrap/20_metadata.sql`（`BOM_STRU_D` 行）+ `WorkbenchCommandHandler.cs:1053-1061` |
| 4 | 底数 `BASE_QTY` 的 `IS_VISIBLE=0`（界面隐藏），但 SAVE 期 `line-require` 强制 `>0` | `20_metadata.sql:2199`；`Migrations/159_catalog_bom_stru.sql:100-102` |
| 5 | 明细版式 25 行里有 3 行对应不可见字段（`PRO_ELEMENT_PRO_NO` / `STUFF_ID` / `SPECIFIC_GRAVITY`），永远渲染不出 | `20_metadata.sql` 的 `MODULE_FORM_LAYOUT` 1204 段 + `FIELDS` 的 `IS_VISIBLE=0` |
| 6 | 主表与明细的 `BROWSE_M_IDX` 指向 1206 / 1210，两个模块已合并进 1201 并从 `MODULES` 消失，料号退化为纯文本 | `20_metadata.sql:2205/2218/2248`；`EOS.API/Data/ModuleBusinessMap.cs:20` |
| 7 | `ELEMENT_QTY` 正则 `^\d+|^$` 是"以数字开头"而非数字格式，`5abc` 也过 | `20_metadata.sql:2207`；`RecordPayloadValidator.MatchesFieldRegex` 用非锚定 `IsMatch` |
| 8 | 明细行的 `PRO_NO` 可编辑，但服务端强制用主表键覆盖，用户改了静默丢弃 | `20_metadata.sql:2218`（`IS_READONLY=0`）+ `WorkbenchCommandHandler.cs:994-1006` |

第 1 项是**静默错误**：不报错、无提示、结果为空。它比任何一项都严重。

### 1.2 三个结构性问题

**P1：产品 BOM 在业务链上没有出口。**
同一张制令单上两个相邻按钮读两张不同的表——「计算用料」读 `BOM_STRU_D`（产品 BOM），「展开子制令」读 `MOC_BOM_STRU_D`（工单 BOM），而两张表之间**没有任何自动桥接**（全仓 `MOC_BOM_STRU` 的 `.cs` 消费点只有这两个处理器与一个孤儿清理）。产品 BOM 维护完不会被任何下游自动消费。

**P2：版次是一个四层各走各的半成品维度。**
数据模型假设它存在（明细有 `EDITION`）、算料逻辑依赖它（`MAX(EDITION)`）、校验规则禁止它存在（`DF_VERIFY` 只看子件）、界面没有提供它（自由文本框、非必填、无下拉、主表那个无人消费）。四层里任意三层不一致，它就无法工作。

**P3：承载形态与数据形态错配。**
BOM 明细录入面排了 25 行，其中可填 5 格、只读展示 14 格（含 6 个印铁排版参数）、死行 3 格、父键回显 1 格、项次 1 格。用户面对的是"一张 25 列的展示表"，而他真正要填的只有子件、用量、损耗率。

P3 是"1204 该不该继续用统一工作台"这个问题的真正来源——**不是工作台不好，是 BOM 的录入面需要重新编排，而统一工作台的版式只能按 `FIELDS` 平铺**。

## 2. 一个必须先认的前提：BOM 有三个读者

设计"展开"之前必须承认：同一份 BOM，三类人的诉求根本不同。

| 读者 | 问的问题 | 要的结果形态 | 不要什么 |
|---|---|---|---|
| **工程** | 这东西怎么组成的？改了会影响到谁？ | 缩进树、层级、路径、Where-used | 损耗、库存、价格 |
| **计划** | 做这张制令单要备多少料？ | 叶子节点汇总的毛需求 | 中间层、路径 |
| **采购** | 哪些料要买、买多少？ | 按料号汇总、按供应商分组 | 层级、父件 |

这三件事**共享同一套遍历，但不共享同一个结果集**。把它们压成一个"BOM 展开页"是过去 129802 的设计，也是它最终说不清自己服务于谁的原因。

本 ADR 据此把展开拆成**三个出口、一套算法**（第 6 节）。

## 3. 决策

### D1：1204 改为定制承载页

`MODULES.M_URL` 由 `/workbench` 改为 `/bom/product`（路径待定，见第 9 节），`NODE_KIND` 随之变为 `CUSTOMPAGE`。

### D2：定制页不重写单据管线，形态与能力解耦

这条是 D1 能否成立的前提。

现状是一条硬链：`NODE_KIND != Workbench` ⇒ `WorkbenchDefinitionBuilder` 直接返回 null（`EOS.API/Data/WorkbenchDefinitionBuilder.cs:186-197`），于是定制页拿不到 `WorkbenchDefinition` 与 `FormDefinition`，也就无法复用 `WorkbenchCommandHandler` 的校验 / 审计 / 效果链 / 幂等 / 范围过滤。

本 ADR 把"谁画界面"与"有没有单据定义"拆成两件事：

| 列 | 回答的问题 | 1204 的取值 |
|---|---|---|
| `MODULES.NODE_KIND`（`V_MODULE_NODE` 派生） | 菜单点进去打开哪个页面 | `CUSTOMPAGE` |
| `MODULES.UNIFIED_FORM_ENABLED` / `UNIFIED_FORM_EDIT_ENABLED` | 这个模块有没有单据表单面、能不能写 | `1 / 1`（不变） |

具体改动是三处判据从"形态"换成"能力位"（**已实施；措辞按实际代码修正**）：

1. `WorkbenchDefinitionBuilder`：装配条件由 `nodeKind != Workbench ⇒ return null` 改为
   `工作台形态 || （定制页 且 UNIFIED_FORM_ENABLED=1）`，目录形态永远不装配。
   为此把 `UNIFIED_FORM_ENABLED` 追加到那条 SELECT 的末尾（只追加，不动既有取位）。
2. **迁移 355 的断言不撤销**——历史迁移不能改，改了已建库也不会重跑。实际做法是"新库的执行
   顺序天然不冲突"：355 在建 1204 为 CUSTOMPAGE 之前执行，那时它仍是 WORKBENCH，断言通过；
   形态变更走 412，排在后面。这条断言从"日常约束"退化为"初始化时的一次性检查"。
3. `MenuAdminRepository.NormalizeForKind`：对"定制页 + 声明了表单能力 + 有主表"的模块，
   **保留** `IF_COPY` / `ERROR_NO_SAVE` / `DETAIL_NO_FIELDS` / `DETAIL_NO_SAVE` / 批核 / 能力位
   （写入仍走工作台管线，它们都有消费方），只清列表视图专属的 `SORT_FIELDS` / `NOT_BACK_FIELDS`；
   其余定制页仍按原逻辑全清。

**这条决策的边界（判据）**：定制页复用工作台定义的前提是**它的数据仍是单据形态**——一主表、可选一张明细表、有主键、主子表同名主键列。数据不是单据形态的定制页（菜单树、字段设置、配置矩阵）必须停在 `0/0`，它们装配不出定义。

这条判据要写进 `docs/guide/03` 的"新增前端页面"登记清单，否则下一个人会把任意管理页判成"我也可以复用工作台"。

**落点（已实施）**：

- 前端 `EOS.Web/src/features/bom/`：`BomProductListPage`（列表）、`BomProductEditorPage`（单层维护）、`BomTreePage`（结构树与毛需求切换）、`BomWhereUsedPage`（反查）、`bomApi.ts`（三个结构端点 + 新建版本）；
- 路由 `workspaceRoutes.tsx` 三条，权限统一 `moduleReadPermission(1204)`；`ModuleRouteValidator.ExactRoutes` 必须加 `/bom/product`——**不加会被判为非法承载页并落占位页**，这是改 `M_URL` 的隐性前置；
- 迁移 `412_bom_custom_page_host.sql`：`M_URL` → `/bom/product`，能力位保持 `1`，标脏等发布；
- 门禁 `check-module-node-kind.ps1` 三条判据同步（见第 11 节）；
- **「新建版本」是端点，不是可配置按钮**：`POST /api/v1/bom/new-version`（`BomController`），鉴权 `PermissionAction.AddNew`，审计 `BOM_NEW_VERSION`，版次由**服务端**算（`MAX+1`，两位数字，上限 99）——版次是主键，让前端传等于把主键交给客户端。复制逻辑在 `BomRepository.CreateNewVersionAsync`（两条 INSERT 同一事务）；复制整棵结构、重置确认位与制单人，明细项次原样保留以便两版逐行对比。

  **为什么不用 `MANUAL` 动作**（一次实施中的机制纠偏）：那套机制（ADR-018）是为**标准单据面**设计的——同一张单要给不同客户配不同按钮组合、调顺序、按角色细分授权（fail-closed、需单独授予）。1204 已经是定制页，它的动作本来就该由代码 + 模块权限位决定，与"保存"同级；「新建版本」的授权语义就是"对这个模块有没有新增权"，不需要按钮级粒度。走 MANUAL 的代价是真实的：管理员要配按钮行、再授一次权、再重新发布，三步做完按钮才出现——这层负担是机制错配带来的，不是业务需要的。

  迁移 `413` 曾把它配成 MANUAL 按钮，`414` 撤销。配置面"候选集与拒存判据改为有单据面"那条改动仍然保留且必要——其它定制页的按钮仍要靠它才配得了。

- **配置面的第三个消费点**：`ModuleBusinessConfigRepository` 的模块候选集（`INNER JOIN V_MODULE_NODE ... NODE_KIND='WORKBENCH'`）与保存拒存判据同样按形态写的。改完 `M_URL` 后 1204 在 230103 里**选不到**、强行保存也会被拒——这是 D2 最容易漏的一处（判据散落在运行期、门禁、配置面三处，改两处不改第三处，表现就是"功能能用但配不了"）。两处已一并改为「有单据面」＝ 工作台形态 **或**（`UNIFIED_FORM_ENABLED=1` 且有主表）。

### D3：定制页的职责边界

定制页**替换的是页面壳，不是数据契约**：

- 复用：`/definition`、`/form-definition`、记录读写、选择器、审计、效果链、范围过滤、字段级成本/保密过滤；
- 不复用：工作台的列表卡片、`ErpTable` 的默认列装配、表单页签渲染。

也就是说，**定制页自己画，但下面的每一笔写入仍然走同一条管线**。这条边界保证"绕过统一工作台"不等于"绕过权限与审计"——后者是 `AGENTS.md` 的红线，不能因为换了个页面而松。

### D4：版本维度用 `(PRO_NO, EDITION)` 复合主键

```sql
BOM_STRU_M(PRO_NO, EDITION, BATCH_QTY, ATTENTION, ...)                 PK (PRO_NO, EDITION)
BOM_STRU_D(PRO_NO, EDITION, SERIAL_NO, ELEMENT_PRO_NO, ...)            PK (PRO_NO, EDITION, SERIAL_NO)
```

- `EDITION` 两位数字（`^\d{2}$`）、`NOT NULL`、**两表都只读**：主表由 DB 默认值 `01` 兜底，明细由服务端按主键回填；
- 明细的 `PRO_NO` 与 `EDITION` 都保留：前者是复合父键的一部分，同时供 `no-cycle` 做**跨版本**图遍历；
- 不加 `STATUS` / 生效日期（理由见 5.4）。

**为什么两表版次都必须只读**（这一条是实施时才看清的）：

主键是记录身份，改它等于换一条记录；而明细是按 URL 里的**旧键值**增删的（`WorkbenchCommandHandler.UpdateRecordAsync` 用 `keyValues` 定位、`SaveDetailsAsync` 用同一组键值删旧插新）。如果允许改主表版次：

1. 主表被 UPDATE 成新版次；
2. 明细按**旧**键值删除 → 删掉的是旧版次的行；
3. 再按**旧**键值插入 → 明细仍挂在旧版次下。

结果是旧版次留下一批孤儿明细，新记录没有明细。所以版次在界面上锁死，**换版走"新建版本"动作**（复制当前明细到新版次），随定制页一起落。

在此之前系统只支持 `01` 版——但版本维度已经就位（主键含 `EDITION`），差的只是一个入口，不是一次重构。

原定的代理键方案（`BOM_ID`）在实施前被推翻，理由见第 5 节——核心是它会让明细必须在 `FIELDS` 里暴露一列可见的自增 ID。

**子件版本也进明细**（迁移 `416_bom_element_edition.sql` 追加）：`BOM_STRU_D` 再加一列
`ELEMENT_EDITION`，显式记录"这个子件用它的哪一版 BOM"。初稿把子件版本留给运行时选
（锁根版次 + 回退最大，见 6.3 的原方案），实施后推翻——**理由、必填规则、回填口径、
以及 `IS_FALLBACK` 为什么恒为 0，都在 6.3**。这是本 ADR 唯一一处"实施后修改设计"的地方。

### D5：三个展开出口，一套遍历

| 出口 | 形态 | 落点 |
|---|---|---|
| **结构视图** | 缩进树 / 可折叠表，带层级、路径、累计用量 | 1204 定制页的一个视图（不是独立模块） |
| **毛需求** | 叶子汇总，按料号合并 | 制令单「计算用料」改读本出口 |
| **反查用途** | 向上路径 | 1204 定制页的第二个视图 + 产品档案的一个入口 |

三者共用第 6 节的递归遍历，只是结果投影不同。

**落点（已实施）**：`EOS.API/Data/BomRepository.cs`（三套递归 SQL，共享"按明细指定版本"与路径环检测）+ `EOS.API/Controllers/BomController.cs`（`GET /api/v1/bom/expand`、`/gross-requirement`、`/where-used`，统一走模块 1204 的 `Browse` 权限）。用例见 `EOS.API.Tests/BomExpansionLiveTests.cs`：三层树、累计用量 2→6、损耗累乘 1.1×1.2=1.32、毛需求只出叶子、反查沿父链向上。

**反查是唯一仍按"父件最大版次"过滤的出口**：它向上找"这个料被哪些 BOM 用了"，无法从被引用方向得知"引用方用的是哪一版自己"，所以保留 `EDITION_PICK` 口径（每个父件取一版）。这不是遗漏——反向查询的语义里没有"子件版本"这一维。

### D6：展开算法用递归 CTE，环检测靠路径

用 SQL Server 递归 CTE 一次取完整棵树，而不是逐层 `#temp` 循环（`NoCycleCheck` 现在的做法）。环检测不靠深度上限，靠**路径字符串里是否已出现该料号**——这样环会在第一次回到自身时被切断，而不是等到第 100 层。

细节见第 6 节。

### D7：产品 BOM 为源，工单 BOM 为快照

产品 BOM（1204）是标准；制令单建立时把它**快照**到工单 BOM（1506），此后工单 BOM 允许人工调整、不再回写产品 BOM。

这是对"双真源"的唯一解：产品 BOM 回答"标准是什么"，工单 BOM 回答"这一单实际用什么"。两个问题本来不同，强行合并成一个必然有一方丢失。

反向依赖的处理：「展开子制令」从工单 BOM 读，与「计算用料」同源；产品 BOM 不再被任何运行期动作直接读取，只被快照动作读取。

**落点（已实施）**：效果处理器 `Data/Effects/ServiceEffectHandlers/BomSnapshotToOrderHandler.cs`（`bom-snapshot-to-order`）+ 迁移 `410_bom_snapshot_to_order.sql`（挂在 1502 的 `SAVE` seq=2，`link-stamp` 之后）。三条硬口径写在处理器头部：**只快照一次**（已有工单 BOM 即跳过，人工调整必须能留下）、**产品没有 BOM 返回 0 不抛异常**（先下制令后补 BOM 是正常流程，为此阻断会把人卡死）、**版次显式记录**（根 BOM 的版次写进目标主表，**每一行的子件版本也写进 `MOC_BOM_STRU_D.ELEMENT_EDITION`**——快照的意义是"当时是什么样"，缺了它半年后说不清那一单用的是 A1 的哪一版）。用例 `EOS.API.Tests/BomSnapshotLiveTests.cs` 三条：整棵快照的行与边、已有工单 BOM 不被覆盖、产品没 BOM 返回 0。

### D8：`BASE_QTY` 回到录入面

比例用量是后端已经认真支持的能力（算料到处做 `ELEMENT_QTY / BASE_QTY`、明确拒绝 `BASE_QTY=0`），界面却把它藏了。放出来，并在版式上紧跟用量。

同时把 `ELEMENT_QTY` 的正则从 `^\d+|^$` 改成 `^\d+(\.\d+)?$`，`LOST_RATE` 加 `0..100` 区间。

### D9：原地修复清单

不依赖上面任何设计决策、可以立即做的六项：

1. `BROWSE_M_IDX` 1206 / 1210 → 1201；`BROWSE_URL` 换成新路径（或清空，退化为纯文本）
2. 删除 3 行死版式（`PRO_ELEMENT_PRO_NO` / `STUFF_ID` / `SPECIFIC_GRAVITY`）
3. `ELEMENT_QTY` 正则、`LOST_RATE` 区间（D8 的前半）
4. 明细 `PRO_NO` 改只读
5. `MODULES.REMARK` 与 `TABLES.T_REMARK` 清掉已退役的 `P_BOM_STRU_After_Save` / `129802`
6. 删除空目录 `EOS.Web/src/features/bom/`（迁移 407 删了文件、留了目录）

**落点：迁移 `408_bom_module_metadata_fixes.sql`**（六项一次落库，含收口断言）；目录已在工作副本删除。迁移末尾把 1204 标脏，**版式段要等下一次发布才固化进快照**——不标脏会被快照落后检测判为静默落后。

实施时踩到的一处口径差异记在这里，供后来者少走一趟：`MODULE_VALIDATION_RULE` 与 `WORKBENCH_MODULE_DIRTY` 的模块列在库内叫 **`M_IDX`**，而迁移 159 的脚本正文写的是 `MODULE_ID`。照抄 159 会在执行期报"列名无效"，必须按库内实际列名写。

### D10：1204 内部是四个视图、六个动作，不是四个模块

`MODULES` 在 EOS 里同时承担菜单项、权限单元、页面入口三件事，所以"要不要再加一个模块"不能按"功能多不多"判，只能按三条判：

| 判据 | BOM 的实际情况 |
|---|---|
| **数据身份不同**（另一张主表 / 另一个生命周期） | 展开、反查、对比操作的都是 `BOM_STRU_M/D` 同一批数据 ⇒ 不成立 |
| **权限需要独立授予**（同一张表但受众完全不同） | 不成立：权限位是**逐动作**的（`SYSDD.ADDNEW_TAG` / `EDIT_TAG` / `DELETE_TAG`，见 `db/bootstrap/10_schema.sql:18676-18684`），"能看不能改"给浏览权 + `EDIT_TAG=0` 即可，不需要另建模块 |
| **入口语义不同**（不是同一件事的另一个视角） | 展开与反查都是"看这份 BOM"的另一个角度 ⇒ 不成立 |

三条全不成立，因此**BOM 族现有的模块划分不动**（1204 产品 BOM / 1205 作业指导书 / 1212 成本试算 / 1506 工单 BOM / 1202 商编变更单，各自因"另一张表或另一个生命周期"而独立），1204 内部以视图承载差异。

**四个视图**（同一模块下的子路由，不是四个菜单项）：

| 视图 | 路由 | 进入方式 | 数据出口 |
|---|---|---|---|
| 列表 | `/bom/product` | 菜单（`M_URL` 精确路径） | 列表 API（复用工作台查询） |
| 单层维护 | `/bom/product/:proNo/:edition` | 列表双击 | 记录读写（复用工作台管线，见第 8 节） |
| 结构树 | `/bom/product/:proNo/:edition/tree` | 维护页「结构树」 | 第 6.1 节出口一 |
| 版本对比 | `/bom/product/:proNo/:edition/compare/:otherEdition` | 维护页「对比」 | 两份明细的 diff（**未实现**） |
| 反查用途 | `/bom/product/where-used/:proNo` | 列表行「反查」 | 第 6.1 节出口三 |

三点说明：

1. **反查挂在料号上而不是主键上**，因为它问的是"这个料被用在哪些 BOM 里"，不隶属于某一条 BOM。它与 `:proNo/:edition` 同为三段，靠**静态段优先**消歧（`bom/product/where-used/xxx` 必须排在 `bom/product/:proNo/:edition` 之前）。
2. **用路径段而不是 query 参数区分视图**：深链可分享、前进后退语义一致、`workspaceRoutes.tsx` 里能一眼数出有几个视图、`RequirePermission` 可按路径配置。
3. **毛需求不是视图，是动作**。它是"算完给下游用"的结果，没有"停下来看"的语义（第 6.1 节出口二），现在挂在结构树页的模式切换里。

**七个动作**（落在列表与单层维护的工具栏）：

| 动作 | 落点 | 状态 |
|---|---|---|
| 新增 | `/bom/product/new`：选料号，版次固定 `01`（DB 默认值） | ✅ |
| 从另一产品复制 | 同一个新建页的「复制自」：先建空单，再把源版次明细导入；复用取试算表端点，校验一套 | ✅ |
| 展开毛需求 | 结构树页的模式切换（不是独立菜单项） | ✅ |
| 取试算表 | 维护页「取试算表」：CSV → `POST /api/v1/bom/import-lines`，项次服务端分配 | ✅ |
| 版本对比 | 维护页「对比」→ `/bom/product/:proNo/:edition/compare/:otherEdition`，按子件对齐 | ✅ |
| 打印 | 维护页「打印」→ `/print/1204`（走 `PrintService` 与工作台定义） | 入口已接；**报表与版式属实施期配置**，没配会提示没有可打印报表 |
| 反查用途 | 列表行「反查」→ `/bom/product/where-used/:proNo` | ✅ |

**版本发布 / 停用不做**：D4 本期不引入 `STATUS`（见 5.4），没有可翻转的状态位。换版的语义由「新建版本」承担。

**"取试算表"为什么不用通用导入**：`ImportController` 的入口是 `AuthorizeFormAsync(..., "new")`——它建的是**新记录**；而试算表是往**已有 BOM** 里补明细。两者权限口径与写入目标都不同，硬套会让"往 A 单导明细"变成"A 单被新建"。所以有 `POST /api/v1/bom/import-lines`（`Edit` 权限 + 同一套子件/底数/损耗率校验 + 服务端分配项次）。

**树用 `ErpTable` 承载，不手写 `<table>`。** `ErpTable` 的列是 TanStack `ColumnDef`，首个业务列用 `cell` 渲染"`paddingLeft: LVL * 16` + 展开箭头"即可。这既是 `AGENTS.md`「所有列表一律用 `ErpTable`」的约束，也让 `scripts/check-page-shell.ps1` 能继续拦住手写表格。

**展开状态在本地，不重新请求**：一次取整棵树（D6 的单次 CTE），前端只做折叠。这保证"环检测与深度上限在服务端一次生效"，也避免"展开一层请求一次"带来的不一致（层与层之间数据可能已被别人改动）。

**不做**：

- 独立的「BOM 展开页」（129802 的老路，第 4 节）；
- 「BOM 变更单 / 工程变更」独立模块——只有"改 BOM 必须审批"成为业务规则时才做，见第 6.6 节；
- 把四个视图做成四个菜单项。判据是：**两个入口打开后 80% 是同一张表、同一批数据，它们就该是一个页面。**

**登记面**：`M_URL` 改 `/bom/product` 后端到端有三处要同改（库内 `MODULES.M_URL`、`ModuleRouteValidatorTests` 的 `[InlineData]`、`workspaceRoutes.tsx`），四视图的子路由要同步补进 `workspaceRoutes.test.ts` 的 `paths` 数组——这是 `AGENTS.md` 第二节的强制登记清单。

## 4. 为什么改定制页，而不是另外两条路

| 方案 | 怎么做 | 代价 | 问题 |
|---|---|---|---|
| **A. 继续用统一工作台** | 只修元数据（D9） | 最小 | 录入面 25 列的问题**修不了**——版式只能按 `FIELDS` 平铺，无法把"只读展示列"折叠起来。没有树、没有版本切换 |
| **B. 多阶展开做成独立模块** | 新模块 `/bom-expand` | 中 | **这正是 129802 的老路**，它已被迁移 407 退役。独立模块会被模块治理周期性地判为"功能重复"，而一旦删掉，能力整块归零 |
| **C. 1204 改定制页**（本决策） | `M_URL` 改 `/bom/product` + 定制前端 | 大 | 要写一个页面，且要动 D2 那三处判据 |

B 的教训值得写进决策：**129802 被删不是因为它没用，而是因为它长成了"独立模块"这个形态**。它当初唯一的保留理由是"它是该功能的唯一入口，删掉就没地方进"（`docs/架构.md`），而当 1204 被确认为产品 BOM 的正主之后，这个理由就消失了。

结论：**结构视图必须长在 1204 身上，而不是长成 1204 的邻居。** 这是选 C 而不是 B 的核心理由。

至于 A 与 C 之间：A 的省事是假省事——它把"录入面难用"永久固化成"元数据只能这样"，而且树与版本这两件事在 A 下无解。

## 5. 版本放在哪一层：复合主键（实施前推翻代理键）

**结论：`(PRO_NO, EDITION)` 复合主键。** 本节记录为什么把原定的代理键方案推翻——不是"哪个更标准"，而是一个具体的实现约束。

### 5.1 代理键的隐性代价

`WorkbenchCommandHandler.SaveDetailsAsync` 要求明细的表单定义里存在与**主表主键同名**的列：

```csharp
var pkField = form.DetailFields.FirstOrDefault(field => field.Key.Equals(pkColumns[i], StringComparison.OrdinalIgnoreCase));
if (pkField is null)
{
    errors.Add(new FieldError(pkColumns[i], "明细表缺少主表关联字段。", "MASTER_KEY_NOT_IN_DETAIL", rowIndex));
    continue;
}
```

而 `form.DetailFields` 的补齐来源只认**可见**的字段行：

```csharp
if (!rowsByKey.TryGetValue(column, out var pkRow)) continue;   // rowsByKey 来自 detailRows
```

`ReadFormFieldRows` 的 SQL 带 `WHERE f.T_ID=@TargetTable AND COALESCE(f.IS_VISIBLE,1)=1`。

所以代理键 `BOM_ID` 若要在明细侧可用，就必须在 `FIELDS` 里有一行 `BOM_STRU_D.BOM_ID` 且 `IS_VISIBLE=1`——**即使版式不给它排位，它也会进 `form.DetailFields`**。它是否出现在界面上取决于渲染侧，这是一个随时会冒出来的隐患，而它冒出来时是一列毫无意义的自增数字。

另一条路是改 `WorkbenchDefinitionBuilder` 的补键逻辑（让主键列不受 `IS_VISIBLE` 限制）。那是**为一个模块改共享装配器**，代价比换主键方案大。

### 5.2 复合主键的三个具体好处

1. **零新增字段**：`PRO_NO` 与 `EDITION` 都是明细上已有的可见业务列，服务端回填主键列时两列一起回填，不需要任何新元数据。
2. **与本库既有先例同构**：模块 1209（产品/料件版次）就是 `(PRO_NO, EDITION)` 复合主键，深链 `/workbench/1209/view/{PRO_NO}/{EDITION}` 已被长期使用。
3. **`no-cycle` 不用改**：它的配置是 `parentField=PRO_NO, childField=ELEMENT_PRO_NO`，靠明细的 `PRO_NO` 做**跨版本**图遍历。代理键方案下明细没有 `PRO_NO`，这条通用校验就得改配置或改实现。

### 5.3 两个必须一起定的约束

**版次必须是两位数字**（`^\d{2}$`，默认 `01`）。这不是洁癖——它让 `MAX(EDITION)` 的字典序与数值序一致，"`V9 > V10`"的问题从根上消失，不需要额外加数值列或排序字段。

起始值 `01` 与 `sample-edition-bump`（样件批核时版次递增）的口径一致：那个处理器已确立"空 → `01`，否则两位补零递增"的规则，BOM 沿用同一套。

**版次只读**：建单时填一次，此后不可改；要换版就复制一条新记录。这消掉了"改版次 = 改主键 = 明细级联"的顾虑——**它不是可编辑字段，是一条记录的身份**。

### 5.4 本期不做状态与生效日期

原稿写的 `STATUS` / `EFFECTIVE_FROM` / `EFFECTIVE_TO` 一并去掉：

- "按日期自动切换版本"是一个独立需求，当前没有；
- 加了它，每次取版本都要判日期区间，而判据一旦有歧义（同一日期两个版本都生效）就要再加区间互斥约束；
- 现在取版本的规则只有一条——**按调用方指定的版次，缺省取最大版次**，没有歧义。

将来要"生效日期"是加列 + 加区间互斥约束，不影响现有主键。

### 5.5 实施前的数据实测

| 指标 | 值 |
|---|---|
| `BOM_STRU_M` / `BOM_STRU_D` 行数 | 185 / 1084 |
| 孤儿明细（`PRO_NO` 不在主表） | 0 |
| 同一料号下多版次混存 | 0 |
| 同一父件下重复子件 | 0 |
| `BASE_QTY = 0` / 用量负数 / 损耗率越界 | 0 / 0 / 0 |
| 版次列取值 | 185 + 1084 行**全部为空**（NULL 或空串） |

所以迁移是"回填默认版次 `01` → 列改 NOT NULL → 换主键"，**不需要拆分记录**。

### 5.6 下游为什么零改动

换主键最容易漏的是"按料号定位"的下游。逐处核过：

| 下游 | 定位方式 | 多版次后 |
|---|---|---|
| `BomSizeBackfillHandler`（长宽回填） | `ServiceEffectSql.MasterKeyFilter` 按 `Plan.MasterPkOrder` **逐列生成谓词**，主键变两列后自动变成 `PRO_NO=@k0 AND EDITION=@k1` | 不会串版，无需改 |
| `ProduceCalcMaterialsHandler`（计算用料） | `WHERE PRO_NO=@pro AND EDITION=(SELECT MAX(EDITION) ...)` | 版次改为 NOT NULL 后 `MAX` 不再返回 NULL，"静默算出 0 行"的缺陷随之消失；两位数字格式让字典序=数值序 |
| `NoCycleCheck`（成环） | `parentField=PRO_NO, childField=ELEMENT_PRO_NO`，**不带版次** | 语义正确——环要跨版本判，A 的某一版用了 B、B 的某一版用了 A 仍是一个环 |
| `ProduceGenSubHandler`（展开子制令） | 读的是工单 BOM `MOC_BOM_STRU_D`，不读产品 BOM | 不受影响 |

结论：**D4 不需要改任何 C# 代码**，只改表与元数据。

## 6. 展开怎么设计

### 6.1 三个出口的结果形态

**出口一：结构树（工程）**

```
层级  料号        品名        用量/父件  累计用量  单位  来源BOM版本  路径
0     A-1000     成品A        1          1         PCS   V2          A-1000
1     B-2000     半成品B      2          2         PCS   V1          A-1000/B-2000
2     C-3000     原料C        0.5        1         KG    —           A-1000/B-2000/C-3000
```

- `用量/父件` = `ELEMENT_QTY / BASE_QTY`；
- `累计用量` = 父级累计 × 本层用量；
- `来源BOM版本` = 这一层的子件**自己的 BOM 版次**（`ELEMENT_EDITION`），**必须显示**——否则用户看不懂"为什么这个子件展开出了东西，那个没有"。它与"父件那条 BOM 的版次"是两个字段，界面上不要合并成一列（见 6.3 的字段语义表）；
- `路径` 用于环检测与"从叶子反查根"。

**出口二：毛需求（计划）**

只出叶子（无下阶 BOM 的料），按 `ELEMENT_PRO_NO` 合并：

```
料号      毛需求        其中损耗      单位
C-3000    1000*1       20*1          KG
```

- 毛需求 = `Σ(累计用量 × 损耗因子) × 制令数量`；
- **损耗沿路径累乘，不是只加最后一层**：三层各 10% 的实际放大是 `1.1 × 1.1 × 1.1 = 1.331`，不是 `1.3`。按层相加在深树上会系统性低估；
- 按料号合并，不保留层级；
- **服务于"不拆单"的场景**：报价、成本估算、整单备料。**它不是「计算用料」的出口**——制令单只负责本单直接投入的那一层，下阶由子制令各自负责，混用会让同一批料被算两遍。

**出口三：反查用途（工程）**

给定 `ELEMENT_PRO_NO`，向上找出所有含它的 BOM：

```
父件        BOM版本   项次   用量    路径
B-2000      01        3      0.5     A-1000/B-2000
A-1000      02        5      2       A-1000
```

- 这是一次反向查询：`WHERE ELEMENT_PRO_NO = @x`；
- 需要新增索引 `(ELEMENT_PRO_NO, PRO_NO, EDITION)`——现有 `IX_BOM_STRU_D(PRO_NO, ELEMENT_PRO_NO)` 的前导列是父件，反查用不上；
- 反查**必须显示路径**，否则用户只知道"被用了"，不知道"在哪一层被用"。

### 6.2 算法

递归 CTE，一次查询取整棵树。展开路径由**明细行指定的子件版本**决定（见 6.3）：

```sql
WITH TREE AS (
    SELECT CAST(N'/' + LTRIM(RTRIM(d.ELEMENT_PRO_NO)) + N'/' AS nvarchar(4000)) AS PATH,
           1 AS LVL,
           LTRIM(RTRIM(d.ELEMENT_PRO_NO)) AS PRO_NO,
           d.EDITION AS USED_EDITION,
           d.ELEMENT_QTY / NULLIF(d.BASE_QTY, 0) AS QTY_CUM,
           1 + ISNULL(d.LOST_RATE, 0) / 100.0 AS LOST_FACTOR
    FROM dbo.BOM_STRU_D d
    WHERE d.PRO_NO = @rootProNo AND d.EDITION = @rootEdition

    UNION ALL

    SELECT CAST(t.PATH + LTRIM(RTRIM(d.ELEMENT_PRO_NO)) + N'/' AS nvarchar(4000)),
           t.LVL + 1,
           LTRIM(RTRIM(d.ELEMENT_PRO_NO)),
           d.EDITION,
           t.QTY_CUM * d.ELEMENT_QTY / NULLIF(d.BASE_QTY, 0),
           t.LOST_FACTOR * (1 + ISNULL(d.LOST_RATE, 0) / 100.0)
    FROM dbo.BOM_STRU_D d
    -- 下一层用**父行指定的子件版本**继续展开；OWN_EDITION 为 NULL（材料）时不命中，
    -- 展开到该行为止——这就是"叶子"的正确判据
    JOIN TREE t ON d.PRO_NO = t.PRO_NO
               AND CAST(d.EDITION AS nchar(10)) = t.OWN_EDITION
    WHERE t.LVL < @maxDepth
      AND CHARINDEX(N'/' + LTRIM(RTRIM(d.ELEMENT_PRO_NO)) + N'/', t.PATH) = 0
)
SELECT * FROM TREE OPTION (MAXRECURSION 100);
```

四个要点：

1. **环检测在 `CHARINDEX` 上**，不在深度上。回到已出现过的料号即停止该分支——这比"跑到第 100 层才失败"快且可解释。路径同时就是给用户看的"为什么停在这里"。
2. **`NULLIF(BASE_QTY, 0)` 不是兜底，是拒绝**：`BASE_QTY=0` 或 NULL 的行必须在进入 CTE 前被拦住并报出料号（现有 `ProduceCalcMaterialsHandler` 的 guard 已这么做，保留）。
3. **`MAXRECURSION` 不能参数化**，必须拼接整数常量，且该整数来自白名单校验（1..100）。这是本项目动态 SQL 约定的直接应用。
4. **展开路径由 `d.EDITION = t.OWN_EDITION` 决定，不是靠"选版表"反查**。原方案（`JOIN EDITION_PICK p ON p.PRO_NO = d.PRO_NO`）在实施时踩过坑：`p.PRO_NO` 是"当前节点自己"而不是"它的子件"，写错会让**叶子节点整行消失**（叶子没有下阶 BOM，join 不上选版表就被过滤掉），表现为树只剩 1 行、毛需求为空。新方案里 `OWN_EDITION` 为 `NULL` 自然不命中，同一个坑不再存在。

### 6.3 版本选择：由明细指定（原"锁版 + 回退"已废弃）

**现行做法**（迁移 `416_bom_element_edition.sql`）：`BOM_STRU_D.ELEMENT_EDITION` 显式记录
"这个子件用它的哪一版 BOM"，展开时直接按它走：

```sql
JOIN TREE t ON d.PRO_NO = t.PRO_NO
           AND d.EDITION = t.OWN_EDITION     -- 下一层用父行指定的子件版本
```

不再有运行时选版，也没有"回退"。

#### 为什么推翻原方案

原方案（本 ADR 初稿）是"整棵树优先锁根节点版次，某层没有该版次则回退该层最大版次，并标
`IS_FALLBACK`"。实施完成后发现它带来四个无法回避的问题：

| 问题 | 具体表现 |
|---|---|
**树不是数据的函数，是请求参数的函数** | 同一份数据，根版次传 `01` 时 B 用 01，传 `02` 时 B 用 02——两次展开结果不同，而数据一行没变 |
**回退是事后标记，不是录入时的决定** | `IS_FALLBACK=1` 只告诉用户"发生了回退"，无法在录入时决定"这一层到底用哪版" |
**无法表达"同一半成品在不同父件里用不同版本"** | 全局锁版意味着 A 用 B 的 01 版时，C 也只能用 01 版 |
**改版会静默穿透** | 半成品出了 03 版，`MAX(EDITION)` 让所有引用它的树自动跟着变——"这份 BOM 用的是 02"这条信息根本不存在 |

#### 新做法把版本变成数据

`ELEMENT_EDITION` 与用量、损耗率同级：**录入时确定，之后不随其他 BOM 的改版而变**。

**必填规则**（效果校验键 `require-when-referenced`，迁移 416）：

| 情形 | 判据 |
|---|---|
子件在 `BOM_STRU_M` 有 BOM（半成品） | `ELEMENT_EDITION` 必填，且 `(PRO_NO, EDITION)` 必须存在 |
子件没有 BOM（材料） | 必须留空——填任何版本都不成立 |

一条规则覆盖两种情形：目标表里没有这个料号，整行跳过。所以材料留空是"规则没命中"，
而不是"另写一个分支"。

**两个版次字段语义不同，不能混**：

| 字段 | 含义 |
|---|---|
`BOM_STRU_D.EDITION` | **父件**那条 BOM 的版次（"我在哪一版父件里"） |
`BOM_STRU_D.ELEMENT_EDITION` | **子件自己**的 BOM 版次（"我自己的 BOM 是哪一版"） |

查"本件 BOM 资料"必须用后者，用前者会把父件的记录当成本件的。

**`IS_FALLBACK` 保留但恒为 0**：没有选版就没有回退。字段留着只为保持响应形状，
**新代码不应依赖它**（这一条正是本次补记的主要目的——否则后来者会以为它还在工作）。

#### 存量回填口径

| 顺序 | 规则 |
|---|---|
① | 子件有"与父件相同的版次" → 填该版次 |
② | 否则填子件的最大版次（等价于原方案的"回退最大"） |
③ | 子件没有 BOM → 留 `NULL`（材料） |

与原方案有一处细微差别：旧的是锁**根**版次，新的是按**父**版次，多层下可能不同。
但只有静态化才能消除"同一份数据不同结果"——这个差别是有意接受的代价。

#### 诚实的代价

半成品改版后，引用它的 BOM **不会自动跟随**，需要人工把明细的 `ELEMENT_EDITION` 改成新版。
这是 PLM 的"版本升级提醒 / 批量升版"能力，本期明确不做（见 6.6）。

理由是：自动跟随会让"我这一版 BOM 用的是什么"变成不可回答的问题——而那恰恰是引入
版本维度要解决的事。

#### 一处 SQL 限制（实施时踩到）

SQL Server 的**递归成员禁止 `OUTER JOIN`、`OUTER APPLY`、`TOP` 和子查询**。原方案因此
必须先算 `EDITION_PICK` 再 inner join。新方案顺带绕开了这个限制：`d.EDITION = t.OWN_EDITION`
是普通 join 条件，`OWN_EDITION` 为 `NULL`（材料）时不命中，展开自然停止。

补充：连带查看"这个料号自己的版次"这类信息，也只能放在最终投影里 `LEFT JOIN`，
不能放进递归成员。

### 6.4 深度与口径

三个数字必须收敛成一个：

| 现状 | 值 | 位置 |
|---|---|---|
| `no-cycle` 校验 | 100 | `Migrations/159_catalog_bom_stru.sql:123` |
| 展开子制令 | 20 | `ProduceGenSubHandler.cs:37` |
| 算料 | 不递归 | `ProduceCalcMaterialsHandler` |

本 ADR 定为 **100**，在 `Features/<域>/` 或 `Data/` 下声明一次，三处引用同一个常量。理由是"100 层"是防御性上限而非业务上限——真实 BOM 极少超过 15 层，设置它的目的是"数据错误时不要挂死"，不是"限制客户"。

### 6.5 虚拟件：本期不做，但留位

虚拟件（Phantom）在五家同行里都是标配：工程 BOM 有五层，制造 BOM 只有两层，中间层靠 phantom 穿透。EOS 没有，参考系统也没有——所以这是**继承，不是退步**。

但 `BOM_STRU_D` 在 D4 里会重排，**顺手加一个 `LINE_TYPE` 列**（`'N'`=普通、`'P'`=虚拟件，默认 `'N'`），成本几乎为零。将来要做穿透，不用再改一次表。

`LINE_TYPE='P'` 的展开语义（本期不实现，只留判据）：**不产出该节点的行，直接把它的子件上提到父级**，累计用量按穿透计算。

### 6.6 明确不做

以下五项**不在本 ADR 范围内**，不是"以后再说"，是"现在做会让系统变差"：

| 不做 | 理由 |
|---|---|
| **MRP 净算**（库存扣减、在途、批量策略、低层码） | EOS 没有 MRP。低层码（LLC）只在 MRP 按层净算时才必需，现在加它是给不存在的问题付复杂度 |
| **替代料 / 替代群组** | 五家里 Oracle 与金蝶都有，但它们的复杂度（优先级、使用概率、适用范围、唯一启用方案）远超当前需求。参考系统也没有 |
| **配置 BOM / 选配** | 需要 model / option class / 特征值的整套体系，是另一个量级的设计 |
| **工艺路线与工序级用料** | 现在只有"料"，没有"在哪道工序投料"。Oracle 的组件挂工序能力不在本次范围 |
| **BOM 变更单 / 工程变更（ECO）** | 当前改 BOM 保存即生效，没有"改结构必须审批"的业务要求。一旦有，它是**另一个模块**——另一张单据、另一套生命周期（草稿 → 审批 → 生效 → 归档）、另一个权限单元，且 1204 会退化为只读标准。这是唯一真正需要新模块的场景，不能用视图承载 |
| **版本升级提醒 / 批量升版** | 子件版本写进明细后（6.3），半成品改版不会自动传导。"哪些 BOM 还引用旧版、要不要批量升"需要另建一套"引用关系 + 版本落后"的查询与提示——那是 PLM 的标准能力，但对当前规模而言，人工改一行的成本低于维护这套机制的持续成本。**做之前先读 6.3 的"诚实的代价"**，那里写了为什么不做自动跟随 |

## 7. 代价

### 7.1 会失去什么

D1 改形态后，以下能力**不会自动跟着过来**，必须逐项确认是"定制页自己实现"还是"明确放弃"：

| 能力 | 现状来源 | 改形态后 |
|---|---|---|
| 列表查询 / 分页 / 排序 / 列设置 | 工作台列表 | 定制页自己画（可调同一批 API） |
| 模块权限 / 行级权限 | `SYSDD`/`SYSDH` + `DATA_FILTER` | **服务端仍生效**（`WorkbenchCommandHandler` 内），前端要自己处理 403/空集 |
| 审计 | `WorkbenchAuditWriter` | **仍生效**（同一管线） |
| 效果链 / 校验目录 | `EffectEngineInvoker` | **仍生效** |
| 批核 / 结案 | `WorkbenchApprovalService` | 仍可调，但按钮要自己画 |
| 打印 / 附件 | 工作台工具栏 | 定制页要自己接 |
| 导入导出 | 工作台工具 | 定制页要自己接 |
| 快照 / 发布 | `WORKBENCH_DEFINITION_SNAPSHOT` | 仍生效（D2 保住定义） |
| 表单设计器（版式） | `LayoutDesignerPage` | **失效**——定制页不读 `MODULE_FORM_LAYOUT` |

最后一行是隐性代价：**1204 从此不能用版式设计器调界面**，`MODULE_FORM_LAYOUT` 里那 46 行对 1204 变成死配置。这必须写进文档并在 2301 里对该模块隐藏设计入口，否则用户会改版式、然后奇怪为什么界面没变。

### 7.2 怎么补

不是所有代价都要自己吃。三条原则：

1. **能用 API 的就不重写**：`/definition`、`/form-definition`、记录读写、选择器数据源，全部复用；
2. **能用组件的就不手写**：列表用 `ErpTable`、选择器用 `UnifiedChooser`（`AGENTS.md` 硬约束），只有树是新组件；
3. **确实没有的才做**：树、展开参数面板、版本切换器、Where-used 结果表——四个新组件。

## 8. 落地顺序（只排序，不含实施细节）

顺序的依据是"谁阻塞谁"，不是"谁重要"：

1. ✅ **D9 原地修复**（六项）——已完成，落迁移 `408_bom_module_metadata_fixes.sql`；
2. **D4 版本维度**——改表 + 迁移。**必须在 D7 之前**，因为"工单 BOM 快照时选哪一版"只有版本抬到头之后才答得干净；
3. ✅ **D5/D6 展开三出口**——三个端点与递归查询已落地（`BomRepository` / `BomController`），用例 `BomExpansionLiveTests` 全绿；**「计算用料」切到毛需求出口尚未做**，它依赖 D7 的快照口径，放在下一步一起；
4. ✅ **D7 产品 BOM → 工单 BOM 快照**——处理器 + 迁移 410 已落地，用例 `BomSnapshotLiveTests` 全绿；**「计算用料」已改读工单 BOM 的单层子件**（本单直接投入的料，下阶由子制令负责），不再读产品 BOM，用例 `DocumentActionProduceCalcLiveTests` 随之改造；
5. ✅ **D2 形态解耦 + D1 定制页**——已落地：判据改为"能力位决定有没有单据面"，`M_URL` 切到 `/bom/product`（迁移 412）。
6. ✅ **子件版本进明细**（迁移 `416_bom_element_edition.sql`）——**实施后追加，且推翻 6.3 的原方案**。改表 + 存量回填 + 新校验键 `require-when-referenced`，外加六处同步：展开、毛需求、版本对比、取试算表、新建版本、工单快照。理由见 6.3。

第 6 步排到最后不是因为优先级低，而是因为它**改的是数据语义**：前五步把"树、快照、定制页"都跑通之后再动选版规则，回填口径才有现成的对照（展开结果必须与改造前一致）。反过来做会把前面每一步的验证都变成移动靶。

第 5 步与前面拆开，是因为 **D2 只在改形态那一刻才需要**：1204 在改 `M_URL` 之前一直是 `WORKBENCH`，工作台定义本来就装配得出来。提前松判据只会留下"判据已松、无人消费"的中间态，而判据是权限与审计的入口，不该空转。

**四个面全部由定制页承载**（"既然是定制页就完全定制"）：

| 面 | 组件 | 说明 |
|---|---|---|
| 列表 | `BomProductListPage` | 自绘列与操作，记录数据走 `/document-workbench/1204/records` |
| 单层维护 | `BomProductEditorPage` | 自绘布局与明细表格，**保存仍走 `PUT /record`**，载荷与统一表单逐字段一致。**双击进浏览态**（`/bom/product/:proNo/:edition`），「编辑」按钮才进可写态（`…/edit`）——与工作台 `/view`、`/edit` 同构，避免"点一下就能改"的误触 |
| 结构树 / 毛需求 | `BomTreePage` | 模式切换，共用第 6 节那一套递归遍历 |
| 反查 | `BomWhereUsedPage` | 按料号向上查父链 |

维护面**复用契约、不复用页面**：`values` / `details` / `original` 并发快照 / `detailSerials` 项次身份 / `validateMasterFields` 客户端校验，全部沿用统一表单那一套。自绘的只是布局与交互外壳——这条线是"完全定制"与"另起一套写入管线"的分界：跨过去就要重写权限、审计、效果链、幂等，那四项都已在 ADR-005/012/013/018 里逐条建立。

**版式对 1204 失效**：`MODULE_FORM_LAYOUT` 的 46 行不再被任何界面读取（见第 11 节）。

## 9. 拍板结果（2026-10-17）

三项均由用户拍板，按原提案通过：

| # | 决定 | 结果 |
|---|---|---|
| 一 | 1204 的承载形态 | **走定制页**（D1 全定制），`MODULE_FORM_LAYOUT` 对 1204 作废 |
| 二 | 版本维度 | **要做**（D4 代理键 `BOM_ID` 抬到 BOM 头） |
| 三 | 产品 BOM 与工单 BOM 的关系 | **产品 BOM 为源**，工单 BOM 为建单时的快照（D7） |

两条随拍板一并确定的边界：

- **D2 的三处判据改动随 D1 一起落**，不单独提前（理由见第 8 节末）；
- 1506 从"手工维护模块"变为"派生 + 允许人工调整"，其模块形态与权限不变，改变的只是**数据来源**。

## 10. 被否决的选项

| 选项 | 为什么否决 |
|---|---|
| 把多阶展开做成独立模块 `/bom-expand` | 129802 的老路，已被迁移 407 退役；独立模块会被模块治理判为冗余，删掉则能力归零 |
| 让定制页自建一套写入管线 | 等于重写权限、审计、效果链、幂等。这些能力在 ADR-005/012/013/018 里逐条建立，重写一次必然有一处不一致，而这类不一致表现为"权限漏判"或"审计缺行" |
| 用 `PRO_NO + EDITION` 做复合主键（**初版否决，实施时重新采纳**） | 初版顾虑是"业务文本进主键，改版次=改主键=明细级联"。实施时发现代理键会让明细必须暴露一列**可见的自增 ID**（见 5.1），而版次本就该只读、换版走"新建版本"——顾虑不成立，故改回。保留此行是为了记住这段弯路 |
| **锁版 + 逐层回退**（初版采纳，实施后推翻） | 初版认为它兼顾"整棵树锁在一个版次上"与"半成品没有该版次时不断链"。实施后发现三个问题：① 树变成**请求参数的函数**——换一个根版次结果就变，而数据一行没改；② 回退只能是事后标记（`IS_FALLBACK`），录入时无法决定"这一层到底用哪版"；③ 无法表达"同一半成品在不同父件里用不同版本"。改为明细显式指定（6.3）。保留此行是为了记住：**"运行时算"与"数据里写"的取舍，不能只按实现便利度判** |
| 展开结果物化成表 | 树是可重算的派生结果，物化即第二处真源，BOM 一改就失真 |
| 本期一并做 MRP / 低层码 | 没有 MRP 的情况下，低层码是纯粹的复杂度 |
| 保留 `MODULE_FORM_LAYOUT` 给 1204 用 | 维护面搬进定制页后，这 46 行不再被任何界面读取（与 3203 的死键同类）。清理动作另做，但**不能再让配置者改它们**——改了没反应比没有这个入口更糟 |

## 11. 与既有约束的关系

- **不违反 ADR-006**：统一表单仍是 259 个模块的默认形态，1204 是**显式的例外**，且例外本身有判据（D2 边界 + 单据形态）。
- **不违反 ADR-012**：效果链与校验目录照常作用于 1204 的写入路径。
- **要更新 ADR-033 的形态语义**：`NODE_KIND` 从"决定一切"退为"只决定页面入口"，能力位独立。
- **`MODULE_FORM_LAYOUT` 的处置（已定稿）**：维护面搬进定制页后，1204 的 46 行版式**不再被任何界面读取**，是与 3203 同类的死配置。本 ADR 不删它们（清理属独立动作，与功能解耦），但 2301 的版式设计入口应当对 1204 隐藏——**不能让配置者改一个没有消费方的东西**。
- **定制页不参与发布**：`M_URL` 切到精确路径后形态为 `CUSTOMPAGE`，230101 本就不提供发布入口；迁移 415 已清掉 1204 的历史快照与待发布标记。运行期判据是"**有快照就一定用快照**"，遗留快照会让它继续用旧定义（主键序、表名都可能是旧的）——`check-module-node-kind.ps1` 新增第 ⑤ 条守住这条：非工作台节点不得有当前快照。
- **`NODE_KIND` 与能力位的门禁口径已同步**：`check-module-node-kind.ps1` 原来断言"声明统一表单的模块必须是 WORKBENCH"，D2 之后改为"必须有主表、且形态不能是目录"，同时把"形态外残留"与"脏标记合法"两条按"有没有单据面"重判。
- **要更新 `docs/guide/03` 第七节**：新增"定制页复用工作台定义"的登记判据（D2 边界 + 单据形态），以及 D10 的四视图子路由登记要求。
- **要更新 `docs/guide/_map.md`**：新增 `EOS.Web/src/features/bom/` 域目录（迁移 407 删了文件但目录还在，D9 第 6 项会先删空目录，重建时按新结构登记）。
- **要更新 `LESSONS.md`**：本次探明的"校验用户看不见的字段"（`BASE_QTY`）与"版式行指向不可见字段"（3 行死版式）是 3203 的同族，应合并成一条"元数据的四张表要互相断言"的教训。
