# ADR-013：单据生命周期列规约（行内状态 + 独立历史 + 列模板治理）

- 状态：已落地（2026-09-15 拍板；2026-09-16 代码 + 迁移 087/088 落地；2026-09-19 真库复核收口，无剩余开放项）
- 日期：2026-09-06（草案）；2026-09-15（核心拍板）
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-012（单据行为效果配置化）、ADR-005（权限/审计/幂等）、ADR-008（字段数据源治理）、工作流 v2/v2.1（WF_MONITOR/WF_APPROVE/2101/2103）

## 1. 背景与事实

### 1.1 现状：状态/审计列以物理列方式重复出现在大量表上

对 `EOS.Database/dbo/Tables`（485 个表 DDL）扫描：

| 列族 | 出现表数 | 说明 |
|---|---|---|
| `CREATE_PERSON/CREATE_DATE` | 262/264 | 建立人/日期 |
| `LAST_UPDATE_BY/LAST_UPDATE_DATE` | 265/265 | 修改人/日期 |
| `CONFIRM_TAG/CONFIRM_PERSON/CONFIRM_DATE` | 256/256/256 | 批核状态/批核人/批核日期 |
| `OWNER/OWNER_G` | 256/255 | 数据范围（EXEC_TAG）行归属 |
| `FINISHED_TAG` | 83 | 结案状态 |
| `FINISHED_PERSON/FINISHED_DATE` | 60/60 | 结案人/结案日期 |

结论：约半数表（含几乎全部单据主表与元数据模块表）重复同一组列；`FINISHED_*` 只出现在需要结案语义的单据表，且人/日期列（60）少于状态列（83），存在不一致。

### 1.2 这些列是读路径的一等公民

状态/归属列不是"写完给人看"的展示字段，而是查询与守卫条件本身：

- "仅已批核"过滤（列表/选择器/报表口径/M10 指标语义）、待办计数、EXEC_TAG 数据范围（OWNER/OWNER_G）都在 WHERE 中引用；
- 批核/结案写路径用同行动态守卫：`UPDATE ... SET CONFIRM_TAG=1 WHERE CONFIRM_TAG=0`；
- 旧库读路径依赖深：存储过程 42 个文件 103 处 `CONFIRM_TAG`、36 个文件 154 处 `FINISHED_TAG`，另有视图引用；EOS.API 14 个 C# 文件 50 处、7 个文件 25 处；
- 删除守卫引用 `CONFIRM_TAG/FINISHED_TAG` 与库存流水。

### 1.3 "行为逻辑统一"已经成立，靠的是约定不是表结构

现代统一管线（`WorkbenchCommandHandler` 保存、`WorkbenchApprovalService` 批核/解批/结案、`WorkflowEngine` 末步落确认）以**列名约定 + ColumnExists 分支**处理所有模块；`WorkflowStates.RecordStatusColumns` 集中声明状态列。485 张异构表能被同一套元数据管线处理，前提是它们长着同样的列。

### 1.4 历史/审计与当前状态已经分离

- 动作历史：`AUDIT_EVENT`/`AUDIT_FIELD_CHANGE`（保存/批核/结案/删除、字段级 diff）；
- 流程步骤历史：`WF_MONITOR`/`WF_APPROVE`（送审/逐级/会签/驳回/撤回）。

主表上的 `CONFIRM_PERSON/DATE`、`FINISHED_PERSON/DATE` 是"最近一次生效的经办快照"，不是历史。

## 2. 问题拆解

"每张单据主表都带同一组列"实际混了三样不同性质的东西，不应捆绑讨论：

1. **审计历史**：已独立成表（见 1.4），不需要再造；
2. **当前状态位**（`CONFIRM_TAG`/`FINISHED_TAG`）：行的当前事实，被读路径过滤与被写路径守卫；
3. **最近经办人/日期**：当前状态的证据快照，供列表直接显示与追溯入口。

草案立场：把 2+3 挪到"通用状态关联表"会引入**每次读写 JOIN**，且不会减少行为代码——统一行为来自"状态列在行上"这一约定。真正的治理对象是**列规约**（列集、空值口径、命名、写入收口），而不是表结构。

## 3. 决策条款

### 3.1 状态位与经办快照保留在主表，不拆通用状态表（已决策）

- 现状延续：单据主表行内保留 `CONFIRM_TAG/FINISHED_TAG` 及最近经办人/日期；
- 不另建"单据 → 通用状态表"关联、不迁移存量 260+ 张表；
- 决策理由（按权重排序，**性能不是主要理由**）：
  1. **同行原子守卫**：`UPDATE ... WHERE ISNULL(CONFIRM_TAG,0)=0` 用"影响行数"同时完成状态翻转与并发防重；
     拆表后要么退化为"先 SELECT 再 UPDATE"（引入竞态），要么上显式事务与额外锁；
  2. **状态位与快照的一致性由同一条 UPDATE 免费保证**：拆表后 `CONFIRM_TAG=1` 且 `CONFIRM_PERSON IS NULL`
     成为可能，且"未批核"与"生命周期行缺失"塌缩为同一个 NULL——与"状态位严格 NOT NULL"直接冲突；
  3. **列表排序/过滤能力**：虚拟列机制（`IsVirtual` + `VirtualExpression`）可在列表渲染，但
     **不可排序、不可过滤**（`WorkbenchQueryComposer` 中排序白名单排除虚拟列、过滤遇虚拟列直接拒绝）；
     而建立/修改/批核日期恰是列表最高频的排序与筛选列，移出主表即丧失该能力；
  4. **删除与复制**：拆表后删除需级联，残留孤儿不指向任何主表行、无法被任何校验发现，
     却会污染按日期的统计；复制单据从单行 `INSERT` 变为两处写入；
  5. **统一管线前提**：`WorkbenchCommandHandler`/`WorkbenchApprovalService` 以"列在行上"为约定
     处理 485 张异构表，这是 ADR-012 效果链触发点的假设；
  6. 读路径单表过滤（无需 JOIN）、避免通用键失去外键约束与删除级联、避免共享热表锁竞争。
- 例外边界：一单多流程实例/多审批维度/会签历史已由 `WF_*` 独立承载；未来若出现"同一单据多个相互独立的状态维度"，
  仅对全新模块试点独立状态行，不迁移存量。
- **"最近经办快照"不是"过程"**：主表只记最后一次，完整过程由 `AUDIT_EVENT`/`AUDIT_FIELD_CHANGE`/`WF_*`
  承载（见 3.2）。以"主表列本意是记录过程"为由移除它们不成立——主表列本就记录不了过程。

### 3.2 历史不回流主表，主表只保留最近快照

- 全量历史继续由 `AUDIT_EVENT`/`AUDIT_FIELD_CHANGE`/`WF_*` 承载；
- 需要"审批历史/变更历史"展示时读独立表，不新增主表历史列。

### 3.3 单据生命周期列规约（列集 / 空值 / 命名 / 写入收口）

1. **列集**：单据主表的标准生命周期列 = 建立人/日期、修改人/日期、批核状态/人/日期、结案状态/人/日期、OWNER/OWNER_G；明细表按需只取部分（含"明细行结案"形态）；
2. **空值口径**（已决策，2026-09-16 精炼）：只收紧状态位与建立组，其余永久可空——状态位（`CONFIRM_TAG/FINISHED_TAG`）一律 `NOT NULL DEFAULT 0`（存量 NULL 批量补 0）；`CREATE_PERSON/CREATE_DATE` 为 `NOT NULL`（新建即由服务端写入，存量按"人填空串表未知、日期回溯修改日期" best-effort 回填）；`LAST_UPDATE_*`/`CONFIRM_PERSON/DATE`/`FINISHED_PERSON/DATE` **永久保持可空**（NULL = 事件尚未发生：未修改/未批核/未结案，回填即伪造历史，不补不收紧），只接受"事件发生即同步写入"的写入收口；
3. **命名**：统一采用既有全大写命名，不允许新增同义变体（如 APPROVE_STATE/CONFIRM_TAG 并存）；
4. **写入收口**：这些列的写路径收敛到统一管线（保存/批核/解批/结案/工作流末步）；旧 SP 直写随 ADR-012 二期迁移逐步退役；
5. **可选性矩阵**：见 3.7（按模块类型分层强制，能力 → 列单向强制）；
6. **新表列治理**：不设 DDL 模板、不自动补列——物理列变更只走 DbUp 版本化迁移；
   配置期由菜单管理主表页签按物理列实时提示缺列，发布期由 `lifecycle_columns` 门按能力拦截
   （见 3.7 与第 6 节第 2 项）；已存在的结构漂移由 `scripts/check-lifecycle-columns.ps1` 巡检。

### 3.4 与 ADR-012 的关系

- ADR-012 的效果链把状态位当守卫与读条件：行内状态保证效果链触发点（APPROVE_EFFECT/DEAPPROVE/ENDCASE）语义一致；
- 本规约的"写入收口"与 ADR-012 Phase C/D（legacy-sproc 退役、UPDATE_SP/AFTERSAVE_SP 收敛）同向，可并入同一实施窗口治理。

### 3.5 系统列组：元数据层隔离（本 ADR 的核心落地增量）

生命周期列（建立人/日期、修改人/日期、批核状态/人/日期、结案状态/人/日期）定性为**系统列**：
由服务端自动产生，不是用户输入项。隔离发生在**元数据与呈现层，不动表结构**。

1. **单点定义**：列集清单收敛到服务端一处。现状散落 4 处且互相不一致——
   `RecordPayloadValidator.AuditColumns` 与 `ImportService.IsAuditColumn` 各自重复定义 4 列、
   `WorkflowStates.RecordStatusColumns` 定义 4 列、`FormFieldSelector` 注释声明 8 列由服务端持有
   但实现只覆盖其中 4 列（批核/结案人日期未纳入）。清单不统一，规约无从落地；
2. **服务端独占写入**：保存/批核/解批/结案/工作流末步统一写入，客户端提交的同名列一律忽略；
3. **元数据呈现**：字段管理（FieldAdmin）中标记为系统列组，默认隐藏、只读、不可删除。

### 3.6 表单与列表呈现规则（已决策）

| 场景 | 呈现 |
|---|---|
| 统一表单 新增态 | 隐藏（服务端生成，无需用户输入） |
| 统一表单 编辑态 | 隐藏 |
| 统一表单 浏览态 | 只读显示（批核/结案人日期为追溯入口） |
| 列表选择列 | 可选，维持现状（2026-09-16 修订：`SYSQL_DEFAULT` 现存上百行系统列默认，改默认属全员可见行为变更，暂不执行；原"默认不勾选"收回） |

- 实现前提：统一表单当前按 `isVisible` 过滤且不区分态，需引入按系统列组的态感知过滤；
- 列表对这些列的**排序与过滤保持可用**——这正是它们留在主表的收益（见 3.1 理由 3）。

### 3.7 模块类型分层强制与显式校验（已决策）

强制的对象是**"模块声明"与"列集"的一致性**，不是"凡走统一工作台的模块一律全建这组列"：

| 模块类型 | 生命周期列 | 可得能力 |
|---|---|---|
| 单据型（有批核/结案/流程） | 全组必备 | 批核/解批/结案/流程全部可用 |
| 档案型（纯 CRUD/字典） | 可不建 | 列表不出现这些列、工具栏不出批核/结案按钮 |

- **能力 → 列 单向强制**：任何模块只要启用批核/结案能力，就必须具备对应状态位，与其类型无关；
- **消灭静默降级**：现状 `WorkbenchApprovalService.AutoApproveAsync` 在缺 `CONFIRM_TAG` 时直接返回
  成功且不做任何事，使用者以为已批核。改为由模块类型声明驱动——单据型缺列在模块校验时报错并引导补列；
  档案型显式声明无生命周期能力（不提供批核入口）；不在运行期靠 `ColumnExists` 静默跳过。

## 4. 明确不做 / 边界

- 不做全库拆表迁移；不引入"事件溯源作为状态唯一事实源"（可另行讨论，v1 不做）；
- 不把 `OWNER/OWNER_G` 挪出行（它们是权限数据范围的行归属，同族但语义不同，纳入同一规约的列集治理、但不拆表）；
- 本 ADR 不拍板具体 DDL 模板 SQL、存量差异清理批次与治理工具形态。

## 5. 风险与权衡

- **治理范围大**：涉及约 260 张存量表，差异清单（FINISHED_* 83 vs 60、NULL 口径、命名变体）需先盘点；
- **存量修正风险**：空值口径/补齐列属行为变更，需顾问逐表确认（对齐旧系统行为）；
- **收益**：新表不再手写列、管线写入单一化、列语义文档化，配合 ADR-012 后"单据生命周期"成为可解释的统一模型；
- **回归面**：列规约不迁移数据时回归面小；一旦涉及存量 NULL/列补齐，回归面扩大，需分域推进。

## 6. 剩余开放问题

1. `FINISHED_*` 只出现在 83 张表且人/日期仅 60 张：差额 23 张是否为"明细行结案"
   （`SFC_PLAN_D`/`SFC_DAILY_D`/`SFC_PRODUCE_D` 有 `FINISHED_TAG` 但无人/日期）？需盘点确认，
   不预设为"遗漏"而盲目补齐；
   → 已盘点关闭（2026-09-16，真库）：差额 23 张**全部**是明细表（`*_D` 明细行结案形态，
   仅 `FINISHED_TAG`、无人/日期），主表形态全部人/日期齐全；结论：不补齐，关闭本项。
2. 新表模板的形态：DbUp 迁移脚本模板 vs FieldAdmin 建表模板 vs 代码生成？
   → 已定并落地（2026-09-16）："拒绝发布 + 配置期提示"，不拦保存、不自动补列——
   发布拒绝由 `lifecycle_columns` 门承载（能力条件式）；配置期提示由菜单管理主表页签
   按主表物理列实时预警（仅提示）；保存保持草稿语义不拦截（模块按主表→能力逐步配置）；
   不设一键自动补列（物理列变更走 DbUp 版本化迁移纪律，不开第二 DDL 入口）；
3. 列规约治理与 ADR-012 Phase A 台账的先后顺序与批次划分；
   → 已关闭（2026-09-19）：空值收紧按"一次性全库"执行（迁移 088 覆盖全部 dbo 表，非按域分批），
   与 ADR-012 的遗留过程退役无耦合——写入收口随管线单点化已经成立（库内仅剩 1 个过程，且与生命周期无关）。
4. 未来"多审批维度"若出现，独立状态行的数据模型先例如何定义（不迁移存量，仅新模块试点）；
5. 存量 260 余张表的列差异盘点与补齐批次（NULL 清零方向已定，按域推进顺序待定）；
   → **✅ 已落地并复核（2026-09-19）**：口径按决策 #102（精炼：仅状态位与建立组 `NOT NULL DEFAULT`，其余 6 列永久可空）/
    #103（新表"拒绝发布 + 配置期提示"）执行；迁移 088 已全库一次性收紧（真库复核：可空列 0 / 缺 DEFAULT 约束 0 /
   存量 NULL 残留 0），无需按域分批；巡检脚本 `scripts/check-lifecycle-columns.ps1`（2026-09-19 复跑 PASS、exit 0，
    1 条非阻断提示 `dbo.INV_OCCUR_IN_M.LAST_UPDATE_BY`）；列"补齐"由 3.7 的能力 → 列单向强制在发布期拦截，
   不预设补齐批次（档案型模块可不建，实测 38 个只读/报表类模块即属此类）。
6. 系统列组的单点清单落在哪个类/表（新增 `LifecycleColumns` 常量类，或扩展 `WorkflowStates`）？
   → 已定并落地（2026-09-16）：扩展 `WorkflowStates`（`LifecycleColumns` 13 列 =
   10 个生命周期列 + 归属三列 `CI`/`OWNER`/`OWNER_G` /
   `LifecycleTagColumns` / `LifecycleActorColumns` / `RecordStatusColumns` 6 列），
   `RecordPayloadValidator.AuditColumns` / `ImportService.IsAuditColumn` /
   `FormFieldSelector.HiddenStatusTags` 均委托，不新增类。

## 7. 已拍板结论

- 状态位 `CONFIRM_TAG/FINISHED_TAG` 与 8 个经办列**保留在单据主表**：不拆通用状态表、不迁移存量（3.1）；
- 隔离发生在元数据与呈现层（系统列组），**不动表结构**（3.5）；
- 统一表单新增态/编辑态隐藏、浏览态只读显示、列表选择列可选（3.6）；
- 缺列从"运行期静默降级"改为"按模块类型显式校验"（3.7）；
- 空值口径按 §3.3.2 精炼口径执行（2026-09-16 修订）：只收紧状态位（存量 NULL 补 0）与建立组（存量 best-effort 回填）；`LAST_UPDATE_*`/`CONFIRM_PERSON/DATE`/`FINISHED_PERSON/DATE` 永久可空（NULL 表事件未发生）；原"存量 NULL 批量补 0 后一律收紧"措辞收回（人/日期列无法补 0，硬填即伪造历史）；
- `FINISHED_PERSON/FINISHED_DATE` 补齐进记录读取契约——结案多为下游单据完成时由系统回写，
  仍需在浏览态与列表中可读；
- 新表模板需覆盖"明细行结案"（`*_D` 表带 `FINISHED_TAG`），不得只按主表形态设计；
- 不引入事件溯源作为状态唯一事实源（v1 不做，可另行讨论）。
