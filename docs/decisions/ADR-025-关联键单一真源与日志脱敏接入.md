## 摘要（先读我，写给人类）

**要解决的问题**：今天"关联键"有两个口径，写日志的两条路径各自取了不同的值。

- 请求级日志（`http_request`）、响应体 `correlationId`、响应头 `X-Correlation-Id`、审计
  `AUDIT_EVENT.CORRELATION_ID` —— 用的是 **`RequestContext`**（即调用方传进来的 `X-Correlation-Id`）；
- 异常出口（`GlobalExceptionHandler`）与被映射的业务拒绝（`ApiExceptionFilter`）的日志字段
  `correlation=` —— 用的是 **`context.TraceIdentifier`**。

后果：用户按界面/响应里拿到的关联键去 `logs/api-json.log` 检索，**正好查不到那条异常**。
排障 SOP（`AGENTS.md`「排障」、`docs/guide/31-运行日志与诊断.md` §八）建立在这个键上，
所以这是"流程正确但证据对不上"的一类缺陷。

**第二个问题**：`LogRedactor` 存在但**没有接进文件日志管道**——它当前唯一的调用点是会话记忆的
敏感值脱敏（`Features/Assistant/Memory/AssistantMemoryStore.cs:210`）。指南写的"输出前对所有
字符串字段与消息应用"与实现不符；一旦要做日志打包外发（ADR-029），未脱敏日志外发就是一次隐私事故。

**本 ADR 的决定，用一句话说**：

> **关联键只有一个真源：`RequestContext.GetCorrelationId(context)`；所有出口（日志/响应体/响应头/
> 审计/前端诊断信息）都读它。日志在唯一出口（provider 写入前）统一过 `LogRedactor`，
> 不靠调用点自觉。**

## 1. 背景：证据

| 口径 | 取值来源 | 落点 |
|---|---|---|
| 正确口径（中间件/响应体/审计） | `RequestContext`（`X-Correlation-Id` → 回退 `TraceIdentifier`） | `Middleware/RequestLoggingMiddleware.cs:27,63-68`、`Errors/ApiProblem.cs:68`、`Data/WorkbenchAuditWriter.cs:56` |
| 偏差口径（异常出口） | `context.TraceIdentifier` | `Middleware/GlobalExceptionHandler.cs:35` |
| 偏差口径（业务拒绝） | `context.TraceIdentifier` | `Errors/ApiExceptionFilter.cs:41` |
| 脱敏未接线 | `LogRedactor` 已实现 8 条模式，唯一调用点在会话记忆 | `Logging/LogRedactor.cs:12-36`；grep `LogRedactor` 仅 2 处命中 |
| 写入侧未脱敏 | provider 直接序列化 state 与 message | `Telemetry/JsonFileLoggerProvider.cs:57-68` |
| 指南与实现不符 | 指南称"输出前对所有字符串字段与消息应用" | `docs/guide/31-运行日志与诊断.md:80-92` |
| 前端一次操作一键（缺失） | 每个请求各自生成 correlationId | `EOS.Web/src/services/api/httpTransport.ts:16,39` |
| 前端关联键不可见（缺失） | 已解析 `correlationId`/`definitionVersion`，无展示与复制入口 | `EOS.Web/src/services/api/httpTransport.ts:28-30`、`EOS.Web/src/types/api.ts:32` |
| 客户端上报不含关联键 | 上报字段仅 kind/message/stack/url | `EOS.Web/src/lib/errorReporting.ts:27-35,45-50` |

附带事实：

- `ApiExceptionFilter` 用 `LogDebug` 记录，而文件日志门限是 `Warning`（`Program.cs:37`）⇒
  业务拒绝的"异常出口自述"**不落盘**，文件里只有中间件那一条。这是设计使然（决策 #50），
  本 ADR **不改级别**，只保证中间件那一条的键是对的；
- 指南 §四 要求"调用方应主动传 `X-Correlation-Id`：一次用户操作可能触发多个请求，用同一个值
  串起来"，与前端现状（每请求一键）相悖。

## 2. 决策

### 2.1 关联键单一真源（后端）

所有写 `correlation`/`correlationId` 的地方**一律**改读 `RequestContext.GetCorrelationId(context)`，
禁止再直接使用 `context.TraceIdentifier` 作为 correlation 值。
`traceId` 仍保留 `TraceIdentifier` 回退语义——**两者是不同字段，不要合并**。

### 2.2 脱敏收口在唯一出口

`JsonFileLoggerProvider` 在**序列化前**对以下内容应用 `LogRedactor.Redact`：

- 格式化后的 `message`；
- `fields` 中所有 `string` 值（容器类型按字符串边界处理，不深入递归业务对象）。

同时新增一条纪律（写进代码注释与指南）：**脱敏是兜底，不是许可**——不得因为"有脱敏"就往日志里
丢整行业务数据、附件正文、LLM 全文（沿用 ADR-005 §5.1 的禁止清单）。

### 2.3 前端：一次用户操作一个关联键，且诊断信息可见

- `httpTransport` 支持"外部注入 correlationId"（由操作发起处生成并传入），未注入时保持现行为；
  助手流式接口已有同类做法（`features/assistant/useChatStream.ts:77-78`），统一到
  `lib/uuid.ts` 的同一函数；
- 解析响应头 `X-Correlation-Id`（服务端已回写，`RequestLoggingMiddleware.cs:31`）与响应体的
  `correlationId`/`definitionVersion`，**由错误提示组件提供"复制诊断信息"**（键 + 版本 + 时间 + 路径）；
- 客户端错误上报带上 `correlationId`。

### 2.4 零迁移、可回退

本 ADR **不新增库对象、不改数据、不改配置文件**。回退 = 把取值换回 `TraceIdentifier`、
摘掉 provider 里的脱敏调用。

## 4. 已知后果（必须写明，接受）

- **(a) 历史日志里的 correlation 值不会追溯修正**：改动前已落盘的异常记录仍带旧口径值，
  排障时要知道"2026-09-29 之前的异常行 correlation 字段可能是 TraceIdentifier"。
- **(b) 脱敏是模式匹配，必然有漏与误伤两面**：已知模式外的敏感形态（自定义字段值、备注里的口令）
  不会命中；反过来 `Server=` 一类模式可能把正常业务文本切成掩码。**取舍是"宁可漏掉掩码、
  不可放过凭据"**，因此模式清单只增不减须谨慎（见 §8）。
- **(c) 打码会降低排障信息量**：命中掩码后原文不可恢复，属预期代价。

## 5. 替代方案（考虑过但未选择）

| 方案 | 未选择原因 |
|---|---|
| 在各调用点自行脱敏 | 与"唯一出口"相悖：新增调用点必然遗漏，且无法用测试穷举；历史已证明静态约定守不住 |
| 引入 Serilog 的 destructuring policy 做脱敏 | 引入依赖的决策应单独拍板（见 ADR-027 §5），不夹带在本 ADR 里 |
| 在读取侧（排障工具/打包器）脱敏，写入侧不动 | 会把敏感值**留在磁盘上**：机器被取走或日志被复制即泄露；且打包路径不止一条 |
| 给 correlation 与 traceId 取同一个值 | 两者语义不同（业务关联键 vs 分布式追踪标识），合并会丢掉 trace 传播能力 |

## 6. 验收标准

1. **口径一致（可判别）**：带自定义 `X-Correlation-Id` 的失败请求（构造 500 与 403 各一例），
   断言：响应体 `correlationId` == 请求头值 **且** 文件日志中该请求的异常行 `correlation=` 同一值
   ⇒ 用该值 grep 文件日志**恰好**命中该请求的相关行；
2. **脱敏生效（正反例）**：一条含 `Password=…` / `Authorization: Bearer …` / `Server=…` 的日志
   落盘后文件中只出现掩码；**反例**：一条只含正常业务中文文本的日志**不得**被改动；
3. **前端可交付关联键**：界面上能复制到"关联键 + 版本 + 时间"；上报的后端日志行含同一关联键；
4. `dotnet build` 0 错、`npm run lint` + `npm run build` 0 错、相关单测全绿；
5. `docs/guide/31-运行日志与诊断.md` 的脱敏与关联键章节与实现一致（不再出现"已应用但实际未接线"）。
