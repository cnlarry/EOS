# ADR-037：数值精度与显示格式的分层治理——精度跟主数据、格式跟读者

- 状态：**已接受并实施完成（2026-10-17）**——十项决定见第 2 节，四批实施的进度与收口结论见第 3 节，拍板结论见第 8 节
- 日期：2026-10-17
- 决策者：用户（Larry）+ 开发 Agent
- 前置依赖：**ADR-038（数值列的语义标准化）**——本文的精度讨论建立在"存储能表达小数位"之上，该前提由 ADR-038 负责做实
- 相关：ADR-017（系统参数纵向化）、ADR-036（共享原语单一真源）、ADR-013（单据生命周期列规约）、`FIELDS`、`CURR`、`UNIT`、`docs/guide/06-测试与质量门禁.md`

> 大白话：**"怎么看"跟读者走，"算多少"跟物走。**
> 千分位与小数点符号是读者习惯（同一份数据，中国财务看 `1,234.56`、德国财务看 `1.234,56`），
> 归 locale；小数位是数字的商业含义（日元没有分、千克有三位小数），归货币与单位主数据。
> 系统参数只装"全库真的只有一个值"的那几个——这也是 ADR-017 给 `SYSSS` 定的边界。
>
> **存储类型不在这里决定**：库内 2074 个 `float` 列如何换成 `decimal` 由 ADR-038 承载。
> 本文只负责"精度怎么算、格式怎么显示"。

## 1. 背景与证据

### 1.1 两个问题被混为一谈

此前讨论把"千分位用什么符号"与"小数点后保留几位"放在同一个"系统参数"里考虑。二者性质不同：

| 问题 | 性质 | 应当归属 | 判据 |
|---|---|---|---|
| 千分位符、小数点符 | 表示层 / 读者偏好 | **用户或 locale** | 同一份数据，不同读者看到的符号不同 |
| 小数点后几位 | 业务 / 会计口径 | **货币、单位、税码等业务对象** | 同一读者、不同数字，位数不同 |

ADR-017 已定：`SYSSS` 是**全库唯一值**表，不做作用域与继承。用它装"每人一个值"（千分位）是维度错配；
用它装"每种货币一个值"（金额小数位）同样是维度错配。

### 1.2 现状：四层只齐了两层

一个数字在系统里有四个精度，现状如下：

| 层 | 现状 | 证据 | 评价 |
|---|---|---|---|
| ① 存储 | 历史业务表数值列**几乎全是 `float`** | §1.5 | **最严重缺口** |
| ② 计算 | 金额固定 2 位、`AwayFromZero` 硬编码 | `EOS.API/Data/AmountCalculator.cs:8,42` | 缺口 |
| ③ 显示 | `FIELDS.DISPLAY_FORMAT` 自由文本；**未配置时无千分位、无小数位** | `EOS.Web/src/features/document-workbench/fieldFormat.ts:138`；`EOS.Web/src/features/field-admin/FieldEditorForm.tsx:611` | 半成品 |
| ④ 输入解析 | 全角/千分位剥离 + `InvariantCulture` | `EOS.API/Data/RecordPayloadValidator.cs:324` | 已达标 |

第 ③ 层"未配置即裸奔"已被测试固化：

```29:31:EOS.Web/src/features/document-workbench/fieldFormat.test.ts
expect(formatFieldValue(1234.5, 'float', '#,##0.00')).toBe('1,234.50')
expect(formatFieldValue(1234.5, 'float', null)).toBe('1234.5')
```

即：**同一个金额字段，配了格式才显示 `1,234.50`，没配就显示 `1234.5`。** 而 `DISPLAY_FORMAT` 在字段设置面
是一个纯自由文本框（`FieldEditorForm.tsx:611`），既无下拉也无格式串校验，业务人员无法安全地表达
"千分位 + 2 位小数"。

### 1.3 千分位是自写正则，且 locale 与币种硬编码

```115:115:EOS.Web/src/features/document-workbench/fieldFormat.ts
return grouping ? result.replace(/\B(?=(\d{3})+(?!\d))/g, ',') : result
```

```55:55:EOS.Web/src/features/document-workbench/fieldFormat.ts
return new Intl.NumberFormat('zh-CN', { minimumFractionDigits: d, maximumFractionDigits: d }).format(num)
```

```65:65:EOS.Web/src/features/document-workbench/fieldFormat.ts
return new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(num)
```

三处问题：

1. 自写正则假定**分组恒为 3 位**。印度地区是 `1,23,456.78`（2-2-3 分组），会算错；
2. 分隔符硬编码为逗号。法语区是**不换行空格**（`1 234,56`）、瑞士是撇号（`1'234.56`）；
3. 货币格式硬编码 `CNY`，与库内 `CURR` 币别主档冲突——外币单据的金额会显示成人民币符号。

CLDR（Unicode 的 locale 数据标准）已经把这些规则定义完整，浏览器 `Intl.NumberFormat` 原生支持。
自写分组逻辑是在重造一份必然不完整的实现。

`DECIMAL_PLACES` 均为 0 命中。

### 1.5 前置问题：金额列几乎全是 `float`

这是本次调研中比"千分位怎么配"更根本的发现，必须先摆出来：

| 统计项 | 实测值 |
|---|---|
| `db/bootstrap/10_schema.sql` 中 `[float]` 列 | **2074**（分布在 **267** 张表） |
| `[decimal]` 列 | **3** |
| `[numeric]` / `[money]` 列 | 0 / 0 |
| 列名为 `AMOUNT`/`PRICE`/`CURR_RATE`/`TAX_RATE`/`QTY` 且类型为 `float` | **435** |
| 含 `AMOUNT [float]` 的表 | **112 张**（`COP_ORDER_M`、`PUR_PURCHASE_M`、`CUS_ACCOUNT_M`、`INV_OCCUR_*` 等） |

后果直接写在现有代码的注释里：

```82:85:EOS.API/Data/RecordPayloadValidator.cs
/// decimal/numeric 超精度校验：precision/scale 源自 sys.types 随 form-definition 下发。
/// 仅 decimal/numeric 启用——float 无精度语义、money 固定 scale=4，均不适用。
/// 校验为拒绝式（不做静默舍入），与服务端 decimal away-from-zero 语义一致。
```

即：**超精度校验（`SCALE_EXCEEDED`/`PRECISION_EXCEEDED`）对 435 个金额/价格/数量列全部不生效**——
因为它们的类型是 `float`，而 `float` 在 `sys.types` 里没有 scale。前后端一致的那套校验只对库里那 3 个
`decimal` 列起作用。

`AGENTS.md` 写的"金额、数量精度以服务端为准"，目前的落地状态是**服务端没有精度约束**，
精度实际由显示格式（`DISPLAY_FORMAT`）承担——这是本末倒置：显示格式随时可改，而数值已经落库。

范围界定（重要，避免把问题说大）：

- 356 个迁移脚本中**没有一条新增 `float` 列**（含 `float` 字样的仅 4 个，均为读写既有列）；
- 3 个 `decimal` 迁移全部在助手域（`291`/`292`/`294`），说明新代码已经在用正确类型；
- 因此这是**历史业务表存量债**，不是仍在扩散的活债。

**处置不在本文**：类型族、语义登记与分批迁移见 **ADR-038**（本文的前置）。本文只保留"写入边界舍入"——
这一条不依赖存储类型，能在 038 完成前独立生效。

### 1.6 同一语义已有四处真源

| 场景 | 格式来源 | 证据 |
|---|---|---|
| 屏幕 | `FIELDS.DISPLAY_FORMAT` | `fieldFormat.ts:145` |
| 打印/PDF | `layout.json` 每列自带 `format` | `EOS.API/ReportFormats/1404/layout.json:191`（`#,##0.######`）、`:217`（`#,##0.00`） |
| 计算 | 代码常量 | `AmountCalculator.cs:42` |
| 迁移基线 | 代码常量 | `EOS.API/Data/DocumentPdfService.cs:53-74`（已标注整体退役） |

四处各自演进，同一张单据在屏幕与打印上可能显示不同位数。

### 1.7 同行做法（调研结论）

| 产品 | 千分位/小数点符号 | 金额小数位 | 数量小数位 | 舍入 |
|---|---|---|---|---|
| **SAP** | **用户个人设置**（`SU3` → 十进制计数法），三选项：句点 / 逗号 / 空格；只影响显示 | **货币**（表 `TCURX`，事务码 `OY04`）：JPY/VND = 0 位，默认 2 位 | **单位**（表 `T006`，事务码 `CUNI`） | 定价过程舍入规则 + 货币舍入；低价物料用"价格单位"（每 100 件）绕开精度 |
| **Odoo** | 跟随**用户语言**，无系统开关 | **货币记录**单独定义 | `Decimal Accuracy` 按**用途**命名（`Product Price`/`Product UoM`/`Discount`/`Stock Weight`） | UoM `Rounding` 属性；现金舍入是独立的会计功能 |
| **Oracle NetSuite** | 由国家格式决定（美国 2 位、日本 0 位） | 账户级 `Decimal Precision`，**UI 不可改**，需联系厂商 | 数量/单价各自精度 | 币种上 `Rounding Method`：Round up / Down / Nearest |
| **Dynamics 365** | 随用户区域设置 | 货币上 `Decimal places` | 单位上小数位 | 货币上 `Rounding precision`（`0.01`/`0.05`/`1`/`1000`）+ `Rounding method`（Normal/Up/Down），可定义多条规则 |
| **用友 U8** | 全局 | 【数据精度】一个对话框 **8 项**：存货数量/体积/重量、存货单价、开票单价、件数、换算率、税率 | 同左 | 改动需独占、需重启 |
| **金蝶 K3** | 全局 | 精度挂在**物料/计量单位** | 同左 | **精度只能改大不能改小**——1.003 入库后改成 0 位，库存永远剩 0.003 出不完 |

三条可迁移的结论：

1. **没有一家把千分位做成系统参数**；符号一律跟用户或国家，只影响显示。
2. **没有一家用一套全局参数管所有小数位**；金额跟货币、数量跟单位是共同解。
3. 精度变更被视为**受限变更**（NetSuite 干脆不开放给用户改），因为它牵连历史数据。

## 2. 决策

### 决定一（四层分离，互不越界）

存储、计算、显示、输入解析四层各自独立治理，任何一层不得替另一层做决定：

- **存储精度** = 数据库列类型，不做参数化；
- **计算精度** = 业务对象（货币/单位）+ 业务语义（单价/汇率/税率，见决定三、四）；
- **显示精度** = 字段元数据 + 读者偏好，**只影响呈现**；
- **输入解析** = 宽容但有确定性规则（决定八）。

### 决定二（存储：新列一律 `decimal`，历史 `float` 分批治理）

**存储类型不在本 ADR 决定，统一由 ADR-038 承载**（五族标准类型 + 语义登记 + 分批迁移）。本文只约定两件事：

- 新增列的类型规则由 ADR-038 的门禁强制，本文不另立一套；
- 在 ADR-038 批 A 完成前，写入路径按"货币小数位"做一次 `decimal` 舍入后再落库，保证**入库的值就是最终值**；
  批 A 完成后该舍入仍然保留（它与存储类型正交），但不再是精度约束的唯一来源。

依据：`float` 无 scale 语义，现有超精度校验对它们全部失效（§1.5）。但把 267 张表的类型迁移写进本文，
会让"精度参数上线"被类型迁移的进度绑架；两件事分开验收更清楚。

### 决定三（金额精度跟货币）

`CURR` 增两列：

| 列 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `DECIMAL_PLACES` | `tinyint` | `2` | 该币种金额的小数位；按 ISO 4217 的 minor unit 取值（JPY/VND = 0、KWD/BHD/OMR = 3、CLF = 4） |
| `ROUNDING_METHOD` | `nvarchar(16)` | `AWAY_FROM_ZERO` | `AWAY_FROM_ZERO`（会计四舍五入）/ `HALF_EVEN`（银行家舍入）/ `UP` / `DOWN` |

`AmountCalculator` 改为接收币种精度与舍入方式，删除 `Round2` 常量。金额类显示精度、入账精度、
写入边界舍入三者同源取这里的值。

依据：SAP `TCURX`/`OY04`、NetSuite 币种、D365 货币；ISO 4217 的 minor unit 差异。

### 决定四（数量精度跟单位）

`UNIT` 增一列 `DECIMAL_PLACES`（`tinyint`，默认 `3`），语义是该计量单位允许的数量小数位
（`个` = 0、`千克`/`米` = 3）。数量类字段的精度取行上 `UNIT_ID` 对应值，取不到时回落该默认。

单价不定在主数据上：单价精度是**业务语义**（用友把它拆成"存货单价 / 开票单价"两套），
本 ADR 取"单价固定 `decimal(18,6)`、显示按字段格式"（与现打印版式 `#,##0.######` 一致）。

依据：SAP `T006`/`CUNI`、金蝶物料精度、Odoo `Product UoM`、D365 单位小数位。

### 决定五（千分位不做系统参数，交给 locale）

- **不新增**任何"千分位符 / 小数点符"的系统参数或字段；
- 删除 `fieldFormat.ts` 的自写分组正则（`:115`），统一走 `Intl.NumberFormat(locale, …)`；
- 删除硬编码的 `'zh-CN'`（`:31`、`:55`、`:166`）与 `currency: 'CNY'`（`:65`），货币符号取 `CURR` 主档；
- locale 三级：

| 场景 | locale 来源 | 理由 |
|---|---|---|
| 屏幕 | **用户偏好**（首选浏览器语言，见 §8 待定 3） | 读者视角 |
| 打印 / 导出文档 | **系统地区**（一个部署一个值） | 文档对外，应使用公司法定格式 |
| API / 集成 / CSV 数据 | **恒 `InvariantCulture`**（点号小数、无千分位） | 机器读，不得随读者变化 |

依据：SAP `SU3` 用户级三选项（只影响显示）、Odoo 跟随用户语言、CLDR 已定义全部分组规则。

### 决定六（显示精度三级回落，负数支持会计括号）

显示格式的取值顺序由"裸奔"改为三级：

1. 字段 `FIELDS.DISPLAY_FORMAT`（显式配置，最高优先）；
2. **按数据类型 + 货币/单位推导的默认**：金额 → `#,##0.` + 货币小数位；数量 → `#,##0.` + 最多 6 位去尾零；
   整数 → `#,##0`；日期 → `yyyy-MM-dd`；
3. 原始值（兜底，仅在无法判定类型时）。

同时补齐两项显示能力：

- **负数会计表示**：格式串支持 `#,##0.00;(#,##0.00)` 语义（分号分段 = 正;负），默认仍用负号；
- `DISPLAY_FORMAT` 的字段设置面由自由文本改为**"预设下拉 + 高级自定义"**：预设覆盖
  "整数 / 2 位小数 / 4 位小数 / 千分位金额 / 百分比 / 日期"，自定义仍允许写格式串，保存前校验可解析。

依据：CLDR 把 `accounting` 格式与普通格式分开定义（负数为括号）；S/4 的 ALV 列格式亦为"字段默认 + 用户覆盖"。

### 决定七（显示精度不得回流）

- 排序、筛选、分组、合计、导出**一律用原始值**，不得用格式化后的字符串；
- 显示位数**可以少于**存储位数，但不得因此改变任何计算结果；
- 导出 Excel 保持 `ss:Type="Number"`（现状已正确，见 `DocumentWorkbenchController.cs:427-429`）；
  CSV 输出 invariant 原始值，不写千分位；
- 前端不承担金额计算的真源：`amountCalculator.ts` 保留作即时预览，最终值以服务端返回为准（现状一致）。

依据：显示精度污染计算是财务最不可接受的缺陷形态（"每行显示都对，加起来差一分"）。

### 决定八（输入解析不猜歧义）

- 解析按**当前用户 locale** 进行，并做确定性回退：能唯一解析为数值才接受；
- **歧义值不猜**：`1,234` 在 `en-US` 是 1234、在 `de-DE` 是 1.234——当同一串在候选解释下得到不同数值时，
  按"当前 locale 的解释"取，并在字段上提示解析结果（不让用户提交后才发现被理解成另一个数）；
- 全角数字、前后空格、货币符号仍然剥离（现状保留）；
- 负数括号输入 `(1,234.56)` 解析为 `-1234.56`。

依据：SAP 的 `decimal notation` 同时决定输入解析口径；跨 locale 的数值歧义是真实的数据错误来源。

### 决定九（精度变更是受限变更）

`CURR.DECIMAL_PLACES` 与 `UNIT.DECIMAL_PLACES` 属**受限变更**：

- 已有业务数据后，**只允许改大、不允许改小**（改小会让历史数量出现无法清零的尾差——金蝶的 0.003 教训）；
- 改大需二次确认并写审计（复用 `SystemParameterService` 的审计口径或字段变更审计）；
- 改小需走迁移评审，不在界面开放；
- `DISPLAY_FORMAT` 与 locale 属**自由变更**，不设限制。

### 决定十（打印格式与屏幕同源）

`layout.json` 每列的 `format` 由"独立真源"降为**显式覆盖**：未写 `format` 时，打印取决定六的同一推导器
（金额 → 货币精度、数量 → 单位精度）。已写 `format` 的 28 个版式资产保持原值，不强制改写。

依据：四处真源（§1.6）会让屏幕与打印长期分叉；但一次改 28 个版式资产风险高，故降级为"可覆盖"而非"统一改写"。

## 3. 实施计划

拍板后按四批执行，每批独立可验证、可单独提交。

### 批 0：写入边界舍入（存储类型治理见 ADR-038，本文不重复）

1. 写入路径在落库前按货币精度做一次 `decimal` 舍入，使"入库值 = 最终值"；
2. 该舍入与存储类型正交：ADR-038 批 A 完成后仍需保留（它是"最终值"的保证，不是精度约束的唯一来源）。

迁移：无（纯代码）。ADR-038 的列类型门禁与分批迁移不在本文范围内。

### 批 1：主数据精度列（决定三、四、九）

1. 迁移 `399_currency_unit_decimal_places.sql`：`CURR` 加 `DECIMAL_PLACES`/`ROUNDING_METHOD`，
   `UNIT` 加 `DECIMAL_PLACES`，带默认值（2 / `AwayFromZero` / 3）；

- **刻意保留 `#,##0` 的 3 位分组算法**：.NET 自定义格式的 `#,##0` 就是固定 3 位分组，不跟随 CLDR 的
  2-2-3（印度）分组；要跟随的只有标准格式 `N`，那里已改用 `Intl.NumberFormat`。删掉自写算法会让
  `#,##0.00` 在印度 locale 下与 .NET/后端打印不一致；

  日期 `yyyy-MM-dd` 等四种），**既能选也能自由输入**，不需要额外的"自定义"开关；
- **第 4 项已完成**：`formatCustomNumber` 支持 .NET 的分号分段（`正;负;零`）。
  负号段写成 `(#,##0.00)` 时输出会计括号 `(1,234.50)`，未写负号段时仍用负号。
  后端 `NumericDisplay` 直接走 `IFormattable.ToString(format)`，.NET 原生支持分号分段，无需改动；
- **第 5 项已完成**：`canonicalizeDecimalValue` 改为**确定性**启发式，不再按 locale 猜：
  同时有点和逗号时最后出现的那个是小数点（`1.234,56` → `1234.56`）；单个逗号后跟 1~2 位按小数点

  `1.234` 这类真歧义统一按小数点解释，与接口/数据库/后端 `InvariantCulture` 口径一致。
  全角数字、全角负号（`－`/`﹣`/`−`/`ー`）、全角句号与逗号一并归一。补 5 个用例。

`fieldFormat.test.ts` 12 个用例通过（含新增 locale 与币别断言）。库内实际配置的数值格式只有

**收口结论（职责边界，避免后来人重复讨论）**：

| 层 | 依据 | 是否按币别动态 |
|---|---|---|
| 计算与入库舍入 | 决定三/四，`CURR.DECIMAL_PLACES` | **是** |
| 写入校验（前后端） | 决定四，`numeric-context` 下发 | **是** |
| 打印（明细/合计/价税合计） | 决定十，`LayoutRenderContext.AmountDecimals` | **是** |
| 屏幕显示位数 | 决定六，`FIELDS.DISPLAY_FORMAT` | **否**，按字段配置 |

给该模块的金额字段配 `0` 位格式即可——这是配置问题，不是渲染问题。

## 4. 已知后果（必须接受的代价）

- **两套 locale 语义并存**：屏幕跟用户、文档跟系统地区，用户在德语界面下看到的屏幕格式与打印格式可能不同。
  这是有意取舍——打印件是给外部看的，应使用公司法定格式。
- **历史 `float` 列短期仍在**：在 ADR-038 批 A 完成前，多数列没有存储级精度约束，精度靠"写入边界舍入 + 显示"
  两层保证。这个代价由 ADR-038 的分批迁移逐步消除，不由本文承担。
- **精度不可逆**：`CURR`/`UNIT` 的小数位只增不减，配错只能配大后再评估，不能回退。
- **`SYSSS` 只承担两个参数**：汇率小数位与税率精度（全库唯一值）。金额、数量精度**不进** `SYSSS`，
  这意味着"一个参数改全系统精度"的便利不存在——这是按 ADR-017 的边界主动放弃的。
- **打印格式短期仍可能与屏幕不同**：`layout.json` 已有的 `format` 不回改。
- **未纳入本轮的两项会计能力**：见下表的第 3、4 项（尾差记账、现金舍入）。

### 与"8 件同等重要的事"的对应关系

| # | 事项 | 本 ADR 的处置 |
|---|---|---|
| 1 | 货币小数位不是常数 2（JPY 0、KWD 3、CLF 4） | **决定三**，批 1 |
| 2 | 数量精度必须跟单位（个 0 位、千克 3 位） | **决定四**，批 1 |
| 3 | 尾差必须能记账（round-off 科目） | **本轮不实施**：`EOS.API` 源码中搜索 `VOUCHER`/`凭证`/`总账`/`GL_ENTRY` 0 命中，无总账与凭证模块。登记为约束：引入总账时，舍入差额必须有科目承接，不得静默吞掉 |
| 4 | 现金舍入 ≠ 账面舍入（瑞士/瑞典 0.05） | **本轮不实施**：无现金支付场景。注意 `CURR.ROUNDING_METHOD` 管的是**账面金额的舍入方式**（四舍五入还是银行家舍入），不是现金舍入；将来若需现金舍入，按支付方式另立规则，不扩这一列 |

| 8 | 接口/集成一律 invariant | **决定五**的第三行，批 2 |

## 5. 替代方案（含未选择原因）

| 方案 | 内容 | 未选择原因 |
|---|---|---|
| **A. 一套系统参数管全部小数位** | `SYSSS` 加 `AMOUNT_DECIMALS`/`QTY_DECIMALS` | 维度错配：一个库所有货币共用一位，日元场景仍错。用友的全局 8 项精度已暴露"改完要重启、且用户以为改了显示就改了计算"的问题 |
| **B. 千分位也做成系统参数** | `SYSSS` 加 `THOUSAND_SEPARATOR` 三选一 | 千分位是"每人一个值"，`SYSSS` 是"全库一个值"（ADR-017 §9）。且自写分组逻辑在印度/法语区必错 |
| **C. 精度只做显示，不动存储** | 保持 `float` + 只管显示格式 | 显示精度无法替代存储精度；`float` 累加误差与"显示 2 位、实际 0.30000000000000004"会让对账无解 |
| **D. 一次性把 2074 列全转 `decimal`** | 单脚本重构 | 267 张表同时变更、回归面不可控；且迁移脚本改名会让 DbUp 重跑（见 `AGENTS.md` 迁移约定）。ADR-038 选的是**按业务域分批 + 每批可回滚**，不是这个方案 |
| **E. 引入第三方多语言/格式化库** | 如 `Intl` 的 polyfill 或 `Globalize` | 原生 `Intl.NumberFormat` 已覆盖需求；多一个依赖要登记 `THIRD-PARTY-NOTICES.md`，收益不足 |

## 8. 拍板结论

**2026-10-17 用户拍板：以下各项全部采纳"建议"列。** 本节保留原始选项与理由，便于后来人理解取舍过程。

| # | 事项 | 背景 | 选项 | 结论 |
|---|---|---|---|---|
| ~~1~~ | ~~历史 `float` 金额列的治理范围~~ | **已定（2026-10-17）：另立 ADR-038 作为本文前置**——2074 个 `float` 列按五族标准类型分批迁移，`FIELDS` 加 `NUMERIC_ROLE` 承载语义 | ✅ 已定，见 ADR-038（本文的存储层前置） | 本文批 0 相应收缩为"写入边界舍入"一项 |
