# ADR-047：1.0.0 的承诺边界与维护策略

- 状态：**已接受（2026-11-08 用户拍板）**——1.0.0 同时承担「对外契约」与「内部冻结基线」，按本 ADR 的三层口径发布
- 日期：2026-11-08
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-026（版本管理与发布流程）、ADR-044（判官）、ADR-045 / ADR-046（助手评估）、ADR-016（助手处境与任务闭环）、[75-部署与环境配置](../guide/75-部署与环境配置.md)
- 适用范围：`v1.0.0` 及其后的维护期

## 1. 问题

1.0.0 被同时赋予两个含义：

1. **对外契约**：使用者可以按稳定接口与数据结构依赖它；
2. **内部冻结基线**：功能范围到此为止，之后进入维护。

风险在于把「对外承诺」误读成「所有模块都已由实施顾问逐表验收、与旧系统并行对账完成」。
那是**客户上线项目**的工作，不是产品版本能替客户完成的；把它当作发版门槛，产品发布就会被单个客户的排期绑住。

## 2. 决策：把承诺拆成三层

| 层 | 1.0.0 承诺什么 | 用什么背书 | **明确不承诺什么** |
|---|---|---|---|
| **契约层**（产品级） | HTTP 接口形状、数据库迁移纪律、权限与审计模型、升级与回滚路径、备份恢复口径 | CI 全绿 + 离线/真库测试 + 静态门禁 + 空库重建 + 升级演练 | 未文档化的内部实现、第三方二次开发接口、跨版本数据双向兼容 |
| **能力层**（模块级） | 列进「已验证」清单的模块可正常使用 | 在**最终发布提交**上重跑的验收扫描、CRUD 回归与全量回归 | 未验证模块「与旧系统完全一致」 |
| **实施层**（客户级） | 提供验收工具与清单（`AcceptanceScan`、`E2eSlice`、`CompareAfterSave`） | 工具可用、清单可导出 | **「任意客户的任意模块都已逐表对账」** |

**关键口径**：逐表验收与旧系统并账属于第三层，由实施顾问在客户上线项目中完成；产品 1.0.0 只对第一、二层负责，并如实标注未验证能力。这样既不说谎，也不把发版绑在外部排期上。

## 3. 契约层的具体内容

### 3.1 HTTP 接口

- 分页响应统一为 `items` / `total` / `page` / `pageSize`（1.0.0 起不再接受 `rows` 作为分页信封）。
- 错误响应使用稳定错误码（`ApiProblem`）；未知 `/api` 路径返回 `404 + ENDPOINT_NOT_FOUND`，不回落到前端外壳。
- 权限边界只在 `EOS.API`：每个请求按当前用户重新授权；前端权限判断只改善体验。

### 3.2 数据库

- 所有库对象经 `EOS.API/Data/Migrations/` 的 DbUp 迁移落地，台账是 `dbo.ERP_SCHEMA_JOURNAL`。
- **维护期只做加法**：新增表 / 列 / 索引 / 参数；不改已有列的语义、不删已有对象。
- 必须改语义的变更留到 2.0；1.x 内如确需过渡，走「新增 + 双写 + 下个版本退役」而不是原地改。
- 迁移编号是排序键、文件名是判重身份；已入台账的脚本不改名。
- 新库基线是 `db/bootstrap/`（空库 → 启动时补齐增量迁移）。

### 3.3 升级与回滚

- **升级**：部署新产物 → `EOS.API` 启动时自动执行未落库迁移 → 核对 `/health/ready` 与 `/health/version`。
- **回滚**：切回上一版产物；**数据库不做自动回退**。涉及结构变更的版本，回滚前按备份恢复库。
- 备份三件套：数据库、附件目录、DataProtection 密钥（缺失会导致会话与加密数据不可读）。
- 支持形态：**单实例 + 同源 + HTTPS**；多实例不支持（三处进程内状态，见 [75](../guide/75-部署与环境配置.md)）。

### 3.4 审计与日志

- 写操作留审计（`AUDIT_EVENT` / `AUDIT_FIELD_CHANGE`）；失败请求带稳定错误码与 `correlationId`。
- 文件日志只保留 Warning 及以上；正常请求以 `correlationId` 串 `AUDIT_EVENT`，不在文件日志里找。

## 4. 能力层：模块分级

发布说明必须给出**模块分级清单**，由发布前在最终提交上跑出的结果生成，**不手抄**：

| 分级 | 含义 | 用户可依赖的程度 |
|---|---|---|
| **已验证** | 通过验收扫描 / CRUD 回归 / 真库全量 | 可按产品文档使用；发现问题按缺陷处理 |
| **可用未逐表验收** | 功能完整、自动化覆盖通过，但未与旧系统逐表对账 | 可试用；上线前由实施顾问按客户场景验收 |
| **预览** | 供应商或数据前置未就绪，或从未完成端到端验证 | 默认关闭或明确标注；**不承诺**可用性与数据正确性 |
| **未发布** | 有代码或配置但未开放入口 | 不承诺任何行为 |

`v1.0.0` 发布时的预览项至少包括：工作助手的判官（ADR-044，供应商未连通，默认关闭）、助手评估基线的复跑、以及实施顾问尚未逐表验收的模块。

## 5. 维护策略

- **只做三类改动**：缺陷修复、安全与数据正确性修复、向后兼容的增量迁移。
- **不主动新增功能**；新需求单独立项，按 MINOR 发布。
- 版本递增沿用 ADR-026 §2.6：`fix` / `perf` → PATCH；`feat` → MINOR；破坏性 → MAJOR。1.0.0 之后不再用 MINOR 表达破坏性变更。
- **不承诺**：多实例部署、未写入文档的第三方集成、未文档化的内部类与方法、对历史版本的无限期支持。
- 支持范围以本 ADR 与 [75](../guide/75-部署与环境配置.md) 为准；两者冲突时以更新的那篇为准，并同批订正另一篇。

## 6. 1.0.0 发布时的已知限制

以下各项必须在 Release 说明中如实列出，**不得从发布说明里消失**：

1. **判官（ADR-044）**：本地实测供应商持续返回 402，未产出任何结论；1.0.0 起默认关闭（`JUDGE_ENABLED = 0`），在 3105 显式开启。
2. **助手评估**：评估基线停在 2026-08-07，之后的大改未复跑；评估运行器本身可用，但「分数」不作为 1.0.0 的质量证据。
3. **110310 库存策略**：写路径已封，界面未发布。
4. **180206 加班申请**：缺少「每月出勤参数」（`HR_ENACTMENT_M`）前置数据时按设计拒绝保存；属数据前置，不是代码缺陷。
5. **4 条报表状态筛选条件**：选项值是列表达式，当前查询构建器只能做等值比较，选了不按预期过滤（待产品决策）。
6. **报表导出上限**：PDF / 导出路径仍是 1 万行硬上限；屏幕路径已分页。
7. **特殊页**：「定制页面清单」中仍有待验收项；验收结论由实施顾问给出。
8. **旧库小写命名对象**：仅影响读 `sys` 时的观感，不影响运行；命名规范只约束新建对象。

## 7. 后果

- **正面**：产品可以脱离单个客户的实施排期发布；使用者能清楚区分「承诺」与「预览」；维护期有明确的改动边界。
- **代价**：1.0.0 之后不能随手改接口与数据结构；预览能力需要用户显式开启；发布说明必须持续维护已知限制清单。
- **验证要求**：每次发布前，在**最终标签提交**上重跑契约层证据（CI、离线/真库测试、空库重建、升级演练）与能力层扫描；证据日期与提交号写进发布说明。
