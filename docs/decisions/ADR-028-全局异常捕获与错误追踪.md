## 摘要（先读我，写给人类）

**要解决的问题**：后端兜底已经很完整，**缺的是"把关联键送到用户手上"和"前端渲染期兜底"**。

已有的（**不复建**）：

- 后端唯一异常出口 `GlobalExceptionHandler`（`IExceptionHandler`）：Error 级日志 + 500 +
  `INTERNAL_ERROR` + 关联键 + 模块定义版本；开发环境附堆栈、生产不泄漏；
- 业务异常映射 `ApiExceptionFilter`：8 类已知异常 → 400/401/403/404/422 + 稳定错误码，
  并对权限拒绝写审计；
- 统一错误契约：RFC 7807 + `code`/`message`/`fieldErrors` + `traceId`/`correlationId`/`clientId`/`moduleId`；
- 关联键回写响应头 `X-Correlation-Id`；
- 前端 `window.onerror` + `unhandledrejection` 上报到 `POST /api/v1/client-errors`。

缺的（**本 ADR 要解决的**）：

1. **关联键口径不一致**（归 ADR-025 修）：异常出口日志里的 `correlation=` 用的是 `TraceIdentifier`；
2. **前端无 ErrorBoundary**：渲染期抛错整树白屏，只能靠 window 兜底；
3. **前端没有"交付关联键"的落点**：`ApiErrorBody` 已解析 `correlationId`/`definitionVersion`，
   但界面不展示、无法复制，用户报障时给不出键；
4. **一次用户操作的多个请求各自一个关联键**，串不起"这一次点击发生了什么"；
5. **客户端错误上报不含关联键与版本**，前后端错误无法在日志里合流；
6. **异常日志上下文偏薄**：异常出口不记录 `moduleId`/`definitionVersion`（只在响应体里），
   业务拒绝走 `LogDebug`（文件门 Warning ⇒ 不落盘，只剩中间件一条）。

**本 ADR 的决定，用一句话说**：

> **异常从产生到用户报障只有一条路：出口唯一、关联键唯一、且用户拿得到的那个键，
> 就是日志里能查到的那个键。**

## 1. 背景

### 1.1 现状证据

| 缺口 | 证据 |
|---|---|
| 关联键双口径 | `GlobalExceptionHandler.cs:35`、`ApiExceptionFilter.cs:41` vs `RequestLoggingMiddleware.cs:27` |
| 无 ErrorBoundary | `EOS.Web/src` 全量 grep `ErrorBoundary\|componentDidCatch\|getDerivedStateFromError` 零命中 |
| 关联键无交付落点 | `httpTransport.ts:28-30` 已解析，界面无展示；`types/api.ts:32` 有字段无消费者 |
| 一次操作一键（缺失） | `httpTransport.ts:16,39` 每请求新生成；与指南 §四 要求相悖 |
| 上报字段缺失 | `errorReporting.ts:27-35,45-50` 仅 kind/message/stack/url；服务端已支持 correlationId（`ClientErrorController.cs:45`） |
| 异常上下文偏薄 | `GlobalExceptionHandler.cs:32-47`（无 moduleId/definitionVersion 写日志）；`ApiExceptionFilter.cs:39-41`（`LogDebug`，文件门为 `Program.cs:37` 的 Warning） |
| 客户端错误无审计 | `ClientErrorController.cs:13-41`（`AllowAnonymous`、只 LogWarning、不落库）——**保持现状**，仅补字段 |
| 运行期实际输出未验证 | API 未运行（`localhost:5261` 连接被拒）⇒ `/health/version` 与错误响应的**真实 JSON 未实测**，相关验收须标注"待服务启动后验证" |

### 1.2 约束

1. 生产环境**不得**把异常堆栈返回给客户端（现状已满足，必须保持）；
2. 错误响应契约不得破坏：前端大量依赖 `code`/`message`/`fieldErrors`（`httpTransport.ts:28-30`）；
3. 权限拒绝必须继续 fail-closed（`Authorization` fallback policy，`Program.cs:136-138`），
   且 `PermissionDeniedException` 继续写审计（`ApiExceptionFilter.cs:51-57`）；
4. 前端上报必须**永不阻塞、永不抛出**（`errorReporting.ts:6-23` 的既定设计）；
5. 客户端错误入口 `AllowAnonymous` 是刻意的（登录页也可能报错），**不得改为需要登录**，
   但也不得因此落库或写审计明细。

## 2. 决策

### 2.1 后端：唯一异常出口，上下文一次写全

- 关联键取值收口（承接 ADR-025 §2.1）；
- 异常出口的日志字段补齐 **`moduleId`、`definitionVersion`、`error.code`、`path`、`user`、`clientId`**
  （都是已有来源，`RequestContext` 与 `WorkbenchDefinitionProvider` 直接可得）；
- **不改 `ApiExceptionFilter` 的级别**（`LogDebug` 保持：业务拒绝不是异常状态，其可观测性由
  `RequestLoggingMiddleware` 的 `error.code` → Error 兜住）——但要用**单测/断言**把这个分工钉死，
  避免将来有人"顺手"把它提到 Warning 造成文件日志被业务拒绝淹没；
- 响应契约不变；生产不带 `detail`（保持）。

### 2.2 前端：补 React 错误边界 + 关联键交付

1. **ErrorBoundary**：包在应用根（路由层之上），捕获渲染期异常 → 展示统一错误页
   （含"重试 / 返回首页 / 复制诊断信息"），**同时**把错误上报到既有 `client-errors` 端点
   （复用 `errorReporting` 的发送函数，避免第二条上报路径）；
2. **诊断信息交付**：提供统一"复制诊断信息"能力（关联键 + 产品版本 + 时间 + 路径 + 环境），
   落点在**既有反馈/错误提示组件**内（具体组件由 §8-2 定），不新造第二套提示体系；
3. **一次用户操作一个关联键**：由操作发起处生成并注入 `httpTransport`（未注入时保持现行为），
   助手流式对话已有同类实现（`useChatStream.ts:77-78`），统一到同一工具函数。

### 2.3 前端上报字段对齐后端

客户端错误上报补：`correlationId`（当前响应头/响应体可得）、`appVersion`（ADR-026 注入）、
`clientId`（固定 `eos.web`）、`routeId`。**不采集**：表单值、Token、任何业务数据
（与 ADR-005 §5.1 一致）。

### 2.4 明确的"不做"

- 不引入第三方错误追踪 SaaS（Sentry 等）——本项目单机部署、无外发通道，且与"数据不出内网"的
  默认取向冲突（若将来需要，另立 ADR，并先解决脱敏与合规）；
- 不做客户端错误落库（保持 `ClientErrorController` 只写日志）。

## 4. 已知后果

**正面**

- 用户报障时给得出键；维护者一把 grep 命中异常、审计、前端上报三条线；
- 渲染期错误不再整树白屏；
- 前端错误与后端请求日志首次能在同一关联键下合流。

**负面 / 风险**

- **(a) 关联键进界面 = 少量信息暴露**：键本身是随机/透传标识，不含业务数据；但若调用方传了
  形如"订单号"的 `X-Correlation-Id`，键会显示给用户。**约束**：前端生成的键必须是随机 ID
  （`lib/uuid.ts` 既有实现），不得用业务值充当关联键。
- **(b) ErrorBoundary 会掩盖部分错误**：捕获后界面显示统一错误页，若不上报就无人知晓——
  因此**上报是强制的**（同一次错误必须同时上报，作为验收项）。
- **(c) 客户端错误入口保持匿名**：存在被刷日志的噪声风险（现状已如此，长度上限与只落 Warning+
  是两道缓解）；本 ADR 不新增速率限制（如需，另立小项）。
- **(d) `client-errors` 不落库 ⇒ 无法事后统计**：与决策 #52 的取向一致（不做日志平台），
  统计口径仍靠文件日志 grep；若将来需要统计，应走 ADR-027 的管道而不是新建表。

## 5. 替代方案

| 方案 | 未选择原因 |
|---|---|
| 不引入 ErrorBoundary，只靠 `window.onerror` | React 渲染期抛错会导致整树卸载，用户只看到白屏；`window.onerror` 能上报但**救不回界面** |
| 把前端错误落库（如 `CLIENT_ERROR` 表） | 与决策 #52「不把排障数据放进被排障对象」的取向相反；且需要新迁移、权限门、保留策略 |
| 引入 Sentry / 第三方错误追踪 | 需外发数据（堆栈+URL 可能含业务信息）、需公网通道，与单机部署取向冲突 |
| 把异常堆栈在非开发环境也返回给客户端 | 直接泄露实现细节与潜在数据；ADR-005 已定"生产不泄漏"，不回溯 |
| 业务拒绝一律记 Warning 落盘 | 会让文件日志被"用户输入不合法"这类正常业务拒绝淹没，违背决策 #50 的取舍 |
| 在 `X-Correlation-Id` 之外再造一个关联键字段 | 会形成第三套口径；关联键只能有一个（ADR-025） |

## 6. 验收标准

1. **端到端关联（可判别）**：构造一次 500——响应体 `correlationId` / 响应头 `X-Correlation-Id` /
   文件日志异常行 `correlation=` / 审计行 `CORRELATION_ID` **四者同值**；
   用该值 grep 文件日志**恰好**命中该请求；
2. **ErrorBoundary**：注入一个渲染期抛错的组件（测试用），断言不出现白屏、显示统一错误页、
   **且**产生一条 `client_error` 上报（含 correlationId 与 appVersion）；
3. **诊断信息**：界面上可复制到"键 + 版本 + 时间 + 路径"；复制内容可直接用于 grep；
4. **一次操作一键**：一次触发多请求的前端操作，其所有请求携带**同一** correlationId（单测断言）；
5. **业务拒绝不落盘**：构造 400/403（如 `INVALID_ARGUMENT`/`FORBIDDEN`），断言文件日志没有
   该请求的 Warning 记录、但有一条 `error.code` 的 Error 记录；
6. **契约不回归**：前端 `httpTransport.test.ts` 既有断言（`code`/`message`/`traceId` 映射）全绿；
   `dotnet build` 0 错、`npm run lint`/`npm run build` 0 错；
7. **待服务启动后验证**：`/health/version` 实际 JSON 与本 ADR 假设的字段一致；一次真实 500 的
   响应体含 `correlationId`（当前仅源码层确认，运行期未实测）。
