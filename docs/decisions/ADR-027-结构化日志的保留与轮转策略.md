# ADR-027：结构化日志的保留与轮转策略（在现有自研 JSONL 管道上收口）

- 状态：**已接受（2026-09-29 用户拍板）**——**不引入 Serilog**，在现有自研 JSONL 管道上收口；裁决见 §9
- 版本：v1（2026-09-29）
- 日期：2026-09-29
- 决策者：用户（Larry）+ 开发 Agent
- 拍板记录：2026-09-29（用户逐条裁决，见 §9）
- 相关：ADR-005 §5.1/§5.2/§5.3（可观测性总纲；§5.4 已被决策 #52 推翻）、
  ADR-025（关联键与脱敏接入，本 ADR 的前置）、ADR-029（诊断打包消费本 ADR 的保留窗口）、
  决策 **#50**（文件日志只留 Warning+，慢阈值 1s）、
  决策 **#52**（日志 MCP 拆除，排障 SOP = 文件尾部 + mssql 查 `AUDIT_EVENT`）、
  `scripts/audit-retention.ps1`（审计保留策略先例：30/90/180 天）
- 范围：`EOS.API/Program.cs`、`EOS.API/Telemetry/`、`EOS.API/Middleware/`、`EOS.API/Health/`、`appsettings*.json`

## 摘要（先读我，写给人类）

**要解决的问题**：日志"写在哪、留多久、会不会带敏感值"三件事都还没有定论。

已落地的部分（**不复建、只承接**）：结构化 JSONL 落盘 + 控制台、按级别分流的定级规则、
关联键字段齐备、文件只留 Warning+（决策 #50）、按 50MB × 3 文件轮转。

仍缺的部分：

1. **脱敏没接线**——`LogRedactor` 存在但唯一调用点在会话记忆（详见 ADR-025），
   文件日志管道直接序列化（`JsonFileLoggerProvider.cs:57-68`）；
2. **保留只有大小、没有时间**——50MB×3 ≈ 150MB 上限，**没有任何"至少保留 N 天"的保证**，
   而审计侧早有 30/90/180 天的明确策略（`scripts/audit-retention.ps1`）；
3. **日志路径依赖宿主工作目录**（`Directory.GetCurrentDirectory()`），IIS/服务宿主下是否稳定**未验证**；
4. **轮转是 `Copy + Delete`**（50MB 级联拷贝 + 瞬时文件缺失），打包/读取必须容忍这个窗口。

**本 ADR 的决定，用一句话说**：

> **不新建第二条日志管道**：在现有自研 JSONL provider 上补齐「脱敏 + 时间&大小双保留 + 显式路径 +
> 可写性守卫」，把"日志在哪、留多久、带了什么"变成写在配置里、能被门禁断言的事实。

### 1.2 约束

1. **不得恢复日志 MCP**（决策 #52 已整体拆除，理由是"排障工具依赖被排障对象"）；
   日志访问仍为文件直读 + mssql。
2. **不得把正常请求写入文件**（决策 #50）：文件日志的价值来自"只留诊断价值高的记录"，
   不得以"方便排障"为由放开门限。
3. **不得记录**（ADR-005 §5.1 禁止清单）：密码/哈希/Cookie/Token/连接串、附件正文、
   LLM prompt/response 全文、未脱敏整行业务数据。
4. 日志路径与轮转参数**必须可配置**（部署环境的工作目录不受本仓库控制）。
5. `TreatWarningsAsErrors` + `dotnet build` 0 错是硬口径（`EOS.API.csproj:9-12`）。

## 2. 决策

### 2.1 保留策略：时间与大小**双门**，先到先删

| 参数 | 建议默认 | 说明 |
|---|---|---|
| `Logging:File:Path` | `logs/api-json.log`（相对 `AppContext.BaseDirectory`） | 显式化，不再依赖 `CurrentDirectory`；支持绝对路径/环境变量展开 |
| `Logging:File:MaxBytes` | 52428800（50MB，沿用现状） | 单文件上限 |
| `Logging:File:MaxFiles` | 3（沿用现状） | 轮转份数 |
| `Logging:File:RetentionDays` | **14（待确认）** | **新增**：任何轮转文件超过该天数即删除，即使未达大小上限 |

配置缺失时按上表默认值运行（fail-safe：宁可少留，不可无界增长）。
保留判定**基于文件最后写入时间**（与审计脚本"按时间截断"同源思路）。

### 2.2 脱敏：唯一出口（承接 ADR-025，不重复决策）

本 ADR 只把"接口"定死：provider 写入前对 `message` 与 `fields` 的字符串值应用 `LogRedactor`；
`LogRedactor` 的**模式清单与正反例单测**归 ADR-025 的范围。

### 2.3 路径与可写性守卫

- 默认根目录改为 `AppContext.BaseDirectory`（与附件、字体、版式的既有做法一致——
  `AttachmentController.cs:189`、`Program.cs:432`），减少"宿主工作目录漂移"这一类不可控因素；
- 启动时确保目录存在并**探测可写**（现有 `AttachmentStorageHealthCheck` 是同构先例）；
- 目录不可写时**不静默**：记一条 Error，并保持控制台管道可用
  （进程不得因日志目录不可写而启动失败）。

### 2.4 轮转实现保持"原地级联改名"，但明确其代价

保留现有 `Copy + Delete` 语义（**不重写为 `File.Move`**：Windows 下同名打开文件会阻止 Move，
而本 provider 的共享读是刻意保留的），并在代码注释与指南里写明两个已知特性：
轮转窗口内旧文件可能瞬时不可见；单次轮转的 IO 代价与 `MaxBytes` 同阶。

### 2.5 级别策略不变（显式承接决策 #50）

- 文件门 `Warning`；慢请求阈值 1000ms；`/api` 正常请求只进控制台。
- **明确不做**：为排障临时把文件门降到 `Information`（指南 §九 已述；本 ADR 把它上升为决策边界）。

## 4. 已知后果

**正面**

- "日志留多久"从隐含（150MB 上限）变成显式可配置，且与审计保留策略（30/90/180 天）在同一份
  认知框架里；
- 路径不再依赖工作目录，IIS 部署下"日志在哪"第一次成为可写下来的事实；
- 打包/外发（ADR-029）有了安全前提。

**负面 / 风险**

- **(a) 14 天保留对低频故障可能不足**：本系统只落 Warning+，长期看文件增长慢（实测 43MB 攒了
  很久），但删除是**不可逆**的——若运维从未归档，超期即永久丢失。缓解：保留天数可配置，
  并在指南/发布说明明确"需要长期留存请在外部做归档"。
- **(b) 时间门与审计策略并存 ⇒ 两套保留语义**：审计在库里（可查询）、文件日志在磁盘（不可查询），
  排障时仍要记得"某个 incident 可能已过期"。这是决策 #52 之后的既有格局，本 ADR 只让它显式。
- **(c) 改默认路径会改变现有部署的落盘位置**：`{CurrentDirectory}/logs` → `{BaseDirectory}/logs`，
  升级后旧目录里的历史日志不会自动搬迁；发布说明必须提示"历史日志在新旧目录各有一份"。
- **(d) 脱敏会降低部分日志的可读性**（与 ADR-025 §4(b) 同一条代价，不重复计）。

## 5. 替代方案（**含 Serilog 选型，明确未选**）

| 方案 | 未选择原因 |
|---|---|
| **引入 Serilog（+ `Serilog.Sinks.File` rolling / `Serilog.Sinks.Console`）** | 收益：成熟的时间滚动（`rollingInterval` + `retainedFileCountLimit`）、结构化 sink 生态、表达式过滤、更少自研代码。未选原因：① **现有自研 provider 已覆盖本系统的真实需求**（结构化 JSONL、级别门、大小轮转、共享读），缺的只是时间保留与脱敏，补这两点是几十行改动；② 引入第三方依赖要走 `THIRD-PARTY-NOTICES.md` 登记与许可确认（`CONTRIBUTING.md` 要求）；③ 会形成"控制台 JSON + Serilog 文件"双管道，配置面与脱敏点各一份；④ 本项目是**单机 Windows 部署**，不需要集中采集/sampling sink。**保留复评条件**：若出现"多 sink 汇聚 / 采样 / 导出 OTel / 集中日志平台"的真实需求，另立 ADR 引入。 |
| 只保留大小轮转（不加时间门） | "150MB 上限"在不同部署下对应的时间跨度可能相差几个数量级（取决于故障频率），无法回答"日志留多久" |
| 按天切分文件（`api-json-20260929.log`） | 对"只留 Warning+"的日志量属过度设计；且会让"当前文件"名字每天变化，现有按固定名尾部读取的排障 SOP 与脚本要改 |
| 把日志同时写数据库（如 `LOG_EVENT` 表） | 与决策 #52 的精神相反：排障工具依赖被排障对象（库不可用时应仍能读日志）；且写库会污染业务库与审计面 |
| 恢复日志 MCP / REST 查询栈 | 决策 #52 已整体拆除并给出理由，本 ADR 明确不回溯 |

## 6. 验收标准

1. **保留可判别**：构造"超天数"与"超大小"两类场景（可改文件最后写入时间或调小阈值），
   断言最旧文件被删、且**当前文件不丢**；
2. **路径可配置**：`Logging:File:Path` 支持相对（基于 `BaseDirectory`）、绝对、含环境变量三种形态；
3. **不静默失败**：日志目录不可写时进程仍可用，且产生一条 Error；
4. **级别门不回退**：正常 `/api` 请求不落盘、5xx 与慢请求落盘（既有行为的回归断言）；
5. **脱敏生效**：与 ADR-025 同一组正反例单测；
6. `dotnet build` 0 错；与日志相关的门禁/自检 PASS；指南篇目已同步。
