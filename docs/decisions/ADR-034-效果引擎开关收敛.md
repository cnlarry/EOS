# ADR-034：效果引擎开关的收敛——分闸下线、总闸改断路器

- 状态：**草案（待拍板，未实施）**——三项待定见第 12 节
- 日期：2026-10-10
- 相关：ADR-012（单据行为效果配置化，本开关的出生地）、`docs/plans/decision-ledger.md` **#58**（开关归属的原始决策）、ADR-023（对拍证据按语义等价判定）、ADR-032 §4（同一把尺子：删掉分组启用位）、迁移 341（列下线的先例）、`LESSONS.md` L27

> 一句话：**"有配置就执行"这件事，本仓在校验侧早就这么做了；本 ADR 把动作侧追上。**

## 1. 问题

模块级效果引擎开关（`MODULES.EFFECT_ENGINE_TAG`，进定义后是 `effectEngine.enabled`）今天的判定是：

```25:26:EOS.API/Data/Effects/EffectEngineInvoker.cs
    public bool IsEnabledFor(WorkbenchDefinition definition) =>
        settings.Enabled && definition.EffectEngineEnabled;
```

也就是"**有配置 且 开关打开** 才执行"。三个问题：

1. **两个真源**：配了动作却不开开关 = 静默什么都不做——正是 ADR-032 §4 删掉分组"启用位"时的同一个病。
2. **它与事实高度重合**（实测，全库 358 个模块）：

| 口径 | 数量 |
|---|---|
| 分闸开着（`EFFECT_ENGINE_TAG=1`） | 114 |
| **开着且有动作** | **110 —— 等于全库有动作的模块总数** |
| 开着但只有校验、没动作 | **0** |
| 关着却配了动作（真正"配了不跑"） | **0** |
| 关着却配了校验 | 16 个模块 / 21 行（**校验不受闸，照跑**，见第 3 节） |
| 开着却零配置（空跑） | 4 个（1201、1401、1601、300303） |
| 动作行的行级 `ENABLED=0` | **0 / 349**（这个字段建了从没用过） |

   即：**分闸的值 ≡ "这个模块有没有动作"，110:110，零例外。**
3. **灰度期已经结束**：它的出生理由是灰度放量＋止血（账本 #58："开关＝发布快照 Definition JSON 扩展段 `effectEngine.enabled`……另设 appsettings `EffectEngine:Enabled` 全局总闸（默认 false），灰度期出系统性问题一行配置止血"）。现在 `appsettings.json` 里总闸已是 `true`，逐模块放量也已完成——它退化为一个与事实重合的冗余字段。

## 2. 决策

1. **分闸下线**：`MODULES.EFFECT_ENGINE_TAG` 退役（列 + `FIELDS` 登记 + 门禁清单 + 2301 表单上的开关复选框）。生效判据改为**推导**：**该事件有启用的动作行 → 执行**；没有 → `Ran=false`，调用方保基线路径（与今天"关闸"的行为逐字一致）。
2. **总闸保留，但改两处**：① 定位从"灰度开关"改为"**引擎断路器**"；② 绑定方式从一次性单例改为 `IOptionsMonitor<EffectEngineSettings>`——否则"一行配置止血"这句话不成立（见第 5 节）。
3. **快照里的 `effectEngine` 段保留、不再消费**（恒写 `{"enabled":true}`），不删段——理由见第 6 节（删段会触发版本漂移与对拍证据降级）。
4. **停用手段统一为行级 `ENABLED`**；配置面提供"停用本模块全部动作"的**批量操作**（操作，不是字段）。
5. **任何一类配置都不得再引入"模块级开关"**——这是本 ADR 要立成纪律的那一条。

## 3. 校验侧早就不用开关，而且是刻意的

```176:183:EOS.API/Data/Effects/EffectEngineInvoker.cs
    /// Runs the validation chain of the given stage without executing any action, and
    /// returns the blocking message (null when everything passes). Validation rules are a
    /// declarative catalog of the module's save-time rules, so they are NOT gated by the
    /// effect-engine switch or by the module takeover flag: gating them there would make an
    /// enabled rule silently do nothing.
```

实测印证：那 16 个"分闸关着、却配了校验规则"的模块（货币资料、员工基本资料、证件资料、保险投保、排班……共 21 行，`ENABLED=1`），今天**一条不少地在跑**——因为校验根本不看这道闸。

所以本仓对"配置类开关"的答案已经写在代码里：**不要让已启用的配置静默什么都不做**。动作侧是唯一还没追上的一处；审批/结案/解批路径同理（`WorkbenchApprovalService` 走的是 `IsEnabledFor`，将随第 2 节决策一起改推导）。

## 4. 为什么动作侧不需要分闸

因为**判据可以由事实推导**，而推导结果与今天逐模块一致：

- 有动作（110 个）→ 推导 = 执行 = 今天（分闸开着）✓
- 无动作、无分闸（244 个）→ 推导 = 不执行 = 今天 ✓
- 唯一差异是那 4 个"开着空跑"的模块（第 7 节单独处置）✓

同时，行级停用这个更细的手段**早就在表里**（`MODULE_BUSINESS_ACTION.ENABLED` / `MODULE_VALIDATION_RULE.ENABLED`），只是从没用过。把"整模块一键停用"做成配置面的**一个操作**（批量置 0），比留一个**长期状态字段**更符合"一件事一个真源"。

## 5. 为什么总闸不能一起删，以及它必须先修好

它管的对象与分闸不同：**分闸管"某个模块的配置"，总闸管"引擎自身"**。删掉总闸后，若引擎出现系统性缺陷（某类事件在真单据上写坏数据），唯一手段是改代码发版——而它的成本只是一个 appsettings 键。

但它今天名不副实：注册是**一次性读入的单例**——

```219:219:EOS.API/Program.cs
builder.Services.AddSingleton(builder.Configuration.GetSection("EffectEngine").Get<EffectEngineSettings>() ?? new EffectEngineSettings());
```

即改 `appsettings.json` **必须重启应用**才生效。所以两件事：

- **改绑定**：换成 `IOptionsMonitor<EffectEngineSettings>` 并在判定处读 `.CurrentValue`（每次调用一次属性读，开销可忽略）——ASP.NET Core 的 `appsettings.json` 默认 `reloadOnChange`，改完即生效，"断路器"才名副其实；
- **改名**：文档与注释里"灰度开关"改为"引擎断路器"，并写明它的适用场景是"引擎自身的系统性缺陷"，不是"单模块配置错误"（后者由配置面修）。

## 6. 为什么保留快照里的 `effectEngine` 段

事实：

- 该段由发布路径按模块开关写出（`EOS.API/Data/WorkbenchDefinitionValidator.cs:347` 读 `EFFECT_ENGINE_TAG`、`:413-427` 组装 `effectEngine` 段写进定义）；
- 262 个现行快照里，**114 个是 `"effectEngine":{"enabled":true}`、148 个是 `"effectEngine":null`**——与 `EFFECT_ENGINE_TAG=1`（114）/ `=0`（148，其中有快照的那批）精确对应；
- 内容比较器**只忽略两类差异**（占位公式行；空串与缺字段），删除一个段属于**真差异**（`EOS.API/Data/Definitions/WorkbenchDefinitionContentComparer.cs` 文档明确"Everything else is a real difference"）→ 重发布即 `VERSION+1` → 对拍证据按 ADR-023 降级。

结论：**段保留**（写出恒 `{"enabled":true}`），只是不再有人读它。代价可接受且可解释：那 148 个 `null` 形态的快照会在**各自下次重发布时**变成 `{"enabled":true}`（各自版本 +1）——它们本来就没有动作，引擎开关对它们毫无意义，而且这次重发布是由别的原因触发的，不是本 ADR 一次性制造的。

**何时清段**：与下一次"定义结构变更"一起做（那时本来就要重置证据），不单独为它付一次全量重发布的代价。

## 7. 唯一会改变行为的一批：4 个"开着空跑"的模块

| 模块 | 名称 | `AUTO_APPROVE` | 流程 | 按钮 | 动作 |
|---|---|---|---|---|---|
| 1201 | 产品/料件基本资料 | 0 | 无 | 无 | 无 |
| 1401 | 客户基本资料 | 0 | 无 | 无 | 无 |
| 1601 | 厂商基本资料 | 0 | 无 | 无 | 无 |
| 300303 | 关 封(转厂) | 0 | 无 | 无 | 无 |

- 今天：分闸开着 → `IsEnabledFor=true`，但它们没有任何动作，效果链跑也是空转；
- 改动后：推导 = false → `WorkflowStates.IsStatelessApproveCapable(effectEnabled:false, hasFlow:false)` 由 **false 变 true** → 它们从"引擎接管（实则空转）"落到"**无副作用批核**"分支（纯状态翻转 + 审计）。这与账本 #108 的口径一致（无副作用模块本就该走这条分支），是一次**修正**而非回归；
- 处置：改造前单独确认这 4 个模块的批核入口与 `CONFIRM_TAG` 口径（它们今天被判"需要 `CONFIRM_TAG` 列"），确认结果登记进 `status.md`；**不为它们补配置**。

## 9. 迁移与实施（三批）

**批 1（代码，列先留着）**：判定改推导；**过渡期双算对拍**——`IsEnabledFor` 内部同时算"开关值"与"推导值"，不一致时写警告日志（临时探针，不改变行为）。跑一轮真库回归（保存 / 批核 / 解批 / 结案），确认 262 个模块上两者只在第 7 节那 4 个上分叉。

**批 2（迁移）**：删列 + 删 `FIELDS` 登记 + 门禁清单同步 + 2301 表单字段下线。**先断言后删**：断言"有启用动作的模块集合"与"`EFFECT_ENGINE_TAG=1` 的集合"的差集**恰好是那 4 个具名模块**（实测 110 vs 114）——不许用模糊条件放行；差集一旦多出别的模块，迁移直接中止（说明数据已漂，得先查清）。

**批 3（断路器）**：总闸改 `IOptionsMonitor`；文档与注释改名。

## 10. 验证

- 对拍：改造前后，同一批单据走"基线路径"与"引擎路径"的结果一致；重点覆盖批核/解批/结案。
- 第 7 节那 4 个模块单独跑批核与解批，确认落到无副作用分支且行为可接受。
- 快照零漂移复核：改造后挑 3~5 个模块做一次**无改动重发布**，断言 `VERSION` 不变（证明第 6 节的段保留策略有效）。
- 门禁：`check-module-node-kind`（清单已同步，不再引用已删列）、`check-snapshot-staleness`、`check-lifecycle-columns`、`check-di-registrations`、手册新鲜度。

## 11. 刻意不做

- **不给校验规则加任何开关**（第 3 节：那正是要消灭的模式）。
- **不把总闸改成"按模块批量开关"**——那是分闸复活。
- **不做"一次性清段 + 全量重发布"**：收益为零，代价是 262 个模块的版本漂移与对拍证据降级。
- **不动行级 `ENABLED` 的语义**：它本来该是唯一的停用手段，本 ADR 只是开始用它。
- **不顺手改"发布"的语义**：那是 ADR-033 的领域（配置面拆分与发布呈现）。

2. **快照里的 `effectEngine` 段保留策略？** 建议保留恒 `{"enabled":true}` 到"下一次定义结构变更"再清（第 6 节）。
