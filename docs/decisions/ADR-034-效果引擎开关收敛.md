# ADR-034：效果引擎总闸改断路器，并清掉快照里的 effectEngine 段

- 状态：**已拍板（两项，未实施）**——模块级"分闸下线"已移交 ADR-035（先落地）
- 日期：2026-10-10
- 相关：ADR-012（单据行为效果配置化）、**ADR-035（批核模型收敛——本 ADR 的兄长，先落地）**、ADR-023（对拍证据按语义等价判定）、`docs/plans/decision-ledger.md` **#58**（灰度开关的原始决策）、**#152**（本文的登记）

## 0. 范围与顺序（先说清）

本文只做**两件与批核模型无关**的事：① 效果引擎总闸改成能即时生效的断路器；② 清掉快照里的 `effectEngine` 段（且不让版本漂移）。

原本的"**模块级分闸（`MODULES.EFFECT_ENGINE_TAG`）下线**"**已移入 ADR-035**。原因：实测发现这个分闸在悄悄承担第二种职责——它是 12 个模块"批核入口"的唯一来源（详见 ADR-035 §1）。先撤分闸、入口无着落，会当场砸掉 3 个核心主档（1201 产品/料件、1401 客户、1601 厂商，其中两个在 2026-10-05 还有人批核）的批核按钮。

**顺序**：ADR-035 先落地；本文两项可并行、互不阻塞。分闸下线的实际操作（引擎判定改推导）也已并入 ADR-035 的实施批次。

## 1. 决策一：总闸改成"能即时生效的断路器"

它管的对象与分闸不同：**分闸管"某个模块的配置"，总闸管"引擎自身"**。风险场景是"引擎出现系统性缺陷（某类事件在真单据上写坏数据）"，此时唯一不需要改代码、也不需要逐个改模块配置的手段就是这道总闸。所以它保留——**但今天它名不副实**：

```219:219:EOS.API/Program.cs
builder.Services.AddSingleton(builder.Configuration.GetSection("EffectEngine").Get<EffectEngineSettings>() ?? new EffectEngineSettings());
```

值在**启动时读一次**就固定了。也就是说账本 #58 写的"灰度期出系统性问题一行配置止血"，实际是"**改配置 + 重启应用**"——而重启会把所有在线用户踢下线。

**决定**：

- 绑定改为 `IOptionsMonitor<EffectEngineSettings>`，判定处读 `.CurrentValue`（`appsettings.json` 默认 `reloadOnChange`，改完即生效，"断路器"才名副其实）；
- 加一条**坏值兜底**：读取失败（配置写错类型等）时**沿用上一次有效值**并记警告——断路器不能因为一个笔误而失效；
- 文档与注释里"灰度开关"一律改称「**引擎断路器**」，并写明它的适用场景是"引擎自身的系统性缺陷"，不是"单模块配置错误"（后者由配置面修）。

**被否的选项**：保持现状，只把文档里的"一行配置止血"如实改成"重启级止血"。零改动，但等于承认这道闸在真正需要它的那一刻（事故中）不可用。

## 2. 决策二：清掉快照里的 `effectEngine` 段，且不让版本漂移

**事实**：该段由发布路径按模块开关写出（`WorkbenchDefinitionValidator.cs:347` 读 `EFFECT_ENGINE_TAG`、`:413-427` 组装 `effectEngine` 段写进定义）。262 个现行快照里 **114 个是 `"effectEngine":{"enabled":true}`、148 个是 `"effectEngine":null`**——与分闸开关值精确对应。而内容比较器**只忽略两类差异**（占位公式行；空串与缺字段），删除一个段属于**真差异**（`WorkbenchDefinitionContentComparer` 文档："Everything else is a real difference"）→ 重发布即 `VERSION+1` → 对拍证据按 ADR-023 降级。

**决定**：**停止写出该段，同时把该段加进内容比较器的忽略清单**（即"运行期确实不读的差异，先归一掉再比"）。

- **为什么忽略是正当的**：这不是"过度归一化"——改造后运行期**确实不再读**这个段（引擎判定改由动作行推导，见 ADR-035 §2 第 4 条）。比较器的既定原则恰恰就是"differences the runtime provably ignores are normalized away"。
- **不需要动历史数据**：那 262 个快照行里的段留着无害（不被读、也不参与比较），将来随各自重发布自然消失。**不做 UPDATE、不做全量重发布**。
- **被否的选项**：清段后全量重发布——262 个模块全部版本 +1、已登记的对拍证据全面过期，收益为零。

## 3. 为什么总闸不能一起删

它管的是"引擎自身"的系统性缺陷，删掉后唯一手段是改代码发版；而它的成本只是一个 appsettings 键。分闸（模块级）可以下线，总闸不能——两者管的不是同一件事。

## 5. 验证

- **即时生效**：改 `appsettings.json` 的 `EffectEngine:Enabled=false`，**不重启**，在 30 秒内保存一张单据，断言效果链不再执行（审计/日志为证）；再改回 true，断言恢复。
- **坏值兜底**：把该键写成一个非法类型，断言不抛 500、沿用上一次有效值并留下警告。
- **清段零漂移**：改造后挑 3~5 个模块做一次"无改动重发布"，断言 `VERSION` 不变。
- 门禁：`check-snapshot-staleness`、`check-di-registrations`、手册新鲜度。

## 6. 刻意不做

- **不做模块级分闸下线**：已移交 ADR-035（它决定"批核入口从哪来"）。
- **不 UPDATE 历史快照**：零收益，且会造出"内容变了"的假象。
- **不把总闸改成"按模块批量开关"**：那是分闸复活。
