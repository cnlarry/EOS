## 背景

ADR-009 §9.7 明确：L3（客户自助版式设计）**不进入 P6、不阻塞任何一期**，但作为标准产品的能力项独立评估、单独出 ADR。
§9.7.1 / §10.3 已由用户拍板渲染器定案——**放弃 Typst，QuestPDF + 可视化设计器**，并留下一份待决策清单：

1. 可视化设计器实现形态：自建 vs 引入成熟报表设计器组件；
2. 布局模型：流式（适配行数变化）vs 绝对定位（适配套打）；
3. 开源约束：EOS 长期开源，设计器组件选型须限于开源栈；
4. `REPORT_LAYOUT` 是否扩展承载套打版式，或另立 `REPORT_FORM` 表 + `REPORT_FORM_BINDING` 绑定表。

### 2. 业务价值与边界（承接 ADR-009，不重述论证）

- **要解决的**：新客户 / 新单据格式的"版式确有差异"场景（发票版 / 外币版 / 抬头差异），不依赖开发商出模板。
- **不解决的**：数据源、汇总口径、参数定义、查询逻辑（§1 分层：开发态，不可由客户改）；"用设计器消化 62 份存量送货单"（§9.1 已证差异来自数据而非版式）。
- **安全前提**：§9.6 三条硬约束——模板只消费 `PrintData`（不得自行取数）、字段引用走白名单、模板语言无副作用。

## 目标用户与角色分级（2026-08-30 用户澄清）

设计器不是单一用户。三类使用者，能力与权限逐级收紧：

| 角色 | 使用场景 | 设计器能力 | 存储 / 权限门 |
|---|---|---|---|
| ① 开发人员（本项目） | 设计内置 / 默认格式（L0/L1/L2） | 全能力（6 元素 + 字段绑定 + schema 级） | 开发态资产，进 Git + code review + 部署只读 |
| ② 实施顾问 | 帮客户设计报表 / 单据格式 | 全能力（完整设计器） | 运行态 copy-on-write，`REPORT_FORM_LAYOUT` + 完整设计权限位 |
| ③ 客户维护人员 | 微调（移位 / 改文案 / 显隐 / 字段映射到已有字段） | 受限（微调模式：不可增删元素类型、不可改 table 结构、不可改 dataContract） | 运行态 copy-on-write + 受限设计权限位 |

三个直接后果，本 ADR 的决策据此校准：

1. **权限门从单 bit 变三档**（§2 决策 4 第 3 点）。「复用 `CanSetup` 语义」不足以区分角色②③：
   实施顾问可全量设计、客户维护人员只可微调。改为三档——角色①不进运行时权限系统（Git/code review 门）；
   角色②、③ 各自独立权限位 + 能力面板。
2. **「零学习成本」只对角色③成立**。ADR-009 §9.7.1「可视化、零学习成本」的措辞须收敛到角色③：
   角色①②是专业用户，可用完整坐标画布；角色③才需要**微调模式**（简化面板：只暴露位置 / 尺寸 /
   文本 / 显隐 / 字段下拉），同时把「绝对定位 + table 流动」的混血复杂度（§2 决策 1 的风险点）对
   最不熟练用户的暴露面压到最小。
3. **单一真源机会**（关键，§2 决策 6）：既然角色①也「用设计器」产出内置格式，则内置版式可由设计器
   直接产出 `layout.json`，`layout.json` 成为**唯一真源**——现有 24 张 C# 命令式版式退化为「迁移来源 +
   对拍基线」，迁移完成后退场。这从根上消灭「C# ↔ layout.json 双源漂移」（§6「解释层与 C# 内置版式
   语义漂移」「JSON 难 diff」两条随之降级）。代价：内置版式不再走 ADR-009 §12.4「C# 直连渲染」的
   快速路径，统一走解释层（单据版式性能差异可忽略，但须用户确认放弃「类型安全直连」这条理由）。

## 1. 核心架构：三件套

本 ADR 的全部交付物围绕一个数据模型展开，它是三重身份：

```
layout.json schema
  ├─ 存储格式（客户定制落盘）
  ├─ 渲染契约（QuestPdfLayoutRenderer 消费）
  └─ 设计器文档模型（前端画布序列化）
```

三个消费方必须共用同一份 schema（含 JSON Schema 定义文件 + 版本化），否则必然分叉。

### 1.1 设计原则

1. **schema 先行**：S1 先定 schema 与解释层，设计器 UI（S2）只是 schema 的编辑器——防止"UI 定义了格式"的反向污染。
2. **元素最小集**：S2 只做 6 种元素，控制自建设计器的工程规模（§9.7.1 登记的最大风险）。
3. **字段引用三重命名空间**：`MASTER.*` / `DETAILS.*` / 系统值（页码/日期/列印人），与 `PrintData` 契约一一对应，天然满足 §9.6 约束 1/3。**页头公司名/LOGO 不属数据字段**，而是页头字典引用（`HEADER_ID` 参数），渲染时经解析链取 `REPORT_LAYOUT` 条目（ADR-009 §9.4.2 领域规则：单据页头 = 开单方主体）。
4. **fail-closed 双校验**：保存时校验（schema + 字段白名单）+ 渲染时校验（防绕过 API 直改库）。

### 1.2 schema v1 草案

```json
{
  "schemaVersion": 1,
  "kind": "document",
  "page": { "size": "A4", "orientation": "portrait",
            "margin": { "top": 32, "right": 32, "bottom": 32, "left": 32 } },
  "sections": {
    "header":  { "height": 60, "elements": [] },
    "content": { "elements": [] },
    "footer":  { "height": 30, "elements": [] }
  },
  "elements": [
    { "id": "e1", "type": "text", "x": 40, "y": 20, "w": 200, "h": 20,
      "content": "送货单", "style": { "fontSize": 14, "bold": true, "align": "center" } },
    { "id": "e2", "type": "field", "x": 40, "y": 40, "w": 120, "h": 18,
      "field": "MASTER.CLIENT_NAME", "format": null },
    { "id": "t1", "type": "table", "x": 20, "y": 80, "w": 170, "h": 200,
      "dataSource": "details",
      "columns": [
        { "field": "PRO_NO",   "label": "料号", "width": 30 },
        { "field": "PRO_NAME", "label": "品名", "width": 60 },
        { "field": "QTY",      "label": "数量", "width": 20, "align": "right", "format": "#,##0.######" }
      ],
      "showHeader": true, "repeatHeaderOnPageBreak": true }
  ]
}
```

> **抬头语义（2026-08-30 澄清，ADR-009 §9.4.2）**：`layout.json` 的 header 段**不得把公司名写成固定 `text`**；
> 页头公司名/LOGO 应作为**页头字典引用（`HEADER_ID` 参数）**绑定，渲染时由
> `CLIENT.HEADER_ID → SYSQR.HEADER_ID → REPORT.HEADER_ID` 链解析到 `REPORT_LAYOUT KIND='HEADER'` 条目。
> `MASTER.CLIENT_NAME` / `MASTER.FULL_NAME_CN` 等往来单位字段属**正文**（收货方/客户信息区），
> 不是页头（P6 曾以 `CLIENT.FULL_NAME` 覆盖页头导致 Title 显示客户公司名，2026-08-30 已修正）。

**元素最小集（S2）**：

| type | 用途 | 绑定 |
|---|---|---|
| `text` | 静态文本（标题/标签） | 无 |
| `field` | 数据字段值 | `MASTER.*` / 系统值 |
| `image` | LOGO / 图片 | 资源 ID（服务端白名单） |
| `line` | 分隔线 | 无 |
| `rect` | 边框/衬底 | 无 |
| `table` | 明细行（自动分页 + 表头重复 + 合计） | `DETAILS.*` |

坐标单位为 **mm**（套打行业惯例，对客户友好）；**注意 QuestPDF 默认单位是 point**
（现有 C# 内置版式 `page.Margin(32)` 即 32pt），解释层须统一换算 mm→pt（1mm ≈ 2.8346pt），
页尺寸/边距/字体/格式复用 `PdfLayout` 既有常量与 `FormatValue` 白名单逻辑；
S1 对拍护栏以换算后的实际渲染为准，不得按"mm 即 QuestPDF 默认单位"直接取值。

## 2. 关键决策（2026-08-31 已拍板）

### 决策 1：布局模型 —— "绝对定位"，一期只服务 document 版式（已拍板）

| 方案 | 评估 |
|---|---|
| 绝对定位（固定坐标画布） | 单据套打的行业标准（FastReport / 金蝶 BOS 套打设计器均为此模型），可精确定位到预印表格坐标；`table` 元素在固定区域内流动，不改变整体模型 |
| 流式（从上往下堆叠） | 适配行数变化，但引入第二套渲染逻辑；list 报表的"格式差异"本质是列定义（`dataContract.columns` 显隐/顺序/宽度），已由 L1/L2 + 报表中心覆盖，**不需要设计器** |

**结论**：一期只做绝对定位的 document 设计器，不实现流式渲染路径。`schema.kind` 字段与 `table` 元素的"区域内流动"语义为未来流式扩展留接口（条件触发，见复审条件）。

### 决策 2：设计器形态 —— "自建 UI + 开源拖拽原语"，否决引入报表设计器组件（已拍板）

开源生态调研（2026-08-30）：

| 候选 | 结论 |
|---|---|
| FastReport Open Source | .NET 后端生成器，**Web 设计器需商业授权**；FRX 格式与 QuestPDF 渲染不匹配 |
| Stimulsoft / Telerik Reporting / ActiveReports | 商业闭源，违反 EOS 开源定位 |
| xinglie/report-designer | 声明"专有软件、禁止反编译/分发"，不可用 |
| Carbone | DOCX/XLSX 模板转换思路，非可视化设计器 |
| inerttila/Report-Builder | 新项目（2026-02），工程化成熟度不足以作为产品依赖 |

**没有可直接引入的开源"报表设计器"组件**。因此：

- 设计器 UI **自建**，拖拽/缩放/吸附用**开源原语库**（候选：`dnd-kit` / `react-moveable`，均 MIT，React 19 兼容；2026 状态活跃维护）；
- 用**元素最小集 + schema 先行 + S2 MVP 严格裁剪**约束工程规模——"自建 ≈ 再造 FastReport"的失控风险靠这三条控制，不靠堆功能。

### 决策 3：存储 —— "内置版式 Git 资产 + 客户定制库表"（已拍板）

§12 格式包模型把格式包设计为文件系统目录（`report-formats/{formatId}/`）。本 ADR 拆为两层：

| 层 | 归属 | 存储 | 写权限 |
|---|---|---|---|
| 内置版式（L0/L1/L2） | **开发态** | Git 资产 + 部署复制到 `ReportFormats:StorageRoot`（只读） | 开发者，code review |
| 客户定制（copy-on-write） | **运行态** | **数据库**：新表 `REPORT_FORM_LAYOUT`（LAYOUT_ID / BASE_FORMAT_ID / OWNER_ID / LAYOUT_JSON / LAYOUT_VERSION / 审计列）+ `REPORT_FORM_BINDING`（FORM_TYPE / CLIENT_ID / LAYOUT_ID / HEADER_ID / TAIL_ID / PRINT_PRICE，§9.5.3 绑定键 + 客户 × 单据类型 级配置） | 客户（设计器），服务端校验 |

**理由**：客户定制存库沿用 EOS"配置在库"一贯模式（`SYSDD_REPORT` / `SYSQR` 均如此），避免文件系统写权限、多实例部署不一致问题；`LAYOUT_VERSION` 支持内置版式升级与定制版本追踪。绑定键沿用 §9.5.3：`(单据类型, 客户)` → 单据类型默认，**收货方不作键**。绑定行携带 `HEADER_ID` 等配置，正好承载"同一开单方多个公司实体、按客户 × 单据类型选 A/B 页头"的需求（斯百德供应链（东莞） vs （香港）场景，ADR-009 §9.2 澄清）。

### 决策 4：安全边界 —— "保存即校验 + 渲染时二次校验"（已拍板）

§9.6 三条硬约束的落地：

1. **保存时（服务端）**：JSON Schema 校验（格式合法、坐标在页内、元素数/文件大小上限）+ **字段引用白名单校验**（`MASTER.*` / `DETAILS.*` 必须 ∈ 该 format 的 `dataContract` + `PrintData` 契约，服务端维护字段字典）——堵死 NetSuite 式"模板暴露敏感字段"绕过口；
2. **渲染时**：`QuestPdfLayoutRenderer` 再次 fail-closed（未知字段渲染为空或拒绝，不猜测）；
3. **权限门（三档，见"目标用户与角色分级"）**：报表中心"自定义"入口按角色分级——角色②（实施顾问）`CanDesign` 独立权限位（完整设计器）；角色③（客户维护人员）`CanAdjust` 独立权限位（微调模式）；角色①（开发人员）不进运行时权限系统，走 Git + code review 门；
4. **资源限制**：`image` 元素只引服务端白名单资源 ID（LOGO 上传路径复用），不允许外链/上传任意图片。

### 决策 5：设计器能力分级（完整模式 / 微调模式）—— "双模式 + 三档权限"（已拍板）

承接"目标用户与角色分级"第 1、2 点：

| 模式 | 面向 | 能力 | 入口 |
|---|---|---|---|
| 完整模式 | 角色①开发 / 角色②实施顾问 | 6 元素 + 字段绑定 + table 结构 + 图层 + 撤销重做 | 开发工具 / 实施后台（`CanDesign`） |
| 微调模式 | 角色③客户维护人员 | 仅移位 / 改文案 / 显隐 / 字段映射到已有字段（下拉） | 报表中心"自定义"（`CanAdjust`） |

- 微调模式是完整模式的**受限视图**（同一 schema、同一渲染层，前端只暴露能力子集），不是第二套实现；
- 角色③ 在微调模式下**不可**增删元素类型、不可改 table 列结构、不可改 `dataContract` / `params`
  （§1 分层原则：数据源 / 参数定义属开发态，客户只改布局）。

### 决策 6：内置版式单一真源 —— "layout.json 唯一真源，C# 命令式版式退役"（已拍板 2026-08-31）

承接"目标用户与角色分级"第 3 点。现状（ADR-009 §12.4）：内置版式以 C# 命令式 QuestPDF 代码为真源，
"同时生成" `layout.json` 供设计器承载——**两个真源**，靠"对拍护栏"维持一致。

角色①既用设计器产出内置格式，则建议反转为**单一真源**：

- `layout.json` 是唯一真源：内置与客户定制**统一走 `QuestPdfLayoutRenderer` 解释层**，一条渲染路径；
- 现有 24 张 C# 命令式版式作为**迁移来源 + 对拍基线**，S1 逐张转成 `layout.json` 并通过逐元素对拍后退役；
- 收益：消灭"双源漂移"；§6 风险表「解释层与 C# 内置版式语义漂移」「JSON 难 diff」两条降级或消除；
  开发者与实施顾问用同一套工具、同一条渲染链；对拍护栏从"持续兜底"降为"迁移期一次性校验"；
- 代价：失去 ADR-009 §12.4「内置版式直连 C# 渲染」的性能与类型安全路径（单据版式场景性能差异可忽略；
  类型安全由 schema 校验 + 字段白名单替代）。

**窗口期**：当前无已上线客户、无存量客户定制，24 张 C# 内置版式均仍在开发中——这是"退役 C# 命令式版式、
统一走解释层"**成本最低的窗口**。越晚迁移，存量定制与外部依赖越多，双源漂移风险越高。故建议在 S1 内一次性完成迁移。

**已拍板（2026-08-31）**：接受"内置版式统一走解释层、C# 命令式版式退役"。迁移在 S1 内一次性完成——
24 张 C# 版式逐张转 `layout.json`、逐元素对拍通过后退役，不保留 C# 直连渲染路径。

---

## 3. QuestPdfLayoutRenderer 解释层（S1 核心）

QuestPDF 是命令式绘图库，但可被声明式描述驱动（§9.7.1 推翻旧论断的依据）。实现要点：

1. 解析 schema → `page.Size / Margin` → 三个 section 依次绘制；
2. 元素按绝对坐标绘制（mm → QuestPDF 布局定位）；
3. `table` 元素：读 `PrintData.Details` 渲染明细，**自动分页 + 表头重复 + 合计行**（合计列复用 `PdfLayout.IsAmountColumn`）；
4. 字段取值复用 `PdfLayout.FormatValue`（含 `DISPLAY_FORMAT` 白名单正则）；
5. fail-closed：未知字段引用、越界坐标、非法格式一律渲染为空串或拒绝；
6. **迁移对拍（一次性）**：S1 将 24 张 C# 内置版式逐张转为 `layout.json`，以 `sample.json`（§12 回归护栏）做"同一 `PrintData` 下解释层 vs 原 C# 版式逐元素对拍"；对拍通过后 C# 版式退役，此后 `layout.json` 为唯一真源，对拍护栏不再持续运行。

## 4. 可视化设计器 UI（S2 核心）

参考成熟"套打设计器"通用结构，对齐 EOS 现有设计规范（ErpCommandBar / UnifiedChooser / TabbedPanel）：

- **画布**：A4 页面模拟（缩放/滚动/标尺/网格），绝对定位元素拖拽、缩放、对齐线吸附；
- **元素库（左）**：text / field / image / line / rect / table，拖入画布；
- **属性面板（右）**：内容 / 样式 / 字段绑定 / 边框；字段绑定走 `UnifiedChooser`（复用字段选择规范与 `formField` 数据源）；**页头公司名/LOGO 走 `HEADER_ID` 字典引用（L2 参数化配置），不在设计器里硬编码公司文本**（ADR-009 §9.4.2 领域规则）；
- **工具栏**：撤销/重做、网格开关、**PDF 预览**（保存后调渲染接口新标签页打开）、保存；
- **图层列表**：重叠元素选择辅助；
- **入口**：报表中心"自定义"→ copy-on-write（复制内置版式 → 生成客户 LAYOUT）→ 设计器编辑 → 保存。

## 5. 执行准则（分期，各期独立回归）

迁移编号自 **031** 起（当前最新 030）。

| 期 | 内容 | 退出条件 |
|---|---|---|
| **S1 解释层 + schema v1** | ① 定 `layout.json` schema v1（含 JSON Schema 定义文件 + `schemaVersion` 版本化）；② 建 `REPORT_FORM_LAYOUT` / `REPORT_FORM_BINDING` 表（迁移 031）+ `ReportFormats:StorageRoot` 配置与内置版式资产部署；③ 实现 `QuestPdfLayoutRenderer`（绝对定位元素 + table 自动分页 + 字段取值 + fail-closed）；④ 24 张 C# 内置版式逐张转为 `layout.json`（迁移来源），对拍通过后 C# 版式退役；⑤ `sample.json` 迁移对拍护栏 | 24 张内置版式**全部迁移为 `layout.json` 且逐元素对拍一致**，迁移完成即 C# 版式退役、无双源残留；未知字段引用 / 越界坐标 E2E fail-closed 通过；字段白名单校验单测绿 |
| **S2 设计器 MVP + copy-on-write** | 报表中心"自定义"入口 + 复制流程；设计器 UI（绝对定位画布 + 6 元素 + 属性面板 + 撤销重做）；保存校验链（§2 决策 4）；PDF 预览；`REPORT_FORM_BINDING` 绑定优先级命中 | 客户可完成"找到报表 → 自定义 → 拖拽改版式 → 保存 → 打印生效"全流程（UI 冒烟 + E2E）；保存时越权字段 / 非法坐标被拦截；内置版式升级不覆盖客户定制（`LAYOUT_VERSION` 验证） |
| **S3 增强**（条件触发） | 二维码 / 条形码元素、多页模板、对齐辅助完善、版本历史、list 版式流式扩展 | 按需求频次立项，不预置；复审条件见 §8 |

**依赖**：S1 依赖 §12 格式包的 `format.json`（`dataContract` 是字段白名单来源）；S2 依赖报表中心（P2 已上线）与 §12 copy-on-write 语义；全程依赖 §9.6 三条安全边界（本 ADR §2 决策 4 落地）。

### 节奏与准入（2026-08-31 前提更新）

当前项目处于**开发阶段：无已上线客户、无存量客户定制**。这修正了 L3 的节奏定位，取代此前"等真实客户案例再触发"的想法：

1. **L3 是"上线前必备"能力，不是"等客户再触发"**。ADR-009 §9.3 的"仅覆盖约 5%、不阻塞一期"
   描述的是**需求规模**，不是**启动条件**——产品一旦上线、首个实施顾问（角色②）进场，就必须能用设计器
   为客户做版式。因此 L3 按 S1→S2→S3 在开发阶段内分批完成，目标：首个实施项目上线前达到 **S2 可用**。
2. **S1 的启动门槛不变**：仍须 L1/L2 落地验收 + `format.json` 落地（`dataContract` 是字段白名单来源，
   未落地前 S1 的校验器无契约可依）。这是**顺序**约束，与"有没有客户"无关。
3. **角色① 是设计器第一批真实用户（dogfooding）**：开发人员用设计器产出内置格式（决策 6）的过程，
   本身就是对设计器可用性的最早验证，不再依赖外部客户案例来发现交互问题。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **设计器工程规模失控**（自建最大风险） | 元素最小集 6 种、schema 先行、S2 MVP 严格裁剪；复用 `UnifiedChooser` / `ErpTable` / `TabbedPanel` 既有规范，不新造 UI 范式 |
| JSON 布局难 diff / review（§9.7.1 已识别） | 单一真源后无"C#↔JSON 需同步"问题（决策 6 已拍板）；`sample.json` 快照对拍 + `LAYOUT_VERSION` 版本历史兜底 |
| 字段白名单绕过（NetSuite 教训："模板暴露敏感字段"） | 保存时双重校验（schema + 字段字典），渲染时 fail-closed；白名单来源是服务端 `dataContract`，非前端提交 |
| 解释层与 C# 内置版式语义漂移 | **已消除**：决策 6 拍板后 C# 命令式版式退役，`layout.json` 单一真源，无双源可漂移 |
| 客户定制与内置版式升级冲突 | copy-on-write 语义：定制独立成新 LAYOUT，内置升级不覆盖定制；升级时版本追踪 + 手动复核入口 |
| 商用字体 / 图片版权 | 资源白名单化，`image` 只引服务端资源；字体沿用 `PdfLayout.FontFamily` |

## 7. 选择理由

- **绝对定位**：单据套打是 EOS 客户版式差异的主要载体，行业标准模型，实现成本低于流式且不引入第二套渲染路径；
- **自建设计器**：开源生态无成熟"报表设计器"组件可直接引入（2026-08-30 调研），商业组件违反开源定位；自建 + 原语库 + 元素最小集是唯一可长期持有的路径；
- **库内存储**：与 EOS"配置在库"模式一致，避免文件系统写权限与多实例不一致；版本追踪天然支持内置升级与定制隔离；
- **双校验**：§9.6 约束落到"保存 + 渲染"两个不可绕过的点，安全边界不依赖 UI 自觉。

## 8. 考虑过的替代方案

| 方案 | 未选择原因 |
|---|---|
| 引入商业设计器组件（FastReport Web / Stimulsoft / Telerik） | 闭源/商业授权，与 EOS 开源定位冲突；格式不匹配 QuestPDF 渲染 |
| 引入开源报表设计器组件 | 2026-08-30 调研无成熟可用项（详见 §2 决策 2 表） |
| 流式布局先行 | list 报表差异已被 L1/L2 覆盖，流式渲染路径无真实需求；两套渲染逻辑成本高 |
| 客户定制存文件系统 | 写权限 + 多实例不一致；与库内绑定表（`REPORT_FORM_BINDING`）耦合割裂 |
| 客户可改 `dataContract` / `params` | 违反 §1 分层原则（数据源/参数定义属开发态）；本 ADR 明确客户只改布局 |

## 9. 复审条件

- list 报表出现"必须自定义版式结构"（非列配置）的真实高频诉求 → 评估流式布局扩展（`schema.kind: "list"` 第二渲染路径）；
- 客户定制量增长到绑定优先级（客户 × 单据类型）无法覆盖 → 评估绑定键扩展（收货方维度启用需 §9.5.4 三前置）；
- 设计器保存量出现性能问题 → 评估 layout 快照化 / 增量校验缓存；
- ADR-009 P7 最小语义层落地后，`format.json` / `layout.json` 字段引用与语义层度量定义对齐。
