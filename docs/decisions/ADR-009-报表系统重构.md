## 背景

报表子系统横跨 14 个源文件、约 **4174 行**代码，是系统中配置表最多、权限模型最特殊的部分。
2026-08-29 做了一次完整盘点（`docs/plans/报表架构调研与收敛建议.md`），确认其复杂度不是来自代码量，
而是**数据模型把本该在开发态固化的东西全部做成了运行时可配**。

### 3. 五个结构性问题

#### 3.1 报表本质被拆成七表联查

报表是两个**纯函数**：

```
Report(参数, 用户) → 行集      ← 取数 + 汇总 + 权限
Layout(行集, 格式) → 文档      ← 格式化呈现（屏幕表格 / PDF / Excel）
```

两者没有业务耦合：同一份行集可以渲染成屏幕表格、PDF、Excel。但 EOS 把这两件事塞进同一张 `REPORT`
表，并额外分出 4 张布局表承载"一份模板"。后果是 `ReportRepository.cs` 运行时要读 **6 张表**
（`MODULES` / `FIELDS` / `REPORT` / `REPORT_SORT` / `SYSQR_DEFAULT` / `SYSQR_USER`）才能确定一张报表
长什么样，权限再查 `SYSDD_REPORT` / `SYSDH_REPORT`。

补上报表另外两个被外挂的输入后，完整模型是**四个输入**：

| 输入 | 应归属 | 理由 |
|---|---|---|
| 数据源（表 / 视图 / SP） | **开发态** | 进 Git、可 review、可做影响分析 |
| 汇总口径（度量定义） | **开发态** | 口径必须唯一，否则每张报表各算各的"销售额" |
| 参数界面（筛选定义） | 运行时可配 | 业务需要按人按场景调 |
| 权限谓词（行级过滤） | 运行时可配 | 但**求值点必须在数据层**，不在报表层 |

**过度工程化的根因：EOS 把四个输入全部做成了运行时可配，且每一个用不同的表承载。**

#### 3.2 两套权限，第二套是第一套的物化展开

`SYSDD`（普通单据权限）里**本来就有 `REPORT_TAG` 报表权限位**。
`DomainRuleService.cs:508-518` 从它笛卡尔积展开出 `SYSDD_REPORT`：

```sql
INSERT INTO dbo.SYSDD_REPORT (USER_ID, M_IDX, REPORT_ID, PREVIEW_TAG, PRINT_TAG, EXPORT_TAG, DATA_FILTER)
SELECT m.USER_ID, r.R_M_IDX, r.REPORT_ID, 1, 1, 1, ''
FROM dbo.SYSDL m CROSS JOIN dbo.REPORT r
WHERE r.R_M_IDX IN (SELECT M_IDX FROM dbo.SYSDD WHERE REPORT_TAG=1 AND USER_ID=@UserId)
```

第二套权限不是独立语义，是第一套里一个 bit 的缓存。代价：

- 行数膨胀为 用户 × 报表（200 用户 × 500 报表 = 10 万行），默认全开 `1/1/1`；
- 新报表只在用户**下次触发时**才补行，中间存在空档；
- `DATA_FILTER` 挂在报表权限行上 → **每张新报表要重配一遍行级过滤**，换个取数路径就可能绕过。

#### 3.3 三张同构的"用户存 SQL"表

```
SYSQD       PK=(USER_ID, T_ID)   列：T_SQL, T_CONDITION
SYSQL       PK=(USER_ID, T_ID)   列：T_SQL, T_CONDITION     ← 与 SYSQD 完全相同
LISTREPORT  PK=(USER_ID, T_ID)   列：T_SQL, T_CONDITION, T_CONDITION_DESC
```

三张表在做同一件事，是三代需求叠加、每代新起一张表的痕迹。`LISTREPORT_CONDITION` 更进一步，把 SQL
语法树拆成列存（`LEFT_KH` 左括号 / `OPERATOR` / `CENTENT_KEY_1` / `RIGHT_KH` 右括号 / `LOGIC` 逻辑符），
等于在关系表里重建 WHERE 子句。

#### 3.4 `REPORT_PATH` 已是死列

`REPORT_PATH` 指向旧系统的 `.rpt` 水晶报表文件，但 `ReportRepository.cs` 中**零引用**——新系统
PDF 渲染已改为 `ReportPdfService`（QuestPDF 通用模板，`ReportPdfRenderInput` 契约），
`REPORT_PATH` 仅在 `ReportAdminRepository.cs:91` 的 INSERT 中被写入，从不读取。

#### 3.5 22 个菜单节点承载同一个页面

`MODULES` 561 条中有 **22 个 `XX98` 报表查询节点**（`1698` 采购 / `1498` 销售 / `1398` 仓库 /
`1598` 生产 …），统一挂在各业务域末尾。它们**全部指向同一个前端页面** `ReportViewerPage`
（路由 `/reports/:moduleId`，`app/routeElements.tsx:64`），只是 `moduleId` 不同，节点本身不绑定
`MASTER_TABLE`——菜单节点被当成报表目录用了。每加一张报表就往菜单树加一个节点，这与 561 条模块
本身失控是同一个模式。

单据侧另有一条**已经正确**的路径：`REPORT.R_M_IDX → MODULES.M_IDX`，`PrintService.cs:138` 用
`R_M_IDX=@ModuleId AND IS_DEFAULT=1` 取默认报表，由统一表单工具栏的 `print` 动作触发
（`commandActions.tsx:49`）。

### 4. 取数的两条路径（现状）

| 路径 | 触发条件 | 实现 |
|---|---|---|
| 动态表查询 | `MASTER_TABLE` 非空 | `MASTER_TABLE` + `FIELDS` 可见列拼参数化 SELECT（`ReportRepository.cs:177-178`） |
| 存储过程 | `definition.SpName` 非空 | `SqlCommand(definition.SpName)`，参数从 `sys.parameters` 读（`:283`、`:343`） |

两条路径都是**服务端受控**的，这点是好的，重构予以保留。

### 5. 外部调研结论（支撑本决策）

| 产品 | 报表定义在哪 | 用户写 SQL 吗 | 报表权限 |
|---|---|---|---|
| SAP S/4HANA | CDS View（ABAP DDL 源码对象，走 CTS 传输） | 否 | PFCG + DCL，一条角色对 ABAP/OData/分析查询全部生效 |
| D365 Business Central | AL 代码，随 .app 扩展分发、进 Git | 否 | 复用统一 permission set |
| NetSuite | Saved Search 元数据对象，可打 bundle | 否（SQL 只在开发者侧） | 统一 role |
| Odoo | `ir.actions.report` + QWeb，写在模块 XML | 否 | 报表 action 直接挂 `res.groups`（与单据同一套组） |

**没有一家做报表专用权限表**；**没有一家把"用户运行时存 SQL"作为一等公民功能**。
行级过滤都挂在**数据模型**上（Odoo `ir.rule` 对 ORM 查询自动生效；SAP DCL 挂在 CDS 上），
不是挂在报表上。Metabase 文档对此表述直白：SQL 权限需要单独授予，因为
"SQL queries can circumvent table-level permissions"。

导航侧（SAP Fiori 官方设计系统与最佳实践）：Space/Page/Section/Tile 按 **"Day in the Life"** 组织、
**整页不超过 25 个 app**、App Finder 兜底、"a page serves as a 'favorites' page"；
D365 BC 用 Role Center + 全局搜索（Tell Me）+ Bookmark + Report Inbox 找报表，而非菜单浏览。

## 决策

### 1. 确立报表模型与配置分层原则（后续所有取舍的依据）

- 报表 = `Report(参数, 用户) → 行集` + `Layout(行集, 格式) → 文档`，两个纯函数，物理分离。
- 四个输入按 §3.1 表分层：**数据源与汇总口径属开发态，参数界面与权限谓词可运行时配置**。

**这是一条可执行的评审规则**：凡是"让业务人员在运行时改数据源或度量口径"的需求，答案一律是 no。
`LISTREPORT.T_SQL` 与 `LISTREPORT_CONDITION` 从根上就不该做。

### 2. 权限：`SYSDD.REPORT_TAG` 唯一真源，`SYSDD_REPORT` 降级为 override

- **`SYSDD.REPORT_TAG` / `SYSDH.REPORT_TAG` 是模块级报表可见性的唯一真源**，与第一套权限完全同构。
- `SYSDD_REPORT` / `SYSDH_REPORT` 降级为**例外表（override）**：只为"确实需要逐报表收紧的人"写行；
  不写行 = 跟随模块 `REPORT_TAG` 全开（`PREVIEW/PRINT/EXPORT` 三项）。
- **删除 `DomainRuleService.cs:508-518` 的物化展开**，改为读取时"默认全开 + override 覆盖"。
- `ReportRightsMatrix` 页面从"N×M 全矩阵"改为"默认开放 + 例外清单"，维护行数从 用户×报表 降到个位数。
- **`DATA_FILTER` 求值从"报表权限行"下沉到统一数据访问层**，让报表、单据列表、Agent 走同一个过滤器。
  求值位置（Repository 基类 / 语义视图 / 拦截器）在本 ADR 中**登记为待定**——**✅ 已落地（2026-08-30 §13 专项评审定案：SQL 构建期 C# 受控组件（`WorkbenchScopeFilter` 同模式），受控解析单点化为 `DataFilterParser`；报表路径 `ReportRepository.ApplyControlledFilter`（`Data/ReportRepository.cs:608-628`）与工作台 `WorkbenchScopeFilter`（`:20,36,63`）同经该解析器白名单化、解析失败即 fail-closed 拒绝；P1 已实施，见 `docs/status.md` 2026-08-30「ADR-009 P1 权限语义落地」条）**。
  （原句"P1 实施时确定并在复审登记中记录（见"复审条件"）"已由 §13 专项评审提前定案，保留原文以免丢失历史。）

**override 表结构**（保留现有主键、新增审计与收藏列，见 §7）：

```
SYSDD_REPORT (
    USER_ID      …, M_IDX INT, REPORT_ID …,
    PREVIEW_TAG  BIT, PRINT_TAG BIT, EXPORT_TAG BIT,
    FAVORITE_TAG BIT   NOT NULL CONSTRAINT DF_SYSDD_REPORT_FAVORITE DEFAULT(0),   -- 新增
    SORT_IDX     INT   NULL,                                                       -- 新增，收藏排序
    LAST_RUN_AT  DATETIME2 NULL,                                                   -- 新增，最近使用
    DATA_FILTER  NVARCHAR(MAX),      -- 保留存量，P1 后只作为 override 语义，不再全量物化
    PK = (USER_ID, M_IDX, REPORT_ID)
)
```

> 收益：权限行数量级从 10 万降到数百；新增报表不再需要补行；行级过滤不再随报表数量线性重配。

### 3. 入口：22 个菜单节点收敛为 1 个报表中心

分类尺子是**参数形状**，不是业务域：

| 参数是什么 | 入口 |
|---|---|
| 某一张具体单据 | **留在单据表单工具栏**（在采购订单上打印采购订单）——机制已存在，不动 |
| 一组筛选条件 | **收敛进报表中心**（销售分析、库存周转） |

22 个 `XX98` 节点全部属于后者，因此：

- 菜单树撤掉 22 个 `XX98` 节点，顶层挂**一个**「报表中心」模块；
- 报表中心内部：**按业务域平铺分组 + 搜索框 + 收藏 + 最近使用**，**不复制侧栏的树形导航**；
- 单据类报表不动，继续走 `PrintService` 默认报表路径。

**不做**："每个业务域一个报表工作台页"——那只是把 22 个节点换个壳。

### 4. 自定义查询：不再新增"用户运行时存 SQL"

- `SYSQD` / `SYSQL` / `LISTREPORT` 三表**不再新增写入**。
- P3 做一次**存量审计**（各表数据量 + 最近修改时间 + 是否可追溯到在用功能点），报告落 `logs/`。
  真有业务价值的查询，转成**受控数据源**：服务端注册命名视图或 `sourceKey`，进 DbUp 迁移、进 Git、
  可 review；其余**物理删除表**。
- 若最终仍须保留"高级用户自定义查询"，套 NetSuite SuiteQL 式笼子：只读连接、函数白名单、强制参数
  绑定、行数配额、权限透传；且作为**单独授予的高危权限**，不给普通角色。

### 5. 布局四表合一 + 死列物理删除

`REPORT_HEADER` / `REPORT_FOOTER` / `REPORT_TAIL` / `REPORT_IMAGE` 合并为单一布局资源表：

```
REPORT_LAYOUT (
    LAYOUT_ID   NVARCHAR(50)  NOT NULL PRIMARY KEY,
    KIND        NVARCHAR(20)  NOT NULL,      -- HEADER / FOOTER / TAIL / IMAGE
    LAYOUT_DESC NVARCHAR(100),
    CONTENT     NVARCHAR(MAX),               -- 文本型（页眉/页脚/表尾）
    IMAGE_PATH  NVARCHAR(500),               -- 图像型（LOGO）
    IS_DEFAULT  BIT NOT NULL CONSTRAINT DF_REPORT_LAYOUT_DEFAULT DEFAULT(0),
    CREATE_BY / CREATE_DATE / LAST_UPDATE_BY / LAST_UPDATE_DATE
)
```

- `REPORT.HEADER_ID` / `TAIL_ID` / `IMAGE_ID` 保留列名与语义，改为指向 `REPORT_LAYOUT.LAYOUT_ID`；
- `REPORT.FOOTER_TEXT`（页脚文字，纯文本）保留在 `REPORT` 上，不进布局表；
- **`REPORT.REPORT_PATH` 物理删除**（§3.4 已证死列，无任何读取点）；
- `REPORT.DEFAULT_PAPER` / `DEFAULT_PRINTER` 迁往 `SYSQR`（用户打印偏好本就在该表），`REPORT` 上物理删除。

### 6. 条件定义结构化（复用 ADR-008 契约）

消灭 `SYSQR_DEFAULT` 的 `F_TYPE` 1-5 专用 DSL，改为结构化参数定义。

**关键区分**：选择器过滤（ADR-008）是**固定条件**，报表条件是**用户填值的参数**——
因此结构化分两层存放：

| 表 | 新增列 | 存什么 |
|---|---|---|
| `SYSQR_DEFAULT` | `FILTER_TEMPLATE NVARCHAR(MAX)` | 参数定义：字段 + 算子 + **参数占位符** `{p.PARA_NAME}` |
| `SYSQR_USER` | 不变（`F_TAG` / `F_VALUE`） | 用户实际填的值 |

契约（条目形状与 ADR-008 §3 一致，新增 `{p.X}` 参数占位符）：

```json
{ "logic": "AND", "items": [
  { "field": "ORDER_DATE", "operator": "GE", "value": "{p.DATE_FROM}" },
  { "field": "CLIENT_ID",  "operator": "EQ", "value": "{p.CLIENT_ID}" }
] }
```

- 运行时：`{p.X}` 从 `SYSQR_USER` 取用户值**参数化绑定**（不是字符串拼接），与 ADR-008 的
  `{m.X}` / `{d.X}` 模板占位符同构、共用校验器对占位符的解析能力；
- `F_TYPE` / `F_EXPR` 在 P4 转换完成后**物理删除**；转换不了的条件仿 ADR-008 §6 三档法，
  入 `logs/` 人工清单 + fail-closed，**绝不猜测落库**；
- `LISTREPORT_CONDITION`（LEFT_KH/OPERATOR/CENTENT_KEY_1/RIGHT_KH/LOGIC）随 `LISTREPORT` 一并处置，
  不再作为新功能承载。

### 7. 报表中心能力三件套（N2，否则中心化会退化成另一棵难用的树）

- **收藏**：`SYSDD_REPORT.FAVORITE_TAG` + `SORT_IDX`（§2 新增列）。
- **最近使用**：`SYSDD_REPORT.LAST_RUN_AT`，取 top N。
- **调度订阅 + Report Inbox**（D365 BC 模式）：让报表主动找人，比让人去找报表更进一步。

**存服务端而非 `localStorage`**：换机不失，且支持管理员预置常用报表。

### 9. 单据套打：开放 Layout，锁死 Report（2026-08-30 补充）

#### 9.1 实证：62 个送货单不是 62 个设计

`PrintService` 目前只产出 `PrintData`（主表+明细+列定义+页头页尾），`Pdf|PDF|QuestPDF`
匹配数 **0**，注释自述为"报表打印模板的**第一步**"——渲染未接上（§8 已登记）。
补充这一环前，先要弄清旧系统为什么会长出 62 份送货单，否则新方案会复刻同一个坑。

| 观测 | 数据 |
|---|---|
| 套打类送货单（`Send*` 非 List） | **62 份**，内容两两不同（md5 全异） |
| 清单类（`Send*List*`） | 24 份 |
| 体积中位数 | 23 552 字节 |
| **四分位区间** | **23 552 – 24 576，跨度 1 024 字节（4%）** |
| 落在 22–26 KB 窄带内 | 52 / 62（**84%**） |

`client_c/` 单目录即有 30+ 份 `Send_client_c_<名>.rpt`，后缀为**收货方名**
（十余个不同收货方），另有 `old` / `bak` / `1` 历史版本后缀并存。

**84% 的变体体积差异 <4%，说明它们不是 62 个不同版式，而是同一个版式绑了 62 组抬头数据。**

#### 9.2 根因：客户级配置已存在，但没有通道到达模板

`CLIENT` 主档上**已经有**抬头所需的全部数据：

```
CLIENT      CLIENT_NAME / FULL_NAME_CN|EN  客户名称
            DELI_ADDR_CN|EN                收货地址
            INV_ADDR_CN|EN                 发票地址
            TEL / FAX / LINKMAN            电话 / 传真 / 联系人
            HEADER_ID                      客户级抬头
            PRINT_PRICE                    是否打印单价
CLIENT_LINKMAN  (CLIENT_ID, SERIAL_NO, …)  一客户多联系人
```

然而报表渲染路径**只认报表级抬头**：

- 旧系统 `RPT/GetReportInfo.aspx.cs:30`、`RPT/RptParent.master.cs:29` 取的是
  `REPORT.HEADER_ID` / `SYSQR.HEADER_ID`，从不 join `CLIENT`；
- `CLIENT.PRINT_PRICE` 在旧系统全库仅出现于维护页 `ERP/COP/Client.aspx:401` 的
  `chk_PRINT_PRICE` 复选框——**渲染侧零消费点**；
- 新系统 `PrintService.cs:136` 同样只读 `r.HEADER_ID`、`r.TAIL_ID`。

于是形成死结：客户要不同抬头 / 不同单价策略 → 在 `CLIENT` 上配不了（配了也没人读）→
实施人员复制一份 `.rpt` 改硬编码 → 每家客户 × 每个收货方 × 每个历史版本各一份。

**结论：这不是"客户需要设计能力"，而是"已有的客户级配置被二进制模板挡住了"。**

> **2026-08-30 抬头语义澄清（用户拍板）**：单据页头（Title）永远是**开单方主体**——
> ERP 使用者自己的公司实体（可多个：东莞公司 / 香港公司），**不是往来单位名称**。
> `CLIENT.HEADER_ID` 的语义是「该客户的单据默认用哪个**开单方**页头」（指向页头字典引用），
> 不是「把客户名当抬头」。客户/收货方/供应商的公司名、地址、联系人属**正文数据**。
> 旧系统的页头设计（`REPORT_HEADER` 少量可复用字典 + 报表默认 + 客户默认 + 用户打印时
> "请选择页头"下拉 + `SYSQR` 记忆）正是这套引用模型，本 ADR 予以保留；**P6 实现曾以
> `CLIENT.FULL_NAME_CN/EN` 直接覆盖页头公司名（导致单据 Title 显示客户公司名），
> 2026-08-30 已修正为只按 HEADER_ID 链解析页头**，见 §9.4.2。

#### 9.3 决策：三层能力，不是给客户一个设计器

| 层 | 客户真正要的 | 提供方式 | 预估覆盖 |
|---|---|---|---|
| **L1 抬头数据化** | 换收货方就换抬头/地址/电话/LOGO | 模板从 `CLIENT` / 收货方主档取值，不再硬编码 | 70–80% |
| **L2 参数化配置** | 是否显示单价、是否含发票联、纸张、份数 | 模板参数面板，取值来自 `CLIENT.PRINT_PRICE` 等既有配置 | 15–20% |
| **L3 模板自定义** | 版式确有差异（发票版 / 外币版） | **可视化设计器 + `layout.json`**（§9.7.1 定案 QuestPDF 解释层），需沙箱与字段白名单 | 约 5% |

> **2026-08-30 澄清**：本节标题"不是给客户一个设计器"指**套打这一层**——L1/L2 用数据化配置解决，
> **不是**让客户用设计器替代数据配置。§9.7.1 定案后，L3（版式确有差异的场景）由
> **可视化设计器 + QuestPDF 解释层**承载，二者不矛盾：L1/L2 解决 85–95% 的"数据差异"，
> 设计器只服务 L3 的"版式差异"。

- **L1/L2 是本 ADR 的决策范围**，基础设施（`CLIENT.HEADER_ID`、`PRINT_PRICE`、
  `DELI_ADDR`、`CLIENT_LINKMAN`）**已存在**，缺的只是打印数据集把客户级字段带出来、
  模板按参数渲染。
- **L3 不纳入本期**，已由 ADR-010 定案（2026-08-31 拍板，见 §9.7.1），作为标准产品能力项独立分期实施。
- 若 L1 需要"一客户多收货方"，优先复用 `CLIENT_LINKMAN` 的 `(CLIENT_ID, SERIAL_NO)`
  模式新增收货方主档，**不要**用复制模板的方式解决。

#### 9.4 既有范式验证：2201–2205 的三层消费链（2026-08-30 补充）

重构目标是做**标准 ERP 产品**——不为任何一家客户做定制，而是提供能力让客户自行配置。那么首先要回答：
**EOS 是否已经有「客户自助配置报表」的既有范式？**

答案是有，且五个页面已全部验收上线（2026-08-28）。它们不是五个孤立的管理页，
而是一条完整的 **配置层 → 消费层 → 选择层** 链路。

**配置层**（管理员在受约束 UI 中定义，写侧服务端校验）

| 模块 | 页面 | 维护对象 | 存量 |
|---|---|---|---|
| 2201 | `/admin/report-setup` | `REPORT` + `REPORT_SORT` | 470 / 562（覆盖 205 张报表） |
| 2202 | `/admin/print-setup?tab=headers` | `REPORT_HEADER`（+ LOGO `POST /print-admin/logo`） | 5 |
| 2203 | `/admin/print-setup?tab=footers` | `REPORT_FOOTER` | 2 **（死表，见 §9.4.1）** |
| 2204 | `/admin/print-setup?tab=tails` | `REPORT_TAIL` | 5 |
| 2205 | `/admin/report-conditions` | `SYSQR_DA` + `SYSQR_DEFAULT` | 148 / 568（覆盖 148 个模块） |

2202–2204 是**同一页面** `PrintSetupPage` 的三个 tab（`Tab = 'headers'|'tails'|'footers'`）。

**消费层**（服务端白名单校验后读取，fail-closed）

- `ReportRepository.ReadConditionsAsync` → 查看器条件面板（消费 2205 产出）
- `ReportRepository.ReadDefaultSortFieldsAsync`（`ReportRepository.cs:371-378`）→ 排序/分组（2201）
- `PrintService.cs:136/155/173` → `REPORT.HEADER_ID` / `TAIL_ID` → `REPORT_HEADER` / `REPORT_TAIL` 文本
- `ReportPdfService.Generate` → QuestPDF 渲染（页头 LOGO/公司名/抬头文本；页脚 `FOOTER_TEXT`；表尾 `TAIL_TEXT`）

**选择层**（终端使用者在打印时选择并记忆）

`SYSQR`（1201 行，968 行 `IS_LAST=1`，`HEADER_ID` 全部非空）按 **用户 × 模块 × 报表** 记忆
`HEADER_ID` / `TAIL_ID` / `LAST_SORT` / `SORT_ASC` / `SHOW_GROUP` / `SHOW_DETAIL` /
`PRINTER_NAME` / `PAPER_SIZE`（`PrintSettingsRepository.SaveAsync`）；
条件值记忆另存 `SYSQR_USER`（1152 行）。

##### 9.4.1 这条链路给出的三个结论

**结论一：不需要新建范式，只需要平移。** 2201–2205 已经证明「客户自助配置报表」在 EOS
是可行的、产品化的、且已被验收的。套打不缺范式，缺的是把这条链路平移过去（§9.4.2）。

**结论二：两处「配置页在维护、运行时没人读」的死表，是范式的反例。**

- `REPORT_FOOTER`（2203）：仅 2 行（`001` 会计/审核/核准、`002` 收货员/品管/仓库）。
  旧系统 `RPT/GetReportInfo.aspx.cs:59` 用 `WHERE FOOTER_ID='" + strReportId + "'` 查询——
  拿**报表编号**当**页尾编号**用，而 `REPORT` 表**根本没有 `FOOTER_ID` 列**（只有 `FOOTER_TEXT`），
  页尾仅 `001`/`002` 两行，语义错配导致该查询恒返回空。真正生效的页脚是
  `REPORT.FOOTER_TEXT`（444 行非空），在 `ReportPdfService` 中经
  `{7}`→列印人、`{1}`/`{5}`→空串 替换后渲染（`{1}`/`{5}` 为 Crystal 时代遗留，已无对应语义）。
- `REPORT_IMAGE` / `REPORT.IMAGE_ID`：0 行、0 引用——**整表从未使用**。

两者均随 §5 `REPORT_LAYOUT` 合并时一并处置。**处置方式已由 2026-08-30 §11 最新裁定修订**
（原 2026-08-30 用户裁定与下述"保留 2203"登记，已由 §11 收回）：

- `REPORT_IMAGE`：**物理删除**（0 行 0 引用，与 `REPORT_PATH` 同批）。
- `REPORT_FOOTER`（2203 页尾设置页）：**§11 已裁定随页一并下线**（§11 评估认为旧系统该表
  恒未生效、新模型页尾由 `REPORT.FOOTER_TEXT` / 模板资产统一承载，无保留必要）。

> **2026-08-30 用户裁定（已按 §11 收回，保留作决策史）**：`REPORT_FOOTER` 保留页面与数据，
> 不删除。下述保留理由与代价登记为该时点的考虑；§11「全新报表系统」方向确立后，
> 该"保留"裁定被推翻——详见 §11 与执行准则 P3。

保留 2203 的（原）理由与代价登记如下（**§11 已收回，仅存决策史**）：

| | 说明 |
|---|---|
| 保留理由 | 该表数据虽恒未生效（查询用报表号当页尾号，语义错配），但页面已验收、已有用户可见入口；删除是不可逆的，而"未生效"是**当前**判断 |
| 保留代价 | `REPORT_LAYOUT` 合并后，页尾将出现**两个写入点**（2203 写 `REPORT_FOOTER`，报表维护写 `REPORT.FOOTER_TEXT`），存在配置分叉风险 |
| 约束 | P3 合并时 `REPORT_LAYOUT.FOOTER_TEXT` 的**唯一真源是 `REPORT.FOOTER_TEXT`**（444 行非空、运行时实际生效），不得反向对齐 `REPORT_FOOTER` |
| 后续 | ~~保留期间若确认无用户使用，可在 P3 之后单独评估下线~~ **（已被 §11 收回：直接下线，不再设观察期）** |

**警告**：保留不等于对齐。任何把 `REPORT_FOOTER` 当作页尾生效基准的实现，都是把从未生效过的
配置变成新的打印行为。

**结论三（最关键）：客户级抬头数据已在库中，且被业务真实维护。**

`CLIENT.HEADER_ID` 存量 **339/339 全部有值**，分布具有明确业务含义：

| HEADER_ID | 公司抬头（`REPORT_HEADER`） | 客户数 |
|---|---|---|
| `HDR_A` | 示例公司A | 180 |
| `DEFAULT` | （默认抬头） | 146 |
| `HDR_B` | 示例公司B | 13 |

而 `REPORT_HEADER` 全表仅 5 行（`DEFAULT` / `HDR_B` / `HDR_A` / `HDR_C` / `HDR_D`），
却支撑了 470 张报表中的 211 张（`DEFAULT` 被 128 张引用、`XX` 52 张、`HDR_A` 10 张）。

**抬头本来就是「少量可复用定义 + 引用」。** 654 个 `.rpt`（含 148 份客户定制副本、
62 份套打送货单）是**「引用」被「复制」替代**的产物——而 `CLIENT.HEADER_ID` 已在库中存有
339 家客户的正确取值，渲染侧却从不读它（§9.2）。

> **2026-08-30 澄清**：这 5 行页头是**开单方（ERP 使用者）自己的公司实体**
> （示例公司A / 示例公司B / 默认…），不是客户公司名；`CLIENT.HEADER_ID` 的语义是
> 「该客户的单据默认用哪个开单方页头」——同一使用者有多个公司实体、按客户/场景选 A/B 抬头
> （如示例公司C（东莞） vs 示例公司C（香港））正是靠这个引用模型承载的，
> 这也强化了 §9.1 的实证：62 份送货单的差异是「数据」（HEADER_ID 引用）而非版式结构。

对照：`CLIENT.PRINT_PRICE` 为 338 家 `0` / 1 家 `1`——分布极度倾斜，印证 §9.2 的风险登记
（该字段从未被消费，存量可信度必须在 P6 启用前审计，不得假设"配了就是对的"）。

##### 9.4.2 对 §9.3 的修正：套打应长成什么样

既有范式直接给出了套打的形态——**不是给客户一个设计器，而是把同一条三层链路平移过去，
并把绑定粒度从「报表级」下沉到「业务对象级」**：

| | 列表型报表（已有，已验收） | 单据套打（待建，P6） |
|---|---|---|
| 配置层 | 2201–2205 | 新增单据版式配置页（类比 2202/2204，不新建范式） |
| 消费层 | `ReportRepository` / `PrintService` / `ReportPdfService` | `PrintService` 数据集 + QuestPDF 套打模板 |
| 选择层 | `SYSQR`（用户 × 模块 × 报表） | 复用 `SYSQR`，粒度改为 **用户 × 单据类型**（可选客户覆盖） |
| 绑定粒度 | 报表级 `REPORT.HEADER_ID` | **单据抬头客户级 `CLIENT.HEADER_ID`**（§9.3 L1） |

**抬头取值优先级**（P6 实施时锁定）：
`SYSQR.HEADER_ID`（使用者选择/记忆）→ `CLIENT.HEADER_ID`（单据抬头客户默认）→ `REPORT.HEADER_ID`（报表默认）。
**2026-08-31 拍板**：用户本次选择/记忆优先（与旧系统一致，支持按场景切 A/B 开单方抬头），
客户默认仅兜底；`PrintController` 已按此定序翻转。

第一级一旦打通，§9.1 的 62 份送货单即可收敛为「1 份模板 + N 条客户/收货方记录」，
无需任何客户侧设计能力。

> **2026-08-30 领域规则（用户拍板）**：单据页头 Title = 开单方主体，永远不是往来单位。
> 页头公司名/LOGO/抬头文本来自解析链最终命中的 **`REPORT_LAYOUT KIND='HEADER'` 字典条目**；
> 客户/厂商的 `FULL_NAME_CN/EN`、地址、联系人只进正文（收货方信息区）。
> **P6 实现偏差修正**：`DocumentPdfService` 曾以 `CLIENT.FULL_NAME_CN/EN` 无条件覆盖
> 页头公司名（`DocumentPdfService.cs`），导致打印送货单/客户订单时 Title 显示客户公司名；
> 2026-08-30 已删除该覆盖逻辑，页头只按 `HEADER_ID` 链解析（控制器 `PrintController.cs`
> 的 `effectiveHeaderId` 链）。**优先级链已拍板（2026-08-31）**：用户本次选择/记忆
> （`request.HeaderId` / `SYSQR`）→ 客户默认（`CLIENT.HEADER_ID`）→ 报表默认（`REPORT.HEADER_ID`）；
> 此前实现"客户默认优先"会覆盖用户下拉选择、无法按场景切 A/B 抬头，`PrintController` 已翻转。
> 客户约束硬需求若出现，由 `REPORT_FORM_BINDING.HEADER_ID`（ADR-010 决策 3，S2）承载。

#### 9.5 版式绑定模型：结构做选择键，数据做填充（2026-08-30 补充）

§9.4.2 确定了绑定粒度下沉到客户级，但留下一个未答问题：**版式要不要绑到「收货方」
（客户的客户）？** 旧系统 `client_c/` 目录下 30+ 份 `Send_client_c_<收货方名>.rpt`
（十余个不同收货方）看似给出了肯定答案。本节用存量数据否证它。

##### 9.5.1 实证：收货方维度在 EOS 几乎没有承载

对 `COP_SEND_M`（送货单主表）实测：

| 指标 | 实测值 |
|---|---|
| 送货单总数 | **8 149** |
| 不同客户数 | **300** |
| 不同收货地址数（`SEND_ADDRESS` 去重） | **190** |
| 单量 TOP5 客户的各自收货地址数 | **全部为 1**（TTI769 1264 张 / BZ769 1035 张 / LK755 612 张 / XB0757 402 张 / XQ752 356 张） |

平均每客户 0.63 个收货地址；**单量最大的五家客户各自只有一个收货地址**。

数据模型侧同样没有承载：`CLIENT` 只有单一 `DELI_ADDR_CN` / `DELI_ADDR_EN`，
**不存在 `CLIENT_ADDR` 式的一客户多地址主档**，也没有独立的收货方主档
（`EOS.Database` 中无 `SHIPTO` / `CONSIGNEE` / `ADDR_BOOK` 类表）。结算单上的
`SEND_ADDRESS` 是**单据级快照字段**，不是引用主档的外键。

##### 9.5.2 原则：会变的是数据，稳定的是结构

由此得出一条可复用的判断尺子，适用于任何"要不要为 X 建一份版式"的需求：

> **多样性高、随单据变化的东西，应该是版式里的数据；
> 数量少、稳定的东西，才值得成为选择版式的键。**

| | 数量 | 性质 | 归属 |
|---|---|---|---|
| 收货地址 | 190（且随单据快照） | 多样、易变 | **版式内数据** |
| 抬头 | 5 行 | 少量、稳定 | **选择键** |
| 表尾 | 5 行 | 少量、稳定 | **选择键** |
| 客户 | 339 | 中等、稳定 | **选择键** |
| 收货方 | 无主档，实证几乎不分化 | — | **不作为键**（见 §9.5.4） |

**62 份送货单的错误在于：把 190 个地址当成了 62 个结构。**
这与 §9.4.1 结论三同源——抬头 5 行支撑 211 张报表是"引用"，62 份送货单是"复制"。

##### 9.5.3 决策：绑定键 =（单据类型，客户），收货方不是键

```
版式定义（少量、可版本化）
  抬头 5 行 · 表尾 5 行 · 版式模板 N 份
        ↓
绑定解析（优先级链，越靠前越优先命中）
  ① 客户 × 单据类型      ← 主绑定键
  ② 单据类型默认         ← 兜底
        ↓
版式内数据（多样、随单据取）
  收货地址 · 客户名 · 电话传真 · 单价显隐
```

绑定关系**不是复制模板，是一条解析规则**。这条规则应落在新的绑定表（P6 实施时定名，
暂称 `REPORT_FORM_BINDING`），形如
`(FORM_TYPE, CLIENT_ID, LAYOUT_ID, HEADER_ID, TAIL_ID, PRINT_PRICE)`，
而**不是** `(收货方 → 一份模板)`。

配套：抬头取值优先级沿用 §9.4.2 的
`SYSQR/本次选择` → `CLIENT.HEADER_ID` → `REPORT.HEADER_ID`（2026-08-31 定序用户优先）。

##### 9.5.4 收货方维度的启用前置条件

**不因本节实证而永久排除收货方维度**，但设定启用门槛——满足下列全部条件才可引入：

1. 先建**收货方主档**（建议复用 `CLIENT_LINKMAN` 的 `(CLIENT_ID, SERIAL_NO)` 模式，
   而非新建范式），并让 `SEND_ADDRESS` 从"自由文本快照"改为"主档引用 + 快照冗余"；
2. 存量审计证明**确有客户存在多个收货方且版式确有差异**（当前证据相反：TOP5 客户各 1 个）；
3. 差异仍须先尝试用版式内数据（地址、联系人、电话）吸收，吸收不了的才上升为绑定键。

在此之前，收货方相关的差异一律由**版式内数据字段**承载。

#### 9.6 安全边界：开放 Layout，锁死 Report

无论做到哪一层，以下三条为硬约束，与 §1「数据源/汇总口径属开发态」闭环：

1. **模板只消费 `PrintData`**（已经过授权、已按 `FIELDS` 过滤成本/保密/禁止字段），
   **不得自行取数**——模板层不接触连接串、不接触表名。
2. **模板语言必须无副作用**：不执行任意代码、不发网络请求、不读写文件系统。
3. **可引用字段走白名单**，来自打印数据集契约，非全表字段。

外部依据（支撑"选声明式模板，不选可编程模板"）：

- **D365 BC** 明确区分信任级别：RDLC 可嵌表达式，**"RDLC layouts aren't trusted, so
  they run in a sandbox app domain"**；而 **Word 布局是纯 XML 映射，不受沙箱约束**，
  Microsoft 因此建议"文档类报表优先用 Word 布局而非 RDLC"。
  —— 即：**可编程布局必然带来沙箱成本，声明式布局不会。**
- **NetSuite Advanced PDF/HTML Templates** 允许客户直接编辑 HTML + FreeMarker，能力最强，
  但实践界的警示是：*"A template can expose sensitive fields even when the transaction
  form does not visibly display them elsewhere"*——**模板会绕过字段级可见性**。
  EOS 已有成本/保密字段过滤，开放模板时必须用白名单兜住，这正是约束 3 的来源。

#### 9.7 待决策（L3，需单独 ADR）

> **✅ 已由 ADR-010 全部 6 项拍板（2026-08-31）**；本节保留为当时的待决策登记，结论见本节末的
> 「L3 待决策清单」逐条映射与 `docs/decisions/ADR-010-可视化版式设计器.md` 决策 1–6。

**先澄清 L3 的定位（2026-08-30，用户"做标准 ERP 产品"的定位引发）**。
本 ADR 在 §9.3 与替代方案 F 中否决的，是**"用设计器消化 62 份存量"**；
这**不等于**否决 L3 作为产品能力。两者是不同问题，此前被混为一谈：

| 问题 | 是否需要 L3 | 理由 |
|---|---|---|
| **消化旧系统 62 份存量送货单** | **否** | §9.1 实证：84% 的体积差异 <4%，差异来自抬头**数据**而非版式；L1/L2 即可收敛为 1 份模板。用设计器只是把"复制 62 份"从开发商侧搬到客户侧，且从此无法回归对拍 |
| **作为标准产品，向客户提供自助版式能力** | **是，但可后做** | EOS 定位是标准 ERP 产品、**不为单个客户做定制**。缺少 L3 则每来一个新客户、每有一种新单据格式，都要开发商出模板——这与"标准产品 + 客户自助"相悖 |

**结论**：

- L3 **不进入 P6**（消化存量用不到它），也**不阻塞**本 ADR 的任何一期；
- 但 L3 应作为**标准产品的能力项**独立评估，单独出 ADR
  （设计器实现形态选型 + 沙箱 + 字段白名单，参照 NetSuite Advanced PDF/HTML Templates；
- L3 立项的**技术前提**是 §9.6 的三条安全边界必须先落地——否则模板层会成为字段权限的绕过口；
- **渲染器已定案（2026-08-30 用户拍板）：继续使用 QuestPDF，不引入 Typst**；
  L3 以「可视化设计器 + QuestPDF 解释层」交付（见 §9.7.1）。

#### 9.7.1 渲染器定案：QuestPDF + 可视化设计器（2026-08-30 用户拍板，推翻 Typst 候选）

**决策**：放弃 Typst，继续使用 QuestPDF（C# 强类型、与 .NET 技术栈完美契合），
通过「可视化拖拽设计器 + 布局 JSON 解释层」满足客户自助版式（L3）诉求。
**24 张内置版式非零重写**：按 ADR-010 决策 6（2026-08-31 拍板），S1 统一转为 `layout.json`、
逐元素对拍通过后 C# 命令式版式退役，`layout.json` 成为唯一真源（C# 版式仅作迁移来源 + 对拍基线）。

**技术原理**：QuestPDF 是命令式绘图库，但**可以被声明式描述驱动**——运行时写一个
`QuestPdfLayoutRenderer` 解释器：读取 JSON 布局描述，逐元素调用 QuestPDF API 绘制。
这与 FastReport / ActiveReports 的「报表定义（FRX/RDL）+ 运行时引擎」是同一经典模式，
**推翻「QuestPDF 编译期绑定结构上无法满足 L3」的旧论断**。

```
拖拽设计器（React 前端）
  ├─ 画布：可视化布局
  ├─ 元素库：文本 / 图片 / 线条 / 二维码 / 表格 / 数据字段
  ├─ 属性面板：字体、边框、对齐、数据绑定（{CLIENT_NAME}）
  └─ 保存 → JSON 布局描述（schema 版本化）

运行时（EOS.API，C#）
  └─ QuestPdfLayoutRenderer
       ├─ 解析 JSON 布局
       ├─ 绑定 PrintData 字段（白名单，§9.6 约束 3）
       └─ 逐元素调用 QuestPDF API 绘制
```

**与 Typst 路线对比（本轮评估结论）**：

| 维度 | 可视化设计器（QuestPDF 解释层） | Typst 文本模板 |
|---|---|---|
| 客户体验 | 可视化、零学习成本 | 需学标记语言 |
| 与 C# 契合 | **完美**（纯 C# 解释器） | 不契合（外部 Rust 引擎） |
| 布局描述 | JSON（机器友好，人难读） | `.typ` 文本（人可读、可 Git diff） |
| 版本化/review | JSON diff 困难（坐标噪音） | 天然可 diff/review/回滚 |
| 工程成本 | 设计器 UI 本身巨大（≈再造 FastReport） | 解释器中等，但引入新运行时 |
| 安全边界 | JSON 只引用白名单字段，无执行能力 | 纯文本模板 + 字段白名单，同样安全 |

**关键取舍**：设计器胜在「客户体验 + C# 契合」，Typst 胜在「模板代码化/可 review」。
本 ADR 选择设计器路线——因为 EOS 的 C# 契合度是强偏好、且不引入第二个运行时。

**L3 待决策清单（2026-08-31 已全部由 ADR-010 定案）**：

1. **可视化设计器实现形态** → ADR-010 决策 2：**自建 UI + 开源拖拽原语**（`dnd-kit`/`react-moveable`），
   否决引入报表设计器组件（开源生态无成熟可用项，商业组件违反开源定位）。
2. **布局模型** → ADR-010 决策 1：**绝对定位**，一期只服务 document 版式；`schema.kind` 与
   `table` 元素"区域内流动"语义为流式扩展留接口。
3. **开源约束** → ADR-010 决策 2 落地：设计器自建、拖拽原语选 MIT 库，全程限于开源栈。
4. **`REPORT_LAYOUT` 是否扩展承载套打版式** → ADR-010 决策 3：**另立 `REPORT_FORM_LAYOUT` +
   `REPORT_FORM_BINDING` 表**（客户定制 copy-on-write 入库），不扩展 `REPORT_LAYOUT`。
5. ~~L1 的"收货方"维度是否新建主档~~ **已由 §9.5 裁定**：不作为绑定键，
差异由版式内数据承载；若将来启用，前置条件见 §9.5.4。

#### 9.8 默认版式的定位：安全网，不是交付品（2026-09-23 补充）

**问题**：内置格式包按三个层级解析——模块专属包 → `_card`（仅 1401/1601）→ `_generic`。
这份回退让新增模块一挂上统一表单就能打印，但掩盖了一个事实：**绝大多数可打印模块并没有专门版式**。
实测：启用模块 363 个，其中有报表定义（可打印）的 202 个，而内置格式包只有 22 个目录
（含 `1406-pick` / `1607-putaway` 两个报表级变体），约 180 个模块实际打印的是 `_generic`。

**决策 1：主要业务单据必须有专门版式，默认兜底不得充当交付品。**
`_generic` 产出的是"一批可见字段的名值表 + 一张全列宽明细"，它够用来应急核数，
但不足以拿给客户、报关或归档。它的角色是**新增模块的最低可用输出**，不是产品的成品形态。

**决策 2：「主要单据」按三条判定，任一命中即视为主要**——用这三条兜住的是"这张纸会产生后果"：

| 判定 | 说明 | 当前典型 |
|---|---|---|
| 出公司的 | 客户/厂商/报关可见 | 报价单、订单、送货单、退货单、Packing List、送货单回执 |
| 要归档或被审的 | 库存/资金入账凭据 | 入库单、收料单、收付款单 |
| 现场作业的 | 仓库/车间照单执行 | 制令单、领料单、拣货单、上架单 |

**决策 3：默认版式收缩为"单别 + 单号 + 明细"的最低形态。**
主表区不再铺全部可见字段，只保留单据标识（单别 + 单号）；明细列取 `SYSQL_DEFAULT`
（`T_ID` = 主表、`T_ID_R` = 子表，按 `F_IDX` 排序），无该配置时回落 `FIELDS.IS_DEFAULT_FIELDS`，
再无则回落全部可见列。用户的个人列配置 `SYSQL_FIELDS` **不参与**——默认版式是共享基线，
不该随某个用户调过列就变。

单别/单号不需要猜字段：模块业务规则里已有 `BillTypeField` / `BillNoField` 的登记
（由主表主键推断——主键中含 `NO` 的是单号，另一列是单别）；未登记自动单号的模块，
回落取主表主键列，主键本身通常就是单别 + 单号。

**决策 4：`_generic` 回退包按模块实例化，消除"假契约"。**
回落到 `_generic` 时，`title` 取模块描述（`MODULES.M_DESC`，与 `PrintData.Title` 和
PDF 文件名同源——打印出来的标题本来就是它，设计器显示"通用单据"反而是不自洽的），
`dataContract` 由该模块真实字段元数据合成。理由是设计器的字段候选直接消费 `dataContract`，
而现在 `format.json` 里写的是一组送货单式的硬编码列，落到 `_generic` 的模块打开设计器
看到的是不属于自己的字段。

> 注意：`formatId` **保持 `_generic` 不变**——它是 copy-on-write 的基线来源
（`REPORT_FORM_LAYOUT.BASE_FORMAT_ID`）与模板库的排除依据，改成模块号会让"内置通用基线"
这件事消失，定制版式日后升级就找不到基线。要改的只有展示用的标题与契约。

**决策 5：版式包与模块解耦，主表相同的模块共用一份。**
`REPORT.FORMAT_ID` 允许任何报表指定任意格式包编号（`1406-pick` / `1607-putaway` 即同类先例），
因此不必一模块一文件：1502 / 1512 / 1522 共用 `MOC_PRODUCE_M`，做一份即可；
1409 与 1407 共用 `COP_RETURN_M`，现有的 1409 独立版式值得核对是否为重复资产。
新增六份建议以结构最完整的现有版式（1406 送货单）为母版派生，不从空白 `layout.json` 起手。

**决策 6：兜底必须可见。** 加一条门禁，输出"当前仍落在默认版式的模块清单"。
兜底本身无害，有害的是静默——正因为没人看得见这 180 个模块，缺版式这件事才一直没暴露。

**本次盘点出的缺口（登记，未开工）**：

| 优先级 | 模块 | 名称 | 备注 |
|---|---|---|---|
| 高 | 1502 | 制令单 | 生产主单据；同时供 1512 / 1522 复用 |
| 高 | 1505 | 入库单 | 库存入账凭据 |
| 高 | 1417 | Packing List | 出公司（客户/报关） |
| 中 | 1413 | 送货单回执 | 客户签收回执 |
| 中 | 1411 / 1412 | 备货单 / 备货返仓单 | 现场作业 |

询价比价段（1402 / 1602 计价表、1403 / 1603 询价单）暂按长尾处理，仍走默认版式。

**未决**：本节登记的是"默认兜底不再是交付品"的定位与随之而来的缺口清单，
实施方式（是否补门禁脚本、是否先做 `dataContract` 实例化）尚有未成形的想法，留待后续再定，暂不进入执行准则。

### 10. 前沿性审计：承袭旧系统的设计，是否错过当代范式（2026-08-30 补充）

#### 10.1 问题与判据

**问题**：新系统报表实现全部承袭自 2008 年前后的旧系统（在其基础上重构、优化、扩展），
是否存在"用现代技术重做了一遍旧设计"的风险——即错过了 2020 年代形成的新范式。

**判据（关键）**：不按"新旧"判断，按**收敛度**判断。前沿技术分两类：

| | 特征 | 策略 |
|---|---|---|
| **已收敛** | 有稳定标准、多家实现、替换成本极高 | **押注**——可直接作为长期地基 |
| **仍在发散** | 无统一标准、厂商各自为政、胜负未定 | **隔离**——通过接口接入，保持可替换 |

追逐"最新"反而危险：发散期的技术若直接写进数据模型，两年后就是新的技术债。
真正保证 5–10 年不过时的，是把已收敛的东西做扎实，把发散的东西挡在接口之外。

#### 10.2 缺口 A（最严重）：度量口径没有单一定义，阻碍 Agent 消费

**现状审计**。EOS 中同一个业务概念（如"销售额""未发数量"）的口径散落在至少五处：

| 承载 | 位置 | 性质 |
|---|---|---|
| 报表取数 | `REPORT.MASTER_TABLE` / `REPORT.SpName` | 报表级，各写各的 |
| 用户自定义 SQL | `LISTREPORT.T_SQL` | 运行时可改，无 review |
| 条件 DSL | `SYSQR_DEFAULT.F_TYPE` / `F_EXPR` | 专用编译器 |
| 字段元数据 | `FIELDS` | 只描述列，不描述度量 |
| 数据过滤 | `SYSDD_REPORT.DATA_FILTER` | 挂在权限行上 |

**没有任何一处定义"销售额 = 什么"。** 这正是当代语义层要解决的核心问题。

**外部证据（2026）**：

- 查询准确率随治理层级递进：直接查原始表准确率低；加 data catalog 定义 → **40–70%**；
  加语义层（vetted metrics + governance policies）→ **70–90%**；再加 tribal knowledge → 90–99%。
- Gartner 已在 **2025 Hype Cycle for BI and Analytics 中将语义层提升为 essential
  infrastructure**（不再是可选中间件）。
- **Open Semantic Interchange (OSI)** 规范于 **2026 年 1 月定稿**，成为厂商中立的
  语义定义交换标准。
- Gartner 预测 **>40% 的 agentic AI 项目将在 2027 年底前被放弃**；MIT NANDA 测得
  ~95% 生成式 AI 试点无可衡量 P&L 影响。行业复盘的共同结论是：
  **"语义层是分离成功 AI 部署与失败部署的主要干预手段——不是模型选择，不是提示工程，
  也不是基础设施优化。"**
- Microsoft Azure Data 总裁 Arun Ulag：
  *"Most data estates were designed for reporting, transactions, and human
  decision-making, not for continuous reasoning or autonomous systems operating
  inside the business."*——EOS 当前的数据模型是这句话的标准反例。
- Gartner：**到 2026 年底 40% 的企业应用将集成 task-specific AI agents**。

**对 EOS 的特殊性**：EOS 的定位是 AI-native Enterprise OS，ADR-007 已将模型推理内聚在
`EOS.API/features/assistant`。这意味着报表未来**不只是给人看，还要被 Agent 消费**。
按 §1 的分层 `Report(参数, 用户) → 行集`，Agent 本应是行集的天然消费者——
但前提是行集背后的口径是机器可读的、唯一的。

**决策**：

1. **不引入 Cube / dbt 等外部语义层产品。** 理由：EOS 是单系统 + 单库，引入独立查询代理
   属运维负担且收益不匹配；且 MetricFlow 虽以 Apache-2.0 开源，**其 serving 层无自托管
   端点**（须经 dbt Cloud 商业 API），与 EOS 自持部署的目标冲突。
2. **但必须内化语义层的原则**：度量口径**定义一次、机器可读、多处消费**。
   本 ADR §1 已确立"汇总口径属开发态"，本节补上其对偶要求——**开发态的口径必须是
   结构化、可枚举、可被引用的定义，而不是散落在 SQL 文本里的表达式**。
3. 落地为 **P7**（见执行准则），形态为库内的最小度量定义表 + API 暴露，**不自建查询引擎**。

> **自我修正**：本节推翻调研文档 `docs/plans/报表架构调研与收敛建议.md` 中
> "不建议引入 dbt/Cube/LookML（在单系统 ERP 上是新一轮过度工程）"的结论。
> 该判断的前提是"报表只被人消费"；当 Agent 消费成为一等公民后，语义层从可选中间件
> 变为必要基础设施。**落地形式不变（仍不引入外部产品），改变的是必须自己实现最小语义层。**

#### 10.3 缺口 B：渲染器选型与 L3 的结构性冲突

**决策（2026-08-30 用户拍板）：渲染器定案为 QuestPDF，放弃 Typst。**

旧论断曾认为 QuestPDF 是 C# Fluent API、编译期绑定，"结构上无法满足 L3 客户自行定义版式"。
**本轮推翻该论断**：QuestPDF 是命令式绘图库，但**可以被声明式描述驱动**——写一个
`QuestPdfLayoutRenderer` 解释层读取 JSON 布局描述、逐元素调用 QuestPDF API，即可承载客户
可视化设计（§9.7.1 定案）。L3 以「可视化设计器 + JSON 布局 + QuestPDF 解释层」交付。

**为什么放弃 Typst（原首选候选，评估记录）**：

| 维度 | Typst 的考量 | 定案判断 |
|---|---|---|
| 与 C# 技术栈契合 | Rust 引擎、外部运行时 | **不契合**，引入第二个运行时（强否决项） |
| 客户体验 | 需学 `.typ` 标记语言 | 可视化设计器零学习成本更优 |
| 模板代码化 | 纯文本可 Git diff/review | JSON 布局虽难 diff，但可快照对拍补偿 |
| 开源 | Apache-2.0 开源 | QuestPDF 亦开源（MIT），无差异 |
| 现有资产 | — | **QuestPDF 24 张内置版式统一迁移为 `layout.json`**（ADR-010 决策 6，迁移 + 对拍后 C# 命令式版式退役；不再"零重写"） |

**Typst 评估记录**（供未来若重新评估参考，均为 2026 年现状）：Apache-2.0、Rust 二进制
<50 MB、纯文本 `.typ` 可 Git 版本化、JSON 注入数据契约、渲染 <100 ms、内容寻址模板注册表、
从 Crystal Reports 迁移先例；局限为生态小于 LaTeX、仅输出 PDF、复杂版式需写脚本。

**HTML + CSS Paged Media 候选**：复用 Web 技能栈与前端资产，但依赖浏览器引擎、内存与
启动开销高，且与 C# 契合度同样不如 QuestPDF——**不在本 ADR 内定案**，仅记录。

#### 10.4 缺口 C：输出形态仍停留在"人去找报表"

2026 年的趋势是仪表板从**默认界面**降级为**可选输出之一**，洞察被推送到决策发生的
工作流中（chat、表格、嵌入式应用、告警）。四波演进为：
Wave 1 专家定制报告 → Wave 2 自助仪表板 → Wave 3 headless/嵌入式分析 →
Wave 4（2024–2026+）对话式与 agentic 分析。
（旁证：Microsoft 已宣布 Power BI 于 2026 年 12 月退役 legacy Q&A，转向 Copilot。）

ADR-009 §7 的报表中心本质仍是 **Wave 2 范式**——人去一个地方找报表。

**决策：不在本期改造。** 但 §1 的 `Report(参数, 用户) → 行集` 分层已经为 Wave 4
留出了接口——同一份行集可以同时喂给 PDF、屏幕表格与 Agent，无需重做取数层。
这正是"押注已收敛分层、隔离发散形态"的具体体现。

#### 10.5 未来 5–10 年不过时的押注清单

| 押注（写进数据模型，长期不动） | 理由 |
|---|---|
| SQL 作为取数原语 | 40+ 年未有替代者，所有语义层最终都编译成 SQL |
| **代码化 + Git 版本化**的资产 | 报表、模板、度量定义全部可 diff / review / 回滚 |
| **声明式数据契约**（JSON / 白名单字段） | 消费方与提供方解耦，模板改版不影响取数 |
| 开发态 / 运行时的分层（§1） | 与具体技术栈无关 |
| 权限求值在数据层而非报表层（§2） | 与具体权限产品无关 |

| 隔离（走接口，可替换） | 理由 |
|---|---|
| 可视化设计器组件 / 布局渲染器实现 | 已由 ADR-010 定案自建（2026-08-31），仍由 §5 的 Layout 抽象 + §9.7.1 的 QuestPdfLayoutRenderer 接口隔离 |
| Agent 框架与 LLM 型号 | 已在 ADR-007 `IChatModel` 后隔离 |
| 调度 / 订阅机制（§8） | 未立项，无标准 |

**不押注**：任何需要把业务语义写进二进制文件、专有 DSL 或单一厂商格式的方案——
包括旧系统的 `.rpt`、以及"把复制模板作为主路径"的等价物（见替代方案 F）。
**QuestPDF 已定案为统一渲染引擎**（2026-08-30），不再作为可替换项押注。

#### 10.6 复审触发

- 若 OSI 规范在两年内被主流 ERP 采纳为事实标准 → 评估 P7 的度量定义表是否对齐 OSI 交换格式；
- 若 Agent 消费报表的实际需求落地（ADR-007 助手进入业务查询场景）→ P7 由"可选"升为"必须"。
- ~~若 Typst 或同类解释型模板成为行业标准 → 启动 L3 选型 ADR~~ **已随 2026-08-30 渲染器定案废除**：
  渲染器确定为 QuestPDF + 可视化设计器（§9.7.1），不再评估 Typst 引入。

### 11. 五个管理页（2201–2205）的去留评估（2026-08-30 补充）

#### 11.1 问题

在「全新报表系统」方向下（标准默认版式 + 客户 copy-on-write 定制 + QuestPDF 统一渲染引擎 +
可视化设计器，见 §9/§10），旧报表管理模型的五个管理页——2201 报表排序汇总设置、2202 页眉设置、
2203 页尾设置、2204 表尾设置、2205 报表过滤条件设置——是否需要保留？

### 12. 报表格式定义：统一格式包模型（2026-08-30 补充）

#### 12.1 问题

在「全新报表系统」方向下，报表分为两类入口：

- **列表明细型** → 报表中心（用户选报表、填参数、看结果）
- **单据打印型** → 统一表单工具栏（用户编辑单据、点打印）

两者都要定义"格式"，但若各走各的路，就会回到旧系统 15 张表的老路上去。
本节用一套统一的**格式包（Format Package）**模型承载两类报表，从根本上消灭格式定义的碎片化。

#### 12.2 格式包 = 一份格式的完整定义

无论列表明细还是单据打印，每份格式就是文件系统中的一个目录：

```
report-formats/
  {formatId}/
    format.json     # 格式定义（开发态，进 Git）
    layout.json     # 布局描述（QuestPDF 解释层消费，开发态编辑，客户可 copy-on-write）
    sample.json     # 对拍样例数据（回归护栏）
```

**每单据类型一份独立默认布局**：`COP_SEND_PRINT/layout.json` 定义送货单独有的抬头
（收货方/地址/电话）和明细（品名/数量/单位）；`PUR_ORDER_PRINT/layout.json` 定义采购单
特有的抬头（供应商/采购日期/付款方式）和明细（品名/数量/单价/金额/税率）。
L0/L1/L2 内置版式由设计器直接产出 `layout.json`（**唯一真源**，ADR-010 决策 6）；
存量 24 张 C# 命令式版式是**迁移来源 + 对拍基线**，S1 逐张迁移、对拍通过后退役，
不保留 C# 直连渲染路径。`_base/` 目录不再需要。

> $\S1$ 分层原则在此落地：**数据源/汇总口径/版式 = 开发态资产，对拍样例 = 回归护栏**。
> 客户 copy-on-write 时复制 `{formatId}` 整个目录为 `{formatId}_{userId}`，**不修改原始资产**。

`format.json` 统一模型：

```json
{
  "formatId": "COP_SEND_PRINT",
  "kind": "list | document",
  "title": "送货单",
  "moduleId": 1403,

  "dataContract": {
    "columns": [
      { "key": "CLIENT_NAME",  "label": "客户名称",  "type": "string",  "width": 200 },
      { "key": "ORDER_DATE",   "label": "订单日期",  "type": "date",    "width": 120 },
      { "key": "AMOUNT",       "label": "金额",       "type": "decimal", "width": 100 }
    ],
    "detailTable": "COP_SEND_D",
    "detailColumns": [ ... ]
  },

  "params": [
    { "name": "DATE_FROM", "field": "ORDER_DATE", "operator": "GE", "label": "日期从" },
    { "name": "CLIENT_ID", "field": "CLIENT_ID",  "operator": "EQ", "label": "客户" }
  ],

  "grouping": [
    { "field": "CLIENT_ID", "sort": "ASC", "aggregate": "SUM" }
  ],

  "bindings": [
    { "docType": "1403", "clientId": null }
  ]
}
```

所有字段名、列名、表名、运算符均为受控白名单（§9.6 约束 3），`format.json` 由开发者维护，
进 Git 版本化，经 code review 后发布 —— 不再有"运行时写 SQL"的入口。

#### 12.3 两类格式的差异

| 维度 | 列表明细型（list） | 单据打印型（document） |
|---|---|---|
| 数据源 | `dataContract.columns` 定义列集，行集来自 `MASTER_TABLE` 或 SP 参数化查询 | `dataContract.columns` + `detailColumns`，行集来自 `PrintService.PrintData` |
| 参数 | 有（用户填筛选条件，存 SYSQR_USER） | 无（单据本身就是"参数"） |
| 排序/分组/汇总 | 有（`grouping` 数组） | 无（单据不需要） |
| 绑定 | 不绑定单据类型，按报表搜索/收藏展示 | 绑定 `(docType, clientId)`，由 PrintService 按 `R_M_IDX` 和 `IS_DEFAULT` 匹配 |
| 入口 | 报表中心（`/reports/:moduleId`） | 统一表单工具栏 print 动作 |
| 输出 | 屏幕表格 / PDF / Excel | PDF（仅打印） |
| 模板 `layout.json` | 负责页眉/页脚/页号/分组标题 | 负责抬头/明细行/表尾/签字/单价显隐 |

**共同点**：`format.json` 结构相同、`layout.json` 由统一 `QuestPdfLayoutRenderer` 解释
（§9.7.1）、安全边界相同（§9.6 三条约束）、数据契约始终走服务端字段白名单。

#### 12.4 格式包的生命周期

**开发态**（开发者，进 Git）：

1. 创建 `format.json`（定义数据契约、参数、排序/分组、绑定）
2. 用可视化设计器产出 `layout.json`（唯一真源；存量 C# 版式逐张迁移 + 对拍后退役，见 ADR-010 决策 6）
3. 编写 `sample.json`（对拍样例数据，供 CI 回归）
4. 提交 PR → code review → merge → 随 DbUp 迁移或部署脚本落地

**运行态**（系统，不进 Git）：

1. 加载 `format.json` 声明，按 `kind` 分发给报表中心或 PrintService
2. 取行集：列表明细型走 ReportRepository 参数化查询，单据打印型走 `PrintService.PrintData`
3. 渲染：`QuestPdfLayoutRenderer.Render(layout.json, { data, params, user })` → PDF
   （内置与客户定制**统一走解释层**，ADR-010 决策 6；类型安全由 schema 校验 + 字段白名单替代）
4. SYSQR_USER 用户参数记忆（列表明细型）和 SYSQR 打印偏好记忆（单据打印型）保留不变

**客户定制**（客户，通过报表中心 UI）：

1. 客户在报表中心找到某格式 → 点击"自定义"
2. 系统做 `copy-on-write`：复制 `{formatId}/` 整个目录为 `{formatId}_{userId}/`
   （含 `format.json` 与 `layout.json` 副本，**不修改原始资产**），
   `format.json` 的 `bindings` 中追加一行 `{ userId, docType, clientId }`
3. 客户在**可视化设计器**中修改布局（字段显隐、抬头文字、LOGO、位置样式），
   **不修改 dataContract 和 params**（数据契约和参数定义是开发态，不可由客户改）
4. 保存 → 新布局生效，下次运行时按 `bindings` 优先级匹配

#### 12.5 对现有机制的继承

- **列表明细型的屏幕表格渲染**：复用现有 `ReportViewerPage`，`format.json` 的 `columns` 定义
  直接喂给表格组件（与现有 `FIELDS` 元数据驱动同构）；
- **单据打印型的抬头取值**：沿用 §9.4.2 的优先级链 `SYSQR/本次选择` → `CLIENT.HEADER_ID` →
  `REPORT.HEADER_ID`（2026-08-31 定序用户优先；`REPORT_HEADER` 下线前将 5 行抬头定义迁移为模板资产）；
- **参数记忆**：`SYSQR_USER` 保留（用户填值）+ `SYSQR` 保留（打印偏好），两者运行态不变，
  只是参数定义从 `SYSQR_DEFAULT.F_TYPE/EXPR` 迁入 `format.json.params`。

#### 12.6 对执行准则的影响

- P3 存储收敛：改为格式包目录结构落地，`REPORT_HEADER`/`FOOTER`/`TAIL`/`IMAGE` 四表数据
  迁移为 `format.json` + `layout.json` 模板资产，不再单独保留版式管理页；
- P4 条件结构化：`SYSQR_DEFAULT` 的 DSL 条件迁移为 `format.json.params` 数组，
  `SYSQR_USER` 用户填值迁移到新参数运行时，`SYSQR_DEFAULT`/`SYSQR_DA` 下线；
- P6 单据套打：标准默认版式 = `layout.json`（唯一真源）+ `format.json`，C# 版式仅作迁移来源（ADR-010 决策 6），
  copy-on-write 定制 = 客户通过报表中心可视化设计器编辑布局；
- 迁移编号自 **025** 起（格式包目录结构落地 + 存量格式逐个迁移）。

### 13. P1 前置专项评审：`DATA_FILTER` 求值层定位（2026-08-30）

> 本评审是 P1 的**硬前置**（ADR 成本与风险 + 开发 Agent 评审意见 §1 均登记）：P1 的退出条件
> 是"权限行为等价"，而求值层位置未定，等价性无从验证。本节基于现有代码盘点锁定求值位置，
> 评审结论即 P1 实施基准，实施中不得再摇摆。

#### 13.1 现有代码盘点（2026-08-30 实测）

| 层 | 位置 | 现状 |
|---|---|---|
| 受控解析器 | `DataFilterParser.cs` | **唯一**受控解析器（白名单字段/参数化/fail-closed），工作台与报表共用 |
| 工作台求值层 | `WorkbenchScopeFilter.cs` | **统一求值层**：列表/导出/详情/子表/打印/记录读取/选择器全部经它组合 模块 FILTER + DATA_FILTER + EXEC_TAG + 分组表达式，fail-closed 403 |
| 报表求值层 | `ReportRepository.ApplyControlledFilter`（:518） | **并行第二套**：仅 `QueryPdfAsync` 应用（moduleFilter/reportFilter/rightsDataFilter 三个），`QueryAsync`（屏幕列表）**未接 filter 参数** |
| 权限数据源 | `LegacyRightsRepository` / `RightsAdminRepository` | 读 `SYSDD`/`SYSDH` 的 `DATA_FILTER`；个人覆盖组、组 OR 已组合为生效值 |
| 报表权限物化 | `DomainRuleService.cs:508-518` | `SYSDD_REPORT` 物化展开（P1 删除对象） |

**两个事实**：① 解析能力已收敛到 `DataFilterParser` 一处；② 求值入口存在**两套并行**（工作台 `WorkbenchScopeFilter` vs 报表 `ApplyControlledFilter`），且报表屏幕查询的 DATA_FILTER 应用现状**待核实**。

#### 13.2 候选方案对比

| 方案 | 做法 | 评估 |
|---|---|---|
| **A. 统一数据访问层（C# 受控组件）** | 报表路径并入 `WorkbenchScopeFilter` 同模式：SQL 构建期把 `DATA_FILTER` 解析为参数化谓词拼进 WHERE，共享 `DataFilterParser` | ✅ **采纳**。与 ADR-005 已确立方向一致；覆盖动态表名/SP 之外全部路径；每用户每模块不同过滤天然支持；只差把报表路径统一进来 |
| B. 语义视图（SQL 视图内嵌过滤） | 在库内建视图固化过滤逻辑 | ❌ 否决。`DATA_FILTER` 是**每用户每模块动态表达式**，无法静态固化进视图；动态标识符白名单 + 参数化在视图层不可行；SP 路径覆盖不到 |
| C. 查询拦截器（全局统一拦截） | 对所有数据访问统一拦截注入过滤 | ❌ 否决。覆盖不到直接 `SqlCommand` 与 SP 内部；改造面远超收益；与现有"组件显式调用"架构相悖 |

#### 13.3 评审结论：求值位置 = 统一数据访问层（C# 受控组件）

- **求值层**：SQL 构建期的受控组件（`WorkbenchScopeFilter` 同模式），把 DATA_FILTER 白名单解析为参数化谓词注入 WHERE；**不采用**语义视图或拦截器。
- **执行要求**：报表路径（`ReportRepository`）的 `ApplyControlledFilter` 与工作台路径统一到**同一组件**，消灭并行第二套；屏幕查询 `QueryAsync` 补接 filter 参数并应用 DATA_FILTER（现状缺失项，P1 核实后修复）。
- **组合语义**：override 报表 `DATA_FILTER` 与数据层模块级过滤器取**交集（AND 收紧）**，写死为"追加收紧"，杜绝"换取数路径绕过"（评审意见 §3 确认）。
- **作用顺序**（P1 落地时固定）：`模块 FILTER ∧ 用户 DATA_FILTER ∧ 报表 REPORT_FILTER ∧ override DATA_FILTER ∧ EXEC_TAG`。
- **SP 报表路径**：`RunSpAsync` 不经过字段过滤（ADR 已登记复审条件），随 P2/P3 一并收口为"SP 结果集列名与 `FIELDS` 元数据取交集白名单（fail-closed）"，本轮 P1 不做。

#### 13.4 待核实项（P1 动工后第一件事，登记复审）

1. 报表屏幕查询（`QueryAsync` 全链路）当前是否以及如何应用 `DATA_FILTER` —— 若缺失，P1 补齐；
2. `ReportRepository` 三条 filter 来源（moduleFilter/reportFilter/rightsDataFilter）逐一确认各自语义，统一到同一组件后行为等价性对拍基准。

## 选择理由

- **复杂度在数据模型，不在代码**：4174 行代码能跑，先动模型、代码跟着瘦；不做一次性重写。
- **第二套权限是第一套的物化展开**，不是独立语义——保留它等于为一个 bit 维护 10 万行，
  且新报表存在权限空档。收成 override 表后语义更清晰、行数降三个数量级。
- **`DATA_FILTER` 挂在报表上会随报表数量线性重配**，且换个取数路径就能绕过；挂在数据层
  （Odoo `ir.rule` / SAP DCL 的共识做法）才对报表、单据、Agent 一致生效。
- **SQL 是开发态资产**：进源码、进包、可 review、可版本化。存成数据库里一行 `VARCHAR(4000)`
  就失去了以上全部——这是所有主流产品的共识，没有例外。
- **22 个节点落到同一个页面**，证明"按业务域铺节点"没有带来任何差异化价值，只是把目录职责
  外包给了菜单树。
- **无存量客户 = 唯一合法窗口期**：错过再改，存量搬移与双轨兼容成本指数上升。

## 考虑过的替代方案

### A：保留两套权限，只把 `SYSDD_REPORT` 生成时机改准

优点：改动最小。未选择原因：10 万行维护成本、新报表权限空档、`DATA_FILTER` 逐报表重配
三个问题原样保留，治标不治本。

### B：删掉 `SYSDD_REPORT`，全部收归 `SYSDD.REPORT_TAG`

优点：最干净。未选择原因：**丢掉了"逐报表收紧"的能力**——现实中存在"某人能看模块的 A 报表
但不能看 B 报表"的需求。保留 override 表是"默认全开 + 例外收紧"，两者都满足，且行数降到个位数。

### C：引入 dbt / Cube / LookML 做独立语义层

优点：度量口径集中定义，BI 与 Agent 友好。**未选择（作为产品引入）**，原因：

1. 这些工具解决的是"数仓 + 多 BI 工具"的 headless BI 场景；EOS 是单系统 + 单库，
   引入独立查询代理属**运维负担且收益不匹配**；
2. MetricFlow 虽以 Apache-2.0 开源，但**其 serving 层无自托管端点**（须经 dbt Cloud 商业 API），
   与 EOS 自持部署的目标冲突。

> **重要澄清（2026-08-30，§10.2 修正）**：否决的是**产品**，不是**语义层本身**。
> 在 Agent 成为报表消费者之后，度量口径的单一定义从"可选中间件"变为"必要基础设施"——
> 因此本 ADR 另行立项 **P7 最小语义层**：不引入外部产品、不自建查询引擎，
> 以库内度量定义表 + API 暴露的方式内化同一职责。

### D：22 个节点保留，只在报表中心加个聚合入口

未选择原因：聚合入口与分散节点并存 = 双份真相，用户不知道该从哪进；且菜单树继续随报表数量膨胀。
要么分散要么集中，选集中。

### E：`REPORT_PATH` 保留废弃 vs 物理删除

**物理删除**。新系统渲染已完全改走 QuestPDF，该列零读取点；保留会在 SSDT 快照、schema 审阅中
留下长期噪音，与"彻底重构"相悖。"有迹可查"由本 ADR + DbUp 迁移历史 + git 承担。

### F：给客户一个在线模板设计器（WYSIWYG 拖拽）

**否决"用设计器消化 62 份存量"**，至少不在本期。理由不是做不了，而是**它解决的是错误的问题**：

- §9.1 实证：62 份送货单中 84% 的体积差异 <4%，差异来自**抬头数据**而非版式；
- §9.2 实证：客户级抬头/单价配置（`CLIENT.HEADER_ID`、`PRINT_PRICE`、`DELI_ADDR`）
  **本来就存在**，只是渲染路径没消费。给设计器不会让这些配置生效，只会把"复制 62 份模板"
  从开发商侧搬到客户侧——**客户照样要维护 62 份**，且从此无法回归对拍；
- 设计器会引入 §9.6 的全部沙箱成本，而 L1/L2 不引入。

> **2026-08-30 澄清（用户"做标准 ERP 产品"定位 + 渲染器定案 QuestPDF）**：否决的是
> **"用设计器消化 62 份存量"**（§9.7 表格左列），**不等于**否决设计器作为 L3 产品能力
> （表格右列）。渲染器定案 QuestPDF 后，L3 已确定为「**可视化设计器 + QuestPDF 解释层**」
> （§9.7.1）——因为它是唯一既满足"客户自助版式"、又与 C# 技术栈契合的方案。
> 本节仍成立的部分：L3 不在本期、需沙箱与字段白名单（§9.6）、参照 NetSuite。

现代产品里最接近的是 **NetSuite Advanced PDF/HTML Templates**（客户可直接编辑 HTML +
FreeMarker），能力最强，但代价是模板层必须承担字段暴露风险与沙箱治理
（"A template can expose sensitive fields even when the transaction form does not visibly
display them elsewhere"）。**L3 立项时 NetSuite 是参照对象；设计器是本 ADR 选定的实现形态
（§9.7.1），不再是"选项之一"。**

## 结果与影响

### 正面影响

- 报表权限从"两套并行 + 10 万行物化"收敛为"一个真源 + 个位数 override 行"；新增报表零补行；
- 行级过滤下沉后，报表 / 单据列表 / Agent 走同一个过滤器，不再随报表数量线性重配、不再被绕过；
- 入口从 22 个菜单节点收敛为 1 个报表中心，菜单树停止随报表数量膨胀；
- 布局四表合一、死列清理，报表定义从 15 张表降到个位数；
- 条件定义消灭专用 DSL，复用 ADR-008 编译器与校验器，保存即校验、运行期零解析失败；
- 单据套打（`PrintService` 默认报表选取机制不动）补齐渲染环节，并首次让 `CLIENT` 上
  沉睡的抬头/单价配置真正生效——**页头 = 开单方主体（页头字典引用），`CLIENT.HEADER_ID`
  选择每个客户默认用哪个开单方页头，客户名/地址属正文**——62 份送货单有希望收敛为
  1 份模板 + N 条主档记录（§9）；
- **五个报表管理页（2201–2205）下线**（§11）：报表定义/版式/条件全部迁往开发态资产，
  运行时不再维护五套配置表，管理面从"5 个页面 + 15 张表"收敛为「报表中心 + 模板资产 + 绑定」。

### 成本与风险

- **`DATA_FILTER` 求值位置未定**：影响面跨越报表/单据/Agent，P1 实施时确定并登记复审；
  定错位置会导致过滤器被绕过或性能退化。
- **22 个节点撤销后，`MODULES` 上的 `M_IDX` 权限单元仍在**：节点没了但 `SYSDD` 里
  `M_IDX` 对应的权限行还在，需随 P2 一并迁移/清理（登记为待决策）。**实际口径（2026-09-19 回填）：
  保留 `M_IDX`、不动 `SYSDD`/`SYSDH` 权限行**——迁移 `023_report_center_menu_converge.sql` 只把 XX98 目录
  与其 `/reports` 叶子置 `M_TAG=0` 隐藏（`REMARK` 注明“仅保留权限单元”），脚本头注释写明
  “MODULES keeps M_IDX permission units for SYSDD/SYSDH permission rows to remain valid … SYSDD/SYSDH permission rows are untouched”。
  本句“迁移/清理”与迁移 023 实际口径冲突，以迁移 023 为准。
- **P4 会推翻刚落地的 2205 定制页成果**（2026-08-28 完成，见 `docs/status.md` §3）：该页维护的
  正是 `SYSQR_DEFAULT.F_TYPE` / `F_EXPR`，且写侧校验镜像了报表运行时的 DSL 解析
  （`ReportConditionsValidator`）。P4 结构化改造后这套校验要重写为消费 `FILTER_TEMPLATE`；
  **§11 已裁定 2205 管理页随 P4 一并下线**（不再保留为运行时管理能力，成果作为开发态定义参考），
  该页校验逻辑随之退役，不再有"在未稳定成果上叠加改造"的问题。
- **P4 条件定义同时服务 22 个报表模块**：`SYSQR_DEFAULT` 是按 `M_IDX` 维护的，改造影响面覆盖全部
  报表模块的条件面板；需等价对拍，不能只验几个模块。
- **P3 存量审计结果不可预知**：`SYSQD` / `SYSQL` / `LISTREPORT` 三表的真实使用率未知，
  若存量 SQL 大量在用，转受控视图的工作量会显著上升；审计先行，不做乐观假设。
- **P4 条件转换可能遇脏数据**：仿 ADR-008 经验，预计存在一定比例不可自动转换的条件，
  需人工清单（ADR-008 实测第三档约 4%）。
- **SP 报表路径不做字段级权限过滤**：动态表报表（`MASTER_TABLE` 非空）的列在数据层就按
  `deniedFields` / `IS_COST` / `IS_SECRECY` 过滤（`ReportRepository.ReadColumnsAsync`），
  无权限字段不进结果集；但 `masterTable` 为空的 SP 报表（`P_RPT_*`）列由 SP 结果集动态提供
  （`ReportRepository.cs:301-302`、`:310`），**不经过任何字段过滤**——SP 返回什么列就展示什么列。
  建议随 P2 报表中心或 P3 存储收敛一并收口：SP 结果集列名与 `FIELDS` 元数据取交集白名单
  （fail-closed），否则"中心化"会把这个绕过列权限的缺口一并放大。
- **（2026-09-19 复核）以上缺口仍未收口**：`ReportRepository.RunSpAsync`
  （`EOS.API/Data/ReportRepository.cs:301-341`）执行 SP 后逐列读取结果集（`:327-328`）直接落行，
  未与 `FIELDS` 元数据取交集做列白名单 fail-closed；同文件 `:69` 注释亦写明“SP 报表……列由结果集动态提供”。
  结论：**尚未做**，与上方建议一致，仍待 P2/P3 收口。
- **代码侧 6 处 API + 4 处前端 + 测试同步改造**，需分阶段独立回归。
- **五个管理页（2201–2205）下线是推翻已验收成果**（§11）：五页 2026-08-28 全部验收上线，
  下线动作须用户明确拍板（§11 即拍板）；下线后相关管理能力不再可用，属有意为之，
  须在 `docs/status.md` 与技术债登记同步收回，避免双重真相。
- **`REPORT_HEADER` 引用迁移**（§11 风险登记）：5 行抬头定义被 `CLIENT.HEADER_ID`（339 家）
  与 211 张报表引用，P3 下线前须将引用迁移为模板资产或 CLIENT 数据，不得直接删除造成引用悬空。
- **`CLIENT.PRINT_PRICE` 从未被消费过，其存量数据可信度未知**：该字段在旧系统仅存在于维护页
  （`Client.aspx:401`），渲染侧零引用，**存量值可能长期未维护**。P6 启用前需先审计取值分布，
  不能假设"配了就是对的"——否则会把陈旧配置变成新的打印行为。
- **P7 的真实成本在业务共识，不在建表**：度量定义的难点是让业务对"销售额 = 什么"达成一致
  并指定 owner，技术部分很小。若缺少口径归属与评审机制，P7 会退化成"又一张没人维护的配置表"，
  反而坐实"过度工程"的批评。因此 P7 的准入条件是**先有高频争议口径清单**（来自 P3 的 T_SQL 审计），
  再建表，而不是先建表再想填什么。

## 开发 Agent 评审意见（2026-08-29，附入正文备实施参考）

以下为开发 Agent 对本文档的复核意见，方向均认可，另提出五点实施关切与一条已知缺口（SP 报表
列权限缺口已补入上文"成本与风险"）。

1. **`DATA_FILTER` 求值位置未定，却是 P1 的退出条件之一**。ADR 将其登记为"P1 实施时确定"，但
   P1 的验收口径是"权限行为等价"——求值层位置未定，等价性拿什么验证？建议 P1 动工前先做一次专项
   "求值层位置"评审（Repository 基类 / 语义视图 / 拦截器三者各在什么场景成立，结合性能与防绕过），
   锁死后再写权限改造，而不是边做边定。

2. **"默认全开 + override 收紧"对新增敏感报表的暴露**。旧方案虽有空档（bug 而非特性），但空档期内
   新报表恰好不可见；新方案下新增报表**立即**对全部有 `REPORT_TAG` 的人可见。业务上合理，但缺少
   "草稿→发布"的可见性控制——管理员忘了 override，新敏感报表直接全开。可考虑报表定义加一个发布
   可见性开关（可选增强，不阻塞主体）。

3. **override 表里 `DATA_FILTER` 的组合语义未明确**。ADR 说它"P1 后只作为 override 语义"，但没说
   它与下沉到数据层的模块级过滤器是**交集还是覆盖**。若覆盖，又会回到"换取数路径绕过"的老问题；
   应写死为"在数据层过滤器基础上追加收紧（取交集）"，写入 P1 复审登记。

4. **P5 是新增功能不是重构**。P1–P4 是收敛（删/并/沉），P5 调度订阅 + Report Inbox 是 N2 增强。
   把它塞进重构 ADR 会模糊验收边界、且新功能可能拖累重构主体。建议 P5 独立成计划，或明确标注为
   增强阶段、单独验收。

5. **P4 对拍工作量可能被低估**。条件 DSL 与 ADR-008 选择器过滤本质不同（前者是用户填值的参数、
   有 `{p.X}` 占位符，后者是固定条件），编译器不能完全复用；且覆盖 22 个模块的条件面板，等价对拍
   是体力活。ADR 已识别并列入退出条件，但实施时要有心理预期并预留人力。
