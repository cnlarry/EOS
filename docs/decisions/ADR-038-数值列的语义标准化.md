# ADR-038：数值列的语义标准化——类型族、语义登记与分批迁移

- 状态：**已接受并实施完成（2026-10-17）**——九项决定见第 2 节，类型族见第 3 节，语义登记见第 4 节，分批实施与遗留项见第 5 节，拍板结论见第 9 节
- 日期：2026-10-17
- 决策者：用户（Larry）+ 开发 Agent
- 前置关系：**本 ADR 是 ADR-037 的前置**。ADR-037 的"金额精度跟货币、数量精度跟单位"建立在"存储能表达小数位"之上；本 ADR 负责把这个前提做实。在本 ADR 批 A 完成前，ADR-037 的批 0 只做写入边界舍入
- 相关：ADR-004（数据库受控迁移与安全切换）、ADR-017（系统参数纵向化）、ADR-036（共享原语单一真源）、`LESSONS.md` L83（快照静默落后）

> 大白话：库里有 **2074 个 `float` 列**在存金额、数量、单价、汇率，而 `float` 没有"小数位"这个概念——
> 所以"金额保留两位"这件事目前**没有地方落地**。本 ADR 把这些列按语义分成五族、每族定一种标准类型，
> 再用两道门禁保证"新列不能写错、存量逐批清干净"。
>
> 关键取舍：**存储给最宽的，计算按语义收窄**。金额存 4 位小数不是因为要显示 4 位，
> 而是因为科威特第纳尔有 3 位、智利 UF 有 4 位；美元单据实际值后两位恒为 0。

## 1. 问题与证据

### 1.1 `float` 承载业务数值，精度校验形同虚设

| 统计项 | 实测值 | 口径 |
|---|---|---|
| `[float]` 列 | **2074** | 解析 `db/bootstrap/10_schema.sql` 的 497 张表 |
| `[decimal]` 列 | **3** | 全部在 `ACC_ACCOUNT`（助手成本核算，新表） |
| `[numeric]` / `[money]` 列 | 0 / 0 | — |
| 含 `float` 列的表 | **267** | — |
| `FIELDS` 中 `F_TYPE = N'float'` 的字段行 | **2258** | 比物理列多 184，说明有字段登记为 float 但物理列不存在（虚拟字段或历史残留），**迁移时不能直接按 `F_TYPE` 批量 UPDATE** |
| 迁移脚本新增 `float` 列 | **0**（356 个迁移中） | 3 个 `decimal` 迁移全在助手域（`291`/`292`/`294`） |

后果写在现有代码注释里：

```82:97:EOS.API/Data/RecordPayloadValidator.cs
/// 仅 decimal/numeric 启用——float 无精度语义、money 固定 scale=4，均不适用。
...
        var type = field.DataType.Trim().ToLowerInvariant();
        if (!type.Contains("decimal") && !type.Contains("numeric"))
        {
            return null;
        }
```

即 `SCALE_EXCEEDED` / `PRECISION_EXCEEDED` 这套前后端同源的校验，对上述列**全部不生效**。
`AGENTS.md` 写的"金额、数量精度以服务端为准"，当前的真实状态是**服务端没有精度约束**。

### 1.2 语义无法被机器识别

`float` 列共 **2075** 个（列名去重后 **703 个**）。按词根规则可归类 **73.6%**，剩余 **548 列（26.4%）**规则无法判定：

| 归类 | 列数 | 占比 |
|---|---:|---:|
| `QTY`（含尺寸/重量/工时/天数/里程） | 802 | 38.7% |
| `AMOUNT`（含 `_SUM`/`FEE`/`COST`） | 388 | 18.7% |
| `PERCENT` / `RATE` | 186 | 9.0% |
| `PRICE` | 151 | 7.3% |
| **`UNKNOWN`** | **548** | **26.4%** |

`UNKNOWN` 的构成正好暴露三类"不可判定"：

**A. 拼音缩写（无法从名字推断语义）**：`ZCLZ`、`SJCKJE`、`SJJKJE`、`SJJKZL`、`YHTCKZL`、`HTCE`、`HTYLZL`、`YFHTJGF`、`BHTYIKFP`、`SUTTLE` 等。

**B. 编号式列名（语义取决于所在表的业务）**：`RESULT1`–`RESULT9`、`GRADE_SUM0`–`GRADE_SUM9`、`SUBTRACT_SUM01`–`SUBTRACT_SUM11`、`ADD_SUM01`–`ADD_SUM15`、`ADD_HOUR12`、`OM_WIDTH1`–`OM_WIDTH5`、`PS_LENGTH2`、`AMERCE1`–`AMERCE5`。

**C. 类型错配**：`SUPPLIER.MIN_BUY_AMOUNT` 是「最小采购金额」——采购总额低于该值供应商不接单，
语义属 `AMOUNT` 族，物理却是 `int`；`WF_FUNCTION_INFO.serialno` 是序号却用 `float`。
（两者均已在收口时修正，见 §5.4。）

结论：**"强迫"不能只靠列名**。但"不能靠列名"不等于"要靠人"——`FIELDS.F_DESC` 里存着字段中文说明
（`SJCKJE`=实际出库金额、`ZCLZ`=折材料重、`SUTTLE`=单个净重），配合两条佐证：

- **同表佐证**：`QC_ANALYSIS_D` 已有 `BAD_QTY`/`GOOD_QTY`/`PRODUCE_QTY`，故 `RESULT1-9` 是缺陷分类计数；
  `QC_REWORK_M` 的 `AMERCE1-5` 依次为工时/人员/良品数/不良报废数/特采品；
- **同簇同质**：`HR_WAGE_D`/`HRM_WAGE_D` 的 `WAGE_ITEM*` 多为工资项，但其中 **40 列是工时/天数/分钟**
  （如 `WAGE_ITEM33`=请假天数、`WAGE_ITEM49`=早退分钟），并非金额。

按此二次判定，548 列中 **529 列可定**，真正需要人工确认的只有 **19 项（0.9%）**。

## 2. 决策

### 决定一（五个语义族，各有标准类型）

所有业务数值必须能归入下表之一；归不进去的登记 `UNKNOWN`，**不强制、不改类型**。

| 族 | `NUMERIC_ROLE` | 标准类型 | 语义 |
|---|---|---|---|
| 金额 | `AMOUNT` | `decimal(18,4)` | 货款、税额、费用、成本、合计 |
| 数量 | `QTY` | `decimal(18,6)` | 件数、重量、长度、面积、工时、天数 |
| 单价 | `PRICE` | `decimal(18,6)` | 单价、加工价、报价 |
| 汇率/系数 | `RATE` | `decimal(18,10)` | 汇率、换算率、单位系数 |
| 比率 | `PERCENT` | `decimal(9,6)` | 税率、折扣率、返利率、损耗率 |

### 决定二（存储宽于计算）

存储类型固定取"该族可能的**最宽**需求"，**不随货币或单位变化**：

- 金额 4 位小数：ISO 4217 中 minor unit 最大为 4（`CLF`、`UYW`）；`KWD`/`BHD`/`OMR` 为 3；
  `JPY`/`VND`/`KRW` 为 0。USD/EUR 单据存下的值后两位恒为 0。
- 实际参与计算与显示的小数位由 ADR-037 的货币/单位精度决定，**取窄的那一侧**；
- **禁止**按货币建不同精度的列（如"USD 金额列 `decimal(18,2)`、KWD 金额列 `decimal(18,3)`"）——
  同族必须同型，见决定三。

依据：SAP 的金额字段内部也是固定宽度 + 由 `TCURX` 决定实际小数位；D365 的货币 `Decimal places`
是显示/换算口径，不是存储宽度。

### 决定三（同族同型，禁止按表定制）

同一语义族在**全库只允许一个 `(p,s)`**。禁止"这张表 2 位、那张表 4 位"的现状式自由。

理由（不是洁癖）：

1. 跨表 `UNION`、`JOIN` 比较、合计会走隐式类型提升，精度语义在运行期漂移；
2. 两列都叫 `AMOUNT` 却不同型，维护者无法从名字判断，只能逐列查 `sys.columns`；
3. 门禁需要一条可判定的规则，多一档就多一条分支。

### 决定四（语义登记：`FIELDS` 加 `NUMERIC_ROLE`）

`FIELDS` 增一列：

| 列 | 类型 | 取值 |
|---|---|---|
| `NUMERIC_ROLE` | `nvarchar(16)` NULL | `AMOUNT` / `QTY` / `PRICE` / `RATE` / `PERCENT` / `UNKNOWN` / NULL（非数值字段） |

- `F_TYPE` 描述**物理类型**，`NUMERIC_ROLE` 描述**业务语义**，两者正交；
- 只有 `NUMERIC_ROLE` 已定的字段才受类型门禁约束；
- 非数值字段（文本/日期）为 NULL，不参与。

不另建独立表的理由：语义是字段的属性，与 `F_TYPE`/`DISPLAY_FORMAT` 同层；单开一张表会在
每次读字段元数据时多一次 join，而 `FIELDS` 已被 `WorkbenchDefinitionBuilder` 高频读取。

### 决定五（只对"已确认语义"强制）

- 能判定的（词根 73.6% + 元数据二次判定，合计 **99.1%**）→ 回填 `NUMERIC_ROLE`，纳入强制范围；
- 不能判定的（**19 项**）→ 保持 `float` 不动，列入待判定清单，逐条确认后再回填；
- `UNKNOWN` 不是"永远不管"，而是"未确认前不施加类型约束"——避免把 `RESULT3` 这种语义未知的列
  强行改成 `decimal` 后才发现它其实存的是编码。

这条是本文与"全量重构"的分界线：**能确定的多做，不能确定的先不动**。

### 决定六（新列命名规范）

新增业务数值列必须落在词根表内，否则视为未登记：

| 前缀/后缀 | 族 |
|---|---|
| `AMOUNT`、`_AMOUNT`、`TAX_SUM`、`_SUM`、`_FEE`、`_COST` | `AMOUNT` |
| `QTY`、`_QTY`、`WEIGHT`、`LENGTH`、`WIDTH`、`HEIGHT`、`AREA`、`_DAYS`、`_HOURS`、`_TIME` | `QTY` |
| `PRICE`、`_PRICE` | `PRICE` |
| `RATE`、`_RATE`（汇率/系数语境的，如 `CURR_RATE`、`BASE_RATE`） | `RATE` |
| `_PCT`、`_PERCENT`、`TAX_RATE`、`REBATE`（比率语境的） | `PERCENT` |

`RATE` 与 `PERCENT` 的歧义（`TAX_RATE` 是百分比、`CURR_RATE` 是汇率）由**登记值**裁决，**不由名字裁决**——名字只用于生成候选。

### 决定七（三层门禁，缺一层就退化成口头约定）

| 层 | 断言 | 失效方式 |
|---|---|---|
| 静态 | 迁移脚本中 `ADD [列名] [float]` 一律 FAIL；列名命中决定六且未用标准类型则 FAIL | CI 直接红 |
| 连库 | `FIELDS.NUMERIC_ROLE` 已定的字段，其物理列类型必须等于标准类型 | 跑门禁即红 |
| 元数据一致性 | `FIELDS.F_TYPE` 必须与 `sys.columns` 的实际类型一致（防 §1.1 那 184 行的漂移） | 跑门禁即红 |

静态门禁只能看到 SQL 文本，所以它靠**列名**判定；连库门禁用**登记值**判定。两者覆盖不同的漏网方式。

### 决定八（只改类型，不改值域）

本 ADR 不改变任何业务语义：

- 不引入单位换算、不做四舍五入策略（属 ADR-037）；
- 转换只做 `float → decimal(p,s)`，值的舍入由 SQL Server 的转换规则决定，**转换前后必须逐列对拍**
  （`SELECT COUNT(*) WHERE CAST(col AS decimal(p,s)) <> col`）；
- 不在本 ADR 更改任何列名；
- **数据服从模型，不是模型服从数据**：当某列出现远超该族整数位的值时，先判断它是不是录错的——
  明显录错的值直接修正（测试数据可归零），**不要为了迁就个别脏值而放宽整列精度**。
  只有"数据本身合法、只是量级确实超出"时才启用单列精度例外，并在迁移注释里写明理由。
  `PRODUCT.PRICE` 曾因一行 522 万亿的错值被放到 `decimal(28,6)`，随后按本原则收回标准类型（迁移 `386`）。

### 决定九（分批、可回滚，每批独立验收）

- 按业务域分四批（第 5 节），每批一个迁移脚本；
- 每批必须能独立回滚（`decimal → float` 可逆，但会在转换中丢失"原本就不精确"的低位——回滚脚本只恢复类型，不承诺恢复位模式）；
- 上一批验收未过，不进下一批。

## 3. 类型族定义与依据

| 族 | 类型 | 整数位 | 小数位 | 依据 |
|---|---|---:|---:|---|
| `AMOUNT` | `decimal(18,4)` | 14 | 4 | ISO 4217 minor unit 最大 4；14 位整数可容纳万亿级金额（`PUR_PURCHASE_M` 8729 张单据无压力） |
| `QTY` | `decimal(18,6)` | 12 | 6 | Odoo 数量精度上限 8 位、SAP 单位小数位 0–3（部分可到 6）；6 位覆盖毫克/微米级 |
| `PRICE` | `decimal(18,6)` | 12 | 6 | 单价必须高于金额精度，否则"单价 × 数量 ≠ 金额"；现行打印版式 `#,##0.######` 已是 6 位 |
| `RATE` | `decimal(18,10)` | 8 | 10 | 交叉汇率需高精度；SAP 有汇率被截断导致冲销金额差异的真实故障 |
| `PERCENT` | `decimal(9,6)` | 3 | 6 | 税率/折扣率 6 位足够；3 位整数容纳 100 以上（如 113% 的价税合计比率） |

`AMOUNT` 取 4 位而非 2 位的取舍：多 2 位小数会让每行多 1 字节存储，但**避免将来为支持 KWD 而二次改类型**。
按当前数据量（千级到万级行）代价可忽略。

## 4. 语义登记

### 4.1 回填流程

1. **规则生成候选**：按决定六的词根表，对 2075 个 `float` 列 + 2258 个 `F_TYPE='float'` 字段生成候选（覆盖 73.6%）；
2. **元数据二次判定**：对剩余 548 列用 `F_DESC` 中文说明 + 同表佐证 + 同簇同质推断（覆盖到 99.1%）；
3. **人工确认例外**：只剩 19 项（清单见 §4.2），逐条勾选后回填；
4. **落库**：迁移脚本写入 `FIELDS.NUMERIC_ROLE`，只写能 `JOIN sys.columns` 命中的字段
   （防止把 §1.1 那 184 行不存在物理列的登记一并改掉）；
5. **留痕**：盘点清单与脚本一并保留，供后来人复核判定依据。

**落地（2026-10-17）**：迁移 `357_field_numeric_role.sql`（`FIELDS` 加 `NUMERIC_ROLE` + 2075 条回填，按 400 条一批、每批带 `sys.columns` 存在性校验），`db/bootstrap/10_schema.sql` 同步加列。生成器 `scripts/oneshot/numeric-role-registry.ps1`，全量清单 `docs/plans/numeric-role-full.csv`。判定分布：`QTY` 976、`AMOUNT` 693、`PRICE` 151、`PERCENT` 141、`RATE` 107、`NON_NUMERIC` 7；来源分布：说明 1150、列名词根 612、簇 294、人工拍板 19。

| `QC_COMPLAIN_M` / `QC_EXCEPTION_M` | `AMERCE4` / `AMERCE5` | 其他 / 材料 | 金额 | 与同组"罚款""电费"并列，推断为费用项 |

| `HR_WAGE_D` / `HRM_WAGE_D` | `WAGE_ITEM37` / `WAGE_ITEM31` / `WAGE_ITEM36` | 有无加班费 / 有无全勤奖 | **非数值** | 布尔语义，应转 `bit` |
| `WF_FUNCTION_INFO` | `serialno` | 工作流项次 | **非数值** | 序号用浮点，已转 `smallint`（迁移 `403`） |

另有 1 项 `[serialno]` 原属"类型错误、待另案"，**已随收口处置**（迁移 `403`）。

`SUPPLIER.MIN_BUY_AMOUNT` 原也列在"待另案"，**已改判**：它是「最小采购金额」，属 `AMOUNT` 族。
迁移 `402` 已把它从 `int` 改为 `decimal(18,4)` 并登记 `NUMERIC_ROLE='AMOUNT'`——
`int → decimal` 不丢数据（存量全为 0），属可安全就地改的一类，不需要另案。

### 4.3 覆盖率目标

- 二次判定后全库真正无法自动归类的只剩 19 项（0.9%），可在批 A 前一次确认完；
- 未确认项保持 `float` 不动，不阻塞其它列迁移；
- **新列不允许产生未登记**：`NUMERIC_ROLE` 为空或为 `UNKNOWN` 的新增数值列，门禁直接红。

### 5.2 每批的固定动作（顺序不可调）

1. **范围扫描**（只读）：对每个待改列执行
   `SELECT MAX(ABS(CAST([col] AS decimal(38,10))))` 与 `SELECT COUNT(*) WHERE ABS([col]) >= 10^(p-s)`
   → 超范围列**单列处置**，不整表强改；
2. **先拆依赖，再改类型**：`ALTER COLUMN` 会被三类对象阻塞（错误 5074：对象依赖于列）——
   列的 `DEFAULT` 约束、**包含该列的索引（含 `INCLUDE` 列）**、引用该列的计算列。
   必须先 `DROP` 再重建。`DROP INDEX` 后按 `sys.index_columns` 的原顺序重建键列与 `INCLUDE` 列，
   注意**键列通常不是数值列**，不能只按"数值列"去筛一个索引的列清单，否则会重建出 `ON ... ()` 的空索引；
3. **迁移脚本**：`ALTER TABLE [dbo].[T] ALTER COLUMN [COL] decimal(p,s) NULL;`
   —— 幂等写法，先查 `sys.columns` 判断当前类型；
4. **`sp_refreshview`**：对本批涉及的视图逐个刷新；
5. **元数据同步**：同事务 `UPDATE FIELDS SET F_TYPE='decimal' WHERE T_ID=... AND F_ID=...`
   （必须按 `(T_ID, F_ID)` 精确写，不按 `F_TYPE='float'` 批量写）；
6. **快照重发布**：`precision`/`scale` 是定义快照的组成部分，旧快照会"静默落后"（`LESSONS.md` L83），
   必须重发布；
7. **验收**：`dotnet build` + **全量 `dotnet test`** + 真库 CRUD 回路 + 本批视图查询；
   **全量单测不能省**——批 A–D 期间只跑了门禁与抽样对拍，事后补跑全量才暴露出 35 处
   `reader.GetDouble` 读 `decimal` 列抛 `InvalidCastException`（生产 7 个文件、测试 14 个文件）。
   这类"读取端仍假定旧类型"的断裂，门禁与数值对拍都看不见：值本身是对的，坏在 `SqlDataReader` 的取值方法上。
   统一改为 `Convert.ToDouble(reader.GetValue(n))`，它对 `decimal`/`double`/`int` 都成立；
8. **对拍**：`CAST(col AS decimal(p,s))` 与转换前值逐列比对，差异行必须为 0（除 `float` 原本就
   带有 15 位尾数的情况，需按 `ROUND(col, s)` 比对）。

**有意遗留：6 个 `NON_NUMERIC` 列仍为 `float`**

| 表.列 | 中文说明 | 应改为 |
|---|---|---|
| `QC_SAMPLE_M.SAMPLE_SG` / `SAMPLE_LC` / `SAMPLE_XD` | 石膏样 / 量产样 / 限度样 | `nvarchar` 或 `bit` |
| `HR_WAGE_D.WAGE_ITEM37`、`HRM_WAGE_D.WAGE_ITEM31` | 有无加班费 | `bit` |
| `HRM_WAGE_D.WAGE_ITEM36` | 有无全勤奖 | `bit` |

按 §9-6 的拍板，这些**不在本 ADR 范围**：它们要改的是"类型语义"（布尔/类别/序号），不是"数值精度"。
改动会牵动录入控件（文本框 → 复选框/下拉）、`FIELDS` 元数据与前端列引用，属独立的一件事。
它们已登记 `NON_NUMERIC`，门禁不会把它们当数值列要求转 `decimal`。

**边界**：2074 个 `float` 里，2068 个本该是数值、已全部标准化；6 个本就不该是数值，留待另案。
把这两类混在一起做，会让验收标准变模糊——这也是本 ADR 停在这里的原因。

那 6 个要改的是 `bit`/`nvarchar`（布尔标记与类别码），改它们会动录入控件，
且与"数值精度"无关，属独立的"错型治理"。届时单独立 ADR 更清楚。

## 6. 风险与处置

| 风险 | 表现 | 处置 |
|---|---|---|
| **数据溢出** | `float` 值整数部分超过 `p-s` 位，`ALTER COLUMN` 报错 | §5.2 第 1 步预扫描，超限列单列定 `(p,s)` 或先降值（需业务确认） |
| **精度观感变化** | `1.1` 变 `1.100000`，前端显示与 E2E 断言红 | 属预期；E2E 夹具按"数值相等"而非"字符串相等"断言（`ADR-023` 的语义等价口径） |
| **视图元数据陈旧** | 改类型后视图仍报旧类型 | `sp_refreshview`，已列 9 个视图 |
| **快照静默落后** | 定义快照与元数据不一致 | 每批重发布；`LESSONS.md` L83 |
| **元数据与物理列漂移** | 184 行 `F_TYPE='float'` 但无物理列 | 迁移按 `(T_ID, F_ID)` 精确写；新增"F_TYPE ↔ sys.columns 一致性"门禁 |
| **`float` 尾数误差被固化** | 原值 `0.30000000000000004` 转成 `0.3000` | 这是**修正**而非损失；但需在对拍报告中显式列出，避免被误判为数据丢改 |
| **回滚不完整** | 回滚只恢复类型，不恢复位模式 | 迁移前对本批列做一次全量快照（`SELECT * INTO bak.xxx`），回滚用快照回填；`bak` schema 用完清理 |
| **执行时长/锁表** | 大表 `ALTER COLUMN` 期间阻塞写入 | 单公司部署、表规模可控（最大 8729 行）；安排在非业务时段，逐表执行 |

- 9 个视图中属于批 A 的已 `sp_refreshview` 且查询正常；
- `FIELDS.NUMERIC_ROLE` 与 `F_TYPE` 同批更新，元数据一致性门禁 0 红；
- 对拍报告：本批每列"转换前后按 `ROUND(s)` 比对"差异行数 = 0，或差异行逐条有业务解释；
- 真库 CRUD 回路（建/读/改/删）全过，金额合计与转换前一致。

## 9. 拍板结论

**2026-10-17 用户拍板：以下各项全部采纳"建议"列。** 本节保留原始选项与理由，便于后来人理解取舍过程。

| # | 事项 | 背景 | 选项 | 结论 |
|---|---|---|---|---|
| 1 | 金额宽度取 `(18,4)` 还是 `(18,6)` | 4 位覆盖全部 ISO 4217 minor unit；6 位为将来的加密/计量金额留余量 | ⒜ `(18,4)` / ⒝ `(18,6)` | **⒜ `(18,4)`**：ISO 上限就是 4，多 2 位无对应业务场景，且整数位从 14 降到 12 |
| 2 | 数量取 `(18,6)` 还是 `(18,4)` | 6 位覆盖毫克/微米；4 位够多数离散制造 | ⒜ `(18,6)` / ⒝ `(18,4)` | **⒜ `(18,6)`**：Odoo 数量精度可到 8 位、制药场景确有 6 位需求；整数位 12 仍远超业务量级 |
| 3 | 语义登记放 `FIELDS` 还是独立表 | `FIELDS` 已 11869 行、被高频读取 | ⒜ `FIELDS` 加列 / ⒝ 独立 `FIELD_NUMERIC_ROLE` 表 | **⒜**：语义是字段属性，同层同表；独立表会让每次读定义多一次 join |
| 4 | 最后 19 项待确认怎么办 | 二次判定后只剩 19 项：12 项语义待定（`PRODUCE_ULLAGE` 是数量还是率、`BACK_*` 是数量还是金额），7 项实为非数值（`SAMPLE_*` 类别码、`WAGE_ITEM37/31/36` 布尔、`serialno` 序号） | ⒜ 保持 `float`、待业务确认 / ⒝ 按建议直接判 / ⒞ 按表整批判 | **⒜**：⒞ 会把类别码强改成 `decimal`；⒝ 里那 7 项要改的是类型（`bit`/`nvarchar`/`int`）而不是小数位，必须另行确认 |
| 5 | 分批顺序与是否包含 `HR`/`HRM` | `HR`+`HRM` 合计 470 列，是第二大块 | ⒜ 按 §5.1 四批（HR 最后）/ ⒝ 先做 HR（工资精度诉求最强）/ ⒞ 只做 A+B，其余另案 | **⒜**：工资精度虽重要，但 `HR` 与核心单据无耦合，先做 A 能最快验证整套门禁与迁移流程 |
| 6 | 是否同批修 `[serialno] [float]` 这类明显错型 | 改的是类型语义（序号用整型），不是数值精度 | ⒜ 本 ADR 只登记、不改 / ⒝ 同批处理 | **⒜**：`serialno` 的值可能带小数，`float → int` 要先确认取整规则。`MIN_BUY_AMOUNT` 已改判并处置（见 §4.2、迁移 `402`）——它是金额、`int → decimal` 无损 |
| 7 | 是否引入 SQL Server 别名类型（`CREATE TYPE dbo.AMOUNT FROM decimal(18,4)`） | 别名类型能做到"一处定义、处处强制" | ⒜ 不引入 / ⒝ 引入 | **⒜**：`sys.types.is_user_defined=1` 会让 `TYPE_NAME()` 返回 `AMOUNT` 而非 `decimal`，`RecordPayloadValidator.cs:94` 的 `type.Contains("decimal")` 当场失效，前后端精度校验会静默放行。收益是"少写几次类型"，代价是整条校验链失效 |
