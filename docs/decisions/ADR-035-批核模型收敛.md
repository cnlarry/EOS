# ADR-035：批核模型收敛——批核本体默认可用，入口归声明与权限

- 状态：**草案（待拍板，未实施）**——两项待定见第 10 节；**本 ADR 先于 ADR-034 落地**
- 日期：2026-10-10
- 相关：ADR-012（单据行为效果配置化）、ADR-019（模块管理拆分，`MODULE_CONFIG_TAG`）、ADR-034（引擎开关收敛，分闸下线已移入本文）、ADR-023（对拍证据按语义等价）、`docs/plans/decision-ledger.md` **#58**（灰度开关）、**#108**（无副作用批核）、**#111**（批核侧旧过程清零）、`LESSONS.md` L27

> 本文的起点是一句大白话：**"批核就是把状态位改成已批核、记下人和日期，仅此而已。"** 而现在的实现要求它必须先有某种"支撑"才给你入口。

## 1. 问题：批核被实现成"必须有某种支撑"

今天的批核入口判据是一处**四者取并集**：

```98:107:EOS.API/Data/WorkflowStates.cs
    internal static bool NeedsApproveColumn(
        bool autoApprove,
        bool effectEnabled,
        bool hasWorkflow,
        IEnumerable<string>? enabledActionEventCodes)
    {
        if (autoApprove || effectEnabled || hasWorkflow)
```

即：**① 自动批核 ② 效果引擎接管 ③ 有审批流程 ④ 有批核/解批动作**——有任意一条，工具栏才显示批核/解批按钮。而"无副作用批核"被写成**兜底**：

```88:91:EOS.API/Data/WorkflowStates.cs
    internal static bool IsStatelessApproveCapable(
        bool effectEnabled,
        bool hasFlow) =>
        !effectEnabled && !hasFlow;
```

字面意思就是"引擎和流程都没有，才轮到你"。

**这两个判据把"实现方式"混进了"能不能批核"**。实测的后果（全库 358 个模块）：

| 口径 | 数量 |
|---|---|
| 有主表的模块 | 299 |
| 今天显示批核入口 | **170** |
| 其中靠**批核动作** | 98（1404 报价单、1405 销售订单、1406 送货单…） |
| 其中靠**自动批核** | 83（1202 商编变更单、1209 版次、1212 成本试算表…） |
| 其中靠**审批流程** | 1（1906 油卡充值单） |
| **其中只靠"效果引擎"那个开关** | **12**（1201 产品/料件、1401 客户、1601 厂商、1204、3014、300303、110309、180208、180301、180309、1803091、180502） |

那 12 个模块**只想要最简单的批核**（翻状态位 + 记人 + 记日期），却必须靠"效果引擎"开关来撑入口——这正是"搞得复杂"的根源。它们里面有 3 个**近期真在用**：1401 客户基本资料与 1601 厂商基本资料在 2026-10-05 还有人批核，1201 产品/料件 8 月批核过，主表分别有 133 / 263 / 1318 行已批核。

**现状隐患（不是改造才有的）**：只要有人在模块管理页把 1401 的「效果引擎（灰度开关）」取消勾选、点发布，它的批核按钮就会**无声消失**——因为它是"独木桥"。

同一个坑的镜像，仓库里已经踩过一次，注释还留着：

```80:83:EOS.API/Data/WorkflowStates.cs
    /// **判据不能绑在 `AUTO_APPROVE` 上**（曾经如此，已修）：自动批核只决定"保存之后要不要自动翻转
    /// 状态"，与"能不能手工批核"是两件事。绑上去的后果是——把一个模块的自动批核关掉（例如月结单要
    /// 改成"建单 / 审核"两个权限位），它的手工批核入口会**跟着一起消失**：服务端 404
    /// `WORKFLOW_NOT_SUPPORTED`，前端工具栏也不显示按钮，于是"关了自动批核就再没人能审"。
```

判据一旦绑上"实现方式"，就会出现"关掉某个实现方式 → 业务入口静默消失"。这已经发生过两次。

## 2. 决策：把三层重新划清

批核这件事，本质只有三层：

| 层 | 内容 | 是否需要配置 |
|---|---|---|
| **批核本体** | 翻 `CONFIRM_TAG=1`，记 `CONFIRM_PERSON` / `CONFIRM_DATE` | **不需要任何配置**——这就是批核的定义 |
| **入口** | 这个模块能否看见并点击批核 | 由**模块声明「支持批核」∧ 用户批核权限**决定 |
| **增强（可选）** | 批核时顺带做事（扣库存、写流水、联动别的单）→ APPROVE 动作链；要走多人审核 → 审批流程 | 需要配置，**但它们不再是你有没有入口的前提** |

四条具体决定：

1. **入口判据收敛为一维**：`NeedsApproveColumn` 不再收 `effectEnabled` / `enabledActionEventCodes` 作为入口依据；入口 = 模块声明「支持批核」∧ 用户有该模块的批核权限（`APPROVE_TAG`）。
2. **「支持批核」是模块的基础字段**，在模块管理页与「自动批核」并排（`AUTO_APPROVE` 语义不变：保存之后自动翻转状态位；它与入口**相互独立**，账本 #108 的教训）。
3. **"无副作用批核"从兜底改成常态**：判据由"没有引擎、没有流程"改为"**没有 APPROVE 动作链、没有流程**"——即"这次批核只需要翻状态位"。`WorkflowEngine` 里那条无副作用分支的逻辑不变，只换判据。
4. **模块级"效果引擎"开关（`EFFECT_ENGINE_TAG`）下线**：引擎接管的判定改为推导——"该事件有启用的动作行"；它的"批核入口"职责由第 2 条的声明承接。停用手段统一走行级 `ENABLED`（＋配置面提供"停用本模块全部动作"的批量操作）。

## 3. 为什么入口必须与"实现方式"脱钩

因为"**要不要人批核**"是业务声明，而"**批核时做什么**"是技术实现。把后者当前者的前提，会连着出三种错：

- 简单批核无处安放（那 12 个模块靠引擎开关凑入口）；
- 关掉某个实现方式就掉入口（`AUTO_APPROVE` 那次、以及今天"取消勾选引擎开关"这次）；
- 判据的来源越多，越没人说得清"这个模块为什么有批核按钮"。

反过来说，脱钩之后每一问都有唯一答案：有入口 ⇔ 声明为真且你有权限；批核时要额外做什么 ⇔ 看动作链；要不要送审 ⇔ 看流程。

## 4. 为什么入口不能改成"有 `CONFIRM_TAG` 列即有入口"

看起来最省事的一条路是"主表带 `CONFIRM_TAG` 列就显示入口"，但实测否掉它：

| 口径 | 数量 |
|---|---|
| 主表带 `CONFIRM_TAG` 列 | **271** |
| 今天有入口（全部都有该列） | 170 |
| **有列、今天没有入口** | **101** |

改成"有列即有入口"，会让入口从 170 涨到最多 **271**——多出 **101 个模块**（基本资料、报表、参数类）的表单上冒出批核按钮，点一下只会把状态位改成没有任何业务含义的"已批核"。**"这张表能表达已批核"不等于"这个模块要人批核"。**

## 5. 声明字段的值给谁（口径）

| 口径 | 值 = 1 的模块 | 将来新增一个带批核动作的模块 |
|---|---|---|
| **X（本 ADR 采用）** | **今天有入口的 170 个** | 必须显式勾「支持批核」才有入口——入口只由声明与权限决定 |
| Y（被否） | 只给"独木桥"的 12 个 | 配了批核动作就自动有入口：隐式来源继续存在，"第三次静默掉入口"的门还开着 |

选 X 的三个理由：**入口集合逐字不变**（170 个模块的可见行为一致）；**语义单一**（一处判据）；**不泛滥**（那 101 个"有列无入口"的模块保持 0）。

## 6. 与 ADR-034 的顺序

本文**先落地**——它决定"入口从哪来"，而 ADR-034 里那项"分闸下线"依赖它：先撤开关、入口无着落，会立刻砸出那 3 个主档的批核按钮。

ADR-034 收缩为两项与批核模型无关的事（总闸改断路器、清快照 `effectEngine` 段），可并行落地、互不阻塞。

## 8. 迁移与实施（先立后破）

**批 1（库，新增不删旧）**：新增 `APPROVE_ENTRY_TAG`（bit，默认 0）＋ `FIELDS` 登记；**值 = 今天显示入口的 170 个模块集合**（判据可机械表达：`AUTO_APPROVE=1` ∨ `EFFECT_ENGINE_TAG=1` ∨ 有流程 ∨ 有启用的批核/解批动作，且主表存在）；收口断言两条——① 置 1 的恰为 170 个；② 那 12 个"独木桥"模块在内。

**批 2（代码，判据切换）**：入口判据改"声明 ∧ 权限"；无副作用分支判据改"无 APPROVE 动作链、无流程"；发布门取参调整。此时 `EFFECT_ENGINE_TAG` 仍在库中但**不再被任何判据读取**。

**批 3（代码，引擎判定改推导）**：`IsEnabledFor` 改为"该事件有启用的动作行"；AD搬运期间用"开关值 vs 推导值"双算对拍守着（与 ADR-034 §0 同一手法）。

**批 4（库，退役旧列）**：断言"新旧两个口径给出的入口集合逐字一致"后，删 `EFFECT_ENGINE_TAG` ＋ `FIELDS` 登记 ＋ 门禁清单。

**为什么不用 `sp_rename` 把旧列改名**：改名会把 114 个旧值当成新语义的值带过来，而新语义要的是 170 个值——反正要整列重算；且改名在应用不停机时有窗口期（旧代码读旧列名会当场报错）。"新增 → 搬值 → 切读 → 删旧"与迁移 341 的手法一致。

## 9. 验证

- **入口集合零漂移**：批 1 与批 4 各取一次"可见入口的模块集合"，逐模块比对（170 个，含那 12 个）。
- 真库用例：① 声明=0 的模块不显示也不允许批核；② 声明=1 且无任何动作的模块（拿 1401 或 1601 真跑一次）显示入口且批核成功（状态位 + 人 + 日期齐备）；③ 有流程的模块仍走送审；④ 有 APPROVE 动作的模块批核时效果链照常执行。
- 存量用例要随之修正：`EOS.API.Tests/WorkflowStatesLifecycleTests.cs`（其 `[InlineData]` 断言的是旧语义）、`EOS.Web/src/features/document-workbench/formToolbar.test.ts`（`hasApproveCapability` 的并集语义）、`MenuAdminPage.test.tsx`（复选框标题与字段名）。
- 门禁：`check-module-node-kind`、`check-lifecycle-columns`（判据取参变了）、`check-snapshot-staleness`、`check-di-registrations`、手册新鲜度。

## 10. 待拍板

1. **声明字段的值口径**：采用 **X（170 个全置 1）**，还是 Y（只 12 个）？——本文按 X 写。
2. **界面标题**：「支持批核」／「人工批核入口」／「需要批核」，选一个（它与「自动批核」并排，两个词要能一眼分清）。

## 11. 刻意不做

- **不把入口改成"有列即有入口"**：会把入口从 170 涨到 271（第 4 节）。
- **不让 `AUTO_APPROVE` 重新参与入口判据**：账本 #108 已否（`WorkflowStates.cs:80-83` 记着那次事故）。
- **不引入第三套开关**：入口是声明，停用是行级 `ENABLED`，没有第三种。
- **不在本 ADR 里动"发布/快照"的语义**：那是 ADR-034 的领域。
