# ADR-035：批核模型收敛——批核本体默认可用，入口归声明与权限

- 状态：**已落地（未提交，2026-10-11）**——五项决定见第 10 节，实施记录见第 12 节；**本 ADR 先于 ADR-034 落地**
- 日期：2026-10-10
- 相关：ADR-012（单据行为效果配置化）、ADR-019（模块管理拆分，`MODULE_CONFIG_TAG`）、ADR-034（引擎开关收敛，分闸下线已移入本文）、ADR-023（对拍证据按语义等价）、`docs/plans/decision-ledger.md` **#58**（灰度开关）、**#108**（无副作用批核）、**#111**（批核侧旧过程清零）、`LESSONS.md` L27

> 本文的起点是一句大白话：**"批核就是把状态位改成已批核、记下人和日期，仅此而已。"** 而现在的实现要求它必须先有某种"支撑"才给你入口。

## 1. 问题：批核被实现成"必须有某种支撑"

今天的批核入口判据是一处**四者取并集**：

```98:107:EOS.API/Data/WorkflowStates.cs
    internal static bool NeedsApproveColumn(
        bool autoApprove,
        bool effectEnabled,
        bool hasWorkflow,
        IEnumerable<string>? enabledActionEventCodes)
    {
        if (autoApprove || effectEnabled || hasWorkflow)
```

即：**① 自动批核 ② 效果引擎接管 ③ 有审批流程 ④ 有批核/解批动作**——有任意一条，工具栏才显示批核/解批按钮。而"无副作用批核"被写成**兜底**：

```88:91:EOS.API/Data/WorkflowStates.cs
    internal static bool IsStatelessApproveCapable(
        bool effectEnabled,
        bool hasFlow) =>
        !effectEnabled && !hasFlow;
```

字面意思就是"引擎和流程都没有，才轮到你"。**这两个判据把"实现方式"混进了"能不能批核"**。实测（全库 358 个模块）：

| 口径 | 数量 |
|---|---|
| 有主表的模块 | 299 |
| 今天显示批核入口 | **170** |
| 其中靠**批核动作** | 98（1404 报价单、1405 销售订单、1406 送货单…） |
| 其中靠**自动批核** | 83（1202 商编变更单、1209 版次、1212 成本试算表…） |
| 其中靠**审批流程** | 1（1906 油卡充值单） |
| **其中只靠"效果引擎"那个开关** | **12**（1201 产品/料件、1401 客户、1601 厂商、1204、3014、300303、110309、180208、180301、180309、1803091、180502） |

那 12 个模块**只想要最简单的批核**（翻状态位 + 记人 + 记日期），却必须靠"效果引擎"开关来撑入口。它们里面有 3 个**近期真在用**：1401 客户基本资料与 1601 厂商基本资料在 2026-10-05 还有人批核，1201 产品/料件 8 月批核过，主表分别有 133 / 263 / 1318 行已批核。

**现状隐患（不是改造才有的）**：只要有人在模块管理页把 1401 的「效果引擎（灰度开关）」取消勾选、点发布，它的批核按钮就会**无声消失**——因为它是"独木桥"。

同一个坑的镜像，仓库里已经踩过一次，注释还留着：

```80:83:EOS.API/Data/WorkflowStates.cs
    /// **判据不能绑在 `AUTO_APPROVE` 上**（曾经如此，已修）：自动批核只决定"保存之后要不要自动翻转
    /// 状态"，与"能不能手工批核"是两件事。绑上去的后果是——把一个模块的自动批核关掉（例如月结单要
    /// 改成"建单 / 审核"两个权限位），它的手工批核入口会**跟着一起消失**：服务端 404
    /// `WORKFLOW_NOT_SUPPORTED`，前端工具栏也不显示按钮，于是"关了自动批核就再没人能审"。
```

判据一旦绑上"实现方式"，就会出现"关掉某个实现方式 → 业务入口静默消失"。这已经发生过两次。

## 2. 决策：把三层重新划清

批核这件事，本质只有三层：

| 层 | 内容 | 是否需要配置 |
|---|---|---|
| **批核本体** | 翻 `CONFIRM_TAG=1`，记 `CONFIRM_PERSON` / `CONFIRM_DATE` | **不需要任何配置**——这就是批核的定义 |
| **入口** | 这个模块能否看见并点击批核 | 由**模块声明「启用批核」∧ 用户批核权限**决定 |
| **增强（可选）** | 批核时顺带做事（扣库存、写流水、联动别的单）→ APPROVE 动作链；要走多人审核 → 审批流程 | 需要配置，**但它们不再是你有没有入口的前提** |

五条具体决定：

1. **入口判据收敛为一维**：`NeedsApproveColumn` 不再收 `effectEnabled` / `enabledActionEventCodes` 作为入口依据；入口 = 模块声明「启用批核」∧ 用户有该模块的批核权限（`APPROVE_TAG`）。
2. **新增模块基础字段 `APPROVE_ENABLED`（bit，默认 0）**，它只表达一件事——"这个模块要有批核入口"；界面文案「**启用批核**」与列名同义（界面与代码之间少一层翻译），摆在「自动批核」旁边。**逐字核对过**：库内与代码里都没有同名的 `APPROVE_ENABLED`，不会与 `SYSDH`/`SYSDD` 的权限位 `APPROVE_TAG`（"这个人有权批核"）或行级 `ENABLED`（某一行是否生效）混淆——三者分属不同表，且模块级这一列带 `APPROVE_` 前缀。
3. **"无副作用批核"从兜底改成常态**：判据由"没有引擎、没有流程"改为"**没有 APPROVE 动作链、没有流程**"，即"这次批核只需要翻状态位"。`WorkflowEngine` 里那条分支的逻辑不变，只换判据。
4. **模块级"效果引擎"开关（`EFFECT_ENGINE_TAG`）下线**：引擎接管的判定改为推导——"**定义里有启用且接在效果链上的动作**"（`WorkflowStates.HasEnabledEngineActions`；`MANUAL` 自定义按钮不算，它走"人点按钮"那条独立通道，也不经过 `IsEnabledFor`）；它的"批核入口"职责由第 2 条的 `APPROVE_ENABLED` 承接。停用手段统一走行级 `ENABLED`（＋配置面提供"停用本模块全部动作"的批量操作）。
5. **`AUTO_APPROVE` 语义不变**（保存之后自动翻转状态位），它与"入口"相互独立——账本 #108 的教训。

## 3. 为什么入口必须与"实现方式"脱钩

因为"**要不要人批核**"是业务声明，而"**批核时做什么**"是技术实现。把后者当前者的前提，会连着出三种错：

- 简单批核无处安放（那 12 个模块靠引擎开关凑入口）；
- 关掉某个实现方式就掉入口（`AUTO_APPROVE` 那次、以及今天"取消勾选引擎开关"这次）；
- 判据的来源越多，越没人说得清"这个模块为什么有批核按钮"。

脱钩之后每一问都有唯一答案：有入口 ⇔ 声明为真且你有权限；批核时要额外做什么 ⇔ 看动作链；要不要送审 ⇔ 看流程。

## 4. 为什么入口不能改成"有 `CONFIRM_TAG` 列即有入口"

看起来最省事的一条路是"主表带 `CONFIRM_TAG` 列就显示入口"，但实测否掉它：主表带该列的模块有 **271** 个，而今天有入口的只有 **170**——改成"有列即有入口"会让入口涨到最多 271，多出 **101 个模块**（基本资料、报表、参数类）的表单上冒出批核按钮，点一下只会把状态位改成没有任何业务含义的"已批核"。**"这张表能表达已批核"不等于"这个模块要人批核"。**

## 5. 声明字段的值给谁：一视同仁（口径 X）

| 口径 | 值 = 1 的模块 | 将来新增一个带批核动作的模块 |
|---|---|---|
| **X（采用）** | **今天有入口的 170 个，一视同仁** | 必须显式勾「启用批核」才有入口——入口只由声明与权限决定 |
| Y（否） | 只给"独木桥"的 12 个 | 配了批核动作就自动有入口：隐式来源继续存在，"第三次静默掉入口"的门还开着 |

选 X 的三个理由：**入口集合逐字不变**；**语义单一**（一处判据）；**不搞特例**——不为那 12 个模块写"因为有历史原因所以单独照顾"的分支，将来也不用回答"为什么它跟别人不一样"。那 101 个"三列齐全、今天没有入口"的模块保持 0（谁将来要给它们批核，勾上即可）。

## 6. 界面与校验（本次一并拍板）

- **字段标题**：`APPROVE_ENABLED` 在模块管理页显示为「**启用批核**」，并且**紧接着**「自动批核」（`AUTO_APPROVE`）——两个词并排，一眼分得清"要有入口"与"保存后自动翻转"。
- **联动一（向上）**：勾选「自动批核」时，「启用批核」**自动被选中**。理由：自动翻转状态位的前提就是这个模块有批核语义；今天 83 个自动批核模块本来也都在那 170 个有入口的模块里。
- **联动二（向下，本条的必然推论）**：取消「启用批核」时，「自动批核」**一并取消**（否则会留下"自动批核但不启用批核"的矛盾状态）。界面给出提示。
- **勾选校验（三列）**：勾选「启用批核」时校验主表是否有 **批核状态（`CONFIRM_TAG`）+ 批核人（`CONFIRM_PERSON`）+ 批核日期（`CONFIRM_DATE`）** 三个基础字段；缺任一列则**不允许勾选**，并指名缺哪一列。**校验放在模块管理内**：前端即时提示（勾选当刻就拦），服务端写路径 fail-closed（绕过前端也存不进去）——前端只改善体验，判据只在服务端。
- **与发布门的关系**：发布门原有的 `lifecycle_columns` 检查**保留**，作为第二道闸（管"配置后来被改坏"与"自动批核"这两条路径）。勾选校验是第一道，发布门是第二道，两者不重复劳动。

**实测支撑（这条校验不会挡住迁移）**：

| 口径 | 数量 |
|---|---|
| 有主表的模块 | 299 |
| 三列齐全 | **271** |
| 只有一两列（中间态） | **0** |
| 一列都没有 | 28 |
| **今天有入口的 170 个** | **全部三列齐全** |

即：三列在库里是"成套出现"的；那 170 个一个不缺；28 个一列都没有的模块**勾不上**——这正是这条校验想要的（它们本来就没有批核语义，也没有任何已批核数据）。缺列又要批核的模块，走迁移补列（**不设一键补列**，物理列变更一律走 DbVersion 迁移）。

## 8. 迁移与实施（先立后破；本 ADR 先于 ADR-034 落地）

**批 1（库，新增不删旧）**：新增 `APPROVE_ENABLED`（bit，默认 0）＋ `FIELDS` 登记；**值 = 今天显示入口的 170 个模块，一视同仁**（判据可机械表达：`AUTO_APPROVE=1` ∨ `EFFECT_ENGINE_TAG=1` ∨ 有流程 ∨ 有启用的批核/解批动作，且主表存在）。收口断言三条：① 置 1 的恰为 170 个；② 那 12 个"独木桥"在内；③ 置 1 的模块主表**三列齐全**（实测成立，写成断言钉住）。

**批 2（代码，判据切换 + 界面）**：入口判据改"声明 ∧ 权限"；无副作用分支判据改"无 APPROVE 动作链、无流程"；发布门取参调整；模块管理页换成「启用批核」+「自动批核」并实现两条联动与三列校验（写路径 fail-closed）。此时 `EFFECT_ENGINE_TAG` 仍在库里但**不再被任何判据读取**。

**批 3（代码，引擎判定改推导）**：`IsEnabledFor` 改为"该事件有启用的动作行"；搬运期间用"开关值 vs 推导值"双算对拍守着。

**批 4（库，退役旧列）**：断言"新旧两个口径给出的入口集合逐字一致"后，删 `EFFECT_ENGINE_TAG` ＋ `FIELDS` 登记 ＋ 门禁清单。

**为什么不用 `sp_rename` 把旧列改名**：改名会把 114 个旧值当成新语义的值带过来，而新语义要的是 170 个值——反正要整列重算；且改名在应用不停机时有窗口期（旧代码读旧列名会当场报错）。"新增 → 搬值 → 切读 → 删旧"与迁移 341 的手法一致。

## 9. 验证

- **入口集合零漂移**：批 1 与批 4 各取一次"可见入口的模块集合"，逐模块比对（170 个，含那 12 个）。
- **三列校验**：① 主表缺任一列时，前端勾不上且服务端拒存（指名缺哪一列）；② 主表三列齐全时正常保存；③ 拿一个 28 个"一列都没有"的模块试一次，断言被拒。
- **两条联动**：勾「自动批核」→「启用批核」自动置 1；取消「启用批核」→「自动批核」一并置 0（含服务端口径，防止只有前端联动）。
- **批核本体**：拿 1401 或 1601 真跑一次——显示入口、批核成功、状态位 + 人 + 日期齐备。
- 存量用例要随之修正：`EOS.API.Tests/WorkflowStatesLifecycleTests.cs`（`[InlineData]` 断言的是旧语义）、`EOS.Web/src/features/document-workbench/formToolbar.test.ts`、`MenuAdminPage.test.tsx`（复选框标题与联动）。
- 门禁：`check-module-node-kind`、`check-lifecycle-columns`（判据取参变了）、`check-snapshot-staleness`、`check-di-registrations`、手册新鲜度。

## 11. 刻意不做

- **不把入口改成"有列即有入口"**：会把入口从 170 涨到 271（第 4 节）。
- **不让 `AUTO_APPROVE` 单独决定入口**：账本 #108 已否（`WorkflowStates.cs:80-83` 记着那次事故）。
- **不设一键补列**：缺三列的模块要批核就走迁移补列；物理列变更一律走版本化迁移。
- **不引入第三套开关**：入口是声明，停用是行级 `ENABLED`，没有第三种。
- **不在本 ADR 里动"发布/快照"的语义**：那是 ADR-034 的领域。

落地时确认/修正的三件事：

1. **入口判据是"并集"不是"严格或"**：`NeedsApproveColumn` 保留四来源取并集，只把 `effectEnabled` 那一来源替换成 `approveEnabled`；`IsStatelessApproveCapable` 由"无引擎且无流程"换成"无 APPROVE 动作链且无流程"。这样今天有入口的 **170 个逐字不变**——那 12 个"只靠引擎开关撑入口"的模块里，6 个另有批核动作、6 个是自动批核，并集下不受影响。
2. **三列校验的落点是模块管理内、按声明判**：勾「启用批核」⇒ 主表必须有**批核状态位 / 批核人 / 批核日期**三列（缺列拒绝保存并**指名缺哪列**，缺列走迁移补列、不设一键补列）；发布门的 `lifecycle_columns` 由"开关或动作"改为"**声明或自动批核或流程或批核动作**"，**同时把要求从 `CONFIRM_TAG` 扩到三列**——两条判据都只到"三列齐全"，不收紧到具体列名（否则存量 30 个已发布模块会被自己的发布门挡下，而 `WorkflowStates` 从未按列名判过）。
3. **删列前自证的是"等价"而非"逐字相等"**：346 的断言是"**不存在'配了启用动作却分闸关着'的模块**"（删列后行为不变的充分条件）。4 个"分闸开着却零配置"的模块（1201/1401/1601/300303）的行为变化是**有意的**：从"引擎接管（空转）"落到"无副作用批核"分支——这正是第 3 节要修的三种错之一。
4. **同一个退役动作还带走了一个"漏进快照的计算属性"**：`WorkbenchDefinition.EffectEngineEnabled` 是只读 getter、没有 `[JsonIgnore]`，默认序列化选项会把它写进每一份快照（`"EffectEngineEnabled":false,` = 28 字符）；删掉它之后，**历史快照与重建定义凭空差出这 28 字符**——叠加 `effectEngine` 段的 20/31 字符，全库 262 份快照里 **261 份**被判"静默落后"（`check-snapshot-staleness`）。处置与 ADR-034 第②项同一条原则：**运行期不再读的差异就该被比较器归一掉**，故把两个键一起加进忽略清单（`WorkbenchDefinitionContentComparer` 摘掉 `effectEngine` 与 `EffectEngineEnabled`），并补正反两条用例。**不做全量重发布**——262 份快照各升一版会把按 ADR-023 记录的对拍证据全部作废，而运行期行为一字未变。

验证（对照 `ci.yml` 三步）：全解决方案 Release 编译 **0 错**（13 条既有告警）；后端离线 **1952 通过 / 0 失败**；前端 lint 0 错 + build 通过 + **113 文件 / 1121 用例**；迁移 345＋346 合并干跑 **PASS**（事务配平、整库回滚、探针前后一致）；迁移落库后 `check-module-node-kind` / `check-lifecycle-columns` / `check-required-columns` / `check-di-registrations` 等门禁全绿，ADR-012 覆盖报告实跑读数"引擎接管 **110**"（与 346 的等价性断言吻合）。

`check-snapshot-staleness` 顺带交出一份真实账：全库 262 份快照里 **261 份是上述假警报**（归一后消失），**1 份是真落后**——**1401 客户基本资料 v62**（快照比重建多 14041 字符、且无脏标记，属该门禁存在的理由那类"迁移/直写改了配置却没人重发布"）。它与本次改造无关，处置是**重发布该模块或给它标脏**（需维护者按 ADR-023 的证据成本决定，故本 ADR 不做）。

### 12.1 收尾三项（ADR 正文承诺 + 覆盖空档 + 真机验证）
