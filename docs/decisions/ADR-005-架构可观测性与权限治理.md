## 背景

EOS 虽然重构自旧 ERP，但应按全新系统持续演进。当前 `EOS.API` 已经形成统一业务入口、服务端权限边界、元数据驱动工作台和 DbUp 版本化迁移；`EOS.Web` 也已建立统一表格、命令栏、表单和前端权限体验。随着统一表单持续放量，现有实现暴露出四类结构性问题：

1. `DocumentWorkbenchRepository` 同时承担模块定义解析、SQL 组装、查询、写入、审批、结案、审计和虚拟列处理，职责过重；
2. 模块行为由 `MODULES` / `FIELDS` / `TABLES` 等元数据决定，但缺少启动期和发布期的强校验，元数据错误会延迟到业务运行时暴露；
3. 领域规则逐渐集中到 `DomainRuleService`，采购、销售、生产、库存、人事等规则缺少稳定边界；
4. 日志以请求文本为主，缺少统一结构化事件、指标、健康检查、链路标识和面向开发 Agent 的检索能力；权限判断、数据范围过滤和审计也分散在控制器与仓储中。

同时，`EOS.Client`、`EOS.Gateway`、`EOS.AgentRuntime` 及相关 AI 链路可能重新立项或推倒重建。本决策不约束这些组件的最终形态，只要求它们未来继续通过 `EOS.API` 访问业务能力。

## 决策

### 1. API 版本与契约治理

- `EOS.API` 面向外部调用方的稳定契约统一挂载到 `/api/v1`；
- 现有控制器先保持当前路由兼容，新增对外契约不得再挂到无版本根路径；
- 迁移采用双轨期：旧路由标记为兼容路由，逐步增加废弃标记和迁移映射，不要求一次性破坏现有页面；
- `EOS.Web` 只依赖 API DTO 与错误契约，不依赖仓储内部类型、SQL 结构或数据库列名；
- 破坏性 DTO 变更必须新增字段优先、必要时新增版本端点，并在 OpenAPI 与前端类型层同步登记；
- API 错误继续沿用 `code` / `message` / `fieldErrors` / trace 标识的统一问题契约；
- OpenAPI 是 API 契约的权威描述，生产环境不匿名开放。

### 2. 拆分 DocumentWorkbench

将当前巨型 `DocumentWorkbenchRepository` 拆成职责明确的服务组件，而不是继续追加业务开关：

| 组件 | 职责 |
|---|---|
| `WorkbenchDefinitionProvider` | 加载、校验和缓存 `MODULES` / `FIELDS` / `TABLES` 派生的模块定义 |
| `WorkbenchQueryComposer` | 构建列表、详情、子表、排序、筛选、字段选择和分页 SQL |
| `WorkbenchCommandHandler` | 处理新增、修改、删除、复制和主子表事务 |
| `WorkbenchApprovalService` | 处理批核、解批、结案、未结案和状态机副作用 |
| `WorkbenchScopeFilter` | 统一应用 `EXEC_TAG`、`DATA_FILTER`、模块过滤和字段权限 |
| `WorkbenchAuditWriter` | 统一写入业务审计与变更明细 |
| `WorkbenchVirtualColumnResolver` | 只处理受控虚拟列、转换函数和展示计算 |

`WorkbenchCommandHandler` 写路径必须支持幂等键，重复提交不产生重复副作用；`WorkbenchApprovalService` 的副作用必须定义补偿语义——批核/解批的库存等副作用不随单据删除回滚是既有技术债，拆分时须显式设计补偿策略（如删除前检测已发生副作用并阻止或提供反向操作），不能延续旧行为。

拆分约束：

- Controller 只做 HTTP 契约、认证入口和用例编排；
- 所有动态标识符必须来自服务端 Definition 白名单；
- 所有用户值必须参数化；
- 子表查询必须携带有效主表关联键；
- 内部行键（`__rowKey`）必须与显示列元数据分离，禁止把隐藏关键字段重新作为显示列返回；
- 无法确定数据范围时默认拒绝；
- 前端 `DocumentWorkbenchPage` 只保留页面编排，不新增业务分支；业务动作继续由领域 feature 和共享组件承接。

### 3. 模块 Definition 快照

建立模块定义的发布快照与运行时快照两层机制：

1. **发布快照**

   - 管理端修改模块、字段、表、路由、必填、默认值、选择器、过滤器或表达式后生成版本化快照；
   - 快照保存定义 JSON、来源元数据版本、校验结果、发布人、发布时间和状态；
   - 未通过校验的定义不能发布到运行时。

2. **运行时快照**

   - API 启动或显式刷新时加载已发布快照；
   - 运行时优先使用不可变 Definition 对象，不在每次请求中重复解析全部元数据；
   - 快照携带版本号，日志、审计和错误响应可关联到定义版本；
   - 权限管理端保存后触发相关模块失效或刷新。

3. **快照落库与触发机制**

   - 快照作为新系统对象经 DbUp 版本化迁移建在 `EOS.ERP` 内（如 `WORKBENCH_DEFINITION_SNAPSHOT`），
     保存定义 JSON、来源元数据版本、校验结果、发布人、发布时间和状态；
   - 元数据写路径（2302 字段维护、工作台列设置、选择器/过滤器配置）保存后仅将该模块标记为"脏"，
     不逐次生成快照，由发布动作批量生成并校验，避免每次字段保存都触发快照；
   - 管理端对"已编辑但未发布"的模块显示明确状态，避免运维误以为改动已生效；
   - 发布校验器与 `scripts/auto-enable-batch.ps1` 的放量预检共用同一道闸，避免两套校验标准；
   - `definitionVersion` 贯穿日志、审计、错误响应并回传前端，作为排障关联键。

发布前必须校验：

- 模块在运行白名单内，路由合法；
- 主表、子表、主键列、关联键真实存在；
- 显示、查询、录入、排序、过滤字段全部通过服务端白名单；
- 必填、默认值、选择器、虚拟列、转换函数可解析；
- 成本、保密、拒绝字段权限可应用；
- 高风险表达式只允许进入受控解析器；
- 校验结果生成机器可读报告，供 CI、发布工具和开发 Agent 使用。

### 4. 按领域拆分规则引擎

`DomainRuleService` 不再作为所有业务规则的长期落点，按领域拆分：

- 采购：`ProcurementRules`
- 销售：`SalesRules`
- 库存：`InventoryRules`
- 生产：`ProductionRules`
- 人事考勤：`HrRules`
- 财务收付：`FinanceRules`

公共能力保留为独立原语：

- 单据状态机；
- 数量回写与超量校验；
- 金额、税率与舍入计算；
- 主子表一致性；
- 引用存在性检查；
- 领域事件或副作用执行器。

领域规则服务只表达本域规则，不直接拼装其他域 SQL；跨域动作通过显式接口或公共单据服务完成。

### 5. 统一可观测性

#### 5.1 结构化日志

引入结构化日志输出，推荐 JSON 格式。每条 API 请求和关键领域事件至少包含：

```json
{
  "ts": "2026-08-22T10:00:00.000+08:00",
  "level": "Information",
  "event": "http_request",
  "traceId": "trace-id",
  "spanId": "span-id",
  "correlationId": "correlation-id",
  "userId": "1001",
  "clientId": "eos.web",
  "moduleId": 1606,
  "action": "document.save",
  "status": 200,
  "elapsedMs": 123,
  "definitionVersion": "module-1606-v12"
}
```

固定字段包括：

- `traceId` / `spanId` / `correlationId`；
- `userId`；
- `clientId`；
- `moduleId`；
- `action`；
- `result`；
- `elapsedMs`；
- `dbElapsedMs`；
- `definitionVersion`；
- `error.code`。

`correlationId` 由调用方（EOS.Web / EOS.Client）经 `X-Correlation-Id` 请求头传入，服务端透传并随
日志、审计与错误响应返回，未携带时由服务端生成。脱敏分类复用 `FIELDS.IS_COST` / `IS_SECRECY`
字段级标记，日志、审计与 MCP 输出统一按该标记脱敏，不另建敏感清单。

禁止记录：

- 密码、哈希、Cookie、Token 和连接串；
- 附件正文；
- LLM prompt / response 全文；
- 未脱敏的整行业务数据；
- 可直接还原敏感字段原文的键值对。

`EOS.Web` 记录前端错误、路由异常、未处理 Promise 和关键用户操作上下文，但不得记录表单全文、Token 或敏感业务值。

#### 5.2 指标

`EOS.API` 建立最小指标集：

| 类型 | 指标 |
|---|---|
| HTTP | 请求数、错误率、P95 / P99 延迟 |
| 数据库 | 连接池使用、慢查询数、失败率、超时率 |
| Workbench | 列表耗时、保存耗时、并发冲突数、范围过滤拒绝数 |
| 审批 | 批核 / 解批 / 结案成功率与耗时 |
| PDF | 生成次数、耗时、失败率 |
| 附件 | 上传下载量、大小分布、失败原因 |
| 权限 | 权限查询耗时、缓存命中率、拒绝数 |

`EOS.Web` 建立最小前端指标：

| 类型 | 指标 |
|---|---|
| 页面 | 首屏耗时、路由切换耗时 |
| 表格 | 列表首帧耗时、大数据量渲染耗时 |
| 表单 | 保存耗时、校验失败数、提交失败数 |
| 错误 | JS 错误数、接口失败数、权限拒绝数 |

指标出口采用 OpenTelemetry（推荐 Prometheus 拉取端点）；`EOS.Web` 前端指标按埋点约定上报到统一
采集端点，不直接写日志。

#### 5.3 健康检查

`EOS.API` 提供分级健康端点：

- `/health/live`：进程存活；
- `/health/ready`：EOS.ERP 连接可用、迁移完成、附件根目录可写、必要配置存在；
- `/health/startup`：Definition 快照加载和迁移初始化结果。

数据库 ready 检查只做轻量探活，不执行重查询。

#### 5.4 开发 Agent 日志访问

> **❌ 已失效（决策 #52，2026-09-05 用户拍板整体拆除；推翻本节）**：日志 MCP（含 REST 查询栈）已删除，
> 排障 SOP 改为文件日志尾部直读 + mssql 查 `AUDIT_EVENT`（见 `AGENTS.md`「日志排障」）。本节以下内容保留为历史记录。

结构化日志落地后，提供面向 Codex、Cursor、OpenCode 等开发工具的日志分析入口。实现形态优先选择 **MCP Server**，必要时再封装为项目 Skill：

最小能力：

1. `search_logs`：按时间、级别、traceId、correlationId、userId、moduleId、action、error code 检索；
2. `get_request_trace`：按 correlationId 聚合 HTTP、SQL、领域动作、审计和异常事件；
3. `summarize_errors`：按错误码、模块、端点和时间窗聚合；
4. `explain_slow_request`：定位慢请求中的 DB、审批、PDF、附件等阶段；
5. `tail_logs`：跟踪最新错误和告警；
6. `redact`：输出前统一脱敏。

安全边界：

- MCP 只读日志，不提供修改、删除日志能力；
- 默认只访问开发或测试环境；生产访问必须显式授权；
- 不返回密码、Cookie、Token、连接串、附件正文和 LLM prompt 全文；
- 输出限制单次行数与字节数，避免 Agent 上下文被日志淹没；
- 每次查询记录工具调用者与查询条件。

Skill 只作为使用说明、查询模板和结果解读规则；日志读取、过滤、聚合和脱敏必须由服务端 MCP 完成。

### 6. 统一权限入口

建立 `IPermissionService` 作为 `EOS.API` 内唯一权限判断入口，控制器和仓储不再直接调用 `LegacyRightsRepository` 决策：

```csharp
public interface IPermissionService
{
    Task<ModulePermission> GetAsync(
        string userId,
        int moduleId,
        CancellationToken cancellationToken);

    Task<ModulePermission> RequireAsync(
        string userId,
        int moduleId,
        PermissionAction action,
        CancellationToken cancellationToken);
}
```

约束：

- 个人权限覆盖组权限、组权限布尔位 OR、`EXEC_TAG` 最大值规则保持不变；
- 权限资源与模块号集中定义，消除控制器中的魔法数字；
- `CanBrowse` / `CanEdit` / `CanDelete` / `CanApprove` / `CanSetup` / 字段权限统一由该服务解释；
- 字段级权限（禁止查看、成本、保密、禁止新增/修改字段）由同一服务提供，`IPermissionService`
  返回或配套方法下发字段级判定结果，`WorkbenchScopeFilter` 只消费、不重复实现；
- 权限决策与范围应用两层的边界必须明确：`WorkbenchScopeFilter` 负责把模块级与字段级权限落地为
  范围 SQL 与列过滤，不自行判定权限；控制器与仓储不再直接调用 `LegacyRightsRepository` 决策；
- 权限结果可加短 TTL 缓存，管理端写入后主动失效；
- 缓存 key 包含用户、模块和权限版本；
- 高风险操作记录权限决策来源与结果。

### 7. 数据范围 fail-closed

`EXEC_TAG`、`DATA_FILTER`、模块过滤、字段权限和主子表范围统一由 `WorkbenchScopeFilter` 应用：

- 列表、详情、子表、搜索中心、报表、导出、打印数据源和选择器必须复用同一范围构建逻辑；
- 明细范围必须通过有效主表关联键从主表范围推导；
- 不允许前端提交范围 SQL、表名、列名、排序字段或隐藏主键；
- `DATA_FILTER` 解析失败、字段不在白名单、缺少主表关联或范围无法确定时返回 403 或明确业务错误，不降级为全量查询；
- 导出、打印和页面查询的数据集合必须一致；
- 新增权限 E2E 矩阵覆盖不同 `EXEC_TAG`、字段隐藏、`DATA_FILTER`、导出与明细越权场景。

### 8. 统一业务审计

在 `EOS.ERP` 内建立新系统审计模型，逐步替代以旧 `SYSDF` 作为核心证据源的做法：

```sql
CREATE TABLE dbo.AUDIT_EVENT
(
    EVENT_ID BIGINT IDENTITY PRIMARY KEY,
    OCCURRED_AT DATETIME2(3) NOT NULL,
    CORRELATION_ID NVARCHAR(64) NOT NULL,
    ACTOR_USER_ID NVARCHAR(20) NOT NULL,
    ACTOR_TYPE TINYINT NOT NULL,
    CLIENT_TYPE TINYINT NOT NULL,
    MODULE_ID INT NULL,
    RESOURCE_TYPE NVARCHAR(50) NOT NULL,
    RESOURCE_KEY NVARCHAR(200) NOT NULL,
    ACTION NVARCHAR(50) NOT NULL,
    RESULT TINYINT NOT NULL,
    DEFINITION_VERSION NVARCHAR(64) NULL,
    SUMMARY NVARCHAR(1000) NULL,
    DETAIL_JSON NVARCHAR(MAX) NULL,
    CREATED_DATE DATETIME2(3) NOT NULL
);

CREATE TABLE dbo.AUDIT_FIELD_CHANGE
(
    EVENT_ID BIGINT NOT NULL,
    FIELD_NAME NVARCHAR(100) NOT NULL,
    OLD_VALUE NVARCHAR(MAX) NULL,
    NEW_VALUE NVARCHAR(MAX) NULL,
    VALUE_HASH BINARY(32) NULL,
    PRIMARY KEY (EVENT_ID, FIELD_NAME)
);
```

约束：

- 对象名全大写；
- 新表和迁移放入 `EOS.API/Data/Migrations/`；
- 审计写入必须与业务事务同生共死；
- 至少覆盖新增、修改、删除、批核、解批、结案、未结案、附件删除、导出、打印、管理端写入和权限拒绝；
- `ACTOR_TYPE` 区分用户、系统任务、Agent 代表用户和外部集成；
- `CLIENT_TYPE` 区分 Web、API、Agent 和集成调用；
- 密码、密钥、Cookie、附件正文不入审计；
- 大字段或敏感字段可只存 hash、掩码或摘要；
- 审计表需规划留存与归档：`AUDIT_FIELD_CHANGE` 按事件滚动归档，`DETAIL_JSON` 大字段限量存储；
- 若审计写入放大影响单据保存 P95 达阈值（见复审条件），先降级为摘要级审计，字段级明细按需开启；
- 旧 `SYSDF` 继续作为兼容查询来源，新功能不得把 `SYSDF` 当作唯一审计事实源。

### 9. 数据访问与一致性

- 强一致路径禁止 `NOLOCK`，包括保存前校验、主子表读取、审批、结案、库存、财务金额和单据编号生成；
- 只读报表、浏览和大列表可在有理由时使用 `NOLOCK`，但必须登记——采用显式注册表机制
  （代码注解 + CI 检查或配置 allowlist），由评审确认，不允许口头约定；
- 新代码默认不使用 `NOLOCK`；
- `DbConnectionFactory` 后续增加统一 CommandTimeout、执行耗时统计、慢查询阈值和失败指标；**2026-09-19 复核仍未做**
  （证据：`EOS.API/Data/DbConnectionFactory.cs` 全文 17 行、只有 `Create()` 建连接，无 CommandTimeout/耗时埋点/慢查询阈值/失败指标；
  已有的 `ApiMetrics.ObserveWorkbenchQuery`（`Telemetry/ApiMetrics.cs:56`，由 `Data/WorkbenchQueryComposer.cs:144,193,256` 调用）
  只覆盖工作台查询耗时，未落在连接工厂统一层）；
- 日志只记录 SQL hash、耗时和错误码，不记录业务参数值；
- 新表优先使用 `ROWVERSION` 或显式版本字段实现乐观并发；
- 新增时间列优先使用 `DATETIME2` 和 UTC；
- DbUp 迁移保持启动必须成功，同时在发布流程中支持独立迁移步骤；多实例部署时通过数据库级锁
  （如 `sp_getapplock`）确保只有一个执行者，启动迁移与发布期独立迁移步骤的行为保持一致。

## 被否决或暂缓的方案

### 继续在 `DocumentWorkbenchRepository` 上扩展

优点是短期改动小。未选择原因是定义、SQL、命令、审批、范围和审计已经互相缠绕，继续扩展会增加回归风险并阻碍模块放量。

### 每个模块复制一套独立 API

优点是局部简单。未选择原因是会造成大量重复权限、审计、SQL 和前端逻辑，破坏统一 API 边界。

### 只靠人工验收元数据

人工验收适合业务确认，不能替代机器校验。元数据规模持续增长后，错误会延迟到运行时暴露。

### 在前端做权限和范围最终判断

前端权限只改善体验。所有数据范围和操作授权必须由 `EOS.API` 重新执行。

### 用文本日志直接作为 Agent 分析源

文本日志格式不稳定，检索和聚合成本高。Agent 应通过受控 MCP 查询结构化日志，不应直接读取原始文件或生产日志流。

## 结果与影响

### 正面影响

- API 契约、权限判断、数据范围、审计和日志口径统一；
- 元数据错误在发布期暴露，而不是运行期 500；
- Workbench 和规则引擎具备持续放量所需的扩展性；
- 开发 Agent 可以安全、快速地分析日志和定位回归；
- `EOS.Web` 与 `EOS.API` 的边界更稳定，AI 相关组件推倒重建时不需要重写核心业务边界。

### 成本与风险

- 拆分巨型仓储和规则服务需要较大回归投入；
- Definition 快照会增加发布流程复杂度；
- 结构化日志、指标和 MCP 需要新增基础设施；
- 权限缓存需要正确设计失效，否则可能出现短期越权或拒绝；
- 统一审计表会增加写路径存储成本；
- `NOLOCK` 收敛可能暴露既有并发问题。

## 执行准则

- 本决策只约束 `EOS.API` 与 `EOS.Web`；`EOS.Client`、`EOS.Gateway`、`EOS.AgentRuntime` 不因本 ADR 增加实现承诺；
- 任何组件不得绕过 `EOS.API` 访问 `EOS.ERP`；
- 新增数据库对象全大写，并通过 `Migrations` 版本化；
- 动态表名、列名、排序字段、查询字段必须来自服务端 Definition 白名单；
- 动态条件必须参数化；
- 无法确定数据范围时默认拒绝；
- API 是最终权限边界，前端权限判断只改善体验；
- 每阶段完成后更新 `docs/status.md`，涉及计划的事项移入活跃计划或归档。

## 复审条件

出现以下情况时复审本决策：

- `EOS.Web` 需要支持多租户、多语言或多组织架构导致权限模型重大调整；
- Definition 快照无法覆盖特殊管理页或复杂报表需求；
- 统一审计表写入量影响核心单据保存 P95；
- 日志 MCP 的查询模式无法满足开发 Agent 的主要排障场景；
- `EOS.API` 需要拆分为多个服务或引入事件驱动架构；
- AI 相关组件重建后提出新的身份委托或业务调用契约。
