# ADR-045：助手评估用例的库化与权限维护（模块 3106）

- 状态：**已接受并实施**（2026-10-31；迁移 `458`、`459` 已落库，模块 3106 可用）
- 日期：2026-10-31
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-044（助手回答质量的窄判官）、ADR-016（处境感知与任务闭环，缺口 #2 黄金集审阅）、ADR-030（助手参数框架）、ADR-036（共享原语单一真源）、ADR-043（生命周期列命名）
- 取代：本 ADR 取代"评估用例只放仓库文件、靠 git diff 留痕"的旧做法——**用户环境没有 git**

## 1. 背景

评估"尺子"（`EOS.API.Tests/AssistantEval/**/*.jsonl`）此前只存在于仓库：

- 想改一条期望，得改文件、跑测试、提交；
- **交付到客户环境后没有任何入口**：客户那里没有仓库、没有 git、没有 CI，顾问只能找开发商；
- 于是"用户按需调整尺子"这件事在产品上根本不存在。

用户 2026-10-31 明确要的方向：**建表、新增模块、走系统权限，谁能维护由管理员决定**。

## 2. 决策

### 2.1 尺子落库，用"统一表单模块"承载

| 项 | 决定 |
|---|---|
| 表 | `dbo.ASSISTANT_EVAL_CASE`（单表、纯主表；主键 `CASE_ID`，稳定业务标识、不用自增） |
| 模块 | **3106 · 评估用例**（挂在「助手」根节点 31 下，`M_URL=/workbench` + `MASTER_TABLE=ASSISTANT_EVAL_CASE`） |
| 形态 | 统一工作台：列表 + 统一表单增改删 + 选择列 + 导出，**不新增前端页面、不新增写端点** |
| 分层 | `LAYER` 列区分 **9 层**（functional/business/diagnosis/config/authz/inference/situation/action，加判官校准层 `judge`）；层内特有字段进 `PAYLOAD_JSON`，列只承载通用面。`judge` 层**不进仓库种子**：标签必须由人给 |
| 审阅状态 | `REVIEW_STATUS`（`DRAFT/SUBMITTED/APPROVED/RETIRED`）+ `REVIEWED_BY/REVIEWED_TIME`；与生命周期位（`APPROVED/FINISHED`）**分开**——后者只满足框架对单据表的列约定，本模块不接流程 |
| 版本 | `CASE_VERSION` 内容版本；改动历史由**审计**（`AUDIT_EVENT` + `AUDIT_FIELD_CHANGE` 旧值/新值）回看，v1 不建历史表 |
| 首批数据 | 现有 8 个种子文件一次性导入 **169 条**（诊断层 30 条按已审阅 = `APPROVED`，其余 `DRAFT`），来源标 `ORIGIN='official'` |

### 2.2 维护权 = 模块权限（不新造角色）

- 可见性与增/改/删/字段级限制全部走 `SYS_GROUP_MODULE_PERMISSION` / `SYS_USER_MODULE_PERMISSION`，
  由管理员在 **2306「用户权限设定」** 分配；
- **默认不预置任何授权**；唯一例外是给现有 `admin` 账号一条与 3101/3102/3105 同形的授权
  （迁移 459）——否则开箱连管理员自己都进不去，第一次分配无从做起；
- 写路径复用统一表单：权限重判、字段级禁止、审计、并发控制一处不少。

### 2.3 留痕在库，不在 git

用户环境没有 git，因此"谁在什么时候把期望从 A 改成 B"的答案只能来自**库内审计**：

- 每次新增/修改/删除都由统一表单写审计（字段级明细含旧值与新值）；
- 需要给别人看时用列表**导出**（CSV/Excel），不需要仓库；
- **不做"库 ↔ 仓库哈希对拍"**：上一轮曾提议用它防"删样本自证"，但那条防线只在"用同一把尺子做对外发布门禁"时才有意义；
  现在两者的用途已经分开（见 2.4），对拍只会让客户环境的正常调整变成红灯。

### 2.4 仓库里的 jsonl 退化为"离线门禁的输入"

| 用途 | 真源 | 说明 |
|---|---|---|
| **运行期维护**（客户/顾问调整尺子） | **库**（模块 3106） | 可增删改，留审计 |
| **离线门禁**（`dotnet test` 里的评估断言） | **仓库 jsonl** | CI 无库；"没连库就跳过"会变成事实上的不验证，所以必须有随代码走的输入 |
| **发布验收** | 仓库 jsonl | 发布前用仓库那一份跑分，作为"我们这个版本做到了什么"的证据 |

**两份允许漂移，且不追求逐字节一致**。需要把库里的调整回流成仓库基线时，由维护者在开发库上**手工导出一次**
（一次性动作），不设自动对拍——这与 `db/bootstrap` 的导出/对拍是两件不同的事：
那套产物是"建库基线"，要求可复现；评估用例是"随业务成长的尺子"，要求可调整。

## 4. 明确不做

1. **不做跑分界面**：用例维护是配置面；跑分仍是离线门禁与发布动作，不在产品里开入口；
2. **不做库 ↔ 仓库对拍**（见 2.3）；
3. **不建历史表**：v1 靠审计回看；审计若被清理策略裁掉而需要长期留痕，再按 §5 复审条件立项；
4. **不新增写端点**：一切经统一表单，助手侧也不例外（可代理面仍受 `AGENTS.md` 红线约束）；
5. **不把用例塞进菜单以外的入口**（不进报表中心、不进助手工具面）。

## 5. 复审条件

- 出现"同一条用例在不同客户/环境期望不同" → 加 `SCOPE` 列（客户/环境维度），并按 `(SCOPE, CASE_ID)` 调整主键；
- 审计保留期短于"需要回看的年限" → 立项历史表（`ASSISTANT_EVAL_CASE_HISTORY`）；
- 用例规模过千 → 为 `LAYER/REVIEW_STATUS/ORIGIN` 的组合查询与列表分页重估索引；
- 需要"改完立即生效于发布验收" → 那时才讨论自动导出/对拍，且只在**开发库**适用。

## 6. 与 ADR-044 的关系

- 本 ADR 管**期望**（尺子）：一条用例说"这个问题应该被这样回答/这样归因"；
- ADR-044 管**实测**（判官 verdict）：对已落库回答按条款判 PASS/FAIL；
- 两者的数据都不写进对方：judge verdict 不成为用例，用例也不因 verdict 自动改判。
  唯一交集是"质量看板"里的聚合展示。
