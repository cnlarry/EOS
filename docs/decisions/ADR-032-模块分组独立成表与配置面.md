# ADR-032：模块列表分组独立成表与配置面

- 状态：**已落地**（迁移 `341`（建表 + 搬数 + 删 15 列 + 登记 2315）与 `342`（2315 改判为定制承载页）；
  同一批交付：配置面页面与读写端点、读侧端点换 `groupId`）
- 日期：2026-10-09
- 相关：ADR-019（模块管理拆分——本次是它的续集：把"配置了要发布才生效"的东西搬出 2301）、
  ADR-021（配置面白箱化）、ADR-022（模块级表单版式，同为"保存即生效"的配置面）、
  ADR-004（数据库受控迁移）、`LESSONS.md` L27（`MODULES` 无默认值的 bit 列）

## 1. 问题

列表分组（工作台列表右上角的下拉筛选）原本是 `MODULES` 上的固定 5 组列：

```
GROUP1..5  bit            启用位
GROUP_EXP1..5  nvarchar   分组表达式（受控子集）
GROUP_DESC1..5 varchar    下拉里显示的名字
```

三处结构性问题：

1. **上限由列数写死**：一个模块最多 5 组，想要第 6 组就得加三列、改四种下标循环。它是数据模型而非业务约束；
2. **"第几组"同时是排序与身份**：读取侧一律按下标偏移取值（`9 + i*2`、`11 + i*3`、错误码 `GROUP{i+1}`、
   `definition.GroupExpressions[index - 1]`），前端深链也用 `?groupIndex=1..5`。序号一变，同一链接就指向
   另一个表达式；
3. **配置面与生效时机错配**：配置写在 2301 模块管理里，而 2301 的保存要**走发布**才生效（模块定义快照）。
   可分组表达式偏偏是**不进快照**的那类配置（见 §3），于是"在 2301 改完还得去别处点一次发布"——
   一步操作的意思与它的实际效果不一致。

## 2. 决策

**分组独立成表 `MODULE_GROUPS`，配置面独立成模块 2315「模块分组」。**

| 列 | 说明 |
|---|---|
| `GROUP_ID` | `IDENTITY(1,1)` 主键，**分组的身份** |
| `M_IDX` | 归属模块（`MODULES.M_IDX`；编号变更时随 `MenuAdminRepository` 的级联语句一并改指） |
| `SORT_IDX` | 同一模块内的先后顺序——只是排序，不是身份 |
| `GROUP_DESC` | 分组下拉上显示的名字 |
| `GROUP_EXP` | 分组表达式（`GroupExpressionParser` 受控子集，字段白名单 = 模块主表的物理字段） |

配置面是**定制承载页**：模块 2315「模块分组」（`M_URL = /admin/module-groups`，迁移 342 定形态），
页面为 `EOS.Web/src/features/admin/ModuleGroupsPage.tsx`，读写端点 `api/v1/admin/module-groups`
（`ModuleGroupAdminController`：读 `CanBrowse`、写 `CanSetup`，写后留审计）。授权行按 2301 镜像
（同一批配置维护者）。

**为什么不是普通工作台模块**（2315 在 341 里曾是，342 改掉了）：

1. 通用表单只能维护 `MODULE_GROUPS` **自己**的行，表达不了"为**其它**模块配置分组"这件事——
   而那正是这个配置面的全部内容；页面需要"选一个模块 → 看它主表的可用字段 → 编它的表达式"，
   这是通用表单给不了的；
2. 工作台的保存要走模块定义快照与发布，而分组配置本来是**保存即生效**的（见 §3）——
   把它留在工作台形态里，"保存"这一步的意思与实际效果不一致；
3. 定制页意味着可以只暴露该有的动作（新增/编辑/删除/排序），并按目标模块的形态给出明确拒绝理由。

形态一改，三类"只对工作台形式有意义"的东西随之失效并同迁移清掉：`MODULE_GROUPS` 的 `FIELDS` 登记与
`FIELD_DATASOURCE` 行（**系统配置表不进字段目录**，先例 `MODULE_FORM_TAB`）、2315 上的工作台配置与
`SEARCH_*`、它的脏标记与非当前快照。2315 也从统一表单写名单里移出（名单是写路径的门，只收工作台模块）。

## 3. 为什么拆出去：它本来就不该等发布

分组表达式在装配工作台定义时**实时读取**（`WorkbenchDefinitionBuilder.ReadGroupExpressionsAsync`），
`WorkbenchDefinition.GroupExpressions` 带 `[JsonIgnore]`、**从不进快照**——这条性质在改造前就成立
（表达式是高风险的受控串，冻结进快照等于让它绕开"随字段保存即校验"的口径）。

也就是说：**改变分组从来不需要发布**，只有"分组配置住在 2301 里"让人以为需要。把它拆成独立模块后，
"保存即生效"是界面与机制一致的事实，而不是一句需要解释的例外。副产品：2315 不进发布流程，
也就不会进脏标记与快照落后清单。

## 4. 为什么不留"启用位"

原方案要三道门齐备才生效：启用位 = 1、表达式非空、描述非空（`NavigationGroupsRepository` 旧实现）。
但**未启用的行不产生任何界面效果**——留着启用位等于让同一件事有两个真源：行在不在，与行算不算数。

新口径是 **"有行即生效"**（行存在且两列非空即可用）。代价是失去了"先配好、暂时不启用"这个用法；
判据是：这不是一个正在被使用的用法（库内实测 16 个模块填过表达式，其中 14 个从未启用、界面从未显示过它们），
为一个假设需求留一个开关，会换来"配了不生效"这类最难排查的现场。

**搬迁口径随之一致**：只搬当时**真正生效**的行（2 个模块共 4 行）。那 14 个模块的历史残留表达式不搬——
搬过去会因为"有行即生效"而突然出现在列表分组里。

## 5. 为什么身份是 `GROUP_ID` 而不是序号

`?groupIndex=N` 的问题是**静默漂移**：调序或删除一个分组后，旧链接照常能打开，只是筛选条件换成了另一个
表达式——结果变了而链接没变。改用 `GROUP_ID` 后，深链要么命中同一个分组、要么干脆被拒（403
`GROUP_EXP_UNSUPPORTED`），不会悄悄换成别的意思。

这与本仓既有纪律同源：**编号是排序键，不是身份**（迁移编号那条）。序号保留为 `SORT_IDX`，只决定下拉顺序。

## 6. 契约变更（外部需跟着改）

| 变更 | 影响面 |
|---|---|
| `MODULES` 卸下 15 个分组列 | 任何直接读这些列的程序；同时删除 `FIELDS` 里 `T_ID='MODULES'` 的 15 行分组元数据 |
| `GET /api/v1/admin/menus` 的模块投影 | `MenuAdminModule` 不再返回 15 个分组字段 |
| 工作台 `/records`、`/query`、`/export`、`/export-selected` | 查询串参数 `groupIndex` → **`groupId`** |
| `GET /api/v1/navigation/{moduleId}/groups/{groupId}/values` | 路径段 `{index}` → `{groupId}` |
| `/api/v1/app/bootstrap` 的 `NavigationItem.groups[]` | 元素 `{ index, description }` → `{ groupId, description }` |
| 2301 模块管理页 | 删除「分组」页签（页签集从 7 个变 6 个） |
| 模块 2315 | 由统一工作台模块改判为**定制承载页** `/admin/module-groups`（迁移 342）；移出统一表单写名单；`MODULE_GROUPS` 的字段登记与数据来源删除 |
| 新增配置端点 | `api/v1/admin/module-groups`（`GET {moduleId}`、`GET {moduleId}/fields`、`POST {moduleId}`、`PUT/DELETE {moduleId}/{groupId}`、`POST {moduleId}/{groupId}/move`），门挂在 2315 |
| 新增选择器数据源 | `module-groups.targets`（候选 = 统一工作台模块，门挂在 2315） |

拒绝口径不变：分组编号不存在、表达式为空、表达式超出受控子集，一律 403 `GROUP_EXP_UNSUPPORTED`
并计 `workbench_scope_rejected_total{reason="group_expression"}`。**不区分这三者**——区分等于告诉调用方
别处配置的存在性（防探测口径见 [04-API契约与前后端协作](../guide/04-API契约与前后端协作.md)）。

## 7. 顺带补上的一块隐患

`MODULES` 剩下的 bit 标志列（`M_TAG` / `DETAIL_NO_SAVE` / `SEARCH_1` / `SEARCH_2` / `IF_COPY`）都没有
`DEFAULT`，新建模块漏填即 NULL，而读取侧按 `GetBoolean` 取值会当场 500（`LESSONS.md` L27）。
分组列下线后它们就是仅剩的风险面，故在同一支迁移里补上 `DEFAULT`。
（显式写 `NULL` 仍能写出 NULL，读取侧"NULL 当 0"的口径不变——由
`MenuAdminRepositoryIntegrationTests.可空标志位为NULL时列表照常返回` 守着。）

## 8. 刻意不做

- **不做"分组发布"**：分组不进快照，也不引入任何形式的发布/预演步骤（见 §3）；
- **不做分组值缓存**：`GET .../values` 每次实时查（`DISTINCT TOP 500`，按值倒序），不新增缓存层；
- **不给报表/助手单开一套分组读取**：分组只有两个消费面（工作台列表筛选、引导数据的 `groups[]`），
  都走 `MODULE_GROUPS` 同一处真源；
- **不设报表级或用户级分组 override**：与报表可见性同一条纪律——"逐处再配一次"就是造第二处真源。
