# ADR-029：用户问题反馈与一键日志打包（受权打包 + 可追溯反馈入口）

- 状态：**已接受（2026-09-29 用户拍板）**——定为**独立定制页「日志管理」**（不走工作台），
  权限锚点为模块 **11**（基础设置）；裁决见 §9
- 版本：v1（2026-09-29）
- 日期：2026-09-29
- 决策者：用户（Larry）+ 开发 Agent
- 拍板记录：2026-09-29（用户逐条裁决，见 §9）
- 相关：ADR-025（脱敏与关联键，**硬前置**）、ADR-026（产品版本，诊断包需携带）、
  ADR-027（日志保留策略决定诊断包能拿到什么）、ADR-028（异常追踪与"复制诊断信息"）、
  ADR-005 §5.1（禁止记录清单）、决策 **#52**（日志 MCP 拆除，排障 SOP = 文件直读 + mssql）
- 范围：`EOS.API/Controllers/`、`EOS.API/Features/`（新诊断能力）、`EOS.API/Program.cs`、
  `EOS.Web/src/features/`、`EOS.Web/src/components/`、`.github/`（如新增 Issue 模板）

## 摘要（先读我，写给人类）

**要解决的问题**：用户遇到问题时，**没有任何入口**，也没有任何"把现场交给维护者"的手段。

现状（实测）：

- **反馈入口 = 0**：无 `.github/`、无 Issue 模板、前端无反馈/帮助/关于页；
  `CONTRIBUTING.md:39` 只有一句"请先开 issue"，README 全文无 Issue 链接与邮箱；
- **一键日志打包 = 0**：后端**没有任何读取 `logs/` 目录的端点**，全仓**无 zip 能力**
  （`ZipFile`/`ZipArchive`/`Compression` 零命中）；
- 前端只能上报未捕获异常（字段少、不含关联键与版本，见 ADR-028）；
- 可复用的资产：附件通道（含 `.zip` 白名单、路径穿越防护、`PhysicalFile` 下载、权限门）、
  共享可读的日志文件（`FileShare.ReadWrite`）、诊断端点（`/health/version`、`/health/ready`、`/metrics`）、
  `AUDIT_EVENT` 查询端点。

**本 ADR 的决定，用一句话说**：

> **在服务端做"受权、限范围、先脱敏、可审计"的诊断包下载；前端只做一件事——把用户的描述与
> 关联键交给这个端点，把 zip 拿回来。**

**边界（同样重要）**：

- 诊断包**不是**数据导出：只含日志白名单 + 环境元数据，**不含业务数据、不含审计明细原文**；
- 不是"自动诊断"：系统不替用户判断问题原因；
- 不把日志目录暴露成静态资源，不新增"任意路径下载"这类通用文件端点。

### 1.2 硬约束

1. **ADR-025 未落地前不得开放打包端点**（否则等于把未脱敏日志外发）；
2. **权限门 fail-closed**：诊断包含日志与内部元数据，必须按既有权限语义判定
   （`IPermissionService` + 模块门），未授权一律拒绝（403，不是 401）；
3. **白名单外一律不打包**：不做"按路径参数取任意文件"的通用端点；文件名只来自服务端枚举；
4. **诊断包不得包含**：连接串/口令/密钥、`appsettings.Development*.json`、附件正文、
   数据库业务数据、`AUDIT_FIELD_CHANGE` 原文；
5. 打包动作**必须可审计**（谁在什么时候打包了哪一类诊断包）；
6. 打包不得阻塞请求线程（同步/异步边界明确），单次体积与时长上限明确；
7. 不引入新的长驻进程/外部服务（沿用决策 #52 的取向）。

## 2. 决策

### 2.1 端点形态：`POST /api/v1/diagnostics/bundle`（受权、即时生成、流式返回）

- **请求**：用户描述（限长）、可选复现步骤、可选关联键（默认取当前请求上下文）、
  可选日志窗口（"最近 N 小时 / 全部"）；
- **响应**：`application/zip` 附件流（文件名含服务器生成的时间戳与短关联键，
  **不使用用户输入拼接文件名**）；
- **权限**（2026-09-29 拍板定死，见 §9）：
  - **读日志与看诊断信息**：模块 **11**（基础设置，日志所在模块）的 **CanBrowse**
    ——与既有 `AuditController`（`Controllers/AuditController.cs:21,35`）同一锚点，
    **拥有该权限的系统用户即可读系统日志**；
  - **打包下载**：同一模块的 **CanSetup**（比"看"更高一档：打包会把日志带出服务器）；
  - 未授权一律 **403**（不是 401、不是 500）；
- **限流/限量**：单次打包体积上限（建议 100MB，可配置）、超限则返回可读错误而不是截断 zip。

### 2.1.1 载体：独立定制页「日志管理」（不走工作台）

- 路由建议 `/admin/logs`（与既有定制页 `/admin/field-audit`、`/admin/tables` 同族），
  前端 `RequirePermission(moduleReadPermission(2313))`；
- 页面能力：日志条目列表（按级别/时间/关联键/模块过滤）+ 诊断信息（版本、构建时间、
  是否"跑的是旧程序"、健康检查结果）+ **一键打包下载** + "复制报障编号"；
- **不**把日志做成工作台模块（工作台由库内元数据驱动、面向业务单据，日志不是业务数据）。
- **权限真源 = 本页自己的模块 `2313`**（2026-09-29 重编号拍板，见下）：页面路由守卫、
  服务端接口门（读 = `CanBrowse`、打包 = `CanSetup`）与菜单可见性三者同锚一个模块，
  不再出现"菜单看一个模块、接口看另一个模块"的双真源。

> **重编号（2026-09-29 用户拍板）**：本页初版按 283 迁移挂在 **`110112`（基本参数 → 系统参数）**
> 之下，与「定制页一律落 `/admin/*`、而 `/admin/*` 都属 23 系统管理」的既有惯例不符，
> 且接口权限另锚在模块 `11`（与 `AuditController` 同锚点）。经拍板改为
> **`2313`（系统管理 23 → 数据表维护 2311 → 日志管理，`SORT_IDX=40`）**，
> 接口锚点一并由模块 `11` 改为 `2313`，**`11xxxx` 旧编号不再保留**（迁移 284 退役）。
> `2313` 的授权行按模块 `11` 与 `110111` 两套授权的**并集**逐主体复制，
> 故重编号前后"谁能读、谁能打包"完全等价（个人权限覆盖组权限，漏搬任一侧都会静默少授权）。

### 2.2 诊断包内容（白名单，逐项可断言）

| # | 条目 | 说明 |
|---|---|---|
| 1 | `logs/api-json.log` 及轮转副本（在保留窗口内） | **唯一**的日志来源；已过 ADR-025 脱敏 |
| 2 | `diagnostics.json` | 产品版本（ADR-026）、commit、构建时间、进程启动时间、环境名、`stale` 标志（来自 `/health/version` 的同一实现，**复用而非另算**） |
| 3 | `health.json` | `/health/ready` 与 `/health/startup` 的逐项结果（含迁移是否成功） |
| 4 | `migrations-summary.json` | 迁移台账摘要：已执行脚本数、最后一个脚本名、是否有磁盘上不存在的记录（**不导出全文**，可选，见 §8-4） |
| 5 | `config-digest.json` | **只含键名与是否已设置**的配置摘要（日志级别、保留参数、路径、开关类），**不含任何值中可能带凭据的项** |
| 6 | `manifest.txt` | 打包时间、包含文件清单与各自大小、脱敏声明（"日志已按 LogRedactor 模式清单脱敏"） |

> **注意（部署包无 `.git` 的降级）**：`/health/version` 的 `commit`/`buildTimeUtc` 依赖构建机上存在
> `.git`（`EOS.API.csproj:47-60` 的条件），部署包解压部署时会双双为 `unknown`。
> 因此诊断包的版本标识**以 ADR-026 的 `version.json`（编译进程序集）为准**，`commit` 作为附带信息，
> 缺失时在 `manifest.txt` 中显式标注 "unknown（构建环境无 .git）"。

**明确排除**：`appsettings*.json` 原文件、`AUDIT_FIELD_CHANGE`/`AUDIT_EVENT` 原文、`db/`、
附件目录、`EOS.Web` 源码、任何 `.git` 内容。

### 2.3 打包实现：流式 zip 到响应，不落中间文件

- 用 BCL 的 zip 能力流式写入响应（**不新增第三方依赖**）；
- **容忍轮转竞态**：读取单个文件失败不使整包失败，在 `manifest.txt` 中标注
  "该文件在打包瞬间不可读"；
- **不复制**到临时目录（避免把日志落到第二个位置，也避免磁盘翻倍）；
- 生成过程不写业务库（除审计外）。

### 2.4 反馈入口（前端 + 仓库）

1. **前端"反馈/诊断"对话框**（落点见 §8-2）：
   - 字段：问题描述（必填，限长）、复现步骤（选填）、关联键（预填，可编辑）、
     是否包含最近日志（默认是，可关）；
   - 动作：一键生成并下载诊断包；生成成功后展示"已包含哪些内容 / 已做哪些脱敏"的说明；
   - **不做**：自动上传到任何外部服务（无外网通道，且违背数据不出内网的取向）。
2. **"复制诊断信息"入口**：与 ADR-028 §2.2 同一实现，避免两套。
3. **仓库侧**：新增 Issue 模板（`.github/ISSUE_TEMPLATE/bug_report.yml`），字段包含
   "版本（来自诊断包 manifest）""关联键""是否已附诊断包"；`CONTRIBUTING.md` 与 `README.md`
   补上唯一的反馈入口链接与"如何生成诊断包"的三步说明。
   > 注意：新建 `.github/` 会改变仓库结构，属**需用户单独确认**的动作（§8-1）。

### 2.5 与既有资产的关系

- **不**把诊断包当作附件入库（附件是业务单据的附属物，有 SHA-256 与单据键，诊断包无单据归属）；
- 复用附件通道的**安全范式**（受权 + 服务端文件名 + 路径穿越防护），但不复用其存储模型；
- 排障 SOP 更新：`AGENTS.md`「排障」增加一条"用户提交诊断包时，按 `manifest.txt` 核对版本与
  关联键，再进日志/审计"。

## 4. 已知后果

**正面**

- 用户报障从"描述一段话"变为"附一个可追溯的诊断包"；
- 维护者拿到的第一个事实是"版本 + 构建时间 + stale 标志 + 迁移状态"，能直接排除
  "跑的是旧二进制"（本仓库实测存在此现象：二进制 `ff53f03` ≠ HEAD `860192b`）；
- 打包动作有审计，谁取走了什么可追溯。

**负面 / 风险**

- **(a) 隐私边界靠白名单与脱敏双重保障，任何一处松动即成事故**：因此 D0 是硬前置，
  且验收必须包含"故意向日志写入一个凭据形态的字符串，断言诊断包里只有掩码"。
- **(b) 日志本身可能含业务信息**（用户备注、单据号出现在 Warning 级业务告警里）：
  脱敏只处理凭据形态，**不处理业务数据**。缓解：对话框里明确告知"诊断包含最近日志，
  可能含业务数据，请确认后再提交"；不默认上传（本 ADR 就不上传）。
- **(c) 打包是 IO 密集操作**：43MB 起，可能到 150MB；并发多次打包会放大磁盘与网络压力。
  缓解：体积上限 + 审计 +（可选）单用户并发限制；**不引入后台队列**（无长驻服务）。
- **(d) 不给"自动诊断结论"**：用户可能期望"点一下告诉我哪里错了"——本 ADR 明确不做，
  避免把猜测包装成结论。
- **(e) `.github/` 与 Issue 模板是新增仓库结构**：属流程性变更，需用户单独拍板；
  若不采用，反馈流程仍成立（用户手动把诊断包发给维护者），只是失去公开追踪入口。

## 5. 替代方案

| 方案 | 未选择原因 |
|---|---|
| 把 `logs/` 目录做成静态可下载（或加 `UseStaticFiles` 子路径） | 无授权、无脱敏、无范围限制：等于把内部日志公开；且绕过审计 |
| 让用户手工从服务器拷贝日志 | 用户是业务人员，通常无服务器访问权；实际操作不可行（这正是本 ADR 的动机） |
| 用附件通道上传诊断包（复用现成端点） | 附件必须挂在某单据的键上（路由含 `{moduleId}` + 主键），诊断包无单据归属；且会进业务附件表，污染业务数据 |
| 新增"通用文件下载"端点（传路径） | 路径穿越风险最高的一类设计；与"白名单"原则相悖 |
| 引入外部错误上报/诊断 SaaS | 需外网与数据出境，与单机部署取向冲突（同 ADR-028 §5） |
| 用户点一下就自动上传到维护者 | 无外发通道；且未经确认外发可能含业务数据 |
| 把诊断包同时落库留存 | 会把日志复制进被排障对象（库），违背决策 #52 的取向 |

## 6. 验收标准

1. **范围严格**：解包后**只有**白名单 6 项（或更少），无 `appsettings*`、无 `AUDIT_*` 原文、
   无业务数据文件；
2. **脱敏可判别（正反例）**：故意写一条含 `Password=…`/`Bearer …` 的日志 → 包内为掩码；
   正常的业务中文日志 → 原样保留；
3. **权限**：无诊断权限的账号请求 → **403**（不是 401、不是 500）；未登录 → 401；
4. **不可穿越**：任何构造的文件名/路径参数都无法让包内含白名单之外的文件；
5. **轮转容忍**：打包瞬间删除轮转文件不导致整包失败（可用测试构造）；
6. **可审计**：每次打包产生一条可检索的审计/日志记录（谁、何时、包含哪些文件、体积）；
7. **体积与性能**：150MB 输入下打包不超时（阈值由 §8-5 定），响应头带正确长度或分块；
8. **UI 可用**：非管理员/授权用户点得开对话框、拿得到 zip；文案明确包含内容与隐私提示；
9. `dotnet build` 0 错、`npm run lint`/`npm run build` 0 错、新增单测全绿。
