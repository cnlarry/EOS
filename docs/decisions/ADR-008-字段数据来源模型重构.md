# ADR-008：字段数据来源（数据选取）模型重构

- 状态：已接受（2026-08-28 用户拍板，尚未实施）
- 日期：2026-08-28
- 决策者：用户（Larry）+ 开发 Agent

## 背景

字段设置是系统核心功能。旧系统在 `FIELDS` 表上用**四组固定列**表达「数据来源（数据选取）」：

```
CHOOSE_ACTIVE1-4, CHOOSE_T_ID1-4, CHOOSE_T_DESC1-4, CHOOSE_M_IDX1-4,
CHOOSE_FILTER1-4, CHOOSE_RETURNVAL1-4        （共 24 列）
```

两个结构性缺陷：

1. **把数组塞进列**：每个字段最多 4 个数据源，是物理写死的上限；新增/调整必须改表结构。
2. **结构无约束**：`CHOOSE_FILTER`（过滤条件）是手写 SQL 字符串、`CHOOSE_RETURNVAL`（回填映射）是 `target=column` 逗号串，靠 `DataFilterParser` 运行期解析 + fail-closed 兜底。**该 SQL 不是注释，是运行时真实参与计算的过滤条件**（`GetChooserOptionsAsync` 把它编译进选择器查询 WHERE，与模块 FILTER/DATA_FILTER/EXEC_TAG 叠加，见 `DocumentWorkbenchRepository.cs:1010`）。手写串的校验只能事后做，且 `CHOOSE_RETURNVAL` 跨模块死映射已发生过一次批量清理事故（EOS-22 迁移 009）。

同时，现代统一表单消费多数据源的语义与旧系统不一致：新系统 `FormEditorPage.tsx:450`/`formEditorUtils.ts:110` 用 `choosers.find(item => item.active && item.table)` **只取第一个启用的数据源**；而旧系统是**多来源并存、各是各的入口**——用户点开选择器时若字段有多个来源，先弹菜单选来源（如送货单明细：可选出货排程，也可选出货通知单，打开的是两个不同的选择器）。

项目处于开发阶段、无受影响的客户，是重构该模型的唯一合法窗口期。

## 决策

### 1. 独立数据源表 `FIELD_DATASOURCE`（替换 FIELDS 四组列）

数据源成为一等实体，任意数量、有序、可审计。DbUp 版本化迁移建表（对象名全大写，EOS.ERP 内）：

```
FIELD_DATASOURCE (
    ID              INT IDENTITY(1,1) PRIMARY KEY,
    T_ID            NVARCHAR(300) NOT NULL,      -- 所属字段表（FIELDS 主键）
    F_ID            NVARCHAR(300) NOT NULL,      -- 所属字段
    SERIAL_NO       INT            NOT NULL,     -- 顺序 1..n（来源菜单显示顺序）
    ACTIVE_TAG      BIT            NOT NULL,     -- 启用
    SOURCE_T_ID     NVARCHAR(300)  NOT NULL,     -- 来源表
    SOURCE_DESC     NVARCHAR(50),                -- 来源说明（多来源菜单显示名）
    SOURCE_M_IDX    INT,                         -- 来源模块（数据范围/权限门，EXEC_TAG 数据范围）
    FILTER_STRUCT   NVARCHAR(MAX),               -- 结构化过滤条件（JSON，见 §3）
    RETURN_ITEMS    NVARCHAR(MAX),               -- 有序回填映射（JSON 数组，见 §4）
    CREATE_BY / CREATE_DATE / LAST_UPDATE_BY / LAST_UPDATE_DATE,   -- 审计
    CONSTRAINT UQ_FIELD_DATASOURCE UNIQUE (T_ID, F_ID, SERIAL_NO)
)
```

- `FOREIGN KEY (T_ID, F_ID) REFERENCES FIELDS(T_ID, F_ID) ON DELETE CASCADE`：
  字段维护（2302）删除字段即级联清数据源定义，不再需要逐引用表清理。
- **字段级选择器行为列保留在 FIELDS**，不属于数据源条目，不迁移：
  `CHOOSE_PAGE`（自定义数据选择页面）、`CHOOSE_MULTI`（支持多笔选入）、`ONLY_CHOOSE`（数据仅可选入）。

### 2. 多数据源语义：各是各的入口（修正 find() 行为）

复刻旧系统真实语义，运行时不再「取第一个启用」：

- 前端 `onChoose`：取 `field.choosers.filter(c => c.active && c.sourceTable)`；
  - 恰好 1 个 → 直接打开该来源的选择器；
  - 多个 → 先弹**来源菜单**（显示 `SOURCE_DESC`，缺省显示 `SOURCE_T_ID`），用户选中后打开对应来源的选择器；
  - 0 个 → 无选择能力。
- 每个来源携带自己的 `sourceTable` / 结构化条件 / 回填映射请求 `form-chooser` 端点；
  端点契约不变（仍按单来源 table 查询，一次请求一个来源），服务端 `GetChooserOptionsAsync` 的
  权限/数据范围（模块 FILTER、DATA_FILTER、EXEC_TAG、成本/保密/禁止字段）对每个来源分别生效。
- 独立表的 `SERIAL_NO` + 任意数量因此有了真实产品价值：数据源是「同一字段的多个可选录入通道」，不是旧上限 4 的延续。

### 3. 过滤条件：纯结构化，消灭手写 SQL

**推翻「结构化 + 原始 SQL 双通道」草案。** 既然彻底重构，过滤条件只有一种存储——结构化条件集
（`FILTER_STRUCT` JSON），运行时由受控编译器生成参数化 SQL。不做「存 SQL 串 + 可逆解析」的往返
（`DataFilterParser` 覆盖的 `ISNULL(列,0)=0`、`DATEDIFF`、`NOT(...)`、跨表 JOIN、`{m.FIELD}` 模板
做无损反向 AST 成本极高且永远追不上）。

**执行路径**：

- 保存路径：`ChooserFilterValidator` 保存即校验——来源表物理列存在、字段类型匹配、算子合法、
  模板占位符可解析、跨表字段引用在 JOIN 白名单内；**模型表达不了的条件拒绝保存并给出可读提示**
  （fail-closed），不留 SQL 后门。
- 运行路径：`ChooserFilterCompiler` 把 `FILTER_STRUCT` 编译为参数化谓词 + 可选 JOIN，再与
  `WorkbenchScopeFilter` 的模块范围谓词（FILTER/DATA_FILTER/EXEC_TAG）AND 叠加；
  `DataFilterParser` 保留用于模块 `FILTER` / `DATA_FILTER`（旧表达式字符串，不在本重构范围）。

**结构化条件模型（第一版契约）**：

```json
{ "logic": "AND", "items": [
  { "field": "CLIENT_ID", "operator": "EQ", "value": "{m.CLIENT_ID}" },
  { "field": "BUSINESS_TAG", "operator": "EQ", "value": "1" },
  { "field": "STOP_TAG", "operator": "EQ", "value": "0" }
] }
```

- 算子：`EQ / NE / GT / GE / LT / LE / LIKE / NOT_LIKE`；显式宏算子覆盖旧系统高频写法：
  `ISNULL_ZERO`（`ISNULL(列,0)=0`）、`DAYS_FROM_TODAY`（`DATEDIFF(day,列,GETDATE())`）；
- 跨表字段用 `表.列` 全名，须在 `ChooserJoinTables` 白名单（沿用现有跨表 JOIN 白名单）；
- `value` 支持 `{m.FIELD}` / `{d.FIELD}` 主表/明细模板占位符（沿用现有参数化替换语义）；
- 第一版平铺 + 顶层 `logic`，嵌套分组视实施反馈再评估（复审条件登记）。

### 4. 回填映射：有序结构对（消除逗号串手写解析）

`RETURN_ITEMS` 存有序 JSON 数组：

```json
[ { "target": "CLIENT_ID", "column": "CLIENT_ID" },
  { "target": "CLIENT_NAME", "column": "CLIENT_NAME" } ]
```

- `target`（表单目标字段）落库前经 `NormalizeChooserTarget` 统一化（去 `txt_/cho_/dro_/chk_/lab_/hidd_` 前缀）；
- 目标字段只能从「主表∪子表模块字段集」选取（复用 `WorkbenchDefinitionValidator` 现有判定逻辑），
  从源头杜绝 EOS-22 那类跨模块死映射复发；
- 来源列允许来源表物理列（`sys.*` 白名单）或来源表内受控虚拟列
  （`FIELDS.IS_VIRTUAL=1` 且 `VIRTUAL_EXP` 非空，运行期经受控解析后经 `QUERY_RELATION` JOIN 求值；
  对齐旧语义——旧系统来源查询结果集本就包含 `VIRTUAL_EXP` 派生列，如 `CLIENT.SALES_NAME=SYSDN.EMP_NAME`）；
  既非物理列也非受控虚拟列才判为“来源表不存在的列”；
- 运行时 `GetChooserOptionsAsync` 的「回填列优先显示」逻辑改为消费 `RETURN_ITEMS`（原 `ParseReturnMapping` 解析退役）。

### 5. 字段设置 UI：统一选择器选表 + 两步式构建

`FieldEditorModal`「权限与备注」页签数据来源区整体重构：

- **来源列表**：数据源条目可增删、排序（拖拽/上下移）、启停，数量不限；
- **第一步选表**：来源表用 `UnifiedChooser`（`sourceKey`，仿 `menu-admin.tables` 注册，权限门 2302），
  禁止 datalist 自由输入；选中后来源说明可由服务端带出表描述，减少手填；
- **第二步构建**：每个来源内按「过滤条件构建器（结构化条件，字段白名单 + 算子 + 值 + AND/OR）→
  回填映射构建器（来源列 ↔ 目标字段配对清单）」两步式；不复用裸 `textarea`。
- 多来源时 `SOURCE_DESC` 即来源菜单显示名，编辑时可见可改。

### 6. FIELDS 旧列物理删除（决定有迹可查）

**24 列全部物理删除**（`CHOOSE_ACTIVE1-4 / CHOOSE_T_ID1-4 / CHOOSE_T_DESC1-4 / CHOOSE_M_IDX1-4 /
CHOOSE_FILTER1-4 / CHOOSE_RETURNVAL1-4`）。`CHOOSE_PAGE / CHOOSE_MULTI / ONLY_CHOOSE` 保留。

有迹可查的载体：本 ADR + DbUp 迁移历史 + git 历史；迁移脚本内注释说明决策来源。

**迁移内顺序（单一 DbUp 迁移，事务内）**：

1. 建 `FIELD_DATASOURCE`；
2. 存量搬移（`UNION ALL` 展开四组列 → `SERIAL_NO 1..n`，仅搬 `SOURCE_T_ID` 非空的行）：
   - `RETURN_ITEMS`：用 DbUp C# 脚本复用 `FormFieldSelector.ParseReturnMapping` 解析为 JSON
     （等价 SQL `STRING_SPLIT` + `CHARINDEX('=')` 亦可），**无损转换**；
   - `FILTER_STRUCT`：**规则化批量转换（分三档）**——存量实测 1008 个非空条件 / 291 个去重值，
     按「受限反向解析器」分层转换（复用 `DataFilterParser` 的 token 识别能力，只识别本 ADR 结构化
     模型覆盖的语法，识别不了不猜测）：
     | 档 | 语法形态 | 占比（去重 291） | 转换规则 |
     |---|---|---|---|
     | 一 | 纯比较链（`表.列 运算符 值` AND 链 + `{m.X}`/`{d.X}`/`{X}` 模板 + `ISNULL(列,0)=0` 等简单宏） | ≈ 70% | 拆 AND 链 → `{field,operator,value}`；裸列补源表前缀；`ISNULL(列,0)=0` → `ISNULL_ZERO` 宏 |
     | 二 | 需扩展模型算子：`ISNULL(列A-列B,0)>0` 差值表达式、`NOT IN (SELECT ...)` / `EXISTS` 排除子查询、`AND (…) OR (…)` 嵌套组、`DATEDIFF(day,列,GETDATE())` | ≈ 28% | 迁移期先转成「扩展算子」结构化（模型扩展随 P3 编译器一起实现）；结构化模型表达不了的暂存 `FILTER_STRUCT=NULL` 入清单 |
     | 三 | 不可自动转（脏数据/超复杂）：`f_get_*` 自定义函数、字符串拼接 `CAST` 排除逻辑、悬空 `AND`/`OR` 结尾、截断/乱码 | ≈ 4%（约 11 个） | **人工清单**落 `logs/`，顾问用新构建器重建，绝不猜测落库 |
     每一档转换结果都必须过**验证护栏**：转换器产出 STRUCT → `ChooserFilterValidator` 试编译
     （字段存在/类型/算子/模板）→ 与原 `DataFilterParser` 解析结果在抽样数据上**等价对拍**；
     任一不过即降档（二档降人工清单），不静默落库。
   - `ACTIVE_TAG` 取自 `CHOOSE_ACTIVEn`，`SOURCE_M_IDX` 取自 `CHOOSE_M_IDXn`；
3. `DROP COLUMN` 24 列（`CHOOSE_M_IDX1` 上的旧索引随列删除自动移除）；
4. `P_Change_M_IDX`（旧 SP，更新 `CHOOSE_M_IDX1-4`）改写为更新 `FIELD_DATASOURCE.SOURCE_M_IDX`；
   SSDT 快照在 VS 中重新导入刷新。

## 选择理由

- **数组语义必须独立实体承载**：数据源是「同一字段的多个可选录入通道」，固定 4 列是物理写死上限，
  独立表 + `SERIAL_NO` 让数量、顺序、启停、审计都成为一等公民；
- **纯结构化把校验前置到保存时**：字段存在性、类型匹配、算子合法性保存即拒绝，运行期零解析失败，
  消灭「双份真相」漂移；这是「构建式输入」的最终形态，也是彻底重构的意义所在；
- **多源「各是各的入口」是旧系统真实语义**（送货单明细选出货排程或出货通知单），现代 `find()`
  取第一个是语义退化，本次一并修正；
- **无存量客户 = 唯一合法窗口期**：错过再改，存量数据搬移与双轨兼容成本指数上升。

## 考虑过的替代方案

### A：保留四组列，只加构建器

优点：改动小。未选择原因：数量上限、结构无约束、手写串校验只能事后，问题原样保留，治标不治本。

### B：独立表，但条件存 SQL 串 + 结构化双通道

优点：专家手写 SQL 的肌肉记忆保留。未选择原因（用户质疑成立）：双份真相漂移
（结构化改了 SQL 没同步），等于把旧坑换个形式搬回来；运行时维护两条解析路径。

### C：独立表 + 条件 JSON，另留 SQL 后门（原始草案）

未选择原因：同 B；fail-closed 应体现在「模型表达不了就拒绝保存并提示」，而非开放原文后门。

### D：FIELDS 旧列保留废弃 vs 物理删除

物理删除（用户拍板）。保留废弃会在 SSDT 快照、旧 SP、schema 审阅中留下长期噪音，
与「彻底重构」目标相悖；「有迹可查」由 ADR + DbUp 迁移历史 + git 承担，不依赖物理列存留。

## 结果与影响

### 正面影响

- 字段级数据源成为结构化、可扩展、可审计的一等实体；数量不限、顺序显式；
- 过滤条件/回填映射保存即校验，运行期零解析失败，死映射/坏表达式从源头杜绝；
- 多来源入口复刻旧系统真实语义，字段设置输入方式（统一选择器选表 + 构建式）与现代规范对齐；
- 字段删除级联清理，`FieldAdminRepository` 删除路径简化。

### 成本与风险

- **存量 `CHOOSE_FILTER` 约 30% 需人工作业**：实测 1008 个非空条件 / 291 去重——第一档 ~70% 规则化
  直转，第二档 ~28% 待结构化模型扩展算子后转换（随 P3 编译器），第三档 ~4%（约 11 个：脏数据、
  `f_get_*` 函数、字符串拼接排除）必须人工重建；迁移报告落 `logs/` 逐档清单；
- 过滤条件表达力受结构化模型约束：第一版算子清单之外的场景需新增算子（复审条件登记）；
- 代码侧 6 处 API + 6 处前端 + 测试同步改造，需分阶段独立回归；
- `DataFilterParser` 保留（模块 FILTER/DATA_FILTER 仍用），与新增 `ChooserFilterCompiler` 并存，
  需在文档中明确两者边界避免误用。

### 需同步修订的文档

`EOS.API/README.md`（DocumentWorkbench 数据边界、Field Admin）、`EOS.Web/README.md`
（FieldEditorModal、统一选择器表单选择器）、`docs/架构.md`（统一选择器节）、`docs/status.md`
（决策与技术债）、本 ADR 的复审登记；数据字典（`docs/eos-development/`）为生成型，随库元数据自动更新。

## 复审条件

- 顾问实施中发现第一版算子清单无法覆盖真实需求、且频率较高 → 扩展结构化模型算子，不重开 SQL 后门；
- 需要嵌套条件分组 → 评估 `FILTER_STRUCT` 增加递归 `nested`；
- 需要真正意义上的多来源同时展示（如来源页签并列）而非菜单单选 → 重评 `form-chooser` 多来源契约；
- 结构化条件在大数据量选择器上出现性能问题 → 评估谓词缓存/索引。

## 复审登记（P1 实施记录，2026-08-28）

本节登记 P1 编码过程中对 ADR 的落地细化与偏差，均不改变决策方向；作为实施期复审证据。

### 落地细化（实现即生效）

1. **`FIELD_DATASOURCE.T_ID/F_ID` 定为 NVARCHAR(100)**：FIELDS 主键为 (T_ID, F_ID) NVARCHAR(100)，ADR 草案的
   NVARCHAR(300) 无法建 FK，已按 FIELDS 键长对齐。
2. **`FILTER_STRUCT` 语义三态**：`{"logic":"AND","items":[]}` = 显式无过滤；合法条件 = 结构化 JSON；
   **NULL = 存量条件待重建（迁移清单内）→ 运行期 fail-closed（空选项 + 日志）**，绝不把「待重建」当
   「无过滤」放大数据范围。空过滤来源迁移落 empty-items，新保存留空落 NULL（字段设置 UI 有提示）。
3. **v1 编译器/校验器提前到 P1**：ADR 执行计划把编译器放 P3，但 P1 的迁移试编译护栏与运行期消费
   `FILTER_STRUCT` 都依赖它；P1 交付 `ChooserFilterCompiler`（EQ/NE/GT/GE/LT/LE/LIKE/NOT_LIKE +
   ISNULL_ZERO/DAYS_FROM_TODAY）+ `ChooserFilterValidator`（保存即校验）。P3 只扩展第二档算子。
4. **迁移渠道仅 SQL**：ErpDatabaseInitializer 只嵌入 .sql；`FILTER_STRUCT` 三档转换改为**离线 C# 生成静态
   UPDATE + 漂移守卫**（仅当 `CHOOSE_FILTERn` 原文与生成时一致才落库，否则保持 NULL + 记 DRIFT），
   试编译护栏在生成时逐条执行；对拍报告落 `logs/fields-chooser-migration/`（不入库）。档一实测 374 行，
   档二/三 603 行入 `CHOOSER_FILTER_MIGRATION_LOG`（审计/待重建队列，非运行时通道）。
5. **nullSafe 扩展算子**：新增条目级 `nullSafe: "ZERO"|"EMPTY"`（`ISNULL(列,0)`/`ISNULL(列,'')` 再比较），
   覆盖旧高频写法 `ISNULL(列,0) op 值`（如 `ISNULL(HR_EMPLOYEE.STATE,0)<4`）；`ISNULL(bit 列,0)` 合法
   （SQL Server 允许），校验器按「数值 + bit」放行。
6. **`form-chooser` 端点新增可选 `serialNo`**：多来源「各是各的入口」由前端传 `serialNo`，服务端从
   `FIELD_DATASOURCE` 取权威来源（表/条件/回填），不接受前端传表名；缺省取首个启用来源（P1 兼容单来源）。
7. **普通用户脱敏**：`form-definition` 下发的 `choosers.filter` 恒为 null（FILTER_STRUCT 仅字段设置
   CanSetup 可见）；运行期由 `GetChooserSourceAsync` 按 serialNo 重读权威定义。
8. **影响面补充 `WorkbenchCommandHandler.ResolveChooserDisplaysAsync`**：读回显（DisplayOnly 从字段）
   消费 `RETURN_ITEMS`；多来源回显**仍取首个启用来源的映射**（旧系统无「来源记录」，P1 保持该语义，
   待 P3/复审评估是否在数据侧记录来源）。
9. **`P_Change_M_IDX` 是活 SP**（菜单管理模块改号调用），非「旧 SP」；迁移内改写为更新
   `FIELD_DATASOURCE.SOURCE_M_IDX`，签名不变（MenuAdminRepository 调用无需改动）。
10. **快照/脏标记**：迁移对受影响模块（主/子表含数据源行）标 `WORKBENCH_MODULE_DIRTY`；
    `SOURCE_METADATA_VERSION` 纳入 `FIELD_DATASOURCE.LAST_UPDATE_DATE`。
11. **新增 `CHOOSER_FILTER_MIGRATION_LOG` 表**：迁移审计/待重建队列（T_ID/F_ID/SERIAL_NO/原文/档/状态/错误），
    字段设置保存路径对清单内来源做「禁止静默清空」保护（留空保存被拒），P3 按清单回填。
12. **字段维护 UI 过渡（P1）**：来源列表可增删/启停任意数量，过滤/回填仍为文本（结构化 JSON），
    P2 替换为构建器；保存路径只接受结构化 JSON，旧手写 SQL 一律拒绝（fail-closed）。

### 收尾复审登记：MANUAL 存量重转 + BuildJoinClause 闭包修复（2026-08-29）

迁移 017/018/020 执行后的运行期复核发现两处实施缺陷，均已修复；不改变 ADR 决策方向。

1. **`BuildJoinClause` 依赖闭包永不成立（运行期缺陷，已修复）**：原实现要求 JOIN 的 ON 条件两侧
   都在「已选集合」内才可选，而 JOIN 自身 ON 必然引用其别名（`base.col=alias.col`）——任何跨表
   JOIN 永远构建不出来，`GetChooserOptionsAsync` 对**所有跨表过滤选择器** fail-closed（空选项）。
   修复为「反向依赖链最小选择」：先从被引用别名回溯依赖上游表集合，再正向选择（候选集 = 已选表
   ∪ 本 JOIN 别名）。单测 `ChooserJoinCatalogTests` 5 例防复发（自引用 ON / 传递链只拉依赖 /
   常量条件 / 不可达返回 null / 空引用返回 null）。
2. **018 离线管线按行非确定性传错源表（迁移缺陷，已重转修复）**：同一（原文, 源表）组合 52 行
   成功 / 14 行失败并存；约八成 MANUAL 行实为「源表名前缀自引用」（如 OWNER 字段源表=SYSDL、
   条件 `ISNULL(SYSDL.ACTIVE_TAG,0)=1`）被误判为跨表死配置挂起。库内提交的转换器/编译器对自表
   引用处理正确（`ResolveColumn` 有「显式表名==源表」分支），缺陷在未入库的离线驱动。
   修复：工具 `EOS.API.Tests/ChooserBackfillRerunTool.cs`（rerun/parity/triage 三模式，提交入库
   可复现）以 `FIELD_DATASOURCE.SOURCE_T_ID` 为权威源表重转，生成迁移 021（漂移守卫：原文一致且
   FILTER_STRUCT 仍为 NULL 才落；日志状态收敛——本次回填行 + 017/018 已落结构但状态滞留行；受影响
   模块标脏；同事务）。护栏：转换 → 编译 → JOIN 闭包可构建 → 物理表/列存在，逐级 fail-closed。
   **新旧对拍校验**：452 行同参数绑定（模板列从源表取样、{module} 取 SOURCE_M_IDX）只读对拍
   「旧 CHOOSE_FILTER 原文 vs 新编译谓词」键集，**424 MATCH / 0 MISMATCH** / 28 UNTESTABLE
   （对拍绑定类型转换问题，非转换语义问题，报告中列明人工复核）。
3. **收尾口径（500 行 MANUAL）**：229 行本次回填 + 222 行既有结构与重转一致仅收敛日志 + 1 行
   既有结构与重转存在表示差异（`SYS_WORK_TASK.W_M_IDX`，人工复核）+ 48 行仍待处置
   （25 CONVERT_FAIL(T2) / 21 跨表引用不在 QUERY_RELATION【旧系统同样绑定失败，默认保持 NULL】/
   1 脏数据 / 1 物理列缺失），按唯一模式分诊报告见 `logs/fields-chooser-rerun/triage.md`（不入库）。
