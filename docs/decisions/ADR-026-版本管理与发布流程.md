## 摘要（先读我，写给人类）

**要解决的问题**：今天**没有产品版本号**，且"发布"这条链上每一环都缺证据。

实测事实：

- `EOS.API`/`EOS.API.Tests` 无任何版本属性（且仓库无 `Directory.Build.props`/`Directory.Packages.props`/
  `Directory.Build.targets`/`global.json`/`nuget.config`）；程序集实测 `AssemblyVersion=1.0.0.0`、
  `FileVersion=1.0.0.0`、`InformationalVersion=1.0.0+<sha>`（SDK 默认拼 SourceRevision）；
- `EOS.Web/package.json:4` 是 `"version": "0.0.0"`（Vite 模板默认值，从未维护）；
- `README.md:6` 散文自称「早期开发阶段（v0.1）」；
  ⇒ **三处版本信号 `0.0.0` / `1.0.0` / `v0.1` 互不相同，没有权威版本号**；
- **`git tag` 为空**（本地、远端均为 0），`git describe --tags` 直接 fatal；
- **无 CHANGELOG、无 Release 说明**；唯一的变更叙事在 `docs/status.md`，而该文件**不入库**
  （`.git/info/exclude` 排除）⇒ 外部使用者拿不到任何变更记录；
- **无任何 CI/CD**：无 `.github/`、无 `.gitlab-ci.yml`/`azure-pipelines.yml`/`Jenkinsfile`/
  `.circleci`/`.travis.yml`/`.appveyor.yml`；`scripts/` 108 个跟踪文件中无 `publish-*.ps1`/
  `release*.ps1`（含 `publish` 字样的三个脚本都是**定义快照发布**，不是发版）；
- 无 `*.pubxml`/`web.config`/`Dockerfile`/`appsettings.Production*.json`；
  `docs/guide/README.md:88` 把「部署与环境配置」列为**待评估篇目（尚未撰写）**。

**本 ADR 的决定，用一句话说**：

> **在仓库根建立唯一版本真源 `version.json`（SemVer），API/Web 的构建元数据、发布标签、
> 变更记录三者由它派生；发布是"一条可复现的脚本流程"，阶段一不追求云端全自动。**

**边界**：

- ✅ 定：版本真源与派生关系、标签命名、变更记录格式与生成方式、发布物清单与发布说明必含项。
- ❌ 不做：CI 云端自动发布（阶段六可选）、自动部署到生产、为历史提交补标签、
  重建 `db/bootstrap/` 基线（能力已失去，属独立立项）。

### 1.2 约束（不可逾越）

1. **数据库结构随代码走**：迁移在 API 启动时由 DbUp 执行（`Program.cs:423`），因此"发一个版本"
   必然含"启动时自动升级库"；发布说明**必须标注是否含迁移、迁移编号区间**。
2. **发布前必须与远端同步**：本仓库当前存在"本地领先 1 个提交"的状态（`origin/main...main` = `0 1`），
   而标签指向本地提交——**未推送的标签对使用者不存在**。发布脚本必须把"远端已包含目标提交"
   作为前置断言。
3. **EOS.API 仅部署 Windows（IIS）**（`EOS.API.csproj:13`）；无既有部署配置，
   **部署形态在本 ADR 中不定义**。
4. **明文凭据禁止入库**（`AGENTS.md`）：发布物与清单不得含连接串、密钥、`appsettings.Development*.json`。
5. `docs/guide/README.md` 写作约定明确「文档里不写日期与版本号」⇒ 版本只出现在 `version.json`、
   程序集、`package.json`、标签、`CHANGELOG.md`、Release 说明。
6. **ADR-023 的"版本"是模块定义快照版本**（如 `module-1606-v12`），与本 ADR 的产品版本
   （`v0.x.y`）**不得混用命名**。
7. **不得为历史补标签**：文档声称的 3 个考古 tag 已不存在，而它们承载的历史快照已被
   `scripts/legacy-groundtruth/sprocs/` 取代；重新造标签只会制造第二处真源。

## 2. 决策

### 2.1 唯一版本真源 = 仓库根 `version.json`

内容形如 `{ "version": "0.1.0" }`（SemVer，可带 `-rc.N` 预发布后缀）。派生关系：

| 消费方 | 派生方式（说明性，不写具体补丁） |
|---|---|
| `EOS.API` 程序集 | 构建时读入并设 `Version`/`VersionPrefix`（`InformationalVersion` 继续由 SDK 追加 `+<sha>`，与现状一致） |
| `EOS.Web` | 构建时注入前端产物（Vite `define` 或构建前同步 `package.json`），界面"诊断信息"可读 |
| Git 标签 | `v<version>`（附注标签） |
| `CHANGELOG.md` | 每次发布顶部追加一节，标题含版本与日期 |
| 发布说明 | CHANGELOG 对应节 + 迁移编号区间 + 制品哈希清单 |

**一致性门禁**：新增只读校验——"`version.json` == 最新标签去掉 `v` 前缀（无标签时跳过）"，
拦住"改了版本忘打标签"。

### 2.2 分支与发布节奏：主干开发，标签即发布

- **不引入 Git Flow**（事实为 `main` + 备份分支，且为集中式发布）。
- 发布序列（在 `main` 上）：**确认远端已包含目标提交** → 跑验证门禁 → 升 `version.json` →
  生成 CHANGELOG 节 → 打附注标签 → 推送标签 → 产出制品与哈希清单 → GitHub Release 粘贴说明。
- 备份/实验分支（`backup/*`）不进发布语义。

### 2.3 CHANGELOG 由提交历史生成草稿、人工定稿

依据：最近 30 条提交 **100% 符合 Conventional Commits**（中文描述），可稳定按
`feat`/`fix`/`perf`/`refactor`/`docs`/`chore`/`ci` 分组生成草稿。
**草稿必审**：`feat!`/`BREAKING CHANGE` 必须人写面向用户的说明（生成器写不出业务影响）。
分组沿用 Keep a Changelog（`Added`/`Changed`/`Fixed`/`Removed`/`Security`）。

草稿头部另由脚本落两行事实，供人工定稿改写措辞：

- **数据库行**：`本版含迁移 283–284（共 2 个），部署时由 EOS.API 启动自动执行` 或 `本版不含迁移`
  —— 即 §1.2 第 1 条要求的"是否含迁移、迁移编号区间"由脚本先算好，不靠人自己数；
- 草稿来源行（自哪个标签起、共多少条提交）。

### 2.3.1 迁移门禁：仓库内嵌脚本与库内台账必须一一对应

版本号与迁移编号**互不参与**（§2.6 只按提交类型递增，与迁移无关），但发布必须确认
"代码里的迁移"与"库里的迁移"是同一份事实，故发布流程第 1 步是**连库只读**的双向集合比对
（`dbo.ERP_SCHEMA_JOURNAL` 的脚本名 vs `EOS.API/Data/Migrations/*.sql` 推导出的资源名）：

| 差集 | 含义 | 处置 |
|---|---|---|
| 台账有、仓库无 | 已执行的迁移脚本被**改名或删除** —— 新环境永远建不出这张库 | **失败**，列名并中止 |
| 仓库有、台账无 | 有迁移**尚未落库**（服务没重启或迁移没跑成功） | **失败**，提示先重启 `EOS.API` |
| 两边一致 | 正常 | 打印脚本总数 |

连不上库时**失败**（发布必须确认这一致性），仅 `-DryRun` 语义下可看清问题；
确要临时跳过用 `-SkipMigrationGate`，并在结论里显式声明未核对。

> **为什么这条门禁值得存在**：`AGENTS.md` 迁移约定里"编号冲突时改内容、不改文件名"与
> "已执行脚本再改内容不会重跑"两条规则，被违反时**编译、单测、健康检查全都不报**——
> 只在将来有人建新库时才炸。把差集检查放进发布动作，是把"将来才炸"提前到"发布前就炸"。

### 2.4 发布物清单（每次发布必须齐备）

1. `EOS.API` 构建产物（含内嵌迁移脚本、`ReportFormats/`、字体资产）；
2. `EOS.Web` 静态产物；
3. 数据库侧说明：本次涉及的迁移编号区间 + 目标库当前迁移位置；**并如实声明**
   `db/bootstrap/` 基线登记的迁移只到 **268**（新库需靠启动时 DbUp 补齐）；
   `MANIFEST.txt` 里的脚本总数与最新编号**由磁盘现算**，不写死（写死的数字会在下一个迁移落地时静默过期）；
4. `CHANGELOG.md` 对应节；
5. 制品哈希清单。

**不包含**：连接串/密钥、`appsettings.Development*.json`、`logs/`、本地脚本产物、
`docs/status.md`（未入库，不得作为发布说明来源）。

### 2.5 阶段一"自动"的准确含义

只要求**一条脚本流程可复现**（远端同步断言 → 门禁 → 升版本 → CHANGELOG 草稿 → 标签 →
制品与清单），**不要求云端 CI**。理由：无 `.github/`、API 仅 Windows、测试含真库用例
（依赖 SQL Server 实例）、无既有部署配置 ⇒ 云端 runner 可行性**未验证**（列为阶段六前置）。

### 2.6 版本号怎么涨（冻结规则）

版本格式 `MAJOR.MINOR.PATCH`，**起点 `0.1.0`**，递增判据按**提交类型**而非"每次提交"：

| 改动性质 | 递增 | 例 |
|---|---|---|
| 新功能（`feat`） | **MINOR +1**，PATCH 归零 | `0.1.0` → `0.2.0` |
| 缺陷修复 / 性能优化（`fix`/`perf`） | **PATCH +1** | `0.2.0` → `0.2.1` |
| 重构 / 文档 / 构建 / 测试（不改对外行为） | **不涨**（随下一个 feat 或 fix 带走） | — |
| **破坏性变更**（旧数据库或旧接口不再兼容，如批量退役库对象、接口签名变更） | **MAJOR +1**，MINOR/PATCH 归零 | `0.x` → `1.0.0` |
| 处于 `0.x` 期间 | **MAJOR 恒为 0**；破坏性变更改由 `MINOR +1` 表达 + CHANGELOG 标 `BREAKING` | `0.4.0` 破坏性 → `0.5.0` |

**为什么不是"每次提交 PATCH+1"**：提交粒度是工程细节，一天可能十几个；版本号是**给人看的**，
涨太快会让"用户报的版本号"失去时间含义（`0.1.37` 说不清是哪天）。按提交类型涨，版本号与
"这一版带来了什么"一一对应，也让 CHANGELOG 分节天然对齐。

**标签不必每个提交都打**：`v<version>` 只在**交付/发布时**打一次（喊"发布"才打标签），
`version.json` 可以先于标签前进——发布脚本的一致性门禁容忍"版本已升、标签未打"这一开发态，
但**不允许"标签已打、版本没升"**。

## 4. 已知后果

**正面**

- 三处版本信号收敛为一个真源；`/health/version` 的 `informationalVersion` 首次有意义；
- 用户报障可提供"版本 + 提交 + 构建时间"三件套（与 ADR-025/028/029 的关联键互补）；
- 制品可复现，减少手工打标签/手写说明的漂移；
- 顺带修掉两处文档自相矛盾（提交信息规范、发布节奏）与一处文档漂移（不存在的 tag）。

**负面 / 风险**

- **(a) 新增人工编辑点**：每次发布要维护 `version.json` 与 CHANGELOG（脚本只出草稿）；
  长期不发布则真源落后——这正是门禁要拦的形态。
- **(b) 首个版本号需拍板**：`0.1.0`（与 README v0.1 对齐）或 `1.0.0`（与程序集默认值对齐）
  对应不同的兼容承诺。
- **(c) `db/bootstrap/` 基线与迁移漂移 14 个，且重建工具已失去**：发布说明必须如实声明，
  **不得声称"基线可由工具重生成"**；补齐基线属独立立项。
- **(d) 台账/状态文件不入库**：`docs/status.md` 被排除，因此"发布说明从 status.md 摘抄"这条路
  对外不成立，CHANGELOG 必须自洽。
- **(e) 远端同步是新增前置**：当前 `0 1` 的领先状态若被忽略，标签会指向远端不存在的提交
  ⇒ 脚本断言必须硬失败。
- **(f) 云端 CI 缺位**：发布仍可能发生在未云端验证的环境（本机还有 WDAC 导致的
  "构建成功 ≠ 可运行"，见 `AGENTS.local.md`）。

## 5. 替代方案

| 方案 | 未选择原因 |
|---|---|
| 版本只写在 `EOS.API.csproj` | Web 与发布物各说各话，回到多真源 |
| 用 Git 标签反推版本（无 `version.json`） | 标签只在发布时存在，**开发中构建就没有版本**，而 `/health/version` 恰要在开发态可用 |
| 用文档声称的考古 tag 作为历史锚点 | **实测这些 tag 不存在**（本地/远端皆无）；以不存在的对象为锚会把断链写进新流程 |
| 引入 GitVersion/MinVer 自动算版本 | 新依赖 + 绑定提交消息解析规则（本项目中文描述，工具默认规则不适用） |
| 全套 Git Flow | 与"主干 + 集中发布"事实不符，纯增流程 |
| 云端 CI 一步到位 | 前置未验证（无 `.github/`、仅 Windows、真库测试、无部署配置），会把不确定性引入最需要确定性的链路 |
| 顺手重建 `db/bootstrap/` 基线 | 属独立工程（需纯导出脚本），且会与迁移编号策略纠缠，不塞进版本 ADR |

## 6. 验收标准

1. 从干净克隆执行发布脚本（不部署），产出：新标签（**且远端可 fetch 到**）、`CHANGELOG.md` 新节、
   制品 + 哈希清单；
2. **一致性可判别**：程序集 `InformationalVersion` 前缀 == `version.json` == 标签去 `v` ==
   Web 产物内版本；任一不符**必须**失败；
3. **可追溯**：给定任一制品，能回答"对应提交、构建时间、是否含迁移、迁移编号区间、
   相对 `db/bootstrap/` 基线的位置"；
4. **无凭据**：制品与清单 grep 不到连接串/口令/密钥关键字（构造正反例）；
5. **前置断言有效**：构造"本地领先远端"状态 ⇒ 脚本在打标签前失败；
6. `dotnet build` 0 错、`npm run lint`/`npm run build` 0 错、相关结构自检 PASS；
7. 待服务启动后补验：`/health/version` 返回的 `informationalVersion` 为新版本
   （**当前 API 未运行，此项标注"待用户启动服务后验证"**）。
