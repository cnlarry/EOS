## 三、由此暴露的结构性问题

**P1 报表身份绑错了对象。** 报表身份是 `reportId`（主键、不可变），但可达性前提却是"宿主模块的 `M_URL` 必须是 `/reports`"（`ReportRepository.cs:57` 的 `IsReportUrl`）。宿主 `M_URL` 不是 `/reports`，它挂的报表就集体失联——第 7、8 条那 25 张就是这么消失的。

**P2 入口撤了，目录建起来却没有任何入口能抵达。** ADR-009 §3 决定"撤 XX98 节点、顶层挂 1 个报表中心"，执行只做了前半句：迁移 023 隐藏了 **176 个节点**，而"顶层挂一个报表中心"**从未落地**（第 11 条）。结果：148 个可用报表**用户一个都点不到**。
（注一：在本 ADR 的 R-1 之下，"撤节点"这个动作**方向是对的**，问题只在于**没有建立任何替代入口**。）
（注二（第 4 版订正）：**报表中心这个页面本身是存在的**——`ReportCenterController` + `ReportCenterPage`，前端路由 `/report-center` 早在 `EOS.Web/src/app/workspaceRoutes.tsx:77` 注册，且刚完成 P0–P4 的 UI 重构。缺的**只是菜单入口**：实测 `M_URL='/report-center'` 的 `MODULES` 行 = **0**，而页面唯一的入站链接来自报表查看器的返回按钮 ⇒ **页面在、门没有**。故 P2 的准确说法是"**目录建起来了但不可抵达**"，R5 的工作量因此是"补一行菜单 + 加工具条动作"，**不是重造目录页**。）

**P3 两套渲染并存。** 单据打印已走完 ADR-010 路线（`layout.json` + 解释层 + `ILayoutRenderer` + DI），报表 PDF 仍在 `ReportPdfService` 的命令式硬编码模板里。同一能力两套实现、两套契约、两个演进方向。

**P4 格式模型只有一半。** `kind: list` 一个都没落地（第 19 条）：单据打印进了统一格式资产体系，列表型报表没进。

**P5 存在一层"影子模块"。** 156 个承载页（`/reports` 模块）**存在的唯一理由是"给报表一个能过 `IsReportUrl` 校验的 URL"**——第 12 条证明它们配的表全都属于某个业务模块，**没有一张表是报表专用的**。它们同时制造了第二个问题：**权限被登记在影子上**（`SYSDD_REPORT` 236 行指向承载页），而不是登记在业务模块上。

**P6 `Q_M_IDX` 的语义在重构中丢失。** 它当年正是想表达"归属"（见 §九 问题一），新系统只写不读，留下一层"看起来还有权限语义、实际没有"的假象。

**P7 报表的"配置"全挂在影子模块上。** 实测第 27 条：**`SYSQR_DEFAULT` 539 行报表条件**、`SYSQR_USER` 1112 行用户填值、`SYSQR` 411 行打印偏好、`SYSQR_DA` 141 行条件定义——**全都登记在承载页模块上**，而不是业务模块上。这让物理删除承载页变成一件**必须先搬迁条件才能做**的事（否则条件随模块一起消失，报表直接退化成"没有筛选条件"）。A5 修复批已经踩过一次同类坑（迁移 262 必须把条件的 `SERIAL_NO` 从 1303 的 1/2 改为 139808 的 5/6，因为 `(M_IDX, SERIAL_NO)` 是键，不重排就撞键）。

**P8 物理删除会波及权限与审计。** `SYSDD` 172 + `SYSDH` 202 行权限、`SYSDD_REPORT` 231 行条目 override 挂在删除目标上；`AUDIT_EVENT` 有 67 行指向这些模块。**审计按设计保留**（项目铁律：审计是追加型痕迹，不得删改），因此删模块后**审计里会留下指向已不存在模块号的行**——这是可接受的，但必须登记，避免后人把它当成数据错误。

## 四、术语与判据

沿用 ADR-009 §1 的两函数分解：

```
Report(参数, 用户) → 行集          ← 取数：有参数、有权限、可查询
Layout(行集, 格式) → 文档          ← 呈现：屏幕表格 / PDF / Excel
```

| 概念 | 构成 | 有参数 | 入口 | 进报表目录 |
|---|---|---|---|---|
| **报表（Report）** | `Report` + `Layout`（`kind: list`） | **是** | 报表中心 / 深链 / **单据工具条（本模块报表）** | **是** |
| **单据版式（Document）** | 仅 `Layout`（`kind: document`），行集由单据提供 | 否 | **单据工具栏的打印** | 否 |
| **格式包（Format Package）** | `format.json` + `layout.json` + `sample.json` | — | 二者共用 | — |

## 六、决策

### D1 报表的资源身份 = `reportId`；规范 URL = `/report/{reportId}`

`reportId` 是主键、0 重复、不可改。规范 URL 采用**单数 + 资源标识**，并立命名约定（写进 `docs/架构.md`）：

> **单数 = 单个资源实例（键为资源标识）；复数或带后缀 = 集合 / 工具页。**

### D2 新增 `REPORT.M_IDX` = 报表归属的模块（R-2）

- 指向**业务模块**（如 `HR_Absent_List` → `180202` 旷工单），**不是菜单节点**。
- 它是报表以下四件事的**唯一锚点**（第 4 版订正：清单**只列真读取点**——"唯一锚点"一旦混入并不存在的语义，犯的正是它自己要治的 P6）：
  1. **数据集**：`MASTER_TABLE` / `DETAIL_TABLE` / `FILTER`（`ReportRepository.cs:37-41` 逐列读取）+ `SYSQR_DEFAULT` 条件（按模块）。
     **不含 `MODULES.GROUP1..5`**：那五组是**第 4 级菜单分组**（唯一消费方 `NavigationGroupsRepository`），报表链路**零读取**；报表的分组来自 `REPORT_SORT` 与 `SYSQR.SHOW_GROUP`；
  2. **字段权限**：成本 / 保密 / 禁止字段（`FIELDS.IS_COST` / `IS_SECRECY` + `SYSDD` 的 deny 列表）；
  3. **行级权限**：模块 `DATA_FILTER` / `EXEC_TAG`；
  4. **模块功能权限**：`SYSDD` / `SYSDH` 的模块权限（含 `REPORT_TAG`）。
- 列名与 `MODULES.M_IDX` 同名同义，`F_ID` 关联可直接复用；**列注释必须写明"归属模块，不是菜单项"**。

### D3 退役 `REPORT.R_M_IDX` 与 `REPORT.Q_M_IDX`

- 两个字段的语义被 `M_IDX` 一个字段取代（`R_M_IDX`＝承载、`Q_M_IDX`＝权限覆盖，二者本就都在表达"这张报表属于谁"）。
- 迁移映射与权限行重指见 §七；**`SYSDH_REPORT`（0 行）一并退役**。

### D4 **报表不进菜单**（硬约束）

- `MODULES` **不得为报表新增菜单节点**；现存的 176 个已被隐藏的报表节点（23 XX98 目录 + 153 承载叶子）**保持隐藏，最终随承载页一起退役**。
- 报表的可发现性由四者提供：**报表中心目录** + **搜索** + **深链** + **情境入口（单据工具条）**。
- **新报表上线 = 加数据行**（`REPORT` + 格式包），**不产生任何菜单节点**。

### D5 `/reports/{M_IDX}` 重新定位

- **不再是"菜单可达的入口解析器"**（D4 之后菜单不会指向它）。
- 保留为**"按归属模块列报表"的跳转端点**：由统一表单工具条（D11）与业务页面调用，语义是"这个模块有哪些报表"。
- 若某模块只有 1 张报表，直接 `replace` 到 `/report/{reportId}`；否则进报表清单。

### D6 接口资源化

| 现在 | 改成 |
|---|---|
| `GET /reports/{M_IDX}/print-settings`（**报表清单 + 打印偏好混在一个响应**，前端从里面抠 reportId） | `GET /report/{reportId}` → `{ reportId, reportName, moduleId, siblings[] }`（资源 + **同模块兄弟报表**，支撑"切换同模块其它报表"）；`GET /report?moduleId=` → **按归属模块列报表**（供 D11 的工具条）；`/reports/{M_IDX}/print-settings` 降级为**只回答打印偏好** |
| `GET /reports/{M_IDX}/definition?reportId=` | `GET /report/{reportId}/definition` |
| `POST /reports/{M_IDX}/query` / `export` / `pdf` | `/report/{reportId}/query` / `export` / `pdf` |

### D7 可达性判据替换：不再要求"宿主必须是 `/reports`"

- 判据改为：**`REPORT` 行存在 ∧（归属模块 `MASTER_TABLE` 合法 ∨ `ReportAggregateRegistry` 已注册）**，**fail-closed**（不满足 → 404）。
- **实测收益：技术可达报表 227 → 约 440（＋93%）**，且不需要逐张搬宿主（这正是"逐张搬"方案净收益为零的原因所在）。
- **口径限定（第 4 版补）**："可达"= **端点不再 404**（技术可达），**不等于"用户能看到"**——后者还叠一层 `REPORT_TAG` + `SYSDD_REPORT`，而 R2 正要改这个口径。两个数**不得并排而不加限定**，否则验收时会拿"440"去对"用户能点到 440 张"。凡本文出现"可达"均指前者，指后者时一律写"可见"。
- **注意**：`∨ aggregate 已注册` 这个分支当前**不过字段级权限**（见 §六 **D15**），D15 未落地前该分支不得扩面。

### D8 报表中心 = **唯一目录入口**；"报表中心"这个页面**可以**进菜单

- 报表中心是"分类聚合 + 搜索 + 收藏 / 最近 + 订阅收件箱"的目录页，**不复制侧栏菜单树**。
- **重要区分**：**"报表不进菜单" ≠ "报表中心不进菜单"**。报表中心是一个**功能页面**（同行里 NetSuite 的 Reports 菜单、BC 的 Role Explorer、Fiori 的磁贴都是它的对应物），**菜单里允许存在且只允许存在这一个报表相关节点**。
- 这是 ADR-009 §3"顶层挂一个报表中心"的**真正落地**（第 11 条证明它从未落地）。
- **第 4 版补充（工作量口径）**：报表中心的**页面与接口已经存在**（`ReportCenterController` + `ReportCenterPage` + `/report-center` 路由 + 收件箱页），实测缺的只是**菜单行**（`M_URL='/report-center'` 的 `MODULES` 记录 = 0）。因此 R5 的交付物是：**① 补 1 行 `MODULES` 菜单；② 统一表单工具条的「报表」动作；③ ADR-018 订正**——**不包含重造目录页**。验收前先确认现有页面未被另起炉灶覆盖。

### D9 格式资产统一：`kind: list` 必须落地

- 格式包 = `format.json` + `layout.json` + `sample.json`（已落地 28 个、schema v1）。
- **`kind: list` 型报表 PDF 也走 `QuestPdfLayoutRenderer` 解释层**；`ReportPdfService`（命令式硬编码）按 ADR-010 决策 6 的同一逻辑**退役**（迁移 + 逐张对拍通过后）。

### D10 单据版式属于 `Layout`，不属于"报表"

- 判定见 §九 问题三。**资产上与报表同源，入口与生命周期上不是报表**。
- 因此：单据版式**不进报表目录、不进报表权限矩阵**（它的权限是"能不能打印这张单据"）；但**共用** `format.json` / `layout.json` / schema / 字段白名单 / 解释层 / 设计器。

### D11 **统一表单工具条新增"报表"动作**（R-3 结论，详见 §八）

- 语义：打开**本单据所属模块的报表清单**（`kind: list`），不是打印当前单据。
- 数据：`GET /report?moduleId=`（按 D2 的归属模块）；
- 授权：只列有权限的报表；**该模块无可见报表时不渲染该动作**（ADR-018 的 fail-closed 名单）；
- 需 **ADR-018 订正**：定序里插在**打印之后、帮助之前**（同属输出类动作），并登记 `FORM_BUTTONS` 白名单 + `COMMAND_ACTIONS` 注册表。

### D12 `REPORT_ID` 定为不可变标识 + 编号规范

- 不可变（现状已是，写进 ADR 锁死）；
- 新增编号必须匹配 `^[A-Za-z0-9_-]{3,40}$`，写入即校验；
- 清理现存 4 个不规范编号（见 §九 问题一）。

### D13 XX98 与 XX98XX 系列模块**物理下线删除**，并扫清遗留残余（R-4）

（第 4 版订正：第 3 版写作"25 个目录 + 156 = 179"，**算术与实测均不成立**——25 是"全库编号尾数 98 的模块总数"，其中 2 个 `M_URL` 非空、不属删除面；`23 + 156 = 179` 才自洽。**迁移必须以这条谓词原文为准，不得按"尾数 98"放宽。**）

| **保留（按设计）** | `AUDIT_EVENT`(67) | **审计不得删改**；删模块后审计里会出现指向已不存在模块号的行，**登记为正常现象**，不得当数据错误处理 |

**删除前必须留底**：179 行 `MODULES` 原始行 + 上述各表受影响行导出到 `logs/`（不可逆操作的可追溯性，比照 ADR-004 的受控迁移口径）。

**门禁（防重现）**：比照 `check-retired-db-objects.ps1` 的既有做法，新增**两类**断言：

1. **编号**：这 **179** 个模块号不得在 `MODULES` 中重现；
2. **形态（第 4 版新增，比编号更重要）**：**不得新增 `/reports` 型模块**（`M_URL='/reports'`），确需保留的必须具名进白名单。只守编号守不住形态——换个编号重建"给报表一个 URL 的影子模块"，编号门禁一声不响。P5 的病根是影子模块，**门禁必须守病根**；
3. 同一脚本内一并守"**报表相关菜单节点数恒为 1（只有报表中心）**"，把 D4 从文字约定变成可执行断言（本仓经验：没有门禁的约定一定会漂回来）。

`MODULES_Backup_ADR004` 这类历史备份表是否同步处理一并决定。

**三方引用核查（删除前，比照 AGENTS.md 的退役口径）**：除 §二-27/29 的库内清单外，已额外实测**软引用** `FIELDS.BROWSE_M_IDX`（选择器回填目标模块）指向删除面 = **0 行**；代码侧按名引用见 §二-23/31（`14998` 有硬编码常量，但**不在**删除面内）。

**术语澄清**：删掉的是**模块**（`MODULES` 行），**不是表**。承载页配的物理表（`CLIENT` / `INV_BATCH_M` 等）全部属于业务模块，**一张都不会删**（第 12 条已证："只被承载页使用"的表 = 0）。

### D14 `REPORT` 不得关联 `TABLES`，也不得新增任何"表 / 字段来源"列

- 判据：报表呈现的表**唯一来自** `M_IDX → MODULES.MASTER_TABLE / DETAIL_TABLE`（+ `FILTER`）；连"报表能选哪些列"也由该模块的 `FIELDS` 派生（实测第 25 条）。`TABLES` 在报表链路上**零读取点**。
- **禁止**在 `REPORT` 上新增 `T_ID` / `MASTER_TABLE` / `TABLE_NAME` 一类列——那会制造**双真源**（模块给一份、报表给一份），而这正是 R-2 要消灭的病：`R_M_IDX` / `Q_M_IDX` 就是同一个"归属"被写了两遍，`CreateReportAsync:99` 把两者都写成同一个 `@ModuleId` 即是明证。
- 需要"查非归属模块主表"的报表（跨表聚合）：**唯一出口是 `ReportAggregateRegistry`**（开发态资产、进 Git、可 review、可对拍），与 ADR-009 §1"数据源属开发态"闭环。
- 同一模块下确需两张报表查两张表 ⇒ **那是两个模块**（各自有 `MASTER_TABLE`），不是两个报表。
- **配套门禁**：扫 `REPORT` 的列名黑名单（`T_ID` / `MASTER_TABLE` / `TABLE_NAME`），出现即 FAIL。
- **前置条件（第 4 版补）**：注册表这条出口当前**不过字段级权限** ⇒ **必须先完成 D15**，D14 才能算数。

### D15 汇总报表必须过字段级权限 —— **D14 的硬前置**（第 4 版新增）

**问题（实测）**：`ReportRepository.GetDefinitionAsync` 的列装配分两路（`EOS.API/Data/ReportRepository.cs:81-94`）：

```csharp
if (aggregate is not null) { columns = aggregate.Columns; pkOrder = []; }   // ← 直接采用，不过任何过滤
else { (columns, pkOrder) = await ReadColumnsAsync(..., canViewCost, canViewSecrecy, deniedFields, token); }
```

`ReportAggregate.Columns` 的元素类型 `ReportColumn(Key, Label, DataType)` **没有成本/保密位**，也不与归属模块的 `FIELDS` 关联 ⇒ **aggregate 型报表的输出列完全不经过 `IS_COST` / `IS_SECRECY` / deny 名单过滤**。

**这不是假设，是已上线样本**：

| 报表 | 注册表条目 | 实际输出了什么 | 该模块的表元数据 |
|---|---|---|---|
| `INV_Pro_Depot_1`（库存日报，宿主 `139901`） | `InventoryDaily` | `PRICE_Q` / `PRICE_J` / `PRICE_X`（期初 / 收入 / 发出**单价**） | `INV_DEPOT_LOG` 的 `FIELDS` 里有 **4 个 `IS_COST=1` 列**（含 `PRICE`）；而这三个派生列在 `FIELDS` 里**一行都没有**（实测该表下 `PRICE_*` 行 = 0） |

⇒ 对 `139901` 无成本权限的用户，打开库存日报**照样看得到单价**。`REPORT_TAG` 只决定"能不能看这张报表"，**字段级权限在这条路上整体缺席**。

**为什么必须现在修**：D14 把注册表定为"查非归属模块主表的报表的**唯一出口**"——等于用一条不过字段权限的通道，去承接**原本最需要字段权限**的那批报表（跨表汇总 / 成本分析）。不先补，D14 落地之日就是权限缺口扩大之时，§十二 第一条正面影响（"权限语义第一次真正对齐"）会当场落空。

**决策**：

1. **取「给 `ReportColumn` 增列权限位」这一条路**（`IsCost` / `IsSecrecy`，另加 `DenyKey` 以匹配用户级拒绝名单）。
   - **订正（2026-09-28 预演实查）**：本 ADR 初稿写的是"或让注册表声明 `F_ID` 映射到归属模块的 `FIELDS`，**取后者优先**"——**这条路走不通**。`FIELDS.T_ID` 是**物理表名**，而聚合列是 SQL 算出来的派生列，不属任何物理表：实测 `PRICE_Q` / `PRICE_J` / `PRICE_X` 在**全库 `FIELDS` 里 0 行**（对比 `PRICE` 88 行、`COST_PRICE` 2 行）。要按后者做，就得为派生列在 `FIELDS` 里编造"物理表"，反而制造假元数据。**故本条改为单一方案，不再二选一。**
2. `GetDefinitionAsync` 的 aggregate 分支应用**与主表分支同一套**过滤（`canViewCost` / `canViewSecrecy` / `deniedFields`）；
3. **未声明权限位的聚合列一律 fail-closed**——不得默认放行（"漏标"等于"公开"）；
4. `ReportAggregateRegistry` 的 **9 个既有条目逐列补标**，补标结果与归属模块 `FIELDS` 对拍并留清单到 `logs/`；
5. **配套门禁**：聚合列既无权限位、又不在显式白名单内 → FAIL；`-SelfTest` 做正反自检。

**退出条件**：在**无成本权限**账号下，`139901` 的 `PRICE_Q/J/X` 既不出现在 `definition` 也不出现在 `query` 结果里；**有权限账号照常可见**（双向验证，缺一不可）；9 个注册表条目逐列补标完成；门禁正反自检通过。

### D16 报表权限管理面收敛：删「报表权限」子页，override 收紧语义退役（第 4 版新增，2026-09-28 用户拍板）

**背景（实测）**：

| 事实 | 实测值 / 位置 |
|---|---|
| 模块级报表可见性真源 | `SYSDD.REPORT_TAG`（个人优先）/ `SYSDH.REPORT_TAG`（组 OR），读取点 `ModuleRightsRepository.cs:166-187`、`PrintSettingsRepository.cs:220-242` |
| 该真源的**维护入口已经存在** | 2305「组权限」/ 2306「权限」子页右侧面板「基本操作」里的 **【报表】勾选框**——`types.ts:200` 定义、`PermissionEditPanel.tsx:113` 渲染、`RightsAdminRepository.cs:1434` 落库、`:1180` 回读、`:48` 参与"全默认空"判定。**自 M92（`950832f`）起一直在，本 ADR 无需新增** |
| `SYSDH_REPORT`（组级 override） | **0 行** ⇒ D3 已判退役 |
| `SYSDD_REPORT`（条目级 override） | **256 行 / 仅涉及 6 个账号**；256 行**全部**带 `PREVIEW/PRINT/EXPORT` 位，其中 **229 行是"三位全 1 且无 `DATA_FILTER`"——与"默认开放"完全等价、零语义**；真正有语义的只有**「收紧」21 行** + 带 `DATA_FILTER` 9 行（两者有重叠） |
| 表的列构成（实查 `sys.columns`） | 主键 `(USER_ID, M_IDX, REPORT_ID)`；权限列 `PREVIEW_TAG` / `PRINT_TAG` / `EXPORT_TAG` / `DATA_FILTER`；报表中心列 `FAVORITE_TAG` / `SORT_IDX` / `LAST_RUN_AT` |
| 同一张表的**第二个用途** | 报表中心在写 `FAVORITE_TAG`（7 行=1）、`SORT_IDX`、`LAST_RUN_AT`（6 行）——见 `ReportCenterController.cs:113-195` |

**为什么收敛**：ADR-024 把权限锚点从**承载页**（影子模块）移到**归属模块**之后，一次【报表】勾选即覆盖该模块**全部报表** ⇒ 独立矩阵只剩"在同一个业务模块内，单独把某张报表收紧"这一件事，而这件事全库只有 21 行在用。继续保留它，等于为 21 行数据维护第二套权限通道（含个人/组双通道 + `SYSDG_USER` 聚合），并使"报表可见性"重新出现双真源。

**决策**：

1. **删除 2305 用户组管理**的【报表权限】按钮、子页路由 `/admin/groups/{id}/report-rights` 与 `GroupReportRightsPage`（`UserGroupAdminPage.tsx:111`、`GroupAdminPages.tsx:80-95`）；
2. **删除 2306 用户权限设定**的【报表权限】按钮、子页路由 `/admin/users/{id}/report-rights` 与 `UserReportRightsPage`（`UserAdminPage.tsx:259`、`UserAdminPages.tsx:41-52`）；
3. **`SYSDD_REPORT` 的权限 override 语义退役**：`PREVIEW_TAG` / `PRINT_TAG` / `EXPORT_TAG` / `DATA_FILTER` 四列退出一切权限判定；`SYSDH_REPORT` 整表退役（D3 已决）；
4. **`SYSDD_REPORT` 表本身保留，收敛为"报表中心用户状态表"**，只承载 `FAVORITE_TAG` / `SORT_IDX` / `LAST_RUN_AT`。**表名与列注释必须同步订正**——否则会造出一个"看起来还有权限语义、实际没有"的东西，正是本 ADR 诊断的 **P6** 同类物。是否随 R7 改名为 `REPORT_USER_STATE` 在 R7 决定；
5. **唯一真源**：报表可见性 = 归属模块的 `REPORT_TAG`（个人 `SYSDD` 优先，否则组 `SYSDH` OR）。**不存在条目级 override**；
6. **那 21 行「收紧」必须逐条核对并登记**（用户 / 模块 / 报表 / 收紧的是哪几位）——它们是本条唯一会**放宽**权限的现存数据，不得静默消失。若某条确需继续收紧，改由字段级/行级权限或拆模块解决，**不得重新引入 override**；
   - **比对范围很小且可枚举**：整表只涉及 **6 个账号**，229 行是零语义的"全 1"行（可直接删）。**逐人比对就比这 6 个人**，不必扫全库账号；
7. 同步删除三个读取点上的 override 分支：`ModuleRightsRepository.cs:43-104`、`PrintSettingsRepository.cs:165-192`、`ReportCenterController.cs:51-65`。

**边界（不得顺手越界）**：`DocumentActionAuthorization`（按钮级授权）的**结构**是照抄 report override 的模式（个人/组双通道 + `SYSDG_USER` 聚合），但语义**刻意不同**（报表无 override 行 ⇒ 跟随模块 `REPORT_TAG` 放行；按钮无 override 行 ⇒ fail-closed 拒绝）。**退役 report override 不得动按钮授权**。

**顺带订正**：`UserGroupAdminPage.tsx:131` 的列表头说明写作"操作列提供组权限/报表权限/成员/编辑/删除"，实际已是"组权限/报表权限/按钮权限/成员/编辑/删除"——**漏了「按钮权限」**，随本条一并改。

**执行时机**：并入 **R7 收口**（与 `R_M_IDX` / `Q_M_IDX` / `SYSDH_REPORT` 一起退役），**不单独提前**——21 行的逐条核对依赖 R2 先把 `SYSDD_REPORT.M_IDX` 重指到归属模块。

**风险**：这是本项目在报表域上的**第三次可见范围变化**（前两次：R2 的 `REPORT_TAG` 锚点变更、R8 删 374 行权限行），必须与 R2/R8 的逐人比对**合并成一次**做，不得各比一遍。

## 七、R-2 的可行性：归属迁移账（实测）

### 1. 为什么这个模型成立（三条证据）

1. **取数表不变**：3 张 `Q_M_IDX ≠ R_M_IDX` 的报表里，`HR_Absent_List` / `HR_AMERCE_LIST` 的业务模块与承载页**配的是同一张 `MASTER_TABLE`**（`HR_ABSENT_M` / `HR_AMERCE_M`）；`INV_Batch_Expiry_1` 是 **aggregate 型**（走注册表 SQL，不依赖主表）⇒ 归位不影响取数。
2. **承载页是冗余的**：156 个承载页中 **149 个**的表与某个业务模块相同，**"只被承载页使用"的表 = 0** ⇒ **没有任何一张表为报表专用**。
3. **权限迁移量小**：`SYSDD_REPORT` 256 行中，指向承载页的 236 行、其中**「收紧」只有 4 行**；`SYSDH_REPORT` **0 行**。

### 2. 469 张报表的归位分布

| 当前宿主 | 张数 | 归位动作 |
|---|---|---|
| `/workbench` 正常业务模块 | **217** | 直接 `M_IDX = R_M_IDX`（零判断） |
| `/reports` 承载页 | **227** | 按"同表业务模块"归位；**落在 28 张歧义表上的需人工复核** |
| 工具/管理页（`/admin/*`、`/import`、`/jobs`、`/car-summary`、`/search-center`、空 URL） | **17** | **人工指定归属** |
| 宿主模块悬空 | **8** | **人工指定归属** |

**人工量 = 25 张（17 + 8）+ 28 张歧义表涉及的报表复核**；其余 217 张零判断、227 张半自动。
另有 **7 个承载页 `MASTER_TABLE` 为空**（含"未建模具/BOM/客户计价/厂商计价/样品"5 张）需一并定口径。

### 3. 归属判定规则（不猜，逐条核对 + 清单落 `logs/`）

1. 优先按**"同表业务模块"**：承载页 `MASTER_TABLE` 与某业务模块相同 ⇒ 归属该模块；
2. 该表对应**多个**业务模块时（28 张表）⇒ **人工按报表语义判定**（如 `COP_ORDER_D`×4 分别是哪个单据的明细）；
3. 报表为 **aggregate 型** ⇒ 归属其语义所对的业务模块（如 `INV_Batch_Expiry_1` → `1303` 料件库存资料，即原 `Q_M_IDX`）；
4. **工具页宿主（17 张）+ 悬空宿主（8 张）** ⇒ 人工指定；
5. 判定结果**逐张落清单**（`logs/`），差异具名，**不得自动猜测落库**（沿用 ADR-008 §6 的三档法）。

### 4. 权限迁移规则

- `SYSDD_REPORT` 指向承载页的 236 行 → 重指到归属模块；
- 其中**「收紧」4 行**逐条人工核对（**这是本次唯一的权限行为变更点**，必须点名）；
- `SYSDH_REPORT` 0 行 ⇒ 退役；
- 旧 `REPORT_TAG`（模块级可见性真源）不受影响——但它挂的是承载页模块的权限行，**归位后模块级可见性改由归属模块的 `REPORT_TAG` 决定**：这一步会**扩大可见范围**（能进业务模块的人变多），已由用户确认为**有意的语义变更**（2026-09-28 确认），但仍须逐人比对。

### 5. 条件归位与撞键（R1b，R-4 的前置）

实测：删除目标上挂着 **`SYSQR_DEFAULT` 539 行**（报表筛选条件）、**`SYSQR_DA` 141 行**（条件模块定义）、**`SYSQR_USER` 1112 行**（用户填值）。**条件是按模块读的**（`SYSQR_DEFAULT.M_IDX`），不搬就随模块一起消失 —— 报表会退化成"没有筛选条件"。

**规则**：

1. 条件行**随归属归位搬到业务模块**（`SYSQR_DEFAULT.M_IDX` / `SYSQR_DA.M_IDX` / `SYSQR_USER.M_IDX`）；
2. **必须重排 `SERIAL_NO`**：`(M_IDX, SERIAL_NO)` 是键，目标模块已有的序号不能撞（A5 迁移 262 的先例：1303 的 1/2 → 139808 的 5/6）；
3. `SERIAL_NO` 会被**前端条件面板与服务端注册表引用**（`ReportAggregateRegistry` 按 `SerialNo` 登记参数）⇒ **注册表里的序号必须同步改**，否则参数绑定错位（A5 已踩过：`ReportAggregateRegistry` 的 `SerialNo` 1/2 → 5/6）；
4. 搬过去后这些条件会出现在**归属模块的其它报表**上 —— 条件按模块共用是既有设计（139901 的 3 张报表共用 7 条条件），不是副作用；
5. 逐条落清单到 `logs/`，**撞键即中止**（不猜测、不静默重排）。

## 八、R-3 讨论：报表入口能否挂到统一表单工具条上？

**结论：可以，而且应该。**

### 1. 业界依据（原厂机制）

| 产品 | 机制 | 出处 |
|---|---|---|
| **BC** | **`RunObject` 属性**：动作触发时**立即运行**指定对象，"replace the query keyword with page, **report**, or codeunit" | MS Learn · RunObject Property |
| **Odoo** | 报表"**主要通过模型视图的 Print 菜单触达**"——记录视图就是报表的主入口 | Odoo 19.0 · QWeb Reports |
| **NetSuite** | Reports 菜单是导航入口，记录/列表上另有相关报表与记录的链接 | NetSuite Help |

### 2. 为什么在 EOS 里值得做（三条）

1. **与 R-1 互补**：报表不挂菜单之后，可发现性必须由"目录 + 情境"分担，工具条正是"情境"的落点；否则又会回到"报表没人找得到"的 P2。
2. **与 R-2 完美契合**：报表归属哪个模块，就出现在哪个模块的工具条上——`REPORT.M_IDX` **直接决定这份清单**，不需要任何额外配置。
3. **复用既有机制**：ADR-018 已经定了"按钮白名单 + 按钮级授权 fail-closed + 工具栏定序"，**不需要引入新范式**。

### 3. 必须区分的两件事（否则会混淆用户）

| 动作 | 语义 | 作用对象 | `kind` |
|---|---|---|---|
| **打印**（已有） | 打印**当前这张单据** | 当前记录 | `document` |
| **报表**（新增） | 打开**本模块的报表清单** | **模块**，不是记录 | `list` |

### 4. 设计要点

- **命名**：用「报表」或「本模块报表」；**不放张数**（否则按钮宽度随数据变化）。
- **位置**：ADR-018 的浏览态定序里插在**打印之后、帮助之前**（同属输出类动作）⇒ 需给 ADR-018 加**日期订正**。
- **交互**：点开下拉/抽屉列出本模块报表（`GET /report?moduleId=`），选中后进 `/report/{reportId}`；**若该模块只有 1 张报表，直接进入**。
- **授权**：只列有权限的报表；该模块**无可展示报表时不渲染该动作**（ADR-018 的 fail-closed 名单，服务端另行鉴权，无豁免）。
- **边界**：报表是**模块级**信息，**只放主工具条一次**，不在明细子表的标题栏重复（ADR-018 已定子表标题栏的位置归明细级自定义按钮）。

## 九、三个问题的答复

### 问题一：`R_M_IDX` 与 `Q_M_IDX` 分别代表什么？

**权威依据是旧系统源码，逐字可读**（`ERP/RPT/RptView.aspx.cs:52`）：

```csharp
int module = dt.Rows[0]["Q_M_IDX"].ToString() == "0"
    ? dt.Rows[0]["R_M_IDX"].ToString()      // Q 为 0 → 用 R
    : dt.Rows[0]["Q_M_IDX"].ToString();     // Q 非 0 → 用 Q
Right.Rights oUserRights = oRight.GetUserRights(Page, module);
Right.ReportRights oReportRights = oRight.GetUserReportRights(userId, module, reportId);
```

| 列 | 语义 | 旧系统怎么用 | 新系统现状 |
|---|---|---|---|
| **`R_M_IDX`** | **报表模块**（承载） | ① 按它列报表清单（`RptParent.master.cs:44-49`：`WHERE s.R_M_IDX=@module`）；② `SYSDD_REPORT` 条目权限也按它；③ `Q_M_IDX=0` 时的默认权限模块 | **在用**（承载页、目录分域、权限单元） |
| **`Q_M_IDX`** | **查询（权限）模块** | **非 0 时替代 `R_M_IDX` 做功能权限判定** ⇒ 语义是"**报表可见性跟业务模块走，而不是跟承载页走**" | **只写不读**（唯一读取点是 `TABLES.QUERY_RELATION` 的显示关联） |

旁证：`FIELDS` 里它的中文名就是**"权限ID"**；选择器被限定为"**只能是叶子模块**"；模块号变更时两列都级联更新。

**注意：`Q_M_IDX` 当年的意图，正是 R-2 要做的事。** 本 ADR 的做法是**把它扶正为唯一的 `M_IDX`**，而不是"退役掉这个语义"。

不规范编号清理（D12）：

| 编号 | 问题 | `REPORT_SORT` | `SYSDD_REPORT` | 备注 |
|---|---|---|---|---|
| `COP_Send_List _jd` | 含**空格** | 5 | 1 | 需连带动这两张表 |
| `INV_Occur_In_List.` | **尾点号** | 3 | 1 | 同上 |
| `MOC_Get.` / `SYS_Company.` | 尾点号 | 0 | 0 | 零引用，零风险 |

（尾点号比空格更麻烦：路由/反代常剥掉路径末尾的 `.`。全库引用 `REPORT_ID` 的表共 7 张：`REPORT`/`REPORT_SORT`/`REPORT_INBOX`/`REPORT_SUBSCRIPTION`/`SYSDD_REPORT`/`SYSDH_REPORT`/`SYSQR`；`ReportAggregateRegistry` 无硬编码这 4 个 ⇒ 一次小迁移可清，不动代码。）

### 问题二：报表需要像模块一样挂载到菜单上吗？

**结论：不需要，而且明确禁止（R-1）。** 依据：

1. **同行没有一家这么做**（§五 五条结论第 1、2 条）。EBS 的暴露机制是"职责 × 请求组"、BC 是"一个属性值"、NetSuite 是"类型 + 角色 + 中心"，Odoo **连"报表类型的菜单项"都不存在**。
2. **我们自己的实测就是反例**：撤掉 176 个节点却没建起那 1 个入口，148 个可用报表一个都点不到。证明"逐张挂节点"既撑不起可发现性，撤掉后也不会自动出现更好的入口。
3. **EOS 还有一个额外理由**：菜单与权限的键都是 `M_IDX`，而报表身份是 `reportId`——**用菜单承载报表，等于强迫"资源身份"屈服于"导航结构"**，这正是 P1 的病根。

**但要区分两件事**（D8）：**"报表不进菜单" ≠ "报表中心不进菜单"**。报表中心是功能页面，菜单里允许且只允许存在这一个报表相关节点。

**报表的四个入口（全部不依赖菜单节点）**：

| 入口 | 形态 | 面向 |
|---|---|---|
| **目录** | 报表中心（分类聚合 + 搜索 + 收藏/最近） | "有哪些报表可用" |
| **情境** | 统一表单工具条的「报表」动作（D11）→ 本模块报表清单 | "我在做这个模块的活，有哪些报表" |
| **深链** | `/report/{reportId}`（可收藏、可分享、可写进通知/邮件） | "我就要看这一张" |
| **外部** | 订阅调度产出的报表进收件箱（ADR-009 §7） | "报表主动找人" |

### 问题三：单据打印（如送货单）的版式算不算报表？

**结论：算"报表格式资产"的一部分，不算"报表"。**

| | 报表（Report） | 单据版式（Document） |
|---|---|---|
| 由哪一半构成 | `Report` + `Layout` | **只有 `Layout`** |
| 行集从哪来 | 查询取数（参数来自 `SYSQR_DEFAULT` 条件） | **单据本身**（`PrintService.GetPrintDataAsync` → `PrintData`） |
| 有用户参数 | 有（条件面板） | 没有（单据即参数） |
| 权限 | 归属模块的 `REPORT_TAG`（**无条目级 override**，见 D16） | "能不能打印这张单据" |
| 入口 | 报表中心 / 深链 / **单据工具条** | **单据工具栏的打印动作** |
| `kind` | `list` | `document` |

实测位置：`EOS.API/ReportFormats/1406/{format.json, layout.json}`，**`"kind": "document"`**、`"title": "送货单"`，由 `REPORT.FORMAT_ID` → `ReportFormatRepository.GetPackage` → `QuestPdfLayoutRenderer` 渲染。**它已经在"报表格式资产"体系里（目录名就叫 `ReportFormats`），只是分类是 `document`。**

**业界依据**：BC 的 `Documents` 与 `ReportsAndAnalysis` 是**同一个 `Report` 对象类型上的同一个属性**的两个取值；EBS 单据打印与报表**同为并发程序**；Odoo 则相反。**EOS 的选择与 BC 同向**：术语分开（报表 / 单据版式），资产统一（格式包），入口分开（目录页+工具条 / 打印动作）。

## 十二、结果与影响

### 正面影响

- **报表技术可达数 227 → 约 440（＋93%）**（**"可达"= 端点不 404**，非"用户可见"；后者另计），且**不需要逐张搬宿主**——只是把"URL 必须绑承载页"这个错误前提去掉；
- **权限语义第一次真正对齐**：报表的成本/保密字段、行级过滤、模块功能权限**全部跟随归属模块**，不再有一层影子模块的间接
  （**前提是 D15 先落地**——汇总报表这条出口目前不过字段级权限，不补则本条正面影响只兑现一半）；
- **消灭 156 个影子模块**：报表不再需要"为了有个 URL"而存在的模块，`M_IDX` 直接指向业务模块；
- **URL 成为稳定资源标识**（`reportId` 主键且不可变），"切换同模块其它报表"有 URL 语义支撑（siblings）；
- **可发现性不再依赖菜单节点**：报表中心 + 工具条 + 深链 + 收件箱四个入口，**新增报表不产生任何菜单节点**；
- **格式资产真正统一**：报表与单据版式共用 `format.json`/`layout.json`/schema/白名单/解释层，`ReportPdfService` 退役后只剩一套渲染；
- 顺带收口两个历史悬案：`Q_M_IDX` 的语义（扶正为 `M_IDX`）、`kind: list` 的缺口（落地）。

### 成本与风险

- **⭐ 汇总报表的字段级权限缺口是本 ADR 最隐蔽的一处**（第 4 版新增，见 **D15**）：它**不报错、不 403，只是多给列**——`ReportRepository.cs:81-94` 的 aggregate 分支直接采用注册表声明的列，`canViewCost` / `canViewSecrecy` / deny 名单**一个都不过**。现存样本 `INV_Pro_Depot_1`（库存日报）已经在输出 `PRICE_Q/J/X`。而 D14 正要把这条出口定为跨表报表的**唯一**通道 ⇒ **不修 D15 而落 D14，等于把权限缺口制度化**。因此 R0 排在 R1 之前；
- **R1 是本次最大的数据工程**：469 张要逐张定归属。缓解：217 张零判断、227 张按"同表"半自动，**人工量 = 25 张（17 工具页宿主 + 8 悬空宿主）+ 28 张歧义表涉及的报表**。**红线：不得自动猜测，歧义一律进人工清单**（ADR-008 §6 三档法）；R1 的退出条件按**清单条数**计量，不用"回填率 100%"代替工作量口径；
- **R2 会改变可见范围**（必须点名）：模块级可见性从"承载页模块的 `REPORT_TAG`"改为"归属模块的 `REPORT_TAG`" ⇒ **能进业务模块的人变多，可见报表可能变多**。这是**有意的语义变更**，必须逐人比对 + 用户确认；**"逐人"的比对对象与规模（哪些账号、多少行）须在执行前由用户确认**——本项目处开发期、无上线存量，照字面做一轮全账号比对可能是空转；
- **权限迁移唯一的高危点**：`SYSDD_REPORT` 指向承载页的 **4 行「收紧」**行——改错会放宽权限或收紧过度，必须逐条人工核对；
- **授权必须 fail-closed**：`/report/{reportId}` 的权限必须经 `M_IDX` 反查判定，**不能信 URL**；否则可拿别人的 `reportId` 绕过模块权限。这是本 ADR 最高危的一处，需专项 E2E；
- **移除 `IsReportUrl` 需等价强度的替代判据**（D7），否则"随便一个模块号"都会变成可打开的报表；
- **遗留缺口要具名**：18 张空 `MASTER_TABLE`（含"未建…"5 张）+ 8 张悬空宿主 + 7 个空表承载页，R4 之后仍是 404，必须点名登记，不能混在"可达 440"里；
- **D11 的边界**：工具条上的「报表」是**模块级**动作，要防止用户误以为"这是给当前单据的报表"——命名与空态必须说清；
- **别再把 2201 做成第二真相**：ADR-009 §11 已裁定 2201"转型为开发态资产、管理页移除"；若将来做报表定义设计态，**必须同时重估 2201**；
- **R-4 是不可逆操作，必须留底**：179 个模块行 + 受影响行导出到 `logs/`；删除与清理写在**同一个迁移事务**内（比照 ENDCASE 批"迁移本体 + 记账同事务"先例）；
- **删除面口径本身也会写错**（第 4 版教训）：第 3 版把"全库尾数 98 的 25 个模块"当成了"25 个目录"，`25 + 156 = 181 ≠ 179`。**不可逆操作的删除面必须由谓词原文定义、并由独立查询复核集合大小**（本次复核：`23 ∪ 156` 恰为 179）；
- **条件归位会撞键，且撞键必须中止**（§七-5）：539 行 `SYSQR_DEFAULT` 要重排 `SERIAL_NO`，并**同步 `ReportAggregateRegistry` 里的 `SerialNo`**——只改库不改代码会让参数绑定错位（A5 已踩过）；
- **删除顺序错一步就制造悬空**：实测已有 8 张报表处于"宿主悬空"状态，就是这类事故的现存样本。R0 → R1 → R1b → R2 → R8 的顺序**不可调换**；
- **权限会被删掉 374 行**（`SYSDD` 172 + `SYSDH` 202）：这是继 R2 `REPORT_TAG` 语义变更之后的**第二次可见范围变化**；
- **第三次可见范围变化在 D16**（退役条目级 override）：那 21 行「收紧」是唯一会因 D16 而**放宽**的现存数据。**三次变化必须合并成一次逐人比对**，不得各比一遍——分开比会把同一批账号反复折腾三趟，且差异归因会互相污染；
- **审计会留下"指向已不存在模块号"的 67 行**：这是**设计允许**的（审计是追加型痕迹，不得删改），必须登记为正常现象，否则后人会当成数据错误去"修"；
- **一刀切按编号删除会误伤真功能**：`14998`（`/detail-query`，另有 `ModuleIds.cs:53` 硬编码）、`16998`（`/workbench`）、`129802`（`/bom-expand`，**全库唯一承载模块**）三个模块编号符合"XX98/XX98XX"形态但**是真实功能页**。D13 的逐条裁决必须先做完再动手；
- **`18069805` 不是空僵尸**（第 4 版订正）：它持有 `HRM_WAGE_LIST`（`IS_DEFAULT=1`）+ 5 行条件，删前必须先归位到 `180504`（同表、已发布）；误当僵尸删除会让工资明细报表与筛选条件一起消失。

## 十四、复审条件

- **D15 落地后** → 复核过滤覆盖 **`definition` / `query` / `export` / `pdf` 四条路径**（列清单由 `GetDefinitionAsync` 统一产出，理论上一次修复全覆盖，须逐条实测，不得推定）；
- **有人要求"在同一个模块内单独收紧某张报表"** → 按 **D16** 拒绝重新引入条目级 override；改走字段级/行级权限（`IS_COST` / `IS_SECRECY` / `DATA_FILTER`），确实表达不了就把该报表拆到独立模块；
- **有人要求恢复 2305/2306 的【报表权限】入口** → 先确认 D16 的前提（模块级 `REPORT_TAG` 是否已足以表达全部需求）已被推翻，否则按 D16 拒绝；
- **`ReportAggregateRegistry` 新增条目时** → 必须同时声明每一列的权限位；**未声明即 fail-closed**，不得默认放行；
- **R2 逐人比对发现可见范围变化超出登记清单** → 暂停 R2，回到用户确认；
- **"一张报表要查的表 ≠ 归属模块的主表"成为真实需求** → 在 `REPORT` 上单独声明数据集（或走 `ReportAggregateRegistry`），**不得重新引入"承载模块"**（且此时必须已经完成 D15）；
- **可用报表增长到目录页难以承载**（经验阈值：分类内超 25 项，参照 SAP 每页上限）→ 评估按角色预置分类；
- **空 `MASTER_TABLE` 18 张 + 悬空宿主 8 张清理完成** → 复核 D7 的"技术可达 440"是否应升为"可达全部"；
- **报表定义设计态立项时** → 必须同时决定 2201 的去留（禁止双份真相）；
- **`/report/{reportId}` 落地后仍有人依赖 `/reports/{M_IDX}` 响应形态** → 评估把后者收敛为纯重定向端点；
- **若 OSI 语义层推进到报表分类粒度** → 复核 D8 的分类是否需与度量口径域对齐；
- **R8 删除后若发现审计/日志里的"孤儿模块号"被当成数据错误** → 在文档与门禁里显式声明"这是设计允许的保留痕迹"（D13）；
- **有人按"编号尾数 98"（而非 D13 的谓词原文）组织删除** → 立即停止：该放宽会命中 `14998` / `16998` 两个真功能模块，其中 `14998` 有代码硬编码常量；
- **`MODULES_Backup_ADR004` 等历史备份表与 `MODULES` 的一致性** → R8 执行时决定是否同步清理；
- **若有人要求在 `REPORT` 上加"表 / 字段来源"列**（例如为了让一张报表查另一张表）→ 按 D14 拒绝，改走 `ReportAggregateRegistry` 或拆成两个模块。
