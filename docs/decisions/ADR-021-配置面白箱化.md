## 摘要（先读我，写给人类）

**要解决的问题**：2301 的配置面今天是**实现层编辑器**——配置者要填"目标表.字段 += 本单明细.字段（合计）
@定位键 ?条件"，要从 **50 个效果键**里挑一个（其中 30 个全库只被用过一次），要从 **16 种**"解批怎么反悔"
里挑一种（而每个功能键实际只认其中几种），参数是一段没人解释过含义的 JSON。

后果有三条，都很具体：

1. **学不会**：目录的规模等于特例的数量。真正被反复使用的是 6 个原语（占 77% 的动作行），
   其余是长尾——一个只用过一次、还带自己一套 JSON 结构的键，**不是原语，是穿配置外衣的一次性代码**。
2. **看不到**：配置者配完只能靠真单据验证。现有的"影响面自检"是**静态**的——它只回答
   "会不会被拒"，回答不了"会不会得到你要的结果"。
3. **不敢配**：解批语义的真实差异写在**引擎根本不读**的自由文本 `note` 里（实测 20+ 种写法）；
   反向 kind 的合法组合随 Handler 而变，却只在**运行时**才拒绝。

**本 ADR 的决定，用一句话说**：

> 给配置面装一面镜子——**能在一张真单据上预演**（跑完回滚，看得见改哪张表哪一行、旧值变新值）、
> **把每个键的说明与合法组合随目录一起下发**（选不到不该选的组合、不用读源码就知道参数什么意思）、
> **给出一份这张单会发生什么的说明书**（可读、可交接、可评审）。

**打个比方**：

- 过去配效果链像**闭着眼睛改电路**——改完只能通电看会不会炸；
- 装上预演之后像**先接上示波器**——每一步通没通、电流从多少变成多少，看得见，而且**没有真的通电**（回滚）；
- 契约下沉则相当于**给每个元件贴上规格标签**——"这个接口只能接 5V，别接 220V"，
  而不是等到烧了才知道。

**与 AI 工作助手的关系（重要）**：预演**不是为了给 AI 用，而是为了让人能看懂**。
但它是 ADR-016 决策 13 B5 给 AI 配置写能力开的**准入门槛**（"幂等键 / 审计同事务 / 预演能力"三缺一不得准入）。
换言之——**先给人做白箱，AI 才不是黑箱**。反过来说：如果先给 AI 开写权限而不做预演，
那就只是把当前的上手难度换成了**风险**。

**本 ADR 定与不做**：

- ✅ 已定：预演端点契约（§3.1）、`EffectStepResult` 扩展（§3.2）、`/schemas` 新增下发字段（§3.3）、
  发布校验新增项（§3.4）、说明门禁（§3.5）、权限门按写面收口（§5.2）、
  预演必须连状态翻转一起做再回滚（§4.2）。
- ❌ 不做：`SAVE` 事件预演、草稿预演、批量预演（§8）；不改效果引擎执行语义（§4.1）；
  不做业务配方层与目录收敛（属后续批次，见 §10）。

**阅读路线**：业务/顾问读摘要、§1、§2、§7；实现者读 §3–§6、§9、§8。

## 1. 背景与调研事实

### 1.1 复审取证（2026-09-25，连 `EOS.ERP` 直查 + 代码核对）

| 项 | 实测 | 含义 |
|---|---|---|
| 在用的效果键 | **50 个**；其中 **30 个只用过 1 次**、8 个用过 2 次 | **76% 是单例键**——目录规模等于特例数量 |
| 头部集中度 | `field-accumulate` 127 / `inventory-move` 44 / `completion-close` 40 / `adjust-projection` 24 / `set-state` 18 / `balance-adjust` 9 ＝ **262/341 ≈ 77%** | 真正被反复使用的是 6 个原语 |
| 动作行分布 | `APPROVE_EFFECT` 276 / `SAVE` 47 / `MANUAL` 15 / `DEAPPROVE` **3** | 反向主要挂在 action 级 `REVERSE_STRUCT` 上，`DEAPPROVE` 事件行几乎不用——**同一概念两个入口** |
| 反向 kind | 16 个闭集枚举，实际写下 **20+ 种自由文本 `note`**；`note` 在 `EOS.API` **零处被读取** | 真实语义写在**引擎不读**的地方 |
| kind 的合法性 | `car-filloil-sync`/`detail-field-sync` 只接受 `restore-previous`；`change-apply` 族只接受 `none`/`no-reverse`；`set-state` 另认 `clear-finish`；`balance-adjust` 对 `none`/`no-reverse` 短路——**均在运行时抛错** | 名义闭集 ≠ 执行闭集 |
| 参数契约 | `EffectStructSchemas` 仅做**根键白名单**，"深度 Schema 随效果注册细化"＝仍未做；`detail-flag-and-rollup` 12 个根键、`stocktake-scope-generate` 15+ | UI 只能给"根键展开 + 专家模式 JSON" |
| 目录说明 | `BusinessActionLabels` 每个效果键只有**一行短语** | 界面里没有说明、没有参数语义、没有示例 |
| 反馈回路 | `businessActionImpact.ts` 注释自陈「这是**静态影响面**，不是真库试算——它不连库、不改数据」 | 配完只能靠真单据验证 |

### 1.2 复杂度归因（决定"哪些能消除"）

| 类型 | 例子 | 处置 |
|---|---|---|
| **领域固有** | "收料批核后回写采购单已收量、超量要拦、收满要结案" | 不可消除，只能**承载** |
| **设计引入** | 抽象层次倒置（暴露表/列/算子）、目录退化为特例清单、闭集只闭一半、一义两表 | **可消除，本 ADR 处理前两项** |
| **机制引入** | 版本↔证据耦合、权限位列式扩展、整份替换遇多页签 | 可消除，属后续批次（§10） |

### 1.3 为什么先做这一批（顺序理由）

1. **不动引擎**：本 ADR 只增加一条"事务内执行后回滚"的路径、一层目录数据、一个只读视图；
   执行语义零改动（`§4.1` 把这一点写成硬约束）。
2. **它是 AI 配置的前置**：ADR-016 决策 13 B5 已把"预演能力"列为配置类写端点的准入门槛。
   为人类做一次，AI 直接搭便车。
3. **后续批次都依赖它**：改目录、统一反向、改并发语义，都需要"改完会发生什么"的验证手段；
   没有预演，每一次改动都只能靠真库对拍兜底。

## 2. 决策

### 2.1 三项交付

1. **效果链预演**（§3.1–§3.2、§4–§6）：对一张真实单据，在**同一事务内**跑真实的
   「前置守卫 → 校验闸 → 状态翻转 → 效果链」，随后**无条件回滚**，返回逐步报告。
2. **契约下沉**（§3.3–§3.5）：效果键的参数说明与反向兼容矩阵随目录下发；
   界面选不到不合法的组合；说明缺失由门禁拦下。
3. **行为说明书**（§3.6）：一个只读汇总，把这个模块**所有事件会发生什么**渲染成人话，可复制为 Markdown。

### 2.2 一句话边界

> 预演是**镜子里跑一遍**，不是"试着做一次"。它**永远不落库**，也**不替代**真实执行。

## 3. 契约冻结（实施前冻结，改契约必须先改本节并升版本）

> 本节照 ADR-018 §11.1（WS-0 冻结）的做法：先冻成文字与骨架，再写实现。

### 3.1 预演端点

```
POST /api/v1/admin/module-business-config/{moduleId}/simulate
权限门：CanSetup(2301) && CanModuleConfig          （见 §5.2）
Body: { "event": "APPROVE_EFFECT" | "DEAPPROVE",   // 闭集，仅此二值
        "key": ["PR20260101"] }                    // 单据主键，与读取/保存同格式
```

- `event` 越界 → `400` + `SIMULATION_EVENT_UNSUPPORTED`（**不接受 `SAVE` / `MANUAL` / `ENDCASE` / `UNENDCASE`**，理由见 §8）。
- `key` 数量与 `definition.masterPkOrder` 不符 → 复用既有 `INVALID_RECORD_KEY`。
- 单据不存在 → **不返回 4xx**，见 §3.2 的 `precondition`（报告本身是产品，用户需要从报告里读到原因）。
- 执行超时 → `504` + `SIMULATION_TIMEOUT`。**锁等待超时（SQL 1222）、命令超时（-2）与总预算用尽
  三者都必须映射到这里**，不得退化成 500——用户看到的应是"这张单太大或被锁住"，而不是内部错误。
- 模块没有已发布定义 → `404` + `MODULE_DEFINITION_NOT_PUBLISHED`。
- 模块没有主表（无法定位单据）→ `400` + `MODULE_NOT_SIMULATABLE`。
- **该模块的这条路径本就不执行效果链** → `400` + `SIMULATION_NOT_SUPPORTED`（判据见 §4.2）。

### 3.2 响应形状（200）

```jsonc
{
  "moduleId": 1607,
  "event": "APPROVE_EFFECT",
  "definitionVersion": "v7",            // 预演所依据的**已发布**定义版本（不做草稿预演，见 §8）
  "recordKey": ["PR20260101"],
  "durationMs": 42,
  "rolledBack": true,                   // 恒为 true；为 false 即框架缺陷，前端须显眼提示

  // 三道闸，按真实链路的先后顺序：前置守卫 → 校验闸 → 效果链
  "precondition": { "passed": true, "code": null, "message": null },
  "validation":   { "passed": true, "message": null },

  "effects": [ /* EffectStepTrace[]，见下；precondition 或 validation 未通过时恒为空数组 */ ],

  "counts": { "total": 12, "ran": 9, "skipped": 2, "failed": 1 },
  "warnings": ["服务型效果只报告影响行数，不含字段级差异"]
}
```

**`precondition`**：复刻真实路径在开事务**之前**与翻转**之时**的全部门槛，`code` 原样透传既有错误码，不新造：

| 场景 | code | 出处 |
|---|---|---|
| 主表缺 `CONFIRM_TAG` | `LIFECYCLE_COLUMN_MISSING` | `WorkbenchApprovalService:166-170` |
| 单据不存在 | `RECORD_NOT_FOUND` | 同上 `:172-176` |
| 批核一个已批核单据 | `WORKFLOW_STATE_CONFLICT` | 同上 `:177-183` |
| 解批一个未批核单据 | `WORKFLOW_STATE_CONFLICT` | 同上 `:184-188` |
| 解批被 NOT_BACK 守卫拦下 | `NOBACK_BLOCKED` | 同上 `:191-196`、`:544` |
| 已结案拒绝解批 | `FINISHED_RECORD_NOT_DEAPPROVABLE` | 同上 `:362` |
| 事务内翻转守卫命中 0 行（并发） | `WORKFLOW_STATE_CONFLICT` | 同上 `:215-223` |

**`validation`**：阶段校验闸（`EffectEngineInvoker.ValidateStageAsync`）。被拦时 `passed=false`、
`message` 为校验器原文，且 **`effects` 为空**——与真实语义一致（被拦时效果链根本不跑），
**不得**"顺便把效果也算出来"给用户看。

**`EffectStepTrace`**：

```jsonc
{
  "seq": 1,
  "effectKey": "field-accumulate",
  "effectName": "量额/日期累加回写",
  "enabled": true,
  "failMode": "BLOCK",
  "outcome": "ran",            // ran | skipped | failed
  "condition": "{\"type\":\"field-compare\",...}",  // 原始条件 JSON，**原样透传**，由前端渲染人话
  "conditionMatched": true,    // 无条件时恒 true
  "skipReason": null,          // outcome=skipped 时必填：人手可读的原因
  "rowsAffected": 2,
  "message": null,             // outcome=failed 时的错误文案
  "ops": [ /* EffectOpTrace[]，仅公式型效果有；服务型恒为空数组 */ ]
}
```

**`EffectOpTrace`**：

```jsonc
{
  "opSeq": 1,
  "targetTable": "PUR_PURCHASE_D",
  "targetField": "RECEIVE_QTY",
  "opCode": "ACCUM",
  "rowsAffected": 2,
  "changes": [                 // 仅公式型效果、仅预演模式采集；上限见 §4.4
    { "identity": "PURCHASE_NO=PO2026001, PURCHASE_ITEM=10",
      "columns": [ { "name": "RECEIVE_QTY", "before": 120, "after": 150 } ] }
  ]
}
```

- `identity` 取值规则：**优先用目标表主键**（按 `key_ordinal` 序，`列=值` 以 `, ` 连接）；
  目标表无主键时回落用该公式行的**定位键列**；两者皆无时用 `"<无标识>"`。
- `columns` 只含**真正发生变化的列**；未变化的列不出现在 `changes` 里。

### 3.3 `EffectStepResult` 扩展

```csharp
public enum EffectStepOutcome { Ran, Skipped, Failed }

public sealed record EffectStepResult(
    int Seq, string EffectKey, bool Success, string? Warning, int RowsAffected,
    EffectStepOutcome Outcome = EffectStepOutcome.Ran,   // 默认值：既有调用点不感知
    string? SkipReason = null,
    bool ConditionMatched = true,
    IReadOnlyList<EffectOpTrace>? Ops = null);           // 仅预演模式填充；正常路径为 null
```

**硬约束**：全部新增参数**必须带默认值**，既有调用点与既有断言**不得需要修改**。
这是"不改引擎语义"（§4.1）在类型层面的落点。

### 3.4 `/schemas` 新增下发字段

```csharp
public sealed record EffectParamFieldDto(
    string Name, string Type, bool Required,
    IReadOnlyList<string>? EnumValues = null, string? Default = null,
    string? Description = null, string? Example = null);

public sealed record EffectParamFieldsDto(
    string EffectKey, IReadOnlyList<EffectParamFieldDto> Fields);

// BusinessConfigSchemasDto 追加两个可选字段（缺省 null，老前端不感知）：
//   paramFields:          IReadOnlyList<EffectParamFieldsDto>?
//   reverseKindsByEffect: IReadOnlyDictionary<string, IReadOnlyList<string>>?

// BusinessConfigLabelsDto 追加两个可选字段：
//   effectKeyDescriptions:  IReadOnlyDictionary<string, string>?
//   reverseKindDescriptions: IReadOnlyDictionary<string, string>?
```

- `Type` 闭式：`string | number | boolean | array | object | fieldRef | tableRef | fieldMap`。
- **只登记能确证语义的键**；没有登记的效果键保持现状（根键展开 + 专家模式 JSON），
  **不得**为凑覆盖率瞎填说明。这是渐进式的，不是一次性全覆盖。

**订正记录（2026-09-27，批次 2B 执行期）**：`link-stamp.targetTable` 与 `set-state.targetTable`
两个 descriptor 原标 `Required=true`，与存量配置**不符**——库内 **23/23 行**（5 + 18）全部使用
`targets[]` 形态，无一行使用 `targetTable`。描述层比现实更严会让界面/校验**误拦存量**，
故按"修描述层、不放宽实现"的原则把这两项改为**选填**，并在 `description` 写明
"两种形态二选一、`targets[]` 为主"。**改动仅是 descriptor 的取值与文案**：
`/schemas` 的形状、字段名与既有字段一个未动（`paramFields` 仍是可选字段），前面各节契约不变。

### 3.5 发布校验新增项

| check 名 | 含义 | 级别 |
|---|---|---|
| `effect_reverse_kind_supported` | `MODULE_BUSINESS_ACTION` 中每个非 `MANUAL` 行的 `REVERSE_STRUCT.kind`，必须落在该 `EFFECT_KEY` 的兼容集合内 | **按 §9-3 的拍板：盘点 0 违规 → BLOCK；非 0 → WARN + 棘轮，修完转 BLOCK** |

### 3.6 行为说明书

- **载体**：2301 表单工具栏「行为说明书」按钮 → **只读抽屉**。**不新增页签**（ADR-019 已定 8 个为上限）。
- **数据源**：既有 `GET /admin/module-business-config/{moduleId}` + `/meta` + `/schemas`，**不新增后端端点**。
- **内容**：按事件分组，渲染该模块的**校验规则 + 效果链（含反向人话）**，覆盖三个行为页签的全部内容；
  支持「复制为 Markdown」。
- **渲染复用（硬）**：**只允许**复用 `EOS.Web/src/features/menu-admin/businessActionText.ts` 的
  `formatOpSentence` / `formatMatch` / `formatCondition` / `makeNameLookup`。
  预演报告与说明书**必须说同一种话**——两处各写一套渲染就会漂移成两种说法。

**实施口径与已接受的三处偏差（2026-09-25 验收时判定，补记以免文档与实现两说）**：

| # | 本节原文 | 实际实现 | 判定与理由 |
|---|---|---|---|
| 1 | 只读**抽屉** | 只读 `Modal`（`size="xl"` + `scrollable`） | **接受**。仓库 `components/ui/` **没有 Drawer 原语**，为一次交付新建 UI 原语超出批次边界；功能等价（只读、可滚动、可复制为 Markdown） |
| 2 | 入口在 **2301 表单工具栏** | 入口在 `BusinessActionsPanel` 的**面板工具栏**（图标注：`行为说明书`） | **接受**。说明书汇总的正是该面板内三个行为页签的内容，入口贴近被汇总的对象更好找；副作用是**两表皆空模块没有入口**——但这类模块本就没有行为可汇总（面板对其整体不渲染），无实际损失 |
| 3 | 覆盖三个行为页签的**全部内容** | 效果链与自定义按钮段完整；**校验规则段是单一平铺列表**（`阶段 #序号 · 模板`），**未按事件/阶段分组、未渲染 `params`** | **接受但记录在案**：这是本节"全部内容"这句话的**实质收窄**——校验规则的参数恰恰是配置者最需要复核的部分。视为已知缺口，**列入 §10 后续批次（R10 UI 入门路径）时一并补齐**，不在本 ADR 内追补 |

> 第 1、2 条是形式差异，第 3 条是内容收窄。三条都**没有**改变本 ADR 的验收结论
> （§6.1 的七条功能验收与 §6.2 的判别力全部成立），但当时的验收记录只写在会话里、未落本文，
> 故在此补记——避免后来人从本节原文推断出"实现里有抽屉、有 params"。

## 4. 关键实施约束

### 4.1 不改引擎执行语义（硬）

允许的只有两类改动：

- **提取**：把 `WorkbenchApprovalService.RunEngineApprovalAsync`（`EOS.API/Data/WorkbenchApprovalService.cs:150-244`）
  的**事务内核心**（校验闸 → 翻转 `CONFIRM_TAG` → 效果链 → 收集步骤）提为可复用方法（**不 commit**），
  原方法改为"建连接 → 建事务 → 调核心 → commit"，**行为逐字不变**。
- **增量**：`EffectStepResult` 加带默认值的字段（§3.3）；trace 采集**仅在预演模式**开启，
  正常路径**零额外开销**。

任何"顺手优化一下执行逻辑"的改动一律拒绝。既有后端用例必须全绿**且无需修改**。

### 4.2 预演必须连状态翻转一起做再回滚（硬）

真实批核链是「校验闸 → 状态翻转 → 效果链」。**预演不能只跑效果链**——
效果链里的条件可能引用 `CONFIRM_TAG`，不翻转就求值会得到**错误答案**（而错误答案比没有答案更糟）。

同理，解批前的 `CheckNotBackFieldsAsync` 守卫必须在事务**之前**复刻（真实路径就在事务外做），
否则会出现"预演说能解批、真点却 `NOBACK_BLOCKED`"。

**分流判据（2026-09-25 回填，实施时补出）**：真实批核入口不是"只有一条链"——
`WorkflowCoreAsync` 在跑效果链之前先按三种形态分流，**只有引擎接管那一条会执行效果链**：

| 真实路径分支 | 真实行为 | 预演必须 |
|---|---|---|
| 无副作用批核（`IsStatelessApproveCapable`） | 只翻转状态位 | **拒绝**（`SIMULATION_NOT_SUPPORTED`） |
| 模块未启用效果引擎 | 不执行效果链 | **拒绝** |
| 已配审批流程且非自动批核（批核方向） | **送审**（启动流程，不翻转、不跑效果链） | **拒绝** |

判据必须与真实路径**同源**（同一批 `WorkflowStates` / `WorkflowEngine` / `EffectEngineInvoker` 调用），
不得在预演侧另写一份近似判断——两份判据一旦漂移，预演就又开始给错误答案。
拒绝要带可读原因，让配置者知道"不是系统坏了，是这条路径本来就没有效果链可看"。

> **缺口记录**：本 ADR v1 只写了"必须连状态翻转一起做再回滚"，**没有枚举上述分流**，
> 实施方按 §4.2 字面实现了一个更宽的链路。这是本 ADR 的缺口，不是实施方的偏离；
> §3.1 新增的 `SIMULATION_NOT_SUPPORTED` 与本节表格即为回填。

### 4.3 回滚保证（硬）

- `try { ... } finally { rollback }`，**任何异常路径都必须回滚**；`rolledBack` 字段如实回报。
- **不写审计**：`AUDIT_EVENT` 在事务内，随回滚消失——这是**有意设计**。
  改为记一条 **Information 级文件日志**（模块 / 事件 / 单据键 / 操作者），供"谁把库拖慢过"追查。
- **不标脏、不顶快照版本、不触发任何 `job-enqueue`**。

### 4.4 超时与资源边界

- `SET LOCK_TIMEOUT` + 命令超时 + 端点总时长上限；超时按 `SIMULATION_TIMEOUT` 返回，
  **不得**退化成部分执行。
- `changes[]` 每步每列的上限（建议每公式行最多 50 行变更），超出即截断并在 `warnings` 里说明。
- **不提供批量预演**（§8）。

### 4.5 事务安全前提（已核实，实施时仍须逐文件复核留证）

**已核实**：`EOS.API/Data/Effects/` 下**只有 `EffectPipeline` 建连接**（`:70-71`，且预演走的是
`ExecuteWithinTransactionAsync` 这条接收环境事务的路径）；`EffectPhysicalColumns.cs:51` 只开只读元数据连接。
**全部服务 Handler 都不自带连接**，因此"同事务执行后回滚"是**完整**的。

**仍须执行方做的事**：逐个复核 `Effects/ServiceEffectHandlers/` 下每个 Handler 与
`EffectFormulaExecutor` / `EffectValidationExecutor` / `WorkbenchAuditWriter`，**逐文件留证**，
不要只写一句"已确认"。这是本 ADR 全部安全论证的地基——**它不成立，整个方案作废**。

**为未来设防**：新增任何"自带连接"的效果 Handler 时，必须同时在 `EffectSimulationService` 的
集成用例里声明其预演行为；否则预演会漏出真实副作用。

## 5. 安全与失败语义

### 5.1 预演的定位

预演是**只读诊断**（不落库），但**会执行真实代码**（跑真实 Handler、在事务里短暂锁行）。
这两条同时成立，是本 ADR 全部权限与超时设计的出发点。

### 5.2 权限门按写面收口（2026-09-25 拍板）

**`CanSetup(2301) && CanModuleConfig`**（不是 `CanBrowse`）。三个理由：

1. **与既有边界一致**：ADR-019 §5.2 已定"只有配置权、没有设置权"的账号**能读不能存**；
   预演归写面，口径统一，不新造一档角色。
2. **今天零代价**：库内 2301 实测仅 `SYSDD` 1 行（admin）+ `SYSDH` 1 行（组 1），两档无实际差别。
3. **为未来设防**：一旦有人新增"自带连接"的 Handler（§4.5），预演会漏出真实副作用；
   门设在写面，能触发它的账号最少。

### 5.3 失败语义汇总

| 情形 | 返回 | 说明 |
|---|---|---|
| 前置守卫不通过 | `200` + `precondition.passed=false` | 报告要完整，用户需要读到原因 |
| 校验闸拦截 | `200` + `validation.passed=false` + `effects=[]` | 与真实语义一致 |
| 某效果步骤失败（BLOCK） | `200` + 该步 `outcome=failed` + `message`，**且 `effects` 非空**（已跑的步骤照常回报） | 后续步骤不再执行（与真实链路一致）。**不得**把它归到 `precondition`——那会让"第几步失败"这个用户最需要的信息消失在"前置守卫没过"里 |
| 某效果步骤失败（WARN） | `200` + 该步 `outcome=failed` + 续跑 | 与真实链路一致 |
| 事件越界 | `400` `SIMULATION_EVENT_UNSUPPORTED` | |
| 主键个数不符 | `400` `INVALID_RECORD_KEY` | 复用既有码 |
| 模块无已发布定义 | `404` `MODULE_DEFINITION_NOT_PUBLISHED` | 预演只认已发布定义（§3.2） |
| 模块无主表 | `400` `MODULE_NOT_SIMULATABLE` | 无法定位单据 |
| 该路径不执行效果链 | `400` `SIMULATION_NOT_SUPPORTED` | 判据见 §4.2；带可读原因 |
| 超时（锁等待 / 命令 / 总预算） | `504` `SIMULATION_TIMEOUT` | 三种都要映射，见 §3.1 |
| 无权限 | `403` | 由门统一处理 |

## 6. 验收口径

### 6.1 功能验收

1. **零残留（硬）**：对真实模块、真实单据预演，**预演前后逐表逐列比对完全一致**（落成断言，不是人工看一眼）。
2. 步骤总数与配置一致；`skipped` 的步骤给出可读原因。
3. **"条件未命中"与"匹配 0 行"必须可区分**（`conditionMatched` 字段 + `skipReason`）。
4. 校验闸拦截时 `effects` 为空。
5. 解批预演对"未批核单据"给出与真实路径**同码**的拒绝。
6. 失败注入：让某 Handler 抛错，断言 `rolledBack=true` 且库内零变化。
7. **既有后端用例全绿且无需修改**（§4.1 的判别标准）。

### 6.2 判别力（验收方会做的反向自检）

> 依据仓库既有验收传统：**把修复打回去，看用例会不会红**。

| 注入 | 期望 |
|---|---|
| 把"条件未命中"改回返回 `0`（与"0 行"混淆） | 区分类用例**变红** |
| 去掉公式型效果的旧值→新值采集 | diff 用例**变红** |
| 去掉预演的 `finally { rollback }` | 零残留用例**变红** |
| 从兼容矩阵删掉一条子集约束 | 保存/发布期拒绝用例**变红** |
| 删掉任一效果键说明 | `check-effect-descriptions.ps1` **exit 1** |

### 6.3 结论口径

验收通过 = 证据齐备 + 判别力成立。**任何"自述通过但拿不出命令与输出"的判为未验**；
需真机（界面点击）而 API 未启动的项登记为"待用户启动后验证"，**不计失败，也不得计通过**。

## 7. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 预演在库上留下副作用 | 任何 Handler 自带连接就会漏出事务 | §4.5 已核实当前**零处**；仍要求逐文件复核留证 + 新增 Handler 由集成用例兜底 |
| 预演拖慢/锁住生产库 | 大单据（如 1406 = 12 效果 / 41 公式行）在事务内跑 | §4.4 `LOCK_TIMEOUT` + 超时上限；不提供批量预演 |

| 兼容矩阵收紧判死存量配置 | 存量 327 行 `REVERSE_STRUCT` 可能有落在集合外的 | §9-3：**先盘点后收紧**；有违规先 WARN + 棘轮，**禁止静默 BLOCK** |

| 用户把预演当"已执行" | 误以为点过就生效 | 报告顶部固定声明 + `rolledBack` 字段 + 按钮文案「预演（不改数据）」 |

## 8. 明确不做（本 ADR 边界）

- **不做 `SAVE` 事件预演**：`SAVE` 链在 `WorkbenchCommandHandler` 里跑，位于"主子表落库**之后**、
  同一事务内"。预演它等于**伪造一次完整保存**（幂等占位、范围过滤、主子表写入、必填校验、单号生成），
  风险与工作量远超批核链；且有一条真坑——**单号序号 `BILL_NO_SEQUENCE` 是否随事务回滚必须先核实**，
  否则预演会真实消耗单号。本 ADR 覆盖 `APPROVE_EFFECT` 276 + `DEAPPROVE` 3 = **279/341 ≈ 82%** 的动作行。
  > **但"不做"不等于"不说"**：界面上必须对 `SAVE` 事件的效果行标注「保存后效果暂不支持预演」并说明原因与计划。
  > **不允许**出现"点了没反应"或"灰掉不说为什么"——那会把一个已知的批次边界变成用户眼里的故障。
- **不做草稿预演**：只用**已发布定义**。"我这次改完会发生什么"属后续批次。
- **不做批量预演**（一次跑多张单据）。
- **不做业务配方层、不做目录收敛、不改反向语义模型**——属后续批次（§10）。
- **不拆模块号、不新增权限位、不新增页签**。
- **不开放任意 SQL/表达式配置**（ADR-012 §3 边界继续有效）。
