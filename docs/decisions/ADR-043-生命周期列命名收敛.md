# ADR-043：单据生命周期列命名收敛（物理列 + 元数据 + 引用）

- 状态：已接受（2026-10-25 用户拍板；本文是可执行方案，落库以迁移 451 为准）
- 日期：2026-10-25
- 决策者：用户（Larry）+ 开发 Agent
- 相关：ADR-013（单据生命周期列规约）、ADR-022（统一表单版式）、ADR-035（批核模型收敛）、ADR-036（共享原语单一真源）、ADR-042（生命周期字段的呈现收敛）
- 取代：ADR-013 的**列名部分**、ADR-042 正文中的旧列名；两篇的语义、空值口径与呈现规则继续有效

## 1. 背景与决策

生命周期列在历史迁移中先后使用过 `CREATE_PERSON/CREATE_DATE`、`LAST_UPDATE_BY/LAST_UPDATE_DATE`、
`CONFIRM_*`、`FINISHED_*` 等不同命名，部分审计表又使用 `CREATE_BY`、`CREATED_AT`、`UPDATED_*`、
`LAST_MODIFIED_*`。这些名字表达同一组语义，却在物理列、元数据、配置和审计里各写一套。

本 ADR 决定**物理列、字段元数据、配置引用、代码引用一起改**，不做“只改元数据映射”、
不保留新旧双列、不建兼容视图。改名使用 `sp_rename`（元数据操作，数据不搬），保留现有数据、
索引与默认值。

用户 2026-10-25 明确：

1. 系统中现有 `CONFIRM_*` **全部是批核语义**，不存在“部分是批核、部分是确认”的分叉；
   因此不引入 `CONFIRMED_*`，统一归入 `APPROVED_*`，73 张表的“确认”标签一并改成“批核”。
2. 审计**动作码**不改；动作码是事件类型，不是字段名。`ACTION_CONFIRM` 表示“用户确认助手动作”，
   不是批核，不能改成 `APPROVED`。
3. 历史审计**不改写**：`AUDIT_FIELD_CHANGE.FIELD_NAME` 等历史值保留原样，新写入使用新字段名。

## 2. 命名与语义

### 2.1 目标列名（纯大写）

| 旧列名 | 新列名 | 说明 |
|---|---|---|
| `CREATE_PERSON` | `CREATED_BY` | 建立人 |
| `CREATE_DATE` | `CREATED_TIME` | 建立时间（实际类型保持 `datetime`/`datetime2`，不是 SQL `time`） |
| `LAST_UPDATE_BY` | `MODIFIED_BY` | 修改人 |
| `LAST_UPDATE_DATE` | `MODIFIED_TIME` | 修改时间 |
| `CONFIRM_PERSON` | `APPROVED_BY` | 批核人 |
| `CONFIRM_DATE` | `APPROVED_TIME` | 批核时间 |
| `CONFIRM_TAG` | `APPROVED` | 批核状态位 |
| `FINISHED_PERSON` | `FINISHED_BY` | 结案人 |
| `FINISHED_DATE` | `FINISHED_TIME` | 结案时间 |
| `FINISHED_TAG` | `FINISHED` | 结案状态位 |

### 2.2 审计/框架表的同义列

| 旧列名 / 位置 | 新列名 |
|---|---|
| `CREATE_BY`（`FIELD_DATASOURCE`、`KB_DOCUMENT`） | `CREATED_BY` |
| `CREATED_DATE`（`AUDIT_EVENT`） | `CREATED_TIME` |
| `CREATED_AT`（`ASSISTANT_*`、`WORKBENCH_IDEMPOTENCY`） | `CREATED_TIME` |
| `UPDATED_BY`（`ASSISTANT_*`、`FORM_CHOOSER_SOURCE_MEMO`、`MODULE_FORM_LAYOUT`） | `MODIFIED_BY` |
| `UPDATED_AT`（同上） | `MODIFIED_TIME` |
| `LAST_MODIFIED_BY` / `LAST_MODIFIED_AT`（`WORKBENCH_MODULE_DIRTY`） | `MODIFIED_BY` / `MODIFIED_TIME` |
| `CONFIRMED_BY` / `CONFIRMED_DATE`（`REPORT_METRIC`） | `APPROVED_BY` / `APPROVED_TIME` |
| `PUBLISHED_BY` / `PUBLISHED_AT`（快照） | **不改**；发布审计不属于这四组（如需统一后缀另立提案） |

### 2.3 中文标签

`FIELDS.F_DESC` 按新列名归一（`F_TYPE`、`DISPLAY_FORMAT`、必填/只读等属性保持不动）：

| 新列名 | 标签 |
|---|---|
| `CREATED_BY` | 建立人 |
| `CREATED_TIME` | 建立时间 |
| `MODIFIED_BY` | 修改人 |
| `MODIFIED_TIME` | 修改时间 |
| `APPROVED_BY` | 批核人 |
| `APPROVED_TIME` | 批核时间 |
| `APPROVED` | 批核状态 |
| `FINISHED_BY` | 结案人 |
| `FINISHED_TIME` | 结案时间 |
| `FINISHED` | 结案状态 |

- `CONFIRM_*` 的“确认人 / 确认日期 / 确认状态”全部改成“批核人 / 批核时间 / 批核状态”
  （73 张表；用户已确认全部是批核语义）。
- `FINISHED_*` 的“确认人 / 确认日期”改成“结案人 / 结案时间”（6 张表）。
- `COP_SHIPMENT_M.CREATE_DATE` 当前标签是“出货日期”（`F_REMARK` 写的是“建立日期”），
  实际值是建立时间；统一为“建立时间”。
- `AUDIT_EVENT.CREATED_TIME` 的标签保留“落库时间”，表示审计行写入时间，不改成“建立时间”。

`APPROVE_ENABLED = 0` 的模块仍拥有 `APPROVED` 列，只是没有批核入口；本次只改列名/标签，
不改能力位、按钮显隐或 `canApprove` 权限。`FINISHED` 同理。

### 2.4 明确不改的列

以下同名列**不是**这四组生命周期列，机械替换会改错语义：

| 列 | 原因 |
|---|---|
| `MODULE_BUSINESS_ACTION.CONFIRM_TAG` | 自定义动作“点击前确认”的配置位；`DocumentActionExecutor` 的 probe 逻辑使用，348 行配置在用 |
| `APPROVE_TAG` / `DEAPPROVE_TAG` / `ENDCASE_TAG` / `UNENDCASE_TAG` | 权限位，不是单据状态列 |
| `APPROVE_DATE` / `APPROVE_MSG` / `APPROVE_NO` / `APPROVE_POWER` / `APPROVE_STATE` / `APPROVER` / `AUTO_APPROVE` | 工作流/业务列，不是本组 |
| `CONFIRM_STATUS` / `IF_CONFIRM` / `CLIENT_CONFIRM` / `SUPPLIER_CONFIRM` | 业务/流程列，不是本组 |
| `FINISHED_QTY` / `FINISHED_AMOUNT` / `FINISHED_*_QTY` 等 | 数量/金额业务列，不是状态位 |
| `AUDIT_EVENT.ACTION` | 事件类型；`APPROVE`/`ENDCASE`/`ACTION_CONFIRM` 保持原值 |
| `AUDIT_FIELD_CHANGE.FIELD_NAME` 历史值 | 历史审计，不改写 |
| `AUDIT_EVENT.DETAIL_JSON` 历史字段快照 | 历史审计，不改写 |
| `PUBLISHED_BY` / `PUBLISHED_AT` | 发布审计，不属于这四组 |

## 4. 可执行方案

### 4.0 前置条件

1. 停写：API 停止对外服务（或进入维护页），后台任务、快照重发布、报表导出全部暂停。
2. 备份：`EOS.ERP` 全库备份 + 当前 `db/bootstrap/` 归档；记录备份文件名与时间。
3. 记录基线：对 297 张表记录行数，对 2,029 列记录 `COUNT(*)`/`COUNT(column)`/`SUM` 抽样校验和，
   保存为迁移前后对拍清单。
4. 预检：确认每张表不存在“旧名与新名并存”；确认 `MODULE_BUSINESS_ACTION.CONFIRM_TAG` 仍在

5. 备份当前 Web/API 构建，确保可回退到旧版本。

### 4.1 迁移 451：物理列改名

新增 `EOS.API/Data/Migrations/451_lifecycle_column_rename.sql`。用临时映射表 + 动态 SQL 执行，
不手写 2,029 条 `sp_rename`：

```sql
DECLARE @map TABLE (OldName sysname PRIMARY KEY, NewName sysname NOT NULL);
INSERT @map(OldName, NewName) VALUES
 (N'CREATE_PERSON', N'CREATED_BY'),
 (N'CREATE_DATE',   N'CREATED_TIME'),
 (N'LAST_UPDATE_BY', N'MODIFIED_BY'),
 (N'LAST_UPDATE_DATE', N'MODIFIED_TIME'),
 (N'CONFIRM_PERSON', N'APPROVED_BY'),
 (N'CONFIRM_DATE',   N'APPROVED_TIME'),
 (N'CONFIRM_TAG',    N'APPROVED'),
 (N'FINISHED_PERSON', N'FINISHED_BY'),
 (N'FINISHED_DATE',   N'FINISHED_TIME'),
 (N'FINISHED_TAG',    N'FINISHED'),
 (N'CREATE_BY',       N'CREATED_BY'),
 (N'CREATED_AT',      N'CREATED_TIME'),
 (N'CREATED_DATE',    N'CREATED_TIME'),
 (N'UPDATED_BY',      N'MODIFIED_BY'),
 (N'UPDATED_AT',      N'MODIFIED_TIME'),
 (N'LAST_MODIFIED_BY', N'MODIFIED_BY'),
 (N'LAST_MODIFIED_AT', N'MODIFIED_TIME'),
 (N'CONFIRMED_BY',    N'APPROVED_BY'),
 (N'CONFIRMED_DATE',  N'APPROVED_TIME');

DECLARE @schema sysname, @table sysname, @old sysname, @new sysname, @qualified nvarchar(300);
DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
SELECT s.name, t.name, c.name, m.NewName
FROM sys.columns c
JOIN sys.tables t ON t.object_id = c.object_id
JOIN sys.schemas s ON s.schema_id = t.schema_id
JOIN @map m ON m.OldName = c.name
WHERE s.name = N'dbo'
  AND NOT (t.name = N'MODULE_BUSINESS_ACTION' AND c.name = N'CONFIRM_TAG');

OPEN cur;
FETCH NEXT FROM cur INTO @schema, @table, @old, @new;
WHILE @@FETCH_STATUS = 0
BEGIN
    SET @qualified = QUOTENAME(@schema) + N'.' + QUOTENAME(@table) + N'.' + QUOTENAME(@old);
    EXEC sp_rename @qualified, @new, N'COLUMN';
    FETCH NEXT FROM cur INTO @schema, @table, @old, @new;
END
CLOSE cur; DEALLOCATE cur;
```

要点：

- `sp_rename` 只改元数据，数据、默认约束、索引不动；
- `MODULE_BUSINESS_ACTION.CONFIRM_TAG` 是唯一明确的动作配置例外，排除；
- `AUDIT_EVENT.CREATED_DATE` 在映射里改成 `CREATED_TIME`；
- 若列名已是新名（重复执行/异常），脚本先 `IF COL_LENGTH(...) IS NOT NULL AND 新列不存在` 再改，
  但**迁移只应执行一次**，不把幂等性当作回滚手段；
- 不使用 `ALTER TABLE DROP/ADD`，否则会丢数据/默认值/索引；
- 执行方式：`sqlcmd -i 绝对路径 -f 65001`（大脚本不要走管道）。

### 4.2 元数据与列配置

在同一个迁移事务内按顺序执行：

1. `FIELDS.F_ID` 按映射更新（1,957 行），`FIELDS.F_DESC` 按 §2.3 归一；
   `AUDIT_EVENT.CREATED_TIME` 标签保留“落库时间”；
2. `SYS_DEFAULT_COLUMN.F_ID`（1,767 行）与 `SYS_USER_COLUMN.F_ID`（1,615 行）按映射更新；
3. `FIELD_DATASOURCE.F_ID` 更新；`FILTER_STRUCT`、`RETURN_ITEMS` 做精确 token 替换（535 行）；
4. `SYS_REPORT_PARAMETER.F_ID` 更新、`F_EXPR` 精确替换（94 行）；
5. `MODULES` 的 `FILTER`、`SORT_FIELDS`、`DETAIL_NO_FIELDS`、`NOT_BACK_FIELDS`、`NOT_BACK_FIELDS_M`
   精确替换（19 行）；
6. `FIELDS.VIRTUAL_EXP` 精确替换（47 行）；
7. `REPORT.REPORT_FILTER` 精确替换（16 行）；
8. `MODULE_BUSINESS_ACTION` 的 `CONDITION_STRUCT`/`PARAM_STRUCT`/`REVERSE_STRUCT`（4 行）与
   `MODULE_VALIDATION_RULE.PARAM_STRUCT`（4 行）精确替换；
9. **删除** `MODULE_FORM_LAYOUT` 中 2,046 行旧生命周期行——它们已不参与版式，
   改名后会变成孤儿行；不映射到新名，直接删除；
10. `AUDIT_FIELD_CHANGE.FIELD_NAME` **不更新**（历史审计）；`AUDIT_EVENT.ACTION`、`AUDIT_EVENT.DETAIL_JSON` **不更新**。

替换必须是**精确字段名 token**（如 `"CONFIRM_TAG"` / `CONFIRM_TAG` / `m.CONFIRM_TAG`），
不能做 `CONFIRM` 前缀替换；`FINISHED_QTY`、`APPROVE_TAG` 等不在映射表中，保持原样。

可选清理（不影响功能）：329 个旧默认约束名、3 张表上的旧列索引名，可另用 `sp_rename` 改成新名；

### 4.6 `db/bootstrap` 基线

`db/bootstrap/10_schema.sql`、`20_metadata.sql` 是建库基线，含约 11,230 处旧名。迁移后：

1. 从迁移后的库重新导出 `10_schema.sql`、`20_metadata.sql`；
2. 更新 `40_journal_baseline.sql`，把 451 记录为已应用；
3. 新装库不应再经历一次“旧 schema → 451 改名”，否则基线长期落后。

若本轮不重生成，功能上新库可先建旧 schema 再跑 451 到位，但**不作为发布终态**。

### 4.7 验收

迁移后必须逐项核对：

3. `FIELDS` 旧 `F_ID` 为 0，新 `F_ID` 计数仍为 1,957；标签符合 §2.3；
4. `SYS_DEFAULT_COLUMN`/`SYS_USER_COLUMN` 旧 F_ID 为 0，行数不变；
5. `MODULE_FORM_LAYOUT` 生命周期旧行 0；
6. 10 个视图可查询；
7. `IS_CURRENT=1` 快照无旧字段名；
8. `AUDIT_FIELD_CHANGE` 历史 189 行仍在；`AUDIT_EVENT.ACTION` 值不变；
9. `MODULE_BUSINESS_ACTION.CONFIRM_TAG` 348 行仍在，动作确认行为不变；
10. 全量后端测试（当前 2,770）、前端测试（当前 1,327）、`lint`/`build`；
11. `check-lifecycle-columns`、`check-form-layout`、`check-field-labels`、`check-required-columns`、
    `check-inventory-read-hosts`、`check-snapshot-staleness`、`check-docs`；
12. 真库冒烟：1606 采购单、1304 月结单的浏览/新增/编辑/批核/结案/打印各一条。

### 4.8 回滚

- 迁移 451 是**不可逆的数据字典变更**；生产回滚以“恢复全库备份 + 回退旧构建”为准；
- 若必须原地回滚，另写 452 反向映射脚本，并在备份副本上先演练；
- 不要依赖 `sp_rename` 的重复执行或半程失败自动恢复；迁移必须在单一维护窗口内完成。

## 5. 工作量与风险

- 物理列 2,029 个、代码/脚本约 1,825 处、current 快照 262 份、视图 10 个、列配置 3,382 行；
- 预计 **5–8 个开发日**（含逐文件核对与全量回归），另需 **1–2 小时停机窗口**（含迁移与快照重发布）；
- 风险等级：**高**。主要风险是视图/快照未同步、`CONFIRM_TAG` 动作配置被误改、历史审计被误写、
  `db/bootstrap` 与迁移后 schema 不一致；
- 不涉及数据搬家，`sp_rename` 成功即数据保留；主要成本在“引用面”和“验证面”。

## 6. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 只改元数据映射，物理列保留旧名 | 用户明确要求物理列和元数据都改；映射会让后续代码继续面对两套名字 |
| 新旧双列 + 双写 + 逐步切换 | 2,029 列 × 双列、代码/配置双写，成本远高于一次维护窗口；本项目无在线零停机的硬约束 |
| 全库按前缀 `REPLACE` | 会误改 `MODULE_BUSINESS_ACTION.CONFIRM_TAG`、`APPROVE_TAG`、`FINISHED_QTY` 等语义不同的列 |
| 保留 `CONFIRMED_*` 与 `APPROVED_*` 分家 | 用户已确认现有 `CONFIRM_*` 全部是批核语义，不再保留确认分叉 |
| 同时改 `AUDIT_EVENT.ACTION` 动作码 | 动作码是事件类型；`ACTION_CONFIRM` 不是批核；历史审计不改写，改名只会制造两套解释 |
| 改写 `AUDIT_FIELD_CHANGE` 历史值 | 审计历史保留原值；新写入用新名 |

## 7. 后果

- `FormDefinition`/`RecordBundle` 的字段键变为新名，前端与外部调用方必须同版本部署；
- 报表过滤、打印版式、选择器回填、效果链、校验规则中的旧字段名全部随迁移更新；
- 历史审计保留旧字段名，新审计使用新名；需要跨新旧查询时按两套键处理，不做历史回写；
- `db/bootstrap` 必须与新 schema 对齐；`ADR-013`、`ADR-042` 加命名注记，正文历史保留。
