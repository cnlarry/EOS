## 1. 背景与事实

### 1.1 这份 ADR 要解决什么

三件事，本质是一件事：

1. **快照**：把某个时点的库存固化下来，让"上个月末是多少"成为一个可回答的问题；
2. **关账**：让已结期间的历史不再被改写——这才是月结的真正价值，出报表只是副产品；
3. **自证**：让"账对不对"成为一个可以被系统回答的问题，而不是靠人肉比对。

第 3 条是这份 ADR 与候选清单原案最大的差别。原案把月结定位成"客户要月度收发存报表就做"；实测之后结论变了——**没有期间锚点，库存账连"是否在恶化"都判断不了**（见 §1.5），所以前两条不是"锦上添花的功能"，而是自证能力的前置。

> **白名单一行的订正（2026-09-25 复核）**：原文写"**不在其中**（`appsettings` 无 1304 ⇒ 今日写入口 404）"——**与库、与代码都不符**。

> 门禁脚本读的是同一个键（`check-inventory-read-hosts.ps1:201 Get-UnifiedFormWhitelist`）。**两个后果**：
>
> 1. **P1-1「1304 进写入口」这一条多半已经不需要做**——它要证明的是"能建单、能填、能存"，而这条路今天就是通的；
>    真正没被证明过的是"**明细的库位 / 批次列在表单上可见**"（ADR-014 复查 D1 的同款问题），P1-1 应据此重新定义，
>    否则会按"入白名单"施工、做完发现无可验收；
> 2. **更关键的是反向风险**：`INV_PRO_MONTH_D` 的快照行经**通用表单直接落库**，不经过移动引擎、不产生流水、
>    也没有任何门禁拦它（`check-inventory-read-hosts` 的写路径断言只覆盖主/明细表是 `INV_PRO_DEPOT`/`INV_DEPOT_LOG`/`INV_BATCH_M`
>    的模块，月结两表**不在其列**）。也就是说：**在快照生成器写进去之前，人可以手工把任何数字填进月结明细**。
>    这与 §1.1 的"自证"直接冲突——一份可以被手工改写的"证据"不是证据。**故 §3.8 追加一条**：快照的派生列
>    （`QTY` / `PRICE`）必须只读，写入口只留"生成快照"按钮与生命周期动作。

**结论**：1304 是一个**有骨架、能录单、无行为**的单据——表、生命周期列、元数据、快照、单别、权限、菜单、**可写入口**全都在，缺的是"生成快照"与"关账"两件事。本 ADR 是给它装上行为，不是另起炉灶。

### 1.4 库存日报已经在依赖月结语义（只是靠不上）

`EOS.API/Data/ReportAggregateRegistry.cs` 的库存日报（`INV_Pro_Depot_1`，即模块 139901 / 报表口径）期初逻辑：

```293:309:EOS.API/Data/ReportAggregateRegistry.cs
MONTHROW AS (
    SELECT pa.DEPOT_ID, pa.PRO_NO, x.MONTH_DATE, x.QTY, x.PRICE
    FROM PAIR pa
    CROSS APPLY (
        SELECT TOP 1 m.MONTH_DATE, d.QTY, d.PRICE
        FROM dbo.INV_PRO_MONTH_M m
        JOIN dbo.INV_PRO_MONTH_D d ON ...
        WHERE d.DEPOT_ID = pa.DEPOT_ID AND d.PRO_NO = pa.PRO_NO AND m.MONTH_DATE < @date1
        ORDER BY m.MONTH_DATE DESC
    ) x
    WHERE EXISTS ( ... AND m.CONFIRM_TAG = 1 )
)
```

两个直接后果：

1. **期初的*意图*是「最近一期 `CONFIRM_TAG=1` 的月结 + 其后流水」**；而 `INV_PRO_MONTH_D` 恒为 0 行 ⇒ `MONTHROW` 恒空 ⇒ 期初退化为"从 `INV_DEPOT_LOG` 全量累加"（`OPENROWS` 第三分支）。**每次查询全量扫流水**，且期初正确性完全依赖"流水自 2012 年以来从未被删"这一假设。
2. **`MONTHROW` 的关联键是两键**（`DEPOT_ID` + `PRO_NO`），并用 `TOP 1` 取一行。今天是安全的——因为明细表的唯一约束也是两键。**一旦快照按维度细分，同一 `(料号, 库别)` 会有多行，`TOP 1` 会静默只取一行**，期初直接少算。这是本 ADR 必须一并处置的隐患（§3.9）。

> **第 3 个后果（2026-09-25 复核新增，原文漏记）——`CONFIRM_TAG` 的过滤位置是错的**：
> `CROSS APPLY` 取数那一支的子查询条件只有 `d.DEPOT_ID` / `d.PRO_NO` / `m.MONTH_DATE < @date1`，**没有 `m.CONFIRM_TAG = 1`**；
> `CONFIRM_TAG = 1` 只出现在外层的 `WHERE EXISTS` 里。两者的语义**不等价**：
>
> - `EXISTS` 只保证"**曾经**有一期已批核"（哪怕它在三年前）；
> - `TOP 1 … ORDER BY m.MONTH_DATE DESC` 取的是**最近的一期，不论批核与否**。
>
> ⇒ 只要有人为某期建了一张**未批核**的 1304 草稿（或批核后又解批），日报期初会**静默改用它**，而 `EXISTS` 因为更早的已批核期仍然成立而**照常放行**。
> 这与 §3.1「未批核的月结单 = 草稿，不参与任何口径」**正面冲突**，且性质正是 §5 表格里"不报错、但数变小/变大"那一类。
>
> **故 §3.1 的理由 (a)"与 §1.4 日报现有过滤条件完全一致，无需改口径"这句要撤回**——现有过滤条件并**不**一致，
> 需随 §3.9 同批修正（并入 P0-4），并补一条判别性用例：**只放一张未批核月结单 ⇒ 期初必须不变**。

**这条事实把"月结"从"可选功能"变成了"既有链路的缺失环节"**：日报的期初链路已经写好，缺的只是数据。

### 1.5 对账试算：管理口径完全平账，非管理口径不平

以"料号 + 库别"为键，余额逐键对流水累计（`IN_OUT='I'` 为正、`O` 为负）：

| 料件类别（`PRODUCT.PRO_TYPE`） | 键数 | 不平键 | 差异合计 |
|---|---|---|---|
| `'2'` | 47 | **0** | **0** |
| `'3'`（**库存报表实际口径**，见 `InventorySources.DistinctProductDepotPairs`） | 241 | **0** | **0** |
| `'1'` | 1472 | 125 | **−130,608** |
| 主档中查不到的料号 | 120 | 20 | −15,295 |

- 145 个不平键中，**99 个在 2026 年仍有流水活动**，46 个已静默；
- **管理口径（`'2'`+`'3'`，288 键）差异为 0**——新移动引擎维护的账是自洽的，这是"地基可信"的第一手证据；
- `PRO_TYPE='1'` 与主档缺失料号的差异**来源未定性**（`PRO_TYPE` 已查明为料件类别：`1` 成品 / `2` 半成品 / `3` 原料 / `4` 辅料，见 §1.2 注——**即差异集中在"成品"**）；
- **"差异是否在扩大"当前无法回答**：没有月结快照 ⇒ 没有时点锚点，只能拿"当前余额"对"全历史流水"，切不开"历史固定偏差"与"持续恶化"；余额维度行为 0 ⇒ 也没有第二套独立口径可交叉验证。

> **复核追加的三条实测（2026-09-25，原文"来源未定性"的第一次收敛）**——不改变任何决策，但**直接削弱了上面那条"地基可信"的推论**，故必须写明：
>
> 1. **132 行 NULL 数量流水全部在"成品"一侧**：按 `PRO_TYPE` 归类是 `'1'`（成品）**124 行 / 62 键** + 主档缺失 **8 行 / 4 键**，
>    `'2'`（半成品）与 `'3'`（原料）**一行都没有**。而库存日报的口径恰好就是 `'3'`（§3.10）。
>    ⇒ **"管理口径差异 = 0"里，有一部分不是因为账干净，而是因为脏的那一类料件根本不在这个口径内。**
> 2. **2026 年仍有活动的流水高度集中在库存报废单（`BF`）**：把 2026 年的流水按单别拆开看，落在 145 个不平键上的主要是
>    `BF` **136 行 / 68 键**、`CKD`（仓库调拔单）72 行 / 72 键，以及大批单行的 `E2E*`（**端到端测试夹具**）。
>    再按"该键历史上有没有出现过 `BF`"分组：**有 `BF` 的 88 键合计 −203,386，没有的 57 键合计 +57,483**。
>    `BF` 正是 ADR-014 §1.4 / §3.16 预警过的**"两条腿"单据**（借出 / 返还 / 报废，归还侧库别列常为空）。
>    ⇒ 差异**不是纯历史遗留**：它有明确的、仍在产生流水的作用点，P0-3 应**从 `BF` 入手**而不是从 `PRO_TYPE` 入手。
> 3. **对账算术本身不是 NULL 安全的**：口径式 `SUM(CASE WHEN IN_OUT='I' THEN QTY ELSE -QTY END)` 里，
>    `QTY IS NULL` 会让该行取值为 `NULL`，而 `SUM` **忽略 NULL** ⇒ 这 132 行**完全不参与对账**，
>    既不报错也不留痕。门禁若照抄这个式子上线，会把"流水缺数量"和"账实不符"两类缺陷**混成一个数字**（§3.10 已据此加前置断言）。
>
> **推论（对 §2.1 / §3.10 的影响）**：`'2'`+`'3'` 干净**不足以**推出"地基可信"，只足以推出"**原料与半成品这一半是可信的**"；
> 成品（`'1'`，1472 键，占余额表 **82%**）**至今没有被任何口径验证过**。这不是要求本 ADR 立刻去修成品账，
> 而是要求**不要把"管理口径 = 0"当成结论写进 §3.10 的门禁口径**——门禁的覆盖范围必须显式声明，且**不得覆盖不到就不说**。

这就是 §1.1 说的第 3 条：**自证能力不是附加项，它是判断"这套账还撑不撑得住"的唯一手段。**

## 2. 问题拆解

### 2.1 为什么把"对账"和"月结"放进同一份 ADR

不是"合成大项"，而是它们共用同一套口径，分开写必然导致同一事实在两处各写一遍（本项目反复栽过的坑）：

| 问题 | 月结要答 | 对账要答 | 是否同一答案 |
|---|---|---|---|
| 算哪些料件 | 快照覆盖哪些行 | 对账覆盖哪些行 | **同一个**（§3.10） |
| 期初从哪来 | 上一期快照 + 其后流水 | 同左 | **同一个**（§3.8） |
| 期末是什么 | 本期快照 | 余额表当前值 | **同一个** |
| 差异怎么解释 | 必须为 0 才能结账 | 不平键清单 | **同一个门禁**（§3.9） |

对账在本 ADR 中的定位是**月结的验收手段**：月结交付的验收标准就是"快照与实时库存逐键一致、期初 + 收发 = 期末"。它不是并列的第二件事。

### 2.2 为什么必须在空窗期把键定死

ADR-014 §3.22 / P1-11 把两个问题明确留给了月结立项，并预告了口径：

> 「`INV_PRO_MONTH_D` 加 `BATCH_NO` / `LOCATION_NO` 两列（可空，未启用时落哨兵值）；**是否进主键待月结立项时按 `MONTH_CLOSE_BY_*` 参数决定**（若进主键则必须 `NOT NULL` + 哨兵值）」

**本次要细化其中一处不成立的地方**：唯一约束是**结构**，不能"按参数决定"——参数是运行时可改的配置，约束是建表时定死的 DDL。正确形态是**结构恒定（一次扩到七列）+ 参数只决定生成时的粒度**（§3.2）。

今天 `INV_PRO_MONTH_D` 是 0 行，改键成本为零；一旦客户上线跑起月结，改键就是历史快照的迁移与重算。

### 2.3 必须先答的三个问题

1. 快照的**粒度键**是什么（决定唯一约束，一次定死）；
2. 关账的**判据与拦截落点**是什么（决定"拦得住"还是"配了不生效"）；
3. 快照生成的**触发方式**是什么（人工动作 / 定时作业 / 效果引擎）。

## 3. 决策条款

### 3.1 月结沿用模块 1304 的单据形态，不另建作业

**状态：待拍板（建议：沿用单据形态）**

- 一张 1304 单据 = 一个期间的快照；`MONTH_DATE` 为该期末（结账）时点；
- **批核 = 生效**：`CONFIRM_TAG=1` 的月结单才是关账锚点与报表期初来源（这是**目标口径**；日报现有实现**尚未**做到，见 §1.4 第 3 条，随 §3.9 同批修正）；
- 未批核的月结单 = 草稿，不参与任何口径。

**理由**：(a) 库内已经是这个形态，旧系统亦然（表注释即「1304:料件每月统计单」）；(b) ADR-013 的生命周期列与统一管线直接复用，不引入第二套状态机；(c) "谁在何时结的账"天然进审计（`AUDIT_EVENT`）；(d) 关账判据可以完全落在既有状态位上（§3.4），不新增真相源。

**备选与否决**：否决"后台定时作业直接写快照表"——它绕开单据与生命周期，会产生"没人知道是谁在什么时候结的账"的黑箱，且无法复现 ADR-013 的守卫语义。

### 3.2 快照明细的唯一约束一次扩为七列（维度进键 + 哨兵值）

**状态：待拍板（建议：扩键，一次定死）**

现状：主键 `(MONTH_TYPE, MONTH_NO, SERIAL_NO)`；唯一索引 `IX_INV_PRO_MONTH_D (MONTH_TYPE, MONTH_NO, DEPOT_ID, PRO_NO)`（**两键**）；`LOCATION_NO` / `BATCH_NO` 均可空、不在键内。

决策：

1. **唯一索引扩为** `(MONTH_TYPE, MONTH_NO, DEPOT_ID, PRO_NO, LOCATION_NO, BATCH_NO, PROCEDURE_TYPE_ID)`；
2. 三个维度列改为 **`NOT NULL` + 默认哨兵值**（位置 `-`、批次 `''`、制程 `''`），与 ADR-014 §3.4 及 `INV_PRO_DEPOT` 的现有形态**逐字一致**；
   > **第三列 `PROCEDURE_TYPE_ID` 的来历（§9.3）**：它服务的是**半成品那本独立账**（`HALF_PRO_DEPOT`，按制程分账）。
   > **主账行一律落哨兵 `''`**——与 `LOCATION_NO` / `BATCH_NO` 在"未启用该维度"时的处理**完全同一手法**；
   > 哪本账由 `MONTH_TYPE` 区分。**末列追加**也符合 ADR-014 §3.6 为将来序列号维预留末列的约定。
   > 今天该表 **0 行**，一次扩到位成本为零；§9.3 已拍板"参数化"，本列是它的结构前提。
   > **实施订正（迁移 `231`，2026-09-25 实测）**：该列原先**并不存在**（原表只有 `BATCH_NO` / `LOCATION_NO` 两个预留维度），
   > 故迁移除改三列可空性外还**新建** `PROCEDURE_TYPE_ID NCHAR(20) NOT NULL DEFAULT ''`（与 `HALF_PRO_DEPOT` 同型）。
   > 另一处实测：四列的旧唯一键由**唯一约束**承载（`sys.objects.type = 'UQ'`，名字仍是 `IX_INV_PRO_MONTH_D`），
   > **不能用 `DROP INDEX` 删**（库会拒绝），必须 `DROP CONSTRAINT` 后重建为同形态的唯一约束——名字与列序保持可追溯。
3. **主键保持 `(MONTH_TYPE, MONTH_NO, SERIAL_NO)` 不变**（`SERIAL_NO` 是明细行身份，沿用明细行项次的既有口径）。

**理由**：

- 不扩键的直接后果是**参数一开就存不下**：`MONTH_CLOSE_BY_BATCH=1`（当前默认值即为 1）时，同一 `(月结单, 库别, 料号)` 的多个批次会撞 `IX_INV_PRO_MONTH_D` 唯一约束——这与盘点单 `TABLES.DF_VERIFY` 两键问题（ADR-014 复查 D2）是同一类缺陷；
- 为什么必须 `NOT NULL` + 哨兵而不是"允许 NULL 且不进约束"：**SQL Server 唯一索引把 NULL 视为彼此相等**，多个 NULL 同样会冲突，无法表达"这两维未启用"；
- 为什么结构恒定而不是"按参数建键"：见 §2.2。

**待验证**：`INV_PRO_DEPOT.BATCH_NO` 是 `NCHAR`，其空串落库为补齐空格、比较时忽略尾随空格。迁移必须保证两张表的哨兵形态一致，并由 `check-stock-depot-level-consistency.ps1` 的同键一致检查覆盖。

> **复核补（2026-09-25）**：原文把这条记为"待验证"，实测**已可定论**，且结论比原文的措辞更值得警惕——
> 尾随空格在**唯一索引所用的 `=` 比较里一律被忽略**（实测 `CAST(N'ABC' AS NCHAR(30)) = N'ABC'` 为真、
> `<>` 为假；`CAST(N'A-' AS NVARCHAR(30)) = N'A- '` **同样为真**——与是否定长无关）。
> 即：`N'- '` 不会另建一行，而是**静默并入 `N'-'` 哨兵行**；`BATCH_NO` 侧同理。这正是 ADR-014 §3.4 警告过的形态。
>
> ⇒ 迁移要做的**不是**"防止重复行"（唯一索引本就拦得住），而是**保证落库值规范**：`INV_PRO_DEPOT` 为此建了
> `CK_INV_PRO_DEPOT_LOCATION_NO_TRIMMED CHECK (NOT [LOCATION_NO] like N'% ')`——注意用的是 **`LIKE`**，
> 因为 `LIKE` **不**忽略尾随空格，正好用来表达"不许有尾随空格"这条 `=` 表达不了的约束。
> **该约束必须镜像到 `INV_PRO_MONTH_D`**；仅靠 `check-stock-depot-level-consistency.ps1` 的同键一致检查只能事后发现分叉
> （而且因为 `=` 会合并，门禁多半**看不见**这类分叉），拦不住第一次写入。

### 3.3 月结单头不按维度拆分

**状态：待拍板（建议：不拆）**

ADR-014 §3.22 遗留问题「`INV_PRO_MONTH_M`（单头）是否按维度拆分」——**不拆**。

理由：单头是"这张月结单"的身份（`MONTH_TYPE` + `MONTH_NO` + 生命周期列），拆开就变成"每个维度一张单"，生命周期、批核、审计、关账判据全部要跟着按维度分裂，且与"批核 = 关账"的语义（§3.4）直接冲突。维度只影响明细行数。

### 3.4 关账判据 = 「该期间存在已批核的月结单」，不新增状态位

**状态：待拍板（建议：以此为准）**

- 「某期间已关账」的判据：存在 `INV_PRO_MONTH_M.CONFIRM_TAG = 1` 且 `MONTH_DATE` 落在该期间的月结单；
- **不新增 `CLOSE_TAG` 之类的第二个状态位**——关账与快照是同一件事的两面，多一个状态就多一处可能不一致；
- 反结账 = 对月结单**解批**（ADR-013 既有动作），无需新动作类型。

**理由**：这是"单一真相源"的直接应用。若新增状态位，则必须回答"已关账但未批核""已批核但未关账"两种中间态如何处置——而它们没有任何业务含义。

> **前置依赖（2026-09-25 复核新增）：本条的判据只在 `MONTH_DATE` = 该期间**期末**时才成立。**
> §7-2 把"`MONTH_DATE` 取月末还是取实际生成时刻"留作开放问题，但 §3.4 的判据「`MONTH_DATE` 落在该期间」**已经取决于它的答案**：
> 若 `MONTH_DATE` 记的是生成时刻（如 9 月 3 日结 8 月的账），那么"8 月是否已关账"按本条判据**永远判不出来**（9 月 3 日落在 9 月）。
> ⇒ **§7-2 不是自由选项，它是本条的前置**：`MONTH_DATE` 必须取期间期末；"何时生成的"另由生命周期列（`CONFIRM_DATE` / `AUDIT_EVENT`）承载，不占用业务日期列。
> 落库前必须先把这条钉死，否则关账拦截会在"补结上个月"这个最常见的动作上直接失效。

### 3.5 关账拦截的落点与口径

**状态：待拍板（建议如下）**

| 项 | 建议 |
|---|---|
| **拦什么** | 只拦**库存变动**：批核会触发 `inventory-move` 的模块（ADR-014 §4 附一登记的 37 模块 / 44 动作 + 库存域 10 模块）。**半成品（2603/2604）是否纳入拦截，由 `MONTH_CLOSE_SCOPE_HALF_STOCK` 决定**——与快照范围**永远一致**（§9.3：今天是"无条件拦但不快照"的不对称状态，本次修正） |
| **用哪个日期判** | **以"将要写入的那条流水日期"为准**，而不是统一取单据日期（见下方修订） |
| **拦哪个动作** | **拦批核**（库存变动的时刻）；建单不受限（草稿不产生流水）；对已批核单据的解批 / 修改同样拦（否则可先解批 → 改 → 再批核绕过） |
| **拦到什么程度** | **拒绝**（fail-closed），错误码建议 `PERIOD_CLOSED`，文案点名期间与月结单号 |
| **落点** | 统一管线的守卫位（保存 / 批核 / 解批），经**单一服务**取值（如 `InventoryPeriodService.IsClosedAsync(业务日期)`）；**不在各模块配校验规则**——与 ADR-014 已论证的理由相同：分散配置既会漏又会与引擎口径分叉 |
| **性能** | 判据查询按业务日期命中月结表，应加缓存（与权限缓存同款 TTL）；只在库存类模块查询，不要挂在所有域的保存路径上 |
| **不拦什么** | 不动库存的单据（销售、采购、人力等）——库存月结没有权限拦别的域的历史 |

> **修订一（2026-09-25 复核，原文口径有分叉）：判据的日期必须与写库的日期同源。**
> 原文写"用**单据日期**判"，理由是"月结按业务日期切期间，用系统时间判会漏"。方向对，但**与真实写入不一致**：
> `InventoryMoveHandler.LedgerDateExpression()` 的实现是——
>
> ```csharp
> private string LedgerDateExpression() => IsApprove ? "t.BILL_DATE" : "SYSDATETIME()";
> ```
>
> 即 **批核写单据日期，解批写系统时间**（注释写明理由：两条腿同库位的单据解批镜像时沿用单据日期必然撞主键）。
> 于是"按单据日期判解批"会漏掉一个真实缺口：**一张单据日期在未关账期间、但解批动作发生在已关账期间的单据，
> 解批会被放行，而它的反向流水却按 `SYSDATETIME()` 落进那个已关账的期间**——
> 这恰恰是 §1.1 承诺"已结期间的历史不再被改写"要防的事，而且它**没有编译期与运行期信号**，只在报表上体现为期初漂移。
>
> ⇒ **判据改为 `IsClosedAsync(将要写入的流水日期)`**：批核路径传 `BILL_DATE`，解批路径传 `SYSDATETIME()`。
> 实现上**建议把守卫放在 `LedgerDateExpression()` 的同一处**（`InventoryMoveHandler` 写入流水/余额的收口点），
> 让"判哪个日期"与"写哪个日期"在结构上不可能分叉；管线层的检查保留为**更早、文案更友好**的一层，不作为唯一防线。
> 这条同时回应了 §5 的"配了不生效"风险：**判据落在写入口，才不依赖"有没有人记得给新模块配拦截"**——新增库存宿主自动被覆盖，不存在"漏宿主"。
>
> **修订二（同轮）：应登记的判别性用例**——① 单据日期落在已关账期间 ⇒ 批核 400 `PERIOD_CLOSED`；
> ② 该单据**解批**同样拒绝；③ **反例**：单据日期在未关账期间、其反向流水将落进已关账期间 ⇒ **必须也拒绝**（这条就是修订一要拦的缺口，
> 去掉日期同源后此用例必红）；④ 不动库存的模块不受影响。

**最容易踩的边界（必须有用例）**：单据日期在已关账期间、批核行为发生在当期（跨月单据）⇒ **按单据日期判，拒绝**。

### 3.6 反结账允许，但必须留痕

**状态：待拍板（建议：允许）**

- 允许对月结单解批（= 取消关账），该期间的写入随即恢复；
- 解批与再次批核均进 `AUDIT_EVENT`；
- **不做**"反结账需二级审批"这类流程（当前无此诉求，将来需要时用工作流承载，不在此处硬编码）。

### 3.7 快照生成用 ADR-018 的自定义按钮，不用效果引擎

**状态：待拍板（建议：按钮）**

- 1304 增加一个明细级 / 单据级自定义按钮「生成快照」：**按 `MONTH_DATE`（期末时点）算出该时点的余额**，按粒度参数展开，写 `INV_PRO_MONTH_D`（取数口径见 §3.8 的修订，**不是**简单读当前余额）；
- 1304 `EFFECT_ENGINE_TAG=0`，**不打开效果引擎**：快照生成是"读库存写快照"的重操作，需要 `confirm` 探路、一次性锁、可审计——ADR-018 的按钮机制（授权名单 / 探路 / 确认 / 审计 / `once` 锁）正是为此设计的；
- **只在未批核状态下允许生成**（已批核 = 已关账，不允许重算）；重复生成的处理：`once` 语义或"先清后写同事务"，开工时定（见 §7）。

### 3.8 期末 / 期初口径与报表同源

**状态：待拍板（建议如下）**

- **快照内容** = 该时点 `INV_PRO_DEPOT` 的余额逐键固化：`QTY` 取余额，`PRICE` 取库别级移动加权成本（与 ADR-014 §3.15 口径一致，不引入第二种计价）；
  > **经 §9.3 修订**：参数 `MONTH_CLOSE_SCOPE_HALF_STOCK` **开启时**，同一张月结单同时产出**半成品账**（`HALF_PRO_DEPOT`）的快照，
  > 按 `PROCEDURE_TYPE_ID` 细分；主账行落哨兵 `''`（见 §3.2）。**默认 `0` 关**——关时半成品账既不快照、也不拦截。
- **期末 = 本期快照**；**期初 = 上一张已批核月结单的快照 + 其后至本期间起点的流水**——与 `InventoryDaily` 现有 `MONTHROW` 逻辑**逐字同源**，不新造口径；
- 推论：**月结一旦产出快照，现有库存日报的期初链路自然生效**，"期间报表"这一交付项**可能无需新做报表**，只需验收（见 §6 P2）。

> **修订一（2026-09-25 复核）：「读 `INV_PRO_DEPOT` 当前余额」与「期间期末快照」是两件事，原文把它们当成了同一件。**
> §3.1 规定 `MONTH_DATE` 为该期**期末**，§3.7 却写"读当前余额"——只有**在期末当天、且当天就是生成当天**时，两者才恰好相等。
> 一旦要**补结一个已经过去的期间**（首次上线补 8 月的账，是很自然的用法），读到的就是"今天"的余额，
> 而它会被贴上 8 月 31 日的标签落库——**快照从第一天起就是错的，且看不出来**。
>
> 更要命的是 **§6 P1-2 的验收抓不到它**：验收写的是"逐键与余额一致、合计 diff = 0"。
> 若生成器读的就是当前余额，那么"快照 == 余额"**必然成立**——这个用例对上述错误**没有判别力**（两边错得一样）。
>
> ⇒ **建议把生成器的取数口径改为"按 `MONTH_DATE` 反算"**：`期末余额(T) = 上一张已批核快照 + 其后至 T 的流水`
> ——**与 §3.8 给期初的定义是同一个算式**，即生成器与日报共用同一条期间算术（这正是 §2.1 说的"同一个答案"）。
> 好处有三：① 补结历史期间在语义上成立；② "快照 == 余额"退化为**只在结当期账时**成立的特例，而**恒等式
> `期初 + 本期收发 = 期末`变成任何期间都成立**，这才是真正有判别力的验收；③ 生成器与报表不会各写一套期间逻辑。
> 若采纳，P1-2 的验收需相应改写（见 §6）。
>
> **修订二（同轮，与 §1.3 注呼应）：`QTY` / `PRICE` 是派生列，必须只读。**
> 1304 **今天就在统一表单编辑白名单内**（§1.3），意味着任何人都能用手工录入的行覆盖快照。
> 一份可被手工改写的"自证材料"不构成证据 ⇒ 这两个字段须置 `FIELDS.IS_READONLY`，
> 写入口只保留「生成快照」按钮与生命周期动作；并建议把"月结表不在库存写入收口覆盖范围内"这一事实
> 补进 `check-inventory-read-hosts.ps1` 的写路径断言（当前它只拦主/明细表为 `INV_PRO_DEPOT`/`INV_DEPOT_LOG`/`INV_BATCH_M` 的模块）。

### 3.9 快照维度化必须同步修正库存日报的期初读取（否则静默错账）

**状态：待拍板（建议：必改，随 §3.2 同批）**

`MONTHROW` 现有写法按两键关联并 `TOP 1`（§1.4）。快照按维度细分后，同一 `(料号, 库别)` 会对应多行，`TOP 1` 会**静默只取一行** ⇒ 期初数量少算、成本加权失真。

**必须改为**按 `(DEPOT_ID, PRO_NO)` **聚合**：`SUM(QTY)`、`SUM(QTY * PRICE) / SUM(QTY)`（与 `OPENING` 已用的加权写法一致）。

**验收**：造多批次快照 ⇒ 日报期初 = 各批次合计（判别性用例：去掉聚合后结果恰好变小）。

> **修订（2026-09-25 复核，这条按字面施工会引入比原缺陷更大的错误）：**
>
> **① 聚合必须是两段式，不能把 `TOP 1` 直接换成 `SUM`。** 现形状是
> `CROSS APPLY (SELECT TOP 1 m.MONTH_DATE, d.QTY, d.PRICE … ORDER BY m.MONTH_DATE DESC)`。
> `TOP 1 … ORDER BY MONTH_DATE DESC` **同时承担了两件事**：选"最近的一期"和"取一行的值"。
> 把取值部分字面替换为 `SUM(...)`，聚合范围会从"某一期的明细行"悄悄放大成"**该键的全部历史月份**"——
> 期初不再是"上月末"而是"开天辟地以来的净额"，**这个错误比 `TOP 1` 少算一个批次大得多，而且同样没有信号**。
>
> ⇒ 正确形状是**先定月、再聚合**：
>
> ```sql
> CROSS APPLY (
>     SELECT TOP 1 m.MONTH_DATE
>     FROM dbo.INV_PRO_MONTH_M m
>     JOIN dbo.INV_PRO_MONTH_D d ON d.MONTH_TYPE = m.MONTH_TYPE AND d.MONTH_NO = m.MONTH_NO
>     WHERE d.DEPOT_ID = pa.DEPOT_ID AND d.PRO_NO = pa.PRO_NO
>       AND m.MONTH_DATE < @date1 AND m.CONFIRM_TAG = 1        -- ← 见 ②
>     ORDER BY m.MONTH_DATE DESC
> ) lm
> CROSS APPLY (
>     SELECT SUM(d.QTY) AS QTY,
>            CASE WHEN SUM(d.QTY) = 0 THEN 0 ELSE SUM(d.QTY * d.PRICE) / SUM(d.QTY) END AS PRICE
>     FROM dbo.INV_PRO_MONTH_M m
>     JOIN dbo.INV_PRO_MONTH_D d ON d.MONTH_TYPE = m.MONTH_TYPE AND d.MONTH_NO = m.MONTH_NO
>     WHERE d.DEPOT_ID = pa.DEPOT_ID AND d.PRO_NO = pa.PRO_NO
>       AND m.MONTH_DATE = lm.MONTH_DATE AND m.CONFIRM_TAG = 1
> ) x
> ```
>
> **验收（判别性，两条都要有）**：⒜ 同一键造**两个批次**的快照 ⇒ 期初 = 两批合计（`TOP 1` 版与聚合版结果不同）；
> ⒝ 同一键造**两个已批核期间** ⇒ 期初只取**最近一期**（把 `lm` 那一段去掉后，此用例必红——它专门守"别把跨月求和当修好了"）。
>
> **② `CONFIRM_TAG` 必须同时加进"选月"这一支**（原写法只在 `EXISTS` 里，见 §1.4 第 3 条）。
> 两条缺陷在同一段 SQL 里、且都会被同一个"造一张草稿月结单"的动作触发，**应合并为一次修正**。
>
> **③ 关于"成本加权失真"的措辞**：按 §3.8 的口径，`PRICE` 是**库别级**移动加权（ADR-014 §3.15），
> 同一 `(料号, 库别)` 的各维度行**存的是同一个值**，因此 `TOP 1` 取到哪一行，价格都一样——**价格其实不会失真，失真的是数量**。
> 加权写法仍然保留（它对未来"批次成本"是向前兼容的，届时才真正承担意义），但**不要把"加权"当成这条的理由**：
> 理由就是数量少算。措辞准确很重要——若以为价格也会错，就会顺带去做本不需要的改动。

### 3.10 对账户径与门禁

**状态：待拍板（建议如下）**

- **对账户径 = 与库存报表同一料件范围**（`InventorySources.DistinctProductDepotPairs` 的口径），避免"报表算一套、门禁算另一套"；
- 新增门禁 `scripts/check-inventory-balance-identity.ps1`：按管理口径逐键比对"余额 vs 流水累计"，**已知不平键以棘轮登记、只减不增**；
- **`PRO_TYPE='1'` 的 −130,608 与主档缺失料号的 −15,295 定性为独立调查项**（§6 P0），结论出来前**不得**把全库口径写进门禁；
- **145 个不平键与 132 行空数量流水必须在效期开工前定性**：效期会在这套账上叠加新维度，地基没定性就叠加不划算。

> **修订（2026-09-25 复核）：原文这一条会生出一个"出生即全绿、且永远绿"的门禁，需要三处收紧。**
>
> **① 口径的范围必须显式写出来，并且要承认它覆盖不到什么。**
> `DistinctProductDepotPairs` 是 `WHERE pr.PRO_TYPE = '3'`（**原料**，字典见 §1.2 注；`ReportAggregateRegistry` 的注释写明这是**照旧实现的硬编码**）。
> 于是"与报表同口径"实际等于 **241 键 / 1797 键**（约 **13%**），且这 241 键**今天差异为 0、也没有一行 NULL 数量流水**。
> §1.5 把"管理口径"写成 `'2'`+`'3'`（288 键），与本条的"报表口径"（仅 `'3'`，241 键）**是两个数**——原文两处不一致，须择一。
> 更要紧的是：**照搬一个"因历史原因而写死的范围"进新门禁，等于把历史口径固化成纪律**。
> 而**差异全部在 `'1'`（成品，1472 键、占 82%）与主档缺失料号上**——正好是门禁不含的那一块。
>
> ⇒ 建议改为：门禁**分两档**——⒜ `'3'`（+`'2'`）档：**必须恒为 0**，出现任何差异即 FAIL（这是回归防线，跑得通、有意义）；
> ⒝ **全库档**：已知不平键以显式清单棘轮冻结（当前 145 键，其中 99 键 2026 年仍有活动），FAIL 文案里**必须写明"本档为棘轮，
> 覆盖范围含未定性差异"**，不能让人误读成"账是全对的"。⒜ 档不覆盖的部分由 ⒝ 档如实呈现——**覆盖不到可以，装作覆盖到了不行**。
>
> **② 门禁必须先断 NULL，再比差异。** 对账算式 `SUM(CASE WHEN IN_OUT='I' THEN QTY ELSE -QTY END)` 不是 NULL 安全的：
> `QTY IS NULL` 时取值为 NULL，**`SUM` 静默忽略**，这 132 行完全不参与对账（§1.5 复核第 3 条）。
> 若不先断，门禁会把"流水缺数量"与"账实不符"压成同一个数字，`ERROR` 指向错误的根因。
> ⇒ 门禁执行顺序固定为：**(1) `INV_DEPOT_LOG` 无 `QTY IS NULL` → (2) 无 `IN_OUT` 越界 → (3) 逐键对账**；
> 且 132 行 NULL 的**存在本身**应在 P0-3 里被清掉（它们全部在 `'1'`/主档缺失料号上，与差异是同一片区域）。
>
> **③ P0-3 的入手点应当改写。** 原文把调查按 `PRO_TYPE` 组织（"`PRO_TYPE='1'` 的差异来源未定性"）。
> 实测按**单别**拆更有指向性：2026 年落在不平键上的流水集中在**库存报废单 `BF`（136 行 / 68 键）**、仓库调拔单 `CKD`（72 行 / 72 键）与 `E2E*` 测试夹具；
> 按"历史上是否出现过 `BF`"分组，有 `BF` 的 88 键合计 **−203,386**、没有的 57 键 **+57,483**。
> `BF` 正是 ADR-014 §3.16 预警的**"两条腿"单据**（归还侧库别列常为空、跳过一腿），
> 也正是那 124 行 NULL 数量流水的来源 ⇒ **P0-3 应从 `BF` 的"两条腿"路径入手，而不是从料件类别入手。**

### 3.11 `USEABLE_QTY` 与本期无关（登记）

**状态：已拍板（2026-09-25 用户）**

实测该列 1797 行全部非空、**值全部为 0**——它不是"脏数据"，是"从未启用的零值占位"。用户拍板：**不清**（既不构成阻碍，也无形态可留）。

**约束（本条的关键）**：将来做可用量（冻结 / 预留）时，**不得把 `0` 实现为"可用量 = 0"**——那会让全部库存看起来不可用；启用时必须显式定义语义（`0` = 未启用，或初始化为等于 `QTY`）。复用还是新建表，属冻结 / 预留立项，不在本 ADR 范围。

## 4. 明确不做

- **不做财务凭证生成 / 与总账对接**——涉及财务域，另立议题；
- **不做库存调价 / 重估**（版图 §5 第 11 项）——计价口径维持库别级移动加权（ADR-014 §3.15），本 ADR 不引入第二种口径；
- **不做自动定时月结**——结账是业务动作，须有人确认时点（§3.7）；
- **不做"关账期间的例外放行白名单"**——任何"这次特殊放一下"的机制都会成为绕过口子；确需补历史，走反结账（§3.6）；
- **不做跨域关账**（财务关账、采购关账）——本 ADR 只关库存；
- **不新增第二个"已关账"状态位**（§3.4）。

|---|---|

| **对账算术不是 NULL 安全的**（2026-09-25 复核新增） | `SUM(CASE WHEN IN_OUT='I' THEN QTY ELSE -QTY END)` 静默忽略 `QTY IS NULL` 的 132 行 ⇒ 门禁会混两类缺陷。对策：门禁前置断言 + 132 行随 P0-3 清掉 |
| **补结历史期间时快照取数错**（2026-09-25 复核新增） | §3.7"读当前余额"与 §3.1"期末快照"矛盾；且 P1-2 原验收"快照 == 余额"对这类错误**无判别力**。对策：生成器改按 `MONTH_DATE` 反算（与期初同一算式），验收改用恒等式 `期初 + 收发 = 期末`（§3.8） |
| **快照可被手工改写**（2026-09-25 复核新增） | 1304 **已在统一表单编辑白名单内** ⇒ `QTY`/`PRICE` 可手填，且没有任何门禁覆盖月结两表的写路径。对策：派生列置只读 + 把月结表纳入写路径断言（§1.3、§3.8） |
| **对账门禁上线即红** | 145 个不平键会让门禁一出生就是红的。对策：口径先按管理口径（已 0 差异），已知不平键棘轮化，定性调查单列（§6 P0） |
| **粒度参数中途变更** | 快照的行形态在生成时固定；客户若中途改 `MONTH_CLOSE_BY_*`，则同一料号的历史快照粒度不一致。**按 `(料号, 库别)` 汇总仍然正确**（不同粒度都是它的子集分区），但"按批次看历史"会断档。对策：在策略界面提示"变更只影响之后的月结"，并在报表按汇总口径取数。**注（复核补）**：这两个参数是 `BIT` 且**只允许部署级**（`ValidateMonthCloseScope` 拒绝库别覆盖）⇒ 变更影响**全库**，不是单个仓库的事，提示文案要据此写 |
| **跨月单据** | 见 §3.5 边界；必须有用例 |
| **关账判据的查询开销** | 每次保存 / 批核查一次月结表；对策：加缓存 + 只对库存类模块查询。**注（复核补）**：判据落点若按 §3.5 修订一放进移动引擎写入口，则"只对库存类模块查询"是**结构自带的**，不需要靠模块清单维护 |
| **快照行数增长** | 维度展开后行数 = 四键行数（今天 1797 全部在哨兵位置，未来按库位 / 批次会增长）；对策：生成走集合写入，不逐行往返 |

### P1 功能实现：快照生成 + 关账

## 7. 剩余开放问题

1. **重复生成快照的语义**：`once` 锁死（同 ADR-018 转单口径）/ 先清后写同事务 / 拒绝二次生成——开工时定；
2. ~~**快照的时点**：`MONTH_DATE` 取"月末 23:59:59"还是"实际生成时刻"？~~ **（2026-09-25 复核：不再开放）** 取**期间期末**。
   它原本被当成自由选项，实为 §3.4 关账判据的**前置**（判据"`MONTH_DATE` 落在该期间"只在取期末时成立）。"何时生成的"由
   `CONFIRM_DATE` / `AUDIT_EVENT` 承载。**跨月补录的历史流水如何对待**仍需定：落进已关账期间的补录应被 §3.5 拒绝，
   落在开账期的补录则正常参与该期收发——但**若补录的单据日期早于上一张快照的期间，它就会被期初算式漏掉**，这一条要单独定（建议：拒绝，理由同 §4「不做例外放行」）；
3. **`MONTH_NO` 的编号粒度**：`BILLKIND` 现为 `KCJZ{YYMMDD}000`（**按日**发号），而月结是**按月**的事。是否改为 `KCJZ{YYMM}000`（按月）需定；不改也能用（一个期间一张单，靠人工不重复），但会影响可读性；
4. **1304 是否需要在 `FORM_BUTTONS` 配批核 / 解批按钮**（`AUTO_APPROVE=1` 时批核是否自动）——`AUTO_APPROVE` 的含义与月结的"人工确认时点"诉求可能冲突，开工时核实。**复核补**：既然 1304 已在统一表单白名单（§1.3），本条还牵出"**一张 1304 草稿足以影响日报期初**"（§1.4-3），
   故 §3.9 的修正应先于 1304 重发布落地，否则修好之前先把它暴露给了所有人；
5. ~~**`PRO_TYPE` 的取值字典**~~ **（2026-09-25 复核：已关闭）** `1` 成品 / `2` 半成品 / `3` 原料 / `4` 辅料，
   出处 `ERP/UserControl/SearchFilter.ascx:105-108`（详见 §1.2 注）。**取代它的是 P0-3 的真正切入问题**：不是"料件类别怎么分类"，
   而是"**库存报废单 `BF` 的'两条腿'路径为什么会留下不平**"（§3.10 修订③）；
6. **`MONTH_CLOSE_BY_*` 默认值与 `BATCH_MODE` 的不一致**：参数默认 `MONTH_CLOSE_BY_BATCH=1`，而策略 `BATCH_MODE=0`（不启用批次）。建议保持（参数只决定"展开维度"，不启用批次时自然落哨兵），但需在界面说明，避免误读为"系统在按批次结账"。

## 9. 配置面能力补齐与声称对齐（七项，2026-09-25 用户拍板）

> **来源**：`docs/plans/库存能力台帐.md` 的普查（S1–S4，**15 条「声明与实现不符」**，其中 6 条属"声明已实现、运行期零消费方"）。
> **共同根因**：**没有机制在守"声称"**——写档位目录的人按"列建好了"判断、写立项方案的人按"快照在"判断、写能力清单的人按"设计了"判断。
> 故除逐条处置外，**保留普查产出的门禁** `scripts/check-capability-ledger.ps1` 作为长期防线。

### 9.1 D1｜存放方式接上线（连同「建议」档一起解决）

**要补的是一根断掉的链，不是补一个 if**：

```
STORAGE_MODE = FIXED    → 依赖「物料默认货位」   → DEPOT_PRODUCT_LOCATION（表在、0 行、0 元数据、0 引用）
STORAGE_MODE = RANDOM   → 依赖「空位查找」       → ADR-014 §3.12 三级退化（无实现）
LOCATION_MODE = 2「建议」→ 依赖「系统给出建议位置」→ 同一个解析器（无实现）
```

⇒ **做一次解析器，同时消掉两个"配了不生效"**。

**交付**：`DepotLocationResolver`——① 该物料在此库别**已占用**的位置；② 该物料**上次放置**的位置（读 `INV_DEPOT_LOG` 最近一笔）；③ 该库区内**当前无库存**的位置（按 `SEQ_NO` 取第一个）。

**三个消费点**：`FIXED` 查 `DEPOT_PRODUCT_LOCATION`（`IS_PRIMARY=1`），**查不到回落哨兵、不报错**；`RANDOM`/`MIXED` 走三级退化；`LOCATION_MODE=2` 用同一解析器。

**边界（硬）**：`LOCATION_MODE = 0 / 1` **不解析**（保持 ADR-014 §0 的 R1「与今天完全等价」）；**两条腿单据的空位置仍按 ADR-014 §3.16 跳过**；解析结果仍过库位存在性预检与哨兵归一化。

> **已拍板（2026-09-25 用户）：取 ⒝——保存期解析并写入。**
>
> **实现范围（写死，避免施工方自行扩张）**：
> - **档 2「建议」**：在 **`SAVE` 事件**解析并把建议位置**写入明细行**，用户打开表单**看得见、可改**；纸质/接口路径同样拿得到；
> - **档 3「强制」行为不变**：既有的批核期"必须指定位置"检查（`InventoryMoveHandler`）**原样保留**，本段**不加**保存期拒绝。
>   **这是刻意的取舍**：保存期拒绝会让**草稿存不下来**（挂单时常常还不知道位置），与 ADR-013 的草稿语义冲突；
>   早反馈的收益不值这个代价。*若将来确要"保存期就拦"，另立段并单独讨论草稿语义*；
> - **档 0 / 1 不解析**（同 §9.1 边界）。
>
> **落点**：档 2 的写入点是 `SAVE` 事件的效果/域规则（与 `130101 / SAVE / stocktake-scope-generate` 同类），
> **不是**批核期的 `InventoryMoveHandler`。**同一个解析器（WS-13）被档 2、档 3 与 `FIXED`/`RANDOM` 三处复用**。


### 9.2 D2｜批次主档与库存主档**单开一扇门**

**背景（务必先读）**：模块 `1302 料件批号资料`（主表 `INV_BATCH_M`）与 `1303 料件库存资料`（主表 `INV_PRO_DEPOT`）
**不在统一表单白名单内，是故意的**——`check-inventory-read-hosts.ps1` 的写路径断言要求
"主表是余额·流水·批次账的模块不得进白名单"，否则通用表单会**绕过移动引擎直接改账**。
后果：两条被登记的"人工改错入口"**实际不存在**（`FormAccess` 对不在白名单的模块返回 `null` ⇒ 写入口 404）。
下游 `docs/plans/批次效期立项方案.md` 据此断言"人工入口已存在、P0 只需补自动落库"——**该前提不成立**。

**决定**：**不给 1302/1303 开白名单**（那等于拆掉一道安全门），而是**新开一个受控入口**：

| 约束 | 内容 |
|---|---|
| **字段白名单** | 只允许改**人工语义列**：`INV_BATCH_M` 的 `EFFECT_DATE` / `BATCH_DATE` / `AGAIN_CHECK_DATE`；其余只读 |
| **引擎维护列禁止** | `IN_SUM` / `OUT_SUM` / `LATELY_IN_DATE`、`QTY` / `COST_PRICE` / `COST_AMOUNT` / `INIT_QTY` / `USEABLE_QTY` / `LAST_CHECK_DATE` **服务端拒写**（不依赖前端灰显） |
| **不产生库存流水** | 只改主档属性，**不得**触发 `inventory-move`、不写 `INV_DEPOT_LOG` |
| **权限与审计** | 独立权限门（建议复用 `110306` 同域或按 ADR-019 分配）；改动进 `AUDIT_EVENT` + `AUDIT_FIELD_CHANGE` |
| **形态** | 优先走 **ADR-018 自定义按钮**（已有授权/探路/确认/审计/`once` 框架），不新建页面 |

**顺带解决**：台帐问题 5 指出 `USEABLE_QTY` / `LAST_CHECK_DATE` 的 `FIELDS.IS_READONLY = 0`（可编辑），
今天靠"模块不在白名单"兜底——**白名单是会改的配置，字段只读才是元数据事实**。本项一并置只读。

### 9.3 D3｜半成品月结**参数化**

**先纠正范围（实测）**：**原材料、耗材本来就在主账 `INV_PRO_DEPOT` 里**，自动跟随月结，不需要单独决定。
真正分出去的只有**一本**账：`HALF_PRO_DEPOT`，键为 `PRO_NO + PROCEDURE_TYPE_ID + DEPOT_ID`，**与主账产品完全不重叠**
（实测 4 行 vs 主账 39 个 `PRO_TYPE='2'` 键，交集 0）。主账里**也有**半成品，它们自动跟随月结。

**三项决定**：

1. **参数化**：新增部署级参数（建议 `MONTH_CLOSE_SCOPE_HALF_STOCK`，`0/1`，**默认 `0` 关**），
   语义 = "月结范围是否含半成品（按制程）账"；归 `DEPOT_STOCK_POLICY`，**仅部署级**（与 `MONTH_CLOSE_BY_*` 同款）。
2. **快照与拦截同源**：**关账拦截必须跟随同一参数**。今天是"无条件拦 2603/2604 但不快照"（不对称）；
   参数化后**不开快照就不拦、开了才拦**——两者永远一致，且该一致性应是一条**可断言**。
3. **结构先备好**：`INV_PRO_MONTH_D` 加 `PROCEDURE_TYPE_ID` 并入唯一索引，主账行落**哨兵 `''`**（见 §3.2）。

> **参数化在这里不是免费的**：主账已有月结表，开关几乎零成本；半成品账的键多一个**制程**，
> 月结明细表原本**没有放制程的地方** ⇒ **开启需结构先行**。故按"**默认关、开启需补结构**"设计。

### 9.4 D4｜P0-09 撤销定性（销号，但**不删**门禁白名单）

ADR-014 §4 附二把 `FIELDS.VIRTUAL_EXP` 的 `LONGTH` / `SUB_QTY` 标为 **P0-09「必改」**。
**实测**：全仓检索这两个名字，命中**只有门禁脚本自己的白名单两行**；`REPORT_SORT` 命中 **0**；两字段 `IS_VISIBLE = 0`；
且 `VIRTUAL_EXP` 由 `VirtualColumnResolver` 解析为**逐行的 SELECT 片段**——**ADR 预设了一个聚合消费方，而找不到**。
作为余额表上的行级显示列，**逐行求值是正确语义**。

**两步**：① ADR-014 §4 附二该行改定性为「**已复核：逐行语义正确、且无消费方，非缺陷**」；
② `check-inventory-read-hosts.ps1` 的两条白名单**改理由不删行**——它们是"配置面引用库存表"的覆盖登记，
**引用客观存在**，删行会让门禁变红；理由由"登记待收口"改为"逐行语义正确，引用合法，非缺陷"。

> **意义不在技术在记账**：一条挂着"必改"却无人承接的项，会让后来者以为"有人欠着这件事"。**销号要销得干净。**

### 9.5 D5｜收口门禁补上批次账（一行）

`check-inventory-read-hosts.ps1` 的 `$tableNames` 现为 `@('INV_PRO_DEPOT','INV_DEPOT_LOG')`——
**代码侧字面量扫描不含 `INV_BATCH_M` / `INV_BATCH_D`**。当前无实害（11 处引用全在已白名单的 `InventoryMoveHandler.cs`），
但**新增一个只读批次账的宿主不会被拦**——而批次账正是效期立项要大量读的表。

### 9.6 D6｜15 条文档漂移**全面对齐**（用事实说话）

**方法**：逐条问「**是文档向事实靠，还是事实向文档靠**？」15 条不是一类东西：

| 类型 | 例子 | 处置 |
|---|---|---|
| 文档写错了、实际是对的 | 1304 写入口"关闭" | 改文档 |
| 实现没做 | 存放方式、物料默认货位 | 改实现（§9.1） |
| 清单失准 / 分类错误 | 版图把海关域当寄售表；§2.3 把枚举当能力 | 改清单 |
| 口径过期 | 版图 §1 五簇仍标"进行中" | 改状态 |

**范围**：只做台帐 §6 登记的 **15 条**。**用户已明确**：文档与机制的**体系性重整**（让人看得懂、AI 更懂）**单独立项**，不在本 ADR。

### 9.7 D7｜库存冻结与预留（可用量）——**全做**（2026-09-25 用户拍板）

**为什么它算缺口**：`INV_PRO_DEPOT.USEABLE_QTY` 是**遗留死列**（1797 行全零、零写入方）；
今天"可用量"在业务上**并不存在**——出库校验用的是 `QTY`，没有任何"已被占用"的概念。
ADR-014 §3.19.1 **用户已拍板"本系统要引入冻结与预留"**，但从未实现。**不收口它就是永久死列。**

**口径（ADR-014 §3.19.1 给定，本节落实）**：

```
可用量 = 库存数量 − 质量冻结 − 客诉/召回冻结 − 订单预留 − 制令预留 − 待检不合格
```

**候选清单 §3.3 的 8 个"必须先定的事"，逐条定死**：

| # | 问题 | 决策 | 理由 |
|---|---|---|---|
| 1 | `USEABLE_QTY` **复用还是新建** | **复用现有列** | 它是 ADR-014 §3.19 定义的**行级字段**，列已在、语义正确；历史值已拍板"不清"且实测全为 0（§3.11）；新建表会引出第二套库存表与 JOIN，与 §3.19「不抽汇总表」的理由冲突 |
| 2 | **存列还是实时算** | **存列（每行冗余快照）** | 出库校验在移动引擎内高频调用，实时聚合冻结/预留表开销大；读取已收口，写入点也能收口到一处（与 §3.19 库别级字段同一手法）。**代价是必须有一条一致性门禁**（WS-25） |
| 3 | **冻结粒度** | **四键行**（料号/库别/库位/批次） | 与库存行同维最自然；更粗的粒度（批次级、料号+库别级）用哨兵维度即可表达，不需要第二套粒度 |
| 4 | **冻结是否影响盘点** | **不影响**——冻结行仍参与盘点 | 盘点核对"实物在不在"，冻结表达"能不能出"。把冻结行排除出盘点会让账面与实物脱节 |
| 5 | **预留自动过期** | **惰性判定**（读取时判），不做定时作业 | 与项目「消除对存储过程 / 定时作业依赖」的方向一致；出库校验本身就会读，判据不会悬空 |
| 6 | **释放规则** | **来源单据取消/关闭即释放、取消结案即收回**（挂 ADR-013 生命周期，**双向**：结案释放、取消结案只收回"由结案释放的那批"）+ **手工释放**兜底 | 预留必须能自动回收，否则占用累积成**假性缺料**——那种问题客户查不出来。收回侧必须**逐行归因**（`INV_RESERVE.RELEASE_KIND`，见 WS-22 补记）：按"该来源所有已取消行"整体复活会把人工释放的预留一并算回占用，那是没有依据的扣减 |
| 7 | **谁可以冻结/释放** | **走 ADR-018 按钮级授权**（fail-closed 名单），**不挂 `CanSetup`** | 冻结是业务动作（品检/客服发起），不该要求配置权；ADR-018 的按钮授权正是为"未授权不渲染 + 服务端另行鉴权"设计的 |
| 8 | **可用量被谁消费** | **三处同源、单一服务**：出库校验（**拦**）、报表/查询下发、选择器显示——全部经 `InventoryAvailabilityService`，**禁止自行聚合** | 口径若分头实现必然分叉（本项目反复栽过的坑，见 `check-inventory-read-hosts` 的教训） |

**硬约束（承接 §3.11 已拍板项）**：**不得把 `0` 实现为"可用量 = 0"**。
启用时必须**初始化 `USEABLE_QTY = QTY`**——启用时冻结与预留均为空，故恒等于 `QTY`；此后由冻结/预留的写入路径维护。

> **行为变更（必须知晓，不是顺带）**：**出库校验由 `QTY` 改为按可用量拦**（上表 8-⑧）。
> 这是冻结/预留的**全部价值所在**——拦不住出库的冻结没有意义。
> 代价是既有 `CheckStockAsync` 的口径改变，**必须**有判别性用例（把口径改回 `QTY` ⇒ 用例变红），并单独成段（WS-23）。

**明确不做**（承接候选清单 §3.4）：在途库存（版图 §6 已定 `TRANSIT` 不承载库存语义）；序列号级冻结（那是第五维，另立议题）。

**依赖就绪性**：候选清单 §3.4 的**强建议前置是"库存读取收口"——已由 2026-09-24 实施完成**
（`EOS.API/Data/Inventory/InventoryQueryService.cs` + 门禁 `check-inventory-read-hosts.ps1`）⇒ **前置已满足，可开工**。
