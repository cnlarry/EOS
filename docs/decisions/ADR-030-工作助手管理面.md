## 1. 为什么要重写

工作助手已经积累了会话、模型接入、知识库、记忆、工具注册表、动作层与配置写能力。管理面按上一版建了
五个模块（3101–3105，见 §12.2），但**它们是"给已完成的界面补说明"，不是框架**：上一版正文六节里，
§1 用 300 字论证"根组 31 为什么不挂 23"、§6 论证"模型配置为什么分两级"、§5 是六批排期——全是界面决策。

框架该回答的五件事，一件也没成文：**助手由哪些参数驱动、参数住在哪、改一个参数会发生什么、谁能改、
配了却没人读怎么被拦住**。这五件事的现状是散开的：

### 1.1 参数住在四个地方，管理面只覆盖了一个

| 来源 | 内容 | 改法 | 生效 |
|---|---|---|---|
| `dbo.ASSISTANT_PROVIDER` / `ASSISTANT_MODEL`（3102） | 模型传输层（端点 / 模型标识 / 超时 / 温度 / 窗口 / 最大输出 / 工具能力 / 单价） | 界面 | 立即 |
| `dbo.ASSISTANT_SETTING`（3105，**9 个键**） | 提示词、日上限、单价兜底、熔断、每轮预留 | 界面 | 立即 |
| `IConfiguration` 四个节 | `AssistantSituation` **19 项**、`AssistantDiagnosis` **8 项**、`AssistantActionLimits` **4 项**、`AssistantConfigWrite` **4 项** | 改文件或环境变量 | **重启** |
| 纯代码常量 | 工具输出截断、记忆提炼阈值、KB 命中与切块、上下文预算、工具轮数等 | 改代码 | 重新部署 |

### 1.2 上一版 §8 与代码不符

上一版 §8 写的是"助手配置**一律**由管理面持有……这是 ADR-016 的明确例外"。实际上搬进库的只有 9 个键：

```317:348:EOS.API/Program.cs
builder.Services.Configure<EOS.API.Features.Assistant.Situation.AssistantSituationBudgetOptions>(
    builder.Configuration.GetSection(EOS.API.Features.Assistant.Situation.AssistantSituationBudgetOptions.SectionName));
...
builder.Services.AddOptions<EOS.API.Features.Assistant.Governance.AssistantActionLimitsOptions>()
    .Bind(builder.Configuration.GetSection(EOS.API.Features.Assistant.Governance.AssistantActionLimitsOptions.SectionName))
```

而 `appsettings.json` 里**这四个节根本不存在**（全文无 `AssistantSituation` / `AssistantDiagnosis` /
`AssistantActionLimits` / `AssistantConfigWrite`）。于是这 35 项行为参数**既不在库里、也不在文件里**，
只存在于代码默认值中——连部署时想改都只能靠环境变量。§8 记录的是一句意图，不是状态。

### 1.3 「配了没人读」没有机制拦住

上一版专门用一节（§7）写"让已经配好的项真的被消费"。**需要专门写一节，就说明当时没有机制拦住
"界面有、代码没人读"**。对照 ADR-017 给系统参数定的判据——"参数 = **有读取方按类型解释其取值**"——
以及它配套的 `scripts/check-system-params.ps1` 门禁，助手这套没有等价物：
`AssistantSettingKeys.All` 里的键有没有读者、`AssistantActionLimitsOptions.MaxConfigCloneObjects` 有没有
消费者，全靠人肉保证。

### 1.4 因此本版要交付的是

**一套参数框架 + 一套运行机制**，使"管理助手"变成"配置一组有名字、有类型、有默认值、有读取方、
有归属、有作用域、有门禁的参数"，而不是"打开五个页面填几个框"。

## 2. 会话可见性：管理员**只看元数据，不看对话正文**（不变）

3101 会话管理给出：归属用户、标题、消息数、最近活跃、创建时间、归档状态，以及归档 / 取消归档 / 永久删除。

**不提供查看对话内容的入口**，理由不变：代码与文档里**没有任何"管理员可看他人会话"的既有口径**；
既有先例只有**聚合口径**（用量看板按人看"用了多少"，不按人看"聊了什么"）；真需要看正文时，它应当是
一件**有独立权限位 + 有审计留痕**的事（谁在何时看了谁的哪条会话），那是另一个决定。
**不要**因为"反正有 3101 读权限"就把正文一并放开。

## 3. 密钥边界：**密钥不入库**，库里只存**环境变量名**（不变）

- 密钥挂在**供应商（接入点）**上，不挂在模型上：`dbo.ASSISTANT_PROVIDER.API_KEY_ENV_VAR` 存的是
  **环境变量名**（如 `EOS_ASSISTANT_KEY_DEEPSEEK`），不是密钥本身。一个供应商一把密钥、一个端点，
  它名下所有模型（DeepSeek 的 Flash 与 Pro）共用；
- 管理员在界面上输入密钥后，服务端写入进程环境变量（当前进程立即生效）并持久化到用户级环境变量，
  界面**永不回显**，只显示"环境变量名 / 是否已配置 / 掩码末四位"；
- 用户级写入失败时接口**如实返回 `persisted=false`**，界面提示"重启后需重设"。**不假装持久化成功**；
- 与既有硬边界一致：前端不持有厂商密钥、不直连模型厂商；诊断包不含密钥。

**本版补充一条框架级规则**：密钥**不是一个参数**——它没有 `PARAM_KEY`，不进 SYSSS、不进作用域表、
不进参数目录。参数目录的"类型"只有 `bit / int / decimal / string` 四种，**没有任何一种能表达凭据**。
这条由门禁机械保证（§9 断言 4）。

## 4. 权限门（扩展）

### 4.1 模块与动作（不变）

| 模块 | 读 | 管理动作 |
|---|---|---|
| 3101 会话管理 | `CanBrowse(3101)` | 归档/取消归档/删除 = `CanEdit(3101)`（沿用"删除只对已归档开放"的服务端守卫） |
| 3102 模型与用量 | `CanBrowse(3102)` | 模型增改/切换/密钥写入 = `CanSetup(3102)` |
| 3103 知识库管理 | `CanBrowse(3103)` | 集合/文档维护 = `CanSetup(3103)` |
| 3104 机制与工具总览 | `CanBrowse(3104)` | 只读，无写动作 |
| 3105 助手设置 | `CanBrowse(3105)` | **参数读写 = `CanSetup(3105)`**（见 4.3） |

**不新造角色**：仍走 `SYSDH`（组）/`SYSDD`（个人）两表，新模块授权行镜像 2306——镜像只保证"与参照模块
同权"，授不授予由管理员在权限界面决定。**个人侧的助手不加权限守卫**（`/assistant` 与 `/assistant/sessions`
仍然登录即可用）。31 段这套权限只约束**管理面**。

### 4.2 参数面的门：按参数归属模块判，不按页面判

参数框架落地后，"谁能改哪个参数"不再由页面决定，而由**参数行的 `OWNER_MODULE`** 决定：

| 参数域（§5） | `OWNER_MODULE` | 读 | 写 |
|---|---|---|---|
| 助手全部域（PROMPT / CHAT / TOOL_LIMIT / CAPABILITY / GOVERNANCE / SITUATION / DIAGNOSIS / MEMORY / KB） | 3105 | `CanBrowse(3105)` | `CanSetup(3105)` |
| 模型与供应商（§12.3） | 保持领域表与 3102 页面 | `CanBrowse(3102)` | `CanSetup(3102)` |

### 4.3 落点：**3105 不走通用参数端点**

先记一个实测事实。通用参数端点 `SettingsController` 是"按 scope 解析归属模块 → 用该模块的
`CanBrowse` / **`CanEdit`** 放行"：

```58:62:EOS.API/Controllers/SettingsController.cs
    private async Task<bool> CanBrowseAsync(int moduleId, CancellationToken token) =>
        (await rightsRepository.GetAsync(userContext.UserId, moduleId, token)).CanBrowse;

    private async Task<bool> CanEditAsync(int moduleId, CancellationToken token) =>
        (await rightsRepository.GetAsync(userContext.UserId, moduleId, token)).CanEdit;
```

而 3105 的既有口径是**写 = `CanSetup`**，且 `PermissionModules.AssistantAdmin.Settings` 的注释写明了
"这一段的写权限比模型管理更要紧"（日上限改小会让所有人被拒、提示词改坏会让回答不再遵守格式契约）。

**⇒ 决定：把 `assistant` 登记进 `ModuleForScope` 会把 3105 的参数暴露在一条 `CanEdit` 就能写的路径下，
这是一次实打实的降权。因此不登记。** 具体做法：

- 助手参数的读写**仍经 `SystemParameterService`**（`ListAsync(3105)` / `SaveAsync(3105, …)` /
  审计与类型校验都在它那里），"单入口"这条不变；
- 但**端点挂在 3105 自己的控制器下**（`GET/PUT /admin/assistant/settings`），写门仍是 `CanSetup(3105)`；
- `ModuleForScope` 与 `ConfigScopes` **不增加** `assistant` 令牌 —— 通用端点在它上面**继续返回 404**；
- 只在**审计 token**（`ScopeToken(3105)` → `assistant`）上登记，让留痕可读。

一句话：**参数只有一个存储、一套读写服务，但入口的权限门按模块本来该有的强度给。**

## 5. 参数目录：唯一真源（正文主体）

### 5.1 一条参数要有哪些字段

现有 `AssistantSettingKeys` 只有 `Key / DisplayName / ValueType / Unit / Description / DefaultText`——
它已经做对了一半（默认值取自 `new AssistantSettings()`，界面提示不会漂移）。**缺的正是构成框架的那几个**：

| 字段 | 作用 | 现状 |
|---|---|---|
| `Key` | 参数键（全大写，下划线分词） | 有 |
| `DisplayName` | 界面标题（短名），与 `Description`（说明全句）分开 | 有 |
| `Group` | 参数域（`PROMPT` / `CHAT` / …），决定页面分组与 `GROUP_CODE` | 缺 |
| `ValueType` | `bit` / `int` / `decimal` / `string`（对齐 SYSSS 白名单，见 §6.3） | 有（多一个 `long`，本次消掉） |
| `DefaultValue` | 默认值，**代码里唯一一份** | 有 |
| `Unit` / `Description` | 界面提示 | 有 |
| `EffectScope` | `immediate`（本次全部是它） | 缺 |
| `ScopePolicy` | 被某一层覆盖时**值能往哪个方向走**（收紧 / 覆盖，§6.2） | 缺 |
| `ScopeLayers` | 这条参数**允许出现在哪些层**（模块 / 用户）。与策略成对声明；收紧型只能声明一层 | 缺（实施 §6.2 时补上的） |
| `Consumers` | **读取方符号清单**（类型名.成员名） | 缺——**这是本次的关键** |
| `ReadLines`（可选） | `Consumers` 门禁失败时给人看的定位提示 | 缺 |

`Consumers` 的作用：门禁脚本逐条断言该符号在源码里出现（§9）。于是"配了没人读"**在门禁上就是红的**，
不需要再靠文档提醒。

### 5.2 什么进参数表（判据）

**进参数表**：管理员**按业务判断**可以改，且改了不该动代码的值。

**不进**，分五类，各有各的理由——这一节本身就是框架的一部分，它挡住"把一切都参数化"的冲动：

| 不进的东西 | 位置 | 为什么不进 |
|---|---|---|
| token 估算系数（`1` 字符 ≈ `1` token） | `ChatService.cs:143` | **不变量**：估小会被厂商直接拒绝，估大只是少带历史；可配只会让裁剪失真 |
| 上下文预算下限 `1024` | `ChatService.cs:554` | 裁剪护栏，防止小窗口把预算算成 0 |
| 元→微元换算因子 `1_000_000` | `ChatService.cs:712` | 单位换算 |
| 三段提示词规则（指标口径 / 知识通道 / 诊断取证） | `ChatService.cs:161-181` | **契约文本，随能力面派生**：工具被关掉时对应规则应当一起消失；参数化会让两者漂移 |
| 敏感数据正则（手机 / 身份证 / 卡号） | `AssistantMemoryStore.cs:69-71` | **安全策略**：可配即等于"允许把身份证号记进记忆" |
| 标识符正则（`^[A-Za-z_][A-Za-z0-9_]{0,127}$`） | `Admin/ChangeSetService.cs:41` 等 | 安全不变量 |
| 职权动词闭集 | `Actions/AssistantActionRegistry.cs:131` | 红线（§6.4） |
| 幂等键长度 `32` | `Actions/AssistantActionIdempotency.cs:38` | 传输细节 |
| 四条红线（预演 / 幂等 / 越权上限 / 批核族条目） | `Governance/AssistantActionLimits.cs:36-45` | **红线**：作为常量登记进目录的红线清单，仅供门禁识别，**不产生可写参数** |
| 权限模块号 `2301` / `2302` / `2306` | `Config/ConfigWriteService.cs`、`KbController.cs` 等 | **权限**：能放宽权限的就不叫配置 |
| 指标表达式护栏（`MaxLength=500` / `MaxNodes=64`） | `Metrics/MetricExpressionParser.cs:38-39` | 属**指标域**（`api/v1/report-metrics` 端点共用），参数化会让两处口径分叉 |
| 被丢弃项标签的裁剪长度（`40` / `60` / `100`） | `Situation/SituationContextSanitizer.cs` | 实现细节，不承载业务语义 |
| 模型行 / 供应商行字段 | 3102 领域表 | 已按对象落在领域表（ADR-014 先例），不重复进 SYSSS |
| 密钥 | — | §3：参数类型里没有一种能表达凭据 |

### 5.3 参数目录全清单（**已交付 118 项**）

> **批后追加（迁移 `304`–`306`，共 11 项）**：报表只读工具 `list_reports` / `run_report`、
> 单据历史工具 `get_record_history` 与附件清单工具 `list_attachments` 的**四个开关**
> （域 `CAPABILITY`，声明在**能力面组末**——排在动作族之后）＋ 七条输出上限（域 `TOOL_LIMIT`）。
> 新工具的名字仍在 `AssistantToolKeys.ToolNames` 里（标题与开关覆盖面按它断言），
> 但开关的**声明位置**由 `AppendedToolNames` 决定：组内序号按声明顺序推导，
> 把新工具插回工具清单中间会把动作族及其后所有参数的序号整体推后，与已落库的行对不上。

> **目录与库按批同步生长**，不是一次建齐。原因：§9 断言 1/2 要求"目录 = 库 = 有读取方"三者一致，
> 一次性把 106 项落库会让其中 97 项在消费改造完成前处于"配了没人读"状态——**那正是本 ADR 要根除的形态**。
> 于是每批交付的是"目录条目 + 库行 + 消费改造 + 门禁"四件套（§10）：批 A 交付 9 项
> （`PROMPT` / `GOVERNANCE` / `MEMORY`），批 C 交付 36 项（`CAPABILITY` 的配置写准入、
> `GOVERNANCE` 的动作阈值、`SITUATION` 19、`DIAGNOSIS` 9），累计 45 项。
>
> **作用域列（"模块 · 收紧"）暂不接线**：这些参数的消费方目前只解析**全局**一层
> （`Layers` 一律 `None`，见 §14.5）。声明一个还没有按层解析的层，就是"配了没人读"的另一种形态。
>
> **2026-10-02 拍板：不逐域补上**。只有记录动作族三键真的按模块解析（`AssistantActionGate`，
> 已接线且已开管理面入口），其余保持全局——模块层不是"顺手补一层"：上限一按模块变，**发给模型的
> 工具声明文本就得跟着变**，工具清单要按请求重建，而工具清单逐模块不同会让**提示词前缀不再稳定**
> （厂商侧前缀缓存命中率下降，成本上升）；"按模块隐藏工具"本身也做不到（工具跨模块共享，
> 注释见 `AssistantActionGate` 类头）。等出现具体场景（"某模块不许用某工具"或"某模块上限更小"）
> 再逐域接，届时按 §6.2 补 `Layers: Module` + 执行门禁，而不是改工具声明。

约定：`作用域` 列写"可作用域化的层级 · 策略"（`收紧` = 只能比上级更严，`覆盖` = 可高可低，见 §6.2）；
`—` 表示不可作用域化。生效方式**全部 `immediate`**（改完即生效，没有"需重启"档）。

## 6. 存储：分区 + 作用域

### 6.1 三档分区

| 档 | 装什么 | 放哪 |
|---|---|---|
| **全局单值** | §5.3 的全部 106 项 | `dbo.SYSSS`，`OWNER_MODULE = 3105` |
| **按对象** | 供应商、模型（端点 / 模型标识 / 窗口 / 温度 / 单价 / 工具能力）；**嵌入模型也走这里**，按**用途**区分（`KIND` / `DIMENSION`，见 ADR-031） | 既有领域表 `ASSISTANT_PROVIDER` / `ASSISTANT_MODEL`（ADR-014 先例：有作用域的参数另立领域表） |
| **按作用域** | 模块级 / 用户级的覆盖值 | **新表** `dbo.ASSISTANT_PARAM_SCOPE`（§6.2） |

四个 `IConfiguration` 节**全部取消**（§8）。

### 6.2 作用域表与取值优先级

```sql
CREATE TABLE dbo.ASSISTANT_PARAM_SCOPE (
    SCOPE_TYPE   NVARCHAR(10)  NOT NULL,   -- MODULE / USER
    SCOPE_KEY    NVARCHAR(50)  NOT NULL,   -- 模块号（如 '1401'）或 USER_ID
    PARAM_KEY    NVARCHAR(64)  NOT NULL,   -- 必须是目录里声明可作用域化的键
    PARAM_VALUE  NVARCHAR(4000) NULL,      -- NULL = 本层不覆盖，继续向上取值
    CREATE_PERSON NCHAR(10) NOT NULL DEFAULT (N''),   -- 生命周期列按 ADR-013 口径
    CREATE_DATE   DATETIME  NOT NULL DEFAULT (GETDATE()),
    LAST_UPDATE_BY   NCHAR(10) NULL,
    LAST_UPDATE_DATE DATETIME  NULL,
    CONSTRAINT PK_ASSISTANT_PARAM_SCOPE PRIMARY KEY (SCOPE_TYPE, SCOPE_KEY, PARAM_KEY),
    CONSTRAINT CK_ASSISTANT_PARAM_SCOPE_TYPE CHECK (SCOPE_TYPE IN (N'MODULE', N'USER'))
);
```

> **与原设计的差异（实施时订正）**：时间戳列名由 `UPDATED_AT/UPDATED_BY` 改为
> `LAST_UPDATE_DATE/LAST_UPDATE_BY`，并补上 `CREATE_PERSON/CREATE_DATE`——ADR-013 的生命周期列口径
> （以及 `check-lifecycle-columns.ps1`）要求新表就位这四列，且与 `SYSSS` 同名同形，免得同一件事两处两个名字。

**取值优先级：用户 > 模块 > 全局（SYSSS）**。解析在唯一一处完成（§7.2），消费方拿到的永远是已合成的值。

三条硬规则，都由服务端强制、**不靠界面自觉**：

1. **只有目录声明可作用域化的键能进这张表**。未声明的键写进来 → 保存拒绝；
   库里已存在这样的行 → 生效时**保持上层值并把原因记进 `Problems`**（**不静默忽略**：
   静默忽略的表现是"界面上写着它是关的、实际却是开的"）。
2. **层与策略分两条声明**（实施时订正）。原设计只有"策略"一个字段，实现时发现它不足以定案：
   收紧型要判"比上层更严"，而**"上层"只用一层时才唯一确定**——模块已收紧、用户再放回全局水平这种组合，
   保存与生效会给出不同答案。于是目录里拆成两个字段：**层**（`Module` / `User` / 两者）与
   **策略**（`Tighten` / `Override`），并加一条规则：
   **收紧型只能声明一层**，覆盖型不受此限。`ScopePolicy` 与 `Layers` 必须**成对声明**
   （声明了一个却没有另一个 = 参数没有任何东西会去读它），由离线门禁 `ValidateCatalog()` 逐条断言。
3. **作用域键必须真实存在**（模块号在 `MODULES`、用户名在 `SYSDL`）。写错一个键，那一行**永远匹配不上
   任何请求**，界面上却显示着"已设置"——管理员的意图静默失效。宁可写的时候被拒。

**方向判据**（"关得掉、放不开"）：

| 策略 | 含义 | 现状 |
|---|---|---|
| **收紧**（`Tighten`） | 作用域值只能比上级更严：布尔只能取 `0`、阈值只能更小。**不允许"给某模块单独打开一个全局已关的能力"** | 已声明的是记录动作族三键（`ACTION_INSERT` / `ACTION_UPDATE` / `ACTION_DELETE`，按模块层解析并生效）；其余参数不声明 `Layers`，因此对它们的模块级覆盖一律被拒——**不逐域补上是 2026-10-02 的拍板**，理由见 §5.3 的注 |
| **覆盖**（`Override`） | 可高可低 | 仅 `USER_DAILY_CAP_YUAN` 一项（批 B 已落地并生效）：给别人调高限额是管理决定，不是越权 |

**红线参数不可作用域化**（§6.4）：目录里标记为红线的不产生可作用域声明，写进作用域表即启动失败。

### 6.3 迁移映射：`ASSISTANT_SETTING` 退役

| 事项 | 决定 |
|---|---|
| 表 | `dbo.ASSISTANT_SETTING` **退役**；迁移把 9 行按 §5.3 的键映射搬进 `SYSSS`（`OWNER_MODULE=3105`），然后 `DROP TABLE` |
| **键名** | **一律改全大写 + 下划线**（`SystemPrompt` → `SYSTEM_PROMPT`、`GlobalDailyCapYuan` → `GLOBAL_DAILY_CAP_YUAN`…）。理由：SYSSS 现存 103 行的键全是这个形状，同一张表两种命名风格会让门禁与检索都要写两套；本轮是重写而非兼容期，改名的代价一次性 |
| **"缺行 = 默认值" 的语义** | 在 SYSSS 里改为 **"`PARAM_VALUE` 为空 = 用 `DEFAULT_VALUE`"**：参数行是**定义**（含默认值），不该为"用默认值"而删行。于是"恢复默认"从"删掉覆盖行"变成"把值清空"，界面语义不变 |
| `ReserveMicroYuanPerRequest`（原 `long`，50000 微元） | 改为 `RESERVE_YUAN_PER_REQUEST`（`decimal`，默认 `0.05` 元）。理由：**微元是实现单位**（内部换算用），不该出现在管理界面的参数名里；SYSSS 的 `VALUE_TYPE` 白名单只有 `bit/int/decimal/string`，不为一个参数扩白名单；`int` 上界换算成元只有约 2147 元，语义上也不合适 |
| 类型收敛 | `bool` → `bit`、`int` → `int`、`decimal` → `decimal`；**取消 `long`**（唯一使用处即上一条） |
| `EFFECT_SCOPE` | 106 项**全部 `immediate`**。助手里没有"改完要重启"的参数——这正是 §7 的目标 |
| 预置行 | **不预置取值**，但**预置定义**：每批的行建齐，`PARAM_VALUE = NULL`、`GROUP_CODE`/`GROUP_LABEL`/`GROUP_SEQ`/`SEQ_NO`/`DESC_TEXT`/`EFFECT_SCOPE`/`OWNER_MODULE` 齐备。ADR-017 的"缺行 = 用默认值"在参数表里表达为"值列为空" |
| `DEFAULT_VALUE` 写不写 | **标量型（`bit`/`int`/`decimal`）写**（它们是运营要校准的数字，写在列里才叫数据）；**`string` 型留 `NULL`**（默认值留在代码里）——长文本写进列只会多出一份要人工同步的副本，它一旦跟不上代码，界面给出的默认值就是错的 |
| 归属白名单 | `SystemParameterService.ScopeModules` 增加 `["assistant"] = 3105`；`scripts/check-system-params.ps1` 的 `$AllowedModules` 与 SQL 断言 `OWNER_MODULE IN (…)` 增加 `3105`（否则门禁会把助手参数判成"归属越界"） |
| 代码引用登记 | `SystemParameterService.CodeReferencedKeys` 增加 `3105|…` 106 条（照现有 `110111|PRO_MRP` 的写法），供页面区分"这个参数有读者 / 没读者" |
| 审计 | 沿用 `SystemParameterService.SaveAsync` 的 `AUDIT_EVENT` + `AUDIT_FIELD_CHANGE`（前后值），`ACTION=PARAM_SAVE`、`RESOURCE_TYPE=SYSTEM_PARAM`、scope token `assistant` |

### 6.4 红线：机制不是文档

红线在 §5.2 里被排除在参数之外，但**必须能被门禁机械识别**。做法是把它们登记成目录里的一组常量清单：

| 红线 | 含义 |
|---|---|
| 预演恒开 | 动作先在同一事务内跑完整条路径后回滚，判不下来的行不写 |
| 幂等恒开 | 执行类动作的幂等键由服务端从工具调用身份推导，schema 里没有这个字段 |
| 越权上限 = 0 | 执行前按当前用户独立重新授权，fail-closed |
| 批核族条目 = 0 | 批核 / 解批 / 结案 / 取消结案在助手侧**没有注册项**（动作枚举与工具名面都表达不出来） |

**语义升级**：现有 `AssistantActionLimitsValidator` 只拦 `appsettings` 里的红线键名。本次改为
**在三个地方拦**：`SYSSS`（`OWNER_MODULE=3105`）、`ASSISTANT_PARAM_SCOPE`、以及任何残留的配置节——
任一处出现红线键名（含 `DryRunEnabled` `IdempotencyEnabled` `UnauthorizedActionLimit` `ApprovalFamilyLimit`
这类同义写法）即**启动失败**。理由不变：一个"配了但没人读"的开关比配错更危险，它会让人以为已经生效。

> **实施后的订正（批 F 记录）**：三处的处理强度**并不相同**，这是刻意的。
> **配置节**那一处（`AssistantActionLimits`）走启动失败：它是一行文件，改了下次启动就好，
> fail-fast 没有任何副作用。**`SYSSS` 与 `ASSISTANT_PARAM_SCOPE`** 那两处走的不是启动失败，
> 而是解析器把红线键记进**问题清单**（3105 页面与日志可见）并忽略其取值——
> 因为它们住在**库里**，而库里的行得能在应用里改：让一行坏数据把整个进程卡在启动阶段，
> 管理员连修的机会都没有。同一句"必须拦住"，落在文件上与落在库里是不同的动作。

## 7. 运行期装配：一个刷新点、一次快照

### 7.1 目录是代码，存储是数据，装配是唯一入口

```
AssistantParameterCatalog（代码声明：106 条 descriptor + 红线清单）
        ↓
AssistantParameterResolver（读 SYSSS + ASSISTANT_PARAM_SCOPE，按 §6.2 优先级合成）
        ↓
AssistantRuntimeSnapshot（强类型：Prompt / Chat / ToolLimit / Capability / Governance / Situation / Diagnosis / Memory / Kb + Model）
        ↓
AssistantRuntimeRegistry（唯一权威来源，实现 IAssistantRuntimeConfig）
        ↓
消费方：ChatService / 处境 / 诊断 / 记忆 / 知识库检索 / 工具装配
```

### 7.2 解析与快照

- **`AssistantParameterResolver`**：一次解析产出**全部 9 个域**的强类型对象 + 每个域的作用域覆盖结果。
  解析失败（值不是合法类型、越界）**逐条记 `Warning` 并沿用该键的默认值**，同时把问题清单随快照带出，
  由 3105 页面显式展示——沿用现有 `AssistantSettingKeys.Apply` 的 `Problems` 口径：
  **绝不静默用默认值冒充成功**（"界面显示 5 元、实际按默认值跑"是查不出来的）。
- **`AssistantRuntimeSnapshot` 扩展**：现有快照只有 `Model` + 全局 `Settings`；本次改为**含全部域**。
  一次请求取一次快照（`ResolvingChatModel` 已示范：Scoped 消费、请求内固定），于是
  **"这一轮回答到底按哪套参数跑的"是可回答的**。
- **消费方去 `IOptions`**：`AssistantSituationBudget` / `RecordDiagnosisReader` / `ConfigWriteService` /
  `FailureBreaker` 等改为从 `IAssistantRuntimeConfig.Current` 取值。`Program.cs` 里四处
  `Configure<T>(GetSection(...))` 一并删除（§8）。
- **刷新点只有两处，不新增第三处**：启动时（迁移之后，照 `WorkbenchDefinitionProvider` 的既有做法）
  与**管理员每次改动之后**（3105 保存、3102 模型改动、作用域表改动）。所以改任何参数都**不需要重启**。
- **刷新是全量或不动**：任一步失败只沿用旧值，绝不把正在工作的模型或参数撤掉——
  数据库短暂不可用、迁移还没跑完，都会走到这条路径上。

### 7.3 能力面门控：关得住，也要堵住"模型仍然调用"

`AssistantToolRegistry` 现在是"在 `Program.cs` 里硬编码 27 个 `GetRequiredService`"，**"开关"就是"删掉那一行"**。
本次改为**注册表定义 → 参数过滤 → 装配**：

- 每个工具声明自己的参数键（`TOOL_*`）、风险级（`Read / Draft / Write / AdminWrite`，已有）、
  以及**需要的模块门**（沿用工具内既有的逐模块重授权，不动）；
- `AssistantToolRegistry.Definitions` 只产出**未被关闭**的工具；`ChatService` 照旧取 `Definitions`；
- **但"发不下去"不等于"调不到"**：模型仍可能幻觉出一个已关闭的工具名。
  ⇒ `TryGet` 必须同时检查开关，命中已关闭的工具一律返回 `Deny`（不是"工具不存在"，
  而是明确告诉模型与用户"该能力已被管理员关闭"）。**关闭是双向的**：既不发给模型，也不执行。
- 红线工具面（批核族、权限授予类）**不产生任何参数键**，因为它们**没有注册项**。
  参数目录里出现这类键名（如 `TOOL_APPROVE` / `TOOL_RIGHTS_ADMIN`）即**启动失败**。

### 7.4 派生规则跟着能力面走

工具被关闭后，系统提示词里对应的**行为规则**必须一起消失（§5.2：三段规则是契约文本、不是参数）：
关掉 `resolve_metric` 与 `enum_metrics` 时不再注入"指标必须走系统口径"那段；
关掉 `kb_search` 时不再注入知识通道规则；关掉 `diagnose_record` 时不再注入诊断取证规则。
**派生而不是配置**，是为了让"规则说要用某个工具"与"那个工具还在不在"永远不会打架。

## 8. 配置归属：助手配置**不进 `appsettings`**（保留，本次落实）

**决定**：工作助手的**运行期业务配置**一律由管理面持有——

| 内容 | 放哪 |
|---|---|
| 106 项行为参数 | `SYSSS`（`OWNER_MODULE=3105`，3105 页面） |
| 模块级 / 用户级覆盖 | `ASSISTANT_PARAM_SCOPE`（§6.2） |
| 模型与供应商 | 3102 领域表（**含嵌入模型**，按用途区分；见 ADR-031） |
| 密钥 | 环境变量，库里只存变量名（§3） |

**为什么**：助手配置是**运行期要能改的业务配置**，不是部署参数。放在 `appsettings` 里，改一个模型名或
一个日上限要改文件加重启；而"管理员在界面上换模型、调限额"正是本能力的核心诉求。这与 ADR-016 的
「`appsettings.json` 成为唯一配置清单」不冲突：那条讲的是**部署配置**（连接串、日志、安全策略），
助手这一段属于运行期可管理的业务配置，是它明确的**例外**——例外写在这里，免得后人拿 ADR-016 把它搬回去。

**本次的落实（这是与上一版的关键差别）**：上一版只搬了 9 个键，本版把**四个 `IConfiguration` 节全部取消**：

| 取消的节 | 原有项数 | 去处 | 状态 |
|---|---|---|---|
| `AssistantSituation` | 19 | 域 `SITUATION`（`SIT_*`） | 批 C 已落地（迁移 `297`） |
| `AssistantDiagnosis` | 8 | 域 `DIAGNOSIS`（`DIAG_*`） | 批 C 已落地 |
| `AssistantActionLimits` | 4 | 域 `GOVERNANCE`（`ACTION_MAX_*`；红线部分转 §6.4） | 批 C 已落地 |
| `AssistantConfigWrite` | 4 | 域 `CAPABILITY` 的 `CONFIG_WRITE_*` | 批 C 已落地 |
| （写死在代码里的归因文案条数 `3`） | 1 | 域 `DIAGNOSIS` 的 `DIAG_ACTION_SUMMARY_LIMIT` | 批 C 顺带收进来 |

`AssistantActionLimits` 那一路的 `AddOptions<T>().Bind(…).ValidateOnStart()` **保留**：它现在只承担一件事——
启动时跑 `AssistantActionLimitsValidator`（配置里出现红线键即启动失败，§6.4）。该类型的取值同样改由
运行期参数视图提供（注册顺序在后，容器取最后一个 `IOptions<T>`）。

**取消"表为空就退回配置文件"这类兜底**：没有当前模型、或那把密钥没配，就是**未配置**——
助手以 `AI_MODEL_NOT_CONFIGURED` 失败，文案**指路**到"工作助手管理 → 模型与用量"。
另加 `GET assistant/availability`（登录即可访问），让前端在**打开助手时**就能说清楚，
而不是等用户打完字发送才失败（那时用户已经付出了打字成本，而原因跟他自己毫无关系）。

## 9. 门禁

### 9.1 四条断言，落在两个地方

**能离线判的走单测**（`dotnet test` 即可，不依赖库、不依赖服务），**必须看库的走真库单测**
（`[Trait("Category","Integration")]`，没有 `MSSQL_ERP_CONN` 时静默跳过，沿用
`AssistantRepositoryIntegrationTests` 的既有策略）。之所以要分：断言 1 只依赖源码，
把它绑在"能连库"上等于让常态 CI 跑不了。

| # | 断言 | 落在哪 |
|---|---|---|
| 1 | **目录 ↔ 读取方互证**：目录每条参数的 `Consumers` 符号必须在 `EOS.API/**/*.cs` 里出现（catalog 自身除外——把键名列一遍不等于有人读）。**"配了没人读"到此为止**——它不靠文档提醒，靠门禁变红 | 离线单测 |
| 2 | **目录 ↔ 库定义一致**：`SYSSS` 中 `OWNER_MODULE=3105` 的行，逐键核对 `VALUE_TYPE` / `DEFAULT_VALUE` / `GROUP_CODE` / `GROUP_SEQ` / `SEQ_NO` / `EFFECT_SCOPE`。**防止"界面显示 5 元、代码其实已经改成 8 元"**这类漂移（这是目录成为唯一真源的前提） | 离线单测（迁移脚本必须点名每个键）+ 真库单测（逐字段比对） |
| 3 | **作用域表合法**：`ASSISTANT_PARAM_SCOPE` 里的 `PARAM_KEY` 必须是在目录里声明可作用域化的键；`SCOPE_TYPE` 合法；**"收紧"策略的键，其值不得比全局值更宽松** | 真库单测（批 B 落地前该表不存在，断言走"表不存在"这一支） |
| 4 | **红线与密钥**：`SYSSS` / `ASSISTANT_PARAM_SCOPE` / 配置文件里出现红线键名 → 失败；参数表里出现疑似凭据键名（`API_KEY` / `SECRET` / `TOKEN`）→ 失败 | 离线单测（目录自检）+ 真库单测（全表扫描，不限归属模块） |

> **约定变更（原计划是 `scripts/check-assistant-params.ps1`）**：这条断言要拿目录的**对象**逐字段比对，
> 而 PowerShell 只能去解析 C# 源码——那是把编译期事实降级成文本匹配，且目录一改格式就会假红。
> 真库单测直接引用 `AssistantParameterCatalog`，比对的是同一份声明。**结构性的那部分**
> （定义完整性、`GROUP_SEQ` 唯一且非 0、归属模块已登记）已经由 `check-system-params.ps1` 覆盖
> ——本批已把 `3105` 加进它的归属白名单，不必再写第二个脚本去重复它。
>
> 落点：
> - `EOS.API.Tests/AssistantParameterCatalogTests.cs`（离线：目录自检、探针、坏值报告、读取方、迁移点名）
> - `EOS.API.Tests/AssistantParameterIntegrationTests.cs`（连库：逐字段比对、无目录外键、无红线/凭据键、旧表已退役）

### 9.2 同步既有门禁

- `scripts/check-system-params.ps1`：`$AllowedModules` 与 SQL 里的 `OWNER_MODULE IN (…)` 增加 `3105`；
  `Get-CodeReferences` 的所有者记号增加 `AssistantOwner`（现为 `SystemOwner|AttendanceOwner|AttendanceMonthlyOwner`）。
- `scripts/check-di-registrations.ps1`：装配层改造会动 DI 注册，改完必须过关（它拦的是"编译 0 错、端点全挂"）。
- `docs/guide/60`、`61`、`02`、`70` 与本 ADR 同批更新；`pwsh docs/guide/_tools/check-freshness.ps1 -Strict` 通过。

### 10.1 收尾批 F：三处"能看出但没堵上"的口子

| 项 | 内容 | 判据 |
|---|---|---|
| **检索端点无上界** | 新增 `KB_ENDPOINT_MAX_HITS`（默认 20，迁移 `302`，累计 **107 项**）：`POST /api/v1/assistant/kb/search` 的 `TopK` 由调用方传入，此前**没有上限**——一句请求就能让检索返回任意条数。现在夹在 1 与本值之间，响应回显实际生效条数。**不复用 `KB_SEARCH_MAX_HITS`**：那个管进模型上下文几条，这个管界面能翻出几条，合成一个会让"为省 token 调小工具上限"顺手把检索页缩水 | 传 100 得到 ≤ 上限，且响应里能看到生效条数 |

## 12. 已落地的事实（保留备查，不是本版的决定）

### 12.1 根级菜单组 31（明确记录的例外）

助手是**横切能力**，不属于任何业务子系统，也不是"系统管理"的子项，因此自成根组 31，与 21 工作流、
25 数据查询中心同级。**这是明确记录的例外**：历史上 `110112 日志管理` 曾因不符惯例被重编号为 `2313`。
为避免 31 段被后人"顺手订正"，本条理由必须留在文档里，**后续迁移不要把它改回 23**。

### 12.2 管理面五个模块（现状）

### 12.3 模型配置两级 + 预设目录

供应商表（端点 / 密钥变量名 / 默认超时）+ 模型表（模型标识 / 窗口 / 最大输出 / 温度 / 超时覆盖 / 单价 /
是否支持工具 / 是否当前）；`(供应商, 模型标识)` 唯一、外键指向供应商、**筛选唯一索引**保证至多一条
`IS_ACTIVE = 1`——"至多一个当前模型"是**数据库层面的事实**，不靠应用代码自觉。

**预设目录放代码里、不写种子数据**（`ModelAccess/AssistantProviderCatalog.cs`）：表装"用户配了什么"、
目录装"系统知道什么"，混在一起日后分不清哪些是官方参数、哪些被人改过；预置行还会绕过"初始状态必须
配置才能用"；价格与窗口随厂商调整，写进数据意味着升级要改数据。目录给**初值**，落库后每一项都能改。

**型号清单由"拉取"得到，不再只靠预设硬编码**（对话与嵌入**同一机制**）：预设目录只保证
"入口可发出去"（端点 / 协议 / 密钥环境变量名 / 超时），型号由管理员**填好密钥后向厂商拉取候选**
（OpenAI 兼容的 `GET /models`；非兼容协议按各家端点分派）、勾选后落库。

- **理由有实据**：目录里硬编码的型号会过期——`deepseek-chat` / `deepseek-reasoner` 与厂商文档
  当前给出的型号已经对不上。型号清单是**厂商的数据**，写在我们的代码里就是一份注定过期的副本；
- **拉取给不给得出字段，因厂商而异**：实测 DeepSeek 的 `GET /models` 除型号标识外**还返回窗口、
  最大输出、输入输出模态与 effort 等级**；而多数厂商只给标识。但**单价一定拉不到**——没有任何厂商在
  模型列表里报价格。所以预设里的元数据降级为"**参考初值**"：拉到的型号命中预设就预填、
  厂商给了就以厂商为准、都没有则留空并标"**未校准**"，由管理员补——**不猜**
  （猜小的窗口会削历史，猜错的单价会把成本归因算歪）；
- **认证头样式也是预设数据**：实测小米 MiMo 用的是 `api-key` 头而不是 `Authorization: Bearer`。
  把这行写死在客户端里，那家供应商就永远 401——所以端点、协议、认证头三者都归预设；
- **用途（对话 / 嵌入）由管理员指定**，不靠型号名猜：猜错会得到一个永远打不通的行，
  嵌入还要同时给出维度（ADR-031 §3.1）；
- **"能不能列出型号"是每家供应商的能力差异**（与"有没有嵌入端点"同类），落在预设数据里；
  界面据此明说"这家不支持列出型号，请手工填标识"，而不是让按钮转完圈给一个空白清单；
- **拉取失败如实说失败**（网络 / 密钥被拒 / 端点不支持），**不退回"用预设里那几个旧型号"**——
  那会把一次失败伪装成一次成功的列表。

**守卫**（服务端强制，不靠界面自觉）：密钥未配置的模型不能设为当前；当前模型删不掉；
名下有模型的供应商删不掉；停用供应商 = 它名下所有模型一起下线。

**一个已知限制**（免得被当成 bug）：`CODE` 上有唯一约束——`CODE` 决定用哪个客户端实现，
所以**同一家供应商暂时只能有一个接入点**。撞上是 409 加一句说明（不是 500）。将来真要支持多个接入点，
去掉那条唯一约束即可（`CODE` 的语义是"类型"而不是"身份"）。

### 12.4 已完成的三处"真正被消费"

单价（台账结算与用量看板按当前模型单价算，**留空退回全局兜底价、不按 0 元算**）、
上下文窗口（按窗口推预算裁剪历史：从最老的一端丢、**最新一条无论如何保留**）、
是否支持工具（不支持的模型不带 `tools` 去请求）。

### 12.5 四条实现要点

- 会话列表是**服务端分页**的，所以排序必须放服务端（前端排序只排当前这一页，看着排了其实是错的）；
- 模型从"启动期单例绑配置"改为"按当前模型解析"时，`IChatModel` 的生命周期由 Singleton 改为 **Scoped**：
  一次请求内模型固定（一条回答不会跨两个模型），跨请求又能读到新快照；
- **改配置与切模型都不需要重启**：`AssistantRuntimeRegistry` 在启动时与每次管理面改动后各刷新一次，
  `ChatService` 在请求开始时取一份快照。

## 13. 明确不做

- **不新建第二套参数机制**：助手参数进 `SYSSS`，不保留 `ASSISTANT_SETTING` 并"补齐元数据"——
  平台里出现两张同构的参数表，正是"造第二处真源"的教科书形态（ADR-017 的判据与门禁只有一份）。
- **不把参数表做成宽表**：不为新参数加列、不加"定义表 + 取值表"两分（ADR-017 §2.3）。
- **不做参数版本历史表**：留痕走既有 `AUDIT_EVENT` / `AUDIT_FIELD_CHANGE`。
- **不做"需重启"档**：助手里没有这类参数；出现一个就说明它本该是部署配置（那它就该留在 `appsettings`）。
- **不把权限与红线参数化**：权限模块号不进参数表；四条红线只登记、不可写（§5.2 / §6.4）。
- **不提供"管理员查看他人会话正文"**（§2）；**不把管理面权限加到个人侧**（§4.1）。
- **不把机制事实写进知识库或提示词**：机制问题走 `describe_mechanism` 从元数据与代码注册表现算，
  写进文档再检索就是第二真源（助手会偏向读文档，目录被架空）。
- **不新增页面解决"参数太多"**：106 项按 9 个域分组呈现在 3105 一页内；域内条目靠分组与搜索收敛，
  不为每个域开一个菜单——那会让"参数住在哪"重新变成需要记忆的事。

### 14.4 实施中的两处订正（批 C）

**① 消费方没有把 `IOptions<T>` 去掉，而是换了它的来源。** §7.2 原写"消费方去 `IOptions`"，实施时改判：
那要动 6 个类的构造签名与十来处取值点，换来的只是"取参数"换个写法；**要守的是数据来源**
（不能是 `IConfiguration`、不能有第二份默认值、改完立刻生效）。所以引入
`RuntimeParameterView<T>`（`Features/Assistant/Parameters/AssistantRuntimeOptions.cs`）——
它实现 `IOptions<T>` 但**每次访问 `Value` 都从运行期快照现取**。收益：

- 六个消费方（处境预算 / 诊断读者与编排 / 两个动作服务 / 配置写）**一行未改**；
- 四处 `Configure<T>(GetSection(…))` 全部删除，`appsettings` 里那四个节不再是任何数据的来源；
- 默认值仍只有一处（各 options 类的属性初始值，目录引用它们），且**改参数立刻生效**——
  连"消费方把值缓存进字段"这种陈旧读法都不会出现。

一处实现细节要记住：`AssistantActionLimitsOptions` 的 `AddOptions<T>().Bind(…).ValidateOnStart()`
**留着**（它承载红线守卫的启动校验），运行期视图的注册排在其后——`IOptions<T>` 取**最后一个**注册。

**② §5.3 里"模块 · 收紧"的条目，`Layers` 一律先声明为 `None`。** 这些消费方目前只解析全局一层；
声明一个还没接线的层，正是要根除的"配了没人读"。模块层的接线方式已经备好
（`IAssistantEffectiveParameters.ForAsync(userId, moduleId, …)`），随各域逐个接。

**③ 模块层从"动作族"这一批开始真正接线**（批 D2）。三个动作族开关是**唯一**声明了
`Layers: Module` 的参数，理由是它们的消费点 `AssistantActionGate` 本来就有"哪个模块"这个入参、
而且是异步方法——接线不需要改造任何签名。至此"某模块不许助手删除"是一条端到端生效的配置，
而不是一个没人读的声明。

**工具开关（27 项）仍然只解析全局一层**，这是刻意的：
- 注册表在自己的**构造函数**里算 `Definitions`，而按模块解析是异步的；
- 更要紧的是**按模块隐藏工具做不到**：`preview_record_action` / `apply_record_action` 是同一个工具
  服务所有模块的，把某个模块的开关反映到"发给模型的工具清单"上，等于替所有模块一起关掉它。
  所以动作族落在门禁处判定（按模块、逐次判定），而不是在工具清单上。

**27 个工具开关的中文标签由批 F 补齐**（`AssistantToolKeys.Labels` + `LabelOf`，标题与工具清单的一一对应由门禁断言）：
本节写它的时候，页面标题还是工具名本身。
它不影响正确性，只影响阅读。

**覆盖缺口已补（批 F）**：作用域查询按 `(SCOPE_TYPE, SCOPE_KEY)` 过滤是在
`AssistantParameterScopeStore.ListForAsync` 的 **SQL WHERE** 里完成的（读回来再筛等于把别人配过什么
带进这次请求的内存）。它此前只有离线断言（"规则层拿到什么行就按什么行算"），
现在由 `AssistantParameterIntegrationTests.Scope_Query_Returns_Only_The_Requested_Module_And_User`
连真库覆盖：造出"我的 / 别人的 / 我的模块 / 别的模块"四行，断言只回来两行，
并额外断言"只给用户不给模块"与"只给模块不给用户"各自只回一层——
按**整层是否出现**断而不是按条数断，这样"两个 `@` 参数接反"这类错误也会被抓住。
