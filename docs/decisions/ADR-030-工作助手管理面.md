# ADR-030：工作助手管理面（菜单组 31）

- 状态：已接受（**批 5 / 批 6 未落地**，见 §5 落地节奏）
- 日期：2026-10-01
- 相关：ADR-015（多标签工作区）、ADR-016（助手缺口清单与配置清单口径，见 §8 的例外）、ADR-029（用户反馈与一键日志打包）

> 本文按"**ADR = 事实**"维护：已落地的写成事实，未落地的**显式标注未落地**并写清当前的中间状态，
> 不把计划写成已完成。查询时以 §5 的批次状态为准。

## 背景

工作助手已经积累了会话、模型接入、知识库、记忆与工具注册表等能力，但**它不在菜单体系里**：

- `dbo.MODULES` 里没有任何"工作助手"模块行（全文搜"助手"零命中）；
- 助手只是悬浮抽屉 + 两个**不在导航里**的工作区标签（`/assistant`、`/assistant/sessions`，都没有权限守卫）；
- 于是"管理"只能靠运维改 `appsettings`、跑 `sync-guide-to-kb.ps1` 脚本、直接查库——**没有管理界面，也没有权限门**。

同时，助手自己的会话管理页（`/assistant/sessions`）是**个人视角**：它按 `USER_ID` 强制隔离，只能看自己的会话。系统侧需要的是**能管全系统**的管理面。

## 决定

### 1. 新开根级菜单组 **31 工作助手管理**，挂在它下面而不是 23 系统管理

模块号 `31` 与 `3101/3102/3103/3104` 此前均未被占用（已核对 MODULES 全表）。

**为什么新开根组，而不是遵循"定制页一律落 `/admin/*`，都归 23 系统管理"的惯例**：

- 助手是**横切能力**，不属于任何一个业务子系统，也不是"系统管理"的一个子项。它与 `21 工作流`、`25 数据查询中心` 同级——那两者也是自成根组的能力面；
- "定制页归 23"这条惯例的适用对象是**系统管理类的运维页**（用户、菜单、日志、数据表）。把助手管理塞进 23 会让"系统管理"这个根组同时承载两种东西，日后既不好找也不好授权；
- **这是明确记录的例外**：历史上 `110112 日志管理` 曾因不符惯例被 `284` 重编号为 `2313`。为避免 31 段被后人"顺手订正"，本条决定与理由必须留在文档里，后续迁移不要把它改回 23。

### 2. 会话可见性：管理员**只看元数据，不看对话正文**

3101 会话管理给出：归属用户、标题、消息数、最近活跃、创建时间、归档状态，以及归档 / 取消归档 / 永久删除操作。

**不提供查看对话内容的入口。** 理由：

- 代码与文档里**没有任何"管理员可看他人会话"的既有口径**（跨用户读会话的路径零命中），这是新决定，按最小暴露原则取窄的一侧；
- 既有先例只有**聚合口径**：用量看板（`GET assistant/metrics`，`2306` 的 `CanSetup` 门）能按人看"用了多少"，但**没有按人看"聊了什么"**；
- 真需要看正文时，它应当是一件**有独立权限位 + 有审计留痕**的事（谁在何时看了谁的哪条会话），那是另一个决定、另一次改动。**不要**因为"反正有 3101 读权限"就把正文一并放开。

### 3. 密钥边界：**密钥不入库**，库里只存**环境变量名**

3102 模型管理允许管理员添加 / 切换模型，但密钥按下列方式处理：

- 密钥**挂在供应商（接入点）上，不挂在模型上**：`dbo.ASSISTANT_PROVIDER.API_KEY_ENV_VAR` 存的是
  **环境变量名**（如 `EOS_ASSISTANT_KEY_DEEPSEEK`），**不是密钥本身**。一个供应商一把密钥、一个端点，
  它名下的所有模型（DeepSeek 的 Flash 与 Pro）共用——这是一把密钥的真实用法，也避免同端点重复填两遍；
- 管理员在界面上输入密钥后，服务端把它写入进程环境变量（**当前进程立即生效**）并持久化到用户级环境变量，
  界面**永不回显**，只显示"环境变量名 / 是否已配置 / 掩码末四位"；
- 用户级写入在受限账户或平台不支持时会失败：接口**如实返回 `persisted=false`**，界面提示"重启后需重设"。
  **不假装持久化成功**——否则重启后助手突然不可用，而界面上什么都看不出来；
- 与既有硬边界一致：`EOS.API/README.md`「前端不持有厂商密钥、不直连模型厂商」、`AGENTS.md`
  「模型调用经受控抽象」、ADR-029「诊断包不得包含密钥」。

这样做的收益：数据库备份 / 导出**不含任何密钥**；轮换密钥不需要改代码或改库；界面上可以安全地展示
"这个供应商用哪个环境变量"。

### 4. 权限门

| 模块 | 读 | 管理动作 |
|---|---|---|
| 3101 会话管理 | `CanBrowse(3101)` | 归档/取消归档/删除 = `CanEdit(3101)`（沿用"删除只对已归档开放"的服务端守卫） |
| 3102 模型与用量 | `CanBrowse(3102)` | 模型增改/切换/密钥写入 = `CanSetup(3102)` |
| 3103 知识库管理 | `CanBrowse(3103)` | 集合/文档维护 = `CanSetup(3103)` |
| 3104 机制与工具总览 | `CanBrowse(3104)` | 只读，无写动作 |

**不新造角色**：权限仍走 `SYSDH`（组）/`SYSDD`（个人）两表，新模块上线时把参照模块（`2306` 系统管理）的授权行**镜像**过来——镜像只保证"与参照模块同权"，授不授予由管理员在权限界面决定。

**个人侧的助手不加权限守卫**：`/assistant` 与 `/assistant/sessions` 仍然登录即可用（它们本来就是"每个用户自己的助手"和"自己的会话"）。31 段这套权限只约束**管理面**，不要顺手拿它去卡普通用户使用助手。

### 5. 落地节奏

1. **批 1（已完成）**：31 根组 + **3101 会话管理**（跨用户端点 + 页面）；随后补齐会话列表的**复选框多选、服务端排序、批量归档/删除**，以及归属用户**姓名**与累计 **Tokens** 两列；
2. **批 2（已完成）**：**3104 机制与工具总览**（纯只读）；**3103 知识库管理**（清单 + 删除，**不开放入库**）；
3. **批 3（已完成）**：**3102 模型与用量** —— 模型表 `dbo.ASSISTANT_MODEL`、可运行期切换的模型注册表，以及 §3 的密钥治理（只写不读、库里只存环境变量名）；顺带补上"按模型"的用量聚合（`MODEL_NAME` 此前只写不聚合）；
4. **批 4（已完成）**：**模型配置改为两级**（§6）—— 新增供应商表、模型表重构为模型级、预设目录、以及让窗口 / 单价 / 工具能力**真正被消费**（§7）。四个管理模块本身在批 3 已全部落地，批 4 是把"配了却没人用"的那部分接上；
5. **批 5（已完成）**：**3105 助手设置**（提示词 / 限额 / 熔断，缺行 = 代码默认值）+ §8 落地——**删掉 `appsettings` 的 `Assistant` 段**，`AssistantSettings` 不再从 `IConfiguration` 绑定，**取消"表为空就退回配置文件"的兜底**；
6. **批 6（已完成）**：**3102 页面改成两级界面**（供应商 → 在其下挂模型；从预设目录选供应商并批量落库；未配置空状态）。

**六个批次至此全部落地。** 四条实现要点留在这里备查：

- 会话列表是**服务端分页**的，所以排序必须放服务端（前端排序只会排到当前这一页，看着排了其实是错的）；
- 模型从"启动期单例绑配置"改成"按当前模型解析"时，消费方 `IChatModel` 的注册生命周期由 Singleton 改为
  **Scoped** —— 一次请求内模型固定（一条回答不会跨两个模型），跨请求又能读到新快照（切换无需重启）；
- **模型的"当前"是数据库层面的事实**：至多一条 `IS_ACTIVE = 1` 由筛选唯一索引保证，不靠应用代码自觉；
- **改配置与切模型都不需要重启**：`AssistantRuntimeRegistry` 在启动时与每次管理面改动后各刷新一次，
  `ChatService` 在请求开始时取一份快照（所以一轮回答全程按同一套参数跑）。

每批都必须**自身完整可用**：出现"菜单点开是空壳"或"页面写不进库"就是没做完。

### 6. 模型配置是**两级**的：供应商 + 模型

同一个供应商下本来就有多个模型（DeepSeek 的 Flash 与 Pro、OpenAI 的 4o 与 4o-mini）。批 3 把"供应商级"
与"模型级"的东西混在一行里，加第二个模型要重复填端点与密钥变量名，换一把密钥要逐条改。批 4 拆成两级
（迁移 `292`）：

| 表 | 装什么 |
|---|---|
| `dbo.ASSISTANT_PROVIDER` | 供应商 / 接入点：`CODE`（与预设目录对应）、显示名、`BASE_URL`、**`API_KEY_ENV_VAR`**、默认超时、启用、排序 |
| `dbo.ASSISTANT_MODEL` | 模型：所属供应商、`MODEL_CODE`（真正发给厂商的那个标识）、**上下文窗口**、最大输出、默认温度、超时覆盖（留空 = 用供应商的）、**输入 / 输出单价**、**是否支持工具**、是否当前、启用、排序 |

约束落在数据库上：`(供应商, 模型标识)` 唯一、外键指向供应商、**筛选唯一索引**保证至多一条 `IS_ACTIVE = 1`
——"至多一个当前模型"是**数据库层面的事实**，不靠应用代码自觉。

**预设目录放代码里，不写种子数据**（`EOS.API/Features/Assistant/ModelAccess/AssistantProviderCatalog.cs`）：
系统"知道"的供应商与模型（DeepSeek / OpenAI / 百炼 / 智谱 / Moonshot / 自定义）连同端点、上下文窗口、
最大输出、是否支持工具一起内置。三条理由：

1. 表的语义是"**用户配了什么**"，目录是"**系统知道什么**"——混在一起，日后分不清哪些是官方参数、哪些被人改过；
2. 在迁移里预置行会**绕过"初始状态必须配置才能用"**（表非空就等于已配置），与 §8 的初始态要求直接冲突；
3. 价格与窗口随厂商调整，写进数据意味着升级要改数据、而且改不动已经落库的那些行。目录给的是**初值**，
   落库后每一项都能改。

价格刻意**留空**：各家实际单价随账号折扣、缓存命中与时段变动，写一串看起来很权威的数字比留空更误导——
留空时界面会明确告诉你"当前用的是全局兜底价"。

**守卫（服务端强制，不靠界面自觉）**：密钥未配置的模型**不能设为当前**（否则所有人的助手立刻不可用，
而原因只写在服务端日志里）；**当前模型删不掉**（否则助手会在无人察觉时变成"未配置"）；**名下有模型的
供应商删不掉**（级联会一次带走整家供应商的配置）；**停用供应商 = 它名下所有模型一起下线**（不必逐个停用模型）。

**一个已知限制（写在这里免得被当成 bug）**：`CODE` 上有**唯一约束**——`CODE` 决定用哪个客户端实现，
所以**同一家供应商暂时只能有一个接入点**。想用"同一个 DeepSeek 的另一个端点或另一把密钥"，得先删掉已有
的那一个，或改用 `custom`。撞上去是**409 加一句说明**（不是 500），界面上目录里的 CODE 被占完时也会解释
一句；将来真要支持多个接入点，去掉那条唯一约束即可（`CODE` 的语义是"类型"而不是"身份"）。

### 7. 让已经配好的项**真的被消费**

这条是批 4 的重点：把配置摆上界面却没有任何代码读它，等于没做。批 3 交付的字段里，有三项当时**一个都没被消费**：

| 配置 | 批 3 的实际状态 | 批 4 之后的消费点 |
|---|---|---|
| **单价**（输入 / 输出，元每百万 token） | 全局常量 `1 / 2 元` | 台账结算（`SettleAsync` 写进 `ASSISTANT_USAGE_DAY` 的钱）与用量看板都改按**当前模型的单价**算 |
| **上下文窗口** | 完全没有——`ChatService` 硬编码"最多 40 条"，**不看 token** | 按窗口推预算裁剪历史：从最老的一端丢、**最新一条无论如何保留** |
| **是否支持工具** | 完全没有——无条件带 `tools` 去请求 | 不支持的模型不再带 `tools`（否则厂商直接报参数不合法，而错误里看不出真正原因） |

两条口径要写清楚，否则后人会"顺手优化"掉：

- **单价留空退回全局兜底价，不按 0 元算**。0 元会让 `SPENT + RESERVED <= CAP` 永远成立，日上限就废了。
  换个单价差十倍的模型却仍用同一套单价判限额，等于把限额变成一个与实际花费无关的数字；
- **窗口裁剪是"估算"不是"精确"**：没有引入 tokenizer（各家算法不同、还要跟着模型版本更新），
  按"1 个字符 ≈ 1 个 token"取**上界**。代价不对称——估多了只是少带些历史，估少了会被厂商直接拒绝。

### 8. 助手配置的归属：**不进 `appsettings`**（**已落地**）

**决定**：工作助手的配置一律由本段的界面持有——模型与供应商在 3102（批 4 已落地），提示词 / 日上限 /
单价兜底 / 熔断参数在 3105（批 5）。写密钥仍然只写环境变量，§3 不变。

**为什么**：助手配置是**运行期要能改的业务配置**，不是部署参数。放在 `appsettings` 里，改一个模型名要改文件
加重启；而"管理员在界面上换模型"正是本能力的核心诉求。这与 ADR-016 的「`appsettings.json` 成为唯一配置
清单」不冲突：那条讲的是**部署配置**（连接串、日志、安全策略），助手这一段属于运行期可管理的业务配置，
是它明确的**例外**——例外写在这里，免得后人拿 ADR-016 把它搬回去。

**落地形态（批 5）**：`appsettings.json` 里的 `Assistant` 段**已删除**，`AssistantSettings` 不再从
`IConfiguration` 绑定。模型与供应商来自 3102，全局策略来自 3105（`dbo.ASSISTANT_SETTING`，
**缺行 = 代码默认值**，所以"恢复默认"就是删掉覆盖行，升级调整默认值时没被改过的参数会自动跟着走）。
**"表为空就退回配置文件"这条退路被取消**：没有当前模型、或那把密钥没配，就是**未配置**——
助手以 `AI_MODEL_NOT_CONFIGURED` 失败，文案**指路**到"工作助手管理 → 模型与用量"。另加
`GET assistant/availability`（登录即可访问），让前端在**打开助手时**就能说清楚，而不是等用户打完字发送
才失败（那时用户已经付出了打字成本，而原因跟他自己毫无关系）。

**消掉的分叉**：原先 `appsettings` 写的是 `${DEEPSEEK_APP_KEY}`，而 `README.md`、`QUICKSTART.md`、
`docs/guide/02`、`scripts/dev/set-eos-env.ps1` 全都让人去设 **`EOS_ASSISTANT_API_KEY`** ——两个名字不一样，
**照文档做的环境里助手的密钥实际是空的**。现在环境变量名是每个供应商一行数据、在界面上填，`appsettings`
里不再有引用，这个分叉自然消失。

## 影响

- `dbo.MODULES` 新增根组 31 与其子模块；`SYSDH`/`SYSDD` 镜像 `2306` 的授权行；
- `ModuleRouteValidator.ExactRoutes` 需登记新页面路径（否则菜单点开是占位页，菜单管理后台也保存不了这个 URL）；
- 前端 `workspaceRoutes.tsx` / `lazyRoutes.tsx` / `routeMeta.ts` 各登记一次；
- 3101 需要**新的跨用户仓储方法与端点**——既有 `AssistantRepository` 的每个 SQL 都硬绑 `USER_ID`，且接口注释声明"所有读写按 USER_ID 强制隔离"；**不改既有方法语义**，另开一个管理侧仓储与端点；
- 批 4（§6 / §7）落了这些位置，查询时按它们找实现：迁移 `292_assistant_provider.sql`（建
  `dbo.ASSISTANT_PROVIDER` + 重构 `dbo.ASSISTANT_MODEL`）、`EOS.API/Data/AssistantModelCatalog.cs`（两级读写）、
  `EOS.API/Features/Assistant/ModelAccess/AssistantProviderCatalog.cs`（预设目录）、
  同目录 `AssistantModelRegistry.cs`（当前模型快照 + `ResolvingChatModel`，`IChatModel` 由 Singleton 改 **Scoped**）、
  `AssistantSecretStore.cs`（只走环境变量的密钥存取）、`EOS.API/Features/Assistant/ChatService.cs`
  （窗口裁剪与按模型计价）、`AssistantAdminController.cs`（`/admin/assistant/{presets,providers,models,usage}`）；
- **迁移 291 + 292 同批交付**：291 建的是一级形状、292 立刻改成两级。292 在检测到"已是两级形状"时跳过重建，
  因此它对已迁移的库可重复执行（干跑门禁 `scripts/test-migration-dryrun.ps1` 正是这么重放它的）；
  真遇到"291 旧形状且已有数据"则**大声 `THROW`**，不静默抹掉别人的配置。
