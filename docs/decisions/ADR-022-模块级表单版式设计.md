# ADR-022：模块级表单版式设计——版式表、设计态与拖拽编排

- 状态：**草案 v6（2026-09-25）**——§11 已拍板 18 项、待确认 0 项；新增 §13 实施契约（写给执行 Agent）、§14 开工检查清单
- 版本：v6（v5 后收敛：`FORM_ADJUST_TAG` 确定退役；补实施契约：接入点/端点/迁移编号/JSON 形状/验收判据）
- 日期：2026-09-25
- 决策者：用户（Larry）+ 开发 Agent
- **重塑**：ADR-006（统一表单一次性重构——本 ADR 推翻其「不做可视化表单设计器」与「只消费既有 `FORM_*` 元数据」两条，
  其余渲染契约继续有效，见文末对照表）；`docs/项目计划.md` §5（「可视化表单设计器 不实施」收敛为「实施**版式编排器**，仍不做低代码」）
- 相关：ADR-008（字段数据来源模型）、ADR-010（可视化版式设计器——**权限位与形态的先例**）、
  ADR-013（单据生命周期列规约）、ADR-018（单据动作按钮——`FORM_BUTTONS` 不动）、
  ADR-019（模块管理拆分——`MODULE_CONFIG_TAG` 先例）、ADR-021（配置面白箱化——同一配置面改造谱系）
- 术语：
  - **版式**＝字段在统一表单上的排布（页签、顺序、占位、复合格、分节、表单内移出），**不含**字段定义（类型/校验/取数/权限）。
  - **设计态**＝统一表单的一种模式：同一套渲染、控件禁用、只做版式操作。
  - **表级默认**＝`FIELDS.FORM_*` 现存配置，本 ADR 后降级为「新模块建版式时的种子与零配置兜底」。
  - **模块级全量定制**＝某模块一旦有版式行，其表单版式即完全由版式表决定（§2.3）。
  - **字段池**＝该模块主表 ∪ 明细表在 `FIELDS` 已注册的字段集合（设计态"添加字段"的来源）。
  - **占位**＝字段在栅格中占据的块大小，`列跨度 × 行跨度`（§3.2）。

## 摘要（先读我，写给人类）

**要解决的问题**：统一表单的"形态"今天配在**字段**上（`FIELDS.FORM_TAB_NO/FORM_ORDER/FORM_SPAN/FORM_CELL_GROUP/FORM_CELL_ROLE`），
而形态是**模块**的属性。后果很硬：

- 一个物理表被多个模块共用（实测 **26 张**，`MOC_PRODUCE_M` 被 **6 个模块**共用），这些模块的版式**只能一模一样**；
- 配置者要改一个字段的位置，得进"字段维护"（一个**表级**页面），既不直观，也会**顺手改到别的模块**；
- 表单形态里有一列（`FORM_NEW_LINE`）**全库 0 行在用**，有一列（`FORM_CELL_GROUP`）**同时承担"复合格组"和"分节"两种语义**，
  分节还得靠"同组 ≥2 个主字段"去**猜**；
- 需求"把客户名从表单上拿掉"，今天只能改 `IS_VISIBLE`——而这一列被**选择器/菜单/打印/报表/权限/表达式/搜索**等
  9 处以上共享，"表单里不显示"根本不是一个独立概念。

**本 ADR 的决定，用一句话说**：

> 把"表单长什么样"从**字段**上摘下来，放进一张**模块级版式表**（`M_IDX` + `T_ID` + `F_ID`）；
> 在统一表单上开一个**设计态**——右键进入、所见即所得、**拖拽排序、右键精修、页签增改、跨页签移动、任意占位块、从字段池增删字段**；
> **保存即生效**；**零配置也能用**（不配就按现有规则生成一份默认版式，丑但可用）。

**打个比方**：

- 现在像**把家具焊死在地板上**——想挪一张桌子，得连房子一起改，而且隔壁房间也跟着动（共用表的模块）；
- 版式表像**给每个房间配一张自己的家具图**——同一批家具（字段），每个房间怎么摆（版式）各管各的；
- 设计态则是**那间房里的"布置模式"**：灯亮着、能搬东西，但**按下开关前一切都是干的**（保存才落库）。

**与"不做低代码"的关系（重要）**：本 ADR **不**打开低代码的口子。设计态只能**重排既有字段**——
不能新增字段定义、不能改数据类型/校验/取数/权限。需求 7 的"添加字段"是
**把模块表里已注册但没排进表单的字段放回来**，不是新增字段定义——这个区别是本 ADR 的边界线。

**本 ADR 定与不做**：

- ✅ 已定：版式表结构与键（§2）、模块级全量定制（§2.3）、零配置推导（§2.4）、明细本期一次到位（§2.5）、
  流式显式装箱（§3.1）、占位块语义（§3.2）、设计态 UX 规格（§4）、不可移除规则（§4.6）、
  权限位复用 `FORM_DESIGN_TAG`（§5.1）、保存即生效（§6）、`FIELDS`/`MODULES` 减负（§7）。
- ❌ 不做：低代码、明细"格"版式（明细只做列顺序与显隐）、按用户/按角色的版式、自由画布（绝对定位）、
  打印版式（属 ADR-010）、版式版本历史表、提交期定义版本校验。

**阅读路线**：业务/顾问读摘要、§1、§4；实现者读 §2–§3、§5–§7、§9；拍板者读 §11。

## 1. 背景与调研事实

### 1.1 实测取证（2026-09-25，连 `EOS.ERP` 直查 + 代码核对）

| 项 | 实测 | 含义 |
|---|---|---|
| 工作台模块 | **279 个**（`MODULES.M_URL='/workbench'`） | 版式的真实作用域 |
| **共用主表** | **26 张**被 ≥2 个模块共用；`MOC_PRODUCE_M` **6 个**、`MOC_GET_M` **5 个**、`INV_OCCUR_OUT_M` **4 个** | **字段级版式无法表达"同表不同单据不同版式"**——本 ADR 最硬的理由 |
| `FIELDS` | 12181 行；`FORM_ORDER` 3471 行、`FORM_CELL_GROUP` 1320 行、`FORM_CELL_ROLE` 1320 行、`FORM_SPAN=2` 118 行、`FORM_OPTIONS` 64 行 | 版式迁移的存量规模 |
| `FORM_NEW_LINE` | **全库 0 行在用** | 死配置 |
| 页签/列数 | 124 个模块有 `FORM_TABS`、139 个有 `FORM_COLUMNS`；`FORM_TABS` 是 `1=客户订单--1;2=客户订单--2` 这种**自造分隔符字符串** | 页签需要行级增删改，字符串格式是阻碍 |
| 孤儿从字段 | **4 处**：`COP_ORDER_M.CLIENT_NAME`、`PUR_PURCHASE_M.SUPPLIER_NAME`、`INV_OCCUR_IN_M.BILL_NAME`、`SYSDL.G_DESC` | 无门禁拦截，配错了不报错、只是不显示 |
| **主/明细同名字段** | **909 组** | **`T_ID` 不可省**：只按 `(M_IDX, F_ID)` 建键会撞车 |
| 必填字段 | `IS_VERIFY=1` 共 773 行；其中**只有 2 行同时 `IS_VISIBLE=0`** | "必填但隐藏"是**特例**（§4.6 例外名单极短） |
| `IS_AUTOINC` | 全库 0 行 | 服务端填充判定主要来自审计列与"必填且隐藏"，不是自增位 |
| 字段池规模 | 单模块最多 **178 个字段**（1209）、2401 样品 177、1502/1512 制令单 114 | 字段池**必须有搜索与筛选** |
| **版式设计权限位** | `SYSDD`/`SYSDH` **已有** `FORM_DESIGN_TAG`（完整设计）与 `FORM_ADJUST_TAG`（微调），迁移 `031` 建、默认 0；**已接线但只接给报表版式设计器**（`ReportFormLayoutRepository.GetDesignerModeAsync` + `LayoutDesignerController` + `LayoutDesignerPage`） | §5.1：**不需要新增列**，需要的是"复用 + 补齐接线缺口" |
| 权限位现状 | `SYSDD.FORM_DESIGN_TAG=1` 共 **465 行**（2026-08-31 给开发期 ADMIN 测试账号按模块批量授过，可逆）；**`RightsAdminRepository` 的读写列白名单里没有这两位** ⇒ 权限管理界面目前**勾不了** | 必须补：否则用户无法在界面上授权 |
| 报表版式先例 | `REPORT_FORM_LAYOUT` / `_VERSION` / `_BINDING` **三表全 0 行** | 借鉴存储形态；「按客户 copy-on-write」不适用于模块版式 |
| 模块 ID 列名 | 旧库表统一 `M_IDX`；新系统自建表用了 `MODULE_ID`（`WORKBENCH_*`/`MODULE_*`/`REPORT_*`/`ATTACHMENT`/`AUDIT_EVENT`/`FORM_CHOOSER_SOURCE_MEMO`） | 用户拍板：**统一 `M_IDX`，不再区分新旧**（§7.5） |

### 1.2 现状渲染模型（决定 §3 的可行性判断）

- 前端 `formLayout.ts`：`buildFormCells`（主从合格）→ `buildFormSections`（分节）→ **`buildFormRows`（按列数打包成"行"）**；
  `FormEditorPage.tsx` 逐行渲染。
- CSS（`styles/app.css:918`）：**每一行是一个独立的 CSS Grid**，行内的 `.erp-form-cell` 是它的格子。
- 结论：**列跨度便宜**；**行跨度在当前模型下无法表达**（跨行的单元格没有承载它的容器）。
  要做"占两行/三行"，必须把**整节改成一张统一的栅格**（§3.1）。

### 1.3 缺口归因

| 现象 | 根因 | 本 ADR 的处置 |
|---|---|---|
| 同表不同模块版式锁死 | 版式配在字段（表级）上 | 建模块级版式表（§2） |
| "表单里隐藏"做不到 | 只有跨子系统的 `IS_VISIBLE` | 新增模块级 `IS_HIDDEN`（§2.1） |
| 分节靠猜 | `FORM_CELL_GROUP` 一个列两种语义 | 拆成 `CELL_GROUP` + `SECTION_ID`（§2.2） |
| 版式错了不报错 | 无结构门禁 | 新增 `check-form-layout.ps1`（§5.3） |
| 改版式要进表级页面 | 没有模块级入口 | 设计态 + 右键入口（§4） |
| 明细列顺序/显隐无法按模块定制 | 明细只认 `IS_VISIBLE` | 明细纳入版式表（§2.5） |
| 权限位存在却无法在界面授予 | `RightsAdminRepository` 漏了两列的读写白名单 | §5.1 接线缺口清单 |

## 2. 决策：数据模型

### 2.1 两张表（DbUp 迁移落地，全大写命名，键一律 `M_IDX`/`T_ID`/`F_ID`）

```
MODULE_FORM_LAYOUT                       -- 字段版式（一行 = 一个字段在某模块表单上的位置与占位）
  M_IDX       INT           NOT NULL     -- 模块 M_IDX
  T_ID        NVARCHAR(100) NOT NULL     -- 字段所在表：模块主表或明细表（909 组同名主/明细字段 ⇒ 不可省）
  F_ID        NVARCHAR(100) NOT NULL
  TAB_NO      INT           NOT NULL     -- 页签号（默认 1；明细行忽略）
  ORDER_NO    INT           NOT NULL     -- 页签内序号（主表）/ 明细列序号（明细）
  SPAN        TINYINT       NOT NULL     -- 列跨度 1..MODULES.FORM_COLUMNS（默认 1；明细忽略）
  ROW_SPAN    TINYINT       NOT NULL     -- 行跨度 1..3（默认 1；明细忽略）
  NEW_LINE    BIT           NOT NULL     -- 强制换行（默认 0；明细忽略）
  SECTION_ID  NVARCHAR(50)  NULL         -- 分节（与 CELL_GROUP 解耦，§2.2；明细忽略）
  CELL_GROUP  NVARCHAR(50)  NULL         -- 复合格组（明细忽略）
  CELL_ROLE   TINYINT       NOT NULL     -- 0 普通 / 1 主字段 / 2 从字段（明细忽略）
  IS_HIDDEN   BIT           NOT NULL     -- 表单/明细内不显示（≠ FIELDS.IS_VISIBLE）
  UPDATED_BY  NVARCHAR(50)  NULL
  UPDATED_AT  DATETIME2     NOT NULL DEFAULT SYSUTCDATETIME()
  PRIMARY KEY (M_IDX, T_ID, F_ID)

MODULE_FORM_TAB                          -- 页签（需求 4 的落点）
  M_IDX       INT           NOT NULL
  TAB_NO      INT           NOT NULL     -- 顺序即页签号；TAB_NO=1 为常驻"默认"页签（§4.3）
  TAB_TITLE   NVARCHAR(50)  NOT NULL     -- 空串 = 显示兜底名"默认"
  PRIMARY KEY (M_IDX, TAB_NO)
```

**不建版本历史表**（用户拍板）：回滚改由 §6.4 的审计留痕 + 「重置为默认版式」承担。

**为什么是行式表而不是整份 `LAYOUT_JSON`**：配置面需要按 `(模块, 表, 字段)` 做**查询、校验、门禁与审计 diff**——
"哪些模块排了这个字段""主从是否成对""必填字段有没有被藏起来"用 JSON 都要先解析。故取
**行式存 → 保存期编译成 JSON 进 `WORKBENCH_DEFINITION_SNAPSHOT.DEFINITION_JSON`**。

**`MODULES.FORM_COLUMNS`（每行列数）已随 P4 退役，统一表单固定一行四列**（用户 2026-08-31 拍板
"全局固定一行四列、忽略该元数据"；实测三处读点全部摘除后删列，见 §15 订正 4）。
`MODULES.FORM_BUTTONS` 保持不动（属 ADR-018 动作按钮域）。只有 `MODULES.FORM_TABS` 迁入 `MODULE_FORM_TAB`。

### 2.2 分节与复合格解耦（修既有缺陷）

现状 `FORM_CELL_GROUP` **一种列两种语义**：既是"复合格组名"，又被 `buildFormSections` 当"分节名"用
（同组 ≥2 个主字段即视为一节）——配置者**无法显式声明"这是一节"**。新模型拆开：

- `CELL_GROUP` + `CELL_ROLE`：**复合格**（`[主][选择钮][从]` 同格）；
- `SECTION_ID`：**分节**（字段归到某节，节标题来自配置，不再靠数量猜）。

层级固定为：**页签 > 分节 > 行 > 格**。分节标题渲染为**整行横条**（沿用 `.erp-form-group-title`）。

### 2.3 模块级全量定制（**关键语义，需求 8 的前提**）

> **某模块一旦存在任何 `MODULE_FORM_LAYOUT` 行，其表单版式即完全由版式表决定；该模块主表/明细表里
> 没有出现在版式表中的字段，一律视为"未加入表单"，不再回落到 `FIELDS.FORM_*`。**

原因：若采用"逐字段回落"（有行用行、无行用默认），则"把字段从表单移除"**在语义上不可能**——
删掉行等于回到默认，字段刷新后又出现了。故必须**模块级原子**。

配套：
- 首次为某模块保存版式时，服务端**从 `FIELDS.FORM_*` 生成一份完整种子**，此后各模块独立演化；
- 共用表的两个模块**互不影响**：A 定制后 B 仍走默认；B 后来定制时，种子来自 `FIELDS`（不来自 A）；
- `FIELDS.FORM_*` 保留为**种子与兜底**，不再作为运行时真源。

### 2.4 零配置默认态（"不配置也能用，只是比较丑"）

| 版式属性 | 默认推导 |
|---|---|
| 页签集合 | 无 `MODULE_FORM_TAB` 行 → 单页签 `TAB_NO=1`，标题显示"默认"（**不写库**，§4.3） |
| `TAB_NO` | `FIELDS.FORM_TAB_NO`，空则 1 |
| `ORDER_NO` | `FIELDS.FORM_ORDER`，空则 `SYSQL_DEFAULT.F_IDX`，再空则 `F_ID` 序 |
| `SPAN` | `FIELDS.FORM_SPAN`（默认 1） |
| `ROW_SPAN` | 备注类 = 2（§3.2），其余 1 |
| `NEW_LINE` | `FIELDS.FORM_NEW_LINE`（历史 0 行在用） |
| `SECTION_ID` | 空（全部落入默认节） |
| `CELL_GROUP`/`CELL_ROLE` | `FIELDS.FORM_CELL_GROUP`/`FORM_CELL_ROLE`（并按 §5.3 校验主从成对） |
| `IS_HIDDEN` | `FIELDS.IS_VISIBLE=0` 且非必填、非系统列 → 1；否则 0 |

**推导器必须是纯函数且有单测**（前端画布、后端种子、P0 对拍三处共用同一套规则）。

### 2.5 明细表的版式范围（**本期一次到位**，用户拍板）

明细是 `ErpTable` **网格**，不是"格"版式。故版式表对明细行**只消费两个属性**：

| 属性 | 明细下的语义 |
|---|---|
| `ORDER_NO` | 明细**列顺序**（解决"明细列顺序无法按模块定制"的既有缺口） |
| `IS_HIDDEN` | 明细**列显隐**（模块级，所有人共享） |
| `TAB_NO`/`SPAN`/`ROW_SPAN`/`NEW_LINE`/`SECTION_ID`/`CELL_GROUP`/`CELL_ROLE` | **忽略** |

**与既有列配置的关系**：`SYSQL_FIELDS`/`SYSQL_DEFAULT` 是**列表**（工作台列表）的用户级/系统级列配置，
与明细网格不是同一个东西。优先级定为 **用户级 > 模块级版式 > 系统默认**；**本期先落"模块级版式"这一层**
（用户级覆盖属既有 `SYSQL_*` 机制，不新增）。

## 3. 决策：渲染与布局模型

### 3.1 流式显式装箱（承载任意占位块）

**模型**：整节一张 CSS Grid，每个格的 `grid-row`/`grid-column` 由**前端纯函数显式计算**，
**不使用 CSS 的隐式流（`grid-auto-flow`）**：

```
packFormGrid(cells, columns, fillHoles) -> Array<{ key, col, row, span, rowSpan }>
.erp-form-section-grid { display: grid; grid-template-columns: repeat(var(--erp-form-cols), minmax(0,1fr)); }
.erp-form-cell { grid-column: var(--cell-col) / span var(--cell-span);
                 grid-row:    var(--cell-row) / span var(--cell-row-span); }
```

**为什么显式装箱而不是 CSS 自动流**：

| 方案 | 顺序语义 | Tab 键顺序 | 空洞 |
|---|---|---|---|
| CSS `grid-auto-flow: row` | 严格 | 与视觉一致 | 保留留白 |
| CSS `grid-auto-flow: row dense` | **可能被回填打乱** | **与视觉不一致**（DOM 顺序 = 配置顺序，视觉是 dense 后顺序）→ 键盘用户在表单上"乱跳" | 自动回填 |
| **显式装箱（采纳）** | 严格可控 | **与视觉一致**（DOM 顺序即装箱结果） | 由 `fillHoles` 显式决定 |

用户要的"流式布局：移走一个，后面的自动补上来、自动换行"，本质是**顺序驱动 + 装箱**，
**不需要 dense**；而 `packFormGrid` 纯函数同时满足"补洞"与"顺序可预期"，且可单测、可与后端对拍。

- **默认 `fillHoles = true`**（已拍板：字段移走后不留坑，与用户预期一致）；
- 窄屏降为单列时**放弃显式定位**，退回纯顺序堆叠（每个 cell 独占一行）；
- `buildFormRows`（不支持跨度的旧打包算法）退役，由 `packFormGrid` 取代。

### 3.2 占位块语义（需求 6 + 用户追问）

**允许用户选择任意 `列 × 行` 占位块**（用户 2026-09-25 确认）：

| 维度 | 取值范围 | 说明 |
|---|---|---|
| 列跨度 `SPAN` | **1 .. `MODULES.FORM_COLUMNS`** | 实测模块列数为 3 或 4；"一行四列"即四列布局下占满整行 |
| 行跨度 `ROW_SPAN` | **1 .. 3**（已拍板：上限 3 够用） | 基准行高约 26px，3 行 ≈ 78px；更高的诉求改用 textarea 高度而非格高（避免整行被撑高） |

- 可选组合数 = `FORM_COLUMNS × 3`（三列布局 9 种、四列布局 12 种）；
- 列跨度超过本行剩余空间时，装箱自动推到下一行（无需特殊处理）；
- **备注类**：默认 `SPAN=列数` + `ROW_SPAN=2`；
- **两个诉求必须分开设置**（今天被同一个正则绑死）：
  **"字段要高"** = `ROW_SPAN`；**"字段独占整行"** = `SPAN=列数`；
- **`FORM_COLUMNS` 变更的越界处置**：模块级列数由 4 降到 2 时，已有 `SPAN=3/4` 越界 →
  **读取时截断到列数上限**（不静默改写配置数据），并在设计态显式提示。

> **备注类的隐含规则要显式化**：现状 `formFieldKind.ts` 按字段名正则 `/REMARK$/` 猜"整行 + textarea"，
> 新模型下这仍是**默认推导**，但成为**可覆盖的版式配置**（配了就优先）。

### 3.3 明细不适用本模型

明细继续 `ErpTable` 网格 + §2.5 的列顺序/显隐；不复合格、不页签、不栅格占位。

## 4. 决策：设计态 UX 规格

> 用户要求"这次用户体验一定要做好"。本节是**可实现的交互规格**，不是愿景描述。

### 4.1 进入与退出（需求 3）

- **入口**：统一表单字段标签**右键菜单 →【表单设计】**（与既有「字段设置」并列）；
- **权限门**：无 `FORM_DESIGN_TAG` 的用户，菜单项不渲染；服务端独立鉴权（§5.1）；
- **设计态特征**：**同一套渲染**（所见即所得）、**所有输入控件禁用**（防止被当成填单）、
  顶部出现设计态工具条：`返回表单 | 保存 | 放弃 | 重置 | 撤销 | 重做 | 紧凑 | 套用来源 | 导入 | 导出`；
- **状态是会话级**（不写库）：下次进入默认仍是正常态；
- **退出保护**：有未保存改动时，"放弃"与离开页面都要二次确认。

### 4.2 界面骨架

```
┌─ 设计态工具条：返回表单 | 保存 | 放弃 | 重置 | ↶撤销 ↷重做 | ☑紧凑 | 套用来源 | 导入 导出 ─┐
├──────────────┬──────────────────────────────────┬───────────────┤
│ 字段池        │  页签条：[默认][基本信息][+]        │  属性面板      │
│ ┌──────────┐ │ ────────────────────────────────  │  字段：客户名称 │
│ │ 搜索框    │ │  ┌────────┬────────┬────────┐   │  占位：[▦ 2×1] │
│ │ 表：主/明细│ │  │ 客户编号 │ 客户名称 │ 单别   │   │  复合格：主/从  │
│ │ ○未排 ●全部│ │  ├────────┴────────┼────────┤   │  分节：基本信息 │
│ ├──────────┤ │  │ 订单日期  │  备注（2行高）  │   │  移出表单：[ ]  │
│ │ 字段卡片…  │ │  └───────────┴────────────────┘   │  恢复默认      │
│ └──────────┘ │  （画布 = 真实表单渲染，值用字段名占位）│               │
└──────────────┴──────────────────────────────────┴───────────────┘
```

**预览用结构占位**（用户拍板）：画布不载入真实单据，用**字段名代替值**。
版式（排布/占位/复合格/页签）是真实的，只有值是占位——这正是"所见即所得"要保证的部分，
同时避开了数据权限问题（设计者无需该模块的浏览权）。

### 4.3 页签交互（需求 4）

- 设计态**始终显示页签条**，即使该模块只有一个页签，标签显示 **"默认"**；
- `TAB_NO=1` **常驻且不可删除**（如同电子表格至少一个工作表）；其余页签可删；
- **删除页签**（用户拍板）：其字段**回到 `TAB_NO=1`「默认」页签，不丢字段**；
- **双击标签改名**（写 `MODULE_FORM_TAB.TAB_TITLE`）；**"默认"两字是显示兜底，不写库**；
- 标签右侧 **`+`** 新增页签；**把字段拖到页签标签上** = 移动到该页签（需求 5 的手势版）；
- **设计态与运行态允许不同**：运行态单页签仍隐藏标签条。这是**有意的差异**，须在 ADR 记明，避免被当成 bug。

### 4.4 拖拽交互（需求 1、5）

| 手势 | 语义 |
|---|---|
| 拖到字段**左/右边缘** | 插入到该字段前/后（显示**竖直落点指示线**） |
| 拖到字段**中心区**（约 40% 面积） | **合并为复合格**（受 §4.5 规则约束，不合法的落点不显示该提示） |
| 拖到**页签标签** | 移动到该页签 |
| 拖到**分节标题** | 归入该分节 |
| 拖出画布 / 拖到字段池 | **移出表单**（等价需求 8；受 §4.6 约束的字段不允许） |
| 从字段池拖入画布 | 添加字段（需求 7） |

- 拖拽时显示 **DragOverlay**（半透明卡片）+ 落点指示；
- 拖拽不是唯一手段：**每个字段悬停显示快捷按钮**（← 左移 / → 右移 / ⤒ 上移一行 / ✕ 移除），
  并支持**键盘操作**（Tab 聚焦、方向键微调顺序、Delete 移除）——纯拖拽对精细操作不友好。

### 4.5 占位选择器（需求 6 的 UX 落点）

不要给用户一个"列跨度/行跨度"数字输入框。用**可视矩阵选择器**：

- 点击字段属性面板的「占位」按钮（或右键「占位…」）→ 弹出 `FORM_COLUMNS × 3` 的小方格矩阵；
- 鼠标划过时**实时高亮** `1..n 列 × 1..m 行` 的块，并显示文字如 `2 列 × 1 行`；
- 点击确认；属性面板常显当前占位（如 `▦ 2×1`）；
- 右键菜单同时提供**常用档位快捷项**：整行 / 半行 / 占 2 列 / 占 2 行 / 占 3 行。

### 4.6 移出表单与**不可移出规则**（需求 8 + 精确化）

**移出表单 = `IS_HIDDEN=1`**（**保留该字段的排版属性**，放回时原位回填；不物理删行）。

设计态界面一律称**「移出表单 / 放回表单」**，不用"隐藏"二字——库里的 `IS_HIDDEN` 是**版式层**的事，
与字段维护里的 `FIELDS.IS_VISIBLE=0`（"不显示"）不是一回事：后者运行态根本不渲染
（`FormFieldSelector.Select` 先剔除，版式施加在其后，改版式也变不出来），字段池也不再收录它们。
历史遗留：迁移 252 清掉了库里引用 `IS_VISIBLE=0` 字段的 1042 行版式行（涉及 95 个模块）。

**主表**被移出的字段仍画在画布上（字段代号带删除线 +「已移出表单」角标），右键「放回表单」原位回填。
**明细**被移出的列设计态**不画**（移出后运行态的明细网格里也没有这一列），放回入口是明细面板标题栏
右上角的「添加列」；选回来即原位放回（写回 `IS_HIDDEN=0`，保留原列序）。

> **订正（2026-09-26）**：放回候选的判定基准是**设计器草稿**，不是库里的版式行——库里的行在保存前
> 不反映本次移出/加入，按库算会把刚移出的字段当成"仍在表单里"而排除掉；该表其余字段又都已排进版式时
> （零配置模块的推导默认即"全部已排"），「添加字段/添加列」就此整屏空白、字段放不回去。
> 故**两表被移出的字段都在候选里**：前端按草稿里"显示中的行"生成排除项（`args.exclude`）交服务端裁剪，
> 移出的行因此重新可选、选中即原位放回。上面"明细 `IS_HIDDEN=1` 的行仍算候选"的旧说法以此条为准。

**下列字段的「移出表单」菜单项根本不出现**（用户拍板：必填字段没有移出选项），
且服务端独立拒绝（双保险）；为了让用户**不困惑于"为什么没有这一项"**，
字段上显示**锁图标**并悬停提示原因（"必填字段，始终显示"）：

| # | 类别 | 判定 |
|---|---|---|
| 1 | 模块主表与明细表的**主键列** | `sys.indexes.is_primary_key` |
| 2 | **单据生命周期系统列** | `CREATE_*`/`LAST_UPDATE_*`/`CONFIRM_*`/`FINISHED_*`（ADR-013 规约） |
| 3 | **用户可填的必填字段** | `IS_VERIFY=1`（773 行）∪（`NOT NULL` 且无默认值且用户可填）——与 `check-required-columns.ps1` 同口径 |
| 4 | 服务端保存管线/效果链依赖的字段 | 由 `WorkbenchDefinitionValidator` 的既有字段集判定 |

**例外（必须保留移出能力）**：**服务端自己填充**的字段——审计列、服务端回填的外键（如
`SUPPLIER_LINKMAN.SUPPLIER_ID`，全库 2 行"必填且不显示"之一）。故规则准确表述是
**"用户可填的必填字段"没有移出选项**，不是"所有必填字段"。

> **订正（2026-09-26）· 浏览态位置**：生命周期系统列在浏览态**不再被强制排到表单尾部**，也不再按
> 固定次序排序——与普通字段同等，位置与次序完全由版式决定（页签、分节、顺序、占位都听画板的），
> 只读呈现不变、仍不可移出。原"浏览态把生命周期列挤到表单尾部 + 固定次序"的规则已退役：
> 它让画板上的拖动在运行态不生效，与"设计态与运行态共用同一份装箱规则"（`packFormSections`）矛盾。
> 判据上的后果只有一条：这 10 列在设计态的位置从"摆设"变成"真的生效"，需要挪动它们时直接在画板上拖。
> CI / OWNER / OWNER_G 本来就不在那条规则里，行为不变。

> **附带发现（登记，不属本 ADR 范围）**：全库仅 2 行"必填且隐藏"，其中
> `SFC_PROCEDURE.PERSON_HOUR_UNIT`（工时/件）既非只读、又非虚拟、也无服务端填充依据，疑似误配。

### 4.7 字段池（需求 7）

- 池 = 该模块主表 ∪ 明细表在 `FIELDS` 注册、**但未排进本模块表单**的字段；
- 池**只收 `IS_VISIBLE=1` 的字段**：管理员在字段维护里标记为"不显示"的字段运行态一律不渲染，
  排进版式也不会有任何效果，让它们出现在候选里是误导（§4.6）；
- **已移出表单的字段（主表与明细）都在候选里**——判定按**当前草稿**算：候选 = 该表可排字段 −
  草稿里显示中的行（`args.exclude`，见 §4.6 订正）。主表移出后画布上还能右键放回，明细列表头不画它们，
  字段池是明细列的唯一放回入口；
- **术语必须写死**：这是"把已注册字段放回表单"，**不是新增字段定义**（新增仍走字段维护）；
- 单模块最多 178 个字段 ⇒ 池**必须**支持：关键字搜索 + 按表（主/明细）筛选 + 「未排/全部」切换；
- 权限相关字段（成本/保密/禁止、权限过滤）**在池中可见但带锁图标**，标注"当前用户不可见"。

### 4.8 复合格（三件套）的设计态规则

1. **"合并为复合格"只对「带启用选择器来源」的字段开放**（`FIELD_DATASOURCE` 中存在 `ACTIVE_TAG=1` 的行）——
   否则合出来是个没有选择按钮的空壳，菜单项**禁用并给出理由**；
2. **一个格最多 1 个从字段**（与"三件套"语义一致；多个从字段会让宽度不可控）；
3. 主从必须**同一张表**（`T_ID` 相同）；
4. 从字段默认只读联动；无物理列的从字段是"幽灵字段"（只显示不保存，读取按来源现算）；
5. **字段框上不挂角色角标**：主从成组后同格相邻、从字段无独立标签，本身就一目了然；
   虚拟列（无物理列的伴生显示列）与实体列改由**占位框样式**区分——实体 = 灰底 + 实线边框，
   虚拟 = 淡红底 + 虚线边框（悬停提示另行注明「虚拟列」）。
6. **拆组与"半拆"**：拆开一个复合格 = 置 `CELL_GROUP=NULL`、`CELL_ROLE=0`（设计器右键「移出复合格」，
   服务端保存期同口径），行本身（位置、跨度、页签、隐藏位）保留。**删版式行时必须复核同组的从字段**：
   组的主字段行被删掉后，从字段就成了"没有主字段的孤儿"——渲染侧虽把它降级成独立格显示（绝不丢字段），
   但这是保存期校验的拦截项（`FORM_LAYOUT_COMPANION_WITHOUT_MAIN`），有它的表在设计器里存不了版式，
   门禁第 ① 条同样会拦。历史上清理"引用不显示字段的版式行"就是这样留下了 10 行孤儿（迁移 254 已按本条拆开）。

### 4.9 反馈与防护（UX 细节）

| 场景 | 设计 |
|---|---|
| 保存成功 | Toast + 顶部显示"已生效（所有人可见）"，并自动刷新画布 |
| 保存失败 | **保留用户编辑内容**（已拍板：不清空、不退出版式）+ 定位到出错字段并高亮 + 说明原因（如"客户编号为必填，不能移出表单"） |
| 乐观锁冲突 | 提示"版式已被他人修改"，提供「刷新查看最新」/「覆盖保存」 |
| 画布为空 | 提示"从左侧字段池拖入字段开始设计" |
| 字段池为空 | 提示"本模块所有字段都已在表单中" |
| 撤销/重做 | `Ctrl+Z` / `Ctrl+Y`，覆盖拖拽、移出表单、改页签、改占位全部操作 |
| 键盘 | Tab 遍历字段；方向键微调顺序；Delete 移出表单（不合法时提示原因） |
| 恢复默认 | 右键单字段「恢复该字段默认排版」+ 工具条「重置为默认版式」（§6.4 的逃生门） |

### 4.10 属性归属表（**设计态与字段维护的边界**，防止双写）

| 属性 | 归属 | 位置 |
|---|---|---|
| 页签集合与标题 | **设计态** | `MODULE_FORM_TAB` |
| 顺序、占位（`SPAN`/`ROW_SPAN`）、换行 | **设计态** | `MODULE_FORM_LAYOUT` |
| 复合格主从、分节 | **设计态** | `MODULE_FORM_LAYOUT` |
| 表单/明细内移出（画布上不再排布） | **设计态** | `MODULE_FORM_LAYOUT.IS_HIDDEN` |
| 明细列顺序 | **设计态** | `MODULE_FORM_LAYOUT.ORDER_NO`（明细行） |
| 每行列数 | **设计态**（同一份保存里一并提交）**且**保留在模块管理 | `MODULES.FORM_COLUMNS`（同一真源、两个入口，不算双写；两处都要审计） |
| 动作按钮 | 模块管理 | `MODULES.FORM_BUTTONS`（ADR-018） |
| 字段标签、类型、必填、只读、格式、宽度 | **字段维护** | `FIELDS` |
| 下拉选项枚举 | **字段维护** | `FIELDS.FORM_OPTIONS`（字段语义，非版式） |
| 选择器来源、过滤、回填映射 | **字段维护** | `FIELD_DATASOURCE`（ADR-008） |
| 跨子系统可见性（列表/打印/报表/选择器） | **字段维护** | `FIELDS.IS_VISIBLE` |

**P1 起**：字段维护页的「表单布局」节改为**只读 + 跳转设计态**（否则 `FIELDS.FORM_*` 与新表双写）。

### 4.11 从其它模块套用版式（**只限同主表**）

共用同一主表的模块多是**孪生单据**（`MOC_PRODUCE_M` 被 6 个模块共用、`MOC_GET_M` 被 5 个），
逐个从零拖一遍没有意义。故提供「套用其它模块版式…」。

**决定：只允许从「共用同一张主表」的模块套用**（用户拍板）：

- 下拉**只列主表相同的模块**，并标注"共用主表 `MOC_PRODUCE_M`"；
- 这条路上字段集几乎完全一致，零风险，且恰好覆盖真实需求；
- **跨主表套用不提供入口，且不作为后续项登记**——设计态已把排版门槛降到很低
  （拖拽 + 右键 + 占位矩阵 + 撤销重做），为省这点时间引入"字段投影 + 差异确认"整套机制不划算。

**为什么必须限定来源**（失败模式，供后人理解该限制的必要性）：

| 场景 | 后果 |
|---|---|
| 不同主表 | 源模块字段在目标模块字段集中**不存在** → 版式行全部悬空 |
| 不同主表但字段同名（**最危险**） | `CLIENT_ID`/`REMARK`/`QTY` 等通用名多表都有；会**业务上不该出现**的字段排进表单，且字段本身合法（就在该模块表里），**用户很难发现** |

**同主表套用仍需处理的差异**（在应用前提示，不能静默）：

- **明细表不同** → 明细行全部落空，提示"目标模块无此明细表，N 个明细字段将被忽略"；
- **`FORM_COLUMNS` 不同** → 源 4 列、目标 3 列，`SPAN=4` 的行越界（按 §3.2 截断到 3），提示"N 个字段宽度将被截断"；
- **权限字段不同** → 目标模块被 `denyNew/denyModi` 禁的字段套进来也不下发（权限仍是最终边界，安全，但须提示）。

**共同约束**：

- 套用是**设计态内的一个动作**：可撤销、保存前不落库；
- 套用产生的行仍走 §5.2 的**全部 fail-closed 校验**——套用**绝不能成为绕过校验的旁路**；
- 套用**不改变权限语义**：权限过滤仍在 `FormFieldSelector`，套用不能把不可见字段"变出来"。

### 4.12 明细列的编辑（本期实现，§2.5 的 UX 落点）

明细是网格不是格版式，故**不进画布**，而是画布下方单独一块「明细列」面板（真实表格横铺，观感对齐运行态明细网格）：
**一行表头**（列名 = 运行态列名，承载拖动/点选/右键）+ **一行占位体**（字段代号 = 主表画布同一套占位口径）。
实体/虚拟的区分落在占位框上（§4.8 第 5 条），表头不必再挂角标。

| 交互 | 说明 |
|---|---|
| 排序 | 表头内拖拽排序；顺序即明细列顺序（写明细行的 `ORDER_NO`） |
| 移出/放回 | 右键「移出表单」（写明细行的 `IS_HIDDEN`）；移出后不再出现在表头上（§4.6），放回入口是标题栏「添加列」；受 §4.6 保护的列该项禁用 + 锁图标 |
| 增删 | 面板标题栏右上角「添加列」→ 统一选择器（来源是**明细表**的字段池；已移出表单的列也在池里，选回来即原位放回） |
| 不支持 | 明细**没有**页签、分节、复合格、占位跨度（§2.5）——面板上不出现这些入口，避免用户找不到效果 |

明细列顺序与 `SYSQL_FIELDS`（列表的用户级列配置）是两件事；本期只写**模块级**（§2.5）。

## 5. 决策：校验、权限与门禁

### 5.1 权限（**复核结论：不新增权限位，复用已有位**）

用户要求"新增【表单设计】粒度，与模块配置同级，不要塞进 `CanModuleConfig`"。
库内取证表明**这个位已经存在**：`SYSDD`/`SYSDH.FORM_DESIGN_TAG`（完整设计）与
`FORM_ADJUST_TAG`（微调），由迁移 `031` 建立（ADR-010 决策 4 的三档权限位），
**已接线但只服务于报表版式设计器**（`ReportFormLayoutRepository.GetDesignerModeAsync`：
个人覆盖组、组布尔 OR；`LayoutDesignerController`；`LayoutDesignerPage`）。

**决定**：

- **复用 `FORM_DESIGN_TAG` 作为"版式完整设计权"**，本 ADR 把它的作用域从"报表版式"扩展为
  **"版式设计（报表版式 + 表单版式）"**；与 `MODULE_CONFIG_TAG`（行为动作/校验规则/自定义按钮/发布）
  **平级且互不包含**——正是用户要的粒度；
- **`FORM_ADJUST_TAG`（微调档）判定为多余，一并退役**（用户拍板）；
- **不新增数据库列**：名字（`FORM_*`）、语义（版式设计）、粒度（与模块配置平级）三者本已吻合。

**为什么"微调档"是多余的（三条理由）**：

1. **它服务的角色现在不存在**——ADR-010 设想微调是给"客户维护人员"（角色③）用的；
   本项目**无真实用户、无上线存量**，现在做等于对着一个想象出来的角色设计权限；
2. **它不是一条安全边界，只是"防手滑"**——微调档禁止增删字段，却允许改顺序与占位，
   "把必填字段排到最后、把备注压到看不见"这类破坏它同样能干；
3. **设计态本身已把门槛降得很低**（拖拽 + 右键 + 占位矩阵 + 撤销重做），
   多一档的收益，抵不上多维护一套受限模式 + 一套保存期基线校验的成本。

**退役范围（牵连面，实测）**：`FORM_ADJUST_TAG` 目前**只被报表版式设计器消费**（ADR-010），
而报表版式三表 `REPORT_FORM_LAYOUT`/`_VERSION`/`_BINDING` **实测 0 行、从未真实启用**。牵连 **8 处**：

| 层 | 位置 |
|---|---|
| 库 | `SYSDD`/`SYSDH.FORM_ADJUST_TAG`（迁移 `031` 建 + 扩展属性）→ **DROP COLUMN** |
| 后端模型 | `EOS.API/Models/LayoutDesignerModels.cs`（`LayoutDesignerMode(CanDesign, CanAdjust)` 收敛为单值） |
| 后端仓储 | `EOS.API/Data/ReportFormLayoutRepository.cs`（个人/组两段 SQL 去掉 `CAN_ADJUST`） |
| 后端控制器 | `EOS.API/Controllers/LayoutDesignerController.cs`（门判定 5 处 + 微调约束段 `:250-289`） |
| 前端 | `features/layout-designer/`：`types.ts` / `LayoutDesignerPage.tsx`（`simpleMode`）/ `LayerPanel.tsx` / `PropertyPanel.tsx` |
| 测试 | `LayoutDesignerPage.test.tsx` 的「微调模式」用例 |
| 文档 | ADR-010「角色分级」与决策 4/5 需登记修订 |
| 权限界面 | `RightsAdminRepository` 只接 `FORM_DESIGN_TAG` 一列（不接 `FORM_ADJUST_TAG`） |

> 该退役**跨越 ADR-010 的域**（报表版式），**已拍板执行**（用户 2026-09-25 选 B），纳入 P4 减负批次。

**必须补齐的三处接线缺口**（否则功能不可用）：

| # | 缺口 | 位置 |
|---|---|---|
| 1 | **权限管理界面勾不了这个位** | `RightsAdminRepository` 的读写列白名单（第 20、214 行的数组）+ `RightsAdminModels` 输入/输出 + 前端权限矩阵勾选框。现状只有脚本能授（2026-08-31 的 ADMIN 批量授权即走脚本） |
| 2 | **判定逻辑不能写第二份** | 把 `ReportFormLayoutRepository` 里"个人覆盖组、组布尔 OR"的两段 SQL 抽成**共享解析器**（AGENTS.md 点名的债根因：同一安全语义两份实现），表单版式与报表版式共用 |
| 3 | **模块级读侧门** | 表单定义接口需下发 `CanFormDesign`（供前端决定是否渲染右键入口），服务端写端点独立鉴权（最终边界，无豁免） |

其余既定纪律：
- 写端点须满足 ADR-016 决策 13 B5 的配置类写端点准入门槛（幂等键 / 审计同事务）；
- **版式只做减法与排布，永不做加法**：版式不能把权限过滤掉的字段"变出来"，也不能绕过
  禁止字段/成本/保密过滤。
- **`FormFieldSelector` 的成本/保密/禁止字段过滤、`denyNew/denyModi`、`DATA_FILTER`、`EXEC_TAG`
  一律保持原样**——版式表只决定"排在哪儿、藏没藏"，**不参与授权**。

### 5.2 服务端 fail-closed 校验（保存时）

1. `F_ID` 必须属于该模块的字段集（主表 ∪ 明细表，且已在 `FIELDS` 注册）；
2. `TAB_NO` 必须存在于 `MODULE_FORM_TAB`（或为 1）；
3. `SPAN ∈ [1, MODULES.FORM_COLUMNS]`，`ROW_SPAN ∈ [1,3]`；
4. **复合格主从成对**：`CELL_ROLE=2` 的 `CELL_GROUP` 必须有同组 `CELL_ROLE=1`；同组主字段唯一；
5. `CELL_GROUP` 不得被 ≥2 个主字段共用（分节由 `SECTION_ID` 显式表达，组名重名直接拒绝）；
6. 不得违反 §4.6 的不可移除规则（用户可填的必填字段被隐藏 → 拒绝）；
7. 复合格主字段必须有启用来源（§4.8）；一格的从字段 ≤1；
8. 页签不得为空；**若提交页签集合，必须包含 `TAB_NO=1`**，且不允许删除它（删其它页签时其字段回落到此，§4.3）。

### 5.3 门禁脚本（新增 `scripts/check-form-layout.ps1`，需连库，带 `-SelfTest` 正反自检）

- 主从成对（**现存 4 处孤儿从字段即首个 FAIL 目标**）；
- 版式引用的 `(M_IDX, T_ID, F_ID)` 三要素在库内真实存在（幽灵引用）；
- 越界字段（字段不属于该模块的表）；
- **用户可填的必填字段被隐藏**（与 `check-required-columns.ps1` 联动，同口径）；
- `SPAN`/`ROW_SPAN` 越界；
- 已有版式的模块，其快照是否落后（与 `check-snapshot-staleness.ps1` 同口径）。

## 6. 决策：保存与生效

### 6.1 一次保存 = 整份表单版式的全量替换

- 提交是**该模块版式的完整文档**（所有页签 + 所有字段行），不是增量 patch；
- 理由：拖拽天然是"整份文档"编辑；全量替换避免大量零碎 diff 与并发合并问题，且与 §2.3 语义一致；
- 实现沿用既有 `ReplaceChoosersAsync` 的做法：**同一事务内 DELETE + INSERT**（`FieldAdminRepository.cs:789`）。

### 6.2 保存即生效（无需发布，用户拍板）

- 写 `MODULE_FORM_LAYOUT`/`MODULE_FORM_TAB` → **模块级标脏** → **同请求内重发布该模块快照** → 响应返回新版本；
- 脏标记粒度从 `MarkDirtyForTableAsync`（表级，会波及共用表的全部模块）改为
  **`MarkDirtyAsync(moduleId)`**（模块级，更准）；
- **这是对既有"字段维护只标脏、须人工发布"模型的有意例外**（版式风险低、且"所见即所得"要求）。
  **例外不等于绕过门禁**：重发布仍跑发布校验器，任一项失败则**整笔回滚、不落库**，失败原因返回设计态。

### 6.3 并发口径（用户拍板：不做定义版本校验）

- **设计者 vs 正在填单的用户**：不新增提交期"定义版本"校验。谁先保存谁生效——
  设计者先保存，用户受新版式约束；用户先保存，用户不受新版式约束。（用户判断：两者同时点击的概率不存在）
- **设计者 vs 设计者**：**保留乐观锁**（提交携带读取时的 `UPDATED_AT` 快照，服务端比对；
  沿用 `FieldAdminRepository` 的 `SameInput` 先例），冲突时提示并给出「刷新查看」/「覆盖保存」。
  这是防"覆盖掉别人刚做的改动"，与"用户填单"无关，成本极低。
- **幂等键**：写端点强制（ADR-006 既定契约）。

### 6.4 不做版本历史表 ⇒ 由审计与"重置"承担

- 每次保存把编译后的 `LAYOUT_JSON` 写入既有 `AUDIT_EVENT`/`AUDIT_FIELD_CHANGE`（配置类写端点本就要求审计同事务），
  历史版式因此**仍可追溯、可人工恢复**；
- 设计态提供**「重置为默认版式」**（回到 §2.4 的推导默认）作为主要逃生门。

### 7.2 `MODULES` 逐列处置

| 列 | 处置 |
|---|---|

| `FORM_BUTTONS` | **不动**（ADR-018 动作按钮域） |

### 7.3 退役执行纪律（**强制**）

列退役前必须完成**三方引用核查**（AGENTS.md 既有规约）：

1. **C# 引用**：`WorkbenchDefinitionBuilder`、`FieldAdminRepository`、`WorkbenchDefinitionValidator`、

### 7.4 旧表单相关对象盘点

|---|---|---|
| `MODULES.FORM_TABS` | 自造分隔符字符串（格式缺陷） | 迁入 `MODULE_FORM_TAB` |
| `REPORT_FORM_LAYOUT` / `_VERSION` / `_BINDING` | 三表 **0 行**，报表版式设计器未真实启用 | **借鉴形态不合并域**；其权限位（`FORM_DESIGN_TAG`）由本 ADR **复用**（§5.1） |
| `SYSQL_FIELDS`(12294) / `SYSQL_DEFAULT`(5358) / `SYSQL_CONDITION` | **列表**的列选择/顺序/条件 | **不动**；"不做"清单明确禁止把"拖拽列表列顺序"塞进本设计器 |
| `WFFORM` / `WFFORM_FLOW` | 旧流程表单残留（1/2 行），代码零引用 | 登记为**退役候选**（另行处理） |
| `FORM_CHOOSER_SOURCE_MEMO`（迁移 214） | 选择器来源记忆，与版式无关 | 不动 |

### 7.5 模块 ID 列统一为 `M_IDX`（用户拍板：不再区分新旧系统）

- **新表一律 `M_IDX`**（`MODULE_FORM_LAYOUT` / `MODULE_FORM_TAB`）；
- **存量自建表改名**：`WORKBENCH_DEFINITION_SNAPSHOT`、`WORKBENCH_MODULE_DIRTY`、`WORKBENCH_IDEMPOTENCY`、
  `MODULE_BUSINESS_ACTION`、`MODULE_VALIDATION_RULE`、`ATTACHMENT`、`AUDIT_EVENT`、`REPORT_INBOX`、
  `REPORT_SUBSCRIPTION`、`FORM_CHOOSER_SOURCE_MEMO` 的 `MODULE_ID` → `M_IDX`；
- 做法沿用迁移 `020`（`FIELDS_CHOOSER` → `FIELD_DATASOURCE` 连同 PK/唯一约束/FK/索引/默认约束一并 `sp_rename`）的既有模式；
- 影响面：C# 读写的列名字符串、脚本与测试夹具、已发布快照 JSON（若含 `moduleId` 属性则不受影响，
  但**发布/回填脚本里的 SQL 列名要改**）；
- **单独立批次**执行，不与本 ADR 的表结构混提。

## 8. 不做（边界，防止滑向低代码）

- ❌ **不新增字段定义**：不能在设计态里给表加列、不能改类型/长度/校验/默认值/取数（仍走字段维护）；
- ❌ **不定义新控件类型**：设计态只排布既有变体（text/decimal/date/datetime/textarea/select/checkbox）；
- ❌ **不做明细"格"版式**：明细只做列顺序与显隐（§2.5）；
- ❌ **不做跨主表套用版式**：套用来源只限共用同一主表的模块，且不登记为后续项（§4.11）；
- ❌ **不做版本历史表**（由 §6.4 承担）；
- ❌ **不做提交期"定义版本"校验**（§6.3）；
- ❌ **不做按用户/按角色/按客户的版式**（表结构预留维度，本期不实现）；
- ❌ **不做自由画布**（绝对定位、任意坐标）——那是报表版式（ADR-010）的形态；
- ❌ **不接管打印/导出布局**；
- ❌ **不接管列表列顺序/列宽**（`SYSQL_*` / `DISPLAY_LENGTH` 域）。

### 13.4 JSON 形状

**编译产物**（进 `DEFINITION_JSON` 的 `formLayout` 段）：

```json
{
  "columns": 3,
  "tabs": [{ "no": 1, "title": "" }],
  "master": [{ "key": "CLIENT_ID", "tabNo": 1, "orderNo": 1, "span": 2, "rowSpan": 1,
               "newLine": false, "sectionId": null, "cellGroup": "CLIENT_ID", "cellRole": 1, "hidden": false }],
  "detail": [{ "key": "PRO_NO", "orderNo": 1, "hidden": false }]
}
```

**保存请求（PUT）**：同形状 + `baseUpdatedAt` + `idempotencyKey`。约定：

- `orderNo` **由服务端按提交顺序重排为 1..n**（避免碎片）；
- **明细行的 `TAB_NO/SPAN/ROW_SPAN/NEW_LINE/CELL_ROLE` 固定写 `1/1/1/0/0`**，`SECTION_ID`/`CELL_GROUP` 写 `NULL`——这些列是 `NOT NULL`，必须显式赋值，否则实现者会被约束绊住；
- **定制判定按 `(M_IDX, T_ID)` 分别进行**：主表有行则主表已定制，明细有行则明细已定制。**不要**用"该模块有无任何行"统一判定——否则只有明细行的模块会把主表字段整批判成"未加入表单"而消失。

### 13.6 纯函数规格（两份，都必须单测）

**① 默认推导器** `deriveDefaultLayout(fields, columns) → LayoutDoc`
逐条实现 §2.4 的规则表。**前后端共用同一套规则**：前端用于画布预览，后端用于生成种子。

**② 装箱** `packFormGrid(cells, columns, fillHoles) → Array<{key, col, row, span, rowSpan}>`

```
row = 0; cursor = 0
for cell in cells:
    if cell.newLine and cursor > 0: row++; cursor = 0
    if cell.span > columns - cursor: row++; cursor = 0      // 本行放不下 → 另起一行
    place(cell, col = cursor + 1, row = row + 1)
    cursor += cell.span
    if cursor >= columns: row++; cursor = 0
if fillHoles:
    对每一行残留的空洞，把后续能塞进的字段提前填入（保持相对顺序不变）
```

- **节内独立装箱**：每节一张网格，`row` 从 1 起算（层级：页签 > 分节 > 行 > 格，§2.2）；
- `fillHoles` 默认 `true`（§3.1 已拍板）；
- **窄屏（单列）放弃显式定位**，退回顺序堆叠。

### 订正 1 · 主表字段列跨度映射错误（**全局观感回退，已订正**）

- **现象**：统一表单从「每行 4 个字段」退化为「每行 2 个字段」，表单高度翻倍，影响全部 261 个已定制模块。
- **根因**：物化版式时用 `旧 FORM_SPAN × (列数/2)` 把字段级旧语义映射到子列——旧 `FORM_SPAN=1` 被当成
  "半行"映射为 2 子列。但旧渲染器里 `.erp-form-cell` **不吃 `grid-column: span`**，每格恒占 1 列，
  旧表单实际是**每行 4 个字段**；映射应当 `旧 span=1 → 1 子列`、`旧 span=2（整行独占）→ 列数`。
  该实现与其自身注释（"默认成 2 会让表单从每行 4 个变成每行 2 个，属纯粹的观感回退"）**自相矛盾**。
- **订正**：迁移 `247_form_layout_span_and_backfill.sql` 把主表普通字段的 `SPAN` 由 2 归一到 1。
  实测订正后：模块 `1406` = 30 个 `span=1` + 1 个整行备注，`110101` = 20 个 `span=1` + 1 个整行备注。

### 订正 2 · 两个模块的版式在 P4 删列后静默退化（**已回放**）

- **现象**：`110101 公司基本资料` 与 `110311 物料主货位` 的版式段为空——表单缺页签、缺复合格、
  备注不再整行（`110101` 的 `REMARK` 由 2 列宽降为 1 列宽）。
- **根因**：P4 先关闭"无版式行则按字段级配置推导"的回落，而删列棘轮把这两个模块**当例外放行**
  （`110101` 因 4 个字段不属该表、`110311` 因搬运时账号无设计权），没有在删列前把它们物化。
- **订正**：同一迁移从 `WORKBENCH_DEFINITION_SNAPSHOT` 的**历史版本**回放（最新一个含非空 `FormLayout`
  的版本），跨度按订正 1 的口径重算。实测 `110101` 25 行、`110311` 5 行，全库 **263/263** 模块均有版式行。

### 订正 3 · 对拍判据有两处失明（**已修**）

初版复核曾写成"归一化把 `span`/`cellGroup`/`tabNo` 等整批剔除"——**这个说法不准确**，实测其
`IgnoredKeys` 只含 `formlayout`/`canformdesign`/`rowspan`/`sectionid`，**`span` 本来就在比对**。
真实缺陷是两条：

1. **`rowSpan`/`sectionId` 被整键剔除** —— 这两个键是 ADR-022 新增的，但**取值**才是语义所在。
   整键剔除让"行高 1→2""新增分节"这类变化**完全不可见**；正确做法是**取值等于默认值才视同缺省剔除**
   （`rowSpan=1`、`sectionId=null`），这样旧基线仍可比，而真变化照样抓到。
2. **它是一次性工具**：`-Capture` 存基线、`-Compare` 事后比对，而它只在 P0 跑过一次，
   P4 物化与回落关闭之后**没有再跑**——订正 1 的 `span` 回归因此从未被度量。
   （即便重跑，当时 `span` 也已在比对范围内，本可发现。）

**已修**（`scripts/compare-form-layout-parity.ps1`）：

- `IgnoredKeys` 收窄为 `formlayout`/`canformdesign`；新增 `DefaultedKeys`（`rowspan=1`、`sectionid=''`）
  按**取值**放行；
- 新增 **`-SelfTest` 判别力自检**（不连库不连 API）：整体新增段/标志/默认值键必须放行，
  **列跨度、行跨度、复合格、页签、字段顺序五类变化必须逐条命中**。
  已做**故障注入**验证：把 `rowspan` 放回 `IgnoredKeys` 后自检立即
  `FAIL ROWSPAN_CHANGED(期望 diff，实得 same)`——判别力是真的。

### 订正 4 · `MODULES.FORM_COLUMNS` 退役追认（§11 决策 19）

- 本文原定"保留"，实施时退役：三处读点（`WorkbenchDefinitionBuilder` 按列序号取值、`MenuAdminRepository`
  模块列、设计态仓储）全部摘除后删列，统一表单固定一行四列。
- **追认依据**：前端 `FormEditorPage` 本就硬编码 4 列、API 的 `columns` 字段无消费方，删除的是**死配置**。
  遗留影响：`FormDefinition.Columns` 现固定返回 `2`（记录默认值），**运行时不消费**，属已知无害差异。

### 订正 5 · 门禁补第 ⑦ 条（**这次的漏口变成断言**）

`check-form-layout.ps1` 增断言：**持当前快照的模块必须都有版式行**。原第六条只校验"已定制模块的
快照是否反映版式"，对"一条版式行都没有"的模块**完全不覆盖**——订正 2 正是从这个口子漏过去的。
自检判别力同步扩到五项（`SNAPSHOT_NO_LAYOUT=1`）。

### 订正 6 · 模块级每行列数回归（迁移 319，**本条推翻订正 4 的结论**）

订正 4 追认"全局固定一行四列"的依据是"前端本就硬编码 4 列、`FormDefinition.Columns` 无消费方"——
**该依据只说明当时没有消费者，不构成"列数不该可配"的判断**。模块字段疏密差异大（有的模块三五个字段、
有的几十个），一律四列让前者空旷、后者拥挤，用户 2026-10-05 拍板把列数交回模块元数据：

- 新列 `MODULES.FORM_LAYOUT_COLUMNS`（1..4，NULL = 4）；**不复活**已退役的同名旧列——
  旧列属字段级排布时代的分栏，新列只表达"本模块表单一行排几列"；
- 三处消费点同源：运行态表单定义（`FormDefinition.Columns`）、设计态（`FormLayoutDefinition.Columns`）、
  保存期校验（`FormLayoutValidator` 按列数判 `SPAN` 越界）；门禁 `check-form-layout.ps1` 同步按各模块列数判；
- 本文 §3.2 关于"列跨度 1..模块列数"与"列数调小后越界如何处置"的口径**依然成立**，
  只是列名换成 `FORM_LAYOUT_COLUMNS`（读取侧照旧夹取到列数上限、不静默改写配置数据）。

同批还加了模块级**打开方式**（`FORM_OPEN_MODE`：本页签 / 新页签 / 弹窗 + 弹窗宽高）：
它属"表单以什么形态打开"，与版式无关，见 [`docs/guide/42-统一表单.md`](../guide/42-统一表单.md)。

### 订正 7 · 呈现配置归设计器，画板按窗体尺寸摆（2026-10-06）

订正 6 把四列呈现配置加回了模块元数据，但配置入口当时仍在菜单管理 2301 的「统一表单」页签，
于是它落在"元数据草稿 → 人工点发布"那条链上：**改完不发布就不生效**（用户实测 110102 配了弹窗、
保存后打开仍是本页签，来问是不是 bug）。订正如下，两条：

1. **呈现配置的配置与保存入口移进表单设计器**（设计器里一行「表单呈现」：打开方式 / 弹窗宽高 / 栅格列数）。
   设计器的保存本就走"**同一请求内重发布**"（版式保存即生效，见本文 §交付与 `FormLayoutRepository` 的
   类注释），呈现配置随版式**同一笔提交**⇒ 保存即生效。2301 那条链不再写这四列（避免陈旧草稿覆盖
   设计器刚配的值），只留只读摘要 + 进入设计器的按钮。**快照仍是运行期唯一契约**——只是"重发布"这一步
   （> **收尾（2026-10-06，同日）**：那份只读摘要连页签一起删了——它既不能配、又得同步两个来处的口径，
   用户判定"完全没有存在的必要"（决策清单 #143）。呈现配置从此只有设计器一处入口：单据表单页的
   字段设置菜单 ›【表单设计】，需 `FORM_DESIGN_TAG`；`MenuAdminModule` 也不再投影那三列）
   由设计器代劳，不是绕过它；两侧校验照旧（库内 CHECK + 设计器端点的白名单/区间校验）。
2. **设计器画板尺寸＝运行态容器尺寸**：打开方式为弹窗时，画板锁到模块声明的窗体宽（高度取下限，
   内容超出时设计区继续滚动——拖拽的滚动补偿挂在设计区上）。这是一条**所见即所得**的补全：
   此前"设计态按整页排、运行态按 900 宽的窗体排"，同一份版式在两处的折行位置不同。

### 订正 8 · 列数下放到页签 + 呈现入口归位 + 弹窗内摆页签（迁移 319，2026-10-06）

> 本节与订正 9 当初各是一份迁移（321 / 322）。提交前把 319+321+322 **折成了一份终态脚本**
> `319_form_presentation.sql`——模块级只留打开方式与窗体尺寸，一行几列一次落到页签表的

用户 2026-10-06 一次提了四件相关的观感/结构问题，收口如下（决策清单 #141）：

1. **布局列数从"模块级"下放到"页签级"**（迁移 321 新增 `MODULE_FORM_TAB.LAYOUT_COLUMNS`；折进 319 后该列一次到位为 NOT NULL DEFAULT 4）：
   订正 6 把列数交回模块元数据，但一个模块往往只有一两个页签、字段疏密差异却在**页签之间**——
   页签 1 一行两列、页签 2 一行一列的诉求，模块级单值表达不了。模块那一列
   （`MODULES.FORM_LAYOUT_COLUMNS`）退化为**未声明页签的兜底列数 + 新页签初值**，不再是呈现配置的一项。
   三处消费点（运行态表单定义、设计态画板、保存期校验）改按**行所属页签**取列数
   （`FormLayoutDerivation.ResolveTabColumns` / 前端 `resolveTabColumns`）；门禁 `check-form-layout` 的
   越界判据同样按各页签判（自检判别力扩到 4 例：无声明 / 页签声明 2 列 / 页签声明 1 列 / 同模块两个页签各判各的）。

2. **调整即合规**：订正 6 的"列数改小后不静默改写跨度、交由校验列出"**被用户推翻**——
   现在改页签列数时**当场把该页签内越界的跨度夹到新列数**（`setTabColumns`），服务端写入侧同口径。
   迁移 321 顺带把存量越界行一并夹齐（本机实测：回填 1 行、夹取 1 行），
   所以"库内数据"与"运行态读取侧的夹取结果"从此一致（新库无存量，这段数据修正只在既有库上有意义）。

4. **弹窗内摆页签**：推翻 2026-10-05 那版"弹窗里不摆页签、所有页签字段挤在同一栅格"的做法——
