- 日期：2026-08-07
- 决策者：项目团队

## 背景

蓝图定位已更正（2026-08-07）：`EOS.Client` 是现代化 ERP 的 Agent 驱动客户端，`EOS.Web` 是传统工作台，二者共用 `EOS.API`，本质是一套系统。据此界定 AgentRuntime 演进方向：服务端自动化、会话/确认点持久化、审计留痕服务端化，均需要 AgentRuntime 脱离桌面进程独立运行。

## 已定决策

### 1. 独立进程宿主：有必要

AgentRuntime 需要独立于 `EOS.Client` 桌面进程运行（7×24、服务端自动化、会话/确认点可持久化、审计不落在用户本机）。此"独立"指服务端自动化场景出现时的宿主形态，不要求当前立即新建进程。

### 2. 部署形态（已撤销）：Gateway 与 AgentRuntime 合并为一个 AI 平台服务进程

- 曾采纳"OpenClaw 式单平台服务"并实施 `EOS.AgentServer` 合并宿主（2026-08-07 试验性实现）。
- **撤销**：合并部署决策于 2026-08-07 撤销，`EOS.AgentServer` 已移除，`EOS.Gateway` 恢复为独立 ASP.NET Core 进程（5288），`EOS.AgentRuntime` 继续以类库嵌入 `EOS.Client`。
- 撤销原因：
  - 合并的唯一当下收益是"少一个进程"；同进程内 Runtime 无真实工作负载（空挂），且为保留职责边界仍走 HTTP 回路，导致"形合神不合"——既没有独立进程的隔离收益，也没有进程内协作的收益；
  - 服务端自动化场景尚未出现，为未来不确定需求提前合并，违反蓝图"条件触发、不提前实现"的原则；
  - "OpenClaw 式合并"套错了位置：编排器（Runtime）实际住在桌面客户端，网关进程内再放一个 Runtime 是多余的第二个编排器。
- 后续方向：`EOS.Gateway` 与未来的服务端 `EOS.AgentRuntime` 宿主都可以做成系统服务，通过统一工具进行开关/重启管理；是否共宿由第一个自动化场景的真实需求决定。
- 与 ADR-002 的关系：ADR-002 反对"网关承担编排导致职责混同"；撤销合并后网关保持单一职责，与 ADR-002 一致。

### 3. 身份：交互场景维持 Cookie 会话；服务凭据 + 用户委托延后

- **服务凭据**：程序身份（如 `X-EOS-Service-Key`），证明"我是被授权的系统服务"；
- **用户委托**：代表身份（如 `X-EOS-Delegated-User`），声明"按哪个用户的权限办事"；
- 两者搭配解决"没有用户登录却要执行"的场景（服务端定时任务/自动化）。
- **交互场景**（用户登录 `EOS.Client` → 使用 AI）：服务端经会话（`EOS.Auth` Cookie）已知用户身份，无需服务凭据/委托；当前"客户端转发 Cookie"方案正确，继续使用。
- 结论：服务凭据 + 用户委托在出现第一个无交互会话的服务端自动化场景时实施，届时解除技术债 1/2。
